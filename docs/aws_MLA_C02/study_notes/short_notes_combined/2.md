# Skill 2.1.1: Evaluate and select appropriate FMs from Amazon Bedrock based on task requirements and performance criteria

## Task 2.1: ML Model and Foundation Model (FM) Development - Choose appropriate modeling approaches for ML and AI solutions

---

## FM Selection Decision Matrix

| Selection Criteria | Primary Metrics | Evaluation Method | Bedrock Tooling |
|---|---|---|---|
| **Output Quality** | Accuracy, relevance, fluency | Comparative benchmarking | Bedrock Model Evaluation (automatic + human) |
| **Latency** | Time-to-first-token, total response time | Load testing with real payloads | CloudWatch metrics, Provisioned Throughput |
| **Cost** | $ per 1K tokens (input/output) | Monthly usage projections | Bedrock Pricing APIs, CloudWatch billing |
| **Domain Fit** | Terminology, reasoning depth | Custom eval prompts on domain corpus | Model Evaluation with curated datasets |
| **Context Limits** | Max tokens supported | Test with representative document lengths | Model spec sheets (e.g., Claude 200K) |

> **Hard Rule:** Provisioned Throughput on Bedrock is the ONLY way to meet hard latency SLAs at scale. On-demand InvokeModel and InvokeModelWithResponseStream do not guarantee throughput.

---

## Amazon Bedrock Model Families & Characteristics

| Model Family | Provider | Strengths | Best Fit | Key Distractors |
|---|---|---|---|---|
| **Claude (3.x)** | Anthropic | Long context (200K), reasoning, tool use | Document analysis, multi-step reasoning | Not the cheapest for simple classification |
| **Titan** | AWS | Cost-efficient, fine-tuning ready | Embeddings, text generation at scale | Weaker reasoning vs. Claude/Llama |
| **Llama 3.x** | Meta | Open-weight, customizable | On-prem parity, fine-tuning flexibility | Requires more prompt tuning |
| **Cohere Command** | Cohere | Strong on structured output, embeddings | Entity extraction, RAG summarization | Smaller ecosystem compared to Claude |
| **Mistral** | Mistral AI | Efficient, strong multilingual | European language tasks, edge deployments | Performance drops on large context |
| **AI21 Jurassic** | AI21 Labs | Long-form generation, factual writing | Content creation, narrative tasks | Higher cost per token than Titan |

> **Exam Gotcha:** Selecting "the largest/most powerful model" is a **distractor** when requirements mention cost controls or simple classification tasks. Smaller models (Titan, Llama 3 8B) often deliver similar accuracy at a fraction of cost.

---

## Core Bedrock APIs & Boto3 Nuances

### Invocation Patterns

| API Method | Use Case | Streaming? | Key Parameter Notes |
|---|---|---|---|
| **`InvokeModel`** | Single synchronous request | No | `body` format varies by provider (JSON vs. prompt strings) |
| **`InvokeModelWithResponseStream`** | Real-time token-by-token display | Yes | Requires chunk handling logic; lower perceived latency |
| **`Converse`** | Provider-agnostic chat API | Yes | Supports tool use, system prompts, multi-turn context |
| **`CreateModelInvocationJob`** | Batch processing (S3 input/output) | No | Async; required for large-scale evaluations |

### Key Boto3 Parameter Considerations

- **`inferenceConfig` vs. provider-specific params** — Use `maxTokens`, `temperature`, `topP` inside `inferenceConfig` when using `Converse` API; provider-specific bodies may use `max_tokens_to_sample`.
- **`system` vs. `messages`** — The `system` parameter sets behavior/guardrails; `messages` contain the conversation history.
- **`stopSequences`** — Control token generation halting to prevent hallucinations or runaway outputs.

---

## Model Evaluation Patterns

### Evaluation Workflow

```
1. Curate Golden Dataset (domain-representative prompts)
2. Choose Evaluation Mode:
   ├─ Automatic: ROUGE, BLEU, F1 (ground truth required)
   └─ Human: Likert scales, pairwise comparison (LLM-as-judge)
3. Run on Multiple Candidate Models
4. Compare Quality × Latency × Cost
5. Select Winner and Document Trade-offs
```

| Evaluation Type | When to Use | Bedrock Integration |
|---|---|---|
| **Automatic Metrics** | Established benchmarks, deterministic outputs | Bedrock Model Evaluation built-in scoring |
| **LLM-as-Judge** | Qualitative judgments (style, coherence) | Custom scoring prompts via Bedrock |
| **Human Review** | Safety-critical, subjective quality | Bedrock Model Evaluation human workflows (SageMaker Ground Truth) |
| **A/B Testing in Production** | Real-world usage patterns | Custom routing with API Gateway + Lambda |

> **Hard Rule:** Evaluation datasets **must** represent production data distribution. Evaluation on synthetic or mismatched data produces inflated or misleading performance metrics.

---

## Security & Compliance Configuration

| Requirement | Bedrock Configuration | Notes |
|---|---|---|
| **VPC Isolation** | Bedrock VPC interface endpoints | Private access without internet egress |
| **Data Encryption** | SSE-KMS for S3 data sources; TLS 1.2+ in transit | Bedrock does not train on your prompts/responses by default |
| **Model Invocation Logging** | Enable in Bedrock settings → CloudWatch/S3 | Captures full prompts, responses, token usage |
| **Cross-Region Redundancy** | Multi-region Bedrock endpoints | Not all models available in all regions |
| **Content Filtering** | Bedrock Guardrails | Apply before/after model invocation |

> **Exam Gotcha:** Bedrock **does not retain or store** your prompts and responses for model improvement by default, but you **must opt out explicitly** on some managed features. Logging should be consciously enabled for compliance.

---

## Cost Optimization Strategies

| Strategy | Use Case | Implementation |
|---|---|---|
| **Model Cascade / Routing** | Route simple requests to small models | API Gateway + Lambda series, or Bedrock Model Invocation policies |
| **Batch Mode** | Non-urgent processing | `CreateModelInvocationJob` (up to 50K requests/job) |
| **Provisioned Throughput** | Predictable high-volume, low-latency | Commit hourly units; best for production workloads |
| **Caching Common Responses** | Repeat queries | ElastiCache or DAX in front of Bedrock calls |
| **Prompt Compression** | Reduce input tokens | Summarize history, truncate retrieved docs |

---

## Common Anti-Patterns & Distractor Traps

1. **Building custom models when Bedrock FMs suffice** — Managed FMs remove infrastructure overhead, access latency-tuning options, and offer built-in evaluation tooling.
2. **Choosing a large model "for safety"** — Without benchmarked evidence, smaller models often meet quality requirements at 10–20× lower cost.
3. **Ignoring tokenization differences** — The same input can produce different token counts across models, invalidating per-request cost comparisons if not normalized.
4. **Fine-tuning without exhausting prompt engineering** — Prompt-based optimizations (few-shot examples, detailed system prompts) resolve most terminology/format gaps at zero additional cost.
5. **Treating model selection as a one-time decision** — Requirements evolve; Bedrock's multi-model API facilitates A/B testing and gradual model migrations without app rewrites.

# Skill 2.1.2: Identify fine-tuning strategies for pre-trained FMs to meet business needs

## Task 2.1: ML Model and FM Development - Choose appropriate modeling approaches

---

### Fine-Tuning Decision Framework

| Evaluation Signal | Action |
|---|---|
| Prompting (zero-shot + few-shot) meets quality bar | **Do NOT fine-tune.** Deploy with prompt engineering only |
| Gap persists in terminology, format, or tone | **Supervised Fine-Tuning (SFT)** with labeled JSONL pairs |
| Model fails on scoring/ranking/reward optimization | **Reinforcement Fine-Tuning (RFT)** with reward functions |
| Large model quality needed at edge/small-model cost | **Distillation** into smaller target model |
| Content changes frequently; citations required | **RAG first**—not fine-tuning |

> **Hard Rule:** Prompt engineering always precedes fine-tuning. Fine-tuning is never the first adaptation step on the exam.

---

### Fine-Tuning Strategy Comparison

| Dimension | Supervised Fine-Tuning | Reinforcement Fine-Tuning | Distillation |
|---|---|---|---|
| **Input Data** | Prompt-response pairs (JSONL) | Reward functions / comparison pairs | Unlabeled prompts (teacher generates responses) |
| **Primary Goal** | Style, terminology, format adherence | Quality ranking, preference optimization | Reduce size/cost while retaining behavior |
| **Bedrock/API Path** | `CreateModelCustomizationJob` | `CreateModelCustomizationJob` with reward config | `CreateModelCustomizationJob` with teacher model |
| **Catastrophic Forgetting Risk** | **High** if narrow domain only | Moderate | Moderate |
| **Typical Latency Impact** | No change | No change | **Improved** (smaller model) |
| **Training Cost** | Moderate | High (iterative sampling) | Moderate (teacher inference cost) |

---

### Critical Fine-Tuning Parameters & Configurations

**Data Preparation Requirements:**
- **SFT:** Minimum ~100–1,000 labeled prompt-completion pairs; JSONL format with `prompt` and `completion` fields
- **Distillation:** Prepare diverse prompts only—Bedrock manages teacher responses internally
- **RFT:** Provide reward function or preference pairs showing "better vs. worse" outputs
- **All paths:** Hold out validation set to measure post-training degradation

**Hyperparameter Considerations:**
- **Epochs:** 1–3 typically sufficient; more epochs amplify catastrophic forgetting
- **Learning rate:** Lower than pre-training (e.g., 1e-4 to 1e-5)
- **Data mixture:** Blend general-domain data with task-specific data to preserve broad capability

---

### Mitigating Catastrophic Forgetting

- **Definition:** Model loses previously held general capabilities after narrow-domain training
- **Defense strategy:** Include 10–20% general/instruction data in fine-tuning mixture
- **Detection:** Evaluate on pre-established benchmark prompts before/after training
- **Rollback:** Version models in Bedrock; retain base model ARN for A/B comparison

---

### Bedrock Fine-Tuning Workflow

```
Raw Prompt → Try Prompt Engineering → Evaluate → Gap Persists?
                                                      ↓ Yes
Prepare Labeled JSONL → Call CreateModelCustomizationJob
                                                      ↓
Monitor Training Metrics → Validate on Holdout Set
                                                      ↓
Deploy as Custom Model ARN → A/B vs. Base Model → Promote if Superior
```

| Boto3 Method | Use Case |
|---|---|
| `bedrock.create_model_customization_job()` | Initiates SFT, RFT, or distillation job |
| `bedrock.get_model_customization_job()` | Monitor training status |
| `bedrock.get_custom_model()` | Retrieve custom model ARN and metadata |
| `bedrock.list_custom_models()` | Enumerate available fine-tuned models |

---

### When NOT to Fine-Tune

| Scenario | Correct Approach |
|---|---|
| Documents revised frequently; citations needed | **RAG / Bedrock Knowledge Bases** |
| One-off format change | **Prompt engineering** (immediate, zero training cost) |
| Task already solved by AWS AI service | **Managed service** (e.g., Textract, Transcribe) |
| Data patterns live in proprietary tabular data | **Traditional ML** (SageMaker built-in algorithms) |
| Stakeholders need full auditability of every step | **Rule-based logic** or interpretable ML |

> **Exam Gotcha:** If a question says "requirements changed weekly" or "must cite sources," fine-tuning is always wrong. RAG is the answer.

---

### Cost & Operational Trade-Offs

| Fine-Tuning Cost Factor | Exam Signal |
|---|---|
| GPU training hours × epochs | Training cost scales with epochs and model size |
| Data labeling effort | SFT requires labeled pairs; distillation does not |
| Ongoing version management | Each fine-tuning job creates a new model version |
| Inference cost after fine-tuning | Typically unchanged for same-size model |
| Distillation inference savings | Smaller target model → lower per-token cost |

---

### Decision Matrix: Prompt vs. SFT vs. RAG

| Requirement | Prompt Engineering | SFT | RAG |
|---|---|---|---|
| Update knowledge without retraining | ✗ | ✗ | ✓ |
| Adopt company terminology/style | Sometimes | ✓ | ✗ |
| Cite specific source documents | ✗ | ✗ | ✓ |
| Zero training infrastructure | ✓ | ✗ | ✓ (managed KB) |
| Handle proprietary reasoning patterns | Limited | ✓ | ✗ |
| Reflect content changes same-day | ✓ | ✗ | ✓ |

---

### Exam-Specific Distractor Traps

- **"Fine-tune to add new facts"** → Always wrong. Fine-tuning changes *behavior*, not *knowledge*. Use RAG.
- **"Fine-tune before trying prompts"** → Wrong order. Prompting first.
- **"Distillation requires labeled data"** → Wrong. Distillation uses unlabeled prompts; the teacher generates responses.
- **"Fine-tuning always improves model"** → Wrong. Narrow fine-tuning can degrade general performance (catastrophic forgetting).
- **"Use SageMaker for FM fine-tuning"** → Wrong unless question specifies custom FM workflow. Exam maps FM fine-tuning to Amazon Bedrock.

## Task 2.1: ML Model and Foundation Model (FM) Development — Choose Appropriate Modeling Approaches

---

## The 4-Tier Selection Hierarchy

**Start at the top. Only move down when the lower tier cannot satisfy the requirement.**

| Tier | Problem Profile | Recommended Approach | AWS Implementation |
|:---:|---|---|---|
| **0** | **Fixed business logic** — deterministic rules | Plain code / API call | Lambda Function, Step Functions |
| **1** | **Pre-solved ML task** — OCR, transcription, sentiment, moderation | Managed AWS AI Service | Textract, Transcribe, Comprehend, Rekognition |
| **2** | **Proprietary patterns in tabular/historical data** | Custom supervised/unsupervised training | SageMaker AI built-in algorithms (XGBoost, Linear Learner, DeepAR) |
| **3** | **General language/reasoning/creative generation** | Foundation Model via API — prompt first | Amazon Bedrock (+ fine-tune only if necessary) |

> **Exam Gotcha:** Tier 0 is a valid "modeling approach." If a problem can be solved with a conditional statement, building any ML model is an **anti-pattern** and will be marked incorrect.

---

## Decision Matrices

### Traditional ML vs. Foundation Model (FM)

| Criteria | Train Custom ML Model (SageMaker AI) | Use Foundation Model (Amazon Bedrock) |
|---|---|---|
| **Knowledge source** | Own labeled historical data | General world knowledge (pre-trained) |
| **Data volume required** | Medium–large labeled dataset | Zero–few-shot examples |
| **Interpretability** | ✅ High (SHAP, coefficients, tree structure) | ⚠️ Low (opaque reasoning) |
| **Latency** | ✅ Millisecond–low seconds (real-time endpoints) | ⚠️ Seconds (LLM token generation) |
| **Cost at scale** | ✅ Lower per-inference after training | ⚠️ Higher per-token, scales linearly |
| **Format adaptability** | Tabular → numeric, time series | Natural language, code, dialogue |
| **Explainability via citations** | ❌ Not applicable | ✅ Via RAG source attribution |
| **Update speed for new knowledge** | 🔁 Retrain required | ✅ Instant via prompt or RAG sync |

### Managed AI Service vs. Custom Model vs. FM

| Capability Required | Managed AI Service (AWS) | Custom Model (SageMaker AI) | Foundation Model (Bedrock) |
|---|---|---|---|
| Extract text from scanned invoices/forms | **Textract `AnalyzeExpense`** ✅ | ❌ Overkill — training + labeling | ⚠️ Possible but unverified |
| Sentiment/entities/key-phrases in text | **Comprehend** ✅ | ❌ Requires labeled corpus | ⚠️ Possible via prompt |
| Speech → text transcription | **Transcribe** ✅ | ❌ Specialized audio pipeline | ⚠️ Limited quality control |
| Face/objects/scenes/moderation in images/video | **Rekognition** ✅ | ❌ Huge labeling cost | ⚠️ Multimodal FMs emerging but managed service is simpler |
| Time-series demand forecasting with feature interpretation | ❌ No service | **SageMaker XGBoost/DeepAR** ✅ | ❌ Not designed for tabular precision |
| Ticket summarization with company terminology | ❌ No dedicated service | ❌ Cannot generate prose | **Bedrock FM + prompting** ✅ |

## Fine-Tuning vs. Prompt Engineering vs. RAG

### The Decision Ladder (Memorize This Order)

```
STEP 1: Prompt Engineering (instructions + few-shot examples)
          │
          ├── SUCCESS → Deploy (zero training overhead)
          │
          └── FAILURE (gap persists in evaluations)
                    │
        ┌───────────┴────────────────┐
        ▼                            ▼
   Need domain KNOWLEDGE        Need domain BEHAVIOR
   (external facts, updated)    (style, terminology, format)
        │                            │
    STEP 2a: RAG                 STEP 2b: Fine-Tuning
   (Bedrock Knowledge Bases)     (SFT on labeled JSONL pairs)
        │                            │
        ▼                            ▼
   Content changes reflected     Weight update = retraining
   within minutes via sync       for every content change
```

> **Exam Gotcha:** The prompt-first order is **non-negotiable** in exam logic. Choosing fine-tuning before attempting prompt engineering is the single most common distractor.

### RAG vs. Fine-Tuning: Key Trade-Offs

| Property | RAG (Retrieval-Augmented Generation) | Fine-Tuning |
|---|---|---|
| **Knowledge storage** | External vector store (index) | Inside model weights |
| **Update latency** | Seconds–minutes (re-sync index) | Hours–days (new training job) |
| **Source citation** | ✅ Built-in (chunk metadata) | ❌ Impossible |
| **Catastrophic forgetting risk** | ✅ None — base model intact | ⚠️ Real risk — mitigated by mixing general data |
| **Whole-document synthesis** | ⚠️ Weaker (chunked retrieval) | ✅ Better on domain-specific task fidelity |
| **Cost model** | Pay per embedding + token + vector storage | Pay per training job + hosting fine-tuned model |
| **Ability to combine** | ✅ Can coexist (fine-tuned model + RAG) | |

## Quick Recall — The Unified Decision Tree

```
1. Fixed deterministic logic?
   └─ YES → Write code. Stop. (No ML.)

2. Problem already solved by AWS AI service?
   └─ YES → Textract / Transcribe / Comprehend / Rekognition. Stop.

3. Patterns only exist in your OWN labeled tabular/historical data?
   └─ YES → Train supervised model (SageMaker AI).
         ├─ Interpretability required → XGBoost / Linear Learner

   └─ YES → Amazon Bedrock Foundation Model.
         ├─ Step 1: Prompt Engineering → Evaluate

         └─ Step 3: Behavior gap persists → Supervised Fine-Tuning
```

## Prompt First, Fine-Tune Second

```bash
Prompt Engineering → Evaluate → Gap Persists? → Fine-Tune
        ↓                            ↑
   Immediate change            Accept training overhead:
                                • Data preparation (JSONL)
                                • GPU compute cost
                                • Version management
```

**Fine-tuning triggers (all must be true):**
- Prompt instructions + few-shot examples consistently fail evaluations
- Task requires specialized domain vocabulary or formatting adherence
- You have labeled input-output pairs ready (SFT) or reward functions (RLHF)

> **Critical Rule:** Fine-tuning writes behavior into weights. Retrieval keeps content outside the model. Choose based on:
> - **Content changes frequently** → RAG/Knowledge Bases (minutes to update)
> - **Behavior/format/domain style is stable** → Fine-tune (weights persist)
> - **Need source citations** → RAG (retrieved chunks have metadata)

## Custom ML vs. Foundation Model Tradeoffs

## SageMaker AI Options Hierarchy

| Option | When | Tradeoff |
|:---|:---|:---|

# Skill 2.1.6: Assess Tradeoffs Between ML Model Performance, Training Time, and Cost

## Task 2.1: ML Model and Foundation Model (FM) Development - Choose Appropriate Modeling Approaches

---

## The Tri-Constraint Decision Framework

Every modeling decision forces a tradeoff between three competing forces. The exam expects you to identify *which* constraint a requirement is asking you to sacrifice.

| Constraint | What It Measures | Typical Metric | AWS Levers |
|---|---|---|---|
| **Performance** | Output accuracy/quality | Accuracy, F1, RMSE, BLEU, ROUGE | Larger model, more epochs, more data, ensemble |
| **Training Time** | Time-to-model-availability | Hours, days, weeks | Distributed training, transfer learning, fewer epochs |
| **Cost** | Total financial spend | Compute $, GPU-hours, tokens | Smaller model, spot instances, batch inference, distillation |

> **Exam Gotcha:** You can optimize two of the three dimensions—never all three simultaneously. If a requirement demands higher accuracy *and* faster training, the tradeoff must fall on cost. If it demands lower cost *and* higher accuracy, expect longer training time.

---

## Decision Matrices

### Traditional ML (SageMaker AI) Tradeoff Matrix

| Scenario | Best Approach | Why | Tradeoff Incurred |
|---|---|---|---|
| Interpretability is critical; finance/auditors must explain predictions | Linear models, decision trees, XGBoost with SHAP/SageMaker Clarify | Transparent feature attribution | Lower raw accuracy vs. deep learning |
| Complex unstructured data (images, audio, long text) | Deep learning (CNNs, Transformers) | Captures non-linear patterns tabular models miss | Training time ↑, cost ↑, interpretability ↓ |
| Rapid experimentation needed | SageMaker built-in algorithms or JumpStart | Pre-optimized; no algorithm engineering | Less customization control |
| Near-zero pretraining budget | Transfer learning: start from pre-trained, fine-tune on domain data | Leverages existing weights; fewer epochs needed | Risk of catastrophic forgetting |
| Cost must stay minimal; can tolerate slower training | Spot instances (SageMaker managed spot), single GPU | Up to 90% cost savings | Training may take 2-3x longer |

### Foundation Model (Bedrock) Tradeoff Matrix

| Scenario | Best Approach | Why | Tradeoff Incurred |
|---|---|---|---|
| Fastest time-to-production; no training pipeline | Prompt engineering + Bedrock API | Zero training overhead; immediate deployment | Less precise domain control |
| Persistent quality gap despite prompting; domain terminology | Supervised fine-tuning (SFT) | Bakes behavior into weights | Cost ↑, time ↑, catastrophic forgetting risk |
| Response must be fast for real-time UX | Smaller FM (e.g., Claude Haiku vs. Opus) or distilled model | Lower parameter count = faster token generation | Output quality ↓ |
| Cost is primary; less latency-sensitive | Batch inference, async APIs | Efficient compute utilization | Higher latency |
| Needs domain precision + low cost + low latency | Distillation (large teacher → small student) | Compresses capability into efficient model | Distillation pipeline effort |

---

## Key Tradeoff Scenarios (High-Yield)

### Tradeoff 1: Interpretability vs. Accuracy
- **When interpretability wins:** Regulated industries (finance, healthcare, HR), stakeholder-facing predictions, audit requirements.
- **Action:** Favor linear/logistic regression, decision trees, or XGBoost. Use SageMaker Clarify for SHAP feature attribution.
- **When accuracy wins:** Unstructured data, image classification, NLP tasks where humans cannot articulate the feature engineering.
- **Action:** Deep learning via SageMaker AI; accept the black-box nature.

> **Rule:** A simpler, interpretable model that stakeholders *trust and deploy* beats a complex model that gets rejected. Model adoption is part of performance.

### Tradeoff 2: Training Time vs. Quality
- **Distributed training** (e.g., SageMaker distributed data parallel) reduces wall-clock time but increases cost and engineering complexity.
- **More epochs** improve convergence up to a point, then overfit. Diminishing returns set in.
- **Early stopping with SageMaker Debugger** prevents wasted epochs—automatically halts training when validation loss plateaus.

| Lever | Impact on Training Time | Impact on Cost | Impact on Quality |
|---|---|---|---|
| More epochs | ↑ | ↑ | ↑ then flattens/overfits |
| Larger batch size | ↓ (more parallel efficiency) | Same per-epoch | May degrade generalization |
| Distributed training | ↓↓ | ↑↑ | Neutral |
| Transfer learning | ↓↓↓ | ↓↓ | Good if domain similar |
| Spot instances | ↑ (interruptions) | ↓↓↓ | Neutral |
| Mixed precision training | ↓ | ↓ | ~Neutral |

### Tradeoff 3: Inference Cost vs. Latency (GenAI Focus)
- **Larger FMs** produce higher-quality outputs but cost more per token and generate tokens more slowly.
- **Smaller FMs or distilled models** reduce cost and latency but may sacrifice reasoning depth.
- **Batching requests** lowers per-request cost but increases individual request latency (not suitable for real-time).
- **Streaming responses** improves perceived latency without changing actual generation speed.

---

## Cost Optimization Levers (When Cost Is the Priority)

| Lever | How It Works | When to Use |
|---|---|---|
| **SageMaker Managed Spot Training** | Uses spare EC2 capacity; auto-checkpoints | Fault-tolerant training jobs |
| **Smaller instance types** | Less compute, slower training | Non-critical experiments |
| **SageMaker Automatic Model Tuning (HPO)** | Finds best hyperparameters efficiently; avoid manual grid search wastes | When hyperparameter search space is large |
| **Model pruning/quantization** | Reduces model size post-training | Deployment to edge or low-cost endpoints |
| **Batch transform vs. real-time endpoint** | Offline inference at lower cost | Non-interactive workloads |
| **Multi-model endpoints** | Host multiple models on one endpoint | Many small models rarely called |

---

## Anti-Patterns & Distractor Traps

- ❌ **"Bigger model = always better"** — For tabular forecasting with interpretability requirements, a foundation model is the wrong tool. The answer is not in the model; it is in the data.
- ❌ **"Skip prompting, go straight to fine-tuning"** — Fine-tuning requires labeled data, GPU training, version management, and ongoing maintenance. Prompt engineering changes behavior immediately at zero cost.
- ❌ **"Train a model for a solved task"** — If Amazon Textract already extracts invoice data, building a custom OCR model wastes engineering time and compute.
- ❌ **"Use spot instances for time-sensitive, interruptible jobs"** — Spot is for fault-tolerant, checkpointed training. If training must complete in fixed hours, use On-Demand.
- ❌ **"Customization (fine-tuning) enables document citations"** — Only RAG/retrieval provides source attribution. Fine-tuning encodes knowledge in weights; no source exists to cite.
- ❌ **"Batch inference meets real-time SLAs"** — Batching lowers cost but adds per-request latency. Real-time endpoints are required for synchronous, low-latency serving.

---

## Quick Decision Checklist

1. **Does the requirement say "explainable," "auditable," or "trusted by stakeholders"?** → Prioritize interpretability over accuracy; choose simple models with SHAP/SageMaker Clarify.
2. **Does the requirement say "fastest time-to-market" or "no ML team"?** → Managed AI service (Textract, Rekognition, Transcribe, Comprehend) or Bedrock with prompting.
3. **Does the requirement say "lowest cost" with tolerance for slow training?** → Spot instances, smaller models, transfer learning, batch inference.
4. **Does the requirement say "real-time inference" with tight latency SLA?** → Smaller FM, distilled model, or optimized real-time endpoint; avoid batching.
5. **Does the requirement demand cited sources or rapid knowledge updates?** → RAG via Bedrock Knowledge Bases; not fine-tuning.
6. **Is the answer in the data or in the model?** → Proprietary patterns = train ML model; general language capability = use FM with prompting first.

## Feature-Specific API Deep Cuts

### Amazon Textract – Critical Distinctions

| API | Use Case | Key Parameters |
|---|---|---|
| `DetectDocumentText` | Simple OCR only, plain text/page blobs | DocumentLocation, FeatureTypes |
| `AnalyzeDocument` | Forms + Tables extraction | FeatureTypes: `FORMS`, `TABLES`, `QUERIES` |
| `AnalyzeExpense` | Invoices/receipts only (Vendor, Tax, Line Items) | Document (single invoice png/jpg/pdf) |
| `AnalyzeID` | Identity doc (license, passport) | DocumentPages → FieldSummary |
| **Async APIs** (`StartDocumentAnalysis`) | Multi-page docs >1 page PDF, or all S3-batch | JobId polling / SNS notification |
| **Sync APIs** (direct) | Single-page, small files, byte arrays | Response inline |

> **Exam Gotcha:** Sync APIs accept image bytes directly and handle <20MB on S3 or local buffer. Async is REQUIRED for multi-page processing (>1 page PDFs) and larger jobs—choosing sync for large payloads or vice versa is a classic distractor.

> **Exam Rule:** `AnalyzeExpense` is optimized for invoices and returns `LINE_ITEM_GROUPS`, `EXPENSE_DOCUMENTS`, `SUMMARY_FIELDS`. It includes **invoice-specific tax and total extraction** that `AnalyzeDocument` does not. 

### Amazon Rekognition – Model Scoping

| Operation | Specific Use | Note |
|---|---|---|
| `DetectLabels` | Generic objects, scenes, brands | Returns parent + child label hierarchy with confidence |
| `DetectFaces` | Facial attributes + landmarks | Does NOT do facial recognition/matching |
| `IndexFaces` + `SearchFacesByImage` | Face matching (requires collection) | Service-side biometric identity storage—requires careful IAM + consent governance |
| `DetectModerationLabels` | Content moderation (explicit/nudity/violence) | Specialized model, top-level + parent categories |
| `DetectText` | Detect text in images/video | Similar to Textract but for **scene text**, not documents |
| `StartContentModeration` / `StartLabelDetection` | Async media (video; S3) | JobId + SNS completion |

> **Exam Gotcha:** `DetectText` (Rekognition) extracts text from arbitrary image/video scenes (signs, billboards) but NOT structured tables/key-value forms. For documents with fields, **Textract is the correct service**. Rekognition `DetectText` ≠ Textract OCR.

> **Exam Rule:** Rekognition Face Matching requires TWO separate steps: (1) `IndexFaces` to create/append to a `CollectionId` vector store of face embeddings; (2) `SearchFacesByImage` to match. "Collected faces" are stored and searchable as `FaceRecords`.

### Amazon Comprehend – Choosing the Right Analysis Type

| API | What It Detects | Representative Use | Output Details |
|---|---|---|---|
| `DetectSentiment` | Sentiment (POSITIVE/NEGATIVE/NEUTRAL/MIXED) | Reviews, feedback | Per-document score, not per-entity |
| `DetectEntities` | Entities (PERSON, ORG, DATE, QUANTITY, etc.) | Knowledge extraction, search | Mentions with offsets, confidence, types |
| `DetectKeyPhrases` | Key noun phrases | Search connectors, topics | Comma-separated phrases w/ Score |
| `DetectPiiEntities` | PII by box (not NER) | Compliance scanning | Type (SSN, EMAIL, ADDRESS, DRIVER_ID), Score, Begin/EndOffsets |

| `DetectDominantLanguage` | Language ID (100+ langs) | Multi-lingual routing | ISO-639-1 code + Score |

> **Exam Gotcha:** `DetectSentiment` returns a document-level sentiment only. Use **`DetectTargetedSentiment`** when you need per-entity (brand/actor-specific) sentiment. 

> **Exam Gotcha:** `DetectPiiEntities` covers a finite built-in list (e.g., SSN, credit card, driver's license, SSN, name, phone). For enterprise-compliance requiring **custom PII types**, use Comprehend **custom entity recognition** (train a custom classifier/entity recognizer). 

### Amazon Transcribe – Key Features & Limits

| Function | How to Access | When |
|---|---|---|
| **Standard Batch** | `StartTranscriptionJob` | Pre-recorded audio on S3 (MP3, WAV, FLAC, etc.) |
| **Streaming** | `StartStreamTranscription` WebSocket/HTTP2 | Real-time call centers, voice input |
| **Custom Vocabulary** | `VocabularyFileUri` or `VocabularyName` | Domain terms (product names, acronyms) – 4 variants |

| **Speaker Diarization** | `ShowSpeakerLabels=True` | Multi-speaker audio; `MaxSpeakerLabels` (1-10) |
| **Channel Identification** | `ChannelIdentification=True` | Stereo audio where speaker left/right channels differ |
| **Subtitling** | `Subtitles` → Formats: `srt`, `vtt` | Video caption workflows |
| **Content Filtering** | `VocabularyFilterMethod` = `mask`, `remove`, `tag` | Profanity masking |

> **Exam Gotcha:** Transcribe supports **custom vocabularies** (lists of 1–10k weighted terms) with `Phrases`, `SoundsLike`, `IPA`, or `DisplayAs` columns. For higher accuracy on domain-specific audio, a **custom language model** (requires 1–100k training transcripts) is the stronger signal—but takes more data.

## Core Retention Summary

**The "Rule of Thumb" by problem class:**

- **Structured docs → Textract (Optimized per-doc type: AnalyzExpense, AnalyzeID)**
- **Computer vision (images/video) → Rekognition (Moderation, Labels, Faces)**
- **NLP tasks → Comprehend (Sentiment, Entities, PII)**
- **Voice/Audio → Transcribe (Diarization, Custom vocab)**
- **General model capability → Bedrock (prompt first)**
- **Own historical data → SageMaker AI (train supervised)**

> **Hard rule:** For every AWS AI service scenario, ask: (1) Is the task already pre-solved? (2) Does the service's built-in label/response schema match the business need exactly? (3) Are we processing the input in a supported format and calling the correct API (sync/async)? If yes—use the service. If the task needs in-domain accuracy not covered by the service—go custom or fine-tune.

## When NOT to use AWS AI Services

- **Latency-critical, high-QPS endpoints** → Custom `SageMaker Endpoint` with low-latency model (e.g., DistilBERT) is more cost-effective than per-API charges.
- **Few-shot custom object detection on edge devices** → AWS Panorama or custom SageMaker model (Rekognition cloud does not run offline on edge).
- **Highly specialized NLP domain models (legal, medical)** → Amazon Comprehend Medical handles clinical entities. For legal contracts beyond Comprehend's generic entity list, fine-tuning Bedrock or training custom detection may be required.
- **Multilingual tasks beyond Comprehend's built-in language coverage** → Custom model or Amazon Translate+Bert based approach.
- **Streaming video analysis at camera-edge for privacy-sensitive workloads** → AWS IoT Greengrass + custom inference; avoid sending all video to Rekognition when local processing is required.

# Skill 2.2.3: Implement Hyperparameter Optimization
## Task 2.2: ML Model and FM Development - Train, fine-tune, and customize models

---

## SageMaker Automatic Model Tuning (AMT) Core Mechanics

| Component | Details |
|-----------|---------|
| **Objective Metric** | Single metric chosen from estimator's `metric_definitions` regex. Must parse from training logs to CloudWatch. |
| **Search Space** | `ContinuousParameterRanges`, `IntegerParameterRanges`, `CategoricalParameterRanges` |
| **MaxParallelTrainingJobs** | Controls concurrency. Higher = faster wall-clock, higher resource cost. |
| **MaxNumberOfTrainingJobs** | Total tuning budget/cap. Independent from time-based criteria. |
| **Completion Criteria** | Max jobs, max wall-clock time (`TrainingJobEarlyStoppingType`), convergence detection. A tuning job stops when ANY criteria met. |
| **Output** | Best training job identified by objective metric. Must call `get_best_training_job()` explicitly. |

**Key Boto3/CLI Params:**
- `TrainingJobEarlyStoppingType: "Auto"` — stops individual jobs unlikely to beat current best (AMT evaluates every 5 minutes)
- `Strategy: "Bayesian"` — default; uses gaussian process to model objective as function of hyperparameters
- `Strategy: "Random"` — uniform random sampling; better for wide, low-signal spaces
- `Strategy: "Hyperband"` — aggressive early-stopping; explores wide ranges on low GPU utilization; best for iterative algorithms (DL)
- `Strategy: "Grid"` — exhaustive; only for small discrete categorical spaces

> **Exam Gotcha:** AMT does NOT return the tuned hyperparameters inline via `fit()`. You must call `tuner.best_estimator()` or `describe_tuning_job()` to access them.

> **Exam Gotcha:** The objective metric direction matters. Set `objective_type` correctly (Minimize for validation loss/RMSE, Maximize for AUC/F1/accuracy). Wrong direction yields worse model, faithfully optimized.

---

## Hyperparameter Ranges & Scaling

| Parameter Type | Log Scale? | Example |
|----------------|-----------|---------|
| **Learning rate** | ✅ Always log-scale | `ContinuousParameter(0.001, 0.1, ScalingType="Logarithmic")` |
| **Dropout rate** | ❌ Linear | `ContinuousParameter(0.0, 0.5, ScalingType="Linear")` |
| **Batch size** | ❌ Linear (integer) | `IntegerParameter(16, 512)` |
| **Optimizer choice** | N/A | `CategoricalParameter(["Adam", "SGD", "RMSprop"])` |
| **Tree depth (XGBoost)** | ❌ Linear | `IntegerParameter(1, 15)` |

> **Exam Gotcha:** Learning rate is the classic trap. Linear scaling wastes trials on unhelpfully small values. Logarithmic scaling uniformly samples across orders of magnitude. SageMaker **does not auto-detect scale** — you must specify.

---

## AMT Search Strategies: Decision Matrix

| Strategy | Use When | Trade-off | Early Stopping |
|----------|----------|-----------|----------------|
| **Bayesian** | Small-to-medium budgets (< 100 jobs), continuous ranges, smooth objective | Learned surrogate model guides search; slower per iteration due to model update | Built-in, via objective tracking |
| **Random** | Very large search spaces, categorical-heavy, parallelizable | Simple, no learning; can waste budget on poor regions | Available |
| **Hyperband** | Deep learning, large budget, need aggressive search | Aggressively kills unpromising jobs early; explores more configs | Core mechanism — not optional |
| **Grid** | Tiny discrete spaces (< 10 combos) | Exponential blowup; impractical beyond 2-3 hyperparameters | N/A |

> **Exam Gotcha:** Bayesian Strategy with early stopping enabled is the default pattern for most production tuning. Hyperband is the fastest for deep learning with large budgets.

---

## Early Stopping Within Training Jobs vs. Tuning Jobs

| Technique | Scope | Mechanism | Benefit |
|-----------|-------|-----------|---------|
| **Job-level early stopping** (in training script) | Single training run | Monitor validation loss, stop when no improvement after N epochs | Saves compute per trial |
| **Tuning-job early stopping** (`TrainingJobEarlyStoppingType: Auto`) | Cross-trial comparison | AMT kills trials unlikely to beat current best objective | Saves total tuning budget |
| **Warm start** (`WarmStartConfig`) | Search reuse | Reuse previous tuning job's learned results | Accelerates new tuning; enables iterative refinement |

> **Exam Gotcha:** Job-level early stopping is implemented in the **training script** (e.g., PyTorch callback). Tuning-level early stopping is configured on the **tuner object**. They are complementary, not interchangeable.

---

## Warm Start Configuration

**When to use:** Iterative HPO across experiments. E.g., tune `max_depth` and `eta` after tuning `subsample`. Warm start reuses prior trial data to initialize Bayesian priors — faster convergence on refined ranges.

| WarmStartType | Behavior |
|---------------|----------|
| `IdenticalDataAndAlgorithm` | Same dataset, preprocessed identically. Can narrow/widen ranges. |
| `TransferLearning` | Different (but related) dataset. Can only narrow ranges. |

> **Exam Gotcha:** `TransferLearning` requires you **cannot expand** parameter ranges compared to the parent tuning job. `IdenticalDataAndAlgorithm` permits range changes.

---

## Integration with Script Mode & Built-in Algorithms

**Script Mode Pattern:**
```python
from sagemaker.tuner import HyperparameterTuner, IntegerParameter, ContinuousParameter

hyperparameter_ranges = {
    "learning-rate": ContinuousParameter(1e-4, 1e-2, ScalingType="Logarithmic"),
    "batch-size": IntegerParameter(32, 256),
    "hidden-dim": CategoricalParameter([128, 256, 512]),
}

tuner = HyperparameterTuner(
    estimator=estimator,
    objective_metric_name="validation:loss",
    objective_type="Minimize",
    hyperparameter_ranges=hyperparameter_ranges,
    max_jobs=50,
    max_parallel_jobs=5,
    strategy="Bayesian",
    base_tuning_job_name="my-tuning-job"
)
tuner.fit({"train": train_s3, "validation": val_s3})
```

**Metric Parsing Requirement:** In script mode, you define `metric_definitions` in the estimator:
```python
metric_definitions=[{
    "Name": "validation:loss",
    "Regex": "val-loss=([0-9.]+)"
}]
```
The script must `print(f"val-loss={loss:.4f}")` or AMT cannot find the objective metric.

> **Exam Gotcha:** Built-in algorithms (XGBoost, Linear Learner, etc.) have **predefined objective metric names** (e.g., `validation:rmse`, `validation:auc`) that require no custom regex. Script mode requires `metric_definitions` or tuning fails.

---

## Anti-Patterns & Failure Modes

| Anti-Pattern | Consequence | Correct Approach |
|--------------|-------------|------------------|
| Tuning on test set | Data leakage; inflated objective scores | Use validation split only |
| Mixing scale types (linear for LR) | Wasted trials, poor search | Log-scale learning rate, regularization |
| `MaxParallelTrainingJobs` = `MaxNumberOfTrainingJobs` | No Bayesian benefit; essentially random | Limit parallel to 5-10 for Bayesian to learn between batches |
| Using accuracy for imbalanced data | Misleading objective | Use F1, precision-recall AUC |
| One large epoch in each trial | No early stopping signal; slow tuning | Use epoch-based tuning with validation metric |
| Tuning without `TrainingJobEarlyStoppingType:"Auto"` | Wasted budget on doomed trials | Always enable for large search spaces |

---

## Cost-Reduction Patterns

| Pattern | Technique |
|---------|-----------|

| **Spot instances** | `estimator = sagemaker.estimator.Estimator(..., use_spot_instances=True, max_wait=3600, max_run=1800)` |

> **Exam Gotcha:** Spot training with AMT requires configuring both `use_spot_instances=True` AND `max_wait` > `max_run`. If spot capacity unavailable, SageMaker waits (billing paused) until `max_wait` timeout.

# Skill 2.2.4: Implement Training Time Reduction Techniques

## Task 2.2: ML Model and Foundation Model (FM) Development - Train, fine-tune, and customize models for ML and AI solutions.

---

## Core Concept & Business Objective

**Primary Goal:** Reduce wall-clock training duration and total compute cost without sacrificing model quality. Techniques fall into three buckets:

| Technique | What It Does | Best Used When |
|-----------|-------------|----------------|
| **Early Stopping** | Halts training when validation metric stops improving | Single-run optimization; prevents wasted epochs |
| **Data Parallelism** | Splits batch across multiple devices; replicates model | Model fits on one device but dataset is large |
| **Model Parallelism** | Partitions model layers/parameters across devices | Model exceeds single-device memory |

---

## Early Stopping

**Mechanism:** Monitor validation metric per epoch; stop when no improvement for `N` consecutive epochs (`patience`).

**Key Configurations:**
- **Patience:** Number of stagnant epochs before stopping (typical: 3–10)
- **Min Delta:** Minimum improvement threshold to count as "better" (avoids noise-triggered stops)
- **Restore Best Weights:** Critical — reload checkpoint from best epoch, not final epoch
- **Monitor Metric:** Must align with objective direction (minimize loss, maximize accuracy)

**SageMaker AI Implementation:**
- **Built-in algorithms:** Some support `early_stopping` hyperparameter directly (e.g., XGBoost: `early_stopping_rounds`)
- **Script mode:** Implement via callback/`EarlyStopping` in framework (e.g., `PyTorch Lightning`, TF `tf.keras.callbacks.EarlyStopping`, Hugging Face `EarlyStoppingCallback`)
- **Automatic Model Tuning (AMT):** Use `TrainingJobEarlyStoppingType` with `Auto` to skip jobs unlikely to beat current best

> **Exam Gotcha:** Early stopping shortens a **single training job**. It does NOT replace hyperparameter tuning. AMT's `Auto` early stopping terminates *promising-to-lose* tuning jobs, not the winning job's training.

---

## Distributed Training

### Data Parallelism

**Use Case:** Model fits on single GPU; dataset too large / time constraints.

| Framework | SageMaker Tool | Key Parameter |
|-----------|---------------|---------------|
| PyTorch | `torch.distributed` / SMDDP | `sagemaker_distributed_dataparallel_enabled` |
| TensorFlow | `tf.distribute.MirroredStrategy` / SMDDP | `sagemaker_distributed_dataparallel_enabled` |
| Hugging Face | Trainer + SMDDP | `distribution="data_parallel"` |

**SageMaker Data Parallel (SMDDP) Library:**
- Requires `mpirun` launcher with `smdistributed` config
- Enables faster `AllReduce` via AWS network optimizations
- Instance types: `ml.p3dn.24xlarge`, `ml.p4d.24xlarge`, `ml.p5.48xlarge`

**Key Hyperparameters:**
- **Batch size:** Scale linearly with number of GPUs (e.g., 2× GPUs → 2× batch size)
- **Learning rate:** Scale proportionally (linear scaling rule) or use LARS optimizer
- **Gradient accumulation:** Simulates large batch on limited memory

> **Exam Gotcha:** Communication overhead can negate scaling benefits. For small models or small datasets, single GPU may be faster than multi-GPU due to `AllReduce` latency.

---

### Model Parallelism

**Use Case:** Model parameters exceed single accelerator memory (e.g., >40B parameter LLMs).

| Strategy | How It Works | When to Use |
|----------|-------------|-------------|
| **Pipeline Parallelism** | Splits layers across devices; micro-batches flow through | Deep models with sequential layers |
| **Tensor Parallelism** | Splits individual layers/operations across devices | Very large single layers (attention heads) |
| **Sharded Data Parallel** | Shards optimizer states, gradients, parameters across devices | Large models that fit marginally with ZeRO |

**SageMaker Model Parallelism Library (SMP):**
- Supports PyTorch and TensorFlow
- Provides pipeline parallelism with `smdistributed.modelparallel`
- Integrates with `torch.distributed` for hybrid sharding
- Requires `mpirun` + distribution config

**Alternative: FSDP (Fully Sharded Data Parallel)**
- PyTorch native; shards optimizer states/gradients/weights across GPUs
- Lower memory footprint; enables larger models without full model parallelism
- Distractor: FSDP is a *data* parallelism variant, not pure model parallelism

---

## Decision Matrix: Training Time Reduction

| Scenario | Recommended Technique |
|----------|----------------------|
| Model fits on GPU; dataset large; single job too slow | **Data Parallelism** |
| Model exceeds GPU memory (large transformer) | **Model Parallelism** / **FSDP** |
| Training plateaus early; wasted compute | **Early Stopping** |
| Many tuning jobs that will obviously lose | **AMT `Auto` Early Stopping** |
| Tuning search space large; budget limited | **Hyperband strategy** in AMT |
| Previous tuning job exists; new search started | **Warm start** from prior results |
| Batch size limited by GPU memory | **Gradient Accumulation** |
| Mixed precision possible (FP16/BF16) | **Automatic Mixed Precision (AMP)** |

## Anti-Patterns & Common Traps

- **Increasing epochs to "fix" slow convergence** → wastes compute; use learning rate schedule or better optimizer instead
- **Using data parallelism for small models/small datasets** → communication overhead dominates; single GPU often faster
- **Scaling batch size without scaling learning rate** → degraded convergence; use LARS or linear scaling
- **Early stopping on training metric** → stops too late or never; must monitor **validation** metric
- **Ignoring checkpoint restore** → model ends with post-plateau weights, negating early stopping benefit
- **Using model parallelism for models that fit on one GPU** → unnecessary complexity and slower training
- **FSDP confused with model parallelism** on exam → FSDP is a **ZeRO-based data parallelism** technique

---

## Quick Reference: Parameters & Thresholds

| Parameter | Typical Value | Notes |
|-----------|--------------|-------|
| `patience` (early stopping) | 3–10 epochs | Higher for noisy metrics |
| `min_delta` | 1e-4 to 1e-3 | Prevents noise-triggered stops |
| Learning rate scaling | Linear with batch size | `lr_new = lr_old × (batch_new / batch_old)` |
| Gradient accumulation steps | 2–8 | Effective batch = `batch × accumulation` |
| Mixed precision (AMP) | FP16/BF16 | BF16 preferred for stability on p5/p4d |
| Hyperband `max_resource` | Set to max epochs | Controls budget allocation |

> **Exam Gotcha:** Early stopping is a **regularization** technique AND a **time reduction** technique. The exam may frame it as "preventing overfitting" — both answers can be correct depending on context.

# Skill 2.2.5: Prevent model overfitting, underfitting, and catastrophic forgetting.

## Task 2.2: Train, fine-tune, and customize models for ML and AI solutions.

### Failure Diagnosis Quick Matrix

| Symptom | Training Score | Validation/Test Score | Diagnosis |
|--------|:---:|:---:|-----------|
| Gap large, val poor | **High** | **Low** | **Overfitting** |
| All scores poor | **Low** | **Low** | **Underfitting** |
| Prior capability lost after fine-tuning | — | Degraded on old/general tasks | **Catastrophic forgetting** |
| Erratic val loss, non-reproducible | Varies | Varies | **Objective metric direction misconfigured** |

> **Exam Gotcha:** "High training accuracy, low validation accuracy" = overfitting. "Low both" = underfitting. "Was fine before fine-tune, now bad on general data" = catastrophic forgetting. These are distinct and testers rarely blur them.

---

### Overfitting: Detection, Causes, and Mitigations

**Detection:**
- **Loss curves:** Training loss ↓ steadily; validation loss ↑ after epoch N.
- **Metric gap:** Train F1/AUC > 0.95, validation < 0.80 (domain-dependent threshold).
- **Learning curves:** Gap widens as training progresses.

**Primary Causes:**
- **Model capacity too high** relative to dataset size (too many layers/params, deep trees).
- **Training too long** (too many epochs/steps without early stopping).
- **Insufficient data** or **non-representative data** (over-sampled noise, class imbalance).
- **Low regularization** (missing/dropout, weight decay, data augmentation).

**Mitigations — Exam-Essential Order:**

| Technique | Mechanism | Amazon SageMaker Implementation |
|-----------|-----------|-------------------------------|
| **Early Stopping** | Halt training when validation metric stops improving for N consecutive epochs | Built into many estimators (e.g., XGBoost `early_stopping_rounds`); custom via callback in script mode |
| **Regularization** | Penalize large weights / reduce effective capacity | `L1`/`L2` for linear models; `dropout` for neural networks; `alpha`, `lambda` for XGBoost/Linear Learner |
| **Data Augmentation** | Artificially expand dataset diversity (rotate, flip, noise, synonym replacement) | In script mode with frameworks (PyTorch/Transforms, TensorFlow/ImageDataGenerator, Albumentations) |
| **Cross-Validation** | Train/validate on K folds to better estimate generalization | SageMaker built-in algos support `nfold` (e.g., Linear Learner, XGBoost) |
| **Reduce Model Complexity** | Lower tree depth, fewer estimators, fewer layers/units | Hyperparameters: `max_depth`, `num_round`, `n_estimators`, `hidden_layer_sizes` |
| **Increase Training Data** | More diverse examples | Data augmentation, additional data collection, synthetic data generation |
| **Transfer Learning (freeze earlier layers)** | Reuse pre-trained weights, train only final layers | SageMaker JumpStart fine-tuning; input mode `Image`, base model selection |

> **Exam Gotcha:** Early stopping *reduces* overfitting from excessive epochs but is a **separate** mechanism from hyperparameter tuning (AMT). Tuning finds good HPOs across jobs; early stopping ends a single job early.

---

### Underfitting: Detection, Causes, and Mitigations

**Detection:**
- **Both training and validation metrics are poor** (low accuracy/high error on both).
- **Loss curves plateau quickly** at a high value — never converges.

**Primary Causes:**
- **Model too simple** (insufficient capacity/parameters to capture patterns).
- **Too few epochs/steps or too low learning rate** (not enough iterations to learn).
- **Under-representative features** (missing engineered variables, insufficient embeddings).
- **Excessive regularization** (too much dropout/weight decay suppressing signal).
- **Incorrect preprocessing** (poor scaling, missing normalization, wrong encoding).

**Mitigations — Exam-Essential Order:**

| Technique | Why it works | Implementation Notes |
|-----------|-------------|---------------------|
| **Add layers / increase units** | Increase model capacity to approximate target function | PyTorch/TensorFlow model definitions; SageMaker built-ins with `hidden_layer_sizes`, `num_layers` |
| **Train longer** | More epochs/steps allow gradient descent to reach lower loss | Increase `epochs` or `num_round` |
| **Raise learning rate** | Model updates further per step, avoids stuck in flat region | Hyperparameters `learning_rate`, `lr`, `eta` |
| **Reduce regularization** | Alleviate over-constraint on learning | Decrease `dropout`, `alpha`, `lambda`, `weight_decay` |
| **Add / improve features** | Provide more informative inputs to model | Feature engineering in preprocessing pipeline, SageMaker Processing |
| **Try higher-capacity algorithm** | E.g., replace linear model with gradient boosted trees, or linear with deeper neural network | SageMaker built-in algorithm choice |
| **Check data preprocessing** | Ensure normalized, scaled, correctly encoded inputs | Scikit-learn preprocessing in script mode |

> **Exam Gotcha:** Underfitting can result from **too low a learning rate** as well as **too few epochs** — both prevent convergence. Increasing `epochs` alone won’t fix a fundamentally too-simple model.

---

### Catastrophic Forgetting: Unique to Customization/Fine-Tuning

**Definition:** When fine-tuning a pre-trained model on a narrow domain, the model *overwrites* weights previously encoding general capability, causing degradation on out-of-domain or original tasks.

**Key Indicators:**
- Performance on **new task** improves.
- Performance on **old/general tasks** degrades significantly.
- Common in **foundation models (FMs)** and **incremental learning** scenarios.

**Mitigations — Exam-Essential Order:**

| Technique | How it works | AWS Service Implementation |
|-----------|-------------|---------------------------|
| **Mixed / Multi-task Fine-tuning** | Combine new-domain data with **general/corpus data** during fine-tuning | SageMaker JumpStart; Bedrock fine-tuning data preparation |
| **Freeze earlier layers (parameter-efficient)** | Only update final layers; keep base weights intact | LoRA, adapters, prefix tuning in Hugging Face PEFT with SageMaker |
| **Lower learning rate for fine-tuning** | Use much lower LR than initial training to prevent large weight shifts | Bedrock/SageMaker fine-tuning hyperparameters |
| **Regularization on old task** | Elastic Weight Consolidation / L2 constraint toward pre-trained weights | Custom implementation in script mode |
| **Replay / rehearsal** | Reuse or regenerate examples from old distribution during training | Custom dataset construction |
| **Distillation** (for smaller model customization) | Train smaller student model from larger teacher, preserving capability | Amazon Bedrock **Distillation** |

> **Exam Gotcha:** Catastrophic forgetting is **not** the same as overfitting. Overfitting is about train/val distribution mismatch; catastrophic forgetting is about **losing prior general ability** during customization. The exam asks remedies like "blend broader data into fine-tuning dataset."

---

### Regularization Techniques: When to Use What

| Technique | Applies To | Effect | Notes |
|-----------|-----------|--------|-------|
| **L1 (Lasso)** | Linear/regression models | Feature sparsity (drives weights to 0) | SageMaker Linear Learner `wd` / `l1` parameter |
| **L2 (Ridge/Weight Decay)** | Linear/regression/NN | Shrink weights, prevent blowup | `wd`, `weight_decay` |
| **Dropout** | Neural networks | Randomly zero hidden units during training | Reduces co-adaptation of neurons |
| **Batch Normalization** | Neural networks | Normalize layer inputs, reduces overfitting + speeds training | Improves stability, allows higher LR |
| **Data Augmentation** | Computer vision/NLP | Expanded data diversity | `ImageDataGenerator`, `transforms` module |
| **Early Stopping** | Any iterative algorithm | Stop when val metric plateaus | Requires validation set |
| **Ensembling** | Any model | Reduce variance of individual models | Bagging (Random Forest), Boosting (XGBoost) |

> **Exam Gotcha:** For XGBoost, **`gamma`** and **`min_child_weight`** are additional regularization hyperparameters commonly asked in exams.

---

### Choosing the Correct Remedy: Decision Matrix

| Question | If Yes | If No |
|----------|--------|-------|
| Both train and validation scores poor? | **Underfit** → More capacity/data, longer training | — |
| Train good, validation poor? | **Overfit** → Regularize, early stop, augment data | — |
| Was model pre-trained and now degrading on old tasks? | **Catastrophic forgetting** → Mixed fine-tune data, freeze layers, lower LR | — |
| Need to detect overfitting automatically? | Use **early stopping callback** with `patience` N | Rely on manual inspection |
| Need to reduce variance without new data? | **Ensemble** (bagging/boosting) or **k-fold CV** | — |
| Need to prevent overfitting in tree models? | Increase `min_child_weight`, `gamma`, `max_depth` reduction | — |
| Need to prevent underfitting in tree models? | Increase `max_depth`, `num_round`, `min_child_weight` decrease | — |

---

### SageMaker-Specific Implementation Details

**Early Stopping in Script Mode:**
```python

```

**Built-in algorithm hyperparameters for overfitting:**
- **XGBoost:** `early_stopping_rounds`, `eval_metric`, `gamma`, `min_child_weight`, `max_depth`, `subsample`
- **Linear Learner:** `early_stopping_rounds`, `wd`, `l1`, `l2`
- **DeepAR:** `test_quantiles`, `early_stopping_patience`

**Catastrophic forgetting in Bedrock:**
- **Fine-tuning:** Uses labeled input/output pairs; **no early stopping** (job-level); watch general capability loss.
- **Knowledge base / RAG route** avoids catastrophic forgetting entirely by using retrieval instead of weight updates.

> **Exam Gotcha:** If a solution needs to add domain knowledge without altering model weights (and without risk of catastrophe), choose **Amazon Bedrock Knowledge Bases / RAG** over fine-tuning.

### Common Exam Distractors

- **"Increase epochs to fix overfitting"** — Wrong; increases overfitting risk.
- **"Add regularization to fix underfitting"** — Wrong; worsens underfitting.
- **"Fine-tune on only new domain data"** — Leads to catastrophic forgetting; should blend data.
- **"Tuning objective metric direction"** — Misconfigured objective causes poor model *selection*, not train/val gap.
- **"Use model parallelism for overfitting"** — Irrelevant; parallelism is a compute strategy, not a generalization strategy.
- **"Early stopping replaces hyperparameter tuning"** — Wrong; they are complementary. Tuning searches HPO ranges, early stopping halts runs.

# Skill 2.2.6: Combine Multiple ML Models to Improve Performance or Reduce Cost

## Task 2.2: Train, fine-tune, and customize models for ML and AI solutions

---

## Core Concept & Business Objective

**Model combination** is an architectural decision that trades added complexity for improved accuracy or reduced inference cost. The primary AWS business objective is to maximize prediction quality per dollar spent while maintaining operational manageability.

| Combination Strategy | Primary Objective | Compute Trade-off | Typical Use Case |
|---|---|---|---|
| **Majority / Soft Voting** | Reduce individual model variance | Higher inference cost (N models) | Classification with heterogeneous models |
| **Weighted Averaging (Bagging)** | Stabilize high-variance models | Parallelizable; near-linear cost | Random Forest, XGBoost ensemble outputs |
| **Stacking (Meta-Learner)** | Correct systematic errors of base learners | Extra training stage + inference hop | Competitions, high-stakes predictions |
| **Boosting** | Reduce bias; sequential error correction | Sequential training; not easily parallelized | Tabular data with weak learners |
| **Multi-Model Endpoint (MME)** | Reduce infrastructure cost | Shared memory; cold-start latency risk | Hosting many similar models with sporadic traffic |
| **Cascade / Model Selection Routing** | Reduce average latency and cost | Requires router model + routing logic | Tiered predictions: cheap model first, escalate to expensive model |

---

## Key SageMaker AI Configuration Parameters

### Multi-Model Endpoint (MME) — Cost Consolidation

| Component | Parameter | Exam-Relevant Notes |
|---|---|---|
| **S3 Model Storage** | `s3://bucket/path/` | Models stored as `model.tar.gz` artifacts in a shared prefix |
| **IAM Role** | `sagemaker:InvokeEndpoint` + `s3:GetObject` | Role needs access to both S3 artifacts and endpoint invocation |
| **Endpoint** | `MultiModelConfig` | Set `Mode: MultiModel` |
| **Invocation** | `TargetModel` header | Specify which model to load at runtime — key Boto3 parameter: `TargetModel='model-v2.tar.gz'` |

```python

```

> **Exam Gotcha:** MMEs share the serving container and instance memory. If a target model is not already loaded, the first invocation triggers a cold start (loading from S3 to memory). MME is **not suited** for strict, low-latency SLA requirements or models requiring GPU acceleration.

### Multi-Container Endpoints (MCE) — Heterogeneous Model Serving

| Feature | Detail |
|---|---|
| **Purpose** | Host different model containers (e.g., XGBoost + PyTorch + TensorFlow) on one endpoint |
| **Routing** | Based on `Invocations` HTTP route (e.g., `/invocations`, `/invocations/model-a`) |
| **Memory allocation** | `iott.py` or `CPU/GPU` per container defined in inference pipeline config |
| **Anti-pattern** | Serial inference chains (ensemble within one endpoint) should use **Inference Pipelines** instead |

---

## Ensemble Techniques: When to Choose What

### Decision Matrix

| Symptom / Requirement | Recommended Ensemble | Reason |
|---|---|---|
| High variance across training runs | **Bagging / Voting** | Averaging reduces variance |
| Weak learners dominate | **Boosting (XGBoost, LightGBM, CatBoost)** | Sequential correction of errors |
| Base models make different types of errors | **Stacking** | Meta-learner learns how to combine diverse predictions |
| Latency-sensitive production traffic | **Single model or simple averaging** | Complex ensembles add inference time |
| Dozens/hundreds of low-traffic models | **Multi-Model Endpoint** | Shared infrastructure reduces cost |
| Need to serve heterogeneous model types | **Multi-Container Endpoint** | Different containers per model | 
| GPU memory constraint with large model | **Model parallelism (Sharding), not ensemble** | Ensemble duplicates memory, does not partition it |

> **Exam Gotcha:** **Model parallelism is NOT an ensemble technique.** Splitting a model across devices (e.g., SageMaker Model Parallelism Library, Tensor Parallelism) distributes one model to fit memory. Ensembles are **multiple complete models** combined at inference time. These are distinct and not interchangeable — choosing one over the other depends on whether the problem is memory footprint or prediction accuracy/cost.

---

## SageMaker Inference Pipelines (Serial Ensemble / Pre/Post Processing)

| Step | Purpose | Example |
|---|---|---|
| **Pre-processing container** | Feature engineering before inference | One-hot encoding, normalization, text vectorization |
| **Inference container(s)** | The model itself | XGBoost, Linear Learner, custom PyTorch model |
| **Post-processing container** | Prediction interpretation, thresholding | Softmax to label mapping, probability calibration |

```python
# Boto3 Inference Pipeline estimator
pipeline_model = PipelineModel(
    models=[preprocessor, model, postprocessor],
    role=role,
    models=[...]
)
```

> **Exam Gotcha:** Inference Pipelines run steps **sequentially on a single endpoint and share memory**. Do **not** confuse with MME where models are independent and loaded on demand. Pipelines are for **chained** operations, MME is for **parallel/independent** model hosting.

---

## Cost Reduction Alternatives to Ensembles

| Technique | Mechanism | Trade-off |
|---|---|---|
| **Knowledge Distillation** | Train smaller student model on teacher ensemble's predictions | Some accuracy loss; requires teacher inference at training time |
| **Model Pruning** | Remove low-magnitude weights | Minimal accuracy impact if <20% pruned |
| **Quantization (FP32 → INT8/FP16)** | Reduce numerical precision | Minimal accuracy loss; requires supported runtime |
| **Early exiting / Cascade** | Cheap model first; escalate to expensive model only when uncertain | Requires routing logic + confidence calibration |

> **Exam Gotcha:** Knowledge distillation trains a **single smaller model** to mimic an ensemble or large teacher. It reduces inference cost while retaining most of the ensemble's performance. The student model's inference cost is equivalent to a single model — not the full ensemble.

| Control | Requirement |
|---|---|

## Common Distractor Traps & Anti-Patterns

| Trap | Why It's Wrong | Correct Approach |
|---|---|---|
| **Use MME for strict low-latency single model** | Cold-start latency from S3 loading | Use standard single-model endpoint or prewarmed MME |
| **Ensemble to fix underfitting** | Underfitting indicates bias; ensembling reduces variance | Increase model capacity, add features, reduce regularization |
| **Boosting for parallel training speedup** | Boosting is sequential by design | Use bagging or data-parallel distributed training |
| **Ensemble when a single model suffices** | Added complexity and cost without measurable gain | Measure baseline; only ensemble if validation metric justifies |
| **MME for GPU-accelerated models** | Most MME infrastructure is CPU-optimized; GPU support limited | Use dedicated GPU endpoints or SageMaker Multi-container with GPU |
| **Confusing ensemble size with model parallelism** | More models = cost increase; model parallelism = memory reduction | Choose based on bottleneck: throughput vs memory |

# Skill 2.2.7: Adjust Fundamental Hyperparameters

### Core Hyperparameter Fundamentals

| Hyperparameter | Definition | Typical Impact | Exam Signal |
|---|---|---|---|
| **Epoch** | One complete pass over the entire training dataset | More epochs → better fit until overfitting begins | Track via validation loss curve, not training loss alone |
| **Batch size** | Number of samples processed before one weight update | Larger → more stable gradients, more memory; Smaller → noisier updates, better generalization | Powers of 2 (32, 64, 128, 256) are common defaults |
| **Learning rate (α)** | Step size for gradient descent updates | Too high → divergence/NaN loss; Too low → slow convergence or local minima | Most sensitive hyperparameter; tune first |
| **Steps** | Total number of parameter updates (batches processed) | Related to epochs: steps = epochs × (samples / batch_size) | For distributed/checkpoint settings, steps may be specified instead of epochs |
| **Validation frequency** | How often to evaluate on held-out set (per epoch or per N steps) | Affects early stopping accuracy and training overhead | SageMaker emits validation metrics to CloudWatch per configured interval |

---

### Decision Matrix: Adjusting Hyperparameters for Common Problems

| Symptom | Diagnostic Signal | Primary Fix | Secondary Fix |
|---|---|---|---|
| **Overfitting** | Train loss ↓, validation loss ↑ | Increase regularization (dropout, weight decay, L2) | Reduce epochs → enable early stopping; reduce model capacity; add data augmentation |
| **Underfitting** | Train loss high and validation loss high | Increase model capacity (layers, units) | Train more epochs; lower regularization; adjust learning rate |
| **Diverging loss (NaN)** | Loss explodes or becomes NaN | Decrease learning rate (10x reduction) | Add gradient clipping; reduce batch size; check data normalization |
| **Slow convergence** | Loss decreasing but plateauing slowly | Increase learning rate | Use learning rate warmup; switch optimizer (Adam vs SGD) |
| **Oscillating convergence** | Loss fluctuates around optimum | Decrease learning rate | Increase batch size; use learning rate decay/schedule |
| **Long training time** | Job runs too long to meet SLAs | Enable distributed data parallelism | Increase batch size; reduce epochs; use early stopping |

---

### Hyperparameter Values & Guidance

> **Exam Gotcha:** Hyperparameters are **not computed or analytically solved**—they are tuned via search (SageMaker AMT) or set by the ML engineer based on domain experience and experimentation.

**Batch Size Considerations:**
- **GPU memory bottleneck:** Reduce batch size until the model and optimizer state fits in GPU memory
- **Generalization benefit:** Smaller batches (< 64) often generalize better due to noisier gradients acting as implicit regularization
- **Throughput benefit:** Larger batches exploit GPU parallelism and reduce communication overhead in distributed settings
- **Batch normalization interaction:** Very small batches (< 8) destabilize BatchNorm statistics

**Epoch Considerations:**
- **Early stopping analog:** Set a high epoch ceiling with `EarlyStopping` callback monitoring `val_loss` with patience of 5–10 epochs
- **Fine-tuning pre-trained models:** Use far fewer epochs (1–5) than training from scratch to avoid catastrophic forgetting
- **SageMaker AMT interaction:** Epochs are often fixed during tuning; optimization focuses on learning rate, batch size, and architectural hyperparameters

**Learning Rate Considerations:**
- **Standard starting points:** `1e-3` for Adam; `1e-2` for SGD with momentum; `1e-5` to `1e-4` for fine-tuning LLMs
- **Schedules:** Use `StepDecay`, `CosineAnnealing`, or `ReduceLROnPlateau` for better convergence than constant rates
- **Warmup:** Linear warmup over first few hundred steps stabilizes training with large batch sizes and Transformer models

**Steps vs. Epochs:**
- **SageMaker built-in algorithms:** Some (e.g., XGBoost, Linear Learner) use `num_round` or `epochs`; TensorFlow/PyTorch script mode typically exposes `epochs`
- **Distributed training:** Steps per epoch = ceil(total_samples / (batch_size × num_instances))
- **Checkpoint frequency:** Set checkpoint every N steps (not epochs) to enable mid-epoch recovery for long jobs

### SageMaker AMT: Hyperparameter Search

| Search Strategy | When to Use | Notes |
|---|---|---|
| **Bayesian Optimization** | Budget ≥ 10 jobs; continuous or integer ranges | Uses past results to guide next sample; best for small search spaces |
| **Random Search** | Exploratory; many categorical parameters | Good coverage; simple; baseline for comparison |
| **Hyperband** | Early stopping of poor performers; large budget | Multi-fidelity; aggressively prunes underperforming configs early |

**Key AMT settings:**
- **Objective metric:** Must be emitted via `report` in script or from built-in algorithm; direction matters (`Minimize` vs `Maximize`)
- **Range types:** `ContinuousParameter`, `IntegerParameter`, `CategoricalParameter`
- **Completion criteria:** `MaxNumberOfTrainingJobs`, `MaxParallelTrainingJobs`, `TargetObjectiveMetricValue`
- **Warm start:** Reuse previous tuning job results to cut search time

> **Exam Gotcha:** AMT runs **separate training jobs** for each hyperparameter combination—it does not modify values within a single training run. Misconfiguring the objective metric direction (e.g., minimizing accuracy) results in the tuner "optimizing" toward the worst model.

### Early Stopping & Regularization

| Technique | Mechanism | Key Parameter | Trade-off |
|---|---|---|---|
| **Early stopping** | Halt training when validation metric fails to improve for `patience` epochs | `patience=5` (epochs) or `min_delta=0.001` | Prevents overfitting; may stop too early with noisy metrics |
| **Dropout** | Randomly zero out neurons during training | `dropout_rate=0.2–0.5` | Adds regularization; increases epochs needed for convergence |
| **Weight decay (L2)** | Penalize large weights in loss | `weight_decay=1e-4–1e-2` | Prevents overfitting; too high causes underfitting |
| **Gradient clipping** | Clip gradient norm to prevent explosion | `max_grad_norm=1.0` | Stabilizes training; essential for RNNs/LSTMs and LLMs |
| **Data augmentation** | Artificially expand dataset | Depends on modality | Reduces overfitting without changing model |

---

### Anti-Patterns & Common Distractor Traps

- **Tuning epochs during AMT instead of using early stopping:** Inefficient; wastes budget on jobs that overfit
- **Increasing batch size to fix overfitting:** Batch size primarily affects optimization stability, not generalization—use regularization instead
- **Using `steps` and `epochs` interchangeably:** They are mathematically related but not equal; `steps = epochs × ceil(total_samples / batch_size)`
- **Setting learning rate too high for fine-tuning:** Pre-trained weights are already good; small learning rates (`1e-5`) preserve them
- **Ignoring validation metrics in CloudWatch:** Training loss alone is misleading; always monitor `val_loss` or `val_accuracy`
- **Tuning one hyperparameter at a time (grid search):** Inefficient; use Bayesian optimization or random search to explore interactions

---

### Fine-Tuning LLM/FM Hyperparameters

| Parameter | Typical Range | Purpose |
|---|---|---|
| **Learning rate** | `1e-6` to `5e-5` | Preserve pre-trained knowledge |
| **Epochs** | `1–5` | Avoid catastrophic forgetting |
| **Batch size** | `8–64` (limited by GPU memory) | Balance stability and convergence |
| **Weight decay** | `0.01–0.1` | Prevent overfitting on small fine-tuning datasets |
| **LoRA rank (r)** | `4–64` | Lower rank = fewer trainable parameters, less overfitting |
| **LoRA alpha** | `16–32` | Scaling factor; typically 2× rank |
| **Max sequence length** | `512–4096` | Must match task context; longer requires more GPU memory |

> **Exam Gotcha for FM fine-tuning:** Catastrophic forgetting manifests as the model performing well on the fine-tuning task but losing general capability. Defenses: **mix general-domain data into the fine-tuning set**, use **low rank adaptation (LoRA)**, or apply **small learning rates**.

# Skill 2.2.8: Apply Customization Techniques for AI Solutions

## Core Decision Framework: Prompt Engineering vs. Fine-Tuning vs. Distillation

| Technique | Best When | Input Requirements | Cost/Latency Impact | Failure Mode |
|---|---|---|---|---|
| **Task-Specific Prompt Engineering** | Style/tone/format needs; few-shot examples sufficient | Curated prompt templates, few exemplars | No training cost; adds token overhead at inference | Prompt drift, token bloat, fragile to model version changes |
| **Supervised Fine-Tuning (SFT)** | Domain vocabulary, specific output structure, labeled data exists | Labeled input-output pairs (hundreds–thousands) | Training cost; inference latency unchanged | **Catastrophic forgetting** of general capabilities |
| **Reinforcement Fine-Tuning (RFT)** | Preference alignment, safety, quality scoring available | Reward functions that score model responses | Higher than SFT; requires reward signal design | Reward hacking—model optimizes proxy, not intent |
| **Distillation** | Reduce cost/latency for high-volume inference | Prompt set; teacher model generates synthetic labels | One-time generation + student training cost | Student capacity ceiling; teacher errors propagate |

> **Exam Gotcha:** Fine-tuning does **not** fix bad retrieval. If retrieved passages lack the answer, fix the embedding model, chunking, or reranking—**not** the generator.

---

## Prompt Engineering Best Practices (First Line of Optimization)

**Core components to include:**
- **Explicit instructions** with clear task definition
- **Stated output format** (JSON schema, markdown, specific structure)
- **3–5 worked examples** (few-shot) covering edge cases
- **Constraints** (max length, prohibited content, required fields)

**Operationalizing prompts:**
- Store prompts in **Prompt Management** (Bedrock) or **Parameter Store/SSM** with versioning
- Treat prompts as **versioned artifacts**—track changes, A/B test, roll back
- Use **variables** for dynamic content; never embed user input directly into system prompts without sanitization

**When prompting fails:** After iterative refinement, if the model still produces incorrect structure, hallucinates domain knowledge, or misses task-specific patterns, move to fine-tuning.

> **Exam Gotcha:** Prompt Engineering is **always the first technique** to attempt. Fine-tuning without first exhausting prompting is a distractor answer.

---

## Amazon Bedrock Customization Options

### 1. Supervised Fine-Tuning (SFT)
- **Data format:** JSONL with `{"prompt": "...", "completion": "..."}` pairs
- **Pre-requisites:** Labeled dataset in Amazon S3; model access granted in Bedrock
- **Output:** A **custom model** (provisioned throughput required for inference)
- **IAM:** Bedrock requires `bedrock:CreateModelCustomizationJob`, `s3:GetObject` on training data, `s3:PutObject` on output bucket

### 2. Reinforcement Fine-Tuning (RFT)
- **Input:** Reward function that scores responses (Python, runs in Bedrock-managed environment)
- **Use Case:** Align outputs to brand voice, safety guidelines, or user preferences where pairwise comparison is easier than absolute labels
- **Key nuance:** Reward model is **not the same** as the generation model being tuned

### 3. Distillation
- **Input:** Prompt set (no labels required)
- **Process:** Bedrock uses a **teacher model** to generate responses, then trains a **smaller student model** to match the teacher
- **Business objective:** Reduce inference cost/latency for high-volume workloads while retaining ~90–95% quality

| Customization Type | Data Requirement | Bedrock API | Provisioned Throughput Required? |
|---|---|---|---|
| SFT | Labeled prompt-completion pairs | `CreateModelCustomizationJob` | Yes—custom models require provisioned throughput |
| RFT | Reward function + prompt dataset | `CreateModelCustomizationJob` | Yes |
| Distillation | Prompt set only | `CreateModelCustomizationJob` | Yes |

> **Exam Gotcha:** Customized Bedrock models require **Provisioned Throughput** for inference—you cannot use on-demand pricing with fine-tuned models. This is a common cost-related distractor.

- Working with **open-weight models** (Llama, Mistral, Falcon) not available in Bedrock

- Need to **deploy to SageMaker endpoints** (not Bedrock-managed endpoints)

## Catastrophic Forgetting Defense Strategies

**Symptoms:** After fine-tuning, model performs well on narrow domain but **degrades on general tasks** it previously handled well.

**Defenses (ranked by effectiveness):**
1. **Mix training data**: Blend 10–30% general-purpose examples with domain-specific data
2. **Low learning rate**: Use 10×–100× smaller LR than base model pre-training (e.g., 1e-5 to 5e-5)
3. **PEFT/LoRA**: Freeze base weights; train only adapter layers—preserves general capabilities
4. **Early stopping**: Monitor validation loss on held-out general task set; stop before degradation
5. **ELM (Elastic Weight Consolidation)**: Add penalty for large weight changes on important parameters (advanced)

> **Exam Gotcha:** "Increase the learning rate to learn domain knowledge faster" is a **wrong answer** in fine-tuning scenarios—it accelerates catastrophic forgetting.

## Retrieval Component Optimization (RAG Customization)

**Diagnostic rule:** Before customizing the generator, classify the failure:
- **Retrieval failure** → passages don't contain the answer → fix retrieval
- **Generation failure** → passages contain the answer but output is poor → fix prompt or fine-tune

**Retrieval optimization levers:**

| Component | What to Tune | Key Metrics |
|---|---|---|
| **Embedding model** | Choose domain-appropriate model (e.g., `Cohere Embed v3` for multilingual, `Amazon Titan v2` for general-purpose) | Recall@k, MRR, nDCG |
| **Chunking strategy** | Size (typically 256–1024 tokens), overlap (10–20%), semantic vs. fixed-size | Chunk coherence, retrieval precision |
| **Retriever** | k-NN top-k values, hybrid search (BM25 + vector), metadata filtering | Precision@k, latency |
| **Reranker** | Cross-encoder models for second-stage ranking | Precision improvement |

**Bedrock Knowledge Bases** configuration:
- **Chunking options**: Fixed-size, semantic, hierarchical, or no chunking
- **Embedding model**: Select at KB creation—cannot be changed later without rebuilding
- **Vector store**: OpenSearch Serverless (default), Pinecone, Redis Enterprise Cloud, or Amazon Aurora PostgreSQL

# Skill 2.2.9: Optimize retrieval components and embedding models

## Task 2.2: Train, fine-tune, and customize models for ML and AI solutions

---

## Core Objective

Retrieval-Augmented Generation (RAG) quality depends on **what the retriever returns** before the generator ever speaks. Optimize the **embedding model → chunking strategy → vector store → retriever/ranker** pipeline to maximize context relevance and answer fidelity.

> **Exam Gotcha:** If retrieved passages fail, no prompt change or model fine-tune will fix the answer. Diagnose retrieval vs. generation failure **before** choosing a remedy.

---

## Embedding Model Selection

| Criterion | Recommendation | Notes |
|-----------|---------------|-------|
| **Domain-specific language** | Fine-tune embeddings or use domain-adapted embedding model (e.g., SageMaker JumpStart embeddings) | Generic embeddings underperform on jargon (medical, legal, engineering) |
| **Multilingual queries** | Use multilingual embedding model (e.g., Cohere Embed v3, Amazon Titan Multimodal) | Single model for multiple languages vs. per-language models |
| **Query vs. passage symmetry** | Use same embedding model for both queries and documents | Asymmetric embeddings break cosine similarity assumptions |
| **Vector dimension size** | Higher dimensions = more precision, more storage/memory cost | May justify 384–768 dims for balance; 1024+ for high precision |
| **Max input length** | Choose embedding model with context window ≥ your chunk size | Truncation silently discards text, harming retrieval |

**SageMaker AI embedding options:**
- **JumpStart** pre-trained embedding models (Hugging Face sentence-transformers, E5, BGE)
- **BlazingText** (`supervised` mode) for custom word/sentence embeddings via fastText
- **TensorFlow/PyTorch script mode** for fine-tuning Bi-encoders with contrastive loss
- **Bedrock Knowledge Bases** for managed embeddings (Titan Text Embeddings v2, Cohere Embed)

---

## Chunking Strategy Optimization

| Technique | Best For | Trade-off |
|-----------|----------|-----------|
| **Fixed-size with overlap** | Simple documents, quick baseline | May split semantic units; overlap mitigates at token cost |
| **Sentence-level / semantic** | Coherent queries needing precise retrieval | Requires sentence segmentation; may fragment context |
| **Recursive / token splitting** | Long structured docs (e.g., whitepapers, contracts) | More complex; better section preservation |
| **Document-structure-aware** (headers, tables, code blocks) | PDFs, markdown, HTML docs | Requires custom parser; highest retrieval precision |
| **Small chunk size (100–200 tokens)** | Granular facts, QA over specific snippets | Loses broader context; more chunks to store/query |
| **Large chunk size (500–1000+ tokens)** | Summarization, document-level reasoning | Dilutes semantic signal; introduces noise |

> **Exam Gotcha:** Chunk size is a **retrieval quality** trade-off, not just a cost decision. Chunks too large average out embeddings (washing out distinct topics), while chunks too small fragment multi-sentence facts.

**Overlap settings:** 10–15% overlap preserves boundary context; too high overlap wastes vector storage and query latency.

---

## Retriever & Ranking Optimization

| Component | Options | When to Use |
|-----------|---------|-------------|
| **Vector search engine** | OpenSearch Serverless, Amazon Kendra, Pinecone, pgvector (RDS) | Default for dense embedding retrieval |
| **Hybrid search** | BM25 + dense vector (OpenSearch, Kendra) | Improves recall when exact terms matter (IDs, product codes, acronyms) |
| **Re-ranking model** | Cross-encoder (e.g., `cross-encoder/ms-marco-MiniLM-L-6`) or SageMaker hosted reranker | Apply after vector search to re-sort top-N; boosts precision |
| **Metadata filtering** | Filter on fields (date, category, author) before/after vector search | Shrinks search space; prevents irrelevant-but-similar documents |

**Re-ranking pipeline pattern:**
1. Retrieve top 50–100 chunks via vector similarity
2. Run cross-encoder on query + each chunk
3. Keep top 3–10 for generation context

> **Exam Gotcha:** Cross-encoders are too slow for full corpus scoring. Use a **two-stage** retrieval architecture: fast bi-encoder (vector search) → slow cross-encoder (re-rank top-N only).

## Bedrock Knowledge Bases Components

| Setting | Impact |
|---------|--------|
| **Embedding model** (Titan v2, Cohere Embed v3) | Fixed for the KB after creation; changing requires rebuilding vector index |
| **Chunking strategy** (fixed-size, semantic, custom parser via Lambda) | Cannot be changed after KB creation without re-ingest |
| **Vector database** (OpenSearch Serverless, Aurora PostgreSQL, Pinecone) | Automatic setup for OpenSearch; bring-your-own for others |
| **Maximum tokens per chunk** | Set below embedding model context limit |
| **Overlap percentage** | Typically 10–15% to preserve multi-chunk context |

> **Exam Gotcha:** Bedrock Knowledge Bases **locks** chunking and embedding model at creation. Changing them requires creating a new KB and re-syncing data sources.

## Optimization Signals & Metrics

| Metric | Indicates | Action |
|--------|-----------|--------|
| **Hit rate / recall@k** | Proportion of queries where correct doc appears in top-k retrieved | Increase k, improve chunking, use hybrid search |
| **MRR (Mean Reciprocal Rank)** | Average rank position of first correct document | Improve ranking model, fine-tune embeddings |
| **nDCG** | Ranking quality across multiple relevant docs | Add cross-encoder re-ranker |
| **Context-faithfulness** | Answer grounded in retrieved context or hallucinated | Reduces retrieval trust requirement |

## Embedding Fine-Tuning for Domain Adaptation

**When to fine-tune:**
- Generic embeddings retrieve irrelevant passages on domain corpus
- Vocabulary includes domain jargon, acronyms, internal entity names
- Labeled pairs/queries with relevant vs. non-relevant documents are available

**Approach (SageMaker script mode):**
1. Build **contrastive learning dataset** — positive pairs (query + relevant doc), negative pairs (query + non-relevant doc)
2. Choose pre-trained sentence-transformer checkpoint (`all-MiniLM-L6-v2`, E5, BGE)
3. Fine-tune with **InfoNCE / MultipleNegativesRankingLoss** or **cosine similarity contrastive loss**
4. Evaluate on held-out query–document relevance set (recall@k, MRR)

> **Exam Gotcha:** Fine-tuning an embedding model on **unlabeled** corpus alone does not help. You need **labeled query–document relevance** pairs for contrastive fine-tuning.

**Alternative:** Use SageMaker JumpStart pre-trained domain embeddings before fine-tuning from scratch. Custom embeddings are a higher-effort, higher-reward path.

---

## Anti-Patterns & Traps

- **Changing the generator (temperature, prompt, fine-tune) when retrieval is failing** — retrieval has no answer so generator hallucinates or hedges.
- **Using same chunk size for all document types** — PDFs need structure-aware parsing; code files need line-aware splitting.
- **Over-large chunks** — dilutes semantic specificity; nearest-neighbor score becomes less meaningful.
- **Neglecting hybrid search for exact identifiers** — numbers, SKUs, product codes need lexical (BM25) match alongside dense retrieval.
- **Skipping re-ranking** — top-10 vector search results may still be loosely related; cross-encoder re-ranking noticeably raises precision.
- **Rebuilding KB frequently** — Bedrock KB locks parameters at creation; plan chunking and embedding model before first build.

## Experiment Tracking with SageMaker AI + MLflow

**Core Purpose:** Record every run's parameters, metrics, artifacts, and lineage so comparisons are auditable and reproducible—critical for ML governance, debugging variance, and regulatory compliance.

### Key Capabilities

- **Automatic tracking:** Parameters (hyperparameters, seeds, data versions), metrics (loss, accuracy, F1), artifacts (model files, confusion matrices, feature importance plots)
- **Generative AI tracing:** Captures inputs/outputs/metadata at each step of an LLM application (prompt → embedding → retrieval → generation) to debug unexpected outputs
- **Run comparison:** Diff two runs side-by-side to identify root causes of score divergence (unseeded initialization, package drift, data mutation)

### SageMaker AI MLflow Configuration

| Setting | Purpose | Exam Note |
|---------|---------|-----------|
| `MLFLOW_TRACKING_URI` | Points to tracking server ARN | Managed by SageMaker; no manual server setup |
| `mlflow.sagemaker` integration | Log SageMaker training jobs automatically | Use `mlflow.sagemaker.autolog()` in training scripts |
| Artifact storage | S3 bucket (implicit via SageMaker session) | Encrypts at rest with KMS |
| Run metadata | Parameters + metrics + tags | Tags enable filtering (e.g., `env:prod`, `version:v2`) |

### Anti-Patterns
- Cherry-picking the best run and deleting others → destroys variance evidence
- Relying on a single accuracy figure without recording inputs and environment → cannot explain *why* scores changed
- Skipping `random_seed` logging → non-deterministic results become unexplainable

**Core Purpose:** Run structured evaluation jobs against FMs or RAG sources—either programmatically (automated metrics), via LLM-as-a-judge (model scores with explanation), or via human raters.

## Drift Detection Patterns

| Drift Type | Detection Signal | Metric/Threshold | Suggested Alert |
|---|---|---|---|
| **Data Distribution** | Input feature distributions depart from baseline | Population Stability Index (PSI) > 0.1–0.25 | CloudWatch Alarm → SNS |
| **Prediction Drift** | Model output distribution shifts | KL divergence, JS distance, Chi-square over prediction bins | SNS → retrain pipeline trigger |
| **Label Drift** | Ground truth outcomes change vs baseline (delayed by merge job) | Compare AUC/F1 of deployed model against baseline on new labels | SageMaker Model Monitor ≥ 1 baseline job |
| **Bias Drift** | CDDPL or DPL exceeds SOC thresholds | CDDPL ≥ 0.8 → immediate P1 alert; DPL thresholds by use-case | Clarify monitoring job → EventBridge |
| **SHAP Drift** | Feature attributions shift meaning | Normalized discounted cumulative gain over feature ranks | Detailed investigation via Notebook |

> **Exam Gotcha:** PSI thresholds are not universal—0.1 flag, 0.25 alert is a common heuristic. If the exam offers an AWS-native preference, choose SageMaker Model Monitor with *statistical bias* as the automated solution before selecting custom Lambda-based checks.

## Anti-Patterns & Distractor Traps

- **Relying solely on training time validation metrics as baseline** — unacceptable because data drift cannot be detected without production input distributions.
- **Setting drift thresholds too tight** → alarm fatigue; or too loose → missed degradation.
- **Capturing only input, not output, when ground truth joins are needed** — ModelQuality jobs require both prediction and ground truth (merged via `join_source: {"Input": ..., "Output": ...}`); DataQuality is input-only.
- **Overlooking periodic re-baselining** — after retraining or feature changes, baseline must be regenerated. Using stale `constraints.json` creates false positives.
- **Confusing A/B testing with shadow testing for baseline comparison** — A/B changes caller-facing responses; shadow tests log without altering responses, both useful but only shadow preserves caller experience.
- **Ignoring label drift** — model degradation not visible from input features alone; requires delayed ground truth labeling and scheduled `ModelQuality` jobs.

> **Exam Gotcha:** If a question says "callers must not be impacted" and includes "live traffic" as the evaluation source, choose **SageMaker Shadow Testing** or **Model Monitor**; if it requires "split live response" → that is A/B, reject it.

# Skill 2.3.3: Compare the Performance of Shadow Variants to Production Variants

## Task 2.3: Analyze and Evaluate the Performance of ML and AI Systems

---

### Core Concept & Business Objective

**Shadow testing** validates a candidate model/container/instance configuration against **real production traffic** with **zero customer impact**. Production answers all callers; the shadow variant receives an async copy of the request and logs its response for offline comparison.

- **Primary Goal:** Prove a change behaves correctly under real-world payloads, concurrency, and latency before exposing it to users.
- **What Gets Compared:** Predictions, latency (p50/p90/p99), error rates, throughput, and resource utilization.
- **Business Value:** De-risks deployments that offline evaluation alone cannot validate—request shapes, payload sizes, and traffic spikes not present in stored datasets.

---

### Shadow vs. Production: Architectural Trade-offs

| Deployment Pattern | Caller Receives | Purpose | Exam Signal Word |
|---|---|---|---|
| **Shadow Test** | Production response only | Compare candidate on live traffic copy | "Zero impact," "copy of live requests" |
| **A/B Test / Canary** | Candidate may serve some % | Measure business outcome against control | "Split traffic," "percentage rollout" |
| **Blue/Green** | New version serves all after cutover | Instant rollback via endpoint flip | "Single endpoint switch" |
| **Offline Evaluation** | N/A (stored dataset) | Pre-deployment scoring | "Before deploying," "benchmark dataset" |

> **Exam Gotcha:** A/B or canary splits route **live users** to the candidate. A shadow test never exposes candidate responses to callers. If the question states "callers must keep receiving production responses," the answer is **always** shadow testing.

---

### Key Configurations & Implementation Notes

- **Deployment Mechanism:** Add a shadow variant to an existing SageMaker AI endpoint using `ProductionVariants` alongside `ShadowProductionVariants` in the endpoint configuration.
- **Traffic Routing:** SageMaker automatically mirrors a configurable percentage (default: 100%) of incoming requests to the shadow variant; responses are **discarded** from the response path.
- **Region Support:** Shadow testing is available only in endpoints with **data capture enabled**—logs are stored in Amazon S3 for offline comparison.
- **Latency Measurement:** Shadow latency is measured end-to-end from request receipt to response generation, **not** including the async dispatch overhead.

**Boto3/CLI Parameter Nuances:**

```
aws sagemaker update-endpoint \
  --endpoint-name my-endpoint \
  --endpoint-config-name my-config \
  --retain-all-variant-properties

# EndpointConfig structure:
{
  "ProductionVariants": [{"VariantName": "prod-v1", "InitialVariantWeight": 1}],
  "ShadowProductionVariants": [{
      "VariantName": "shadow-v1",
      "ModelName": "candidate-model",
      "InitialInstanceCount": 2
  }]
}
```

---

### Comparison Metrics to Log & Analyze

| Metric Category | What to Compare | Why It Matters |
|---|---|---|
| **Operational** | Latency (p50/p90/p99), error rate, CPU/GPU utilization | Catches infra regressions invisible in offline tests |
| **Prediction Quality** | Shadow predictions vs. production predictions (agreement rate, drift in distribution) | Detects behavioral divergence on real data |
| **Request Shape** | Payload size, feature ranges, missing fields | Identifies production data patterns absent from training/validation sets |
| **Throughput** | Requests/sec, concurrent request handling | Validates autoscaling and capacity assumptions |

> **Exam Gotcha:** SageMaker shadow testing **does not** automatically compute prediction-quality comparisons. You must log shadow responses via Data Capture and run offline analysis (e.g., in Amazon CloudWatch, Athena over S3, or a custom pipeline). The shadow variant only mirrors traffic—it does not score predictions against labels unless you build that pipeline. Shadow tests validate *operational behavior* and enable *offline* model quality comparison.

---

### Anti-Patterns & Common Distractor Traps

| Distractor | Why It's Wrong |
|---|---|
| "Use SageMaker Model Monitor with a baseline" | Model Monitor detects **drift post-deployment**; it does not compare a shadow variant against production on live requests. |
| "Run an Amazon Bedrock programmatic evaluation" | Bedrock evaluations score models on **stored prompt datasets**, not live traffic streams. |
| "Create an MLflow tracking run" | MLflow tracks training experiments—parameters, metrics, and artifacts—not endpoint traffic mirroring. |
| "Replace production variant and watch error rate" | Exposes real users to candidate—violates the zero-impact constraint. |
| "Send half of traffic to candidate" | That's an A/B test, not a shadow test; callers receive candidate responses. |

---

### When to Use Shadow vs. Alternatives

**Choose SageMaker Shadow Testing when:**
- Candidate uses a different container image, framework, instance type, or inference code path.
- Need to validate against production traffic patterns without customer exposure.
- Comparing operational metrics (latency, error rate) under real concurrency.

**Choose Bedrock Evaluations when:**
- Evaluating a **foundation model** (not a SageMaker endpoint) on a curated prompt dataset.
- Running programmatic (ROUGE/BLEU/BERTScore), LLM-as-a-judge, or human-based scoring jobs.

**Choose MLflow on SageMaker when:**
- Tracking training runs, hyperparameters, artifact lineage, or tracing GenAI application steps.

**Choose SageMaker Model Monitor when:**
- Post-deployment monitoring of a **single live variant** for drift against a baseline.

---

### Key Takeaways for the Exam

- **Shadow = live traffic mirror, production answers, candidate logged.**
- **Data capture must be enabled** on the endpoint for shadow testing to log responses to S3.
- **Shadow testing is an operational validation tool**—it tells you the candidate survives real traffic; quality comparison requires separate offline analysis of logged predictions.
- **Latency measurement nuance:** SageMaker reports shadow latency excluding async dispatch overhead.
- **Do not confuse shadow with A/B testing**—A/B exposes users to both variants; shadow exposes users to only one.
- **SageMaker shadow tests support real-time inference endpoints**, not serverless inference or batch transform.

# Skill 2.3.4: Explain Model Outputs

## Task 2.3: Analyze and Evaluate the Performance of ML and AI Systems

---

### Core Concept & Business Objective

**Explanation ≠ Evaluation.** An evaluation score tells *how well* a system performed; an explanation tells *why* a specific output emerged. This distinction is critical for auditors, regulators, and stakeholders who need defensible, traceable AI decisions.

**Primary objective:** Provide audience-appropriate, source-attributable explanations for both traditional ML predictions and FM-generated answers so decisions can be audited, debugged, and trusted.

---

### Explanation Techniques: Traditional ML vs. GenAI

| Output Type | Technique | AWS Service / Tooling | What It Reveals |
|---|---|---|---|
| **Tabular/Classification/Regression** | Feature attribution (SHAP, feature importance) | SageMaker Clarify | Which input features drove a specific prediction |
| **Tabular/Classification/Regression** | Partial dependence plots, surrogate models | SageMaker Model Monitor + custom analysis | Directional effect of features on outputs |
| **FM-generated text (RAG)** | Source passage citation / retrieval trace | Bedrock Knowledge Bases + Bedrock Evaluations (retrieval metrics) | Which retrieved chunk informed the generated answer |
| **FM-generated text (non-RAG)** | LLM-as-a-judge explanation + chain-of-thought scoring | Bedrock Evaluations (judge model mode) | Why a judge model rated a response as correct/incorrect |
| **FM-generated text (human-facing)** | Human-readable rationale appended to output | Bedrock Prompt Management (templated explanation format) | Stakeholder-facing justification with confidence |

> **Exam Gotcha:** A customized (fine-tuned) model **cannot** point to its source documents. Only a RAG architecture can trace an answer to a retrieved passage. If an auditor demands source attribution, the answer is RAG—not fine-tuning.

---

### SageMaker Clarify: Explaining Traditional Model Outputs

| Feature | Purpose | Key Parameter / Config |
|---|---|---|
| **SHAP values** | Per-prediction feature attribution | `explainability_config` with SHAP baseline |
| **Feature importance** | Global model-level ranking | Computed on training or validation dataset |
| **Partial dependence plots** | Feature-to-output relationship | Supplied in bias report / explainability report |
| **Bias detection** | Pre-training, in-training, post-training bias metrics | Monitors sensitive attributes (e.g., gender, race) |

**Key boto3 pattern:**
```python

clarify_processor.run_explainability(
    data_config=..., model_config=..., explainability_config=...,
    model_scores=..., 
)
```

> **Exam Gotcha:** Clarify's SHAP explanations require a **baseline dataset** (representative sample) for marginal contribution calculations. Missing baseline = Clarify job fails silently or returns meaningless attributions.

---

### RAG Output Explanation: Retrieval Traceability

To explain a RAG-generated answer, split the pipeline and monitor each layer separately:

| Layer | What to Measure | Metric | Tool |
|---|---|---|---|
| **Retrieval** | Did the retriever find the relevant chunks? | Context Precision, Context Recall | Bedrock Knowledge Bases → Bedrock Evaluations |
| **Generation** | Did the LLM faithfully use retrieved context? | Faithfulness (hallucination detect), Answer Relevance | Bedrock Evaluations (programmatic or judge mode) |
| **End-to-end** | Did the answer satisfy the question? | Answer Correctness, BERTScore | Bedrock Evaluations (programmatic) |

> **Exam Gotcha:** A fluent answer that omits facts found in source documents is a **retrieval failure**, not a generation failure. Always measure retrieval separately from generation to identify root cause.

---

### LLM-as-a-Judge: Automated Explanation

**When to use:** Scaling output assessment beyond human review capacity; providing consistent scoring with rationale.

| Mode | Judge Model Role | Output Format | Key Config |
|---|---|---|---|
| **Programmatic** | N/A (rule/metric-based) | Numeric score only | Predefined metrics (BLEU, ROUGE, BERTScore) |
| **LLM-as-a-Judge** | FM scores response against rubric | Score + natural-language explanation | Custom prompt with scoring criteria |
| **Human-based** | Human workers (SMEs, Mechanical Turk) | Rating with optional feedback | Requires browser UI for rating interface |

> **Exam Gotcha:** Human-based evaluation jobs created in the Bedrock console **require a browser-facing display** because raters must visually interact with prompts/responses. Automated jobs have no such requirement.

---

### Common Distractor Traps

| Incorrect Choice Pattern | Correct Reasoning |
|---|---|
| "Use accuracy to evaluate text generation quality" | Accuracy fails because multiple wordings can be correct; need overlap + semantic metrics + judgment |
| "Measure only the final answer to diagnose RAG failure" | Black-box measurement cannot distinguish retrieval vs. generation root cause |
| "Use feature attribution (SHAP) to explain an FM's generated text" | SHAP applies to tabular/traditional models; FM explanation requires retrieval trace or judge rationale |
| "Replace model and monitor error rate to compare variants" | In-place replacement exposes users to candidate; use shadow testing instead |
| "Fine-tune a model to enable source citation for auditing" | Fine-tuning bakes knowledge into weights—no source traceability. Only RAG provides citations. |

---

### Security & Compliance Considerations

| Requirement | Best Practice |
|---|---|
| **Audit trail for explanations** | Log explanation outputs alongside predictions to CloudWatch Logs / S3 for replay |
| **Sensitive attributes in explanations** | Use Clarify with `sensitive_data` config; restrict access via IAM conditions |

> **Exam Gotcha:** SageMaker Clarify works with **models deployed on SageMaker endpoints** or **batch transform jobs**—not arbitrary external endpoints. Ensure the model is deployed in SageMaker before invoking explainability.

# Skill 2.3.5: Debug Model Convergence Issues

## Task 2.3: Analyze and evaluate the performance of ML and AI systems

---

## Convergence Failure Signature Chart

| Loss Pattern | Primary Diagnosis | First Action |
| :--- | :--- | :--- |
| **Oscillating / bouncing loss** | Learning rate too high | Reduce LR by factor of 10; add LR scheduler |
| **Slow, steady decrease (plateau)** | LR too low OR model capacity insufficient | Increase LR; add layers/width/features |
| **NaN/Inf loss** | Exploding gradients (LR too high, unnormalized data) | Gradient clipping, input normalization, lower LR |
| **Train ↓, Validation ↑ (diverging gap)** | Overfitting | Regularization, dropout, early stopping, more data |
| **Train & Val both high (flatlined)** | Underfitting / capacity ceiling | More features, deeper model, reduce regularization |
| **Sharp drop then immediate plateau** | Dead ReLU units / saturation | Check activation outputs; Swap to Leaky ReLU; re-init weights |

> **EXAM GOTCHA:** Oscillating loss is **always** learning rate as the *first* hyperparameter to inspect — not batch size, not optimizer choice. Batch size changes may require LR re-tuning, but the oscillation signature itself points to step size overshoot.

---

## Diagnostic Workflow (Order of Operations)

1. **Record baseline curves** — Always log train *and* validation loss per epoch (e.g., MLflow `mlflow.log_metric("val_loss", val_loss, step=epoch)`).
2. **Inspect gradient magnitude** — Monitor gradient norms; if `grad_norm > 100`, apply clipping (e.g., `tf.clip_by_norm` / `torch.nn.utils.clip_grad_norm_`).
3. **Check data pipeline** — Shuffle training data; verify no label leakage; normalize/standardize float inputs (`StandardScaler`, `Normalize`).
4. **Adjust optimizer / schedule** — Swap Adam→SGD only if needed; introduce `CosineDecay` or `ReduceLROnPlateau`.
5. **Verify model capacity** — Run a tiny batch to overfit; if model cannot overfit one batch, capacity is insufficient.
6. **Inspect activations** — Log layer output distributions; detect dead ReLUs (all-zero activations) or exploding outputs.

---

## PyTorch / TensorFlow / SageMaker-Specifics

| Framework | Key Tool | Common Flag / Parameter |
| :--- | :--- | :--- |
| **PyTorch** | `torch.nn.utils.clip_grad_norm_` | `max_norm=1.0` |
| **TensorFlow / Keras** | `tf.keras.optimizers.schedules` | `ExponentialDecay(initial_lr, decay_steps, decay_rate)` |
| **SageMaker Training** | `DebuggerHookConfig` | Tensors: `Loss`, `Gradients`; Rules: `Overfit`, `LossNotDecreasing` |
| **SageMaker Debugger** | `ProfilerConfig` | System metrics: CPU/GPU utilization, I/O wait time (slow data pipeline) |

> **EXAM GOTCHA:** SageMaker Debugger **rules** (e.g., `Overfit`, `VanishingGradient`, `LossNotDecreasing`) auto-detect convergence issues during training but **do not fix them** — they emit CloudWatch Events for human/automated intervention.

---

## RAG / FM Convergence Considerations

| Context | Convergence Issue | Fix |
| :--- | :--- | :--- |
| **Distributed training (data parallel)** | Divergence after batch size increase | Scale LR linearly (`lr = base_lr × world_size`) |
| **Reinforcement learning (RL)** | Policy loss oscillates | Increase entropy coefficient, reduce LR, use PPO clipping |
| **LLM fine-tuning (LoRA/PEFT)** | No loss improvement | Increase LoRA rank (`r=16→64`); ensure trainable params frozen correctly |
| **Generative adversarial networks (GANs)** | Discriminator loss → 0, Generator loss → high | Rebalance training ratio (train discriminator less frequently) |

---

## Anti-Patterns & Traps

- **Restarting a failed training run without changing anything** — the same failure will repeat.
- **Only logging final loss** — without per-epoch curves, convergence issues are undiagnosable.
- **Tuning batch size without adjusting LR** — LR and batch size are coupled; large batch often requires higher LR.
- **Applying early stopping on oscillating curves without first fixing LR** — masking the root cause.
- **Assuming distributed training always converges faster** — communication overhead can slow convergence; smaller batch per worker may destabilize.
- **Using `ReduceLROnPlateau` with `patience=1`** — prematurely reduces LR on noise, hiding real signal.

## Formula Reference

| Metric | Formula / Definition |
| :--- | :--- |
| **Train-Val gap** | `|train_loss - val_loss|` — gap widening = overfitting |
| **Gradient norm** | `‖∇θ L‖₂` — stable range: `0.1–10`; explosive if `>100` |

## Rapid Decision Matrix

| Symptom | Action |
| :--- | :--- |
| Loss jumps wildly epoch-to-epoch | Lower LR by 10x → if still oscillating, check data shuffling |
| Loss decreases then suddenly spikes | Suspect a bad data batch → validate data pipeline |
| Validation loss better than train loss | Underfitting, or validation set too easy/leaked |
| Loss stuck at ~0.69 (binary CE) | Model outputting random guesses — capacity/features insufficient |
| Loss stuck at ~2.30 (multi-class CE) | Same: near-uniform random output |
| Train loss perfect, val loss terrible | Severe overfitting — add dropout/weight decay/early stop |

## Traditional ML Evaluation Core Techniques

**Classification metrics by problem type:**
- **Binary classification:** AUC-ROC, Log Loss, F1 (when class imbalance), Precision-Recall AUC
- **Multiclass:** Macro-F1 (class balance), Micro-F1 (label frequency), Cohen's Kappa (agreement)
- **Highly imbalanced:** Precision@K, Average Precision, Matthews Correlation Coefficient

**Regression metrics selection:**
- **RMSE:** Penalizes large errors heavily; sensitive to outliers
- **MAE:** Robust to outliers; linear error scale
- **MAPE:** Percent-based; fails when target contains zeros
- **R²:** Explains variance proportion; misleading for non-linear relationships

**Validation strategies:**
- **Stratified k-fold:** Preserves class proportions; mandatory for imbalanced data
- **Time-series split:** Forward-chaining only; never use random splits on temporal data
- **Group k-fold:** Prevents data leakage when samples belong to the same entity/group

> **Exam Gotcha:** Shuffling time-series data before splitting introduces lookahead bias. Time-series splits must preserve chronological order, with no future data in training folds.

---

## GenAI Text Evaluation Metrics

### Overlap-Based (N-gram) Metrics

| Metric | Focus | Best For | Weakness |
|--------|-------|----------|----------|
| **BLEU** | Precision of n-grams | Machine translation | Penalizes valid paraphrases; poor for short answers |
| **ROUGE-N** | Recall of n-grams | Summarization | Rewards verbosity; misses semantic equivalence |
| **ROUGE-L** | Longest common subsequence | Summarization | Struggles with reordered content |
| **METEOR** | Precision + recall + synonym matching | Translation | Requires synonym/paraphrase tables |

### Embedding-Based (Semantic) Metrics

- **BERTScore:** Cosine similarity between contextual embeddings; aligns tokens via greedy matching
- **Sentence-BERT Similarity:** Mean-pooled sentence embeddings for paraphrase detection
- **Semantic Answer Similarity (SAS):** Cross-encoders for question-answer pair scoring

> **Exam Gotcha:** Overlap metrics (ROUGE/BLEU) fail to recognize meaning when wording differs significantly. Embedding-based metrics (BERTScore) capture semantic similarity but may miss factual correctness. For GenAI quality, combine overlap + embedding + LLM-as-judge.

## Convergence Debugging Decision Tree

| Symptom | Diagnosis | Action |
|---------|-----------|--------|
| Loss oscillates violently | Learning rate too high | Reduce LR; add LR scheduler |
| Loss plateaus immediately | Learning rate too low OR model capacity insufficient | Increase LR; increase model width/depth |
| Train loss ↓, validation loss ↑ | Overfitting | Add regularization; early stopping; more data |
| Both losses flat | Data leakage OR loss function mismatch | Audit data pipeline; verify loss function |
| Loss spikes sporadically | Batch size too small OR bad samples | Increase batch; audit data quality |

> **Exam Gotcha:** Oscillation = learning rate too high (examine first). Never attribute convergence issues to instance count, data storage format, or number of output classes—these do not directly control gradient descent step size.

# Skill 2.3.8: Apply NLP Evaluation Metrics (BLEU, ROUGE, BERTScore, Semantic Similarity)

## Task 2.3: Analyze and evaluate the performance of ML and AI systems

---

## Metric Selection Decision Matrix

| Metric | Type | Best Use Case | Key Limitation | Compute Cost |
|--------|------|---------------|----------------|--------------|
| **BLEU** | N-gram overlap (precision-focused) | Machine translation quality | Penalizes valid paraphrases; ignores recall; poor for short text | Low |
| **ROUGE-N** | N-gram overlap (recall-focused) | Summarization completeness | Misses semantic equivalence; inflated by length | Low |
| **ROUGE-L** | Longest common subsequence | Summarization fluency + structure | Still lexical; ignores synonyms | Low |
| **BERTScore** | Contextual embedding similarity | Semantic equivalence across wordings | Requires transformer model; higher latency | Medium-High |
| **Semantic Similarity** | Embedding cosine similarity | Paraphrase detection, answer relevance | Sensitive to embedding model choice; no factual grounding | Medium |

---

## Core Concepts & Definitions

- **BLEU (Bilingual Evaluation Understudy):** Measures n-gram *precision* with brevity penalty. Scores range 0–1 (or 0–100 scaled). Intended for machine translation where concise outputs are preferred.
- **ROUGE (Recall-Oriented Understudy for Gisting Evaluation):** Measures n-gram *recall* against reference summaries. ROUGE-N (n-gram overlap), ROUGE-L (longest common subsequence), ROUGE-S (skip-bigram).
- **BERTScore:** Uses contextual embeddings (BERT, RoBERTa) to compute token-level cosine similarity between candidate and reference. Produces Precision (P), Recall (R), and F1. Aligns tokens via greedy matching.
- **Semantic Similarity:** Compares sentence/paragraph embeddings (e.g., sentence-transformers, Amazon Titan Embeddings). Measured as cosine similarity; threshold-based decisions (e.g., > 0.8 = "similar").

---

## BLEU Deep Dive

- **Formula:** `BLEU = BP × exp(Σ wₙ log pₙ)` where `pₙ` = modified n-gram precision (clipped), `BP` = brevity penalty.
- **Brevity penalty applies when candidate length < reference length.** Long outputs are not penalized beyond the precision clipping.
- **Default weighting:** Uniform across n-grams (typically up to 4-gram).
- **Smoothing required** when no n-gram matches (avoid `log(0)`), especially for short candidates.

> **Exam Gotcha:** BLEU is *precision-oriented*. A short, safe answer can score high BLEU even if it omits critical content. BLEU alone cannot detect omissions, hallucinations, or factual errors.

---

## ROUGE Deep Dive

| Variant | Measures | Formula Intuition |
|---------|----------|-------------------|
| **ROUGE-N** | N-gram recall | `matched n-grams / total reference n-grams` |
| **ROUGE-L** | Longest common subsequence | Captures sentence-level structure; F-measure used |
| **ROUGE-S** | Skip-bigram (any pair of words in order) | More flexible than contiguous n-grams |

- **ROUGE is recall-oriented:** Favors thorough coverage of reference content.
- **Common pitfall:** A generated summary that repeats all reference content plus irrelevant text scores high ROUGE but low precision.

> **Exam Gotcha:** A system can game ROUGE by producing overly long outputs. Always report ROUGE alongside a precision metric or a length penalty.

---

## BERTScore Deep Dive

- **Requires a pre-trained transformer** (e.g., `bert-base-uncased`, `roberta-large`).
- **Algorithm:** Tokenize both candidate and reference → compute contextual embeddings → greedy alignment (each candidate token matched to most similar reference token) → compute P, R, F1 with optional importance weighting (IDF).
- **Rescaled to 0–1** for interpretability (baseline-rescaled BERTScore).
- **Advantage over BLEU/ROUGE:** Captures semantic similarity across different wordings (e.g., "quick brown fox" vs "fast auburn fox" still scores moderately high).

> **Exam Gotcha:** BERTScore requires downloading model weights. For offline evaluation or when compute is constrained, prefer BLEU/ROUGE. For semantic nuance, BERTScore outperforms lexical metrics.

---

## Semantic Similarity in Practice

- **Embedding models:** `sentence-transformers/all-MiniLM-L6-v2` (lightweight), Amazon Titan Embeddings (Bedrock), Cohere Embed v3.
- **Cosine similarity range:** -1 to 1; for text, typically 0 to 1.
- **Threshold selection is task-dependent:**
  - Answer relevance: > 0.7
  - Paraphrase detection: > 0.8
  - Near-duplicate detection: > 0.9

- **Use cases in exam scenarios:**
  - **RAG answer relevance:** Compare generated answer embedding vs. question embedding.
  - **Grounding/faithfulness:** Compare generated answer vs. retrieved context (semantic similarity can detect fabricated content when similarity is low).
  - **Duplicate question detection** in support systems.

---

## Trade-offs & Anti-Patterns

| Anti-Pattern | Why It Fails | Correct Alternative |
|--------------|--------------|---------------------|
| Using BLEU for summarization | Ignores recall; summaries need completeness | ROUGE or BERTScore |
| Using ROUGE for translation | Ignores precision; translations need conciseness | BLEU or BERTScore |
| Reporting a single metric to prove quality | No metric captures factuality, coherence, fluency | Combine overlap + embedding + LLM-as-judge |
| Relying on BLEU/ROUGE for creative writing | Lexical matching fails on paraphrases | BERTScore or semantic similarity |
| Using semantic similarity for factual grounding | Embedding similarity ≠ factual verification | RAG triad: context relevance + faithfulness + answer relevance |
| Assuming higher ROUGE = better model always | Overly long outputs inflate recall | Report ROUGE-L F1 with length statistics |

- **Bedrock evaluations** support VPC endpoints (Interface endpoint `bedrock`). Ensure IAM roles have `bedrock:CreateEvaluationJob`, `bedrock:GetEvaluationJob`, and S3 read/write permissions.
- **Logging NLP metric outputs** to CloudWatch: Use structured JSON logs; enable log group encryption with KMS.

> **Exam Gotcha:** Human-based Amazon Bedrock evaluation jobs created in the console require a browser-facing UI for raters. Programmatic evaluation jobs do not.

---

## Exam Quick Reference

- **BLEU** → precision, translation, brevity penalty.
- **ROUGE** → recall, summarization, vulnerable to verbose outputs.
- **BERTScore** → semantic robustness, higher cost, contextual embeddings.
- **Semantic similarity** → paraphrase/answer relevance, embedding model dependent, threshold tuning required.
- **Never trust a single NLP metric.** Production-grade evaluation combines overlap + embedding + judge/human review.

# Skill 2.3.9: Perform AI Evaluation

## Task 2.3: Analyze and evaluate the performance of ML and AI systems

---

## Core Evaluation Modes (Amazon Bedrock)

| Mode | Mechanism | Best For | Key Limitation |
|---|---|---|---|
| **Programmatic (Algorithmic)** | Computes ROUGE, BLEU, BERTScore, semantic similarity | Fast, deterministic scoring over large prompt datasets | Requires reference outputs; misses nuanced quality |
| **LLM-as-a-Judge** | A judge model scores responses, provides rationale | Subjective quality, instruction following, safety | Judge bias; needs calibration and rubric alignment |
| **Human-in-the-Loop** | Ratings from human workers or SMEs | High-stakes outputs, final quality gates | Slow, costly; needs workforce setup |

> **Exam Gotcha:** Human-based evaluation jobs created in the AWS console **require browser-facing display** (prompts/responses rendered for raters). Programmatic and judge-model jobs **do not** require this.

---

## LLM-as-a-Judge Framework

- **Pattern:** Use a strong FM (e.g., Claude) to score another model's outputs against a rubric.
- **Rubric Design:** Define 1–5 scale per dimension (accuracy, relevance, safety, tone).
- **Key Outputs:** Score + textual rationale → enables debugging and audit trails.
- **Bias Risks:** Judge models may favor their own responses, prefer verbose outputs, or be intolerant to style variations.
- **Mitigation:** Rotate judge models, use pairwise comparisons, calibrate with human-labeled ground truth.

| Configuration | Guidance |
|---|---|
| **Metric Type** | `Builtin` (Amazon Bedrock curated metrics like Helpfulness, Correctness) or custom metric |
| **Judge Model** | Select a different model from the one being evaluated when possible |
| **Prompt Dataset** | Include diverse inputs: edge cases, adversarial prompts, low-resource language samples |

---

## Content Quality Validation

- **Multi-dimensional scoring:** Accuracy, coherence, relevance, helpfulness, harmlessness.
- **Automated metrics:**
  - **ROUGE-N/L** — recall-focused n-gram overlap (summarization)
  - **BLEU** — precision-focused n-gram overlap (translation)
  - **BERTScore / Semantic Similarity** — embedding-based; captures meaning beyond exact wording
  - **Embedding cosine similarity** — semantic distance between output and reference
- **RAG Triad:** Evaluate separately:
  - **Faithfulness** — is the answer grounded in retrieved context?
  - **Answer Relevance** — does the answer address the user query?
  - **Context Relevance** — did retrieval return pertinent passages?

> **Exam Gotcha:** A fluent answer that omits facts from source documents is a **retrieval failure**, not necessarily a generation failure. Always isolate retrieval metrics (context precision/recall) from generation metrics (faithfulness, answer relevance).

---

## Bias Detection

- **Definition:** Systematic errors or unfair outcomes across demographic groups (gender, race, age, geography).
- **Traditional ML:**
  - **Disparate Impact Ratio:** `P(positive | group A) / P(positive | group B)` — values < 0.8 flag concern
  - **Equal Opportunity Difference:** Compare TPR across groups
  - **Demographic Parity:** Ensure similar positive prediction rates
  - **SageMaker Clarify:** Pre-training bias metrics (CDDL, KLL) and post-training bias metrics (DPPL, TE, DCA)
- **GenAI Bias:**
  - **Representational harm:** Stereotypes in generated text
  - **Toxicity detection:** Use classifiers or judge models for harmful content
  - **Prompt-injection resistance:** Evaluate robustness to adversarial instructions

| Tool | Use Case |
|---|---|
| **SageMaker Clarify** | Bias drift, feature attribution, pre/post-training bias for tabular ML |
| **Bedrock Evaluations (judge model)** | Safety, toxicity, and bias scoring for generated text |
| **Custom evaluation dataset** | Deliberately include counter-stereotypical prompts and edge cases |

> **Exam Gotcha:** Bias detection requires **stratified evaluation datasets** that include sufficient samples from all demographic groups. Reporting a single global accuracy metric hides group-level disparities.

---

## Evaluating RAG Systems

| Component | Metrics | Failure Signature |
|---|---|---|
| **Retrieval** | Context precision, context recall, hit rate, MRR | Correct answer absent from retrieved chunks |
| **Generation** | Faithfulness (groundedness), answer relevance, semantic similarity | Retrieved context correct, but answer omits facts or hallucinates |
| **End-to-End** | Human preference score, judge model score | Combined pipeline quality |

- **Chunking impact:** Retrieval quality degrades with overly large or poorly segmented chunks
- **Embedding model choice:** Different embeddings affect retrieval performance; evaluate per-domain accuracy
- **Monitoring:** Track embedding drift and retrieval latency in CloudWatch against baseline

---

## Evaluation vs. Monitoring (Baselines & Drift)

- **Baseline:** Period of known-good behavior captured post-launch. Store in CloudWatch metrics.
- **Drift Signals:**
  - **Data drift:** Input distribution shifts (embedding distance, feature statistics)
  - **Model quality drift:** Prediction confidence changes, human feedback scores decline
  - **Operational drift:** Latency, error rate, token count changes
- **CloudWatch Alarms:** Trigger retraining or rollback when drift exceeds threshold

> **Exam Gotcha:** A baseline without recorded inputs is useless for diagnosing *why* a metric moved. Log prompt text, retrieved context, model parameters, and output metadata for every inference.

---

## Key Trade-offs & Anti-Patterns

| Anti-Pattern | Correct Approach |
|---|---|
| Using BLEU alone for open-ended generation | Combine overlap (BLEU/ROUGE) + semantic similarity (BERTScore) + judge model |
| Evaluating RAG only via final answer quality | Measure retrieval and generation separately |
| Reporting single accuracy figure for NLP | Multi-metric evaluation: fidelity, relevance, safety, bias |
| Using same model as judge and candidate | Use different judge model; calibrate against human labels |
| Ignoring prompt versioning in evaluations | Store prompts in Bedrock Prompt Management; compare variants systematically |
| Evaluating on training data | Strict train/validation/test splits; hold out unseen data |

---

## Amazon Bedrock Evaluations — Key Parameters

- **Job Types:** `model-invocation` (generation quality) and `RAG evaluation` (retrieval + generation)
- **Input:** Evaluation dataset in S3 (JSONL format for model evaluation; JSON for RAG)
- **Output:** S3 location for results and per-metric scores
- **Metric types:** Built-in (faithfulness, correctness, robustness, etc.) or custom
- **Judge Model:** For LLM-as-judge jobs, choose a separate model with strong reasoning

> **Exam Gotcha:** Amazon Bedrock RAG evaluations **do not require deployment** of the retriever/generator — the job runs against your Knowledge Base and model directly. Shadow tests (SageMaker) require deployed endpoints.

---

## Shadow Testing vs. A/B Testing vs. Offline Evaluation

| Approach | Live Traffic? | Caller Impact | Use Case |
|---|---|---|---|
| **Shadow Test (SageMaker)** | Yes (copied) | None — production responds | Validate latency, errors, request shape compatibility |
| **A/B Testing** | Yes (split) | Varies — candidates respond | Statistical comparison of business metrics |
| **Offline Evaluation (Bedrock)** | No (static dataset) | None | Prompt/dataset-driven quality scoring |

> **Exam Gotcha:** Shadow testing is unavailable for **some endpoint configurations** — assume design constraints. It validates operational performance and output comparisons on real traffic, not business outcomes that require caller exposure.

# RAG System Monitoring & Retrieval Accuracy Assessment

## Core Objective: Isolate Retrieval Failure from Generation Failure

**Primary business goal:** Determine whether wrong/incomplete answers stem from the retriever fetching bad context or the generator ignoring good context.

> **Exam Gotcha:** A fluent answer that omits facts present in source documents is a **retrieval failure wearing a generation costume**. Always split monitoring into retrieval metrics and generation metrics separately.

---

## RAG Evaluation Architecture

```
┌─────────────┐    ┌──────────────┐    ┌─────────────┐
│   Query     │──►│   Retriever  │──►│  Generator  │──► Answer
└─────────────┘    └──────┬───────┘    └─────────────┘
                          │
              ┌───────────▼───────────┐
              │ Retrieval Metrics     │
              │ - Context Precision   │
              │ - Context Recall      │
              └───────────────────────┘
                          │
              ┌───────────▼───────────┐
              │ Generation Metrics    │
              │ - Faithfulness        │
              │ - Answer Relevance    │
              └───────────────────────┘
```

## Retrieval Accuracy Metrics (RAG Triad)

| Metric | Measures | Formula/Definition | Low Score Indicates |
|--------|----------|-------------------|---------------------|
| **Context Precision** | Signal-to-noise in retrieved chunks | Relevant retrieved chunks ÷ Total retrieved chunks | Irrelevant chunks flooding the prompt |
| **Context Recall** | Completeness of retrieval | Relevant retrieved chunks ÷ All relevant chunks in corpus | Facts missing from top-k results |
| **Context Relevance** | Overall utility of retrieved context | LLM-judged relevance of context to query | Wrong chunk indexing, bad embeddings |
| **Hit Rate** | Binary: was the correct chunk retrieved? | Queries with relevant chunk in top-k ÷ Total queries | k too small or embedding failure |
| **MRR** | Reciprocal rank of first relevant chunk | Mean(1/rank₍ᵣₑₗₑᵥₐₙₜ₎) | Relevant chunks ranked too low |

## Generation Metrics (Evaluate Separately)

| Metric | Measures | Distractor Trap |
|--------|----------|-----------------|
| **Faithfulness / Groundedness** | Does answer match retrieved context only? | High fluency ≠ factual accuracy |
| **Answer Relevance** | Does answer actually address the query? | Right context + wrong answer = generation failure |
| **Hallucination Rate** | Claims not supported by context | Judge model flags unsupported entities |

## Implementation Patterns for Retrieval Assessment

**Retrieval-only evaluation:**
- Build gold-standard query → relevant chunk IDs dataset
- Call `Retrieve` API (not `RetrieveAndGenerate`) to isolate retriever
- Compute Context Precision/Recall against gold labels
- Monitor metric drift in CloudWatch

**End-to-end with retrieval attribution:**
- Use SageMaker AI MLflow tracing to log `retrieved_document_ids` per request
- Compare answer quality only on requests where correct chunks were retrieved
- This isolates whether generation is the bottleneck

**Bedrock Evaluations retrieval job:**
- Configure `evaluationSource` as Knowledge Base
- Choose `RetrieveAndGenerate` metric mode
- Judge model scores Context Relevance + Faithfulness + Answer Relevance

---

## Monitoring & Drift Detection

**Key metrics to baseline and alert on:**

| Metric | Healthy Baseline | Drift Signal |
|--------|-----------------|--------------|
| Context Precision @k | > 0.7 | New irrelevant docs in vector store |
| Context Recall @k | > 0.8 | Embedding model change, chunking change |
| Faithfulness | > 0.9 | LLM hallucination increase |
| Retrieval Latency (p50/p99) | Stable over 7 days | Index performance degradation |
| Vector store freshness | < 24h since last sync | Stale documents serving wrong facts |

**CloudWatch alarm pattern:**
- `ContextPrecision < 0.65 for 3 consecutive 5-min periods` → alert
- `ContextRecall p99 latency > 2s` → alert on retriever performance

---

## Anti-Patterns & Distractor Traps

| Anti-Pattern | Why It Fails | Correct Approach |
|--------------|-------------|------------------|
| **Only measuring final answer quality** | Cannot isolate retrieval vs generation failure | Split metrics into RAG triad |
| **Using BLEU/ROUGE for retrieval** | Overlap metrics measure generation text, not retrieval relevance | Use Context Precision/Recall, MRR |
| **Assuming high embedding similarity = relevant** | Cosine similarity to query ≠ factual usefulness | Use LLM-as-judge or human labels for relevance |
| **Evaluating only in offline datasets** | Live query distribution differs from golden datasets | Shadow test RAG pipeline with live traffic |
| **Monitoring only token count** | Length tells nothing about retrieval quality | Track retrieved chunk IDs and relevance |
| **Storing embeddings without source metadata** | Cannot trace which document version was retrieved | Version chunks; log `document_version` with each retrieval |

## Human Evaluation Integration

**When human review is required:**
- Retrieval results where Context Recall is borderline (0.4–0.7)
- High-stakes domains (medical, legal, financial)
- When judge model confidence is low

**Bedrock human evaluation workflow:**
- Create evaluation job with human worker source (employees or MTurk)
- Display query + retrieved chunks + generated answer for rating
- **Console requirement:** human-based jobs require browser-facing display for workers

> **Exam Gotcha:** Automated evaluation jobs carry **no browser display requirement**, but human-based evaluation jobs created in the console **do**, because prompts and responses must be rendered to raters.

## Security & Compliance for RAG Monitoring

- **KMS encryption:** Encrypt evaluation data and trace logs at rest (S3, CloudWatch Logs)
- **IAM roles:** Evaluation jobs need `bedrock:Retrieve` + `bedrock:RetrieveAndGenerate` on the Knowledge Base ARN
- **VPC endpoints:** Route retrieval API calls through VPC endpoints to keep corpus queries private
- **PII in traces:** Redact PII before logging retrieval queries to MLflow/CloudWatch; use SageMaker Data Wrangler or custom redaction
- **Audit trail:** Store `retrieved_document_ids` with each inference for regulator explanation
