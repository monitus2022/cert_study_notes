# Skill 4.1.1: Monitor model performance in production by using Amazon CloudWatch generative AI observability, Amazon Bedrock Model Evaluation, and drift detection pipelines.

## Task 4.1: Operating, Monitoring, and Securing ML and AI Solutions - Monitor ML and AI model inference and performance.

---

## Core Monitoring Architecture

| Component | Purpose | Key Output |
|-----------|---------|------------|
| **CloudWatch generative AI observability** | Pre-built dashboards for LLM/agentic workloads | Token usage, latency, errors, throttles, prompt traces |
| **Amazon Bedrock Model Evaluation** | Score model/knowledge base response quality | Automatic metrics, judge model scores + explanations, human ratings |
| **Drift Detection Pipeline** | Detect shifts in input distribution vs. baseline | Statistical distance metric + alert when threshold breached |
| **AWS X-Ray** | Distributed request tracing across components | Step-level latency/failure attribution |
| **SageMaker Production Variants** | A/B testing on live traffic via weighted routing | Per-variant metrics on same window |

> **Exam Gotcha:** CloudWatch generative AI observability is the ONLY option that combines token usage, latency, error rates, throttling, AND end-to-end prompt traces for agents in one view. CloudTrail logs APIs only; Config tracks resources; Cost Explorer is billing-only.

---

## Drift Detection Pipeline: Four Moving Parts (Memorize)

1. **Capture baseline** — record distribution during an agreed stable period.
2. **Capture current** — sample same metric from live traffic.
3. **Compare distributions** — statistical test suited to data type/dimensionality.
4. **Alert** — fire when distance crosses pre-agreed threshold.

| Drift Type | P(X) Inputs Shift? | P(Y|X) Relationship Shift? | Detection Method |
|------------|:------------------:|:-------------------------:|------------------|
| **Data drift (covariate shift)** | ✅ Yes | ❌ No | Compare prompt embeddings vs. baseline using high-dimensional statistic (e.g., MMD, energy distance, KS test for low-dim) |
| **Concept drift** | ❌ No | ✅ Yes | Downstream business metrics, user feedback, label acceptance rates |

> **Exam Gotcha:** A drift pipeline built on prompt embeddings detects **data drift only**. Concept drift — where prompts look identical but expected answers change — surfaces in user acceptance metrics, not distribution comparisons. Do not claim drift detection catches concept drift.

---

## CloudWatch Alarms & Anomaly Detection

- **Flat-line alarms are as critical as spike alarms:** invocation count dropping to zero = broken pipeline/endpoint, not just low traffic.
- **Duration growth run-over-run:** monitor p50/p99 latency drift on inference calls.
- **Throttling (HTTP 429 / ThrottlingException):** indicates quota exceeded; alert on throttle count as separate metric from general errors.
- **Anomaly Detection (CloudWatch):** band-based anomaly detection on metrics with seasonal/trend patterns; reduces manual threshold tuning.

### Data Pipeline Monitoring — Check Output, Not Just Completion

> **Exam Gotcha:** A preprocessing job that exits with status `SUCCESS` can still produce empty partitions, nulled columns from a schema change, or duplicate records from retries. Monitor **output row counts, null ratios, schema validation** — not only job status. Failure shape: upstream job "succeeds," downstream invocation errors spike.

---

## Amazon Bedrock Model Evaluation

| Evaluation Type | When to Use | Output |
|-----------------|-------------|--------|
| **Automatic evaluation** | Fast, deterministic metrics (BLEU, ROUGE, BERTScore, toxicity, robustness) | Numeric scores |
| **LLM-as-a-judge** | Subjective quality, helpfulness, safety, instruction following | Score + plain-language explanation per response |
| **Human-based evaluation** | Final validation, cost-tolerant, regulatory needs | Reviewer ratings |

- **Use-case separation:** Bedrock Evaluations score response **quality**, not runtime health. Pair with CloudWatch for latency/errors.
- **Custom prompt datasets:** S3 input with curated prompts + reference responses for automatic evaluation.

---

## Production Variants: A/B Testing & Shadow Testing

| Configuration | Weight Distribution | Live Responses Returned? | Use Case |
|---------------|:-------------------:|:------------------------:|----------|
| **A/B (weighted production variants)** | Sum of weights = 100% of traffic | ✅ Yes — both variants serve users | Prove candidate better on real metrics before full rollout |
| **Shadow variant** | 0% traffic weight; copy of incoming requests | ❌ No — responses recorded only | Test serving stack/model without user exposure |

- **Traffic split formula:** fraction = variant_weight / Σ(all_variant_weights).
- **Fair comparison:** same metric set, same time window, same error/latency thresholds across variants.
- **Weighted models** with `TargetVariant` / `ProductionVariant` in `CreateEndpointConfig`.

> **Exam Gotcha:** SageMaker production variants enable live A/B testing on ONE endpoint. If requirements say "single endpoint, gradual rollout, compare versions," choose production variants — do NOT provision separate endpoints (those give separate metrics and no traffic split control).

---

## Security & Compliance Notes

- **VPC Endpoints:** CloudWatch and Bedrock support VPC interface endpoints; keep monitoring traffic off public internet.
- **Encryption:** Bedrock model evaluation datasets in S3 should use **SSE-KMS**; CloudWatch Logs support KMS at-rest encryption.
- **IAM for Bedrock Evaluations:** Requires `bedrock:GetModelEvaluationJob` / `bedrock:CreateModelEvaluationJob` plus S3 read access to evaluation datasets.

---

## Anti-Patterns (Common Exam Distractors)

- ❌ **Monitoring only model invocation** — miss upstream data pipeline corruption; alert on output anomalies, not just job completion.
- ❌ **Single threshold on high values only** — misses flat-line (zero invocation) failures; add `<= 0` or anomaly bands.
- ❌ **Treating drift detection as "done" without threshold agreed in advance** — drift must have a numeric distance and a pre-set alert trigger.
- ❌ **Using CloudTrail for runtime metrics** — it logs API calls for audit, does not render latency or token usage.
- ❌ **Assuming cost allocation tags help monitoring** — tags are for billing attribution only.
- ❌ **Comparing model versions on different endpoints at different times** — use production variants on one endpoint for controlled A/B comparison.

# Skill 4.1.2: Monitor workflows to detect anomalies or errors in data processing or model inference

## Core Objective & Exam Scope
**Detect failures across the entire ML pipeline**—upstream data processing, inference endpoints, and agentic/genAI execution paths—without relying on end-user complaints. Success = attributing a symptom (e.g., inference errors) to the correct failing component (e.g., bad ETL output).

---

## Monitoring Architecture: Three Jobs

| Job | AWS Service | What It Detects |
|-----|-------------|-----------------|
| **Collect metrics/logs/traces** | CloudWatch, X-Ray, Bedrock AgentCore Observability | Latency, error rates, token usage, throttles, invocation path |
| **Judge quality/correctness** | Bedrock Model Evaluation (auto/judge/human) | Response degradation not visible in raw metrics |
| **Trace cross-component requests** | X-Ray, CloudWatch genAI observability prompt tracing | Handoff failures, slow tool calls, partial executions |

> **Exam Gotcha:** A monitoring gap is usually a **missing job** (no quality check on pipeline output, no tracing), not a missing dashboard.

---

## Key Metrics & Alarm Patterns

### Inference-Level Metrics
- **InvocationCount:** Flatline to zero = broken pipeline/upstream failure → alarm on **low threshold** too, not just spikes.
- **ModelLatency / Duration:** Growth run-over-run = model overload, cold starts, tool slowness.
- **ErrorRate (4xx/5xx):** 429 = throttling; 5xx = container/model failures.
- **Token usage (genAI):** Anomalous prompt/completion token counts = prompt injection attempts or runaway completions.

### Data Processing Metrics (Upstream)
- **Job completion ≠ output validity.** Always validate output artifacts.
- Check: **record counts, non-null constraints, schema integrity, partition emptiness, duplicate retry writes**.
- Use **CloudWatch metrics/alarms** on ETL steps (Glue, EMR, Step Functions, Lambda) tied to output quality checks, not just exit codes.

> **Exam Gotcha:** A job that exits with code `0` but writes empty/corrupt partitions is the classic "handoff failure" pattern. The symptom appears downstream at inference; the alarm must sit **upstream** and measure output.

---

## Failure Signature → Root Cause Matrix

| Symptom | Likely Cause | Monitoring Fix |
|---------|--------------|----------------|
| Job succeeds, invocation errors climb | Empty/corrupt ETL output | Validate output artifacts post-job |
| Invocation count drops to zero | Upstream pipeline stalled / event source disabled | Low-value alarm on invocation count |
| Elevated 429 errors | Throttling limits (account/endpoint/FM invocation) | Track Throttling metric; raise limits or optimize batching |
| Schema change nulls a column silently | Upstream feature change without contract validation | Schema validation in pipeline; Glue Schema Registry |
| Duplicate records after retry | Non-idempotent writer | Idempotency checks, dedup keys in output |
| Tool call returns empty but "success" | Agent tool contract broken | AgentCore Observability; tool output validation |

---

## Anomaly Detection Approaches

| Approach | Use Case | Trade-Off |
|----------|----------|-----------|
| **Static thresholds (CloudWatch alarms)** | Known SLAs (latency < 200ms, error < 1%) | Simple; misses gradual drift |
| **CloudWatch Anomaly Detection** | Dynamic baselines for seasonal/custom metrics | Auto-adjusts; needs training period on stable window |
| **Drift detection pipeline on prompt embeddings** | GenAI input distribution shift | Catches data drift only; **not** concept drift |
| **Bedrock Model Evaluation (LLM-as-judge)** | Output quality score degradation | Subjective; judge bias possible; periodic not continuous |
| **A/B or shadow variant comparison** | Prove new model ≥ incumbent on live traffic | Requires dual infrastructure; shadow = no user impact |

---

## Agentic Workflow-Specific Signals

- **Truncated streaming:** Detect incomplete responses via end-of-stream markers, token count anomalies, or missing termination tokens.
- **Coordination failure:** Agent loops without completing; detect via step count thresholds or missing terminal state in trace.
- **Tool failure:** Non-2xx from tool API, empty tool output despite success code, retry storms.
- **Memory operation errors:** Drift in conversation state, failed memory write/read spans.

> **AgentCore Observability** is **default telemetry** for Bedrock AgentCore Runtime agents. OpenTelemetry-compatible; traces model calls, tool calls, memory ops **without custom instrumentation**.

---

## Security & Compliance in Monitoring

| Requirement | Configuration |
|-------------|---------------|
| **Encrypt log data at rest** | KMS-CMK on CloudWatch Logs groups (default is SSE; CMK for key control) |
| **Restrict metric access** | IAM policies on CloudWatch; least-privilege for dashboard viewers vs alarm editors |
| **Private network for monitoring APIs** | VPC Interface Endpoints for CloudWatch Logs, X-Ray, Bedrock, SageMaker |
| **Audit trail of alarm/configuration changes** | CloudTrail on CloudWatch Alarms and resource policies |
| **PII in prompts/tool outputs** | Do not log raw prompt/completion without redaction; use structured metrics for token counts, not content |

---

## CloudWatch GenAI Observability (Exam Favored)

**Pre-built dashboards for LLM/agent workloads:**
- Model invocation metrics (tokens, latency, errors, throttles)
- End-to-end **prompt tracing** (X-Ray integration)
- Agent-specific views for Bedrock AgentCore
- **Single console** for token usage + traces + error rates

> **Select When:** Question describes needing token usage, latency, error rates, **and** prompt-level trace in one place → CloudWatch genAI observability, not CloudTrail, Config, or Cost Explorer.

---

## Anti-Patterns (Pitfalls to Avoid)

- **Monitoring only inference:** Ignores upstream data handoffs that cause most failures.
- **Alarming only on high thresholds:** Misses "flatline to zero" outages.
- **Treating job exit code as proof of output quality:** Requires post-job validation.
- **Using raw logs for token/PII monitoring:** Cost explosion; privacy leak.
- **Confusing data drift with concept drift:** Embedding distribution unchanged but answers expected changed = concept drift (detected via business metrics/user feedback, not embedding stats).
- **One metric per variant in A/B tests over different windows:** Breaks comparability; measure both variants on same metrics in same period.

# Skill 4.1.3: Detect changes in data distribution that can affect model performance

## Task 4.1: Operating, Monitoring, and Securing ML and AI Solutions - Monitor ML and AI model inference and performance

---

## Core Drift Detection Pipeline (Memorize This)

| Component | Purpose | Key AWS Implementation |
|---|---|---|
| **Capture baseline** | Snapshot stable-period data distribution | SageMaker Model Monitor (data quality job), stored in S3 |
| **Capture current traffic** | Sample live inference inputs continuously | Endpoint data capture (SageMaker), Bedrock invocation logs |
| **Compare distributions** | Statistical measure of divergence | sagemaker.model_monitor.DataCaptureConfig, drift metric thresholds |
| **Alert on breach** | Trigger action when distance exceeds threshold | CloudWatch Alarm → SNS → Lambda/EventBridge |

> **Exam gotcha:** A drift detection pipeline finds **data drift** (input distribution shift, P(X) changes). It does **NOT** find **concept drift** (P(Y|X) changes while P(X) stays stable). Concept drift surfaces via downstream business metrics, user feedback, or quality evaluation scores.

---

## Data Drift vs. Concept Drift — Distractor Trap

| Condition | P(X) (inputs) | P(Y|X) (correct outputs) | Detection method |
|---|---|---|---|
| **Data drift / covariate shift** | **Changes** | Stays same | Statistical drift detection (embeddings, feature distribution comparison) |
| **Concept drift** | Stays same | **Changes** | Downstream metrics, human feedback, model evaluation scores |
| **Both together** | Changes | Changes | Requires multi-signal approach — drift pipeline + quality monitoring |

> **Exam Alert:** Questions often describe "prompts look the same but answers users expect have changed" — this is **concept drift**. If "input features/prompt topics are statistically different from baseline" — this is **data drift**.

---

## SageMaker Model Monitor — Drift Detection Configuration

### Key Boto3 / SDK Parameters

| Parameter | Purpose | Notes |
|---|---|---|
| `DataCaptureConfig` | Enable live request/response capture from endpoint | `EnableCapture=True`, `SamplingPercentage`, `DestinationS3Uri` |
| `DataQualityJobDefinition` | Configure data quality/drift monitoring | Compare `BaselineS3Uri` vs. `CurrentS3Uri` |
| `ModelQualityJobDefinition` | Monitor model output quality | Compares predicted vs. ground truth (needs labeled data) |
| `ModelBiasJobDefinition` | Monitor bias drift | Requires ground truth labels |
| `ModelExplainabilityJobDefinition` | Monitor feature attribution drift | Uses SHAP-based explainability |
| `MonitoringSchedule` | Run monitoring on schedule (cron/rate) | `ScheduleExpression` (e.g., `cron(0 1 * * ?*)`) |

### Statistical Methods for Drift Detection

| Data type | Recommended statistic | Why |
|---|---|---|
| **Numeric / tabular features** | Kolmogorov-Smirnov (KS) test, Wasserstein distance | Distribution shape comparison, robust for continuous data |
| **Categorical features** | Chi-squared test, Jensen-Shannon divergence | Frequency shift detection across discrete categories |
| **Text / embeddings (GenAI)** | Cosine similarity of embedding centroids, Maximum Mean Discrepancy (MMD) | Works in high-dimensional embedding space |
| **Images** | Embedding-based drift detection, per-pixel histogram comparison | Raw pixel comparison too brittle |

> **Exam gotcha:** For prompt/text drift in GenAI workloads, use **embedding centroid drift** or **MMD** — not raw text matching or simple TF-IDF cosine similarity alone. Embeddings capture semantic shifts that surface-level text metrics miss.

---

## Amazon Bedrock — Drift & Foundation Model Monitoring

| Capability | Feature | Notes |
|---|---|---|
| **Model Evaluation (automatic)** | FMEval library (fmeval) | Computes accuracy, toxicity, robustness, semantic robustness for FMs |
| **CloudWatch GenAI Observability** | Pre-built dashboards | Token usage, latency, error rates, prompt traces; catches invocation-level anomalies |
| **Bedrock invocation logging** | CloudWatch Logs / S3 | Capture prompt text, input tokens, output tokens, stop reason |
| **Bedrock AgentCore Observability** | OTel-compatible auto-telemetry | Traces model calls, tool invocations, memory ops; detect coordination failures |

### Bedrock Streaming / Agent Anomaly Signals

| Signal | What it reveals | Monitoring action |
|---|---|---|
| **`stop_reason` = `max_tokens`** | Truncated output — model hit token limit | Alert on high occurrence rate; increase max tokens or chunk inputs |
| **`stop_reason` = `stop` (normal)** | Expected completion | Baseline signal — monitor for sudden drops |
| **Tool call failing (null output, error)** | Tool invocation failure in agent | X-Ray trace shows failed tool span; alarm on tool error rate |
| **Invocation count drops to zero** | Pipeline broken (not just low traffic) | **Flat line alarm** — set low threshold, not just high threshold |
| **Latency increasing monotonically** | Model overloaded / resource contention | CloudWatch anomaly detection / static threshold on p99 |
| **Throttling errors (429)** | Rate/concurrency limit exceeded | Use `ThrottlingExceptions` metric; adjust quota or retries |

> **Critical exam rule:** **A flat-zero metric requires a low threshold alarm.** Alarms configured only for high values never fire when invocations drop to zero — this is a classic broken pipeline failure. Always configure bilateral or low-count alarms for invocation metadata.

- **Monitoring only the inference endpoint** — missing failures in upstream data processing that silently corrupt inputs.
- **Threshold only for high values** — misses zero-invocation or zero-output failures.

# Skill 4.1.1: Monitor model performance in production by using A/B testing

## Core Concept & Primary Business Objective

A/B testing (production variant comparison) proves a candidate model is better on real traffic before it carries all of it. The mechanism places multiple production variants behind a single SageMaker endpoint. Traffic is distributed according to each variant's weight relative to the total sum of all weights.

> **Weight formula:** Traffic to Variant A = Weight_A / (Weight_A + Weight_B + ...).

## SageMaker Production Variants Configuration

### Key Boto3 / CLI Parameters

| Parameter | Purpose | Exam Notes |
|---|---|---|
| `InitialVariantWeight` | Sets traffic percentage per variant | Sum of all weights = 100% |
| `TargetVariant` | Destination for endpoint updates | Used with `UpdateEndpointWeightsAndCapacities` |
| `ProductionVariants[]` | Array defining each variant | Model + instance type + weight |
| `InstanceType` | Compute per variant | Different variants can use different instance types |

### Boto3 Methods

```python
# Update traffic weights only (no redeploy)
sagemaker_client.UpdateEndpointWeightsAndCapacities(
    EndpointName="ml-endpoint",
    DesiredWeightsAndCapacities=[
        {"VariantName": "VarientA", "DesiredWeight": 90},
        {"VariantName": "VarientB", "DesiredWeight": 10},
    ],
)
```

> **Critical exam rule:** Use `UpdateEndpointWeightsAndCapacities` to shift traffic. Do NOT redeploy the endpoint—it causes downtime.

### CreateEndpointConfig with two variants

```python
ProductionVariants=[
    {
        "VariantName": "VariantA",  # incumbent
        "ModelName": "model-v1",
        "InitialVariantWeight": 95,
        "InstanceType": "ml.m5.large",
    },
    {
        "VariantName": "VariantB",  # challenger
        "ModelName": "model-v2",
        "InitialVariantWeight": 5,
        "InstanceType": "ml.m5.large",
    },
]
```

## CloudWatch Metrics for A/B Comparison

| Metric | Meaning | Alarm Use Case |
|---|---|---|
| `InvocationModelErrors` | 4xx/5xx errors from model container | Candidate crashing on real traffic |
| `ModelLatency` | Model inference time | Candidate slower than incumbent |
| `OverheadLatency` | SageMaker overhead (container startup, data transfer) | Serving stack issues |
| `CPUUtilization` / `MemoryUtilization` | Instance resource pressure | Variant under-provisioned |
| `Invocations` | Request count per variant | Verify traffic split is occurring |

**Key metric path:** `AWS/SageMaker` namespace → `EndpointName` and `VariantName` dimensions.

> **Exam gotcha:** You must track metrics per `VariantName` dimension. Comparing aggregate endpoint metrics without variant dimension = two separate observations, not a comparison.

## A/B Testing Workflow

1. **Baseline period:** Record incumbent metrics (latency, error rate, business KPI).
2. **Deploy challenger:** Add as new variant with small initial weight (1–10%).
3. **Observation window:** Collect identical metrics from both variants over the same time period.
4. **Statistical comparison:** Verify the difference is significant before shifting weight.
5. **Ramp or rollback:** Use `UpdateEndpointWeightsAndCapacities` to shift traffic gradually or roll back.

## A/B Testing vs. Shadow Testing

| Property | A/B Testing | Shadow (Dark) Testing |
|---|---|---|
| Real user sees candidate output? | Yes (small percentage) | No—copy of traffic is logged |
| Risk level | Low (limited exposure) | Zero user-facing risk |
| Traffic distribution | Weighted (e.g., 95/5) | 100% to production, 100% copy to shadow |
| Best for | Testing output quality and user response | Testing infrastructure, latency, error rates |
| SageMaker feature | Production variants with weights | Shadow variant with `InitialVariantWeight=0` |

> **When to choose shadow over A/B:** Candidate has high risk of harmful/incorrect outputs, or regulatory constraints prevent real user exposure. Shadow variant receives copied traffic and records responses without returning them.

## Comparison Metrics & Statistical Rigor

- **Identical metrics, identical window:** Both variants must be measured on the same KPIs across the same time window. Sampling one variant at a different time invalidates the comparison.
- **Minimum traffic threshold:** Ensure each variant receives enough traffic to reach statistical significance before concluding.
- **Business KPI vs. technical metric:** A/B testing must track business outcomes (conversion, user acceptance, task success rate), not only model latency or error rates.
- **Avoid non-determinism:** Set the same random seed for inference routines where applicable to reduce noise between variants.

## Common Anti-Patterns (Exam Traps)

| Anti-Pattern | Why It Fails |
|---|---|
| Redeploying endpoint to change weights | Causes downtime; violates zero-downtime traffic shifting |
| Comparing metrics from different time windows | Confounds comparison with temporal effects |
| Setting both variants at 50% from day one | Exposes too much traffic to unproven model |
| Watching only `Invocations` count | Confirms traffic split, but not model quality |
| Using different instance types for variants without accounting for it | Confounds latency comparison with hardware differences |
| Monitoring without setting alert thresholds ahead of time | Delays detection; thresholds must be agreed in advance |
| Assuming aggregate endpoint metrics are sufficient | Variant-level diagnosis hidden |

## Security & IAM Considerations

- **Endpoint invocation:** IAM policy must allow `sagemaker:InvokeEndpoint` for client role.
- **Update weights permission:** Requires `sagemaker:UpdateEndpointWeightsAndCapacities`.
- **KMS encryption:** Model data encrypted at rest using `KmsKeyId` in endpoint config; in transit via TLS 1.2 minimum.
- **VPC endpoint:** Private inference via Interface VPC endpoint (`com.amazonaws.region.sagemaker.runtime`) removes public internet exposure.

## Exam Gotchas & Hard Rules

> **Weights are proportional, not absolute.** Setting weights 50/50 yields 50% traffic each; setting 1/9 yields 10%/90%.

> **Zero weight does not delete a variant.** A variant with `Weight=0` remains deployed and available for future use.

> **`UpdateEndpointWeightsAndCapacities` does not modify model or container.** It only changes weights and instance counts.

> **Concept drift ≠ measurable by A/B.** A/B testing compares model versions against each other; it does not detect shifting business expectations over time.

> **Both variants must serve the same input schema.** If the candidate model expects different features, the endpoint will fail on shared traffic.

> **SageMaker endpoint invocation logs go to CloudWatch, not X-Ray by default.** Enable model container logging to capture inference details; X-Ray requires explicit integration.

## Key Takeaway Matrix

| Scenario | Recommended Approach |
|---|---|
| New model ready, moderate risk | A/B with 5–10% initial weight |
| New model high-risk (regulated) | Shadow variant with `InitialVariantWeight=0` |
| Traffic shift needed without downtime | `UpdateEndpointWeightsAndCapacities` |
| Need to measure per-variant performance | CloudWatch metrics with `VariantName` dimension |
| Both variants must be compared | Same metrics, same window, same traffic |

# Skill 4.1.5: Monitor and Automate the Management of Agent Performance and Coordination

## Task 4.1: Operating, Monitoring, and Securing ML and AI Solutions - Monitor ML and AI model inference and performance

---

## Core Concept & Business Objective
**Primary goal:** Detect, diagnose, and automate recovery from agentic system failures *before* end-users experience degraded or incorrect outputs. Agent workloads introduce unique failure modes beyond single-model inference: broken tool chains, unterminated streams, and failed coordination between sub-agents.

### Agent Failure Taxonomy (Know These Cold)

| Failure Mode | Signal | Primary Detection Tool | Automated Remediation |
|---|---|---|---|
| **Coordination failure** | Multiple agents stuck in loop, no final answer, excessive turns | X-Ray trace analysis, AgentCore spans, step count alarms | Max-iteration guards, circuit breaker, supervisor timeout |
| **Truncated streaming** | Response ends mid-token, incomplete JSON, missing `finish_reason` | CloudWatch `CompletionTokens` vs expected, stream-end checks | Retry with backoff, reduce `max_tokens`, split requests |
| **Tool failure** | Non-200 tool response, malformed tool output, unsupported action | AgentCore tool invocation spans, error metrics per tool | Fallback tool, retry, degrade gracefully, human escalation |
| **Model invocation failure** | 4xx/5xx from FM, throttling (429), timeouts | CloudWatch generative AI observability, Bedrock metrics | Exponential backoff, cross-region failover, quota increase |

---

## Key AWS Services & Configurations

### Amazon Bedrock AgentCore Observability
- **Default instrumentation** for AgentCore Runtime agents; emits OpenTelemetry-compatible spans and metrics without manual agent code changes.
- **Captures:** Model inference calls, tool invocations, memory operations, coordinator handoffs.
- **Boto3 / API interaction:**
  - Enable via agent config: `orchestrationConfiguration` → `observabilityConfiguration`
  - Query traces: `bedrock-agent-runtime` → `GetAgentMemory`, `GetAgentResponse` for post-hoc analysis.

### Amazon CloudWatch Generative AI Observability
- **Pre-built dashboards** over Bedrock invocations and AgentCore agents.
- **Key metrics to alarm on:**
  - `InvocationClientErrors` / `InvocationServerErrors`
  - `InvocationThrottles` — near-quota signals
  - `InputTokenCount` / `OutputTokenCount`
  - `InvocationLatency` (p50/p99)
  - **Per-tool error rate** (custom metric from AgentCore spans)

### AWS X-Ray for Agent Tracing
- **End-to-end prompt tracing** across orchestrator → LLM → tool → memory.
- **Annotations to add:** `agent_id`, `turn_number`, `tool_name`, `finish_reason`.
- **Critical check:** Candidate agent completes *all* spans; missing spans = silent tool failure or early termination.

> **Exam Gotcha:** CloudTrail logs *management* API calls (who created what). It does **not** show agent runtime coordination failures, tool call traces, or stream truncation. Do not select CloudTrail for agent performance monitoring.

---

## Automation & Guardrail Patterns

### Coordination Failure Detection
- **Set maximum turn/iteration guards** in agent orchestration. Alert when `step_count` approaches limit repeatedly.
- **Circuit breaker pattern:** If tool failure rate > threshold (e.g., 20% over 5 min), route to fallback or stop agent, notify human.
- **Dead-letter detection:** Monitor for agents that emit tool calls but never a final response within SLA window.

### Truncated Streaming Detection
- **Check `finish_reason`**: `length` (truncated) vs `stop` (normal) vs `tool_use` (expected continuation).
- **Validate output structure:** JSON schema check, required field presence, completeness markers.
- **Alert on:** `OutputTokenCount == max_tokens` while `finish_reason = length` — patterns of consistent truncation warrant config changes.

### Tool Failure Automation
- **Retry policies:** 2–3 retries with exponential backoff for transient errors; no retry for validation errors.
- **Fallback tool mapping:** Define per-tool fallback (e.g., search tool → cached results; DB tool → read replica).
- **Graceful degradation:** Agent returns partial answer with `is_complete: false` and escalation path when critical tool unavailable.

---

## Key Metrics & Alarm Thresholds

| Metric | Healthy Signal | Alarm Condition |
|---|---|---|
| Agent end-to-end latency | Stable p95, below SLA | Sustained p95 increase > 2× baseline |
| Steps per conversation | Stable median | Median exceed max-guard × 0.7 (near-loop) |
| Tool success rate | > 95% per tool | < 85% for 5 min |
| Truncation rate | < 1% of streams | > 5% of streams |
| Zero-invocation | N/A | Any drop to 0 for 10 min |
| Coordination time (orchestrator idle) | < 20% of total latency | > 50% (agents stalling) |

> **Exam Gotcha:** Alarms on **absence** of traffic are as critical as spikes. A flat-zero invocation count indicates a broken agent, dead consumer, or misconfigured routing — a high-threshold-only alarm will never fire.

---

## Decision Matrix: Which Monitoring Approach?

| Scenario | Recommended Service | Why |
|---|---|---|
| Agent uses Bedrock AgentCore Runtime | **AgentCore Observability** (default) | Zero-config OTel spans for model, tool, memory steps |
| Multi-service agent (Lambda + Step Functions + Bedrock) | **X-Ray** with manual annotations | Cross-service trace correlation, span-level attribution |
| Need LLM-specific dashboards (tokens, latency, errors) | **CloudWatch generative AI observability** | Pre-built aggregation over Bedrock APIs |
| Need to judge agent output quality | **Bedrock Model Evaluation** (automatic or judge) | Scores response correctness, helpfulness; not runtime coordination |
| Detect drift in user prompts to agent | **Embedding-based drift pipeline** | Compare prompt embeddings against baseline distribution |

---

## Anti-Patterns & Distractor Traps

- **Anti-pattern:** Monitoring only the final model invocation; agent failures occur in orchestration and tool layers *before* the model sees input.
- **Anti-pattern:** Relying on exit codes from tools. A tool can return `200` with `{"error": "permission denied"}`; validate tool response payloads, not just HTTP status.
- **Anti-pattern:** Single-alarm-only monitoring. Agents need layered alarms: invocation, coordination, tool, truncation, and drift.
- **Distractor trap:** "CloudWatch Logs alone is sufficient" — logs need parsing, metric generation, and alarms to be actionable; logs without alarms are archives.
- **Distractor trap:** "Increase `max_tokens` to fix truncation" — this treats symptom, not cause. Investigate `finish_reason` patterns first; may indicate prompt complexity or model limitation.
- **Distractor trap:** "SageMaker Model Monitor detects agent coordination issues" — Model Monitor handles data drift and model quality for hosted models, not agent orchestration or tool chains.

---

## Security & Compliance Notes

- **IAM for AgentCore telemetry:** Agents write spans to CloudWatch Logs/X-Ray; ensure execution role has `logs:PutLogEvents`, `xray:PutTraceSegments`.
- **KMS encryption:** Agent memory and conversation history at rest in DynamoDB/S3 should use KMS CMK; spans may contain sensitive prompt text — enable X-Ray encryption.
- **VPC endpoints:** For private agents, use VPC endpoints for CloudWatch Logs, X-Ray, and Bedrock to keep telemetry traffic off public internet.

## Core Objective & Evaluation Architecture

**Purpose:** Quantify foundation model output quality (not just operational metrics) using automated, judge-based, or human evaluation jobs on Amazon Bedrock.

## Anti-Patterns & Common Distractor Traps

- **Using CloudWatch Logs alone** for FM quality evaluation—logs show raw prompt/response text but do not compute quality scores or judge-based evaluations.
- **Confusing Bedrock Model Evaluation** with SageMaker Model Monitor—Bedrock evaluation is batch-scored offline; Model Monitor is online drift/quality monitoring for SageMaker endpoints.
- **Expecting automatic evaluation to catch toxicity or refusal behavior**—use judge-based evaluation with explicit harmful-content criteria.
- **Setting both production variants at 100% weight** in A/B testing—traffic routing requires weight ratios summing to 100% across variants.
- **Missing X-Ray traces for agentic workflows**—CloudWatch GenAI observability depends on X-Ray for end-to-end span correlation.
- **Over-provisioning evaluation at runtime**—evaluation jobs are offline batch jobs, not real-time request-time monitors; do not invoke them per user request.

## Security & Compliance Notes

- **Data at rest:** Evaluation datasets and results are in S3—default to SSE-S3 or SSE-KMS (customer-managed).
- **Data in transit:** Bedrock service endpoints support TLS 1.2+; VPC endpoints for Bedrock and S3 avoid public internet.
- **IAM scoping:** Grant Bedrock evaluation role only `bedrock:InvokeModel` on the specific model ARN being evaluated; avoid wildcard model permissions.
- **PII in prompts:** If evaluation data contains PII, use KMS encryption and restrict result bucket permissions; consider Bedrock Guardrails redaction prior to storage.
- **Auditability:** CloudTrail logs `CreateEvaluationJob`, `GetEvaluationJob`, and `StopEvaluationJob` API calls—essential for compliance evidence.

| Signal | What it indicates |
|--------|-------------------|
| **Token count spike** | Prompt length growth, template regression, or prompt injection attempts |
| **Throttle count increase** | Bedrock service quota breach or bursty agent tool-calling backoff |
| **Zero invocations at expected peak** | Upstream pipeline failure or agent coordination stall (no model calls being issued) |
| **Judge evaluation score decline** | FM version change, prompt template drift, or data drift affecting output quality |

## High-Yield Summary

1. **Bedrock Model Evaluation** = offline, batch-scored output quality (automatic / judge / human).
2. **CloudWatch GenAI Observability** = real-time operational metrics for FM invocations and agent workflows (tokens, latency, errors, X-Ray traces).
3. **AgentCore Observability** = built-in OTel spans for agent reasoning, tools, and memory—no manual instrumentation.
4. **Judge-based evaluation** is mandatory for subjective quality dimensions; automatic evaluation covers deterministic metrics only.
5. **Monitoring FM performance** combines operational telemetry (CloudWatch) + output quality scoring (Model Evaluation) + end-to-end tracing (X-Ray/AgentCore).
6. **A flat line on invocation count** is as important as a spike—zero invocations indicate a broken upstream pipeline or stalled agent loop.

# Skill 4.2.1: Select inference instance families to optimize performance and cost

## Task 4.2: Operating, Monitoring, and Securing ML and AI Solutions - Optimize and manage ML and AI infrastructure costs and performance

---

## Instance Family Selection Framework

### Primary Decision Drivers

| Decision Factor | Questions to Answer | Action |
|----------------|---------------------|--------|
| **Compute Shape** | CPU-bound or GPU-bound workload? | Select family matching dominant compute need |
| **Model Size** | Fits in memory headroom? | Size to measured peak utilization + 15-20% buffer |
| **Latency SLO** | p99 target requires accelerator? | GPU/Inferentia if CPU cannot meet threshold |
| **Batch vs. Real-Time** | Interactive or asynchronous processing? | Batch favors throughput-optimized; real-time favors latency-optimized |
| **Traffic Pattern** | Steady, diurnal, bursty, or intermittent? | Determines family flexibility and scaling strategy |

### Core Instance Families for SageMaker Inference

| Family | Optimized For | Best Use Case | Trade-off / Avoid When |
|--------|---------------|---------------|------------------------|
| **ml.c5 / ml.c6i** | Compute-optimized CPU | Smaller models, low concurrency, cost-sensitive inference | GPU not needed; latency SLAs loose |
| **ml.m5 / ml.m6i** | General-purpose CPU | Balanced CPU/memory; feature preprocessing with inference | Memory-heavy or GPU-bound models |
| **ml.r5 / ml.r6i** | Memory-optimized CPU | Large models not requiring GPU multipliers; embeddings servers | CPU compute insufficient for model math |
| **ml.g4dn** | NVIDIA T4 GPU, cost-effective inference | Medium CNN/transformer models; batch + real-time hybrid | Memory bandwidth-bound LLMs (>13B params) |
| **ml.g5** | NVIDIA A10G Tensor Core GPU | LLM inference, CV models, higher throughput than g4dn | Cost overkill for small tabular models |
| **ml.g6** | NVIDIA L4 GPU, improved TCO vs. g5 | Generative AI inference, superior performance/Watt | Availability in all regions may lag |
| **ml.p4d / p5** | NVIDIA A100/H100, training-grade | Very large model inference requiring top throughput | Excessive cost for standard inference |
| **ml.inf1 / inf2** | AWS Inferentia custom silicon | High-throughput, cost-efficient deep learning inference | Requires compilation (Neuron SDK); CPU fallback needed |
| **ml.trn1** | AWS Trainium (also serves inference) | Training-centric; inference for compatible compiled models | Complexity; not first choice for pure inference |

> **Exam Gotcha:** Inferentia (`ml.inf2`) can deliver up to 40% better price-performance for deep learning inference compared to comparable GPU instances, **but** models must be compiled with the AWS Neuron SDK—this is a hard prerequisite that often appears as a distractor for "works with any PyTorch model."

---

## Architecture Decision Matrix

### When to Use Each Family Type

| Scenario | Selected Family | Rationale |
|----------|-----------------|-----------|
| Tabular/structured data model (XGBoost, LightGBM) with low QPS | **ml.c5 / ml.c6i** | CPU families handle tree-based inference; no GPU needed |
| Computer vision (ResNet, YOLO) at moderate throughput | **ml.g4dn** | T4 GPU provides inference acceleration at lowest GPU cost |
| Real-time recommendations with <50ms p99 requirement | **ml.g5 / ml.inf2** | Need accelerator to hit strict latency targets |
| LLM serving (7B–13B params) for chatbot | **ml.g5 / ml.g6** | Memory (24–48GB GPU) needed for KV-cache + weights |
| LLM serving (>70B params) | **ml.p4d / multi-GPU** | Requires multiple A100s or tensor parallelism |
| High-throughput image classification at lowest cost | **ml.inf2** | Inferentia wins on total cost per million inferences |
| Embedding generation service | **ml.c6i / ml.r6i or ml.g4dn** | CPU handles many embedding models; GPU if heavy transformer |

### Accelerated vs. General-Purpose Compute

> **Hard Rule:** **Never right-size on launch configuration.** Always size from measured CloudWatch utilization over a representative window (min. 2 weeks to capture weekly seasonality). An endpoint busy 1 hour/day is a **scaling problem**, not a **sizing problem**.

---

## Key Configuration Parameters

### Boto3 / SDK Parameter Nuances

| Parameter | Purpose | Exam Note |
|-----------|---------|-----------|
| `InstanceType` | Sets the `ml.*` instance family/size | Must be compatible with container + model size |
| `InitialInstanceCount` | Starting instance count | Only for real-time endpoints; not serverless |
| `InstanceCount` | Number of instances behind endpoint | Target for auto-scaling policies |
| `ServerlessConfig` | Enables SageMaker Serverless Inference | No instance selection; pay per invocation + duration |
| `MaxConcurrency` | Max concurrent invocations per instance | Higher = denser utilization but riskier latency |
| `ModelDataDownloadTimeoutInSeconds` | Model download time before fail | Relevant for multi-model endpoints with cold starts |
| `VolumeSizeInGB` | EBS volume for model + container | Must exceed model + container layer size |

### Multi-Model Endpoint (MME) Instance Selection

| Consideration | Guidance |
|---------------|----------|
| **Instance memory** | Must hold **active models** + container runtime; not all models simultaneously |
| **Cold start latency** | Pay on-demand model load penalty when model not resident |
| **Storage** | EBS volume must fit all models + container; impacts load time |
| **When to use MME** | Dozens/hundreds of **intermittently invoked** models sharing a framework |
| **When NOT to use MME** | High-traffic single model, strict latency SLOs, divergent frameworks |

> **Exam Gotcha:** MME vs. Single-model endpoint is a classic trade-off. MME is **not** designed for consolidating a high-traffic production model—it introduces cold-start latency and contention. Reserve MME for many low-QPS models.

---

## Cost-Performance Trade-offs

| Optimization Action | When Appropriate | What You Sacrifice |
|--------------------|------------------|-------------------|
| **Downsize instance family** (g5 → g4dn) | GPU utilization consistently <50% at peak | Throughput headroom, future spike absorption |
| **CPU to GPU migration** | p99 latency > SLO on CPU family | Higher hourly cost; may need container rebuild |
| **GPU to Inferentia migration** | Stable deep learning model, compiled with Neuron | Flexibility: any model change requires recompilation |
| **Add instances (scale out)** | Vertical scaling cannot meet QPS | Higher base cost; requires load balancing |
| **Scale up (larger instance)** | Model size exceeds current memory | Fewer instances = less fault tolerance |
| **Multi-model endpoint** | Many intermittent small models | Cold-start latency; shared compute contention |

### Anti-Patterns and Common Traps

- ❌ **Selecting an instance based on training size** — Inference needs are smaller; training instances are oversized
- ❌ **Exclusively using GPU instances** — CPU families handle many models (XGBoost, TabNet, small PyTorch) at a fraction of cost
- ❌ **Oversizing to "plan for growth" without scaling policies** — Hold peak capacity during idle periods; ignores auto-scaling
- ❌ **Choosing `ml.p4d` for inference when `ml.g5` meets latency** — GPU VRAM/compute overkill inflates costs exponentially
- ❌ **Using single-model endpoints for hundreds of micro-models** — Each endpoint bills for dedicated instance hour(s)
- ❌ **Moving to Inferentia without recompiling** — Neuron SDK compilation is **mandatory**; PyTorch models cannot run directly
- ❌ **Rightsizing based on CPU utilization alone for GPU instances** — Monitor GPU utilization via CloudWatch `GPUUtilization`, not just `CPUUtilization`

## Monitoring Metrics for Instance Selection

| Metric | Where | What It Tells You |
|--------|-------|-------------------|
| `CPUUtilization` | CloudWatch | CPU headroom/family sizing |
| `GPUUtilization` | CloudWatch (custom or Container Insights) | GPU headroom; required for GPU right-sizing |
| `MemoryUtilization` | CloudWatch custom metric | Memory headroom; critical for MME |
| `DiskUtilization` | CloudWatch custom metric | Model storage pressure on EBS |
| `InvocationsPerInstance` | SageMaker CloudWatch | Traffic per instance; scaling trigger |
| `ModelLatency` | SageMaker CloudWatch | End-to-end processing time; size vs. speed trade-off |
| `OverheadLatency` | SageMaker CloudWatch | Model download/load time; MME cold start impact |
| `ModelCacheHit` | SageMaker CloudWatch (MME) | MME cache effectiveness; informs instance memory size |

## Instance Selection for SageMaker Serverless Inference

| Factor | Guidance |
|--------|----------|
| **When to choose serverless** | Intermittent traffic, low QPS, or can't predict baseline |
| **Instance selection** | None — AWS handles compute abstraction |
| **Cost model** | Per invocation + per GB-second of memory provisioned |
| **Memory range** | 1024 MB to 6144 MB, in 1 GB increments |
| **Max concurrency** | Provisioned concurrent invocations, configured separately |
| **Anti-pattern** | High sustained throughput; cost exceeds provisioned real-time |

> **Exam Gotcha:** Serverless Inference is **not** an instance "type" you select. It replaces instance selection entirely. The cost lever shifts from instance hours to **memory configuration + concurrency**—an exam distractor pairs "serverless" with "instance family selection."

## Quick Reference: Cost-Efficiency Hierarchy for Deep Learning Inference

```
Lowest cost → Highest cost (for equivalent throughput):
ml.inf2 (Inferentia) < ml.g4dn (T4) < ml.g6 (L4) < ml.g5 (A10G) < ml.p4d (A100) < ml.p5 (H100)
```

**But:** Inferentia requires Neuron compilation; prioritize ease-of-deployment vs. absolute cost when choosing.

## Exam-Ready Decision Flow

1. **Identify workload type**: tabular, CV, NLP, LLM, or embeddings
2. **Check latency SLO**: strict (<100ms) → accelerator; loose (>500ms) → CPU viable
3. **Measure utilization**: if <40% sustained → downsize; if >70% sustained → upsize
4. **Check traffic pattern**: steady → sized instance; diurnal → auto-scaling; intermittent → serverless
5. **Count models**: 1–5 models → per-model endpoints; dozens+ → multi-model endpoint
6. **Evaluate cost**: compare families at equivalent throughput; check Inferentia eligibility
7. **Select purchasing option**: steady baseline → SageMaker Savings Plan; variable → On-Demand

## Amazon CloudWatch

**Primary purpose:** Aggregate operational telemetry for ML endpoints, Bedrock invocations, and compute resources.

### Key ML-Specific Metrics to Monitor

- **SageMaker Endpoint:** `InvocationsPerInstance`, `ModelLatency`, `OverheadLatency`, `CPUUtilization`, `GPUUtilization`, `MemoryUtilization`, `DiskUtilization`
- **Bedrock (On-Demand):** `InvocationLatency`, `InputTokenCount`, `OutputTokenCount`, `InvocationThrottles`, `InvocationClientErrors`, `InvocationServerErrors`
- **Bedrock (Provisioned Throughput):** `ProvisionedModelInvocationCount`, `ProvisionedModelThrottles`

> **Exam Gotcha:** Throttling on Bedrock (`InvocationThrottles`) indicates you've hit the model's rate or token-per-minute quota — the fix is Provisioned Throughput, not auto-scaling (there are no instances to scale).

### CloudWatch Features for Cost/Performance Optimization

| Feature | Use Case | Why It Matters |
|---|---|---|
| **Metric Math** | Compute derived metrics (e.g., tokens per invocation) | Combines separate metric streams for richer analysis |
| **Dashboards** | Correlate utilization + latency + errors + token usage side-by-side | Shortens root-cause decisions |
| **Alarms** | Trigger on threshold breach (e.g., `CPUUtilization > 80%` for 15 min) | Proactive notification before SLA impact |
| **Logs Insights** | Query structured/unstructured logs for specific error patterns or invocation IDs | Faster than manual log scanning |
| **Contributor Insights** | Identify top-N contributors to a metric (e.g., which endpoint variant drives most latency) | Pinpoints resource hotspots |
| **Synthetics (Canary)** | Simulate user requests to verify endpoint availability/performance | Proactive external monitoring |

> **Exam Gotcha:** CloudWatch collects *metrics and logs* — not raw network packet captures (that's VPC Traffic Mirroring) and not database schemas (that's AWS Glue Data Catalog).

---

## AWS X-Ray

**Primary purpose:** Distributed tracing — attribute end-to-end request latency to specific components in a multi-service ML pipeline.

### X-Ray Core Concepts

| Concept | Description |
|---|---|
| **Trace** | End-to-end path of a single request across all components |
| **Segment** | Portion of the trace recorded by a single service/resource |
| **Subsegment** | Finer-grained breakdown within a segment (e.g., a database call inside a Lambda function) |
| **Service Map** | Visual representation of all services and their connections/latencies |
| **Annotations** | Key-value pairs for filtering traces (e.g., `model_version: v2.3`) |
| **Sampling** | Controls the percentage of requests traced (default: 1/sec + 5% of additional) |

### When X-Ray Beats CloudWatch

> **Exam Gotcha:** CloudWatch gives you *average* latency; X-Ray tells you *which component* caused the slowness. Use X-Ray when a request traverses multiple components (API Gateway → Lambda → Bedrock → DynamoDB) and you need to isolate the bottleneck.

### Instrumentation Methods

- **Lambda:** Enable "Active tracing" on function configuration (no code changes needed for entry-point tracing)
- **SageMaker Inference:** Add `X-Amzn-Request-Id` to invocation request; trace appears in X-Ray console
- **EC2/ECS:** Use X-Ray SDK (Python, Java, Node.js) to create segments/subsegments manually
- **API Gateway:** Enable X-Ray tracing on stage settings

> **Exam Gotcha:** X-Ray does *not* replace CloudWatch — they serve different questions. CloudWatch answers "is it slow/erroring?" (aggregate), X-Ray answers "where specifically did the slow request get stuck?" (per-request trace).

---

## Amazon Bedrock AgentCore Observability

**Primary purpose:** Capture the full internal workflow of a Bedrock Agent invocation — model inference, tool usage, knowledge base retrieval, memory operations, guardrails.

### What It Records

| Trace Component | Description | Cost/Performance Insight |
|---|---|---|
| **Agent invocation trace** | Start → planning → tool calls → synthesis → response | One user request = multiple model calls |
| **Model inference calls** | Each Bedrock FM invocation within the agent | Identifies number of model calls per user request |
| **Tool invocations** | Lambda calls, API calls, or other tools executed by the agent | Surfaces tool latency and failure loops |
| **Knowledge base retrieval** | Vector search results, retrieval timing | Separates retrieval latency from model latency |
| **Memory operations** | Session memory reads/writes | Tracks state persistence overhead |
| **Guardrail evaluations** | Content filtering, sensitive data detection | Latency + compliance cost |

### When to Use AgentCore Observability

- **Agent cost amplification:** One user request produces multiple model calls → monitor `cost_per_invocation`, not `cost_per_model_call`
- **Retry loop detection:** Tool failures causing infinite retry cycles that inflate token usage without producing user value
- **Component latency attribution:** Is slowness from the model or from the tool/retrieval layer?

> **Exam Gotcha:** Agent cost is *amplified*. A single user request = planning call + N tool calls + synthesis call. Watch cost per *user invocation*, not per individual model call. A retry loop invisible to users can balloon the bill without any traffic change.

## Core Principle: "What Are You Actually Paying For?"

| Workload Type | Billing Unit | Optimization Levers |
|---|---|---|
| **Hosted Inference (SageMaker AI)** | Compute hours / instance capacity | Right-sizing, Auto Scaling, MMEs, Savings Plans |

## Traditional ML: Inference Capacity Optimization (SageMaker AI)

### Instance Family Selection Matrix

| Workload Pattern | Instance Family | Rationale |
|---|---|---|
| **CPU-bound inference** (tabular, XGBoost, small models) | General purpose (ml.m5, ml.c5) | Cost-effective; no GPU needed |
| **GPU-dependent** (LLMs, vision, large transformers) | Accelerated (ml.g5, ml.p4/p5) | Required for low-latency inference |
| **Memory-heavy models** (>10GB) | Memory-optimized (ml.r6) or multi-GPU | Prevent OOM; enable batch sizing |
| **Intermittent sporadic traffic** | Serverless inference | Pay per invocation; no idle cost |
| **Large payloads (>1GB) or 15min+ processing** | Asynchronous inference | Queued; auto-scales to zero |
| **Many small models sharing framework** | Multi-Model Endpoint (MME) | Shared compute; load-on-demand |

### Capacity Optimization Decision Path

1. **Measure first:** CloudWatch `InvocationsPerInstance`, `CPUUtilization`, `GPUUtilization`, `ModelLatency`, `OverheadLatency`
2. **Busy all day = sizing problem** → Right-size instance family
3. **Busy peak, idle overnight = scaling problem** → Configure Application Auto Scaling
4. **Intermittent usage = over-provisioned** → Serverless or MME
5. **Steady year-round = predictable spend** → SageMaker AI Savings Plans

> **EXAM GOTCHA:** Busy one hour, idle 23 = **scaling problem** (fix with auto scaling), NOT sizing problem (do not downsize instance).

### Auto Scaling Configuration

| Parameter | Recommendation |
|---|---|
| **Target metric** | `InvocationsPerInstance` (preferred over CPU for inference) |
| **Target value** | Set from measured peak; avoid >70% utilization |
| **Scale-out cooldown** | 60–180 seconds (rapid response) |
| **Scale-in cooldown** | 300+ seconds (prevent flapping) |
| **Min instances** | 0 for async; ≥1 for real-time (zero-capacity not supported on real-time) |

## Generative AI: Token Cost Optimization (Amazon Bedrock)

### Cost Levers Ranked by Impact

| Lever | Mechanism | Typical Savings |
|---|---|---|
| **Model downgrade** | Smaller FM meets quality bar | 50–90% per request |
| **Prompt caching** | Reuse KV cache for stable prefix | Up to 90% on cached tokens |
| **Input truncation** | Reduce context window / trim instructions | Proportional to token reduction |
| **Output cap** | Limit `max_tokens` | Limits worst-case cost |
| **Batch inference** | 50% discount for tolerant workloads | 50% vs on-demand |
| **Provisioned Throughput** | Commit to model units | Up to 50% vs on-demand |

> **EXAM GOTCHA:** Prompt caching is **not free**. Cached tokens are billed at reduced rate, cache writes can cost MORE than uncached input, minimum prefix length applies, and **any dynamic content in prefix invalidates the cache entirely**.

### Provisioned Throughput vs On-Demand

| Factor | On-Demand | Provisioned Throughput |
|---|---|---|
| **Billing** | Per token (input/output) | Fixed hourly per Model Unit |
| **Commitment** | None | 1-month or 6-month term |
| **Latency** | Variable | Predictable, lower |
| **Traffic pattern** | Variable, experimental | Steady, high-volume, predictable |
| **Scaling** | Automatic | Manual (purchase additional MUs) |

### Bedrock Billing Rules

- **Input tokens:** Priced per 1K tokens; includes system prompt, context, user message
- **Output tokens:** Priced per 1K tokens; generated response only
- **Batch inference:** ~50% discount on both input/output; asynchronous
- **Cache writes:** May be 25–100% premium over normal input tokens
- **Cache reads:** Up to 90% discount on cached input tokens

## Agent Cost Amplification

### Cost Anatomy of a Single Agent Invocation

**1 user request → 1 planning call + N tool calls + 1 synthesis call = (N+2) × token cost**

| Component | Cost Driver |

| **Tool invocation** | Tool name + arguments + tool result (can be large) |
| **Synthesis** | Full conversation history + tool outputs + final response |

> **EXAM GOTCHA:** A retry loop that a human never notices (e.g., agent retries a failed tool call 5 times) **multiplies cost without any change in traffic**. Track cost per invocation, not per conversation.

| **Provisioned Throughput** | Per model unit per hour (fixed) | Commit to model + throughput level | Steady, predictable, high-volume FM traffic |
| **Batch Inference** | Per token (discounted vs. on-demand) | Submit async jobs | Large offline evaluation; tolerance for delays |
| **Prompt Caching** | Cached input tokens at reduced rate; cache writes at premium | Enable stable prefix (minimum length required) | Repeating, static system prompts/instructions |

> **Exam Gotcha:** Provisioned Throughput translates the "Savings Plans" concept to Bedrock, but it is **not** a Savings Plan. The unit changes from instance hours (SageMaker) to model units (Bedrock).

---

### When to Use What (Decision Logic)

**Steady SageMaker AI inference baseline → SageMaker AI Savings Plans**  
**EC2-based custom ML stack (ECS/EKS) → Compute Savings Plans**  
**Interruptible training job with checkpointing → EC2 Spot Instances**  
**SageMaker Training job with no checkpointing → On-Demand or Savings Plans (do NOT use Spot)**  
**Predictable Bedrock FM traffic → Provisioned Throughput**  
**Experimental/variable Bedrock traffic → On-Demand (do NOT commit)**  
**Large async FM jobs → Bedrock Batch Inference**

---

### Anti-Patterns & Distractors

- **Applying Compute Savings Plans to SageMaker endpoints** – Wrong. Compute Savings Plans do NOT cover `ml.*` instance usage.
- **Applying EC2 Instance Savings Plans to SageMaker training jobs** – Wrong. EC2 Instance Savings Plans are locked to standard EC2 instances only.
- **Using Spot Instances for a production serving baseline** – Wrong. Spot capacity can be reclaimed with a 2-minute warning, invalidating a serving guarantee.
- **Using a Budget to reduce costs** – Wrong. AWS Budgets tracks and alerts; it provides **no discount**.
- **Committing to Provisioned Throughput for intermittent traffic** – Wrong. You pay for reserved model units regardless of utilization; variable traffic belongs on On-Demand.
- **Treating Savings Plans as a service-agnostic discount** – Wrong. Each plan has explicit coverage boundaries.

|---|---|

| Compute Savings Plans max savings | Up to 66% (EC2), 17% (Lambda) |
| EC2 Instance Savings Plans max savings | Up to 72% |

| Provisioned Throughput billing granularity | Per hour per model unit |
| Savings Plans term options | 1-year or 3-year |

# Skill 4.2.8: Monitor agent resource consumption patterns

## Task 4.2: Operating, Monitoring, and Securing ML and AI Solutions - Optimize and manage ML and AI infrastructure costs and performance

## Core Concept & Primary Business Objective

**Agent resource consumption monitoring** answers: *"How many downstream calls does one agent invocation trigger?"*

A single user request to an agent (e.g., Amazon Bedrock Agents) amplifies into **multiple billable operations**:

```
User Request
    ├── Planning/Orchestration call (LLM tokens)
    ├── Tool call 1 (Lambda, API, Knowledge Base retrieval)
    ├── Tool call 2 (additional model inference)
    ├── Memory read/write operations
    └── Synthesis/final response call (LLM tokens)
```

> **Exam Gotcha:** Agent cost is **amplification, not a single charge**. One user request can generate 5–15+ model calls and multiple tool invocations. Monitoring must be **per invocation**, not per account aggregate.

---

## Key Monitoring Tools & Their Roles

| Tool | What It Captures | Agent-Specific Value |
|---|---|---|
| **Amazon Bedrock AgentCore Observability** | Per-invocation trace of agent orchestration: inference calls, tool invocations, memory operations, guardrail evaluations | Primary tool for agent consumption visibility |
| **Amazon CloudWatch Metrics** | Aggregate token counts, invocation counts, latency percentiles, error rates | Trending and alerting at scale |
| **AWS X-Ray** | Distributed trace across components (agent → Lambda → KB → model) | Attribute latency to a specific component |
| **CloudWatch Logs / Insights** | Structured agent trace logs, tool call payloads | Debugging retry loops and tool failures |
| **AWS Cost Explorer (with tags)** | Spend per agent, per model, per team attribution | Cost driver identification |

---

## Bedrock AgentCore Observability: Critical Details

> **Exam Gotcha:** AgentCore Observability is **disabled by default** for Bedrock Agents. You must enable it explicitly at agent creation or update time to capture trace data.

| Setting | Options / Notes |
|---|---|
| **Trace Capture** | Enabled/Disabled per agent |
| **Destination** | CloudWatch Logs (default), Amazon S3, or both |
| **Data Captured** | Model invocation inputs/outputs, tool call params, memory ops, guardrail results |
| **Retention** | CloudWatch Logs retention policy (default: never expire — set explicit retention to control storage cost) |

**Observability event types captured per invocation:**
- `PRE_PROCESSING` — input classification and routing decisions

- `POST_PROCESSING` — final response synthesis
- `GUARDRAIL` — content filter evaluations (billed separately when invoked)

## Metrics to Monitor Per Invocation

| Metric | What It Detects | Action Signal |
|---|---|---|
| **Model calls per user request** | Orchestration complexity, retry storms | Investigate planning prompt efficiency, tool batching |
| **Token usage per invocation** (input + output) | Prompt bloat, context window overrun | Trim system prompts, cap tool result lengths |
| **Tool call count and latency** | External API dependency, N+1 query patterns | Parallelize tool calls, cache tool responses |
| **Retry loops (same action repeated)** | **Silent cost amplifier** — bill grows with no traffic change | Fix error handling, validate tool inputs |
| **Memory operation count** | Session state churn, oversized memory payloads | Reduce memory write frequency, prune session data |
| **Knowledge base retrieval token volume** | Over-fetching context, broad embeddings | Tighten retrieval filters, reduce chunk size |

| Anti-Pattern | Why It's Wrong | Correct Pattern |
|---|---|---|

## Optimization Checklist

**Reduce model calls per invocation:**
- Move static instructions into system prompt (not repeated per tool call)
- Batch multiple tool operations into single action group execution
- Use agent memory efficiently — avoid re-fetching context already in session

**Reduce token consumption per call:**
- Cap tool result length returned to orchestration model
- Trim retrieved knowledge base chunks (smaller chunk size = fewer input tokens)
- Set `maxTokens` response limits on synthesis call

**Reduce tool call cost:**
- Use short-lived Lambda functions (sub-second where possible)
- Cache repetitive tool responses (e.g., policy lookups) with short TTL
- Parallelize independent tool calls in orchestration prompt instructions

**Monitor proactively:**
- Set CloudWatch alarms on **tokens per invocation** and **retry loop detection**
- Alert when agent trace shows >X model calls per request
- Track cost per invocation as a primary dashboard metric

## FM Inference Cost Levers (Ranked by Impact)

- **Best practice:** Static content (system prompts, tool schemas, few-shot examples) at the start; dynamic user input at the end.

| Retry loops | Hidden amplification on failures | Set max retries; use exponential backoff with jitter |

## Token Usage Optimization (Bedrock / LLM Inference)

**Monitor First:**
- **CloudWatch Metrics:** `InputTokenCount`, `OutputTokenCount`, `Invocations`, `InvocationLatency`, `InvocationClientErrors`
- **Bedrock AgentCore Observability:** Trace token consumption per agent orchestration step (planning call, tool calls, synthesis call)
- **Cost Explorer Groupings:** Filter by usage type to separate input vs output token spend

**Optimization Levers:**

| Lever | Mechanism | Impact |
|---|---|---|
| **Model Selection** | Switch to smaller model meeting quality bar | Reduces per-token rate on every request |
| **Prompt Trimming** | Shorten system prompts, remove redundant instructions | Reduces input tokens per request proportionally |
| **Context Window Management** | Retrieve only necessary context; truncate history | Linear reduction in input token cost |
| **Response Length Capping** | Set `max_tokens` / `maxTokens` parameter | Hard ceiling on output token spend |
| **Prompt Caching** | Cache static prefix KV states (e.g., tool schemas, system prompts) | Cached reads billed at reduced rate (typically ~10% of uncached) |
| **Batch Inference** | Move tolerant workloads to Bedrock Batch Inference | 50% discount vs on-demand token rates |

> **Exam Gotcha - Prompt Caching Rules:**
> - Minimum prefix length required (e.g., Anthropic Claude: 1024 tokens; Amazon Nova: vary by model).
> - Cache writes billed **higher** than uncached input tokens on some models.
> - Any change to tokens within prefix invalidates the entire cache backward from the change point — place all dynamic content **after** stable prefix.
> - Cached tokens billed at reduced rate on cache hit; cache TTL defaults (e.g., 5 minutes) require frequent reuse to justify.

**Prompt Structure for Cache Efficiency:**

```
[STATIC: System Prompt + Tool Definitions + Examples]  ← Cached
[DYNAMIC: User Query + Retrieved Context + Session]    ← Not cached
```

## Embedding Computation Costs

**Billing Patterns:**
- On-demand embedding inference: billed per token processed by embedding model
- Self-hosted embedding endpoints: billed per instance-hour regardless of actual usage

**Monitoring:**
- Track `embedding model invocation count` and `tokens per invocation` via CloudWatch
- For self-hosted: measure `GPU utilization` and `requests per second` to detect idle capacity

**Optimization Strategies:**

| Strategy | When to Use | Notes |
|---|---|---|
| **Embedding Caching** | Same text re-embedded repeatedly (e.g., document store with stable corpus) | Store hash → vector mapping; eliminates redundant API calls |
| **Batch Embedding Generation** | Large corpus ingestion, not user-facing | Lower per-token rates; amortizes overhead |
| **Right-Sized Embedding Model** | Quality bar is moderate | Smaller dimension models (e.g., 384 vs 1024 dims) process faster and store smaller |
| **Pre-compute at Ingestion** | Read-heavy workloads | Move embedding cost from query time to write time |
| **Dimension Reduction** | Legacy embeddings oversized | PCA/Matryoshka embeddings reduce storage and compute on downstream retrieval |

> **Exam Gotcha:** Amazon Bedrock `Batch` APIs for embedding models (`CreateBatchInferenceJob` with Embeddings models) apply **50% discount** vs on-demand — a common correct answer for bulk ingestion scenarios.

## Vector Database Storage Optimization

**Cost Components:**
- **Storage:** Per-GB pricing for vector data (e.g., Amazon OpenSearch Serverless, Amazon Aurora PostgreSQL with pgvector, Amazon MemoryDB)
- **Compute:** Index build, query processing, and memory residency costs
- **Replication overhead:** Multi-AZ replication multiplies storage cost

**Monitoring:**
- **OpenSearch Serverless:** Track `VectorSearchCollectionStorageUsed`, `OCU hours`
- **Aurora PostgreSQL:** Track `FreeStorageSpace`, `IOPS`, `CPUUtilization`
- **Cost Explorer:** Filter by `Tag` on vector collection to attribute cost per application/model

**Optimization Strategies:**

| Strategy | Mechanism | Trade-off |
|---|---|---|
| **Dimensionality Reduction** | Store 256-dim instead of 1536-dim vectors | Slightly reduced recall @ k |
| **Quantization / Compression** | Scalar quantization (int8), product quantization (PQ) | Lower memory footprint; minor accuracy loss |
| **Index Selection** | HNSW (higher memory, faster query) vs IVF (compact, lower memory) | Balance query latency vs storage cost |
| **Tiering / Lifecycle** | Move rarely queried vectors to S3 + lazy reload | Cold vectors unavailable until rehydrated |
| **Pruning** | Remove stale, duplicate, or low-value vectors | Requires metadata filtering logic |
| **Ghost Vector Elimination** | Dedupe semantically equivalent vectors | Saves storage + reduces query noise |
| **Collection Sharding** | Partition by tenant/domain | Better cache locality; lower per-query cost |

> **Exam Gotcha:** OpenSearch Serverless charges based on **OCU hours** (compute) and **storage GB** — scaling to zero OCUs when idle is automatic if you configure `Idle OCU` settings. For infrequent query patterns, enabling `At rest collection tiering` moves cold vectors to S3.

| `Invocations` | Is traffic rising or is cost per request rising? |
| `InputTokenCount` + `OutputTokenCount` | Are prompts longer, or responses longer? |
| `InvocationLatency` | Is slowness a capacity issue or a model-size issue? |
| `ModelErrors` / `Throttles` | Are errors adding retry costs? |
| `GPU/CPUUtilization` (SageMaker) | Is provisioned capacity actually used? |
| `NumberofRequests` per agent | Are user actions amplified differently over time? |
| Vector DB: `StorageUsed` + `QueryLatency` | Is storage growing faster than queries? |

> **Exam Gotcha:** AWS X-Ray traces **per-request component attribution** (which service made it slow), while CloudWatch aggregates show **trends over time**. Use both: aggregate to spot a problem, trace to localize it. For Bedrock agents, **AgentCore Observability** adds per-step token/action detail that CloudWatch alone doesn't capture.

---

## Cost Attribution & Guardrails

- **Cost Allocation Tags:** Apply `Project`, `Model`, `Environment`, `Team` tags to Bedrock invoke calls (via log-based tagging), SageMaker endpoints, OpenSearch collections, and agent configurations.
- **AWS Budgets:** Set **forecasted** token/usage budgets — alerts when projected spend exceeds threshold before it happens.
- **Service Control Policies (SCPs):** Restrict expensive model access (e.g., deny `InvokeModel` on premium models) for dev environments.
- **Bedrock Guardrails + Model Invocation Logging:** Enable `ModelInvocationLogging` to S3/CloudWatch for token-level auditability.

---

## Anti-Patterns (Common Distractor Traps)

| Anti-Pattern | Why It's Wrong |
|---|---|
| Applying SageMaker auto-scaling to Bedrock token costs | Bedrock on-demand has no instances to scale; optimize tokens instead |
| Enabling prompt caching on volatile prefixes | Cache invalidates every request; no savings materialize |
| Buying EC2 Savings Plans for SageMaker | EC2 Savings Plans don't cover SageMaker `ml.*` instance types |
| Reducing vector dimensions without recall testing | May fall below quality requirements |
| Using Provisioned Throughput for intermittent traffic | Provisioned Throughput bills hourly regardless of utilization — only for steady or predictable workloads |
| Tagging only infrastructure resources (not model calls) | Token costs aren't instance-tied; tags must propagate to invocation logs |
| Assuming all caching is free | Cache writes billed; minimum prefix required; TTL reset on first cache hit after expiry |

# Skill 4.3.1: Secure CI/CD Pipelines by Checking for Code and Image Vulnerabilities

## Task 4.3: Operating, Monitoring, and Securing ML and AI Solutions — Secure ML and AI workloads and model endpoints

| Dimension | Amazon CodeGuru Security | Amazon Inspector |
|---|---|---|
| **Primary target** | Application source code (custom logic in pipeline repos) | Built workload artifacts (EC2, ECR images, Lambda packages) |
| **What it finds** | Hardcoded credentials, injection flaws, insecure patterns, policy violations, secrets in code | CVEs in OS packages/app dependencies, unintended network exposure, package vulnerabilities in assembled images |
| **Pipeline stage** | Pre-build / commit phase (static analysis on source) | Post-build / artifact phase (image scan after assembly) |
| **Exam trigger terms** | "source code vulnerability," "hardcoded API key," "secret in repo," "static analysis" | "container image CVE," "vulnerable package," "base image scan," "ECR image scan" |
| **Output action** | Findings gate merge/build via CodePipeline manual approval or failure | Findings gate deployment via Inspector + EventBridge → build failure or alert |

---

## Complementary Controls in the Pipeline (Do Not Confuse)

- **CodeGuru Security** = source-level → **does NOT inspect compiled images or third-party package CVEs.**
- **Inspector** = artifact-level → **does NOT find secrets or logic flaws in application code.**
- **Both needed together** — a pipeline with only one has a diagnostic blind spot.
- **AWS Secrets Manager** = runtime secret retrieval/rotation → replaces hardcoded credentials found by CodeGuru, but is not a scanner.

> **Exam Gotcha:** A question about "vulnerable Python package in a built image" → **Amazon Inspector**, not CodeGuru. A question about "credentials committed to a Git repo" → **CodeGuru Security**, not Inspector.

---

## Pipeline Integration & Gating Patterns

- **CodePipeline / CodeBuild integration:** Findings from CodeGuru Security appear as test reports; configure **manual approval stage** or **fail build on high-severity findings** using EventBridge rules that react to Inspector/CodGuru events.
- **Amazon ECR Enhanced Scanning (Inspector):** Enable at registry level; scans on push — supports continuous monitoring (re-scans when new CVEs published).
- **Lambda vulnerability scanning:** Inspector scans Lambda functions and associated layers for package-level CVEs — no agent required.
- **EC2 scanning:** Inspector requires SSM Agent on instances for host-based assessments.

**Decision matrix: What to scan and when**

| Artifact/Stage | Scanner | Notes |
|---|---|---|
| Raw source code (Python, Java, etc.) pre-commit | CodeGuru Security | Flags secrets, insecure APIs, OWASP Top 10 patterns |
| Dockerfile / build scripts | CodeGuru Security / manual review | Misconfigured image build steps |
| Built container image in ECR | Inspector (ECR Enhanced) | CVE scan, base image risks |
| Deployed EC2 instance | Inspector | OS/package vulnerabilities + network exposure |
| Lambda function | Inspector | Package vulnerabilities in deployment package/layers |

---

## Security Configurations & IAM for Pipeline Scanning

- **CodeGuru Security role needs:** `codeguru-security:CreateScan`, `codeguru-security:GetFindings`, access to source repo (CodeCommit/GitHub token) via IAM role or Secrets Manager.
- **Inspector role needs:** `inspector2:Enable`, `inspector2:ListFindings`, and for ECR: `ecr:DescribeRepositories`, `ecr:DescribeImages`; for EC2: SSM permissions to collect inventory.
- **Encryption:** ECR repo encrypted with **KMS customer-managed key (CMK)** to meet compliance; Inspector findings stored encrypted in S3 if exported.
- **VPC endpoint for ECR/Inspector:** Use interface endpoints (`com.amazonaws.region.ecr.api`, `com.amazonaws.region.inspector2`) to keep scan traffic private and avoid internet egress from build environments.

> **Exam Gotcha:** Inspector requires ECR repositories to be in **same account** for continuous scan unless delegated admin is configured in AWS Organizations. Cross-account image scanning requires **ECR repository policy + Inspector delegated admin**.

---

## Anti-Patterns & Common Traps

- **Widening IAM permissions to silence scan errors** — Scanner failures are not IAM denials; read the error type before changing policy.
- **Running scans but not gating deployment** — Findings that don't stop a pipeline are "reports nobody reads." Exam expects **gating** language.
- **Using Inspector to find secrets** — Inspector does not detect credentials; that is CodeGuru Security's job.
- **Using CodeGuru to find CVEs** — CodeGuru is static source analysis, not a CVE database scanner.
- **Scanning only on push, never re-scanning** — Inspector continuous monitoring alerts on **newly published CVEs** against existing images; trigger re-deployment or quarantine on critical findings.

---

## Compliance & Audit Tie-Ins

- **AWS CloudTrail:** Logs API calls for scanning activities (`codeguru-security:CreateScan`, `inspector2:Enable`). Configure **data events** if tracking object-level access to ECR images.
- **AWS Config:** Tracks whether ECR Enhanced Scanning is enabled; whether Inspector is enabled across accounts — use managed rules like `ecr-repository-tag-immutable-enabled`, `inspector-ecr-scan-enabled`.
- **Amazon EventBridge:** Route CodeGuru/Inspector findings to SNS/Security Hub/automated remediation (e.g., quarantine image by changing ECR lifecycle policy).

> **Exam Gotcha:** "Audit needs to prove images were scanned before deployment" → combination of **CodePipeline stage transitions in CloudTrail + Inspector findings export to S3/CloudWatch Logs**. Neither service alone gives a complete audit trail.

---

## Pipeline Security Deep-Dive (Beyond Scanning)

| Control | Implementation |
|---|---|
| **Least privilege for pipeline roles** | Separate roles: `CodeBuildRole` (pull source, push image), `DeployRole` (SageMaker create endpoint), `ScanRole` (Inspector/CodeGuru). Never reuse human IAM user. |
| **Secrets in pipeline** | Use **Secrets Manager** for GitHub tokens, ECR credentials, model registry auth; never bake into buildspec.yaml or Dockerfile. |
| **Image provenance** | Enable **ECR tag immutability**, sign images with **AWS Signer** (for Lambda/SageMaker containers), block unsigned images in deployment policy. |
| **Supply chain protection** | Pin base image digests (`FROM public.ecr.aws/...@sha256:...`), maintain private ECR mirror of approved base images, scan dependencies before promotion. |
| **Model artifact pipeline** | Validate model artifacts from Model Registry; block unregistered external models — use IAM conditions on `sagemaker:ModelApprovalStatus`. |

---

## Rapid Decision: Finding Type → Service

| Finding described in question | Correct AWS service |
|---|---|
| Hardcoded AWS access key in Python file in repo | Amazon CodeGuru Security |
| SQL injection pattern in application code | Amazon CodeGuru Security |
| CVE-2024-XXXX in `numpy==1.24.0` inside Docker image | Amazon Inspector (ECR Enhanced) |
| Open SSH port on training EC2 instance | Amazon Inspector (Network Reachability) |
| Container running as root in image | Amazon Inspector (CIS benchmarks) or CodeGuru for Dockerfile misconfig |
| Prompts attempting jailbreak at inference time | Amazon Bedrock Guardrails (runtime control, not pipeline scan) |
| Model endpoint accessible from public internet | VPC/Security Group review; Inspector network exposure findings |

> **Exam Gotcha:** "Inference path reachable from internet" is a **security group / network configuration issue**, not solved by CodeGuru or Inspector. Inspector may *flag* network exposure on EC2, but the fix is SG/VPC configuration.

---

## Memorize — Hard Rules

- **CodeGuru Security is SAST** (static); **Inspector is DAST/packages** (dynamic/package-level).
- **Inspector + ECR Enhanced Scanning:** continuous, default enabled on push, re-scans within 24h of new CVE publication.
- **CodeGuru findings:** severity levels Critical/High/Medium/Low/Info; gate on **Critical + High** for production ML pipelines.
- **Neither service scans model weights or training data** for data poisoning — that requires separate validation (e.g., data quality checks, model evaluation in SageMaker Clarify).
- **Secrets Manager rotation** does not auto-update code that bakes secrets; it is for runtime retrieval.

# Skill 4.3.2: Configure Least Privilege Access to ML and AI Artifacts

## Task 4.3: Operating, Monitoring, and Securing ML and AI Solutions - Secure ML and AI workloads and model endpoints

---

## Core Objective & Scope

Grant identities the **minimum permissions required** to perform their job on ML artifacts — training data, model artifacts, endpoints, pipeline resources — and nothing beyond. Apply to both **human identities** (engineers, data scientists) and **workload identities** (training jobs, inference endpoints, Lambda functions).

---

## IAM Policy Scoping for ML Artifacts

| Artifact Type | Primary Resource ARN Pattern | Key Actions to Scope |
|---|---|---|
| **S3 Training Data** | `arn:aws:s3:::bucket/prefix/*` | `s3:GetObject`, `s3:PutObject`, `s3:ListBucket` (bucket-level) |
| **SageMaker Model** | `arn:aws:sagemaker:region:acct:model/*` | `sagemaker:CreateModel`, `DescribeModel`, `DeleteModel` |
| **SageMaker Endpoint** | `arn:aws:sagemaker:region:acct:endpoint/*` | `sagemaker:InvokeEndpoint` (data-plane), `CreateEndpoint` (control-plane) |
| **SageMaker Training Job** | `arn:aws:sagemaker:region:acct:training-job/*` | `sagemaker:CreateTrainingJob`, `StopTrainingJob` |
| **ECR Image** | `arn:aws:ecr:region:acct:repository/repo-name` | `ecr:GetDownloadUrlForLayer`, `ecr:BatchGetImage`, `ecr:BatchCheckLayerAvailability` |
| **Bedrock Foundation Model** | `arn:aws:bedrock:region::foundation-model/model-id` | `bedrock:InvokeModel`, `bedrock:InvokeModelWithResponseStream` |
| **KMS Key (artifact encryption)** | `arn:aws:kms:region:acct:key/key-id` | `kms:Decrypt`, `kms:GenerateDataKey`, `kms:Encrypt` |

---

## Policy Construction Patterns

- **Resource-level scoping** — Always attach `Resource` ARNs to `Allow` statements. Avoid `"Resource": "*"` in production policies.
- **Condition keys to narrow access** — Use `aws:SourceIp`, `aws:PrincipalTag`, `s3:prefix`, `sagemaker:WorkteamArn`, or `aws:RequestedRegion` to add context boundaries.
- **Permission boundaries** — Attach to IAM entities to cap maximum permissions regardless of attached policies. Critical for delegated admin scenarios.
- **Separate human vs. workload identities** — Engineers get IAM Users/Roles with console access; training jobs and endpoints get **execution roles** with only API-level permissions required at runtime.
- **Scoped-down S3 access for training** — Grant bucket-level `s3:ListBucket` with `Condition: {"StringLike": {"s3:prefix": ["training-data/*"]}}` and object-level `s3:GetObject` on `arn:aws:s3:::bucket/training-data/*`.

> **Exam Gotcha:** `s3:ListBucket` is a **bucket-level** action (Resource must be the bucket ARN). `s3:GetObject` and `s3:PutObject` are **object-level** actions (Resource must be the object ARN or wildcard prefix).

---

## Credential Selection Decision Matrix

| Scenario | Credential Type | Rationale |
|---|---|---|
| **Production workload** invoking FM/endpoint | **IAM Role with temporary credentials** (via STS) | Auto-rotated, least privilege, inherits identity policy, no static secret in code |
| **Short-term exploration/notebook** | Short-term Bedrock API key (session-bound) | Inherits generating identity's permissions; expires with session |
| **Long-running dev/test** | Long-term API key stored in **AWS Secrets Manager** | Rotatable via Secrets Manager; still not recommended for production |
| **Cross-account access** | IAM Role with trust policy (sts:AssumeRole) | No static keys shared across accounts |
| **On-prem/hybrid** | IAM Roles Anywhere (certificate-based) | Temporary credentials for non-AWS hosts |
| **SageMaker training needing S3** | Execution role attached to training job | Role policies scope exactly which bucket/prefix the job can read/write |

> **Exam Gotcha:** Long-term API keys are documented by AWS for **exploration and development only** — never production. The correct answer for production is always a role with temporary credentials. A key found in code, an image, or an environment file is the anti-pattern.

---

## Service-Specific Least Privilege Configurations

### SageMaker
- **Execution role** (training/inference) — distinct role per workload type; avoid reusing admin or human roles.
- **Notebook instances** — attach role with least privilege; disable direct internet access by placing in private subnet with VPC endpoints.
- **Model registry / pipeline** — separate roles for `sagemaker:RegisterModel` vs. `sagemaker:DeployModel` to enforce separation of duties.

### Amazon Bedrock
- **InvokeModel permissions** — scope to specific foundation model ARNs, not `bedrock:*` across all models.
- **Knowledge base access** — separate role for `bedrock:Retrieve` vs. `bedrock:InvokeModel` when RAG is involved.
- **Guardrails application** — associate guardrail policy at the API call or agent level; ensure role has `bedrock:ApplyGuardrail` where required.

### S3 (Datasets & Artifacts)
- **Versioning + lifecycle** — enable versioning to protect against accidental deletion; least privilege includes denying `s3:DeleteObject` for readers.
- **Block public access** — enable at account and bucket level; use as defense-in-depth alongside IAM.

### KMS (Encryption Keys)
- **Key policy always wins** — IAM policies grant permission, but the KMS key policy must also allow the principal. Both must grant `kms:Decrypt` for S3/SageMaker encrypted artifacts.
- **Separate keys per use case** — training data key vs. model artifact key vs. log encryption key; limits blast radius.

---

## Security & Compliance Integration

| Control | Purpose in Least Privilege Context |
|---|---|
| **IAM Access Analyzer** | Identifies resources shared with external entities; flags overly permissive S3 buckets, KMS keys, IAM roles |
| **IAM Policy Simulator** | Dry-run policy changes before applying; validates effective permissions |
| **AWS CloudTrail (management events)** | Audits who granted/revoked permissions, who assumed roles |
| **AWS Config rules** | Detect over-permissive policies (e.g., `iam-policy-no-statements-with-admin-access`) |
| **S3 Storage Lens + Trusted Advisor** | Flags buckets with public read/write or cross-account access |

> **Exam Gotcha:** IAM policy grants and KMS key policy grants must **both** allow access to KMS-encrypted artifacts. If S3 access succeeds but decryption fails, the error is `AccessDenied` or `InvalidObjectState` — the root cause is often a missing `kms:Decrypt` in the IAM policy **or** a key policy that doesn't include the principal.

---

## Anti-Patterns & Common Distractor Traps

- **Widening permissions to clear an `AccessDenied` error** — Read the error: it names the denied action, resource, and principal. Grant exactly that action on exactly that resource.
- **Using a single elastic role for everything** — Over-permissive role attached to training job or endpoint is a top finding. Separate roles per workload type and pipeline stage.
- **Placing credentials in environment variables or baked into images** — Correct answer always references Secrets Manager or IAM roles.
- **Granting `sagemaker:*` or `s3:*` wildcard actions** — Scoped `Allow` with named actions always preferred.
- **Confusing control-plane and data-plane permissions** — `sagemaker:CreateEndpoint` (deploy) vs. `sagemaker:InvokeEndpoint` (call) are separate; a caller who can deploy does not automatically have invoke rights, and vice versa.
- **Forgetting bucket-level vs. object-level S3 actions** — `ListBucket` on `"Resource": "arn:aws:s3:::bucket"`; `GetObject` on `"Resource": "arn:aws:s3:::bucket/*"`. Mixing these is a classic incorrect answer.
- **Assuming Bedrock API key equals IAM credential** — Bedrock API keys are not IAM entities; they are generated from an IAM identity but scoped by that identity's permissions and a set expiration.

|---|---|

|---|---|

# Skill 4.3.4: Comprehensive Monitoring, Auditing, Compliance & Logging for ML/AI Systems

## Task 4.3: Secure ML and AI workloads and model endpoints

---

## Three-Pillar Recording Model

| Record Type | Service | Question Answered | Configuration Notes |
|---|---|---|---|
| **API Activity** | AWS CloudTrail | Who did what, when, from where? | **Management events**: default. **Data events**: manual enable |
| **Configuration State** | AWS Config | What did the resource look like? Was it compliant? | Requires rules defined; records timeline & drift |
| **Model Invocation** | CloudTrail **Data Events** OR Bedrock/SageMaker logging | What prompt went in? What response came back? | Often high-volume; may require separate enablement |

> **CRITICAL EXAM GOTCHA:** Default CloudTrail trails capture **only management events** (e.g., `CreateEndpoint`, `CreateModel`). Model invocation calls (e.g., SageMaker `InvokeEndpoint`, Bedrock `InvokeModel`/`Converse`) are **data events** — if a trail wasn't explicitly configured for data events, an auditor will find **nothing** even though models were invoked.

---

## Service-by-Service Configuration Matrix

| Service | Primary Purpose | Key Config Parameters | Common Distractor Trap |
|---|---|---|---|
| **AWS CloudTrail** | API activity audit trail | `EnableDataEvents`, `EventSelectors`, `TrailARN`, multi-Region toggle, S3/KMS destination | Assume trail = all events (data events excluded by default) |
| **AWS Config** | Resource configuration compliance & drift detection | `ConfigRule` (managed/custom), `ConfigurationRecorder`, `DeliveryChannel`, `RemediationAction` | Confuse with CloudTrail (Config is state, not activity) |
| **Amazon Inspector** | Vulnerability scanning (EC2, ECR images, Lambda) | `AssessmentTemplate`, `ScanConfiguration`, enabled per resource type | Think it logs API calls or checks IAM |
| **Amazon CodeGuru Security** | Static code analysis (code vulnerabilities, hardcoded secrets) | `AssociatedRepositories`, `Findings` output, built into CI/CD | Expect it to scan container images (that's Inspector) |
| **SageMaker Model Monitor** / **Bedrock Logging** | Model invocation input/output capture, data quality, drift | SageMaker: `DataCaptureConfig`, `MonitoringSchedule`; Bedrock: `ModelInvocationLoggingConfiguration`, S3/CloudWatch Logs destination, KMS key | Disable capture for cost but still expect audit trail |

---

## CloudTrail Deep Dive (High-Yield)

**Event Types**
- **Management Events** (default): Create, Update, Delete operations — e.g., `CreateModel`, `DeleteEndpoint`, `PutBucketPolicy`
- **Data Events** (explicit): Resource-level read/write — e.g., `InvokeEndpoint`, `InvokeModel`, S3 `GetObject`
- **Insights Events** (opt-in): Anomalous API call patterns detection

**Key CLI/Boto3 Parameters**
| Parameter | Purpose |
|---|---|
| `--enable-data-events` / `DataResources[]` | Specify which S3 buckets, Lambda functions, DynamoDB tables, or SageMaker endpoints to log at data-plane level |
| `--is-multi-region-trail` | Capture events from all Regions in a single trail |
| `--kms-key-id` | Encrypt log files at rest with customer-managed KMS key |
| `--cloud-watch-logs-log-group-arn` | Send logs to CloudWatch Logs for alerting/metrics |

## Common Anti-Patterns & Exam Traps

> **Trap 1 — "Trail exists, so invocation is logged"**
> Management event trail ≠ data event coverage. Always verify `EventSelectors` include model invocation resources.

> **Trap 2 — "Config = Activity"**
> Config tracks **configuration state**, not API activity. Config answers "was it encrypted?" CloudTrail answers "who called `InvokeEndpoint`?"

> **Trap 3 — "Inspector = CodeGuru"**
> Inspector scans **assembled artifacts** (EC2, ECR images, Lambda packages). CodeGuru Security scans **source code** for insecure patterns. Both are needed in a pipeline.

> **Trap 4 — "Bedrock logging = CloudTrail"**
> Bedrock's `ModelInvocationLoggingConfiguration` captures prompt/response **content** to CloudWatch Logs/S3. CloudTrail data events capture API call metadata (principal, time, IP) but **not** the payload content.

> **Trap 5 — "Multi-Region trail covers everything"**
> Multi-Region affects **geographic** coverage, not **event type** coverage. A multi-Region trail still logs only management events unless data events are configured.

# Troubleshoot & Debug Security Issues in ML/AI Systems

## Security Diagnostic Hierarchy

| Layer | Diagnostic Question | Primary Tool |
|---|---|---|
| **Identity** | Was the principal authorized for this action on this resource? | IAM Policy Simulator, CloudTrail `AccessDenied` |
| **Network** | Could traffic reach the endpoint/service? | VPC Flow Logs, Security Group rules, Reachability Analyzer |
| **Encryption** | Did decrypt fail due to wrong KMS key/permission? | CloudTrail KMS `Decrypt` events, Key policies |
| **Safeguards** | Was content blocked/masked by a guardrail policy? | Bedrock Guardrails traces, `InvokeModel` response `guardrailAction` |
| **Data Plane** | Was a model invocation captured for audit? | CloudTrail **data events** (configured separately) |

## Root-Cause Pattern Matching

### Symptom → Likely Cause

| Symptom | Most Probable Cause | Fix |
|---|---|---|
| **403 / AccessDenied on InvokeEndpoint** | Missing `sagemaker:InvokeEndpoint` on role; SCP denial; resource policy mismatch | Read `AccessDenied` message: names **operation + resource**. Grant least-privilege permission on that exact resource |
| **Training job fails in private subnet (timeout)** | No internet route AND no interface/VPC endpoint for required API (S3, ECR, CloudWatch Logs) | Add **interface endpoints** (PrivateLink) or **gateway endpoint for S3** |
| **Decrypt failure on model artifact/dataset** | KMS key missing `kms:Decrypt` for the role; key policy does not grant principal | Add grant/statement on **key policy** (key policies trump IAM alone) |
| **Model responds with blocked/masked content** | Guardrail policy triggered (content filter, denied topic, word filter, PII, grounding) | Inspect `trace` in `Converse`/`InvokeModel` response for `guardrailAction`: `INTERVENED`, `NONE`, `GUARDRAIL_INTERVENED` |
| **Audit sees no InvokeModel/InvokeEndpoint calls** | CloudTrail default trail records **management events only** | Configure **data events** on trail for `InvokeEndpoint`, `InvokeModel`, `Converse` |
| **Hardcoded credential found in code** | Static analysis gap (CodeGuru) | Remove from code; store in **AWS Secrets Manager** with rotation; grant runtime role temporary credentials |
| **CVE in deployed container image** | Image scanning not gating pipeline (Inspector/ECR scan) | Scan at build AND deploy; fail pipeline on `CRITICAL`/`HIGH` |
| **Widening policy fixed the error** | Anti-pattern: masking the symptom | Revert; use exact `AccessDenied` message to grant minimal operation |

> **Hard rule:** CloudTrail **data events are not enabled by default** and incur additional cost. A trail with only management events cannot show `sagemaker:InvokeEndpoint` or `bedrock:InvokeModel` — this is the #1 audit gotcha.

## IAM & Credential Debugging

### Bedrock Credential Types

| Credential | Lifespan | Use Case | Production? |
|---|---|---|---|
| **IAM Role (temporary via STS)** | Auto-rotated, session-bound | Production workloads, EC2/ECS/Lambda | ✅ **Required** |
| **Short-term Bedrock API key** | Inherits identity session expiry | Notebook exploration, ad-hoc testing | ⚠️ Dev only |
| **Long-term Bedrock API key** | Explicit expiry, own identity | Exploration & development (AWS-documented) | ❌ **Not for production** |
| **Static secret in code/image/env** | Infinite until leaked | Never | ❌ **Compliance failure** |

### Debug IAM Denials

- **Read the explicit deny first:** SCP → resource policy → permissions boundary → session policy → identity policy
- **CloudTrail `AccessDenied`** includes: `userIdentity.arn`, `eventSource`, `eventName`, `errorMessage`, `sourceIPAddress`
- **Explicit deny always wins** over allow
- **KMS requires both IAM permission AND key policy allow** — IAM alone is insufficient

```python
# Boto3: debug endpoint invocation denial
response = sm_runtime.invoke_endpoint(
    EndpointName="my-endpoint",
    ContentType="application/json",
    Body=payload
)  # Catch ClientError; read e.response['Error']['Code'] and ['Message']
# AccessDeniedException → IAM; ValidationError → payload; ModelError → model serving
```

## Network Isolation Debugging

```
[Instance/Job] → [Security Group (outbound)] → [Subnet Route Table] → [NAT IGW | VPC Endpoint | Nothing]
                                                        ↓
                                                "Failed to connect"  
```

| Failure Point | Error Signature | Fix |
|---|---|---|
| **No route to internet AND no endpoint** | `ConnectionTimeout`, `EndpointConnectionError` | Add **VPC interface endpoint** (PrivateLink) for each API (SageMaker, S3, ECR, STS, CloudWatch Logs) |
| **Security Group outbound denies** | Timeout (not AccessDenied) | Allow outbound `TCP 443` to VPC endpoint prefix list |
| **Security Group inbound too broad** | `0.0.0.0/0` on endpoint/inference SG | Restrict to VPC CIDR or specific SG reference |
| **PrivateLink limitation** | Cross-Region connectivity | PrivateLink is Region-scoped; use Transit Gateway across Regions |

> **Gotcha:** Network connectivity failure is **timeout**, not `AccessDenied`. If you see `AccessDenied` with VPC endpoints, check the **endpoint policy** — it can deny even when IAM allows.

## Guardrails & Content Safeguards Debugging

### Bedrock Guardrails Policy Types

| Policy | Detects | Debug Output |
|---|---|---|
| **Content filters** | Harm categories (hate, sexual, violence) with strength thresholds | `guardrailAction`: `BLOCKED` |
| **Denied topics** | Prohibited subject areas (free text + regex) | `INTERVENED` |
| **Word filters** | Profanity, custom blocklist terms | `MASKED` or `BLOCKED` |
| **Sensitive information filter** | PII (SSN, account numbers, custom regex) | `MASKED` |
| **Contextual grounding** | Response not supported by retrieved passages (RAG hallucination) | `groundingAction`: `BLOCKED` |
| **Automated Reasoning** | Statement contradicts formally-expressed rules/policies | `BLOCKED` |

### Debugging Guardrail Intervention

```python
response = bedrock_runtime.converse(
    modelId="...",
    guardrailConfig={"guardrailIdentifier": "...", "guardrailVersion": "1"},
    messages=[...]
)
# Response includes:
# response['trace']['guardrail']['guardrailAction']  # NONE | INTERVENED
# response['trace']['guardrail']['inputAssessments'][0]  # per-policy details
```

> **Separate controls:** Guardrails filter **content**; IAM controls **access**. A blocked response may mean the guardrail worked (not a bug). Validate against `guardrailAction` before troubleshooting IAM.

## CI/CD & Image Security Debugging

| Tool | Detects | NOT Detects |
|---|---|---|
| **Amazon CodeGuru Security** | Hardcoded credentials, insecure patterns, OWASP-vulnerable code | CVE packages in base image |
| **Amazon Inspector** | CVEs in ECR images, EC2, Lambda; unintended network exposure | Application logic flaws, hardcoded secrets |
| **Amazon ECR Scan (Basic/Enhanced)** | CVEs in stored images | Runtime exploits |

**Pipeline gates:** Fail build on `CRITICAL`/`HIGH`; pass with `MEDIUM` if documented; block deploying image with CVEs in base OS.

> **Anti-pattern:** Running only static analysis (CodeGuru) or only image scanning (Inspector). Both answer different questions; both must gate delivery.

## Monitoring & Audit Integration

| Tool | Records | Configure |
|---|---|---|
| **CloudTrail — Management events** | `CreateEndpoint`, `DeleteModel`, `PutModel` | On by default (90-day history) |
| **CloudTrail — Data events** | `InvokeEndpoint`, `InvokeModel`, `GetObject`, `Converse` | **Manually enabled**; sent to S3/CloudWatch Logs |
| **AWS Config** | Configuration drift of endpoints/roles against rules | Write custom/managed rules; timeline view |
| **VPC Flow Logs** | Network flows (who connected to endpoint, port, bytes) | Publish to CloudWatch Logs/S3 |
| **Bedrock invocation logs** | Model prompts + responses | CloudWatch Logs model invocation logging toggle |

> **Key exam trap:** CloudTrail records *who* did it; AWS Config records *what the config looked like*; invocation logs record *what went in/out*. Each answers a different question. Compliance questions typically require **two of the three** together.

## Security Anti-Patterns (Fast-Fix Trap List)

1. **Widening IAM to clear `AccessDenied`** — Read the message: it names `arn:aws:iam::...` and exact operation. Grant precisely.
2. **Broad SG inbound rule (`0.0.0.0/0`) to fix connectivity** — Use source SG references or VPC CIDR ranges.
3. **Hardcoding credentials into image to avoid Secrets Manager setup** — Fails audit; use runtime IAM role + Secrets Manager for external keys.
4. **Enabling only management events for model audit** — Missing all invocation data; enable data events for `sagemaker:InvokeEndpoint` and `bedrock:InvokeModel`.
5. **Trusting VPC endpoints for content filtering** — Private connectivity is transport control, not data classification/scrubbing. Pair with Guardrails.
6. **Replacing permission error with broader S3 bucket policy** — Use bucket policy condition keys (`aws:PrincipalArn`, `aws:SourceVpce`) to add precision.

# Skill 4.3.6: Create VPCs, Subnets, and Security Groups to Securely Isolate ML and AI Systems

## Task 4.3: Secure ML and AI Workloads and Model Endpoints

---

### Core Concept & Business Objective

**Network isolation for ML/AI** ensures training jobs, notebooks, model artifacts, and inference endpoints operate in a private network unreachable from the public internet, with explicit egress controls to AWS service APIs via private endpoints.

> **Primary objective:** Eliminate public exposure of ML systems while preserving required connectivity to AWS services (S3, SageMaker, Bedrock, ECR, CloudWatch) through private paths only.

---

### VPC Architecture Decision Matrix

| Component | ML-Specific Use | Key Consideration |
|---|---|---|
| **Public Subnet** | Internet-facing notebooks (rare), NAT gateway placement | Never place training jobs, model endpoints, or artifact stores here |
| **Private Subnet** | Training jobs, batch transform jobs, notebook instances, inference endpoints, processing jobs | Default for all ML compute; requires NAT or VPC endpoints for AWS API access |
| **Isolated Subnet** | Highly sensitive data workloads; model endpoint enclaves | No internet path at all—must use VPC endpoints exclusively |
| **VPC Endpoint (Gateway)** | S3, DynamoDB access from private subnets | Free; route-table based; regional only |
| **VPC Endpoint (Interface / PrivateLink)** | SageMaker API, Bedrock API, ECR, CloudWatch Logs, STS, KMS | Billed per ENI/hour; uses DNS; requires security group on endpoint ENI |

---

### Security Group Rules for ML Workloads

| Direction | Source/Destination | Port | Purpose | Anti-Pattern |
|---|---|---|---|---|
| **Inbound** | VPC CIDR or specific SG | 443 | Model endpoint invocation from internal apps | `0.0.0.0/0` inbound |
| **Inbound** | VPC CIDR | 2049 | EFS/NFS mount for training data | Broad CIDR exposure |
| **Outbound** | VPC endpoint SG | 443 | S3, SageMaker, Bedrock, ECR API calls | Allowing `0.0.0.0/0` outbound "for convenience" |
| **Outbound** | NAT gateway SG | 80/443 | External package downloads (PyPI, conda) | Unrestricted external egress |
| **Inbound (endpoint SG)** | ML compute SG | 443 | VPC interface endpoint accepting calls | No SG on interface endpoint |

> **Exam Gotcha:** An interface VPC endpoint (PrivateLink) takes a security group. A gateway VPC endpoint (S3/DynamoDB) does not—it uses route table entries only.

---

### SageMaker Network Isolation Configurations

**Use VPC configuration parameters in SageMaker APIs:**

| SageMaker Resource | VPC Parameters | Notes |
|---|---|---|
| Training job (`CreateTrainingJob`) | `VpcConfig.Subnets`, `VpcConfig.SecurityGroupIds` | Requires 1+ private subnet; containers get ENIs in those subnets |
| Batch Transform (`CreateTransformJob`) | `VpcConfig.Subnets`, `VpcConfig.SecurityGroupIds` | Same pattern as training |
| Notebook Instance (`CreateNotebookInstance`) | `VpcConfig.Subnets`, `VpcConfig.SecurityGroupIds` | Direct internet disabled; API access via VPC endpoints required |
| Processing job (`CreateProcessingJob`) | `VpcConfig`, `NetworkConfig.EnableInterContainerTrafficEncryption` | Enable encryption flag defaults to `True` when VPC specified |
| Endpoint (`CreateEndpoint`) | `VpcConfig` via `CreateEndpointConfig` | When VPC attached, endpoint re-deployment needed to change VPC config |
| Studio Domain (`CreateDomain`) | `VpcConfig` with `AppNetworkAccessType=VpcOnly` or `PublicInternetOnly` | `VpcOnly` requires endpoints for SageMaker API, STS, CloudWatch |

> **Hard rule:** If a SageMaker job is in a VPC, it **cannot** have direct internet access unless a NAT gateway/instance exists in a routed public subnet. Mislated "broaden inbound SG" fixes are incorrect—the failure is egress/routing.

### Required VPC Endpoints for Common ML Architectures

| ML System Component | Required Endpoint(s) if No NAT |
|---|---|
| **SageMaker training/processing in VPC** | `sagemaker.api`, `sagemaker.runtime` (for invoke from VPC), `sts`, `ecr.api`, `ecr.dkr`, `logs`, `s3` (gateway) |
| **SageMaker notebook (VpcOnly)** | `sagemaker.api`, `sts`, `logs`, `s3` (gateway), `ecr.api`, `ecr.dkr` |

---

### Security & Compliance

| Concern | Control |
|---|---|
| **Data at rest** | KMS customer-managed keys for S3 artifacts, ECR images, EBS volumes attached to training jobs/notebooks, and SageMaker model artifacts |
| **Data in transit** | TLS enforced by SageMaker endpoints by default; inter-container traffic encryption for processing jobs with VPC; PrivateLink keeps traffic on AWS backbone |
| **Audit trail** | CloudTrail data events for `InvokeEndpoint` and `InvokeModel`; VPC Flow Logs for network-level traffic attribution |
| **Endpoint malware/insider risk** | Restrict outbound SG rules to only required services; deny `0.0.0.0/0` egress; use interface endpoints to eliminate NAT dependency |

---

### Common Distractor Traps

| Wrong Answer Pattern | Why It's Wrong |
|---|---|
| **"Add a NAT gateway to fix SageMaker API call failures from private subnet"** | NAT provides internet egress, but the more restrictive/efficient fix is an interface endpoint—keeps traffic private and avoids NAT data processing fees |
| **"Attach an internet gateway to the subnet"** | Exposes ML resources to inbound internet; violates isolation requirement |
| **"Broaden inbound security group rule"** | Inbound rules address incoming traffic; SageMaker jobs fail on egress/API reachability |
| **"Use a gateway endpoint for SageMaker API"** | Gateway endpoints support only S3 and DynamoDB; SageMaker/Bedrock require interface endpoints |
| **"Security groups control routing between subnets"** | SGs are stateful firewalls on ENIs; routing uses route tables, not SGs |
| **"Private connectivity encrypts traffic end-to-end"** | PrivateLink isolates the network path; encryption (TLS) is a separate control at the application layer |

---

### Anti-Patterns (High-Yield)

> **Anti-Pattern 1: Single broad security group shared across all ML resources.**  
> "Public-accessible" inbound rules or `0.0.0.0/0` egress on a training job SG defeats isolation. Use per-component SGs, referencing other SGs as sources/destinations.

> **Anti-Pattern 2: Creating a VPC but not attaching SGs with explicit endpoint egress.**  
> Resources fail with timeouts reading S3, pulling ECR images, or calling SageMaker APIs—and the debugger typically mistakes it for an IAM issue.

> **Anti-Pattern 3: Using public subnets for SageMaker Studio `VpcOnly` mode.**  
> Studio requires private subnet ENIs; public subnet configuration with non-VpcOnly mode still routes Studio traffic through internet by default, breaking data residency.

> **Anti-Pattern 4: Assuming VPC isolation replaces IAM controls.**  
> VPC limits *network reachability*; IAM limits *API authorization*. A private endpoint still requires proper IAM policies on the calling role and the endpoint policy.

---

### IAM & Endpoint Policies (Defense-in-Depth)

| Policy Type | Purpose | Example Restriction |
|---|---|---|
| **VPC Endpoint Policy** (interface) | Restrict which principals/actions can traverse the endpoint | Allow only `sagemaker:InvokeEndpoint` from specific roles; deny `sagemaker:DeleteEndpoint` |
| **IAM Role for ML Job** | Scope API permissions | `sagemaker:InvokeEndpoint` on specific endpoint ARN only |
| **Resource Policy on Endpoint** (if supported) | Limit invocation from specific VPCs/accounts | `aws:SourceVpce` condition to require PrivateLink origin |
| **KMS Key Policy** | Restrict decryption to specific VPC-originated principals | `aws:SourceVpce` or `aws:SourceVpc` condition |

**Condition keys to recognize:**
- `aws:SourceVpce` — Matches calls originating from a specific VPC endpoint
- `aws:SourceVpc` — Matches calls from any resource in a specific VPC
- `aws:VpcSourceIp` — Source IP (not commonly used for PrivateLink)

---

### Quick Decision Flow

```
Does the ML resource need internet access?
├── YES (external package downloads, public FM API)
│   ├── Place in PRIVATE subnet
│   ├── Route egress through NAT Gateway in PUBLIC subnet
│   └── Add SG outbound rule: destination = NAT SG, port 443
└── NO (all AWS services only)
    ├── Place in PRIVATE or ISOLATED subnet
    ├── Create interface endpoints for: SageMaker API/Runtime, Bedrock, ECR, STS, Logs
    ├── Create gateway endpoint for S3
    └── SG outbound rules: destination = endpoint SGs, port 443
```

> **Final Exam Gotcha:** When training jobs fail in a VPC with errors like `Connection timeout` or `Could not connect to endpoint URL`, the first diagnosis is **missing VPC endpoints or SG egress rules**—not IAM denial (IAM errors say `AccessDenied`).

# Skill 4.3.7: Identify and Mitigate Security Risks and Vulnerabilities in ML and AI Systems

## Task 4.3: Secure ML and AI workloads and model endpoints

---

## Risk Identification Framework

| Risk Category | Examples in ML/AI | Detection Service | Mitigation |
|---|---|---|---|
| **Code vulnerabilities** | Hardcoded credentials, insecure API patterns, injection flaws | Amazon CodeGuru Security | Fix code; store secrets in AWS Secrets Manager |
| **Image vulnerabilities** | Vulnerable base OS packages, outdated dependencies | Amazon Inspector, ECR scanning | Rebuild image with patched packages; gate CI/CD |
| **Over-permissive access** | Training job role with `s3:*` or `iam:*` | IAM Access Analyzer, CloudTrail | Scope to least privilege; resource-level permissions |
| **Network exposure** | Endpoint security group open to `0.0.0.0/0` | AWS Config, VPC Flow Logs, Inspector Network Reachability | Private subnets; restrictive SGs; PrivateLink |
| **Artifact store leakage** | S3 bucket readable by `AllUsers` | AWS Config, S3 Block Public Access, Trusted Advisor | Bucket policies; VPC endpoints; KMS encryption |
| **Untrusted model artifacts** | Model sourced from external registry | CodeGuru Security, Inspector | Verify provenance; scan before deploy; sign models |
| **Model invocation abuse** | Prompt injection, data exfiltration via responses | Bedrock Guardrails, CloudTrail data events | Input/Output filters; denied topics; sensitive info masking |
| **Configuration drift** | Endpoint encryption disabled post-deploy | AWS Config | Config rules with auto-remediation |
| **Insider threats / unauthorized calls** | Unknown principal invoking model | CloudTrail data events, CloudWatch Logs | IAM boundaries; service control policies (SCPs) |

---

## Security Controls Decision Matrix

| Requirement | Primary Control | Secondary Control | Anti-Pattern |
|---|---|---|---|
| **Who can invoke model** | IAM policy on endpoint/InvokeModel | SCP at org level | Static API key in image |
| **How calls reach model** | VPC endpoint (PrivateLink) | Security group ingress rules | Internet-facing endpoint with broad SG |
| **What enters/leaves model** | Bedrock Guardrails | Custom input validation | Logging prompts without PII masking |
| **Encryption at rest** | KMS CMK on S3, EBS, model artifacts | Bucket default encryption | Relying on SSE-S3 for compliance |
| **Encryption in transit** | TLS 1.2+ enforced | VPC private routing | Allowing HTTP (port 80) |
| **Audit trail** | CloudTrail (mgmt + data events) | CloudWatch Logs for app | Assuming default trail captures InvokeEndpoint |
| **Configuration record** | AWS Config | AWS Config conformance packs | Manual drift checks |
| **Secret storage** | AWS Secrets Manager | Parameter Store (SecureString) | Env vars, code, image layers |
| **CI/CD gating** | Inspector + CodeGuru in pipeline | Custom policies (OPA, cfn-guard) | Scan as post-deploy report only |

---

## Key Configuration Nuances (Exam-Gotchas)

> **CloudTrail Data Events are OFF by default.** Model invocations (`sagemaker:InvokeEndpoint`, `bedrock:InvokeModel`, `bedrock:Converse`) are data-plane operations. You must explicitly enable data events on the trail or the audit will show nothing.

> **Security group outbound rules matter equally.** Overly permissive egress (e.g., `0.0.0.0/0` to port 443) bypasses VPC endpoint enforcement if routes exist. Inbound rules prevent compromise; outbound rules prevent data exfiltration.

> **Safeguards are content controls, not access controls.** Bedrock Guardrails filter what the model sees/returns; they do not replace IAM. A user denied access to `InvokeModel` is blocked before any guardrail runs.

> **Static analysis vs. image scanning are NOT interchangeable.** CodeGuru Security finds issues in what developers wrote (hardcoded secrets, insecure patterns). Inspector finds known CVEs in what was assembled (base OS, third-party libraries). Pipelines need both.

> **Private connectivity ≠ content protection.** A VPC interface endpoint ensures traffic stays off the internet, but does not encrypt it (TLS handles that) or filter content (Guardrails handle that).

## Troubleshooting Security Issues

| Symptom | Likely Cause | Diagnostic | Fix |
|---|---|---|---|
| `AccessDenied` on `InvokeEndpoint` | Missing IAM action; wrong resource ARN; SCP blocking | CloudTrail event shows actual error + principal | Add scoped `sagemaker:InvokeEndpoint` for specific endpoint ARN |
| Training job fails in private subnet | No route to S3/SageMaker API | VPC Flow Logs showing egress blocks | Add Gateway Endpoint (S3) / Interface Endpoint (SageMaker) |
| Guardrail not blocking expected content | Policy not attached to invocation; filter misconfigured | Bedrock console review; test with known bad input | Attach guardrail version; adjust severity threshold |
| CloudTrail shows no model invocations | Data events not enabled on trail | CloudTrail console → Data events config | Enable data events for `sagemaker.amazonaws.com` / `bedrock.amazonaws.com` |
| Config rule flags endpoint non-compliant | Endpoint created with public access; encryption off | AWS Config compliance report | Recreate endpoint in VPC with encryption; use config remediation |
| Inspector finding on training image | Known CVE in base Python image | Inspector console → finding detail | Rebuild with patched base image; scan before deploy |

## High-Frequency Exam Traps

- **Widening IAM policy to fix `AccessDenied`** — Wrong. Read the error, grant only the specified action on the specified resource.
- **Adding inbound rules to fix outbound connectivity** — Wrong. SG inbound controls only ingress; egress issues require outbound rules or VPC endpoints.
- **Using CloudTrail default trail for invocation audit** — Wrong. Must explicitly enable data events.
- **Relying on Guardrails for authentication** — Wrong. Guardrails filter content; IAM controls who calls the model.
- **Assuming private subnet = secure** — Incomplete. Private networking controls path; you still need VPC endpoints (for access), TLS (for encryption), and Guardrails (for content).
- **Storing Bedrock API keys in Lambda env vars** — Wrong. Use Execution Role with `bedrock:InvokeModel` permission; secrets only if absolutely necessary, via Secrets Manager with rotation.

## Boto3 / SDK Patterns

# ✅ Correct: Assume role for production FM access

## Credential Precedence & Resolution

**AWS SDK credential resolution order (first match wins):**
1. Explicit credentials passed to client constructor
2. Environment variables (`AWS_ACCESS_KEY_ID`, etc.)
3. Shared credentials file (`~/.aws/credentials`)

## Anti-Patterns (Distractor Traps)

- **Embedding API keys** in container images, Lambda environment variables, or config files → use Secrets Manager only if a static secret is unavoidable
- **Using long-term API keys** in production because "it works" → rotation burden, breach blast radius
- **Shared keys across hosts/environments** → no per-principal auditability; use per-workload roles
- **Manual key distribution** by engineers per shift → human error, no automation
- **Widening IAM permissions** to clear `AccessDenied` → read the error: it names the operation and resource; grant only that

## Secrets Manager Integration (When a Static Key Must Exist)

- **Use case:** Third-party FM provider with no IAM federation (non-AWS model endpoints)
- **Pattern:** Store key → application retrieves via `GetSecretValue` at runtime → enable automatic rotation with Lambda rotation function
- **KMS:** Encrypt secret with customer-managed key; grant decrypt only to the workload role
- **Never log secret value** from response; use `SecretBinary` vs `SecretString` appropriately

```

  └─ Yes → IAM role + temporary credentials (EC2/ECS/Lambda role)
  └─ No (exploration) → Short-term key from current identity session

```

# Skill 4.3.9: Implement Safeguards and Sensitive Data Protection for ML/AI Solutions

## Task 4.3: Operating, Monitoring, and Securing ML and AI Solutions — Secure ML and AI workloads and model endpoints

---

## Core Concept & Primary Objective

**Purpose:** Insert policy enforcement between users and foundation models—evaluating **inputs (prompts)** and **outputs (responses)** to satisfy responsible AI requirements, prevent PII leakage, block prohibited content, and prevent hallucinated/unsupported claims.

> **Exam Gotcha:** Bedrock Guardrails evaluates **both prompts and responses**—you configure the direction explicitly. A guardrail applied only to input does nothing to block sensitive data in model output. Safeguard policies are **content-level controls**, not access controls. Guardrails do not replace IAM, VPC endpoints, or CloudTrail logging.

---

## Amazon Bedrock Guardrails: Policy Types Matrix

| Policy | Evaluates | Direction | Use Case | Block vs. Mask |
|---|---|---|---|---|
| **Content filter** | Harmful categories (violence, hate, sexual, insults, misconduct, prompt attacks) | Both | General toxicity/safety enforcement | Block or allow with threshold |
| **Denied topic** | Semantic topic match (not keywords) | Both | Refusing out-of-scope subjects (e.g., medical advice) | Block |
| **Word filter** | Custom keywords/bad words, regex | Both | Blocking profanity, internal codenames | Block or mask |
| **Sensitive information filter** | PII: SSN, DOB, email, phone, credit card, account numbers, custom regex | Both | Preventing customer/patient data exposure | Block or mask |
| **Contextual grounding check** | Claim vs. retrieved source passages | Output | RAG hallucination detection | Block or flag |
| **Automated Reasoning check** | Statement vs. formalized rules/policies | Output | Consistent policy-bound answers | Block or flag |

> **Exam Gotcha:** Contextual grounding uses **retrieved passages from the application's context**—you supply them in your API call. Automated Reasoning uses **formal rules** authored in Amazon Bedrock's Automated Reasoning language, not just textual policies. These two are distinct and not interchangeable.

---

## Key Configuration Parameters

### Boto3 / API Patterns

| Parameter | Purpose | Notes |
|---|---|---|
| `name` | Guardrail identifier | Max 50 chars, alphanumeric + `-`, `_` |
| `blockedInputMessaging` | Message shown when input blocked | Required if input blocking enabled |
| `blockedOutputMessaging` | Message shown when output blocked | Required if output blocking enabled |
| `contentPolicyConfig` | Content filter threshold: `LOW`, `MEDIUM`, `HIGH` | `NONE` to disable per category |
| `sensitiveInformationPolicyConfig` | PII entity list + `BLOCK`, `ANONYMIZE`, `MASK`, or `NONE` | `ANONYMIZE` replaces with generic label; `MASK` replaces with `***` |
| `contextualGroundingPolicyConfig` | `threshold` (0–0.99) + `filteringConfiguration` per type | Lower threshold = stricter |
| `applyGuardrailIdentifier` | Associate with a model invocation | Used via `InvokeModel`, `Converse`, `ConverseStream`, or Agents |

### CLI Reference

```
aws bedrock create-guardrail --name "finance-guardrail" \
  --blocked-input-messaging "Input blocked by policy" \
  --blocked-output-messaging "Output blocked by policy" \
  --sensitive-information-policy-config '{...}' \
  --contextual-grounding-policy-config '{...}'

aws bedrock apply-guardrail \
  --guardrail-identifier "abcd1234" \
  --guardrail-version "1" \
  --model-id "anthropic.claude-3-sonnet"
```

> **Exam Gotcha:** Guardrails are **versioned**. Updating a guardrail creates a new version—deployed applications keep using the old version until you explicitly update the version reference. Guardrails are **account- and Region-scoped**.

---

## Sensitive Data Protection: Full-Path View

The guardrail policy is necessary but **not sufficient** for sensitive data protection. The value must be protected **end-to-end**:

| Layer | Control | Purpose |
|---|---|---|
| **Prompt/response** | Bedrock Guardrails sensitive info filter | Mask/block PII in transit to/from model |
| **At rest** | AWS KMS encryption | Encrypt datasets, artifacts, logs, S3 buckets |
| **In transit** | TLS (default for Bedrock APIs) + VPC endpoint (PrivateLink) | Prevent network interception |
| **Logs** | CloudTrail data events, CloudWatch | Scan logs for residual PII; guard against logging raw payloads |
| **Code/artifacts** | CodeGuru Security (hardcoded secrets), Secrets Manager | No creds in code; rotate API keys |

---

## Deployment Patterns & Trade-offs

### Pattern A: Guardrails Applied at Bedrock API Level

**Use when:** All model invocations flow through Bedrock (`InvokeModel`, `Converse`, Agents).

**Advantage:** Centralized enforcement; no application code to deploy.  
**Caveat:** Does not cover models outside Bedrock or data leaving via other paths.

### Pattern B: Guardrails Applied at Application Layer

**Use when:** Custom orchestration, multi-model routing, or SageMaker-hosted models need protection.

**Advantage:** Unified policy across any model; application can log/monitor before calling downstream.  
**Caveat:** Requires embedding SDK calls and maintaining version alignment in application code.

### Pattern C: Hybrid (Bedrock + WAF/API Gateway)

**Use when:** Need rate limiting, IP restrictions, request size limits **plus** content filtering.

**Advantage:** Network-level abuse prevention complements content-layer guardrails.  
**Caveat:** Two distinct control planes; must test both in integration.

---

## Critical Decision: Which Guardrail Policy?

| Requirement | Correct Policy | Distractor |
|---|---|---|
| Block hallucinated RAG responses | **Contextual grounding check** | Denied topic |
| Prevent PII in model output | **Sensitive information filter** | Word filter |
| Stop discussion of financial advice | **Denied topic** | Content filter |
| Block offensive language variants | **Word filter** | Denied topic |
| Ensure answer follows internal policy rules | **Automated Reasoning check** | Contextual grounding check |
| Block harmful categories with adjustable severity | **Content filter** | Sensitive information filter |

> **Exam Gotcha:** Denied topics use **semantic similarity**, not simple keyword lists. Word filters use **literal matching** and **custom regex**. If the question says "topics the model should refuse to answer"—that's denied topics. If it says "specific terms or words"—that's word filter.

---

## IAM & Security Integration

- **Guardrail permissions:** `bedrock:CreateGuardrail`, `bedrock:ApplyGuardrail`, `bedrock:ListGuardrails`
- **Invocation with guardrail:** Requires both `bedrock:InvokeModel` (or `bedrock:Converse`) **and** permission to use the guardrail (`bedrock:ApplyGuardrail`)
- **Cross-account guardrails:** Not directly shared; replicate or manage in the calling account
- **Data protection:** Guardrails evaluate content in memory—configure **CCI/PHI handling** at the Bedrock API layer (model invocation logging still captures inputs/outputs unless explicitly disabled or redacted)

> **Exam Gotcha:** Guardrails **log blocked activity in CloudTrail** as `bedrock:ApplyGuardrail` or in CloudWatch. But the **prompt/response content** is only logged if you enable model invocation logging. Guardrails themselves do not log content autonomously.

---

## Anti-Patterns & Traps

| Anti-Pattern | Why It Fails | Correct Approach |
|---|---|---|
| Widening IAM to "fix" blocked guardrail responses | Guardrails are content-level, not permission-level | Adjust policy threshold or regex |
| Assuming contextual grounding = Automated Reasoning | Grounding checks source passage support; Automated Reasoning checks formal rules | Configure both if needed |
| Masking PII only in output but logging raw requests | Unmasked PII persists in CloudTrail/CloudWatch | Redact or disable invocation logging for sensitive fields |
| Setting content filter to `HIGH` for all categories | False positives block legitimate queries | Tune per category (`LOW`/`MEDIUM`) based on use case |
| Using denied topics for profanity | Semantic matcher isn't exact-match | Use word filter with custom regex |
| Storing guardrail version "1" but referencing "LATEST" in code | Version drift causes silent policy changes | Pin exact version in production |

---

## Memory Hooks

- **Six guardrail policies:** "C-D-W-S-C-A" → **C**ontent, **D**enied topics, **W**ord, **S**ensitive info, **C**ontextual grounding, **A**utomated Reasoning
- **Direction rule:** Content/Word/Sensitive → both; Contextual grounding/AR → output only
- **Grounding = Ground Truth (source text); AR = As Rules (formal policies)**
- **Masking hides value; blocking stops response entirely; anonymize replaces with label (e.g., `<PHONE_NUMBER>`)**
- **Guardrails = Layer 7; VPC endpoint = Layer 3/4; IAM = Layer 2** — all three needed for defense-in-depth
