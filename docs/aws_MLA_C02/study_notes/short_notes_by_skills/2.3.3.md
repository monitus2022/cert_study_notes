# Skill 2.3.3: Compare the Performance of Shadow Variants to Production Variants

## Task 2.3: Analyze and Evaluate the Performance of ML and AI Systems

---

### Core Concept & Business Objective

**Shadow testing** validates a candidate model/container/instance configuration against **real production traffic** with **zero customer impact**. Production answers all callers; the shadow variant receives an async copy of the request and logs its response for offline comparison.

- **Primary Goal:** Prove a change behaves correctly under real-world payloads, concurrency, and latency before exposing it to users.
- **What Gets Compared:** Predictions, latency (p50/p90/p99), error rates, throughput, and resource utilization.
- **Business Value:** De-risks deployments that offline evaluation alone cannot validate—request shapes, payload sizes, and traffic spikes not present in stored datasets.

---

### Shadow vs. Production: Architectural Trade-offs

| Deployment Pattern | Caller Receives | Purpose | Exam Signal Word |
|---|---|---|---|
| **Shadow Test** | Production response only | Compare candidate on live traffic copy | "Zero impact," "copy of live requests" |
| **A/B Test / Canary** | Candidate may serve some % | Measure business outcome against control | "Split traffic," "percentage rollout" |
| **Blue/Green** | New version serves all after cutover | Instant rollback via endpoint flip | "Single endpoint switch" |
| **Offline Evaluation** | N/A (stored dataset) | Pre-deployment scoring | "Before deploying," "benchmark dataset" |

> **Exam Gotcha:** A/B or canary splits route **live users** to the candidate. A shadow test never exposes candidate responses to callers. If the question states "callers must keep receiving production responses," the answer is **always** shadow testing.

---

### Key Configurations & Implementation Notes

- **Deployment Mechanism:** Add a shadow variant to an existing SageMaker AI endpoint using `ProductionVariants` alongside `ShadowProductionVariants` in the endpoint configuration.
- **Traffic Routing:** SageMaker automatically mirrors a configurable percentage (default: 100%) of incoming requests to the shadow variant; responses are **discarded** from the response path.
- **Region Support:** Shadow testing is available only in endpoints with **data capture enabled**—logs are stored in Amazon S3 for offline comparison.
- **Latency Measurement:** Shadow latency is measured end-to-end from request receipt to response generation, **not** including the async dispatch overhead.

**Boto3/CLI Parameter Nuances:**

```
aws sagemaker update-endpoint \
  --endpoint-name my-endpoint \
  --endpoint-config-name my-config \
  --retain-all-variant-properties

# EndpointConfig structure:
{
  "ProductionVariants": [{"VariantName": "prod-v1", "InitialVariantWeight": 1}],
  "ShadowProductionVariants": [{
      "VariantName": "shadow-v1",
      "ModelName": "candidate-model",
      "InitialInstanceCount": 2
  }]
}
```

### Comparison Metrics to Log & Analyze

| Metric Category | What to Compare | Why It Matters |
|---|---|---|
| **Operational** | Latency (p50/p90/p99), error rate, CPU/GPU utilization | Catches infra regressions invisible in offline tests |
| **Prediction Quality** | Shadow predictions vs. production predictions (agreement rate, drift in distribution) | Detects behavioral divergence on real data |
| **Request Shape** | Payload size, feature ranges, missing fields | Identifies production data patterns absent from training/validation sets |
| **Throughput** | Requests/sec, concurrent request handling | Validates autoscaling and capacity assumptions |

> **Exam Gotcha:** SageMaker shadow testing **does not** automatically compute prediction-quality comparisons. You must log shadow responses via Data Capture and run offline analysis (e.g., in Amazon CloudWatch, Athena over S3, or a custom pipeline). The shadow variant only mirrors traffic—it does not score predictions against labels unless you build that pipeline. Shadow tests validate *operational behavior* and enable *offline* model quality comparison.

---

### Anti-Patterns & Common Distractor Traps

| Distractor | Why It's Wrong |
|---|---|
| "Use SageMaker Model Monitor with a baseline" | Model Monitor detects **drift post-deployment**; it does not compare a shadow variant against production on live requests. |
| "Run an Amazon Bedrock programmatic evaluation" | Bedrock evaluations score models on **stored prompt datasets**, not live traffic streams. |
| "Create an MLflow tracking run" | MLflow tracks training experiments—parameters, metrics, and artifacts—not endpoint traffic mirroring. |
| "Replace production variant and watch error rate" | Exposes real users to candidate—violates the zero-impact constraint. |
| "Send half of traffic to candidate" | That's an A/B test, not a shadow test; callers receive candidate responses. |

---

### When to Use Shadow vs. Alternatives

**Choose SageMaker Shadow Testing when:**
- Candidate uses a different container image, framework, instance type, or inference code path.
- Need to validate against production traffic patterns without customer exposure.
- Comparing operational metrics (latency, error rate) under real concurrency.

**Choose Bedrock Evaluations when:**
- Evaluating a **foundation model** (not a SageMaker endpoint) on a curated prompt dataset.
- Running programmatic (ROUGE/BLEU/BERTScore), LLM-as-a-judge, or human-based scoring jobs.

**Choose MLflow on SageMaker when:**
- Tracking training runs, hyperparameters, artifact lineage, or tracing GenAI application steps.

**Choose SageMaker Model Monitor when:**
- Post-deployment monitoring of a **single live variant** for drift against a baseline.

---

### Key Takeaways for the Exam

- **Shadow = live traffic mirror, production answers, candidate logged.**
- **Data capture must be enabled** on the endpoint for shadow testing to log responses to S3.
- **Shadow testing is an operational validation tool**—it tells you the candidate survives real traffic; quality comparison requires separate offline analysis of logged predictions.
- **Latency measurement nuance:** SageMaker reports shadow latency excluding async dispatch overhead.
- **Do not confuse shadow with A/B testing**—A/B exposes users to both variants; shadow exposes users to only one.
- **SageMaker shadow tests support real-time inference endpoints**, not serverless inference or batch transform.
