# Skill 4.2.1: Select inference instance families to optimize performance and cost

## Task 4.2: Operating, Monitoring, and Securing ML and AI Solutions - Optimize and manage ML and AI infrastructure costs and performance

---

## Instance Family Selection Framework

### Primary Decision Drivers

| Decision Factor | Questions to Answer | Action |
|----------------|---------------------|--------|
| **Compute Shape** | CPU-bound or GPU-bound workload? | Select family matching dominant compute need |
| **Model Size** | Fits in memory headroom? | Size to measured peak utilization + 15-20% buffer |
| **Latency SLO** | p99 target requires accelerator? | GPU/Inferentia if CPU cannot meet threshold |
| **Batch vs. Real-Time** | Interactive or asynchronous processing? | Batch favors throughput-optimized; real-time favors latency-optimized |
| **Traffic Pattern** | Steady, diurnal, bursty, or intermittent? | Determines family flexibility and scaling strategy |

### Core Instance Families for SageMaker Inference

| Family | Optimized For | Best Use Case | Trade-off / Avoid When |
|--------|---------------|---------------|------------------------|
| **ml.c5 / ml.c6i** | Compute-optimized CPU | Smaller models, low concurrency, cost-sensitive inference | GPU not needed; latency SLAs loose |
| **ml.m5 / ml.m6i** | General-purpose CPU | Balanced CPU/memory; feature preprocessing with inference | Memory-heavy or GPU-bound models |
| **ml.r5 / ml.r6i** | Memory-optimized CPU | Large models not requiring GPU multipliers; embeddings servers | CPU compute insufficient for model math |
| **ml.g4dn** | NVIDIA T4 GPU, cost-effective inference | Medium CNN/transformer models; batch + real-time hybrid | Memory bandwidth-bound LLMs (>13B params) |
| **ml.g5** | NVIDIA A10G Tensor Core GPU | LLM inference, CV models, higher throughput than g4dn | Cost overkill for small tabular models |
| **ml.g6** | NVIDIA L4 GPU, improved TCO vs. g5 | Generative AI inference, superior performance/Watt | Availability in all regions may lag |
| **ml.p4d / p5** | NVIDIA A100/H100, training-grade | Very large model inference requiring top throughput | Excessive cost for standard inference |
| **ml.inf1 / inf2** | AWS Inferentia custom silicon | High-throughput, cost-efficient deep learning inference | Requires compilation (Neuron SDK); CPU fallback needed |
| **ml.trn1** | AWS Trainium (also serves inference) | Training-centric; inference for compatible compiled models | Complexity; not first choice for pure inference |

> **Exam Gotcha:** Inferentia (`ml.inf2`) can deliver up to 40% better price-performance for deep learning inference compared to comparable GPU instances, **but** models must be compiled with the AWS Neuron SDK—this is a hard prerequisite that often appears as a distractor for "works with any PyTorch model."

## Architecture Decision Matrix

### When to Use Each Family Type

| Scenario | Selected Family | Rationale |
|----------|-----------------|-----------|
| Tabular/structured data model (XGBoost, LightGBM) with low QPS | **ml.c5 / ml.c6i** | CPU families handle tree-based inference; no GPU needed |
| Computer vision (ResNet, YOLO) at moderate throughput | **ml.g4dn** | T4 GPU provides inference acceleration at lowest GPU cost |
| Real-time recommendations with <50ms p99 requirement | **ml.g5 / ml.inf2** | Need accelerator to hit strict latency targets |
| LLM serving (7B–13B params) for chatbot | **ml.g5 / ml.g6** | Memory (24–48GB GPU) needed for KV-cache + weights |
| LLM serving (>70B params) | **ml.p4d / multi-GPU** | Requires multiple A100s or tensor parallelism |
| High-throughput image classification at lowest cost | **ml.inf2** | Inferentia wins on total cost per million inferences |
| Embedding generation service | **ml.c6i / ml.r6i or ml.g4dn** | CPU handles many embedding models; GPU if heavy transformer |

### Accelerated vs. General-Purpose Compute

> **Hard Rule:** **Never right-size on launch configuration.** Always size from measured CloudWatch utilization over a representative window (min. 2 weeks to capture weekly seasonality). An endpoint busy 1 hour/day is a **scaling problem**, not a **sizing problem**.

## Key Configuration Parameters

### Boto3 / SDK Parameter Nuances

| Parameter | Purpose | Exam Note |
|-----------|---------|-----------|
| `InstanceType` | Sets the `ml.*` instance family/size | Must be compatible with container + model size |
| `InitialInstanceCount` | Starting instance count | Only for real-time endpoints; not serverless |
| `InstanceCount` | Number of instances behind endpoint | Target for auto-scaling policies |
| `ServerlessConfig` | Enables SageMaker Serverless Inference | No instance selection; pay per invocation + duration |
| `MaxConcurrency` | Max concurrent invocations per instance | Higher = denser utilization but riskier latency |
| `ModelDataDownloadTimeoutInSeconds` | Model download time before fail | Relevant for multi-model endpoints with cold starts |
| `VolumeSizeInGB` | EBS volume for model + container | Must exceed model + container layer size |

### Multi-Model Endpoint (MME) Instance Selection

| Consideration | Guidance |
|---------------|----------|
| **Instance memory** | Must hold **active models** + container runtime; not all models simultaneously |
| **Cold start latency** | Pay on-demand model load penalty when model not resident |
| **Storage** | EBS volume must fit all models + container; impacts load time |
| **When to use MME** | Dozens/hundreds of **intermittently invoked** models sharing a framework |
| **When NOT to use MME** | High-traffic single model, strict latency SLOs, divergent frameworks |

> **Exam Gotcha:** MME vs. Single-model endpoint is a classic trade-off. MME is **not** designed for consolidating a high-traffic production model—it introduces cold-start latency and contention. Reserve MME for many low-QPS models.

## Cost-Performance Trade-offs

| Optimization Action | When Appropriate | What You Sacrifice |
|--------------------|------------------|-------------------|
| **Downsize instance family** (g5 → g4dn) | GPU utilization consistently <50% at peak | Throughput headroom, future spike absorption |
| **CPU to GPU migration** | p99 latency > SLO on CPU family | Higher hourly cost; may need container rebuild |
| **GPU to Inferentia migration** | Stable deep learning model, compiled with Neuron | Flexibility: any model change requires recompilation |
| **Add instances (scale out)** | Vertical scaling cannot meet QPS | Higher base cost; requires load balancing |
| **Scale up (larger instance)** | Model size exceeds current memory | Fewer instances = less fault tolerance |
| **Multi-model endpoint** | Many intermittent small models | Cold-start latency; shared compute contention |

### Anti-Patterns and Common Traps

- ❌ **Selecting an instance based on training size** — Inference needs are smaller; training instances are oversized
- ❌ **Exclusively using GPU instances** — CPU families handle many models (XGBoost, TabNet, small PyTorch) at a fraction of cost
- ❌ **Oversizing to "plan for growth" without scaling policies** — Hold peak capacity during idle periods; ignores auto-scaling
- ❌ **Choosing `ml.p4d` for inference when `ml.g5` meets latency** — GPU VRAM/compute overkill inflates costs exponentially
- ❌ **Using single-model endpoints for hundreds of micro-models** — Each endpoint bills for dedicated instance hour(s)
- ❌ **Moving to Inferentia without recompiling** — Neuron SDK compilation is **mandatory**; PyTorch models cannot run directly
- ❌ **Rightsizing based on CPU utilization alone for GPU instances** — Monitor GPU utilization via CloudWatch `GPUUtilization`, not just `CPUUtilization`

## Monitoring Metrics for Instance Selection

| Metric | Where | What It Tells You |
|--------|-------|-------------------|
| `CPUUtilization` | CloudWatch | CPU headroom/family sizing |
| `GPUUtilization` | CloudWatch (custom or Container Insights) | GPU headroom; required for GPU right-sizing |
| `MemoryUtilization` | CloudWatch custom metric | Memory headroom; critical for MME |
| `DiskUtilization` | CloudWatch custom metric | Model storage pressure on EBS |
| `InvocationsPerInstance` | SageMaker CloudWatch | Traffic per instance; scaling trigger |
| `ModelLatency` | SageMaker CloudWatch | End-to-end processing time; size vs. speed trade-off |
| `OverheadLatency` | SageMaker CloudWatch | Model download/load time; MME cold start impact |
| `ModelCacheHit` | SageMaker CloudWatch (MME) | MME cache effectiveness; informs instance memory size |

## Instance Selection for SageMaker Serverless Inference

| Factor | Guidance |
|--------|----------|
| **When to choose serverless** | Intermittent traffic, low QPS, or can't predict baseline |
| **Instance selection** | None — AWS handles compute abstraction |
| **Cost model** | Per invocation + per GB-second of memory provisioned |
| **Memory range** | 1024 MB to 6144 MB, in 1 GB increments |
| **Max concurrency** | Provisioned concurrent invocations, configured separately |
| **Anti-pattern** | High sustained throughput; cost exceeds provisioned real-time |

> **Exam Gotcha:** Serverless Inference is **not** an instance "type" you select. It replaces instance selection entirely. The cost lever shifts from instance hours to **memory configuration + concurrency**—an exam distractor pairs "serverless" with "instance family selection."

## Quick Reference: Cost-Efficiency Hierarchy for Deep Learning Inference

```
Lowest cost → Highest cost (for equivalent throughput):
ml.inf2 (Inferentia) < ml.g4dn (T4) < ml.g6 (L4) < ml.g5 (A10G) < ml.p4d (A100) < ml.p5 (H100)
```

**But:** Inferentia requires Neuron compilation; prioritize ease-of-deployment vs. absolute cost when choosing.

## Exam-Ready Decision Flow

1. **Identify workload type**: tabular, CV, NLP, LLM, or embeddings
2. **Check latency SLO**: strict (<100ms) → accelerator; loose (>500ms) → CPU viable
3. **Measure utilization**: if <40% sustained → downsize; if >70% sustained → upsize
4. **Check traffic pattern**: steady → sized instance; diurnal → auto-scaling; intermittent → serverless
5. **Count models**: 1–5 models → per-model endpoints; dozens+ → multi-model endpoint
6. **Evaluate cost**: compare families at equivalent throughput; check Inferentia eligibility
7. **Select purchasing option**: steady baseline → SageMaker Savings Plan; variable → On-Demand
