# Skill 2.2.9: Optimize retrieval components and embedding models

## Task 2.2: Train, fine-tune, and customize models for ML and AI solutions

---

## Core Objective

Retrieval-Augmented Generation (RAG) quality depends on **what the retriever returns** before the generator ever speaks. Optimize the **embedding model → chunking strategy → vector store → retriever/ranker** pipeline to maximize context relevance and answer fidelity.

> **Exam Gotcha:** If retrieved passages fail, no prompt change or model fine-tune will fix the answer. Diagnose retrieval vs. generation failure **before** choosing a remedy.

---

## Embedding Model Selection

| Criterion | Recommendation | Notes |
|-----------|---------------|-------|
| **Domain-specific language** | Fine-tune embeddings or use domain-adapted embedding model (e.g., SageMaker JumpStart embeddings) | Generic embeddings underperform on jargon (medical, legal, engineering) |
| **Multilingual queries** | Use multilingual embedding model (e.g., Cohere Embed v3, Amazon Titan Multimodal) | Single model for multiple languages vs. per-language models |
| **Query vs. passage symmetry** | Use same embedding model for both queries and documents | Asymmetric embeddings break cosine similarity assumptions |
| **Vector dimension size** | Higher dimensions = more precision, more storage/memory cost | May justify 384–768 dims for balance; 1024+ for high precision |
| **Max input length** | Choose embedding model with context window ≥ your chunk size | Truncation silently discards text, harming retrieval |

**SageMaker AI embedding options:**
- **JumpStart** pre-trained embedding models (Hugging Face sentence-transformers, E5, BGE)
- **BlazingText** (`supervised` mode) for custom word/sentence embeddings via fastText
- **TensorFlow/PyTorch script mode** for fine-tuning Bi-encoders with contrastive loss
- **Bedrock Knowledge Bases** for managed embeddings (Titan Text Embeddings v2, Cohere Embed)

## Chunking Strategy Optimization

| Technique | Best For | Trade-off |
|-----------|----------|-----------|
| **Fixed-size with overlap** | Simple documents, quick baseline | May split semantic units; overlap mitigates at token cost |
| **Sentence-level / semantic** | Coherent queries needing precise retrieval | Requires sentence segmentation; may fragment context |
| **Recursive / token splitting** | Long structured docs (e.g., whitepapers, contracts) | More complex; better section preservation |
| **Document-structure-aware** (headers, tables, code blocks) | PDFs, markdown, HTML docs | Requires custom parser; highest retrieval precision |
| **Small chunk size (100–200 tokens)** | Granular facts, QA over specific snippets | Loses broader context; more chunks to store/query |
| **Large chunk size (500–1000+ tokens)** | Summarization, document-level reasoning | Dilutes semantic signal; introduces noise |

> **Exam Gotcha:** Chunk size is a **retrieval quality** trade-off, not just a cost decision. Chunks too large average out embeddings (washing out distinct topics), while chunks too small fragment multi-sentence facts.

**Overlap settings:** 10–15% overlap preserves boundary context; too high overlap wastes vector storage and query latency.

## Retriever & Ranking Optimization

| Component | Options | When to Use |
|-----------|---------|-------------|
| **Vector search engine** | OpenSearch Serverless, Amazon Kendra, Pinecone, pgvector (RDS) | Default for dense embedding retrieval |
| **Hybrid search** | BM25 + dense vector (OpenSearch, Kendra) | Improves recall when exact terms matter (IDs, product codes, acronyms) |
| **Re-ranking model** | Cross-encoder (e.g., `cross-encoder/ms-marco-MiniLM-L-6`) or SageMaker hosted reranker | Apply after vector search to re-sort top-N; boosts precision |
| **Metadata filtering** | Filter on fields (date, category, author) before/after vector search | Shrinks search space; prevents irrelevant-but-similar documents |

**Re-ranking pipeline pattern:**
1. Retrieve top 50–100 chunks via vector similarity
2. Run cross-encoder on query + each chunk
3. Keep top 3–10 for generation context

> **Exam Gotcha:** Cross-encoders are too slow for full corpus scoring. Use a **two-stage** retrieval architecture: fast bi-encoder (vector search) → slow cross-encoder (re-rank top-N only).

## Bedrock Knowledge Bases Components

| Setting | Impact |
|---------|--------|
| **Embedding model** (Titan v2, Cohere Embed v3) | Fixed for the KB after creation; changing requires rebuilding vector index |
| **Chunking strategy** (fixed-size, semantic, custom parser via Lambda) | Cannot be changed after KB creation without re-ingest |
| **Vector database** (OpenSearch Serverless, Aurora PostgreSQL, Pinecone) | Automatic setup for OpenSearch; bring-your-own for others |
| **Maximum tokens per chunk** | Set below embedding model context limit |
| **Overlap percentage** | Typically 10–15% to preserve multi-chunk context |

> **Exam Gotcha:** Bedrock Knowledge Bases **locks** chunking and embedding model at creation. Changing them requires creating a new KB and re-syncing data sources.

## Optimization Signals & Metrics

| Metric | Indicates | Action |
|--------|-----------|--------|
| **Hit rate / recall@k** | Proportion of queries where correct doc appears in top-k retrieved | Increase k, improve chunking, use hybrid search |
| **MRR (Mean Reciprocal Rank)** | Average rank position of first correct document | Improve ranking model, fine-tune embeddings |
| **nDCG** | Ranking quality across multiple relevant docs | Add cross-encoder re-ranker |
| **Context-faithfulness** | Answer grounded in retrieved context or hallucinated | Reduces retrieval trust requirement |

## Embedding Fine-Tuning for Domain Adaptation

**When to fine-tune:**
- Generic embeddings retrieve irrelevant passages on domain corpus
- Vocabulary includes domain jargon, acronyms, internal entity names
- Labeled pairs/queries with relevant vs. non-relevant documents are available

**Approach (SageMaker script mode):**
1. Build **contrastive learning dataset** — positive pairs (query + relevant doc), negative pairs (query + non-relevant doc)
2. Choose pre-trained sentence-transformer checkpoint (`all-MiniLM-L6-v2`, E5, BGE)
3. Fine-tune with **InfoNCE / MultipleNegativesRankingLoss** or **cosine similarity contrastive loss**
4. Evaluate on held-out query–document relevance set (recall@k, MRR)

> **Exam Gotcha:** Fine-tuning an embedding model on **unlabeled** corpus alone does not help. You need **labeled query–document relevance** pairs for contrastive fine-tuning.

**Alternative:** Use SageMaker JumpStart pre-trained domain embeddings before fine-tuning from scratch. Custom embeddings are a higher-effort, higher-reward path.

---

## Anti-Patterns & Traps

- **Changing the generator (temperature, prompt, fine-tune) when retrieval is failing** — retrieval has no answer so generator hallucinates or hedges.
- **Using same chunk size for all document types** — PDFs need structure-aware parsing; code files need line-aware splitting.
- **Over-large chunks** — dilutes semantic specificity; nearest-neighbor score becomes less meaningful.
- **Neglecting hybrid search for exact identifiers** — numbers, SKUs, product codes need lexical (BM25) match alongside dense retrieval.
- **Skipping re-ranking** — top-10 vector search results may still be loosely related; cross-encoder re-ranking noticeably raises precision.
- **Rebuilding KB frequently** — Bedrock KB locks parameters at creation; plan chunking and embedding model before first build.

## Exam Recall Checklist

1. **Diagnosis order**: Check retrieval → check generation → refine iteration
2. **Chunking changes require re-ingest** in Bedrock KB; parameter changes after creation not allowed
3. **Use same embedding model** for queries and documents in symmetric search
4. **Hybrid search** for exact terms; **dense vector** for semantic similarity
5. **Cross-encoder** for re-ranking top-N, not full corpus
6. **Fine-tuning embeddings** needs contrastive pairs (positive + negative examples)
7. **Overlap of 10–15%** is typical, not 50%+ unless structured docs demand it
8. **Embedding model context window** must exceed chunk size or text is truncated before vectorization
