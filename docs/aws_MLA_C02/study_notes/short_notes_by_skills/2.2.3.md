# Skill 2.2.3: Implement hyperparameter optimization (SageMaker AI automatic model tuning [AMT])
## Task 2.2: ML Model and Foundation Model (FM) Development — Train, fine-tune, and customize models for ML and AI solutions

**Core concept:** Hyperparameters are *not computable* — AMT searches them empirically by launching **many full training jobs** across declared ranges and keeping the combination that scores best on **one** declared objective metric. You pay for every trial.

| Manual HPO | SageMaker AMT | SageMaker Autopilot |
|---|---|---|
| You pick values, retrain, compare | You declare ranges + objective; AMT searches | AutoML: explores data prep, algorithms, *and* hyperparameters |
| Full control, no orchestration cost | No algorithm selection — you supply the estimator | Uses AMT **under the hood** to generate candidates |
| Fine for 1–2 knobs | Best for 3–10 impactful knobs | When you don't know the algorithm/problem framing |

> **Gotcha:** If the question asks "which algorithm/feature engineering is best," the answer is **Autopilot**, not AMT. AMT only tunes parameters of an estimator you already chose.

## AMT Job Anatomy — what must be configured

| Element | Rule |
|---|---|
| **Tunable hyperparameters** | Declared as ranges (Integer / Continuous / Categorical) — everything else is a **static** hyperparameter and must be passed separately |
| **Objective metric** | Exactly **one**; must appear in CloudWatch Logs (built-ins ship defaults; custom metrics need a **regex metric definition**) |
| **Objective type** | `Maximize` (AUC, accuracy, F1) vs `Minimize` (RMSE, MAE, log-loss) — pointing it the wrong way optimizes toward a *worse* model |
| **Resource limits** | `MaxNumberOfTrainingJobs` (search budget), `MaxParallelTrainingJobs` (concurrency), max runtime per training job |
| **Stopping condition** | Overall tuning-job runtime cap — separate from per-training-job caps |
| **Output** | Best training job's model artifacts + full tuning-job analytics (all trials, metrics) written to S3 |

> **Gotcha:** A trial whose objective metric never appears in the logs is marked **failed for tuning purposes** and is excluded from "best" — the job can burn budget with zero usable results. Verify the regex before launching.

> **Gotcha:** The **best training job ≠ production model**. Retrain the final model with the winning hyperparameters on the **full dataset** (trials often used a subset/validation split), and consider a larger instance for the final fit.

## Search Strategy Decision Matrix

| Strategy | How it works | Use when | Watch out |
|---|---|---|---|
| **Bayesian** (default) | Sequential model-based; picks next point from a surrogate model of past results | Small search space, **few hyperparameters**, budget under ~100 jobs | Poorly parallelizes — high `MaxParallelTrainingJobs` degrades it |
| **Random** | Samples independently from ranges | Large space, cheap trials, want max parallelism | No learning between trials |
| **Hyperband** | Successive halving; kills weak trials early, reallocates budget | **Large search space + long training times**; resource-constrained | **Requires early-stopping support** in the training container |
| **Grid** | Exhaustive over discrete values | Tiny, well-understood space; auditability | Combinatorial explosion; unsuited to continuous ranges |

> **Gotcha:** Adding a *categorical* hyperparameter multiplies the search space — cap categorical choices (≤ ~3–5 values) and tune the highest-impact knobs first (learning rate, batch size, tree depth, regularization).

> **Gotcha:** For learning rate and other scale-sensitive parameters, use a **logarithmic scaling type** — a linear range wastes most trials at values that never converge.

## Early Stopping, Completion Criteria & Warm Start

- **Automatic early stopping** — terminates a trial that has stopped improving on the objective metric; **reduces tuning cost directly**. Requires the container to emit the metric and support the early-stopping signal (built-ins and supported frameworks do).
- **Completion criteria** — stop when `TargetObjectiveMetricValue` is reached, or when the best result hasn't improved across *N* trials (convergence detection).
- **Warm start** — reuses prior tuning jobs so the search starts informed instead of cold. Types:
  - **IDENTICAL_DATA_AND_ALGORITHM** — same data, same algorithm, refined ranges.
  - **TRANSFER_LEARNING** — same algorithm, different dataset.
  - **SAME_DATA_DIFFERENT_ALGORITHM** — compare algorithms on one dataset.
- **Early stopping vs warm start vs more instances:** early stopping shortens *one run*; warm start shortens *the search*; more instances shorten *elapsed time* only while communication stays cheaper than the work saved.

> **Gotcha:** A warm-start configuration accepts up to **5 parent tuning jobs**, and a combined training-job cap applies across parents. Parent jobs must be in the same account/Region and already completed.

> **Gotcha:** A tuning job **cannot be resumed or restarted** — stop it and create a new one. Use `StopHyperParameterTuningJob` / `DescribeHyperParameterTuningJob`; `ListTrainingJobsForHyperParameterTuningJob` enumerates trials and `BestTrainingJob` names the winner.

## Cost, Time & Scale Interactions

- **Cost model:** total tuning cost ≈ (number of trials) × (per-job training cost). Every trial is a real, billed training job.
- **Cheapest-first pattern:** tune on a **data subset + smaller instance**, then retrain the winner on full data with the full instance type.
- **Distributed training × tuning:** data parallelism (replicas split batches) suits models that fit one device; model parallelism partitions a model too large for one device. Combining either with a large search multiplies cluster cost — shrink the search space first.
- **Time reduction is orthogonal to HPO:** more epochs = longer; changing the reported metric = no effect; shrinking validation = negligible. Only distribution/concurrency/early stopping move the needle.

## Security, Compliance & Operations

- **IAM:** a single **execution role** is assumed by the tuning job and inherited by every trial training job — scope it to the S3 data/artifact buckets, ECR image, and CloudWatch Logs.
- **Encryption:** **KMS** at rest for input data, model artifacts, and tuning-job output; TLS in transit to S3/ECR.
- **Network isolation:** enable **network isolation** + VPC config (subnets, security groups) to run trials with no outbound internet — required for regulated data; the container must not need external downloads at runtime.
- **Observability:** per-trial metrics and logs land in **CloudWatch** — this is where the loss curve that flattened (and should have triggered early stopping) is visible.

## High-Yield Anti-Patterns

- **Tuning everything at once** — dimensionality explodes the budget; tune the 3–5 knobs with real impact.
- **Wrong objective direction** — a tuning job will *faithfully* optimize toward the worst model.
- **No objective metric regex** — trials fail silently from the search's perspective.
- **Grid search on continuous ranges / huge spaces** — use Bayesian, Random, or Hyperband.
- **Bayesian with very high parallelism** — defeats the sequential surrogate model; use Random/Hyperband instead.
- **Assuming AMT selects the algorithm or cleans data** — that is Autopilot (or your own pipeline).
- **Expecting a hyperparameter to be *calculated*** — HPO is empirical search, never a closed-form solve.
- **Deploying the best trial's artifact without a full-data retrain.**
- **Ignoring early stopping** — the single highest-leverage cost lever in a tuning job.
- **Confusing within-run learning with HPO** — gradient descent updates *weights* inside one job; AMT varies *hyperparameters* across jobs.
