# Skill 4.1.6: Configure AI-Specific Performance Monitoring for Foundation Models (FMs), Such as Amazon Bedrock Evaluations

## Task 4.1: Monitor ML and AI Model Inference and Performance

---

## Core Objective & Evaluation Architecture

**Purpose:** Quantify foundation model output quality (not just operational metrics) using automated, judge-based, or human evaluation jobs on Amazon Bedrock.

| Evaluation Type | Mechanism | Best For | Scoring Output |
|----------------|-----------|----------|----------------|
| **Automatic** | Predefined metrics (accuracy, robustness, toxicity, semantic similarity) | Regression testing, fast iteration | Numeric scores per metric |
| **LLM-as-a-Judge** | Judge model (e.g., Claude) scores responses with explanations | Custom quality dimensions, agent workflows | Scores + rationale text |
| **Human-Based** | Amazon Mechanical Turk or private workforce ratings | Subjective quality, safety validation | Aggregated human ratings |

> **Exam Gotcha:** Automatic evaluation computes deterministic metrics only. If you need subjective quality, helpfulness, or brand-tone assessment, you **must** use judge-based or human-based evaluation—automatic jobs cannot produce these scores.

## Model Evaluation Job Configuration

### Key Parameters (Boto3/CLI)

| Parameter | Notes |
|-----------|-------|
| `evaluationConfig` | `automated` vs `human` |
| `inferenceConfig` | Model ARN, temperature, max tokens, top_p |
| `evaluationDataset` | S3 location + `metricNames` for automatic jobs |
| `evaluatorModelConfig` | Judge model ARN + prompt templates (`evaluatorModelConfig`) |
| `outputDataConfig` | S3 destination for results |
| `roleArn` | Bedrock evaluation role with S3 access |

### Sample CLI Structure
```bash
aws bedrock create-evaluation-job \
    --job-name "eval-v2" \
    --role-arn "arn:aws:iam::123456789012:role/BedrockEvalRole" \
    --inference-config '{"modelIdentifier": "anthropic.claude-3-sonnet-20240229"}'
```

> **Exam Gotcha:** Evaluation jobs require the IAM role to have `bedrock:InvokeModel` and `s3:GetObject`/`s3:PutObject` permissions. Missing role trust policy for `bedrock.amazonaws.com` is a common failure cause.

## CloudWatch Generative AI Observability

**What it monitors for FMs:**

| Metric Category | Specific Measures |
|-----------------|-------------------|
| **Invocation health** | Invocations, latency (p50/p90/p99), error count, throttles |
| **Token economics** | Input/output token counts, total tokens per invocation, cost proxies |
| **Agent traces** | End-to-end prompt chains: model calls, tool invocations, memory reads/writes |
| **X-Ray integration** | Distributed tracing spans for agent reasoning steps |

**Enabling:** CloudWatch > Generative AI > Enable → creates CW Agent or uses Bedrock/AgentCore native emission.

---

## Amazon Bedrock AgentCore Observability

| Feature | Detail |
|---------|--------|
| **Instrumentation** | OpenTelemetry-compatible spans emitted automatically—no manual SDK instrumentation for each tool/model call |
| **Captured spans** | Model inference, tool invocation, memory operations, guardrail evaluations |
| **Failure modes surfaced** | Tool call timeouts, truncated streaming responses, coordination stalls (agent retry loops), guardrail blocks |
| **Export options** | X-Ray, Amazon Managed Prometheus, 3rd-party OTel collectors |

> **Exam Gotcha:** AgentCore Observability is the **default** telemetry for agents on AgentCore Runtime. It is **not** a separate agent to build—it comes built in. Distractor options often suggest adding custom spans per tool, which is unnecessary.

## Monitoring Decision Matrix: FM vs Traditional ML

| Monitoring Need | Traditional ML (SageMaker) | Foundation Models (Bedrock) |
|-----------------|---------------------------|------------------------------|
| **Operational metrics** | CW Endpoint metrics (Invocations, ModelLatency, OverheadLatency) | CW GenAI Observability (InvocationLatency, TokenCount) |
| **Quality evaluation** | Custom metrics via inference pipeline, Model Monitor constraints | Bedrock Model Evaluation jobs |
| **Drift detection** | SageMaker Model Monitor (data quality, model quality, bias) | Prompt embedding distribution drift custom pipeline |
| **Traceability** | X-Ray with SageMaker SDK integration | Bedrock/AgentCore auto X-Ray spans |
| **Concept drift** | Model Monitor model quality (needs ground truth labels) | Not directly detectible—requires business metrics/user feedback |

> **Exam Gotcha:** SageMaker Model Monitor does **not** natively evaluate FM output quality. For Bedrock FMs, use Bedrock Model Evaluation for output quality, and CloudWatch GenAI observability for operations.

## Anti-Patterns & Common Distractor Traps

- **Using CloudWatch Logs alone** for FM quality evaluation—logs show raw prompt/response text but do not compute quality scores or judge-based evaluations.
- **Confusing Bedrock Model Evaluation** with SageMaker Model Monitor—Bedrock evaluation is batch-scored offline; Model Monitor is online drift/quality monitoring for SageMaker endpoints.
- **Expecting automatic evaluation to catch toxicity or refusal behavior**—use judge-based evaluation with explicit harmful-content criteria.
- **Setting both production variants at 100% weight** in A/B testing—traffic routing requires weight ratios summing to 100% across variants.
- **Missing X-Ray traces for agentic workflows**—CloudWatch GenAI observability depends on X-Ray for end-to-end span correlation.
- **Over-provisioning evaluation at runtime**—evaluation jobs are offline batch jobs, not real-time request-time monitors; do not invoke them per user request.

## Security & Compliance Notes

- **Data at rest:** Evaluation datasets and results are in S3—default to SSE-S3 or SSE-KMS (customer-managed).
- **Data in transit:** Bedrock service endpoints support TLS 1.2+; VPC endpoints for Bedrock and S3 avoid public internet.
- **IAM scoping:** Grant Bedrock evaluation role only `bedrock:InvokeModel` on the specific model ARN being evaluated; avoid wildcard model permissions.
- **PII in prompts:** If evaluation data contains PII, use KMS encryption and restrict result bucket permissions; consider Bedrock Guardrails redaction prior to storage.
- **Auditability:** CloudTrail logs `CreateEvaluationJob`, `GetEvaluationJob`, and `StopEvaluationJob` API calls—essential for compliance evidence.

## Cost & Operational Efficiency Signals

| Signal | What it indicates |
|--------|-------------------|
| **Token count spike** | Prompt length growth, template regression, or prompt injection attempts |
| **Throttle count increase** | Bedrock service quota breach or bursty agent tool-calling backoff |
| **Zero invocations at expected peak** | Upstream pipeline failure or agent coordination stall (no model calls being issued) |
| **Judge evaluation score decline** | FM version change, prompt template drift, or data drift affecting output quality |

---

## High-Yield Summary

1. **Bedrock Model Evaluation** = offline, batch-scored output quality (automatic / judge / human).
2. **CloudWatch GenAI Observability** = real-time operational metrics for FM invocations and agent workflows (tokens, latency, errors, X-Ray traces).
3. **AgentCore Observability** = built-in OTel spans for agent reasoning, tools, and memory—no manual instrumentation.
4. **Judge-based evaluation** is mandatory for subjective quality dimensions; automatic evaluation covers deterministic metrics only.
5. **Monitoring FM performance** combines operational telemetry (CloudWatch) + output quality scoring (Model Evaluation) + end-to-end tracing (X-Ray/AgentCore).
6. **A flat line on invocation count** is as important as a spike—zero invocations indicate a broken upstream pipeline or stalled agent loop.
