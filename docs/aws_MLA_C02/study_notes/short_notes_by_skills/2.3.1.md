## Experiment Tracking with SageMaker AI + MLflow

**Core Purpose:** Record every run's parameters, metrics, artifacts, and lineage so comparisons are auditable and reproducible—critical for ML governance, debugging variance, and regulatory compliance.

### Key Capabilities

- **Automatic tracking:** Parameters (hyperparameters, seeds, data versions), metrics (loss, accuracy, F1), artifacts (model files, confusion matrices, feature importance plots)
- **Generative AI tracing:** Captures inputs/outputs/metadata at each step of an LLM application (prompt → embedding → retrieval → generation) to debug unexpected outputs
- **Run comparison:** Diff two runs side-by-side to identify root causes of score divergence (unseeded initialization, package drift, data mutation)

### SageMaker AI MLflow Configuration

| Setting | Purpose | Exam Note |
|---------|---------|-----------|
| `MLFLOW_TRACKING_URI` | Points to tracking server ARN | Managed by SageMaker; no manual server setup |
| `mlflow.sagemaker` integration | Log SageMaker training jobs automatically | Use `mlflow.sagemaker.autolog()` in training scripts |
| Artifact storage | S3 bucket (implicit via SageMaker session) | Encrypts at rest with KMS |
| Run metadata | Parameters + metrics + tags | Tags enable filtering (e.g., `env:prod`, `version:v2`) |

> **Exam Gotcha:** MLflow tracks *training* metadata and traces—it does **not** deploy models, handle live traffic, or score endpoints. Do not confuse it with SageMaker Endpoints or Bedrock evaluations.

### Anti-Patterns
- Cherry-picking the best run and deleting others → destroys variance evidence
- Relying on a single accuracy figure without recording inputs and environment → cannot explain *why* scores changed
- Skipping `random_seed` logging → non-deterministic results become unexplainable

## Amazon Bedrock Evaluations

**Core Purpose:** Run structured evaluation jobs against FMs or RAG sources—either programmatically (automated metrics), via LLM-as-a-judge (model scores with explanation), or via human raters.

### Evaluation Modes

| Mode | Mechanism | When to Use | Key Metrics/Methods |
|------|-----------|-------------|---------------------|
| **Programmatic** | Computes deterministic scores over prompt datasets | Fast, reproducible, no judge model cost | ROUGE, BLEU, BERTScore, semantic similarity |
| **LLM-as-a-Judge** | Another FM scores response quality + explains score | Subjective quality, coherence, harmfulness | Custom rubric via judge prompt |
| **Human-based** | Ratings from S3 workers, employees, or SME task force | High-stakes outputs, bias auditing, nuanced preference | Quality criteria, instructions, rating scales |

### RAG Evaluation Split

| Component | Metrics | Isolation Purpose |
|-----------|---------|-------------------|
| **Retrieval accuracy** | Context Precision, Context Recall | Determines if correct chunks were returned |
| **Generation quality** | Faithfulness, Answer Relevance | Determines if generator used context properly |

> **Exam Gotcha:** A fluent answer that omits facts from source documents is **a retrieval failure wearing a generation costume**. Measure retrieval and generation separately or you cannot localize the fault.

### Configuration Nuances
- **Automated jobs:** No browser-facing display required
- **Human-based jobs (console):** *Require* browser-facing display setup so workers can view prompts/responses
- **Bedrock Knowledge Bases** serves as the retrieval source whose accuracy is measured independently from story generation

## Amazon Bedrock Prompt Management

**Core Purpose:** Store, version, and compare prompt templates with variables—turning wording changes into tracked, repeatable experiments rather than unexplained behavior shifts.

### Key Features

| Feature | Purpose |
|---------|---------|
| **Prompt versioning** | Retains full history of prompt changes; enables rollback |
| **Variable schemas** | Define placeholders (`{context}`, `{user_query}`) for dynamic injection |
| **Side-by-side comparison** | Compare prompt variants on the same evaluation dataset |
| **Integration with Bedrock Evaluations** | Run automated/judge/human jobs against prompt versions |

### When to Use vs. Alternatives

| Scenario | Best Tool |
|----------|-----------|
| Compare prompt wording impact | **Prompt Management** variants |
| Track training run lineage | **MLflow** on SageMaker AI |
| Compare live candidate vs. production on real traffic | **SageMaker shadow tests** |
| Evaluate retrieval quality from vector DB | **Bedrock Knowledge Bases** + Evaluations |

## Security & Compliance

- **IAM roles:** All evaluation jobs require `bedrock:EvaluateModel` on the target model + S3 read/write for input/output datasets
- **Encryption at rest:** KMS keys for prompt datasets, evaluation results, MLflow artifacts (S3)
- **Encryption in transit:** TLS by default across SageMaker, Bedrock, and MLflow services
- **VPC endpoints:** `bedrock-runtime`, `bedrock`, `sagemaker`, `s3` via Interface/Gateway VPC endpoints to avoid public internet
- **Human evaluation data governance:** Prompt/response pairs shared with workers must be redacted of PII; use AWS Private Workforce for sensitive data

> **Exam Gotcha:** Bedrock evaluation jobs do **not** use live production traffic—they evaluate against stored prompt datasets. Live traffic comparison requires SageMaker shadow variants.

## Reproducibility Decision Matrix

| Requirement | Service/Pattern |
|-------------|-----------------|
| Track training run params/metrics/artifacts | **MLflow** on SageMaker AI |
| Trace LLM app steps (inputs/outputs per step) | **MLflow tracing** for GenAI apps |
| Compare prompt template versions | **Bedrock Prompt Management** |
| Reproduce a GenAI eval with fixed dataset | **Bedrock Evaluations** (programmatic) |
| Mirror live traffic to candidate without user impact | **SageMaker shadow test** |
| Detect drift from known-good baseline | **CloudWatch** metrics + baseline thresholds |

## Common Distractor Traps

- **MLflow for live comparison** → Wrong; MLflow is offline tracking only
- **Bedrock Evaluations for live traffic** → Wrong; uses pre-compiled datasets
- **Prompt Management for endpoint deployment** → Wrong; it only versions template text
- **Shadow test returning candidate responses to callers** → Wrong; only production answers the caller
- **Single metric (ROUGE alone) settles quality** → Wrong; combine overlap + embedding similarity + judge/human judgment
- **Accuracy as metric for text generation** → Wrong; open-ended outputs require semantic + lexical measures
