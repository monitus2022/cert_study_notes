# Skill 4.1.5: Monitor and automate the management of agent performance and coordination
## Task 4.1: Operating, Monitoring, and Securing ML and AI Solutions – Monitor ML and AI model inference and performance

**Core objective:** Agentic workloads fail *between* components, not inside them. Single-model monitoring (latency, errors, tokens) is necessary but insufficient — you must observe **traces spanning orchestrator → sub-agents → tools → memory**, detect **non-termination**, and validate **handoffs** rather than trusting "success" status codes.

---

### Agent Failure Taxonomy → Signal → Where to Detect

| Failure class | Concrete symptom | Detection signal | Primary source |
|---|---|---|---|
| **Tool failure** | Tool call errors, empty/null output, schema mismatch, permission denied | Tool error rate, tool span status = ERROR, non-retryable exceptions | AgentCore Observability, X-Ray subsegments |
| **Silent tool corruption** | Tool returns 200 but unusable/duplicated data | Output contract validation, record-count / null-rate checks, duplicate-key detection | Pipeline validation + DLQ |
| **Coordination failure** | A→B→A ping-pong, no termination, orchestrator picks wrong agent | Steps/turns per session, agent-pair transition counts, identical tool-signature repeats | Trace span graph, loop-detection counter |
| **Deadlock / stall** | Sub-agent never returns; orchestrator waits | Span duration > threshold, missing child span, heartbeat timeout | Step Functions heartbeat, X-Ray |
| **Truncated streaming** | Response stops mid-sentence / mid-JSON | Finish reason ≠ normal stop; absent terminal event; inter-token gap | Invocation logs, GenAI observability |
| **Context/memory failure** | Context window overflow, stale or failed memory read/write | Context-overflow errors, memory-op span failures | AgentCore memory spans |
| **Guardrail intervention** | Response filtered or cut short | Guardrail intervention count / trace | Bedrock Guardrails + invocation logs |
| **Runaway cost** | Loop burns tokens; cost spike with no traffic spike | Tokens per session, cost anomaly detection | CloudWatch + Cost Anomaly Detection |

---

### Observability Stack — Match the Service to the Job

| Job | Service | Notes / Trap |
|---|---|---|
| **Agent-native telemetry** | **Amazon Bedrock AgentCore Observability** | Default, OpenTelemetry-compatible instrumentation for agents on AgentCore Runtime; captures model inference, tool invocations, memory ops with session/trace/span IDs — no custom spans needed |
| **GenAI dashboards** | **CloudWatch generative AI observability** | Pre-built views: token usage, latency, errors, throttling, end-to-end prompt tracing for Bedrock + AgentCore |
| **Cross-component tracing** | **AWS X-Ray** | Service map + subsegments per tool/agent call; attributes a slow/failing step to one component |
| **Aggregate measures + alerting** | **CloudWatch metrics, Logs Insights, Alarms, Composite Alarms, Anomaly Detection** | Alarms are the automation trigger; composite alarms reduce noise |
| **Automated remediation** | **EventBridge → Lambda / Step Functions** | Route alarm state changes and log patterns to automated response |
| **Deterministic orchestration guardrails** | **Step Functions** | Retry, Catch, Timeout, Heartbeat, task tokens, DLQ — enforces termination where the model would loop |
| **Quality scoring** | **Bedrock Model Evaluation** (automatic / LLM-as-judge / human) | **Offline/near-line**, not a live coordination detector |

> **Gotcha:** X-Ray applies **default sampling** (not 1:1). Never derive error *counts* from X-Ray alone — use CloudWatch metrics/logs for counts, X-Ray for attribution.

---

### Metrics That Actually Predict Agent Breakage

- **Non-termination:** steps/turns per session (p99), tool calls per session, **repeated identical tool-call signature**, agent-pair handoff counts, recursion/iteration limit hits.
- **Handoff integrity:** tool input/output schema validation failures, null/empty tool result rate, duplicate side-effect detection.
- **Streaming health:** time-to-first-token (TTFT), **inter-token latency**, streams ending without a terminal event, finish-reason distribution.
- **Reliability:** error rate by type (throttling 429 vs 5xx vs validation vs tool), retry counts, DLQ depth.
- **Cost-as-signal:** input/output tokens per session, tokens per resolved task — a loop shows as token spend without a traffic increase.
- **Drop-to-zero:** invocation/session counts falling flat is a **broken pipeline**, not "no demand."

> **Gotcha:** Threshold alarms written only for *high* values never fire on a flat line. Always pair spike alarms with **low/absent-data** alarms (treat missing data as breaching).

---

### Truncated Streaming — Causes vs. Mitigations

| Cause | Distinguishing signal | Mitigation |
|---|---|---|
| Output token limit reached | Finish reason = length / max-token cutoff | Raise output token limit; chunk or paginate long generations |
| Overly generic stop sequence | Early, clean termination at odd point | Tighten/remove stop sequences |
| **Proxy/ALB/API Gateway idle timeout** | Stream dies at a consistent wall-clock duration | Raise idle timeout; use WebSocket/HTTP2 with keepalive chunks |
| Client disconnect / user navigates away | Session ends without terminal event | Track abandonment rate; checkpoint partial output |
| Context window overflow | Error/refusal before completion | Summarize/trim context; memory compaction |
| Guardrail block mid-stream | Intervention trace, buffered-then-cut response | Tune guardrails; surface a graceful message |
| Partial tool-call arguments | Truncated JSON in tool-use block | Validate full argument payload **before** invoking the tool |

> **Gotcha:** A "successful" HTTP 200 stream can still be truncated. Detect on **presence of the terminal completion event and finish reason**, not on connection status.

### Tool Failure Handling — Retryable vs. Not

| Class | Examples | Action |
|---|---|---|
| **Retryable** | Throttling (429), 5xx, timeouts, transient network | Exponential backoff **with jitter**, bounded attempts, circuit breaker |
| **Non-retryable** | Validation/schema errors, access denied, resource not found | Fail fast, alert, route to DLQ — retrying wastes tokens and hides the defect |
| **Unknown / repeated failure** | Same tool fails N times | Trip circuit breaker, fall back to alternate tool or degrade gracefully |
| **Side-effecting tools** | Writes, payments, ticket creation | **Idempotency keys** — retry must not duplicate the side effect |

- **Contract enforcement at every hop:** validate tool input and output schemas; a job exiting with success while writing an empty partition is the classic handoff failure.
- **Escalation:** human-in-the-loop for high-risk or irreversible tool actions.
- **DLQ + alarm** for tool invocations that exhaust retries.

---

### Automating Management & Response

- **EventBridge rules** on CloudWatch alarm state changes or log patterns → Lambda/Step Functions remediation (disable tool, shift traffic, restart agent session).
- **Automated rollback:** shift endpoint/variant weight off a degraded agent version rather than redeploying.
- **Triggered evaluation:** quality/drift alarm fires a Bedrock Model Evaluation job for re-scoring.
- **Termination enforcement:** orchestrator-level deadline/timeout propagation and max-iteration limits; Step Functions heartbeat for long-running sub-agents.
- **Auto scaling** on latency, queue depth, or throttle rate.

---

### Security, Compliance & Governance

- **IAM:** distinct execution role per agent; **least privilege per tool**; avoid one broad role shared across all tools (confused-deputy risk).
- **Agent identity:** use managed agent identity/token vaulting rather than embedding long-lived credentials in tool code.
- **Encryption:** KMS CMKs for invocation logs, trace data, and the S3 buckets storing traces/evaluations — at rest; TLS in transit.
- **Network isolation:** VPC endpoints (PrivateLink) for Bedrock, CloudWatch Logs, X-Ray, and S3 so agent traffic never traverses the public internet.
- **Audit:** CloudTrail data events for agent/tool API activity.
- **Prompt/trace data is sensitive:** full request-response logging captures PII. Apply **CloudWatch Logs data protection** masking, guardrail sensitive-information filters, and explicit log retention limits.
- **Governance decision:** tracing granularity vs. data exposure — trace metadata and span timing liberally; redact prompt/response payloads where regulated.

### Trade-offs & Distractor Traps

| Decision | Choose A when | Choose B when |
|---|---|---|
| **A: CloudWatch GenAI observability** vs **B: X-Ray** | You need GenAI-specific token/latency/throttle dashboards and prompt traces | You need generic distributed tracing and a service map across non-GenAI components |
| **A: AgentCore Observability (built-in OTel)** vs **B: custom instrumentation** | Agent runs on AgentCore Runtime — telemetry is on by default | Self-hosted agent outside AgentCore |
| **A: Deterministic workflow orchestration** vs **B: Model-driven orchestration** | Coordination must be auditable and terminating | Open-ended reasoning path needed |
| **A: Programmatic/rule-based runtime checks** vs **B: LLM-as-judge** | Deterministic contract validation, cheap, real-time | Open-ended response quality scoring (offline/near-line) |
| **A: Offline evaluation** vs **B: Online monitoring** | Pre-deployment regression gate | Production drift, tool failures, coordination degradation |

> **Hard rules to memorize:** AgentCore Observability is **default-on** for AgentCore Runtime agents. Bedrock Model Evaluation **scores quality — it does not detect coordination failures or tool errors at runtime.** CloudWatch GenAI observability is the single-pane answer for token usage + latency + errors + prompt traces.

> **Anti-patterns:** alarming only on job *completion* status; treating X-Ray as a complete error count; retrying non-idempotent tools; no max-iteration limit on agent loops; monitoring inference but not the upstream data step whose silent failure caused it; assuming HTTP 200 means the stream completed.
