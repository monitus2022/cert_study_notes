# Skill 4.1.5: Monitor and Automate the Management of Agent Performance and Coordination

## Task 4.1: Operating, Monitoring, and Securing ML and AI Solutions - Monitor ML and AI model inference and performance

---

## Core Concept & Business Objective
**Primary goal:** Detect, diagnose, and automate recovery from agentic system failures *before* end-users experience degraded or incorrect outputs. Agent workloads introduce unique failure modes beyond single-model inference: broken tool chains, unterminated streams, and failed coordination between sub-agents.

### Agent Failure Taxonomy (Know These Cold)

| Failure Mode | Signal | Primary Detection Tool | Automated Remediation |
|---|---|---|---|
| **Coordination failure** | Multiple agents stuck in loop, no final answer, excessive turns | X-Ray trace analysis, AgentCore spans, step count alarms | Max-iteration guards, circuit breaker, supervisor timeout |
| **Truncated streaming** | Response ends mid-token, incomplete JSON, missing `finish_reason` | CloudWatch `CompletionTokens` vs expected, stream-end checks | Retry with backoff, reduce `max_tokens`, split requests |
| **Tool failure** | Non-200 tool response, malformed tool output, unsupported action | AgentCore tool invocation spans, error metrics per tool | Fallback tool, retry, degrade gracefully, human escalation |
| **Model invocation failure** | 4xx/5xx from FM, throttling (429), timeouts | CloudWatch generative AI observability, Bedrock metrics | Exponential backoff, cross-region failover, quota increase |

## Key AWS Services & Configurations

### Amazon Bedrock AgentCore Observability
- **Default instrumentation** for AgentCore Runtime agents; emits OpenTelemetry-compatible spans and metrics without manual agent code changes.
- **Captures:** Model inference calls, tool invocations, memory operations, coordinator handoffs.
- **Boto3 / API interaction:**
  - Enable via agent config: `orchestrationConfiguration` → `observabilityConfiguration`
  - Query traces: `bedrock-agent-runtime` → `GetAgentMemory`, `GetAgentResponse` for post-hoc analysis.

### Amazon CloudWatch Generative AI Observability
- **Pre-built dashboards** over Bedrock invocations and AgentCore agents.
- **Key metrics to alarm on:**
  - `InvocationClientErrors` / `InvocationServerErrors`
  - `InvocationThrottles` — near-quota signals
  - `InputTokenCount` / `OutputTokenCount`
  - `InvocationLatency` (p50/p99)
  - **Per-tool error rate** (custom metric from AgentCore spans)

### AWS X-Ray for Agent Tracing
- **End-to-end prompt tracing** across orchestrator → LLM → tool → memory.
- **Annotations to add:** `agent_id`, `turn_number`, `tool_name`, `finish_reason`.
- **Critical check:** Candidate agent completes *all* spans; missing spans = silent tool failure or early termination.

> **Exam Gotcha:** CloudTrail logs *management* API calls (who created what). It does **not** show agent runtime coordination failures, tool call traces, or stream truncation. Do not select CloudTrail for agent performance monitoring.

## Automation & Guardrail Patterns

### Coordination Failure Detection
- **Set maximum turn/iteration guards** in agent orchestration. Alert when `step_count` approaches limit repeatedly.
- **Circuit breaker pattern:** If tool failure rate > threshold (e.g., 20% over 5 min), route to fallback or stop agent, notify human.
- **Dead-letter detection:** Monitor for agents that emit tool calls but never a final response within SLA window.

### Truncated Streaming Detection
- **Check `finish_reason`**: `length` (truncated) vs `stop` (normal) vs `tool_use` (expected continuation).
- **Validate output structure:** JSON schema check, required field presence, completeness markers.
- **Alert on:** `OutputTokenCount == max_tokens` while `finish_reason = length` — patterns of consistent truncation warrant config changes.

### Tool Failure Automation
- **Retry policies:** 2–3 retries with exponential backoff for transient errors; no retry for validation errors.
- **Fallback tool mapping:** Define per-tool fallback (e.g., search tool → cached results; DB tool → read replica).
- **Graceful degradation:** Agent returns partial answer with `is_complete: false` and escalation path when critical tool unavailable.

## Key Metrics & Alarm Thresholds

| Metric | Healthy Signal | Alarm Condition |
|---|---|---|
| Agent end-to-end latency | Stable p95, below SLA | Sustained p95 increase > 2× baseline |
| Steps per conversation | Stable median | Median exceed max-guard × 0.7 (near-loop) |
| Tool success rate | > 95% per tool | < 85% for 5 min |
| Truncation rate | < 1% of streams | > 5% of streams |
| Zero-invocation | N/A | Any drop to 0 for 10 min |
| Coordination time (orchestrator idle) | < 20% of total latency | > 50% (agents stalling) |

> **Exam Gotcha:** Alarms on **absence** of traffic are as critical as spikes. A flat-zero invocation count indicates a broken agent, dead consumer, or misconfigured routing — a high-threshold-only alarm will never fire.

## Decision Matrix: Which Monitoring Approach?

| Scenario | Recommended Service | Why |
|---|---|---|
| Agent uses Bedrock AgentCore Runtime | **AgentCore Observability** (default) | Zero-config OTel spans for model, tool, memory steps |
| Multi-service agent (Lambda + Step Functions + Bedrock) | **X-Ray** with manual annotations | Cross-service trace correlation, span-level attribution |
| Need LLM-specific dashboards (tokens, latency, errors) | **CloudWatch generative AI observability** | Pre-built aggregation over Bedrock APIs |
| Need to judge agent output quality | **Bedrock Model Evaluation** (automatic or judge) | Scores response correctness, helpfulness; not runtime coordination |
| Detect drift in user prompts to agent | **Embedding-based drift pipeline** | Compare prompt embeddings against baseline distribution |

## Anti-Patterns & Distractor Traps

- **Anti-pattern:** Monitoring only the final model invocation; agent failures occur in orchestration and tool layers *before* the model sees input.
- **Anti-pattern:** Relying on exit codes from tools. A tool can return `200` with `{"error": "permission denied"}`; validate tool response payloads, not just HTTP status.
- **Anti-pattern:** Single-alarm-only monitoring. Agents need layered alarms: invocation, coordination, tool, truncation, and drift.
- **Distractor trap:** "CloudWatch Logs alone is sufficient" — logs need parsing, metric generation, and alarms to be actionable; logs without alarms are archives.
- **Distractor trap:** "Increase `max_tokens` to fix truncation" — this treats symptom, not cause. Investigate `finish_reason` patterns first; may indicate prompt complexity or model limitation.
- **Distractor trap:** "SageMaker Model Monitor detects agent coordination issues" — Model Monitor handles data drift and model quality for hosted models, not agent orchestration or tool chains.

## Security & Compliance Notes

- **IAM for AgentCore telemetry:** Agents write spans to CloudWatch Logs/X-Ray; ensure execution role has `logs:PutLogEvents`, `xray:PutTraceSegments`.
- **KMS encryption:** Agent memory and conversation history at rest in DynamoDB/S3 should use KMS CMK; spans may contain sensitive prompt text — enable X-Ray encryption.
- **VPC endpoints:** For private agents, use VPC endpoints for CloudWatch Logs, X-Ray, and Bedrock to keep telemetry traffic off public internet.
