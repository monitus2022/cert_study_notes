# Skill 4.2.3: Set Up Dashboards to Monitor Performance Metrics

## Task 4.2: Optimize and manage ML and AI infrastructure costs and performance

### Core Objective & Dashboard Rationale
**Dashboards shorten decisions by co-locating correlated metrics.** A dashboard earns its place when it surfaces the measures that move together, eliminating the need to navigate multiple consoles to answer a single operational question.

| Dashboard Focus | Metrics to Co-Locate | Decision It Enables |
|---|---|---|
| **Endpoint Health** | Invocations, InvocationErrors, ModelLatency, OverheadLatency, CPU/GPU Utilization, Memory Utilization | Scale vs. rightsize vs. debug |
| **Token Usage** | InputTokens, OutputTokens, InvocationCount, CacheHitRate | Traffic growth vs. prompt bloat vs. caching effectiveness |
| **Agent Consumption** | TraceCount, ToolCallCount, RetrievalCallCount, ModelCallCount, Duration per component | Isolate agent-specific overhead |
| **Cost → Performance** | Spend-by-tag overlay on latency/throughput | Attribution of cost drivers per team/model |

### Key CloudWatch Metrics by Service

**Amazon SageMaker AI (Real-Time Endpoints)**
| Metric Name | Use Case | Key Nuance |
|---|---|---|
| `Invocations` | Request throughput baseline | Namespace: `AWS/SageMaker` |
| `Invocation4XXErrors` / `Invocation5XXErrors` | Error rate differentiation | 4XX = client, 5XX = server-side |
| `ModelLatency` | Time inside model execution | Excludes payload serialization/network |
| `OverheadLatency` | Time outside model (payload processing) | Isolate framework vs. model issues |
| `CPUUtilization` / `GPUUtilization` / `GPUMemoryUtilization` | Capacity headroom | Target scaling policies use these |
| `MemoryUtilization` | OOM risk detection | Not a default target for autoscaling |
| `DiskUtilization` | Instance storage pressure | Common anti-pattern to ignore |

**Amazon Bedrock (Foundation Models)**
| Metric Name | Use Case | Key Nuance |
|---|---|---|
| `Invocations` | Request count per model | Namespace: `AWS/Bedrock` |
| `InputTokenCount` | Input side of bill | Sum or `Sum` statistic only |
| `OutputTokenCount` | Output side of bill | Sum or `Sum` statistic only |
| `InvocationLatency` | End-to-end model latency | Do not gate autoscaling on this alone |
| `InvocationClientErrors` | Throttling, validation, guardrails | Distinguish from server errors |

**Amazon Bedrock AgentCore Observability**
| Metric/Field | Use Case | Key Nuance |
|---|---|---|
| `TraceCount` | Agent invocation volume | Namespace: `AWS/BedrockAgentCore` |
| `TraceLatency` | Total invocation duration | Includes all tool/retrieval calls |
| Span-level `ModelCallCount`, `ToolCallCount`, `RetrievalCallCount` | Cost and latency attribution within a single agent request | One user request = multiple model/tool calls |
| `TraceErrors` / `TraceSpanErrors` | Failure localization inside agent workflow | Distinguish model vs. tool vs. memory failures |

### Dashboard Construction Patterns

- **Capacity Decision Dashboard:** Co-display `CPUUtilization`, `GPUUtilization`, `ModelLatency`, `InvocationsPerInstance`. High latency with low utilization → not a scaling problem; high latency with high utilization → capacity problem.

- **Token Cost Dashboard:** Co-display `Invocations`, `InputTokenCount`, `OutputTokenCount`, and Cost Explorer tag-filtered spend as a CloudWatch custom metric. Rising token count with flat invocations → prompts are getting longer → prompt optimization, not capacity.

- **Agent Trace Dashboard:** Use AgentCore Observability spans to build per-invocation breakouts of model vs. tool vs. retrieval time. Aggregates hide where agent time actually goes.

- **Dashboard Use of Logs:** Use CloudWatch Logs Insights queries backed by metric filters to surface structured application logs (e.g., inference-specific latencies, payload sizes) as dashboard time series.

### CloudWatch Dashboard Features for Exam Recall

| Feature | Use Case | Exam Gotcha |
|---|---|---|
| **Cross-account / cross-region dashboards** | Aggregate fleet views in one pane | Must use `CloudWatch-CrossAccountSharingRole` |
| **Metric math expressions** | Derived metrics (e.g., tokens per invocation) | `AVG(METRICS('InputTokenCount')) / AVG(METRICS('Invocations'))` |
| **Alarms with anomaly detection** | Threshold-free anomaly alerting | Available on CloudWatch metrics with sufficient history |
| **Contributor insights** | Identify top talkers (IPv4, user, model) | Works on structured logs; not raw metrics |
| **S3-backed dashboard sharing** | Template for multi-account deployments | Exports via CloudFormation after dashboard save |

### Exam Gotchas

> **CloudWatch metrics for Bedrock token counts are pushed by Bedrock, not by the model invocation code.** Do not use custom metric emission as a substitute for the native namespace.

> **`ModelLatency` on SageMaker measures only the model execution time inside the container; `OverheadLatency` covers payload processing and serialization.** Isolate framework latency to attribute slowness correctly.

> **SageMaker autoscaling target tracking supports `InvocationsPerInstance`, `CPUUtilization`, `GPUUtilization`, and `GPUMemoryUtilization`.** Use target tracking (not step scaling) for typical diurnal patterns.

> **Throttling with `Invocation4XXErrors` rising while `CPUUtilization` is low → not a capacity issue.** Could be invocation rate limits, payload size limits, or Bedrock regional quota exhaustion.

> **Dashboards do not replace alarms.** A dashboard provides visibility; an alarm provides action. Always pair master dashboards with alarm overlays.

---

### Anti-Patterns & Common Distractors

- **Anti-pattern:** Scaling endpoint based on `ModelLatency` alone. → High latency may stem from oversized payloads, framework overhead, or upstream dependencies, not instance saturation.

- **Anti-pattern:** Building a dashboard from default metrics only. → Always add custom metrics for business-level KPIs (e.g., recommendation accuracy, personalization coverage) alongside infrastructure telemetry.

- **Anti-pattern:** Monitoring `Invocation5XXErrors` without segmenting by `Invocation4XXErrors`. → 4XX (client-side) and 5XX (server-side) demand completely different remediation.

- **Distractor:** "Use CloudWatch dashboards to set budgets." → AWS Budgets handles spend thresholds; CloudWatch dashboards visualize operational metrics, not fiscal enforcement.

- **Distractor:** "Use CloudWatch to trace requests across components." → That is AWS X-Ray's domain; CloudWatch aggregates per-resource metrics but does not show cross-component request paths.
