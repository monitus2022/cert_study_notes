# Skill 2.1.7: Assess Tradeoffs Between AI Model Performance, Latency, and Cost

## Task 2.1: ML Model and Foundation Model (FM) Development - Choose Appropriate Modeling Approaches

---

## Core Decision Framework: The Triple Constraint

```
                    PERFORMANCE
                        ▲
                       / \
                      /   \
                     /     \
                    /  SWEET \
                   /   SPOT   \
                  /             \
    LATENCY ◄────┴───────────────┴────► COST
```

> **Exam Gotcha:** You can optimize **two** of the three constraints. The exam asks which constraint the requirement is forcing you to sacrifice—never that all three can be maximized simultaneously.

|---|---|---|---|---|
| **Claude 3 Opus** | Highest reasoning/quality | Highest latency | Highest per-token cost | Complex reasoning, multi-step tasks |

### Selection Criteria: Read the Requirement First

| Requirement Says | Optimize | Sacrifice | Model Choice |
|---|---|---|---|
| "Must respond under 200ms" | Latency | Performance/Cost | Claude Haiku or smaller model |
| "Answers must be authoritative/accurate" | Performance | Latency/Cost | Claude Opus or domain fine-tuned model |
| "Will serve millions of daily requests" | Cost | Latency/Performance | Smaller model + aggressive batching |

## Traditional ML Model Tradeoffs

| Algorithm | Performance | Training Time | Inference Latency | Interpretability | Cost Profile |
|---|---|---|---|---|---|
| **Linear Regression** | Low on complex data | Very fast | Very low | **Highest** | Very low |
| **XGBoost** | High on tabular data | Moderate | Low | **High** (feature importance/SHAP) | Low |
| **Random Forest** | High | Moderate | Moderate | **High** | Low |
| **Deep Neural Network** | Highest on unstructured | **Very long** | Moderate | **Lowest** | **Very high** (GPU) |
| **SVM** | Moderate | Slow on large data | Low | Low | Moderate |

> **Exam Gotcha:** Interpretability is a **selection criterion, not an afterthought**. Finance/healthcare/regulated contexts require explainable models even if a deep model is marginally more accurate. The exam will present a DNN with 1% higher accuracy and expect you to reject it in favor of interpretable options.

## Latency vs. Cost Optimization Strategies

### Foundation Models (Bedrock)

| Strategy | Reduces | Tradeoff | When to Use |
|---|---|---|---|
| **Smaller model (Haiku vs Opus)** | Latency + Cost | Performance | Simple tasks, high volume |
| **Prompt compression** | Latency + Cost | Context quality | Long documents, retrieval output |
| **Response streaming** | Perceived latency | Complexity (event tracking) | Chat interfaces |
| **Cross-Region inference routing** | Latency spikes | None (slight cost variance) | Global deployments |
| **Provisioned throughput** | Cold-start latency | **Fixed cost regardless of usage** | Predictable traffic |

### Trained Models (SageMaker)

| Strategy | Reduces | Tradeoff | When to Use |
|---|---|---|---|
| **Multi-model endpoints** | Cost | Cold-start latency per model | Many infrequently-called models |
| **Inference optimization (Neo/compilation)** | Latency | Engineering effort | Edge/lambda deployments |
| **Spot instances for training** | Cost | Training reliability | Non-urgent experiments |
| **Distributed training (data parallelism)** | Training time | Cost + complexity | Large datasets |
| **Model distillation (teacher→student)** | Inference latency + cost | Performance (student is smaller) | Production deployment of large models |

## Architectural Selection Decision Tree

```
Is the task a solved pattern?
├── YES → Managed AWS AI Service (Textract, Rekognition, Transcribe, Comprehend)
│         → Lowest engineering + infrastructure cost, pre-optimized latency
│
├── NO → Is the capability general (language, summarization, generation)?
│       ├── YES → Amazon Bedrock Foundation Model
│       │         → Prompt first, evaluate, fine-tune only if gap persists
│       │
│       └── NO → Are patterns in proprietary data?
│               ├── YES → Train with SageMaker AI
│               │         → Consider interpretability, training time, inference cost
│               │
│               └── NO → Fixed business logic → Write rules/code
└── Hybrid RAG case: Add Bedrock Knowledge Bases for external knowledge
                      → Updates without retraining, citations available
```

## RAG vs. Fine-tuning Tradeoffs

| Dimension | RAG (Knowledge Bases) | Fine-tuning |
|---|---|---|
| **Knowledge freshness** | Minutes (re-sync vector index) | Hours-days (retrain required) |
| **Source citation** | **Native** (chunk metadata) | None |
| **Response latency** | Higher (retrieval step added) | Lower (no retrieval) |
| **Inference cost** | Higher (tokens for retrieved context) | Lower (smaller prompt) |
| **Domain behavior/style** | Weak (model behavior unchanged) | **Strong** (weights updated) |
| **Catastrophic forgetting risk** | None | **Present** (mitigate with broader training mix) |
| **Use case fit** | Document Q&A, cited answers | Terminology, formatting, specialized output |

> **Exam Gotcha:** Retrieval and customization answer **different questions**. Retrieval keeps content outside the model (fresh, citable). Fine-tuning writes behavior into the weights (style, domain terminology). Requirements that demand citations + rapid updates **pick RAG**. Requirements that demand consistent specific output patterns **pick fine-tuning**—but only after prompting has failed evaluation.

---

## Prompt Engineering vs. Fine-tuning Decision

```
1. Task-specific prompting (instructions + few-shot examples)
   → Zero training cost, immediate deployment
   → Evaluation shows acceptable performance?
        ├── YES → Deploy (do not fine-tune)
        └── NO  → Proceed to step 2

2. Fine-tuning (SFT on labeled pairs or Reinforcement Fine-tuning)
   → Data prep + GPU training + version management
   → Accept overhead only when evaluations consistently show gaps
```

> **Hard Rule:** The exam will present scenarios where teams skip prompting and jump straight to fine-tuning. That is a **distractor answer**. The correct architectural path is always: **Prompt Engineering → Evaluate → Fine-tune only if necessary**.

| Business Requirement | Primary Optimization | Acceptable Sacrifice |
|---|---|---|
| **Real-time chat assistant** | Latency | Performance (use Haiku), Cost (pay for throughput) |
| **Document summarization batch job** | Cost | Latency (use batch, spot instances) |

## Key Boto3/SDK Parameters

| Parameter | Service | Effect on Tradeoff |
|---|---|---|
| `max_tokens` / `max_gen_len` | Bedrock | Higher = better completions, higher latency/cost |
| `temperature` | Bedrock | Higher = creative (less predictable), lower = deterministic |
| `InstanceType` | SageMaker | GPU = faster training/inference, higher cost |
| `InstanceCount` | SageMaker training | Distributed = faster, linear cost increase |
| `EndpointType` | SageMaker | Multi-model = cost savings, higher per-call latency |
| `VolumeKmsKeyId` | SageMaker/Bedrock | Encryption at rest, no performance impact |

## Anti-Patterns to Recognize

| Anti-Pattern | Why It Fails | Correct Approach |
|---|---|---|
| **Building custom model for solved task** | Wastes engineering time, creates maintenance burden | Use Amazon Transcribe/Rekognition/Textract/Comprehend |
| **Fine-tuning before prompt evaluation** | Incurring training cost/overhead unnecessarily | Prompt with few-shot examples first |
| **Selecting Opus for simple classification** | Paying 5-10x cost for marginal quality gain | Use Haiku or Sonnet |
| **RAG for whole-document synthesis** | Retrieval returns passages, not full context | Use long-context models or chunk strategically |
| **Training ML model when fixed rules suffice** | Overengineering, auditability suffers | Write deterministic business rules |
| **Choosing DNN when stakeholders need explanations** | Performance gain useless if model rejected | XGBoost/Forest + SHAP explanations |
