# Skill 4.3.4: Comprehensive Monitoring, Auditing, Compliance & Logging for ML/AI Systems

## Task 4.3: Secure ML and AI workloads and model endpoints

---

## Three-Pillar Recording Model

| Record Type | Service | Question Answered | Configuration Notes |
|---|---|---|---|
| **API Activity** | AWS CloudTrail | Who did what, when, from where? | **Management events**: default. **Data events**: manual enable |
| **Configuration State** | AWS Config | What did the resource look like? Was it compliant? | Requires rules defined; records timeline & drift |
| **Model Invocation** | CloudTrail **Data Events** OR Bedrock/SageMaker logging | What prompt went in? What response came back? | Often high-volume; may require separate enablement |

> **CRITICAL EXAM GOTCHA:** Default CloudTrail trails capture **only management events** (e.g., `CreateEndpoint`, `CreateModel`). Model invocation calls (e.g., SageMaker `InvokeEndpoint`, Bedrock `InvokeModel`/`Converse`) are **data events** — if a trail wasn't explicitly configured for data events, an auditor will find **nothing** even though models were invoked.

## Service-by-Service Configuration Matrix

| Service | Primary Purpose | Key Config Parameters | Common Distractor Trap |
|---|---|---|---|
| **AWS CloudTrail** | API activity audit trail | `EnableDataEvents`, `EventSelectors`, `TrailARN`, multi-Region toggle, S3/KMS destination | Assume trail = all events (data events excluded by default) |
| **AWS Config** | Resource configuration compliance & drift detection | `ConfigRule` (managed/custom), `ConfigurationRecorder`, `DeliveryChannel`, `RemediationAction` | Confuse with CloudTrail (Config is state, not activity) |
| **Amazon Inspector** | Vulnerability scanning (EC2, ECR images, Lambda) | `AssessmentTemplate`, `ScanConfiguration`, enabled per resource type | Think it logs API calls or checks IAM |
| **Amazon CodeGuru Security** | Static code analysis (code vulnerabilities, hardcoded secrets) | `AssociatedRepositories`, `Findings` output, built into CI/CD | Expect it to scan container images (that's Inspector) |
| **SageMaker Model Monitor** / **Bedrock Logging** | Model invocation input/output capture, data quality, drift | SageMaker: `DataCaptureConfig`, `MonitoringSchedule`; Bedrock: `ModelInvocationLoggingConfiguration`, S3/CloudWatch Logs destination, KMS key | Disable capture for cost but still expect audit trail |

## CloudTrail Deep Dive (High-Yield)

**Event Types**
- **Management Events** (default): Create, Update, Delete operations — e.g., `CreateModel`, `DeleteEndpoint`, `PutBucketPolicy`
- **Data Events** (explicit): Resource-level read/write — e.g., `InvokeEndpoint`, `InvokeModel`, S3 `GetObject`
- **Insights Events** (opt-in): Anomalous API call patterns detection

**Key CLI/Boto3 Parameters**
| Parameter | Purpose |
|---|---|
| `--enable-data-events` / `DataResources[]` | Specify which S3 buckets, Lambda functions, DynamoDB tables, or SageMaker endpoints to log at data-plane level |
| `--is-multi-region-trail` | Capture events from all Regions in a single trail |
| `--kms-key-id` | Encrypt log files at rest with customer-managed KMS key |
| `--cloud-watch-logs-log-group-arn` | Send logs to CloudWatch Logs for alerting/metrics |

> **HARD RULE:** Data events for model invocation must be enabled **explicitly on the trail's event selectors with the specific resource** (e.g., SageMaker endpoint ARN or Bedrock model invocation). Enabling data events on S3 does **not** capture model invocations.

## AWS Config Deep Dive

**Core Concepts**
- **Configuration Recorder**: Captures resource configuration changes continuously
- **Config Rules**: Evaluate resource state against desired policy
  - **Managed Rules**: AWS-provided (e.g., `sagemaker-endpoint-encryption-enabled`)
  - **Custom Rules**: AWS Lambda-based evaluation
- **Remediation Actions**: SSM Automation Documents auto-fix non-compliance

**ML-Specific Managed Rules**
| Rule | Enforces |
|---|---|
| `sagemaker-endpoint-encryption-enabled` | KMS encryption on endpoint storage |
| `sagemaker-notebook-instance-encryption-enabled` | KMS on notebook storage |
| `sagemaker-endpoint-vpc-protected` | Endpoint attached to VPC |
| `guardduty-enabled` | Threat detection active in account |

**Key Boto3 Methods**
| Method | Action |
|---|---|
| `put_config_rule()` | Create/update a rule |
| `start_config_rules_evaluation()` | Trigger on-demand evaluation |
| `get_compliance_details_by_config_rule()` | Retrieve non-compliant resources |

## Bedrock-Specific Logging & Auditing

**Model Invocation Logging**
```json
{
  "loggingConfig": {
    "cloudWatchConfig": {
      "enabled": true,
      "logGroupName": "/aws/bedrock/model-invocations",
      "largeDataDeliveryS3Config": { "bucketName": "invocation-logs" }
    },
    "s3Config": { "enabled": true, "bucketName": "model-logs" },
    "textDataDeliveryEnabled": true,
    "imageDataDeliveryEnabled": true,
    "embeddingDataDeliveryEnabled": true
  }
}
```

**Key Points**
- **CloudWatch Logs**: Retain prompt/response text for real-time analysis
- **S3**: Durable storage for large payloads, images, embeddings
- **KMS**: Encryption key for both destinations recommended
- **PII Concern**: If logging prompts/responses containing sensitive data, pair with **Bedrock Guardrails sensitive information filters** to mask/redact before logging, or disable text data delivery

> **EXAM GOTCHA:** Bedrock model invocation logging is **opt-in** and must be explicitly configured per model or account. CloudTrail data events for Bedrock are separate and must also be explicitly enabled.

## Decision Matrix: Audit / Compliance Question → Service

| Scenario | Correct Service | Why |
|---|---|---|
| "Who invoked this endpoint at 3 AM?" | **CloudTrail** (data events) | API-level activity attribution |
| "Was the endpoint encrypted at rest last month?" | **AWS Config** | Historical resource configuration state |
| "What prompt did a user send that caused a toxic output?" | **Bedrock Model Invocation Logging** or **SageMaker Data Capture** | Content-level capture |
| "Is this container image vulnerable to CVE-2024-12345?" | **Amazon Inspector** | Image vulnerability database |
| "Does this Python code contain hardcoded AWS credentials?" | **Amazon CodeGuru Security** | Static analysis of source code |
| "Has any security group changed in the last 7 days?" | **AWS Config** + **CloudTrail** | Config shows state change; CloudTrail shows who made `AuthorizeSecurityGroupIngress` call |
| "Are all SageMaker endpoints in VPCs?" | **AWS Config** (managed rule) | Continuous compliance evaluation |

## Common Anti-Patterns & Exam Traps

> **Trap 1 — "Trail exists, so invocation is logged"**
> Management event trail ≠ data event coverage. Always verify `EventSelectors` include model invocation resources.

> **Trap 2 — "Config = Activity"**
> Config tracks **configuration state**, not API activity. Config answers "was it encrypted?" CloudTrail answers "who called `InvokeEndpoint`?"

> **Trap 3 — "Inspector = CodeGuru"**
> Inspector scans **assembled artifacts** (EC2, ECR images, Lambda packages). CodeGuru Security scans **source code** for insecure patterns. Both are needed in a pipeline.

> **Trap 4 — "Bedrock logging = CloudTrail"**
> Bedrock's `ModelInvocationLoggingConfiguration` captures prompt/response **content** to CloudWatch Logs/S3. CloudTrail data events capture API call metadata (principal, time, IP) but **not** the payload content.

> **Trap 5 — "Multi-Region trail covers everything"**
> Multi-Region affects **geographic** coverage, not **event type** coverage. A multi-Region trail still logs only management events unless data events are configured.

## Pipeline Integration Pattern (Compliance-Centric)

```text
[Source Code] 
    │
    ▼
[CodeGuru Security scan] ──► Block if findings (hardcoded secrets, insecure patterns)
    │
    ▼
[Build Container Image]
    │
    ▼
[Amazon Inspector scan] ──► Block if CVEs above threshold
    │
    ▼
[Deploy to SageMaker/Bedrock]
    │
    ├── [CloudTrail data events] ──► S3 (audit trail)
    ├── [AWS Config rules] ──► Compliance dashboard + SSM remediation
    └── [Model Invocation Logging] ──► CloudWatch Logs / S3 (content capture)
```

## S3 Log Storage Security Posture

| Requirement | Configuration |
|---|---|
| **Encryption at rest** | KMS customer-managed key (`s3:BucketKeyEnabled` for cost optimization) |
| **Encryption in transit** | TLS enforced via bucket policy `aws:SecureTransport: false → Deny` |
| **Access control** | Bucket policy restricted to CloudTrail service principal; lifecycle rules for archival to S3 Glacier |
| **Integrity** | CloudTrail log file validation (`sha256` digest) — use `ValidateLogs` |
| **Object lock** | Optional: WORM for compliance retention |

> **CRITICAL:** When logging prompts/responses that contain PII to S3 or CloudWatch Logs, apply **Bedrock Guardrails sensitive information filters** with masking action so redacted values appear in logs rather than raw PII.

## Integration with Security Monitoring (Bonus)

| Control | Purpose |
|---|---|
| **CloudWatch Logs Metric Filters** | Alert on specific events (e.g., `AccessDenied` count > threshold, `InvokeEndpoint` rate anomaly) |
| **Amazon GuardDuty** | Threat detection at account level; feeds from VPC Flow Logs, DNS logs, CloudTrail |
| **AWS Security Hub** | Aggregated findings from Config, Inspector, GuardDuty, IAM Access Analyzer |
| **Amazon EventBridge Rules** | Trigger Lambda on Config non-compliance or CloudTrail security events for auto-remediation |
