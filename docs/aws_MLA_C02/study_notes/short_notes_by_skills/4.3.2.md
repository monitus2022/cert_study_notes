# Skill 4.3.2: Configure Least Privilege Access to ML and AI Artifacts

## Task 4.3: Operating, Monitoring, and Securing ML and AI Solutions - Secure ML and AI workloads and model endpoints

---

## Core Objective & Scope

Grant identities the **minimum permissions required** to perform their job on ML artifacts — training data, model artifacts, endpoints, pipeline resources — and nothing beyond. Apply to both **human identities** (engineers, data scientists) and **workload identities** (training jobs, inference endpoints, Lambda functions).

---

## IAM Policy Scoping for ML Artifacts

| Artifact Type | Primary Resource ARN Pattern | Key Actions to Scope |
|---|---|---|
| **S3 Training Data** | `arn:aws:s3:::bucket/prefix/*` | `s3:GetObject`, `s3:PutObject`, `s3:ListBucket` (bucket-level) |
| **SageMaker Model** | `arn:aws:sagemaker:region:acct:model/*` | `sagemaker:CreateModel`, `DescribeModel`, `DeleteModel` |
| **SageMaker Endpoint** | `arn:aws:sagemaker:region:acct:endpoint/*` | `sagemaker:InvokeEndpoint` (data-plane), `CreateEndpoint` (control-plane) |
| **SageMaker Training Job** | `arn:aws:sagemaker:region:acct:training-job/*` | `sagemaker:CreateTrainingJob`, `StopTrainingJob` |
| **ECR Image** | `arn:aws:ecr:region:acct:repository/repo-name` | `ecr:GetDownloadUrlForLayer`, `ecr:BatchGetImage`, `ecr:BatchCheckLayerAvailability` |
| **Bedrock Foundation Model** | `arn:aws:bedrock:region::foundation-model/model-id` | `bedrock:InvokeModel`, `bedrock:InvokeModelWithResponseStream` |
| **KMS Key (artifact encryption)** | `arn:aws:kms:region:acct:key/key-id` | `kms:Decrypt`, `kms:GenerateDataKey`, `kms:Encrypt` |

---

## Policy Construction Patterns

- **Resource-level scoping** — Always attach `Resource` ARNs to `Allow` statements. Avoid `"Resource": "*"` in production policies.
- **Condition keys to narrow access** — Use `aws:SourceIp`, `aws:PrincipalTag`, `s3:prefix`, `sagemaker:WorkteamArn`, or `aws:RequestedRegion` to add context boundaries.
- **Permission boundaries** — Attach to IAM entities to cap maximum permissions regardless of attached policies. Critical for delegated admin scenarios.
- **Separate human vs. workload identities** — Engineers get IAM Users/Roles with console access; training jobs and endpoints get **execution roles** with only API-level permissions required at runtime.
- **Scoped-down S3 access for training** — Grant bucket-level `s3:ListBucket` with `Condition: {"StringLike": {"s3:prefix": ["training-data/*"]}}` and object-level `s3:GetObject` on `arn:aws:s3:::bucket/training-data/*`.

> **Exam Gotcha:** `s3:ListBucket` is a **bucket-level** action (Resource must be the bucket ARN). `s3:GetObject` and `s3:PutObject` are **object-level** actions (Resource must be the object ARN or wildcard prefix).

## Credential Selection Decision Matrix

| Scenario | Credential Type | Rationale |
|---|---|---|
| **Production workload** invoking FM/endpoint | **IAM Role with temporary credentials** (via STS) | Auto-rotated, least privilege, inherits identity policy, no static secret in code |
| **Short-term exploration/notebook** | Short-term Bedrock API key (session-bound) | Inherits generating identity's permissions; expires with session |
| **Long-running dev/test** | Long-term API key stored in **AWS Secrets Manager** | Rotatable via Secrets Manager; still not recommended for production |
| **Cross-account access** | IAM Role with trust policy (sts:AssumeRole) | No static keys shared across accounts |
| **On-prem/hybrid** | IAM Roles Anywhere (certificate-based) | Temporary credentials for non-AWS hosts |
| **SageMaker training needing S3** | Execution role attached to training job | Role policies scope exactly which bucket/prefix the job can read/write |

> **Exam Gotcha:** Long-term API keys are documented by AWS for **exploration and development only** — never production. The correct answer for production is always a role with temporary credentials. A key found in code, an image, or an environment file is the anti-pattern.

## Service-Specific Least Privilege Configurations

### SageMaker
- **Execution role** (training/inference) — distinct role per workload type; avoid reusing admin or human roles.
- **Notebook instances** — attach role with least privilege; disable direct internet access by placing in private subnet with VPC endpoints.
- **Model registry / pipeline** — separate roles for `sagemaker:RegisterModel` vs. `sagemaker:DeployModel` to enforce separation of duties.

### Amazon Bedrock
- **InvokeModel permissions** — scope to specific foundation model ARNs, not `bedrock:*` across all models.
- **Knowledge base access** — separate role for `bedrock:Retrieve` vs. `bedrock:InvokeModel` when RAG is involved.
- **Guardrails application** — associate guardrail policy at the API call or agent level; ensure role has `bedrock:ApplyGuardrail` where required.

### S3 (Datasets & Artifacts)
- **Versioning + lifecycle** — enable versioning to protect against accidental deletion; least privilege includes denying `s3:DeleteObject` for readers.
- **Block public access** — enable at account and bucket level; use as defense-in-depth alongside IAM.

### KMS (Encryption Keys)
- **Key policy always wins** — IAM policies grant permission, but the KMS key policy must also allow the principal. Both must grant `kms:Decrypt` for S3/SageMaker encrypted artifacts.
- **Separate keys per use case** — training data key vs. model artifact key vs. log encryption key; limits blast radius.

## Security & Compliance Integration

| Control | Purpose in Least Privilege Context |
|---|---|
| **IAM Access Analyzer** | Identifies resources shared with external entities; flags overly permissive S3 buckets, KMS keys, IAM roles |
| **IAM Policy Simulator** | Dry-run policy changes before applying; validates effective permissions |
| **AWS CloudTrail (management events)** | Audits who granted/revoked permissions, who assumed roles |
| **AWS Config rules** | Detect over-permissive policies (e.g., `iam-policy-no-statements-with-admin-access`) |
| **S3 Storage Lens + Trusted Advisor** | Flags buckets with public read/write or cross-account access |

> **Exam Gotcha:** IAM policy grants and KMS key policy grants must **both** allow access to KMS-encrypted artifacts. If S3 access succeeds but decryption fails, the error is `AccessDenied` or `InvalidObjectState` — the root cause is often a missing `kms:Decrypt` in the IAM policy **or** a key policy that doesn't include the principal.

## Anti-Patterns & Common Distractor Traps

- **Widening permissions to clear an `AccessDenied` error** — Read the error: it names the denied action, resource, and principal. Grant exactly that action on exactly that resource.
- **Using a single elastic role for everything** — Over-permissive role attached to training job or endpoint is a top finding. Separate roles per workload type and pipeline stage.
- **Placing credentials in environment variables or baked into images** — Correct answer always references Secrets Manager or IAM roles.
- **Granting `sagemaker:*` or `s3:*` wildcard actions** — Scoped `Allow` with named actions always preferred.
- **Confusing control-plane and data-plane permissions** — `sagemaker:CreateEndpoint` (deploy) vs. `sagemaker:InvokeEndpoint` (call) are separate; a caller who can deploy does not automatically have invoke rights, and vice versa.
- **Forgetting bucket-level vs. object-level S3 actions** — `ListBucket` on `"Resource": "arn:aws:s3:::bucket"`; `GetObject` on `"Resource": "arn:aws:s3:::bucket/*"`. Mixing these is a classic incorrect answer.
- **Assuming Bedrock API key equals IAM credential** — Bedrock API keys are not IAM entities; they are generated from an IAM identity but scoped by that identity's permissions and a set expiration.
