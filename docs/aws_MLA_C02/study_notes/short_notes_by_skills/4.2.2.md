# Skill 4.2.2: Configure and use tools to troubleshoot and analyze resources (for example, Amazon CloudWatch, Amazon Bedrock AgentCore Observability, AWS X-Ray)

## Task 4.2: Operating, Monitoring, and Securing ML and AI Solutions - Optimize and manage ML and AI infrastructure costs and performance

---

## Tool Selection Decision Matrix

| Troubleshooting Need | Primary Tool | Key Signal Produced | Exam Distractor |
|---|---|---|---|
| **Aggregate performance metrics** (latency, CPU, token usage) | Amazon CloudWatch | Time-series metrics, alarms, dashboards | CloudTrail (audit API calls) |
| **Distributed request tracing** (component-level latency attribution) | AWS X-Ray | Service map, trace segments, subsegments | VPC Flow Logs (network IP traffic) |
| **Agent invocation breakdown** (model calls, tool calls, memory ops) | Amazon Bedrock AgentCore Observability | Per-invocation traces of agent steps | CloudWatch Logs Insights (log queries only) |
| **Correlate metrics + logs + traces together** | CloudWatch + X-Ray integration | Unified observability view | — |

## Amazon CloudWatch

**Primary purpose:** Aggregate operational telemetry for ML endpoints, Bedrock invocations, and compute resources.

### Key ML-Specific Metrics to Monitor

- **SageMaker Endpoint:** `InvocationsPerInstance`, `ModelLatency`, `OverheadLatency`, `CPUUtilization`, `GPUUtilization`, `MemoryUtilization`, `DiskUtilization`
- **Bedrock (On-Demand):** `InvocationLatency`, `InputTokenCount`, `OutputTokenCount`, `InvocationThrottles`, `InvocationClientErrors`, `InvocationServerErrors`
- **Bedrock (Provisioned Throughput):** `ProvisionedModelInvocationCount`, `ProvisionedModelThrottles`

> **Exam Gotcha:** Throttling on Bedrock (`InvocationThrottles`) indicates you've hit the model's rate or token-per-minute quota — the fix is Provisioned Throughput, not auto-scaling (there are no instances to scale).

### CloudWatch Features for Cost/Performance Optimization

| Feature | Use Case | Why It Matters |
|---|---|---|
| **Metric Math** | Compute derived metrics (e.g., tokens per invocation) | Combines separate metric streams for richer analysis |
| **Dashboards** | Correlate utilization + latency + errors + token usage side-by-side | Shortens root-cause decisions |
| **Alarms** | Trigger on threshold breach (e.g., `CPUUtilization > 80%` for 15 min) | Proactive notification before SLA impact |
| **Logs Insights** | Query structured/unstructured logs for specific error patterns or invocation IDs | Faster than manual log scanning |
| **Contributor Insights** | Identify top-N contributors to a metric (e.g., which endpoint variant drives most latency) | Pinpoints resource hotspots |
| **Synthetics (Canary)** | Simulate user requests to verify endpoint availability/performance | Proactive external monitoring |

> **Exam Gotcha:** CloudWatch collects *metrics and logs* — not raw network packet captures (that's VPC Traffic Mirroring) and not database schemas (that's AWS Glue Data Catalog).

## AWS X-Ray

**Primary purpose:** Distributed tracing — attribute end-to-end request latency to specific components in a multi-service ML pipeline.

### X-Ray Core Concepts

| Concept | Description |
|---|---|
| **Trace** | End-to-end path of a single request across all components |
| **Segment** | Portion of the trace recorded by a single service/resource |
| **Subsegment** | Finer-grained breakdown within a segment (e.g., a database call inside a Lambda function) |
| **Service Map** | Visual representation of all services and their connections/latencies |
| **Annotations** | Key-value pairs for filtering traces (e.g., `model_version: v2.3`) |
| **Sampling** | Controls the percentage of requests traced (default: 1/sec + 5% of additional) |

### When X-Ray Beats CloudWatch

> **Exam Gotcha:** CloudWatch gives you *average* latency; X-Ray tells you *which component* caused the slowness. Use X-Ray when a request traverses multiple components (API Gateway → Lambda → Bedrock → DynamoDB) and you need to isolate the bottleneck.

### Instrumentation Methods

- **Lambda:** Enable "Active tracing" on function configuration (no code changes needed for entry-point tracing)
- **SageMaker Inference:** Add `X-Amzn-Request-Id` to invocation request; trace appears in X-Ray console
- **EC2/ECS:** Use X-Ray SDK (Python, Java, Node.js) to create segments/subsegments manually
- **API Gateway:** Enable X-Ray tracing on stage settings

> **Exam Gotcha:** X-Ray does *not* replace CloudWatch — they serve different questions. CloudWatch answers "is it slow/erroring?" (aggregate), X-Ray answers "where specifically did the slow request get stuck?" (per-request trace).

## Amazon Bedrock AgentCore Observability

**Primary purpose:** Capture the full internal workflow of a Bedrock Agent invocation — model inference, tool usage, knowledge base retrieval, memory operations, guardrails.

### What It Records

| Trace Component | Description | Cost/Performance Insight |
|---|---|---|
| **Agent invocation trace** | Start → planning → tool calls → synthesis → response | One user request = multiple model calls |
| **Model inference calls** | Each Bedrock FM invocation within the agent | Identifies number of model calls per user request |
| **Tool invocations** | Lambda calls, API calls, or other tools executed by the agent | Surfaces tool latency and failure loops |
| **Knowledge base retrieval** | Vector search results, retrieval timing | Separates retrieval latency from model latency |
| **Memory operations** | Session memory reads/writes | Tracks state persistence overhead |
| **Guardrail evaluations** | Content filtering, sensitive data detection | Latency + compliance cost |

### When to Use AgentCore Observability

- **Agent cost amplification:** One user request produces multiple model calls → monitor `cost_per_invocation`, not `cost_per_model_call`
- **Retry loop detection:** Tool failures causing infinite retry cycles that inflate token usage without producing user value
- **Component latency attribution:** Is slowness from the model or from the tool/retrieval layer?

> **Exam Gotcha:** Agent cost is *amplified*. A single user request = planning call + N tool calls + synthesis call. Watch cost per *user invocation*, not per individual model call. A retry loop invisible to users can balloon the bill without any traffic change.

## Tool Integration Patterns

| Pattern | How | When to Use |
|---|---|---|
| **CloudWatch + X-Ray** | X-Ray traces appear in CloudWatch console; use CloudWatch alarms on X-Ray trace metrics | Multi-service latency troubleshooting |
| **CloudWatch + Bedrock Metrics** | Bedrock emits token metrics to CloudWatch automatically | Token cost trend monitoring |
| **AgentCore Observability + CloudWatch** | Agent traces stream to CloudWatch Logs + X-Ray for permanent storage/analysis | Agent debugging and cost attribution |
| **CloudWatch Dashboards + Cost Explorer** | Build custom CloudWatch dashboards with token usage; correlating with Cost Explorer for spend attribution | Unified cost-performance view |

---

## Anti-Patterns & Common Distractors

| Anti-Pattern | Why It's Wrong | Correct Approach |
|---|---|---|
| Using X-Ray for aggregate monitoring | X-Ray samples traces; not designed for continuous metric collection | CloudWatch for metrics/alarms |
| Using CloudTrail for performance troubleshooting | CloudTrail records API calls for audit/compliance; not latency/throughput data | CloudWatch/X-Ray for performance |
| Scaling up instances when CloudWatch shows *average* latency is high but no individual component is slow | Average latency may be skewed; need to isolate the actual bottleneck | X-Ray trace to identify specific slow component |
| Disabling X-Ray sampling to trace 100% of requests in production | Introduces significant overhead and cost; statistically unnecessary | Default sampling rate (1/sec + 5%); increase temporarily for debugging |
| Using CloudWatch Logs only (no metrics) for endpoint health | Can't set alarms on log contents alone; lacks quantitative measurement | Combine with metric filters to extract numeric data |

## Quick Recall Matrix

| Question | Tool | Signal |
|---|---|---|
| Is my endpoint healthy? | CloudWatch | Health check metrics, invocation errors |
| Which component slowed this specific request? | X-Ray | Trace segments with timings |
| How many tokens did each agent step consume? | AgentCore Observability | Per-invocation trace with token counts per model call |
| What percentage of requests are failing? | CloudWatch | Error rate metric |
| How do I trace a request across Lambda + Bedrock + DynamoDB? | X-Ray | Cross-component trace |
| Why is my agent unexpectedly expensive? | AgentCore Observability + Cost Explorer | Count model calls per user request; attribute token spend |

---

> **Critical Exam Rule:** The three tools are complementary, not competitive. **CloudWatch** = aggregate metrics + alarms + dashboards. **X-Ray** = per-request distributed tracing. **AgentCore Observability** = per-invocation agent step breakdown. A question asking about "which tool isolates a slow component in a distributed ML pipeline" → X-Ray. "Which tool shows agent resource consumption per invocation" → AgentCore Observability.
