# Skill 4.3.8: Select the Appropriate Credential Type to Access FMs

## Task 4.3: Operating, Monitoring, and Securing ML and AI Solutions - Secure ML and AI workloads and model endpoints

---

## Credential Type Decision Matrix

| Credential Type | Lifespan | Rotation | Production Use | Best For | Backed By |
|---|---|---|---|---|---|
| **IAM Role (Temporary)** | Short-lived (15 min–12 hr) | Automatic via STS | ✅ **Yes** | Production workloads, cross-service access | IAM identity + session policy |
| **Short-term API Key** | Session-bound | Automatic with session expiry | ⚠️ Limited | Exploration, ad-hoc testing | Identity that generated it |
| **Long-term API Key** | Customer-defined | Manual | ❌ **No** (AWS documents for dev/exploration) | Legacy dev workflows | Its own IAM identity |
| **Static Secret in Code/Image** | Indefinite | None | ❌ **Never** | Anti-pattern | None |

> **Exam Gotcha:** The correct production answer is **always** an IAM role with temporary credentials. Any option embedding a key in an image, environment variable, or shared file is an automatic distractor.

---

## Access Patterns by Runtime

| Runtime | Recommended Credential Mechanism | Key Configuration |
|---|---|---|
| **Amazon EC2** | Instance Profile (IAM Role) | Attach role at launch; credentials auto-rotated via IMDSv2 |
| **Amazon ECS/EKS** | Task Role / IRSA | `taskRoleArn` in task definition; service account annotation for EKS |
| **AWS Lambda** | Execution Role | Set in function configuration; assume-role chain to Bedrock |
| **SageMaker Notebook** | Execution Role + short-term key for exploration | Notebook role scoped to S3/KMS only |
| **Local CLI / AWS SDK** | Short-term via `aws sts assume-role` or SSO | Never export long-term keys; use `aws configure sso` |
| **CI/CD Pipeline** | OIDC federation to IAM role | GitHub Actions / GitLab → `AssumeRoleWithWebIdentity` |

## Boto3 / SDK Patterns

```python
# ✅ Correct: Assume role for production FM access
sts = boto3.client('sts')
creds = sts.assume_role(
    RoleArn='arn:aws:iam::123456789012:role/BedrockProductionRole',
    RoleSessionName='ml-workload'
)
bedrock = boto3.client('bedrock-runtime',
    aws_access_key_id=creds['Credentials']['AccessKeyId'],
    aws_secret_access_key=creds['Credentials']['SecretAccessKey'],
    aws_session_token=creds['Credentials']['SessionToken']
)
```

**Boto3 parameter nuances:**
- `RoleSessionName`: required, max 64 chars, used in CloudTrail `userIdentity`
- `DurationSeconds`: 900–43200 (12h max); shorter = tighter blast radius
- `ExternalId`: required when third parties assume your role (confused deputy prevention)

## Credential Precedence & Resolution

**AWS SDK credential resolution order (first match wins):**
1. Explicit credentials passed to client constructor
2. Environment variables (`AWS_ACCESS_KEY_ID`, etc.)
3. Shared credentials file (`~/.aws/credentials`)
4. ECS task role / EKS IRSA
5. EC2 instance profile (IMDSv2)

> **Exam Gotcha:** If a denial occurs, check **which credential source won** — an old key in `~/.aws/credentials` can silently override a correctly configured instance profile. Use `aws sts get-caller-identity` to verify the active principal.

## Security Controls per Credential Type

| Control | IAM Role | Short-term Key | Long-term Key |
|---|---|---|---|
| **Scope via IAM Policy** | ✅ | ✅ (inherits creator's perms) | ✅ (own identity) |
| **Automatic Rotation** | ✅ | ✅ (session expiry) | ❌ |
| **Auditable in CloudTrail** | ✅ (`assumedRole`) | ⚠️ (key identity only) | ⚠️ |
| **Revocation** | Instant (detach policy / delete role) | Automatic at expiry | Manual (delete key) |
| **MFA Enforcement** | Via `Condition: {Bool: {aws:MultiFactorAuthPresent: true}}` | N/A | N/A |
| **VPC Confinement** | ✅ via `aws:SourceVpce` | ❌ | ❌ |

## Anti-Patterns (Distractor Traps)

- **Embedding API keys** in container images, Lambda environment variables, or config files → use Secrets Manager only if a static secret is unavoidable
- **Using long-term API keys** in production because "it works" → rotation burden, breach blast radius
- **Shared keys across hosts/environments** → no per-principal auditability; use per-workload roles
- **Manual key distribution** by engineers per shift → human error, no automation
- **Widening IAM permissions** to clear `AccessDenied` → read the error: it names the operation and resource; grant only that

---

## Secrets Manager Integration (When a Static Key Must Exist)

- **Use case:** Third-party FM provider with no IAM federation (non-AWS model endpoints)
- **Pattern:** Store key → application retrieves via `GetSecretValue` at runtime → enable automatic rotation with Lambda rotation function
- **KMS:** Encrypt secret with customer-managed key; grant decrypt only to the workload role
- **Never log secret value** from response; use `SecretBinary` vs `SecretString` appropriately

## Quick Decision Protocol

```
Production workload invoking FM?
  └─ Yes → IAM role + temporary credentials (EC2/ECS/Lambda role)
  └─ No (exploration) → Short-term key from current identity session

Static secret unavoidable (third-party FM)?
  └─ Secrets Manager + automatic rotation + KMS encryption

Credential in code, image, or env file?
  └─ Refuse. This is always wrong.
```

> **Hard Rule:** AWS documents long-term API keys for **development and exploration only**. Any exam answer selecting them for production access is incorrect regardless of the other options' apparent complexity.
