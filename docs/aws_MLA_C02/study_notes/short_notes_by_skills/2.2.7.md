# Skill 2.2.7: Adjust Fundamental Hyperparameters

## Task 2.2: ML Model and Foundation Model (FM) Development - Train, fine-tune, and customize models for ML and AI solutions

---

### Core Hyperparameter Fundamentals

| Hyperparameter | Definition | Typical Impact | Exam Signal |
|---|---|---|---|
| **Epoch** | One complete pass over the entire training dataset | More epochs → better fit until overfitting begins | Track via validation loss curve, not training loss alone |
| **Batch size** | Number of samples processed before one weight update | Larger → more stable gradients, more memory; Smaller → noisier updates, better generalization | Powers of 2 (32, 64, 128, 256) are common defaults |
| **Learning rate (α)** | Step size for gradient descent updates | Too high → divergence/NaN loss; Too low → slow convergence or local minima | Most sensitive hyperparameter; tune first |
| **Steps** | Total number of parameter updates (batches processed) | Related to epochs: steps = epochs × (samples / batch_size) | For distributed/checkpoint settings, steps may be specified instead of epochs |
| **Validation frequency** | How often to evaluate on held-out set (per epoch or per N steps) | Affects early stopping accuracy and training overhead | SageMaker emits validation metrics to CloudWatch per configured interval |

---

### Decision Matrix: Adjusting Hyperparameters for Common Problems

| Symptom | Diagnostic Signal | Primary Fix | Secondary Fix |
|---|---|---|---|
| **Overfitting** | Train loss ↓, validation loss ↑ | Increase regularization (dropout, weight decay, L2) | Reduce epochs → enable early stopping; reduce model capacity; add data augmentation |
| **Underfitting** | Train loss high and validation loss high | Increase model capacity (layers, units) | Train more epochs; lower regularization; adjust learning rate |
| **Diverging loss (NaN)** | Loss explodes or becomes NaN | Decrease learning rate (10x reduction) | Add gradient clipping; reduce batch size; check data normalization |
| **Slow convergence** | Loss decreasing but plateauing slowly | Increase learning rate | Use learning rate warmup; switch optimizer (Adam vs SGD) |
| **Oscillating convergence** | Loss fluctuates around optimum | Decrease learning rate | Increase batch size; use learning rate decay/schedule |
| **Long training time** | Job runs too long to meet SLAs | Enable distributed data parallelism | Increase batch size; reduce epochs; use early stopping |

### Hyperparameter Values & Guidance

> **Exam Gotcha:** Hyperparameters are **not computed or analytically solved**—they are tuned via search (SageMaker AMT) or set by the ML engineer based on domain experience and experimentation.

**Batch Size Considerations:**
- **GPU memory bottleneck:** Reduce batch size until the model and optimizer state fits in GPU memory
- **Generalization benefit:** Smaller batches (< 64) often generalize better due to noisier gradients acting as implicit regularization
- **Throughput benefit:** Larger batches exploit GPU parallelism and reduce communication overhead in distributed settings
- **Batch normalization interaction:** Very small batches (< 8) destabilize BatchNorm statistics

**Epoch Considerations:**
- **Early stopping analog:** Set a high epoch ceiling with `EarlyStopping` callback monitoring `val_loss` with patience of 5–10 epochs
- **Fine-tuning pre-trained models:** Use far fewer epochs (1–5) than training from scratch to avoid catastrophic forgetting
- **SageMaker AMT interaction:** Epochs are often fixed during tuning; optimization focuses on learning rate, batch size, and architectural hyperparameters

**Learning Rate Considerations:**
- **Standard starting points:** `1e-3` for Adam; `1e-2` for SGD with momentum; `1e-5` to `1e-4` for fine-tuning LLMs
- **Schedules:** Use `StepDecay`, `CosineAnnealing`, or `ReduceLROnPlateau` for better convergence than constant rates
- **Warmup:** Linear warmup over first few hundred steps stabilizes training with large batch sizes and Transformer models

**Steps vs. Epochs:**
- **SageMaker built-in algorithms:** Some (e.g., XGBoost, Linear Learner) use `num_round` or `epochs`; TensorFlow/PyTorch script mode typically exposes `epochs`
- **Distributed training:** Steps per epoch = ceil(total_samples / (batch_size × num_instances))
- **Checkpoint frequency:** Set checkpoint every N steps (not epochs) to enable mid-epoch recovery for long jobs

### SageMaker Script Mode: Hyperparameter Passing

**Boto3 API parameters:**
```python
estimator = PyTorch(
    entry_point="train.py",
    hyperparameters={
        "batch-size": 256,
        "epochs": 10,
        "learning-rate": 0.001,
        "weight-decay": 0.0001,
    }
)
```

**In training script (argparse):**
```python
parser.add_argument("--batch-size", type=int, default=64)
parser.add_argument("--epochs", type=int, default=10)
parser.add_argument("--learning-rate", type=float, default=1e-3)
```

> **Exam Gotcha:** SageMaker injects hyperparameters as command-line arguments to your script. **Keys must be lowercase** and use hyphens (not underscores) when passed via the estimator's `hyperparameters` dict. Inside the script, use `argparse` with `--batch-size` style flags.

### SageMaker AMT: Hyperparameter Search

| Search Strategy | When to Use | Notes |
|---|---|---|
| **Bayesian Optimization** | Budget ≥ 10 jobs; continuous or integer ranges | Uses past results to guide next sample; best for small search spaces |
| **Random Search** | Exploratory; many categorical parameters | Good coverage; simple; baseline for comparison |
| **Hyperband** | Early stopping of poor performers; large budget | Multi-fidelity; aggressively prunes underperforming configs early |

**Key AMT settings:**
- **Objective metric:** Must be emitted via `report` in script or from built-in algorithm; direction matters (`Minimize` vs `Maximize`)
- **Range types:** `ContinuousParameter`, `IntegerParameter`, `CategoricalParameter`
- **Completion criteria:** `MaxNumberOfTrainingJobs`, `MaxParallelTrainingJobs`, `TargetObjectiveMetricValue`
- **Warm start:** Reuse previous tuning job results to cut search time

> **Exam Gotcha:** AMT runs **separate training jobs** for each hyperparameter combination—it does not modify values within a single training run. Misconfiguring the objective metric direction (e.g., minimizing accuracy) results in the tuner "optimizing" toward the worst model.

### Early Stopping & Regularization

| Technique | Mechanism | Key Parameter | Trade-off |
|---|---|---|---|
| **Early stopping** | Halt training when validation metric fails to improve for `patience` epochs | `patience=5` (epochs) or `min_delta=0.001` | Prevents overfitting; may stop too early with noisy metrics |
| **Dropout** | Randomly zero out neurons during training | `dropout_rate=0.2–0.5` | Adds regularization; increases epochs needed for convergence |
| **Weight decay (L2)** | Penalize large weights in loss | `weight_decay=1e-4–1e-2` | Prevents overfitting; too high causes underfitting |
| **Gradient clipping** | Clip gradient norm to prevent explosion | `max_grad_norm=1.0` | Stabilizes training; essential for RNNs/LSTMs and LLMs |
| **Data augmentation** | Artificially expand dataset | Depends on modality | Reduces overfitting without changing model |

### Anti-Patterns & Common Distractor Traps

- **Tuning epochs during AMT instead of using early stopping:** Inefficient; wastes budget on jobs that overfit
- **Increasing batch size to fix overfitting:** Batch size primarily affects optimization stability, not generalization—use regularization instead
- **Using `steps` and `epochs` interchangeably:** They are mathematically related but not equal; `steps = epochs × ceil(total_samples / batch_size)`
- **Setting learning rate too high for fine-tuning:** Pre-trained weights are already good; small learning rates (`1e-5`) preserve them
- **Ignoring validation metrics in CloudWatch:** Training loss alone is misleading; always monitor `val_loss` or `val_accuracy`
- **Tuning one hyperparameter at a time (grid search):** Inefficient; use Bayesian optimization or random search to explore interactions

### Fine-Tuning LLM/FM Hyperparameters

| Parameter | Typical Range | Purpose |
|---|---|---|
| **Learning rate** | `1e-6` to `5e-5` | Preserve pre-trained knowledge |
| **Epochs** | `1–5` | Avoid catastrophic forgetting |
| **Batch size** | `8–64` (limited by GPU memory) | Balance stability and convergence |
| **Weight decay** | `0.01–0.1` | Prevent overfitting on small fine-tuning datasets |
| **LoRA rank (r)** | `4–64` | Lower rank = fewer trainable parameters, less overfitting |
| **LoRA alpha** | `16–32` | Scaling factor; typically 2× rank |
| **Max sequence length** | `512–4096` | Must match task context; longer requires more GPU memory |

> **Exam Gotcha for FM fine-tuning:** Catastrophic forgetting manifests as the model performing well on the fine-tuning task but losing general capability. Defenses: **mix general-domain data into the fine-tuning set**, use **low rank adaptation (LoRA)**, or apply **small learning rates**.
