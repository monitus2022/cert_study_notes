## Evaluation Scope by Model Type

| Dimension | Traditional ML | GenAI Models |
|-----------|---------------|--------------|
| **Output** | Single prediction (class, value) | Open-ended text, embeddings |
| **Primary Metrics** | Accuracy, Precision, Recall, F1, AUC-ROC, RMSE, MAE | ROUGE, BLEU, BERTScore, Semantic Similarity |
| **Ground Truth** | Fixed, exact-match | Multiple valid paraphrases |
| **Validation Set** | Holdout, cross-validation | Prompt dataset + reference outputs |
| **Failure Modes** | Overfitting, class imbalance, data drift | Hallucination, toxicity, bias, unfaithfulness |
| **Explainability** | SHAP, feature importance, partial dependence | Source attribution (RAG citations), trace inputs |

## Traditional ML Evaluation Core Techniques

**Classification metrics by problem type:**
- **Binary classification:** AUC-ROC, Log Loss, F1 (when class imbalance), Precision-Recall AUC
- **Multiclass:** Macro-F1 (class balance), Micro-F1 (label frequency), Cohen's Kappa (agreement)
- **Highly imbalanced:** Precision@K, Average Precision, Matthews Correlation Coefficient

**Regression metrics selection:**
- **RMSE:** Penalizes large errors heavily; sensitive to outliers
- **MAE:** Robust to outliers; linear error scale
- **MAPE:** Percent-based; fails when target contains zeros
- **R²:** Explains variance proportion; misleading for non-linear relationships

**Validation strategies:**
- **Stratified k-fold:** Preserves class proportions; mandatory for imbalanced data
- **Time-series split:** Forward-chaining only; never use random splits on temporal data
- **Group k-fold:** Prevents data leakage when samples belong to the same entity/group

> **Exam Gotcha:** Shuffling time-series data before splitting introduces lookahead bias. Time-series splits must preserve chronological order, with no future data in training folds.

## GenAI Text Evaluation Metrics

### Overlap-Based (N-gram) Metrics

| Metric | Focus | Best For | Weakness |
|--------|-------|----------|----------|
| **BLEU** | Precision of n-grams | Machine translation | Penalizes valid paraphrases; poor for short answers |
| **ROUGE-N** | Recall of n-grams | Summarization | Rewards verbosity; misses semantic equivalence |
| **ROUGE-L** | Longest common subsequence | Summarization | Struggles with reordered content |
| **METEOR** | Precision + recall + synonym matching | Translation | Requires synonym/paraphrase tables |

### Embedding-Based (Semantic) Metrics

- **BERTScore:** Cosine similarity between contextual embeddings; aligns tokens via greedy matching
- **Sentence-BERT Similarity:** Mean-pooled sentence embeddings for paraphrase detection
- **Semantic Answer Similarity (SAS):** Cross-encoders for question-answer pair scoring

> **Exam Gotcha:** Overlap metrics (ROUGE/BLEU) fail to recognize meaning when wording differs significantly. Embedding-based metrics (BERTScore) capture semantic similarity but may miss factual correctness. For GenAI quality, combine overlap + embedding + LLM-as-judge.

## Amazon Bedrock Evaluations

### Evaluation Modes

| Mode | Description | Use Case | Console Requirements |
|------|-------------|----------|---------------------|
| **Programmatic** | Algorithmic scoring (ROUGE, BLEU, BERTScore) | Regression testing, fast automated checks | No human UI needed |
| **LLM-as-Judge** | Judge model scores + explanation | Custom quality rubrics, nuanced grading | No human UI needed |
| **Human** | Human raters score responses | Subjective quality, safety, brand voice | Requires browser-facing console |

### Key Configuration Points

- **Judge models:** Use stronger model as judge (e.g., Claude 3.5 Sonnet judging Claude 3 Haiku output)
- **Metrics:** Define custom rubrics (helpfulness, correctness, style, harmlessness)
- **Retrieval evaluation:** Measure `context relevance`, `context coverage` separately from answer quality

> **Exam Gotcha:** Human-based evaluation jobs created in the AWS Console require a browser-facing display to present prompts and responses to raters. Automated jobs do not.

## RAG System Evaluation

### The Two-Layer Split

| Layer | Question Answered | Metrics | Failure Signal |
|-------|-------------------|---------|----------------|
| **Retrieval** | Did we fetch the right context? | Context Precision, Context Recall, NDCG, Hit Rate | False negatives from vector search |
| **Generation** | Did the LLM use the context correctly? | Faithfulness, Answer Relevance, Hallucination Rate | Omission of retrieved facts |

**Critical anti-pattern:** Evaluating only the final answer masks the failure source. A fluent answer that omits facts is a retrieval failure in generation's clothing.

### Faithfulness vs. Answer Relevance

- **Faithfulness:** Does the answer contain claims supported by retrieved context? (hallucination detection)
- **Answer Relevance:** Does the answer actually address the question asked?
- **Context Relevance:** Is the retrieved context actually about the question?

## Human Evaluation Frameworks

**When human review is mandatory:**
- Safety-critical outputs (medical, legal, financial)
- Brand voice and tone compliance
- Ground-truth labeling for custom judge models
- Content moderation escalation

**Workflow integration patterns:**
- **HITL loop:** Human approval before customer-facing response
- **A/B rating:** Side-by-side preference scoring between models
- **Likert-scale rubrics:** 1-5 scoring on defined dimensions (accuracy, fluency, safety)

> **Exam Gotcha:** Treat human ratings as structured data (inter-rater agreement, consensus thresholds), not anecdotal feedback. Use Krippendorff's alpha or Cohen's kappa to validate rater consistency.

## Shadow Testing vs. A/B Testing vs. Offline Evaluation

| Approach | Traffic Pattern | Caller Impact | Metrics Captured | Best For |
|----------|----------------|---------------|------------------|----------|
| **Shadow** | Mirror copy to candidate | Zero (production answers only) | Latency, error rate, prediction drift | Pre-production validation |
| **A/B** | Split traffic between variants | Partial (candidate answers some callers) | Business KPIs, user engagement | Hypothesis testing on outcomes |
| **Offline** | Stored dataset | None | Accuracy, precision, semantic scores | Regression testing |

**SageMaker Shadow Test limitations:**
- Some endpoint configurations excluded (multi-model endpoints, serverless endpoints)
- Shadow responses are logged or discarded async (not returned to caller)

## Convergence Debugging Decision Tree

| Symptom | Diagnosis | Action |
|---------|-----------|--------|
| Loss oscillates violently | Learning rate too high | Reduce LR; add LR scheduler |
| Loss plateaus immediately | Learning rate too low OR model capacity insufficient | Increase LR; increase model width/depth |
| Train loss ↓, validation loss ↑ | Overfitting | Add regularization; early stopping; more data |
| Both losses flat | Data leakage OR loss function mismatch | Audit data pipeline; verify loss function |
| Loss spikes sporadically | Batch size too small OR bad samples | Increase batch; audit data quality |

> **Exam Gotcha:** Oscillation = learning rate too high (examine first). Never attribute convergence issues to instance count, data storage format, or number of output classes—these do not directly control gradient descent step size.

## Drift Detection & Performance Baselines

**Baseline types:**
- **Data drift:** Input feature distribution shifts from training
- **Model drift:** Prediction confidence degradation over time
- **Concept drift:** Relationship between features and target changes

**CloudWatch integration:**
- Publish evaluation metrics (accuracy, F1, semantic similarity) as custom metrics
- Set CloudWatch Anomaly Detection on metric baselines
- Alert on divergence from baseline window

**SageMaker Model Monitor:**
- Data quality: Schema violations, missing values, distribution shift
- Model quality: Needs ground truth labels (captured via SageMaker Capture)
- Bias drift: Monitors per-class prediction ratios

> **Exam Gotcha:** Model quality monitoring requires ground truth labels. If labels are not being collected at inference time (e.g., via SageMaker Capture or custom logging), only data quality and bias drift can be monitored.
