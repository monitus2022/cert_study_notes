# Skill 2.1.5: Select Retrieval Augmented Generation (RAG) Architecture Patterns Based on Use Case Requirements

## Task 2.1: ML Model and Foundation Model (FM) Development - Choose appropriate modeling approaches for ML and AI solutions

---

## RAG Architecture Decision Matrix

| Use Case Requirement | Recommended Pattern | Key Trade-off |
|---|---|---|
| **Rapid knowledge freshness** (minutes, not hours) | Managed RAG (Bedrock KB) | Sacrifices retriever customization |
| **Custom retriever/vector store control** | Custom RAG (LangChain, LlamaIndex) | Higher engineering overhead |
| **Source citations mandatory** | RAG (any pattern) | Slightly higher latency than pure FM |
| **Whole-document synthesis** | Fine-tuning or long-context FM | RAG weak at cross-passage synthesis |
| **Narrow-domain terminology stuck** | RAG + Supervised Fine-Tuning | Highest cost; combine only when both needed |
| **Static knowledge, no citations needed** | Prompt engineering or fine-tuning | RAG unnecessary complexity |

---

## Managed vs. Custom Retrieval

| Dimension | Amazon Bedrock Knowledge Bases | Custom RAG Pipeline |
|---|---|---|
| **Setup effort** | Minimal (source → sync) | High (orchestrator, chunker, embedder, store) |
| **Vector store** | Managed (OpenSearch Serverless, Aurora PG, Pinecone, Redis) | Your choice |
| **Chunking strategy** | Default or custom Lambda | Fully controllable |
| **Embedding model** | Amazon Titan default; configurable | Any model |
| **Re-sync cadence** | Automated on source change | Manual trigger or custom scheduler |
| **Cost** | API + storage | API + storage + engineering maintenance |

> **Exam Gotcha:** Bedrock Knowledge Bases **automatically** handles source sync to the vector index when documents are updated. In a custom RAG architecture, the engineer must build and trigger re-ingestion—the exam tests awareness of this operational burden.

## Production RAG: 8 Required Components

| # | Component | AWS Tool Options |
|---|---|---|
| 1 | **Connectors** to sources | S3, SharePoint, Salesforce, Confluence, Web Crawler |
| 2 | **Document processing** | AWS Lambda, Amazon Textract (PDF/OCR), Bedrock Data Automation |
| 3 | **Embedding model** | Amazon Titan Embeddings, Cohere Embed, custom SageMaker |
| 4 | **Vector store** | OpenSearch Serverless, Aurora PostgreSQL (pgvector), Pinecone, Redis Enterprise |
| 5 | **Retriever** | Semantic (vector similarity), hybrid (BM25 + vector), metadata-filtered |
| 6 | **Generating FM** | Amazon Bedrock (Claude, Llama, Titan, Mistral) |
| 7 | **Guardrails** | Amazon Bedrock Guardrails (content filtering, PII, topic blocking) |
| 8 | **Orchestrator** | LangChain, LlamaIndex, custom state machine, AWS Step Functions |

> **Exam Gotcha:** Retrieval **keeps content outside model weights**. Edited documents reflect immediately after re-ingestion; citations point to source chunks. Fine-tuning **writes knowledge into weights**—no citation capability, requires a new training job to update knowledge.

## RAG vs. Fine-Tuning: Selection Rules

| Requirement | RAG | Fine-Tuning |
|---|---|---|
| **Source citations** | ✅ Native | ❌ Not possible |
| **Knowledge refresh** | Minutes | Hours/days |
| **Whole-corpus synthesis** | ❌ Weak | ✅ Strong |
| **Domain tone/style/terminology** | ⚠️ Prompt-dependent | ✅ Persistent in weights |
| **External factual grounding** | ✅ Retrieves at runtime | ❌ Hallucination risk |
| **Catastrophic forgetting risk** | ✅ None (weights untouched) | ⚠️ Real—blend broad data |

```
Decision Order:
1. Try Prompting (instructions + few-shot)
2. If factual freshness/citations needed → RAG
3. If behavior/style/terminology still failing → SFT (possibly + RAG)
4. Never fine-tune before exhausting prompting + RAG
```

---

## Retrieval Quality Knobs

| Knob | Effect | Anti-Pattern |
|---|---|---|
| **Chunk size** | Larger = more context; smaller = precise retrieval | Too-small chunks lose semantic context |
| **Chunk overlap** | Preserves boundary context | Excessive overlap bloats index |
| **Top-K** | More passages = broader coverage | Too many dilutes relevance; wastes tokens |
| **Hybrid search** | BM25 + vector = better for IDs, codes, jargon | Relying solely on embeddings for exact terms |
| **Metadata filtering** | Restrict by department, date, region | Retrieving across entire corpus for scoped queries |

> **Exam Gotcha:** A support assistant requiring **citations** and **minutes-fresh policy edits** always selects RAG over fine-tuning. The vector index is external to the model—updates flow through re-embedding, not retraining.
