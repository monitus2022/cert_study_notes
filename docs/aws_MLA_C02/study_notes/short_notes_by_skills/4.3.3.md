# Skill 4.3.3: Configure IAM Policies and Roles for Users and Applications in ML and AI Systems
## Task 4.3: Operating, Monitoring, and Securing ML and AI Solutions - Secure ML and AI workloads and model endpoints

---

## Core Objective & Scope
Grant **least-privilege access** to ML/AI artifacts (training data, models, endpoints, Bedrock FMs, pipelines) by separating **human identities** from **workload identities** and selecting the correct credential type for each operational context.

---

## Identity & Credential Selection Matrix

| Context | Credential Type | Expiry | Use Case |
|---|---|---|---|
| **Production application** invoking SageMaker endpoint / Bedrock | **IAM Role** (EC2 instance profile, ECS task role, Lambda execution role) | Temporary (STS) | Required for prod workloads |
| **Exploration/Notebook** | Short-term Bedrock API key | Inherits session expiry | Convenient, inherits identity permissions |
| **External/Dev tooling** | Long-term Bedrock API key | Own identity, configurable expiry | AWS-documented for **exploration/dev only** |
| **Static secret must exist** | **AWS Secrets Manager** (rotated) | Rotating | Never in code, image, or env file |

> **Exam Gotcha:** Long-term API keys are explicitly documented by AWS for **exploration and development only** — not production. Production access always maps to an **IAM role with temporary credentials**. A shared key in environment variables or baked into an image is an anti-pattern.

## IAM Policy Scoping for ML Artifacts

### Key Resource Patterns (SageMaker)
| Resource Type | ARN Pattern |
|---|---|
| Training job | `arn:aws:sagemaker:region:account:training-job/*` |
| Model | `arn:aws:sagemaker:region:account:model/*` |
| Endpoint | `arn:aws:sagemaker:region:account:endpoint/*` |
| Endpoint config | `arn:aws:sagemaker:region:account:endpoint-config/*` |
| Notebook instance | `arn:aws:sagemaker:region:account:notebook-instance/*` |
| S3 bucket (data/artifacts) | `arn:aws:s3:::my-ml-bucket/*` (or prefix-scoped) |

### Bedrock Action Scoping
| Action | Description |
|---|---|
| `bedrock:InvokeModel` | Invoke a specific FM |
| `bedrock:ListFoundationModels` | List available FMs (broad) |
| `bedrock:Converse` | Converse API for supported models |
| `bedrock:CreateGuardrail` / `bedrock:ApplyGuardrail` | Manage/apply guardrails |

### Identity-Based Policy Structure (Least Privilege)
```json
{
  "Effect": "Allow",
  "Action": ["sagemaker:InvokeEndpoint"],
  "Resource": "arn:aws:sagemaker:region:account:endpoint/prod-model-v1",
  "Condition": {
    "StringEquals": { "aws:PrincipalTag/team": "ml-eng" }
  }
}
```

> **Exam Gotcha:** Widening a policy to clear an `AccessDenied` is the fastest wrong fix. The error names the **exact operation and resource refused** — grant precisely that, not a wildcard.

## Identity Separation Patterns

| Identity Type | AWS Mechanism | Key Principle |
|---|---|---|
| **Human (engineer/data scientist)** | IAM User with MFA, or IAM Identity Center (SSO) | Never shared; per-user audit trail |
| **Workload (training job, endpoint, Lambda)** | IAM Role (service-linked or custom) | Temporary credentials; no long-term keys |
| **Cross-account access** | IAM Role with trust policy | Role assumption, not static credentials |
| **Service-to-service** | Resource-based policies (S3 bucket, KMS key) or identity-based role | Least privilege per interaction |

### SageMaker Execution Role
- Attached to training jobs, processing jobs, and inference endpoints.
- Requires permissions for: S3 (read/write artifacts), ECR (pull images), CloudWatch Logs (write logs), KMS (decrypt data if customer-managed keys used).
- **Anti-pattern:** Granting `s3:*` or `*:*` to an execution role — scope to specific buckets/prefixes.

### Bedrock IAM Conditioning
| Condition Key | Purpose |
|---|---|
| `bedrock:ModelArn` | Restrict which FMs a principal may invoke |
| `aws:RequestedRegion` | Enforce data residency |
| `aws:PrincipalTag/*` | Attribute-based access control (ABAC) |

## Permission Boundaries & Guardrails

| Control | Function |
|---|---|
| **IAM Permission Boundary** | Caps maximum permissions a role can grant — prevents privilege escalation in CI/CD pipelines |
| **Service Control Policy (SCP)** | Organization-level guardrail preventing specific actions across accounts |
| **IAM Access Analyzer** | Identifies over-permissive policies, cross-account access paths, and unused access |
| **IAM Roles Anywhere** | Workloads outside AWS obtain temporary credentials via PKI (no long-term keys) |

> **Exam Gotcha:** Permission boundaries do **not** grant permissions — they only limit. A role's effective permissions are the **intersection** of its identity policy and boundary (and SCP at org level).

## CI/CD Pipeline IAM Considerations

| Pipeline Stage | IAM Requirement |
|---|---|
| **Source (CodeCommit/S3)** | Read-only access to repo/bucket |
| **Build (CodeBuild/SageMaker Pipelines)** | Role to push images to ECR, access Secrets Manager for registry creds, write to S3 |
| **Deploy (CodeDeploy/CloudFormation)** | Role to create/update SageMaker endpoints, pass execution role (`iam:PassRole`) |
| **Scan (CodeGuru/Inspector)** | Service-linked roles; findings written to Security Hub |

> **Critical `iam:PassRole` Nuance:** When a pipeline or service creates a SageMaker endpoint with a specific execution role, the calling principal must have `iam:PassRole` for that execution role ARN. Missing `iam:PassRole` is a common deployment failure.

## Cross-Service IAM Integration Points

| Integration | IAM Requirement |
|---|---|
| **SageMaker → S3** | Execution role needs `s3:GetObject`, `s3:PutObject` on specific buckets/prefixes |
| **SageMaker → ECR** | `ecr:GetDownloadUrlForLayer`, `ecr:BatchGetImage`, `ecr:BatchCheckLayerAvailability` |
| **SageMaker → KMS** | `kms:Decrypt`, `kms:GenerateDataKey` for customer-managed keys (CMKs) |
| **Bedrock → S3 (data source)** | `s3:GetObject` via role or bucket policy |
| **Lambda → Bedrock** | Lambda execution role includes `bedrock:InvokeModel` scoped to model ARN |
| **CloudWatch Logs** | `logs:CreateLogGroup`, `logs:CreateLogStream`, `logs:PutLogEvents` |

> **Exam Gotcha:** If a training job fails with `AccessDenied` when reading from S3 but the role looks correct, check: (1) S3 bucket policy, (2) KMS key policy if bucket is encrypted with CMK, (3) VPC endpoint policy if in private subnet. IAM identity policy is only one of three permission layers.

## Security Best Practices Summary

| Practice | Implementation |
|---|---|
| **Least privilege** | Scope actions + resources; revisit when workload changes |
| **Separation of duties** | Human users ≠ workload roles; pipeline roles scoped per stage |
| **Temporary credentials everywhere** | Use instance profiles, task roles, Lambda roles; never embed keys |
| **Secrets in Secrets Manager** | Rotation enabled; retrieved at runtime only |
| **MFA for humans** | Enforced via IAM policy condition or IAM Identity Center |
| **ABAC (tag-based)** | Use principal tags (`team`, `environment`) for scalable policy management |
| **Monitor policy drift** | IAM Access Analyzer + CloudTrail data events for `iam:CreatePolicyVersion`, `iam:PutRolePolicy` |

## Common Exam Distractor Traps

| Distractor | Correct Approach |
|---|---|
| "Store long-term API key in environment variable" | Use IAM role or Secrets Manager |
| "Grant `sagemaker:*` to fix endpoint error" | Scope to specific endpoint ARN + `InvokeEndpoint` |
| "IAM policy alone grants cross-account access" | Requires **trust policy** on destination role |
| "Permission boundary grants extra access" | Boundaries only **limit**; never grant |
| "One execution role for all pipeline stages" | Separate roles per stage (build vs deploy) for blast-radius reduction |
| "CloudTrail alone captures model invocation calls" | Requires **data events** configured separately |
