# Skill 2.3.5: Debug Model Convergence Issues

## Task 2.3: Analyze and evaluate the performance of ML and AI systems

---

## Convergence Failure Signature Chart

| Loss Pattern | Primary Diagnosis | First Action |
| :--- | :--- | :--- |
| **Oscillating / bouncing loss** | Learning rate too high | Reduce LR by factor of 10; add LR scheduler |
| **Slow, steady decrease (plateau)** | LR too low OR model capacity insufficient | Increase LR; add layers/width/features |
| **NaN/Inf loss** | Exploding gradients (LR too high, unnormalized data) | Gradient clipping, input normalization, lower LR |
| **Train ↓, Validation ↑ (diverging gap)** | Overfitting | Regularization, dropout, early stopping, more data |
| **Train & Val both high (flatlined)** | Underfitting / capacity ceiling | More features, deeper model, reduce regularization |
| **Sharp drop then immediate plateau** | Dead ReLU units / saturation | Check activation outputs; Swap to Leaky ReLU; re-init weights |

> **EXAM GOTCHA:** Oscillating loss is **always** learning rate as the *first* hyperparameter to inspect — not batch size, not optimizer choice. Batch size changes may require LR re-tuning, but the oscillation signature itself points to step size overshoot.

---

## Diagnostic Workflow (Order of Operations)

1. **Record baseline curves** — Always log train *and* validation loss per epoch (e.g., MLflow `mlflow.log_metric("val_loss", val_loss, step=epoch)`).
2. **Inspect gradient magnitude** — Monitor gradient norms; if `grad_norm > 100`, apply clipping (e.g., `tf.clip_by_norm` / `torch.nn.utils.clip_grad_norm_`).
3. **Check data pipeline** — Shuffle training data; verify no label leakage; normalize/standardize float inputs (`StandardScaler`, `Normalize`).
4. **Adjust optimizer / schedule** — Swap Adam→SGD only if needed; introduce `CosineDecay` or `ReduceLROnPlateau`.
5. **Verify model capacity** — Run a tiny batch to overfit; if model cannot overfit one batch, capacity is insufficient.
6. **Inspect activations** — Log layer output distributions; detect dead ReLUs (all-zero activations) or exploding outputs.

## PyTorch / TensorFlow / SageMaker-Specifics

| Framework | Key Tool | Common Flag / Parameter |
| :--- | :--- | :--- |
| **PyTorch** | `torch.nn.utils.clip_grad_norm_` | `max_norm=1.0` |
| **TensorFlow / Keras** | `tf.keras.optimizers.schedules` | `ExponentialDecay(initial_lr, decay_steps, decay_rate)` |
| **SageMaker Training** | `DebuggerHookConfig` | Tensors: `Loss`, `Gradients`; Rules: `Overfit`, `LossNotDecreasing` |
| **SageMaker Debugger** | `ProfilerConfig` | System metrics: CPU/GPU utilization, I/O wait time (slow data pipeline) |

> **EXAM GOTCHA:** SageMaker Debugger **rules** (e.g., `Overfit`, `VanishingGradient`, `LossNotDecreasing`) auto-detect convergence issues during training but **do not fix them** — they emit CloudWatch Events for human/automated intervention.

## RAG / FM Convergence Considerations

| Context | Convergence Issue | Fix |
| :--- | :--- | :--- |
| **Distributed training (data parallel)** | Divergence after batch size increase | Scale LR linearly (`lr = base_lr × world_size`) |
| **Reinforcement learning (RL)** | Policy loss oscillates | Increase entropy coefficient, reduce LR, use PPO clipping |
| **LLM fine-tuning (LoRA/PEFT)** | No loss improvement | Increase LoRA rank (`r=16→64`); ensure trainable params frozen correctly |
| **Generative adversarial networks (GANs)** | Discriminator loss → 0, Generator loss → high | Rebalance training ratio (train discriminator less frequently) |

## Anti-Patterns & Traps

- **Restarting a failed training run without changing anything** — the same failure will repeat.
- **Only logging final loss** — without per-epoch curves, convergence issues are undiagnosable.
- **Tuning batch size without adjusting LR** — LR and batch size are coupled; large batch often requires higher LR.
- **Applying early stopping on oscillating curves without first fixing LR** — masking the root cause.
- **Assuming distributed training always converges faster** — communication overhead can slow convergence; smaller batch per worker may destabilize.
- **Using `ReduceLROnPlateau` with `patience=1`** — prematurely reduces LR on noise, hiding real signal.

## Formula Reference

| Metric | Formula / Definition |
| :--- | :--- |
| **Train-Val gap** | `|train_loss - val_loss|` — gap widening = overfitting |
| **Gradient norm** | `‖∇θ L‖₂` — stable range: `0.1–10`; explosive if `>100` |
| **Learning rate warmup** | `lr(t) = initial_lr × min(1, t / warmup_steps)` |
| **Cosine decay** | `lr(t) = min_lr + 0.5 × (max_lr - min_lr) × (1 + cos(πt / T))` |

## Rapid Decision Matrix

| Symptom | Action |
| :--- | :--- |
| Loss jumps wildly epoch-to-epoch | Lower LR by 10x → if still oscillating, check data shuffling |
| Loss decreases then suddenly spikes | Suspect a bad data batch → validate data pipeline |
| Validation loss better than train loss | Underfitting, or validation set too easy/leaked |
| Loss stuck at ~0.69 (binary CE) | Model outputting random guesses — capacity/features insufficient |
| Loss stuck at ~2.30 (multi-class CE) | Same: near-uniform random output |
| Train loss perfect, val loss terrible | Severe overfitting — add dropout/weight decay/early stop |
