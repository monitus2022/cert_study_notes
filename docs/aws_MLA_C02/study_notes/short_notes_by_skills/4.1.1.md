# Skill 4.1.1: Monitor model performance in production by using Amazon CloudWatch generative AI observability, Amazon Bedrock Model Evaluation, and drift detection pipelines.

## Task 4.1: Operating, Monitoring, and Securing ML and AI Solutions - Monitor ML and AI model inference and performance.

---

## Core Monitoring Architecture

| Component | Purpose | Key Output |
|-----------|---------|------------|
| **CloudWatch generative AI observability** | Pre-built dashboards for LLM/agentic workloads | Token usage, latency, errors, throttles, prompt traces |
| **Amazon Bedrock Model Evaluation** | Score model/knowledge base response quality | Automatic metrics, judge model scores + explanations, human ratings |
| **Drift Detection Pipeline** | Detect shifts in input distribution vs. baseline | Statistical distance metric + alert when threshold breached |
| **AWS X-Ray** | Distributed request tracing across components | Step-level latency/failure attribution |
| **SageMaker Production Variants** | A/B testing on live traffic via weighted routing | Per-variant metrics on same window |

> **Exam Gotcha:** CloudWatch generative AI observability is the ONLY option that combines token usage, latency, error rates, throttling, AND end-to-end prompt traces for agents in one view. CloudTrail logs APIs only; Config tracks resources; Cost Explorer is billing-only.

## Drift Detection Pipeline: Four Moving Parts (Memorize)

1. **Capture baseline** — record distribution during an agreed stable period.
2. **Capture current** — sample same metric from live traffic.
3. **Compare distributions** — statistical test suited to data type/dimensionality.
4. **Alert** — fire when distance crosses pre-agreed threshold.

| Drift Type | P(X) Inputs Shift? | P(Y|X) Relationship Shift? | Detection Method |
|------------|:------------------:|:-------------------------:|------------------|
| **Data drift (covariate shift)** | ✅ Yes | ❌ No | Compare prompt embeddings vs. baseline using high-dimensional statistic (e.g., MMD, energy distance, KS test for low-dim) |
| **Concept drift** | ❌ No | ✅ Yes | Downstream business metrics, user feedback, label acceptance rates |

> **Exam Gotcha:** A drift pipeline built on prompt embeddings detects **data drift only**. Concept drift — where prompts look identical but expected answers change — surfaces in user acceptance metrics, not distribution comparisons. Do not claim drift detection catches concept drift.

## CloudWatch Alarms & Anomaly Detection

- **Flat-line alarms are as critical as spike alarms:** invocation count dropping to zero = broken pipeline/endpoint, not just low traffic.
- **Duration growth run-over-run:** monitor p50/p99 latency drift on inference calls.
- **Throttling (HTTP 429 / ThrottlingException):** indicates quota exceeded; alert on throttle count as separate metric from general errors.
- **Anomaly Detection (CloudWatch):** band-based anomaly detection on metrics with seasonal/trend patterns; reduces manual threshold tuning.

### Data Pipeline Monitoring — Check Output, Not Just Completion

> **Exam Gotcha:** A preprocessing job that exits with status `SUCCESS` can still produce empty partitions, nulled columns from a schema change, or duplicate records from retries. Monitor **output row counts, null ratios, schema validation** — not only job status. Failure shape: upstream job "succeeds," downstream invocation errors spike.

## Amazon Bedrock Model Evaluation

| Evaluation Type | When to Use | Output |
|-----------------|-------------|--------|
| **Automatic evaluation** | Fast, deterministic metrics (BLEU, ROUGE, BERTScore, toxicity, robustness) | Numeric scores |
| **LLM-as-a-judge** | Subjective quality, helpfulness, safety, instruction following | Score + plain-language explanation per response |
| **Human-based evaluation** | Final validation, cost-tolerant, regulatory needs | Reviewer ratings |

- **Use-case separation:** Bedrock Evaluations score response **quality**, not runtime health. Pair with CloudWatch for latency/errors.
- **Custom prompt datasets:** S3 input with curated prompts + reference responses for automatic evaluation.

## Production Variants: A/B Testing & Shadow Testing

| Configuration | Weight Distribution | Live Responses Returned? | Use Case |
|---------------|:-------------------:|:------------------------:|----------|
| **A/B (weighted production variants)** | Sum of weights = 100% of traffic | ✅ Yes — both variants serve users | Prove candidate better on real metrics before full rollout |
| **Shadow variant** | 0% traffic weight; copy of incoming requests | ❌ No — responses recorded only | Test serving stack/model without user exposure |

- **Traffic split formula:** fraction = variant_weight / Σ(all_variant_weights).
- **Fair comparison:** same metric set, same time window, same error/latency thresholds across variants.
- **Weighted models** with `TargetVariant` / `ProductionVariant` in `CreateEndpointConfig`.

> **Exam Gotcha:** SageMaker production variants enable live A/B testing on ONE endpoint. If requirements say "single endpoint, gradual rollout, compare versions," choose production variants — do NOT provision separate endpoints (those give separate metrics and no traffic split control).

## Security & Compliance Notes

- **VPC Endpoints:** CloudWatch and Bedrock support VPC interface endpoints; keep monitoring traffic off public internet.
- **Encryption:** Bedrock model evaluation datasets in S3 should use **SSE-KMS**; CloudWatch Logs support KMS at-rest encryption.
- **IAM for Bedrock Evaluations:** Requires `bedrock:GetModelEvaluationJob` / `bedrock:CreateModelEvaluationJob` plus S3 read access to evaluation datasets.

---

## Anti-Patterns (Common Exam Distractors)

- ❌ **Monitoring only model invocation** — miss upstream data pipeline corruption; alert on output anomalies, not just job completion.
- ❌ **Single threshold on high values only** — misses flat-line (zero invocation) failures; add `<= 0` or anomaly bands.
- ❌ **Treating drift detection as "done" without threshold agreed in advance** — drift must have a numeric distance and a pre-set alert trigger.
- ❌ **Using CloudTrail for runtime metrics** — it logs API calls for audit, does not render latency or token usage.
- ❌ **Assuming cost allocation tags help monitoring** — tags are for billing attribution only.
- ❌ **Comparing model versions on different endpoints at different times** — use production variants on one endpoint for controlled A/B comparison.
