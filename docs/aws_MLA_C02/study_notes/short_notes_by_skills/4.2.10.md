# Skill 4.2.10: Monitor AI-specific cost patterns (token usage optimization, embedding computation costs, vector database storage optimization)

## Task 4.2: Operating, Monitoring, and Securing ML and AI Solutions - Optimize and manage ML and AI infrastructure costs and performance.

---

## Core Billing Units by AI Workload Type

| Workload | Primary Cost Driver | Optimization Target |
|---|---|---|
| **SageMaker Real-Time Endpoint** | Instance-hours (provisioned compute) | Utilization %, instance family, scaling policy |
| **Bedrock On-Demand Inference** | Input + output tokens per request | Prompt length, model size, response caps |
| **Embedding Generation** | Tokens processed × model rate | Batch processing, caching embeddings, right-sized embedding model |
| **Vector Database** | Storage (GB) + index compute (instance-hours) | Dimension reduction, pruning, tiering, index type |

> **Exam Gotcha:** Token cost = (input tokens × input rate) + (output tokens × output rate). Output tokens typically cost 3-4x input tokens. A 1000-token output costs more than a 1000-token input.

## Token Usage Optimization (Bedrock / LLM Inference)

**Monitor First:**
- **CloudWatch Metrics:** `InputTokenCount`, `OutputTokenCount`, `Invocations`, `InvocationLatency`, `InvocationClientErrors`
- **Bedrock AgentCore Observability:** Trace token consumption per agent orchestration step (planning call, tool calls, synthesis call)
- **Cost Explorer Groupings:** Filter by usage type to separate input vs output token spend

**Optimization Levers:**

| Lever | Mechanism | Impact |
|---|---|---|
| **Model Selection** | Switch to smaller model meeting quality bar | Reduces per-token rate on every request |
| **Prompt Trimming** | Shorten system prompts, remove redundant instructions | Reduces input tokens per request proportionally |
| **Context Window Management** | Retrieve only necessary context; truncate history | Linear reduction in input token cost |
| **Response Length Capping** | Set `max_tokens` / `maxTokens` parameter | Hard ceiling on output token spend |
| **Prompt Caching** | Cache static prefix KV states (e.g., tool schemas, system prompts) | Cached reads billed at reduced rate (typically ~10% of uncached) |
| **Batch Inference** | Move tolerant workloads to Bedrock Batch Inference | 50% discount vs on-demand token rates |

> **Exam Gotcha - Prompt Caching Rules:**
> - Minimum prefix length required (e.g., Anthropic Claude: 1024 tokens; Amazon Nova: vary by model).
> - Cache writes billed **higher** than uncached input tokens on some models.
> - Any change to tokens within prefix invalidates the entire cache backward from the change point — place all dynamic content **after** stable prefix.
> - Cached tokens billed at reduced rate on cache hit; cache TTL defaults (e.g., 5 minutes) require frequent reuse to justify.

**Prompt Structure for Cache Efficiency:**

```
[STATIC: System Prompt + Tool Definitions + Examples]  ← Cached
[DYNAMIC: User Query + Retrieved Context + Session]    ← Not cached
```

## Embedding Computation Costs

**Billing Patterns:**
- On-demand embedding inference: billed per token processed by embedding model
- Self-hosted embedding endpoints: billed per instance-hour regardless of actual usage

**Monitoring:**
- Track `embedding model invocation count` and `tokens per invocation` via CloudWatch
- For self-hosted: measure `GPU utilization` and `requests per second` to detect idle capacity

**Optimization Strategies:**

| Strategy | When to Use | Notes |
|---|---|---|
| **Embedding Caching** | Same text re-embedded repeatedly (e.g., document store with stable corpus) | Store hash → vector mapping; eliminates redundant API calls |
| **Batch Embedding Generation** | Large corpus ingestion, not user-facing | Lower per-token rates; amortizes overhead |
| **Right-Sized Embedding Model** | Quality bar is moderate | Smaller dimension models (e.g., 384 vs 1024 dims) process faster and store smaller |
| **Pre-compute at Ingestion** | Read-heavy workloads | Move embedding cost from query time to write time |
| **Dimension Reduction** | Legacy embeddings oversized | PCA/Matryoshka embeddings reduce storage and compute on downstream retrieval |

> **Exam Gotcha:** Amazon Bedrock `Batch` APIs for embedding models (`CreateBatchInferenceJob` with Embeddings models) apply **50% discount** vs on-demand — a common correct answer for bulk ingestion scenarios.

## Vector Database Storage Optimization

**Cost Components:**
- **Storage:** Per-GB pricing for vector data (e.g., Amazon OpenSearch Serverless, Amazon Aurora PostgreSQL with pgvector, Amazon MemoryDB)
- **Compute:** Index build, query processing, and memory residency costs
- **Replication overhead:** Multi-AZ replication multiplies storage cost

**Monitoring:**
- **OpenSearch Serverless:** Track `VectorSearchCollectionStorageUsed`, `OCU hours`
- **Aurora PostgreSQL:** Track `FreeStorageSpace`, `IOPS`, `CPUUtilization`
- **Cost Explorer:** Filter by `Tag` on vector collection to attribute cost per application/model

**Optimization Strategies:**

| Strategy | Mechanism | Trade-off |
|---|---|---|
| **Dimensionality Reduction** | Store 256-dim instead of 1536-dim vectors | Slightly reduced recall @ k |
| **Quantization / Compression** | Scalar quantization (int8), product quantization (PQ) | Lower memory footprint; minor accuracy loss |
| **Index Selection** | HNSW (higher memory, faster query) vs IVF (compact, lower memory) | Balance query latency vs storage cost |
| **Tiering / Lifecycle** | Move rarely queried vectors to S3 + lazy reload | Cold vectors unavailable until rehydrated |
| **Pruning** | Remove stale, duplicate, or low-value vectors | Requires metadata filtering logic |
| **Ghost Vector Elimination** | Dedupe semantically equivalent vectors | Saves storage + reduces query noise |
| **Collection Sharding** | Partition by tenant/domain | Better cache locality; lower per-query cost |

> **Exam Gotcha:** OpenSearch Serverless charges based on **OCU hours** (compute) and **storage GB** — scaling to zero OCUs when idle is automatic if you configure `Idle OCU` settings. For infrequent query patterns, enabling `At rest collection tiering` moves cold vectors to S3.

## Agent Resource Consumption Patterns

**Why Agents Multiply Costs:**
A single user request triggers:
1. Planning/orchestration model call
2. One or more tool invocation model calls
3. Memory read/write operations
4. Final synthesis/response generation call
5. Potential retry loops (invisible to user)

**Monitoring with Bedrock AgentCore Observability:**
- Enable tracing to capture **per-invocation** breakdown: `modelInvocation`, `toolInvocation`, `memoryOperation`
- CloudWatch metrics: `NumberOfModelCalls`, `NumberOfToolCalls`, `TokensPerInvocation`
- Set custom CloudWatch dashboards showing `cost per agent invocation` rather than `cost per model call`

> **Exam Gotcha:** Agent cost per invocation can be 3-10x a direct model call. A retry loop that a human never sees can double spend without traffic change. **Watch tokens per orchestration step**, not total endpoint invocations.

**Optimization Levers for Agents:**

| Lever | Impact |
|---|---|
| **Reduce tool description length** | Lower input tokens on every planning + tool call |
| **Use smaller model for planning steps** | Cheaper overhead (model A for orchestrator, model B for tools) |
| **Cache tool schemas & agent instructions** | Stable prefix reused across invocations |
| **Limit agent memory** | Bound memory operations; use session-scoped memory only |
| **Set max iterations** | Prevents runaway retry loops |

## Monitoring Dashboards — Required Metrics Together

**A useful cost dashboard displays these side by side:**

| Metric | Answers |
|---|---|
| `Invocations` | Is traffic rising or is cost per request rising? |
| `InputTokenCount` + `OutputTokenCount` | Are prompts longer, or responses longer? |
| `InvocationLatency` | Is slowness a capacity issue or a model-size issue? |
| `ModelErrors` / `Throttles` | Are errors adding retry costs? |
| `GPU/CPUUtilization` (SageMaker) | Is provisioned capacity actually used? |
| `NumberofRequests` per agent | Are user actions amplified differently over time? |
| Vector DB: `StorageUsed` + `QueryLatency` | Is storage growing faster than queries? |

> **Exam Gotcha:** AWS X-Ray traces **per-request component attribution** (which service made it slow), while CloudWatch aggregates show **trends over time**. Use both: aggregate to spot a problem, trace to localize it. For Bedrock agents, **AgentCore Observability** adds per-step token/action detail that CloudWatch alone doesn't capture.

## Cost Attribution & Guardrails

- **Cost Allocation Tags:** Apply `Project`, `Model`, `Environment`, `Team` tags to Bedrock invoke calls (via log-based tagging), SageMaker endpoints, OpenSearch collections, and agent configurations.
- **AWS Budgets:** Set **forecasted** token/usage budgets — alerts when projected spend exceeds threshold before it happens.
- **Service Control Policies (SCPs):** Restrict expensive model access (e.g., deny `InvokeModel` on premium models) for dev environments.
- **Bedrock Guardrails + Model Invocation Logging:** Enable `ModelInvocationLogging` to S3/CloudWatch for token-level auditability.

## Anti-Patterns (Common Distractor Traps)

| Anti-Pattern | Why It's Wrong |
|---|---|
| Applying SageMaker auto-scaling to Bedrock token costs | Bedrock on-demand has no instances to scale; optimize tokens instead |
| Enabling prompt caching on volatile prefixes | Cache invalidates every request; no savings materialize |
| Buying EC2 Savings Plans for SageMaker | EC2 Savings Plans don't cover SageMaker `ml.*` instance types |
| Reducing vector dimensions without recall testing | May fall below quality requirements |
| Using Provisioned Throughput for intermittent traffic | Provisioned Throughput bills hourly regardless of utilization — only for steady or predictable workloads |
| Tagging only infrastructure resources (not model calls) | Token costs aren't instance-tied; tags must propagate to invocation logs |
| Assuming all caching is free | Cache writes billed; minimum prefix required; TTL reset on first cache hit after expiry |
