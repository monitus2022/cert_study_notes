# Skill 4.3.9: Implement Safeguards and Sensitive Data Protection for ML/AI Solutions

## Task 4.3: Operating, Monitoring, and Securing ML and AI Solutions — Secure ML and AI workloads and model endpoints

---

## Core Concept & Primary Objective

**Purpose:** Insert policy enforcement between users and foundation models—evaluating **inputs (prompts)** and **outputs (responses)** to satisfy responsible AI requirements, prevent PII leakage, block prohibited content, and prevent hallucinated/unsupported claims.

> **Exam Gotcha:** Bedrock Guardrails evaluates **both prompts and responses**—you configure the direction explicitly. A guardrail applied only to input does nothing to block sensitive data in model output. Safeguard policies are **content-level controls**, not access controls. Guardrails do not replace IAM, VPC endpoints, or CloudTrail logging.

---

## Amazon Bedrock Guardrails: Policy Types Matrix

| Policy | Evaluates | Direction | Use Case | Block vs. Mask |
|---|---|---|---|---|
| **Content filter** | Harmful categories (violence, hate, sexual, insults, misconduct, prompt attacks) | Both | General toxicity/safety enforcement | Block or allow with threshold |
| **Denied topic** | Semantic topic match (not keywords) | Both | Refusing out-of-scope subjects (e.g., medical advice) | Block |
| **Word filter** | Custom keywords/bad words, regex | Both | Blocking profanity, internal codenames | Block or mask |
| **Sensitive information filter** | PII: SSN, DOB, email, phone, credit card, account numbers, custom regex | Both | Preventing customer/patient data exposure | Block or mask |
| **Contextual grounding check** | Claim vs. retrieved source passages | Output | RAG hallucination detection | Block or flag |
| **Automated Reasoning check** | Statement vs. formalized rules/policies | Output | Consistent policy-bound answers | Block or flag |

> **Exam Gotcha:** Contextual grounding uses **retrieved passages from the application's context**—you supply them in your API call. Automated Reasoning uses **formal rules** authored in Amazon Bedrock's Automated Reasoning language, not just textual policies. These two are distinct and not interchangeable.

## Key Configuration Parameters

### Boto3 / API Patterns

| Parameter | Purpose | Notes |
|---|---|---|
| `name` | Guardrail identifier | Max 50 chars, alphanumeric + `-`, `_` |
| `blockedInputMessaging` | Message shown when input blocked | Required if input blocking enabled |
| `blockedOutputMessaging` | Message shown when output blocked | Required if output blocking enabled |
| `contentPolicyConfig` | Content filter threshold: `LOW`, `MEDIUM`, `HIGH` | `NONE` to disable per category |
| `sensitiveInformationPolicyConfig` | PII entity list + `BLOCK`, `ANONYMIZE`, `MASK`, or `NONE` | `ANONYMIZE` replaces with generic label; `MASK` replaces with `***` |
| `contextualGroundingPolicyConfig` | `threshold` (0–0.99) + `filteringConfiguration` per type | Lower threshold = stricter |
| `applyGuardrailIdentifier` | Associate with a model invocation | Used via `InvokeModel`, `Converse`, `ConverseStream`, or Agents |

### CLI Reference

```
aws bedrock create-guardrail --name "finance-guardrail" \
  --blocked-input-messaging "Input blocked by policy" \
  --blocked-output-messaging "Output blocked by policy" \
  --sensitive-information-policy-config '{...}' \
  --contextual-grounding-policy-config '{...}'

aws bedrock apply-guardrail \
  --guardrail-identifier "abcd1234" \
  --guardrail-version "1" \
  --model-id "anthropic.claude-3-sonnet"
```

> **Exam Gotcha:** Guardrails are **versioned**. Updating a guardrail creates a new version—deployed applications keep using the old version until you explicitly update the version reference. Guardrails are **account- and Region-scoped**.

## Sensitive Data Protection: Full-Path View

The guardrail policy is necessary but **not sufficient** for sensitive data protection. The value must be protected **end-to-end**:

| Layer | Control | Purpose |
|---|---|---|
| **Prompt/response** | Bedrock Guardrails sensitive info filter | Mask/block PII in transit to/from model |
| **At rest** | AWS KMS encryption | Encrypt datasets, artifacts, logs, S3 buckets |
| **In transit** | TLS (default for Bedrock APIs) + VPC endpoint (PrivateLink) | Prevent network interception |
| **Logs** | CloudTrail data events, CloudWatch | Scan logs for residual PII; guard against logging raw payloads |
| **Code/artifacts** | CodeGuru Security (hardcoded secrets), Secrets Manager | No creds in code; rotate API keys |

## Deployment Patterns & Trade-offs

### Pattern A: Guardrails Applied at Bedrock API Level

**Use when:** All model invocations flow through Bedrock (`InvokeModel`, `Converse`, Agents).

**Advantage:** Centralized enforcement; no application code to deploy.  
**Caveat:** Does not cover models outside Bedrock or data leaving via other paths.

### Pattern B: Guardrails Applied at Application Layer

**Use when:** Custom orchestration, multi-model routing, or SageMaker-hosted models need protection.

**Advantage:** Unified policy across any model; application can log/monitor before calling downstream.  
**Caveat:** Requires embedding SDK calls and maintaining version alignment in application code.

### Pattern C: Hybrid (Bedrock + WAF/API Gateway)

**Use when:** Need rate limiting, IP restrictions, request size limits **plus** content filtering.

**Advantage:** Network-level abuse prevention complements content-layer guardrails.  
**Caveat:** Two distinct control planes; must test both in integration.

## Critical Decision: Which Guardrail Policy?

| Requirement | Correct Policy | Distractor |
|---|---|---|
| Block hallucinated RAG responses | **Contextual grounding check** | Denied topic |
| Prevent PII in model output | **Sensitive information filter** | Word filter |
| Stop discussion of financial advice | **Denied topic** | Content filter |
| Block offensive language variants | **Word filter** | Denied topic |
| Ensure answer follows internal policy rules | **Automated Reasoning check** | Contextual grounding check |
| Block harmful categories with adjustable severity | **Content filter** | Sensitive information filter |

> **Exam Gotcha:** Denied topics use **semantic similarity**, not simple keyword lists. Word filters use **literal matching** and **custom regex**. If the question says "topics the model should refuse to answer"—that's denied topics. If it says "specific terms or words"—that's word filter.

## IAM & Security Integration

- **Guardrail permissions:** `bedrock:CreateGuardrail`, `bedrock:ApplyGuardrail`, `bedrock:ListGuardrails`
- **Invocation with guardrail:** Requires both `bedrock:InvokeModel` (or `bedrock:Converse`) **and** permission to use the guardrail (`bedrock:ApplyGuardrail`)
- **Cross-account guardrails:** Not directly shared; replicate or manage in the calling account
- **Data protection:** Guardrails evaluate content in memory—configure **CCI/PHI handling** at the Bedrock API layer (model invocation logging still captures inputs/outputs unless explicitly disabled or redacted)

> **Exam Gotcha:** Guardrails **log blocked activity in CloudTrail** as `bedrock:ApplyGuardrail` or in CloudWatch. But the **prompt/response content** is only logged if you enable model invocation logging. Guardrails themselves do not log content autonomously.

## Anti-Patterns & Traps

| Anti-Pattern | Why It Fails | Correct Approach |
|---|---|---|
| Widening IAM to "fix" blocked guardrail responses | Guardrails are content-level, not permission-level | Adjust policy threshold or regex |
| Assuming contextual grounding = Automated Reasoning | Grounding checks source passage support; Automated Reasoning checks formal rules | Configure both if needed |
| Masking PII only in output but logging raw requests | Unmasked PII persists in CloudTrail/CloudWatch | Redact or disable invocation logging for sensitive fields |
| Setting content filter to `HIGH` for all categories | False positives block legitimate queries | Tune per category (`LOW`/`MEDIUM`) based on use case |
| Using denied topics for profanity | Semantic matcher isn't exact-match | Use word filter with custom regex |
| Storing guardrail version "1" but referencing "LATEST" in code | Version drift causes silent policy changes | Pin exact version in production |

## Memory Hooks

- **Six guardrail policies:** "C-D-W-S-C-A" → **C**ontent, **D**enied topics, **W**ord, **S**ensitive info, **C**ontextual grounding, **A**utomated Reasoning
- **Direction rule:** Content/Word/Sensitive → both; Contextual grounding/AR → output only
- **Grounding = Ground Truth (source text); AR = As Rules (formal policies)**
- **Masking hides value; blocking stops response entirely; anonymize replaces with label (e.g., `<PHONE_NUMBER>`)**
- **Guardrails = Layer 7; VPC endpoint = Layer 3/4; IAM = Layer 2** — all three needed for defense-in-depth
