# Skill 4.3.9: Implement Safeguards & Sensitive Data Protection (Amazon Bedrock Guardrails)
## Task 4.3: Operating, Monitoring, and Securing ML and AI Solutions — Secure ML and AI workloads and model endpoints

**Core concept:** Guardrails are a **runtime content-policy layer** that evaluates the **prompt before the FM sees it** and the **response before the user sees it**, returning a configured action (**BLOCK** or **MASK**). Business objective: enforce **responsible AI policies** and **sensitive-data protection** without retraining or modifying the model.

> **Hard rule:** Guardrails are a **content filter, not an access control**. They do **not** decide *who* can invoke a model — that is IAM. A compliance answer usually needs **both** layers, not one.

**Where it sits in the control stack (do not confuse these):**

| Layer | Question answered | Service |
|---|---|---|
| Identity | *Who* may call the model? | IAM roles/policies, Bedrock API keys |
| Network | *What path* does the call take? | VPC, PrivateLink interface endpoints |
| Encryption | Is data protected at rest/in transit? | KMS |
| **Safeguard** | *What content* is allowed through? | **Bedrock Guardrails** |
| Record | *What happened* afterward? | CloudTrail (data events), Config, invocation logs |

## Guardrail Policy Catalog (recognize, don't memorize)

| Policy | Evaluates | Applies to | Key config |
|---|---|---|---|
| **Content filters** | Harmful categories: hate, insults, sexual, violence, misconduct, **prompt attacks** | Input **and** output | Strength per category: `NONE/LOW/MEDIUM/HIGH`, set separately for input and output |
| **Denied topics** | Off-limits subject areas defined in natural language | Input **and** output | Name + definition + up to 5 sample phrases; up to **30 topics** per guardrail |
| **Word filters** | Literal term match (custom list, managed profanity list) | Input **and** output | Exact/custom words; regex-free |
| **Sensitive information filters** | PII and custom patterns | Input **and** output | Built-in entities (NAME, EMAIL, PHONE, SSN, CREDIT_DEBIT_CARD_NUMBER…) + **custom regex**; action `BLOCK` or `MASK` |
| **Contextual grounding check** | Is the response *supported by the retrieved source* and *relevant to the query*? | **Output only** | `grounding` threshold (0.0–0.99) + `relevance` threshold; requires `grounding_source` + `query` in the API call |
| **Automated Reasoning check** | Is the statement *consistent with formally expressed rules*? | **Output only** | Natural-language policies translated to formal logic; returns a confidence score/threshold |

> **Gotcha:** The **prompt-attack** filter lives inside **content filters** and can only be applied to **input**. It must be set to at least **MEDIUM** strength to detect; `NONE` disables detection entirely.

## Applying Guardrails — Configuration Nuances

- **Versioning is mandatory for production:** `CreateGuardrail` → `CreateGuardrailVersion` → `CreateGuardrailAlias`. `DRAFT` is **mutable**; pin a **numbered version or alias** in production.
- **Reference in the call:** `InvokeModel` / `Converse` / `InvokeAgent` / `RetrieveAndGenerate` accept `guardrailIdentifier` + `guardrailVersion`.
- **`ApplyGuardrail` API:** evaluates text **independently of model invocation** — the key exam point. Use it to enforce policy on **non-Bedrock / self-hosted models** (e.g., a SageMaker endpoint), to **pre-screen user input** before routing, or to build a **centralized policy enforcement layer**. Consumes no model tokens.
- **Streaming:** `ConverseStream` supports guardrails on both input and output. `InvokeModelWithResponseStream` has **limited output filtering** — prefer `ConverseStream` when output must be guarded in a streaming app.
- **`trace` parameter:** returns per-policy assessments (which policy fired, confidence, action taken) — required for **debugging** a guardrail and for custom redaction workflows.
- **Region-scoped:** guardrails must be **recreated in every Region** you operate in. They are not global resources.

## Sensitive Data Protection Path

- **`MASK` vs `BLOCK`:** `MASK` substitutes a placeholder (e.g., `{NAME}`) and preserves conversational utility; `BLOCK` rejects the entire request/response. Use **MASK** for PII redaction, **BLOCK** for prohibited content.
- **Custom regex** handles domain-specific identifiers (account numbers, employee IDs) that built-in PII entities do not cover — the correct answer when a scenario names an internal identifier format.
- **End-to-end protection:** masking a response does **not** sanitize your own logs. Pair guardrails with **Bedrock model invocation logging** redaction and CloudWatch log data-protection policies, or the value is masked in the chat and **unmasked in the log**.

> **Gotcha:** A guardrail does not stop the model from being invoked, and it does not encrypt anything. If a scenario asks for "prevent exposure over the public internet," that is a **VPC interface endpoint**, not a guardrail.

## Decision Matrix — Which Safeguard?

| Requirement in the scenario | Correct control |
|---|---|
| Block profanity / a specific banned term | **Word filter** |
| Refuse a business subject (e.g., investment advice) | **Denied topic** |
| Block harmful categories (hate, violence, misconduct) | **Content filter** |
| Stop jailbreak / prompt injection | **Content filter → prompt attack** |
| Prevent account numbers / PII leaving the app | **Sensitive information filter** (MASK or BLOCK) |
| Stop hallucinated answers unsupported by RAG passages | **Contextual grounding check** |
| Enforce a regulatory rule statement-by-statement | **Automated Reasoning check** |
| Apply the same policy to a non-Bedrock model | **`ApplyGuardrail` API** |
| Keep invocation calls off the public internet | **VPC interface endpoint (PrivateLink)** |
| Know which principal invoked the model and when | **CloudTrail data events** |

**Common distractor traps:**
- **Denied topic vs. word filter:** denied topics are **semantic intent**; word filters are **literal string** matches. A scenario about "the model keeps discussing a competitor" → denied topic.
- **Contextual grounding vs. Automated Reasoning:** grounding = *supported by the retrieved source* (RAG); Automated Reasoning = *consistent with formal rules* (policy-bound answers). Both are **output-only**.
- **Guardrails vs. Amazon Macie:** Macie discovers/classifies sensitive data **at rest in S3**; guardrails protect content **in flight** at inference time.
- **Guardrails vs. Amazon Inspector / CodeGuru Security:** those scan **images and code** in the CI/CD pipeline, not runtime prompts.

## Security, IAM & Compliance

- **IAM actions:** `bedrock:CreateGuardrail`, `GetGuardrail`, `UpdateGuardrail`, `DeleteGuardrail`, `ListGuardrails`, `CreateGuardrailVersion`, **`bedrock:ApplyGuardrail`**.
- **Least privilege:** the invoking identity needs **both** `bedrock:InvokeModel` (or `Converse`) **and** guardrail permissions — granting one does not imply the other. Denied calls return `AccessDenied`; **do not widen the policy** to clear it — read the operation and resource named in the error.
- **Encryption:** guardrail configuration and Automated Reasoning policies support **customer managed KMS keys**. Key use is recorded, so decryption is attributable.
- **Production credential for FM access:** a **role with temporary STS credentials** (instance profile, ECS task role, Lambda execution role). Long-term Bedrock API keys are documented for **exploration/development only**; never bake keys into images or environment files — use **Secrets Manager** with rotation for the rare static secret.
- **Auditing:** guardrail configuration changes are **management events** (captured by default). Model **invocation** calls are **data events** — a trail created without extra configuration records **nothing** about them.

## Monitoring, Auditing & Troubleshooting

- **Three records, three questions:** CloudTrail activity = *who did it*; AWS Config = *what the resource looked like*; model invocation logs = *what went in and what came back*.
- **Guardrail observability:** enable **model invocation logging** to CloudWatch Logs/S3 to capture inputs, outputs, and **guardrail intervention** details; CloudWatch publishes guardrail invocation/intervention metrics and added **latency**.
- **Latency cost:** guardrails add processing time to every call. If a scenario is latency-sensitive, scope policies narrowly rather than disabling them.
- **Debugging workflow:** turn on `trace`, read which policy fired and its confidence, then adjust thresholds or the policy definition — do not disable the guardrail to make an error disappear.
- **Failure mode to expect:** a private subnet with no internet route fails to reach Bedrock → add an **interface endpoint**; the error is a **network** failure, not a guardrail or IAM denial.

> **Exam gotchas to memorize:** (1) Guardrails filter content — they never grant or deny model access. (2) Prompt-attack filtering is input-only and requires ≥ MEDIUM. (3) Contextual grounding and Automated Reasoning are **output-only**. (4) `DRAFT` is mutable — production pins a version/alias. (5) `ApplyGuardrail` extends policy to non-Bedrock models. (6) Masking output does not mask your logs.
