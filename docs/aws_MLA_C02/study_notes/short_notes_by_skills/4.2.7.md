# Skill 4.2.7: Evaluate Cost Implications of Using FMs for Inference in Production

## Task 4.2: Optimize and manage ML and AI infrastructure costs and performance

### Core Cost Model: What Are You Actually Paying For?

| Billing Dimension | Traditional ML (SageMaker Hosted) | FM Inference (Bedrock On-Demand) |
|---|---|---|
| **Unit charged** | Instance-hours (compute held) | Token count (input + output) |
| **Idle cost** | Yes — pay even with zero traffic | No — pay only when invoked |
| **Prediction cost driver** | Type/size of instance, count | Model size, prompt length, output cap |
| **Scale lever** | Instance count/family | Token volume, model tier, caching |

> **Exam Gotcha:** Applying endpoint levers (right-sizing, auto-scaling) to token-billed workloads does not reduce cost. Always identify the billing unit first.

---

### Bedrock Inference Modes: Cost Trade-offs

| Mode | Billing Basis | Best For | Anti-Pattern |
|---|---|---|---|
| **On-Demand** | Per-token (input/output) | Intermittent, variable, experimental traffic | Steady high-volume production with predictable load |
| **Provisioned Throughput** | Fixed hourly (model units reserved) | Consistent, predictable token throughput | Spiky or bursty traffic — underutilized reservation wastes spend |
| **Batch Inference** | Per-token, efficiency-priced | Async, latency-tolerant large workloads | Real-time interactive user-facing requests |

> **Exam Gotcha:** Provisioned Throughput is the cost commitment equivalent of Savings Plans — but for model units, not instance-hours. It requires a supported model and does NOT auto-scale.

---

### FM Cost Optimization Levers

| Lever | What It Reduces | Key Nuance |
|---|---|---|
| **Smaller model selection** | Per-token cost across ALL requests | Validate quality threshold before downgrading; "right-size the model, not the instance" |
| **Prompt trimming** | Input tokens per request | Remove redundant instructions, examples, context payload |
| **Output length cap** | Output tokens per request | Use `max_tokens`/`max_completion_tokens` parameter; lower = deterministic cost ceiling |
| **Prompt caching** | Reused input prefix token cost | Reduced rate for cached tokens, but cached token WRITES may cost more than uncached reads |
| **Context window pruning** | Total input token volume | No auto-pruning; you must actively limit what travels with each call |

#### Prompt Caching Rules (High-Yield Details)

> **Exam Gotcha:** Caching is not a free discount. Cached tokens bill at reduced read rate; writes may bill at a premium. A **minimum prefix length** is required. Any dynamic content in the prefix **invalidates the entire cache** on every request.

- **Static to front:** System instructions, tool schemas, few-shot examples FIRST
- **Dynamic to end:** User query, session-specific values LAST
- **Cache hit requires:** Exact sequence match from prompt start

### Cost Monitoring & Governance

| Tool / Practice | Purpose | Exam-Relevant Specifics |
|---|---|---|
| **CloudWatch** | Token usage metrics, dashboards | Monitor token usage beside invocation count to distinguish heavier prompts from more traffic |
| **AWS Budgets** | Threshold alerts (incl. forecasted) | Alert BEFORE threshold breached; supports SNS/email |
| **Cost Allocation Tags** | Attribute spend to team/model/env | Prerequisite for any meaningful cost attribution; without tags, only service-level totals visible |
| **Cost Explorer** | Historical & forecast reporting | Group/filter by tag, service, usage type; identifies cost driver |
| **Bedrock AgentCore Observability** | Per-invocation agent trace | Shows model calls, tool calls, memory ops separately |

---

### Agent Cost Amplification Pattern

> **Exam Gotcha:** A single user request to an agent typically produces MULTIPLE model invocations: planning call → tool call(s) → synthesis call. Cost per USER invocation is the metric to track, not per model call. Retry loops are silent cost multipliers.

**Vector database consideration:**
- Embedding computation cost scales with token volume, NOT number of documents
- Vector index storage costs scale with document count × dimension × precision
- Optimize: reduce dimensionality (PCA, smaller embedding models), prune obsolete vectors, batch embedding jobs

---

### Cost vs. Performance Trade-off Matrix

| Scenario | Cost-Optimized Choice | Performance Trade-off |
|---|---|---|
| Intermittent inference calls | On-Demand (per-token) | Cold-start latency possible (~seconds) |
| Steady stream, latency-tolerant | Batch inference (reduced token rates) | Poll-based response; not interactive |
| Consistent user-facing load | Provisioned Throughput | Fixed cost even if demand dips |
| Small model fleet, shared framework | Multi-model endpoint (SageMaker) | Model load latency for non-resident models |
| High-volume training only | SageMaker Savings Plans / Spot | Spot may interrupt — requires checkpointing |

### Template: FM Cost Evaluation Checklist

1. **Confirm billing mode:** On-demand token, provisioned throughput, or batch?
2. **Measure current token pattern:** Input vs. output ratio (heavy input = caching/trimming opportunity; heavy output = cap length)
3. **Evaluate model tier:** Is the larger model justified for task complexity?
4. **Assess traffic predictability:** Steady > provisioned; variable > on-demand
5. **Tag all resources:** Enables attribution before optimization
6. **Set budget alerts:** Forecast-based, not just actual-spend alerts
7. **Trace agent invocations:** AgentCore Observability for per-call breakdown
