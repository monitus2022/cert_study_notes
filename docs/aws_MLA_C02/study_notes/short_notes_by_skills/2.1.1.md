# Skill 2.1.1: Evaluate and select appropriate FMs from Amazon Bedrock based on task requirements and performance criteria

## Task 2.1: ML Model and Foundation Model (FM) Development - Choose appropriate modeling approaches for ML and AI solutions

---

## FM Selection Decision Matrix

| Selection Criteria | Primary Metrics | Evaluation Method | Bedrock Tooling |
|---|---|---|---|
| **Output Quality** | Accuracy, relevance, fluency | Comparative benchmarking | Bedrock Model Evaluation (automatic + human) |
| **Latency** | Time-to-first-token, total response time | Load testing with real payloads | CloudWatch metrics, Provisioned Throughput |
| **Cost** | $ per 1K tokens (input/output) | Monthly usage projections | Bedrock Pricing APIs, CloudWatch billing |
| **Domain Fit** | Terminology, reasoning depth | Custom eval prompts on domain corpus | Model Evaluation with curated datasets |
| **Context Limits** | Max tokens supported | Test with representative document lengths | Model spec sheets (e.g., Claude 200K) |

> **Hard Rule:** Provisioned Throughput on Bedrock is the ONLY way to meet hard latency SLAs at scale. On-demand InvokeModel and InvokeModelWithResponseStream do not guarantee throughput.

## Amazon Bedrock Model Families & Characteristics

| Model Family | Provider | Strengths | Best Fit | Key Distractors |
|---|---|---|---|---|
| **Claude (3.x)** | Anthropic | Long context (200K), reasoning, tool use | Document analysis, multi-step reasoning | Not the cheapest for simple classification |
| **Titan** | AWS | Cost-efficient, fine-tuning ready | Embeddings, text generation at scale | Weaker reasoning vs. Claude/Llama |
| **Llama 3.x** | Meta | Open-weight, customizable | On-prem parity, fine-tuning flexibility | Requires more prompt tuning |
| **Cohere Command** | Cohere | Strong on structured output, embeddings | Entity extraction, RAG summarization | Smaller ecosystem compared to Claude |
| **Mistral** | Mistral AI | Efficient, strong multilingual | European language tasks, edge deployments | Performance drops on large context |
| **AI21 Jurassic** | AI21 Labs | Long-form generation, factual writing | Content creation, narrative tasks | Higher cost per token than Titan |

> **Exam Gotcha:** Selecting "the largest/most powerful model" is a **distractor** when requirements mention cost controls or simple classification tasks. Smaller models (Titan, Llama 3 8B) often deliver similar accuracy at a fraction of cost.

## Core Bedrock APIs & Boto3 Nuances

### Invocation Patterns

| API Method | Use Case | Streaming? | Key Parameter Notes |
|---|---|---|---|
| **`InvokeModel`** | Single synchronous request | No | `body` format varies by provider (JSON vs. prompt strings) |
| **`InvokeModelWithResponseStream`** | Real-time token-by-token display | Yes | Requires chunk handling logic; lower perceived latency |
| **`Converse`** | Provider-agnostic chat API | Yes | Supports tool use, system prompts, multi-turn context |
| **`CreateModelInvocationJob`** | Batch processing (S3 input/output) | No | Async; required for large-scale evaluations |

### Key Boto3 Parameter Considerations

- **`inferenceConfig` vs. provider-specific params** — Use `maxTokens`, `temperature`, `topP` inside `inferenceConfig` when using `Converse` API; provider-specific bodies may use `max_tokens_to_sample`.
- **`system` vs. `messages`** — The `system` parameter sets behavior/guardrails; `messages` contain the conversation history.
- **`stopSequences`** — Control token generation halting to prevent hallucinations or runaway outputs.

## Model Evaluation Patterns

### Evaluation Workflow

```
1. Curate Golden Dataset (domain-representative prompts)
2. Choose Evaluation Mode:
   ├─ Automatic: ROUGE, BLEU, F1 (ground truth required)
   └─ Human: Likert scales, pairwise comparison (LLM-as-judge)
3. Run on Multiple Candidate Models
4. Compare Quality × Latency × Cost
5. Select Winner and Document Trade-offs
```

| Evaluation Type | When to Use | Bedrock Integration |
|---|---|---|
| **Automatic Metrics** | Established benchmarks, deterministic outputs | Bedrock Model Evaluation built-in scoring |
| **LLM-as-Judge** | Qualitative judgments (style, coherence) | Custom scoring prompts via Bedrock |
| **Human Review** | Safety-critical, subjective quality | Bedrock Model Evaluation human workflows (SageMaker Ground Truth) |
| **A/B Testing in Production** | Real-world usage patterns | Custom routing with API Gateway + Lambda |

> **Hard Rule:** Evaluation datasets **must** represent production data distribution. Evaluation on synthetic or mismatched data produces inflated or misleading performance metrics.

## Security & Compliance Configuration

| Requirement | Bedrock Configuration | Notes |
|---|---|---|
| **VPC Isolation** | Bedrock VPC interface endpoints | Private access without internet egress |
| **Data Encryption** | SSE-KMS for S3 data sources; TLS 1.2+ in transit | Bedrock does not train on your prompts/responses by default |
| **Model Invocation Logging** | Enable in Bedrock settings → CloudWatch/S3 | Captures full prompts, responses, token usage |
| **Cross-Region Redundancy** | Multi-region Bedrock endpoints | Not all models available in all regions |
| **Content Filtering** | Bedrock Guardrails | Apply before/after model invocation |

> **Exam Gotcha:** Bedrock **does not retain or store** your prompts and responses for model improvement by default, but you **must opt out explicitly** on some managed features. Logging should be consciously enabled for compliance.

## Cost Optimization Strategies

| Strategy | Use Case | Implementation |
|---|---|---|
| **Model Cascade / Routing** | Route simple requests to small models | API Gateway + Lambda series, or Bedrock Model Invocation policies |
| **Batch Mode** | Non-urgent processing | `CreateModelInvocationJob` (up to 50K requests/job) |
| **Provisioned Throughput** | Predictable high-volume, low-latency | Commit hourly units; best for production workloads |
| **Caching Common Responses** | Repeat queries | ElastiCache or DAX in front of Bedrock calls |
| **Prompt Compression** | Reduce input tokens | Summarize history, truncate retrieved docs |

---

## Common Anti-Patterns & Distractor Traps

1. **Building custom models when Bedrock FMs suffice** — Managed FMs remove infrastructure overhead, access latency-tuning options, and offer built-in evaluation tooling.
2. **Choosing a large model "for safety"** — Without benchmarked evidence, smaller models often meet quality requirements at 10–20× lower cost.
3. **Ignoring tokenization differences** — The same input can produce different token counts across models, invalidating per-request cost comparisons if not normalized.
4. **Fine-tuning without exhausting prompt engineering** — Prompt-based optimizations (few-shot examples, detailed system prompts) resolve most terminology/format gaps at zero additional cost.
5. **Treating model selection as a one-time decision** — Requirements evolve; Bedrock's multi-model API facilitates A/B testing and gradual model migrations without app rewrites.
