# Skill 2.3.7: Implement Integrated Human Evaluation Frameworks
## Task 2.3: ML Model and Foundation Model (FM) Development - Analyze and Evaluate Performance

---

### Core Objective & Framework Architecture

**Primary Business Objective:** Assemble a defensible, multi-layered evaluation system combining programmatic scoring, LLM-as-judge, and human raters to validate generative AI outputs where single-metric evaluation is insufficient.

**Three-Layer Evaluation Framework:**

| Layer | Mechanism | Best For | Limitation |
|-------|-----------|----------|------------|
| **Programmatic** | ROUGE, BLEU, BERTScore, semantic similarity | High-volume, reproducible scoring | Misses nuance, style, factual grounding |
| **LLM-as-Judge** | Amazon Bedrock evaluations with judge model | Scalable quality scoring with reasoning | Judge bias, prompt sensitivity |
| **Human-in-the-Loop** | SageMaker Ground Truth / A2I / Bedrock human evaluation jobs | Consequential outputs, final validation | Cost, latency, inter-rater variance |

> **Exam Gotcha:** Human-based Amazon Bedrock evaluation jobs created via console require browser-facing display; programmatic evaluation jobs have no display requirement.

### Amazon Bedrock Human Evaluation Workflows

**API & Console Parameters:**

| Parameter | Required | Notes |
|-----------|----------|-------|
| `evaluationConfig.mode` | ✅ | `HUMAN` (vs `AUTOMATIC`) |
| `evaluationConfig.humanWorkflowConfig` | ✅ | Defines worker type, task template |
| `workerType` | ✅ | `PUBLIC` (MTurk), `PRIVATE` (own workforce), `VENDOR` |
| `taskTemplate` | ✅ | Custom UI for prompt/response presentation |
| `ratingMethod` | ✅ | Thumbs up/down, Likert scale, custom rubric |

**Boto3 Core Operations:**
```python
# Create human evaluation job
bedrock.create_evaluation_job(
    jobName="human-eval-medical-qa",
    roleArn="arn:aws:iam::...",
    evaluationConfig={
        "mode": "HUMAN",
        "humanWorkflowConfig": {"workerType": "PRIVATE"}
    }
)

# Required IAM role permissions
# bedrock:CreateEvaluationJob
# s3:GetObject on input dataset
# s3:PutObject on output bucket
```

> **Hard Rule:** Human evaluation jobs require S3 locations for both input prompts AND output ratings. Worker identities are managed via Amazon SageMaker Ground Truth workforce or AWS Marketplace vendor pools.

### Human-in-the-Loop (HITL) Integration Patterns

**SageMaker Ground Truth vs Augmented AI (A2I):**

| Feature | Ground Truth | A2I |
|---------|--------------|-----|
| **Purpose** | Labeling workflows, eval datasets | UI review in inference pipelines |
| **Trigger** | Batch labeling job | Lambda > SDK `StartHumanLoop` |
| **Output** | Labeled dataset in S3 | Review outcome + model output |
| **Workteam** | Private / vendor / MTurk | Same workteam integration |
| **Task Template** | Custom HTML/Crowd templates | A2I task UI (built-in or custom) |

**A2I Flow Configuration:**
```
Model Inference → HumanLoopConfig → SageMaker A2I → Workteam review → S3 output → App response
```

> **Exam Gotcha:** A2I human loops must be completed within a time limit. Unreviewed tasks route to `ConditionFailed` result. Configure `HumanLoopActivationConditions` in Flow Definition JSON (e.g., confidence < 0.7 triggers review).

### Text Generation Quality Assessment Metrics

**Overlap vs Embedding vs Semantic Metrics Decision Matrix:**

| Metric | Type | Measures | Use When | Distractor Trap |
|--------|------|----------|----------|-----------------|
| **BLEU** | N-gram precision overlap | Exact phrase overlap | Machine translation | Penalizes valid paraphrases; precision-biased |
| **ROUGE** | N-gram recall overlap | Coverage of reference content | Summarization | Misses semantic equivalence |
| **BERTScore** | Contextual embedding similarity | Semantic meaning alignment | Open-ended generation | Computationally heavier |
| **Semantic Similarity** | Embedding cosine distance | Meaning equivalence | Paraphrase evaluation | Requires good embedding model |

**RAG-Specific Evaluation Triad:**

| Metric | Question Answered | Failure Signal |
|--------|-------------------|----------------|
| **Faithfulness** | Is answer grounded in retrieved context? | Hallucinated facts |
| **Answer Relevance** | Does answer address the query? | Off-topic responses |
| **Context Recall** | Did retriever fetch all relevant chunks? | Missing facts despite fluent output |

> **Exam Gotcha:** A fluent answer that omits facts from source documents is a **retrieval failure**, not a generation failure. Measure retrieval (context recall/precision) separately from generation (faithfulness/relevance).

### LLM-as-Judge Configuration

**Judge Model Setup (Bedrock Evaluations):**

| Parameter | Value / Options | Notes |
|-----------|-----------------|-------|
| `metricType` | `GENERATIVE` | For LLM-judged quality |
| `judgeModelId` | e.g., `anthropic.claude-3-sonnet` | Judge ≠ evaluated model |
| `promptDataset` | JSONL with `prompt`, `referenceResponse`, `category` | Reference optional for judge |
| `autoGenerationMetrics` | `Faithfulness`, `AnswerRelevance`, `Toxicity` | Only for automatic eval |

**Judge Prompt Design Principles:**
- **Provide rubric** with explicit scoring criteria (1-5 scale with anchors)
- **Require reasoning** before final score ("explain then score")
- **Calibrate** judge against human ratings on sample set (minimum ~50-100 examples)
- **Debias** by randomizing model response order in pairwise comparisons

> **Hard Rule:** Judge model bias is a known failure mode. Position bias (preferring first response) and self-preference bias (judge favoring its own architecture) require mitigation via response order randomization and diverse judge models.

### Security, Compliance & Workforce Management

**IAM Role Requirements for Human Evaluation:**

```
Required Permissions:
- bedrock:CreateEvaluationJob
- bedrock:GetEvaluationJob
- s3:GetObject (input dataset bucket)
- s3:PutObject (output ratings bucket)
- groundtruth:CreateWorkteam (if private workforce)
```

**Workteam Configuration:**

| Workforce Type | Setup Requirement | Use Case |
|----------------|-------------------|----------|
| **Private** | Cognito user pool / existing directory | Internal SMEs, compliance |
| **Vendor** | AWS Marketplace vendor selection | Domain-specific expertise |
| **Public (MTurk)** | Open marketplace workers | High-volume, generic tasks |

> **Exam Gotcha:** SageMaker Ground Truth private workforces use **Amazon Cognito user pools**. Workers must verify email before joining. CloudWatch metrics track `TasksAvailable`, `TasksReturned`, `TasksRejected`.

**KMS Encryption:**
- ● Input datasets: SSE-KMS or SSE-S3 at rest
- ● Human review responses: Encrypted in S3; KMS key must be accessible to Ground Truth/A2I service role
- ● In-transit: TLS 1.2+ enforced

**VPC Considerations:**
- ● A2I and Ground Truth can operate with VPC endpoints for S3, SageMaker, and Bedrock
- ● Workteam UI is public-facing; workers require internet access unless using private workforce with VPN/Direct Connect

### Anti-Patterns & Common Distractor Traps

| Anti-Pattern | Why It Fails | Correct Approach |
|--------------|--------------|------------------|
| Relying solely on BLEU/ROUGE for open-ended generation | Penalizes valid paraphrases | Combine overlap + embedding + LLM-judge |
| Using human raters for all outputs | Cost-prohibitive, latency | Tiered: programmatic → LLM-judge → human only for edge cases |
| Treating RAG evaluation as single end-to-end score | Cannot isolate retrieval vs generation failures | Split metrics: context recall vs faithfulness |
| Single human rater without calibration | Subjective, no reliability measure | Multiple raters + inter-rater agreement (Cohen's Kappa, Fleiss' Kappa) |
| Deploying A2I without `ConditionFailed` handling | Requests hang when no review completes | Route to fallback response or retry logic |
| Using judge model same as evaluated model | Self-preference bias | Use different model families |

> **Critical Exam Distinction:** A/B testing (split traffic) ≠ Shadow testing (copy traffic) ≠ Human evaluation (offline rating). Human evaluation is **asynchronous offline assessment**, never real-time serving.

### Monitoring Human Evaluation Systems

**CloudWatch Metrics to Track:**

| Metric | What It Reveals |
|--------|-----------------|
| `HumanLoopTasksSubmitted` | Volume entering review |
| `HumanLoopTasksCompleted` | Reviewer throughput |
| `TasksAvailable` (Ground Truth) | Backlog / SLA risk |
| `Inter-rater agreement` | Annotator consistency / training need |
| `TasksRejected` | Template or instruction issues |

**Quality Gates in Production ML Pipelines:**
1. **Pre-deployment:** Human eval on edge cases + adversarial samples
2. **Shadow testing:** Compare candidate vs production on live traffic
3. **Post-deployment:** Drift detection triggers re-evaluation workflow
4. **Continuous feedback:** User-reported quality issues feed back into HITL review queue

### Integration with SageMaker Pipelines

**HITL as Pipeline Step:**
```
ProcessingStep (score batch) 
  → ConditionStep (check confidence threshold) 
    → LambdaStep (trigger A2I human loop) 
      → WaitStep (poll for completion) 
        → ProcessingStep (merge human labels with predictions)
```

> **Exam Gotcha:** SageMaker Pipelines does not natively wait for human review. Use `WaitStep` with polling or EventBridge pattern to trigger continuation after A2I `HumanLoopCompleted` event.
