# Skill 2.1.4: Evaluate Tradeoffs Between Custom Solutions, Managed Services, Pre-trained Models, and FMs

## Task 2.1: ML Model and FM Development - Choose Appropriate Modeling Approaches

---

## The Core Decision Framework

| Decision Point | Primary Question | Decision Drives |
|:---|:---|:---|
| **Does this need ML at all?** | Is logic fixed/rule-based? | Rule vs. Model selection |
| **Where does the capability live?** | In your data or in pre-trained weights? | Train vs. Select |
| **Is this a solved problem?** | Does AWS already offer this as a service? | Managed Service vs. Build |
| **Can prompting close the gap?** | Has prompt engineering been exhausted? | Prompt vs. Fine-tune |

---

## 4-Tier Solution Hierarchy

| Tier | Solution Type | When to Use | AWS Implementation | Cost Profile |
|:---|:---|:---|:---|:---|
| **0** | **Fixed Rules / Code** | Deterministic logic, auditability critical | Lambda, plain conditionals | Lowest |
| **1** | **Managed AI Service** | Solved task (OCR, transcription, images) | Textract, Rekognition, Comprehend, Transcribe | Pay-per-call |
| **2** | **Custom ML Model** | Proprietary tabular/structured data patterns | SageMaker built-in algorithms (XGBoost) | Medium-High |
| **3** | **Foundation Model** | General language, generation, reasoning | Amazon Bedrock + Prompt Engineering | Variable (token-based) |

> **Exam Gotcha:** Choosing a more complex tier than necessary is a common anti-pattern. The exam rewards selecting the *simplest sufficient* solution.

---

## Managed AI Services Quick-Match Matrix

| Service | Solves | Use When |
|:---|:---|:---|
| **Amazon Textract** | Extracts text, forms, tables from scans/PDFs | Invoices, medical forms, tax documents |
| **Amazon Rekognition** | Image/video analysis: objects, faces, moderation | Content moderation, identity verification |
| **Amazon Comprehend** | NLP: entities, key phrases, sentiment | Customer feedback analysis, PII detection (Comprehend Medical) |
| **Amazon Transcribe** | Speech-to-text | Call center analytics, meeting transcription |

> **Anti-Pattern:** Training a custom CV model for standard invoice extraction when Textract's `AnalyzeExpense` API handles it off-the-shelf.

## Foundation Model Selection Criteria (Amazon Bedrock)

| Criterion | What to Evaluate | Bedrock Capability |
|:---|:---|:---|
| **Output Quality** | Accuracy, relevance, domain fit | Model evaluation jobs, `bedrock:EvaluateModel` |
| **Inference Latency** | Time-to-first-token, tokens/sec | Cross-region inference profiles, model choice |
| **Cost Per Request** | Token pricing, output length | Different models per tier (Titan vs. Claude) |

**Key API Parameters:**
- `max_tokens` — trims output length, not reasoning quality
- `temperature` — lower = deterministic; higher = creative
- `stop_sequences` — control response boundaries

## Prompt First, Fine-Tune Second

```bash
Prompt Engineering → Evaluate → Gap Persists? → Fine-Tune
        ↓                            ↑
   Immediate change            Accept training overhead:
                                • Data preparation (JSONL)
                                • GPU compute cost
                                • Version management
```

**Fine-tuning triggers (all must be true):**
- Prompt instructions + few-shot examples consistently fail evaluations
- Task requires specialized domain vocabulary or formatting adherence
- You have labeled input-output pairs ready (SFT) or reward functions (RLHF)

> **Critical Rule:** Fine-tuning writes behavior into weights. Retrieval keeps content outside the model. Choose based on:
> - **Content changes frequently** → RAG/Knowledge Bases (minutes to update)
> - **Behavior/format/domain style is stable** → Fine-tune (weights persist)
> - **Need source citations** → RAG (retrieved chunks have metadata)

---

## RAG vs. Fine-Tuning Decision Matrix

| Requirement | RAG / Knowledge Bases | Fine-Tuning |
|:---|:---|:---|
| **Document updates within minutes** | ✅ Re-ingest to vector store | ❌ Requires new training job |
| **Source citations required** | ✅ Chunk metadata carries attribution | ❌ No citation mechanism |
| **Whole-document synthesis** | ✅ Better fit | ❌ Weaker fit |
| **Enforce specific output format** | ⚠️ Prompt-dependent | ✅ Weight-level consistency |
| **Domain-specific terminology** | ⚠️ Via prompt examples | ✅ Strongest |
| **Catastrophic forgetting risk** | ✅ No weight modification | ⚠️ Present (defend with mixed data) |

## Custom ML vs. Foundation Model Tradeoffs

| Factor | Custom ML (SageMaker) | Foundation Model (Bedrock) |
|:---|:---|:---|
| **Where capability lives** | In proprietary training data | In pre-existing model weights |
| **Interpretability** | High (tree-based, SHAP, Clarify) | Low (black box reasoning) |
| **Data requirement** | Labeled historical data (tabular/structured) | Few examples in prompt / zero-shot |
| **Training time** | Hours-days | None (token-based inference) |
| **Latency** | Optimizable (dynamic batching, multi-model endpoints) | Variable by model size |
| **Cost model** | Instance-hour based; predictable | Token-based; scales with usage |
| **Typical use case** | Forecasts, fraud detection, churn prediction | Summarization, generation, reasoning |

> **Interpretability Constraint:** Finance/regulated stakeholders demanding explainable predictions force custom ML with interpretable algorithms over FMs.

---

## SageMaker AI Options Hierarchy

| Option | When | Tradeoff |
|:---|:---|:---|
| **Built-in Algorithm** | Classic problem (XGBoost, Linear Learner) | Less flexible, zero container maintenance |
| **Training Script (BYOM)** | Custom logic needed | Full control, container management overhead |
| **JumpStart** | Start from pre-trained baseline | Faster iteration, less customization |
| **Autopilot** | AutoML; no algorithm preference | Black box, limited tuning control |

---

## Anti-Patterns (Exam Traps)

| Trap | Why It's Wrong |
|:---|:---|
| **Fine-tuning before prompting** | Ignoring zero-cost improvement; accepts unnecessary overhead |
| **Training custom model for solved task** | Rebuilding what Textract/Rekognition already provides |
| **Using FM for tabular forecasting** | Context window limits; tabular data doesn't fit token paradigm well |
| **Writing rules for dynamic patterns** | Fixed logic cannot capture seasonality, promotions, local variance |
| **Using RAG for stable format requirements** | Retrieval doesn't change output behavior; fine-tune does |
| **Missing latency checks** | Selection criteria are constraints, not afterthoughts |

## Decision Flow Cheatsheet

```
Problem Statement
        │
        ├─ Logic is fixed? ──────────────→ Write a rule (Lambda)
        │
        ├─ AWS service already does this? → Managed AI Service
        │
        ├─ Patterns in your structured data? → Custom ML (SageMaker)
        │
        ├─ General language/generation capability? → FM via Bedrock
        │       │
        │       ├─ Prompt works? → Done (evaluate, deploy)
        │       │
        │       └─ Prompt fails consistently? → Fine-tune or RAG
        │               │
        │               ├─ Content changes frequently → RAG + Knowledge Bases
        │               └─ Stable behavior/format gap → Supervised Fine-Tune
        │
        └─ Hybrid needed? → Combine RAG + fine-tuned model
```
