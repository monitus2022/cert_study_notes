# Skill 4.2.9: Manage FM Inference Costs with Usage Optimization

## Task 4.2: Optimize and manage ML and AI infrastructure costs and performance

---

## Core Concept: What Are You Actually Paying For?

| Billing Model | Unit Charged | Optimization Levers |
|---|---|---|
| **SageMaker Real-Time Endpoint** | Instance hours (provisioned compute) | Right-size, autoscale, MMEs, Savings Plans |
| **Amazon Bedrock On-Demand** | Input + Output tokens | Model selection, prompt discipline, caching, batch |
| **Amazon Bedrock Provisioned Throughput** | Fixed hourly model units (reserved) | Commit only for predictable high-volume baselines |
| **Agents** | Amplified tokens (planning + tools + synthesis per invocation) | Cache tool schemas, limit retry loops, watch cost/invocation |

> **Exam Gotcha:** Applying endpoint levers to a Bedrock bill optimizes nothing. Right-sizing instances does not reduce token spend. The first step is always identifying the billing driver.

---

## FM Inference Cost Levers (Ranked by Impact)

| Lever | What It Does | When It Fails / Distractor Trap |
|---|---|---|
| **Model selection** | Smaller FM = lower cost per token on every request | Don't downsize if quality SLA breaks—validate with eval metrics first |
| **Prompt discipline** | Shorten system instructions, trim context, cap `max_tokens` output | Output caps too low truncate valid responses; balance UX vs. cost |
| **Prompt caching** | Reuses KV-cache for cached token prefixes at reduced rate | Dynamic content in prefix invalidates cache (static first, dynamic last) |
| **Batch inference** | Process async jobs at ~50% discount vs. on-demand | Only for delay-tolerant workloads; not for interactive traffic |
| **Provisioned Throughput** | Fixed hourly rate for reserved model units | No savings for variable/spiky traffic—on-demand is cheaper |

### Prompt Caching Nuances (High-Yield Exam Detail)

- **Cached tokens** are billed at a reduced rate vs. uncached input tokens.
- **Cache writes** may be billed higher than uncached input tokens (model-dependent).
- **Minimum prefix length** required to create a checkpoint (e.g., 1,024 tokens on some models).
- **Cache TTL** typically 5 minutes to 1 hour of inactivity (model-specific).
- **Invalidation triggers:** Any dynamic content mixed into or before the prefix, or any change to the prefix sequence.
- **Best practice:** Static content (system prompts, tool schemas, few-shot examples) at the start; dynamic user input at the end.

## Agent Cost Patterns (Amplification Model)

> **Exam Gotcha:** A single agent invocation may produce 3–10+ model calls (planning → tool calls → synthesis). Cost per invocation—not per user request—is the metric to monitor.

| Agent Component | Cost Driver | Optimization |
|---|---|---|
| Planning/Orchestration call | Full system prompt + tool schemas | Cache the orchestration prefix (tool schemas are static) |
| Tool calls | Tool input/output tokens + execution cost | Minify tool responses; return only necessary fields |
| Retrieval step | Embedding computation + vector DB storage | Batch embeddings; use dimension reduction if quality holds |
| Synthesis call | Accumulated context from all steps | Truncate intermediate context; cap final output |
| Retry loops | Hidden amplification on failures | Set max retries; use exponential backoff with jitter |

**Monitoring:** Use **Amazon Bedrock AgentCore Observability** to trace per-invocation token consumption, tool call counts, and memory operations—not just account-level totals.

## Cost Governance Stack

| Tool | Purpose | Key Setup Parameter |
|---|---|---|
| **AWS Budgets** | Alert before forecasted spend passes threshold | Set **forecasted** alerts (not just actual) |
| **Cost Allocation Tags** | Attribute spend to model/team/environment | Must be activated in Billing Console before they appear in Cost Explorer |
| **CloudWatch Metrics** | Token usage beside invocation count | Distinguishes "more traffic" vs. "heavier prompts" |
| **AWS Cost Explorer** | Identify cost driver (filter by usage type, tag) | No alerting—analysis only |

> **Exam Gotcha:** AWS Budgets is the only service among the four that sends alerts. Cost Explorer visualizes; Trusted Advisor surfaces idle resources; X-Ray traces latency.

## Decision Matrix: Bedrock Capacity Modes

| Scenario | Mode | Rationale |
|---|---|---|
| Interactive chatbot, unpredictable traffic | **On-Demand** | Pay per token; no upfront commitment |
| High-volume, steady year-round production | **Provisioned Throughput** | Fixed hourly rate; predictable billing |
| Document processing, data labeling, offline jobs | **Batch Inference** | ~50% discount; async queue, 24-hour window |
| Experimental / prototype | **On-Demand** | No minimum commitment |

## Anti-Patterns & Distractor Traps

- **❌ Autoscaling a Bedrock endpoint:** Bedrock manages capacity; autoscaling is a SageMaker concept.
- **❌ Compute Savings Plans for SageMaker endpoints:** Only applies to EC2, Lambda, Fargate. SageMaker requires **SageMaker AI Savings Plans**.
- **❌ Moving a busy daytime endpoint to async inference:** Async is for large payloads (up to 1GB) or long processing, not diurnal traffic patterns—autoscale instead.
- **❌ Placing dynamic variables early in prompt prefix:** Invalidates caching; savings never materialize.
- **❌ Treating spot capacity as a serving baseline:** Spot is for interruptible workloads (checkpointed training), not inference SLAs.

## Quick Recall Chain

1. **Question:** What am I actually paying for?
2. **Endpoint bill** → Compute hours → Right-size / autoscale / Savings Plans.
3. **Bedrock bill** → Tokens → Model selection / prompt discipline / caching / provisioned throughput.
4. **Agent bill** → Amplified tokens → Cache orchestration prefixes / minify tool responses / limit retries.
