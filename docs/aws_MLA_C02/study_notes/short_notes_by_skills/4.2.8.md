# Skill 4.2.8: Monitor agent resource consumption patterns

## Task 4.2: Operating, Monitoring, and Securing ML and AI Solutions - Optimize and manage ML and AI infrastructure costs and performance

---

## Core Concept & Primary Business Objective

**Agent resource consumption monitoring** answers: *"How many downstream calls does one agent invocation trigger?"*

A single user request to an agent (e.g., Amazon Bedrock Agents) amplifies into **multiple billable operations**:

```
User Request
    ├── Planning/Orchestration call (LLM tokens)
    ├── Tool call 1 (Lambda, API, Knowledge Base retrieval)
    ├── Tool call 2 (additional model inference)
    ├── Memory read/write operations
    └── Synthesis/final response call (LLM tokens)
```

> **Exam Gotcha:** Agent cost is **amplification, not a single charge**. One user request can generate 5–15+ model calls and multiple tool invocations. Monitoring must be **per invocation**, not per account aggregate.

---

## Key Monitoring Tools & Their Roles

| Tool | What It Captures | Agent-Specific Value |
|---|---|---|
| **Amazon Bedrock AgentCore Observability** | Per-invocation trace of agent orchestration: inference calls, tool invocations, memory operations, guardrail evaluations | Primary tool for agent consumption visibility |
| **Amazon CloudWatch Metrics** | Aggregate token counts, invocation counts, latency percentiles, error rates | Trending and alerting at scale |
| **AWS X-Ray** | Distributed trace across components (agent → Lambda → KB → model) | Attribute latency to a specific component |
| **CloudWatch Logs / Insights** | Structured agent trace logs, tool call payloads | Debugging retry loops and tool failures |
| **AWS Cost Explorer (with tags)** | Spend per agent, per model, per team attribution | Cost driver identification |

## Bedrock AgentCore Observability: Critical Details

> **Exam Gotcha:** AgentCore Observability is **disabled by default** for Bedrock Agents. You must enable it explicitly at agent creation or update time to capture trace data.

| Setting | Options / Notes |
|---|---|
| **Trace Capture** | Enabled/Disabled per agent |
| **Destination** | CloudWatch Logs (default), Amazon S3, or both |
| **Data Captured** | Model invocation inputs/outputs, tool call params, memory ops, guardrail results |
| **Retention** | CloudWatch Logs retention policy (default: never expire — set explicit retention to control storage cost) |
| **PII Handling** | Trace data may contain prompt content and tool arguments — constrain IAM read access tightly |

### Enabled Trace Event Types

**Observability event types captured per invocation:**
- `PRE_PROCESSING` — input classification and routing decisions
- `ORCHESTRATION` — planning, tool selection, reasoning tokens
- `KNOWLEDGE_BASE` — retrieval queries and returned chunks
- `ACTION_GROUP` — Lambda/API tool execution
- `POST_PROCESSING` — final response synthesis
- `GUARDRAIL` — content filter evaluations (billed separately when invoked)

## Metrics to Monitor Per Invocation

| Metric | What It Detects | Action Signal |
|---|---|---|
| **Model calls per user request** | Orchestration complexity, retry storms | Investigate planning prompt efficiency, tool batching |
| **Token usage per invocation** (input + output) | Prompt bloat, context window overrun | Trim system prompts, cap tool result lengths |
| **Tool call count and latency** | External API dependency, N+1 query patterns | Parallelize tool calls, cache tool responses |
| **Retry loops (same action repeated)** | **Silent cost amplifier** — bill grows with no traffic change | Fix error handling, validate tool inputs |
| **Memory operation count** | Session state churn, oversized memory payloads | Reduce memory write frequency, prune session data |
| **Knowledge base retrieval token volume** | Over-fetching context, broad embeddings | Tighten retrieval filters, reduce chunk size |

## Security & Compliance for Agent Monitoring

| Requirement | Implementation |
|---|---|
| **Least-privilege IAM role for observability** | `bedrock:GetAgentTrace` only on specific agent ARNs |
| **Trace data encryption at rest** | CloudWatch Logs default encryption or customer-managed KMS key |
| **Trace data encryption in transit** | TLS via AWS API endpoints (mandatory) |
| **VPC Endpoint for observability write path** | Interface VPC endpoints for CloudWatch Logs when agent runs in VPC |
| **PII in trace payloads** | Use CloudWatch Logs **data protection policies** to detect/mask sensitive data |
| **Cross-account trace access** | CloudWatch Logs cross-account subscriptions with KMS key sharing |

> **Exam Gotcha:** Trace data contains full model inputs, tool arguments, and retrieved context. This is **not just operational data** — it may include user PII, proprietary prompt engineering, or sensitive knowledge base content. IAM access must be restricted to debugging roles only.

## Cost Attribution for Agents

| Tagging Strategy | Tag Key Example | Purpose |
|---|---|---|
| **Per agent** | `agent-id` or `workload:agent-name` | Isolate spend per agent |
| **Per user feature** | `feature:summarization` | Attribute agent cost to business function |
| **Per environment** | `environment:prod` | Separate dev experimentation from production |
| **Per team** | `team:fraud-detection` | Chargeback / showback |

**Enable cost allocation tags on agent resources:** Bedrock agents, Lambda functions invoked as tools, knowledge base OpenSearch Serverless collections, and CloudWatch Logs groups for trace storage.

## Common Distractors & Anti-Patterns

| Anti-Pattern | Why It's Wrong | Correct Pattern |
|---|---|---|
| **Monitoring only aggregate token spend** | Hides per-invocation amplification — 10x traffic increase may be invisible if prompt discipline improves | Track **tokens per invocation** alongside total tokens |
| **Treating agent cost as model cost only** | Tool calls (Lambda invocations, KB retrievals) are separately billed | Monitor **total cost per invocation** across all AWS service calls |
| **Keeping trace logging on indefinitely** | CloudWatch Logs ingestion and storage add continuous cost | Set retention policies, sample traces in high-traffic prod |
| **Applying endpoint auto-scaling logic to agents** | Agent serves no persistent instances; cost is per call | Use prompt discipline, tool call optimization, model selection |
| **Ignoring retry loops** | A failed tool call with infinite retry burns tokens silently | Set max retry thresholds in agent configuration |

## Quick Reference: Cost Amplification Example

| Component | Calls per User Request | Bill Impact |
|---|---|---|
| Orchestration (planning) | 1–2 | Input + output tokens on main model |
| Knowledge base retrieval | 1–3 | KB query cost + retrieval token input |
| Action group (Lambda) | 1–5 | Lambda invocations + duration |
| Tool response synthesis | 1–2 | Input tokens (tool results) + output tokens |
| Final response | 1 | Output tokens |
| **Total per user request** | **5–13+ downstream calls** | **Multiply by MAU for monthly cost** |

> **Exam Gotcha:** Bedrock Agents **does not bill for agent orchestration itself** — you pay for the underlying model calls, tool invocations (Lambda/API), knowledge base retrievals, and guardrail evaluations. Optimizing orchestration reduces underlying billable calls.

## Optimization Checklist

**Reduce model calls per invocation:**
- Move static instructions into system prompt (not repeated per tool call)
- Batch multiple tool operations into single action group execution
- Use agent memory efficiently — avoid re-fetching context already in session

**Reduce token consumption per call:**
- Cap tool result length returned to orchestration model
- Trim retrieved knowledge base chunks (smaller chunk size = fewer input tokens)
- Set `maxTokens` response limits on synthesis call

**Reduce tool call cost:**
- Use short-lived Lambda functions (sub-second where possible)
- Cache repetitive tool responses (e.g., policy lookups) with short TTL
- Parallelize independent tool calls in orchestration prompt instructions

**Monitor proactively:**
- Set CloudWatch alarms on **tokens per invocation** and **retry loop detection**
- Alert when agent trace shows >X model calls per request
- Track cost per invocation as a primary dashboard metric
