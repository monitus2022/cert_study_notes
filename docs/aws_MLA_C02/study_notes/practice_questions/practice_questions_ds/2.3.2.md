### Question 1 - Establishing Model Performance Baselines with SageMaker Model Monitor

A financial services company has deployed a fraud detection model on **Amazon SageMaker** to score real-time credit card transactions. The compliance team requires the ML engineering team to track model quality over time and detect when prediction accuracy degrades.

The team wants to implement a solution with **minimal operational overhead** that automatically captures ground truth labels from a post-transaction database, compares them against model predictions, and generates alerts when model accuracy drops below a configured threshold.

Which **ONE** approach should the ML engineer implement?

* **A)** Deploy the model to a SageMaker endpoint and enable **SageMaker Model Monitor** with a **model quality monitoring** schedule. Configure the monitoring job to merge inference inputs with ground truth labels from Amazon S3, compute accuracy metrics against a stored baseline, and publish violations to Amazon CloudWatch alarms.

* **B)** Create an AWS Lambda function that runs every hour, queries the post-transaction database, manually computes precision and recall using scikit-learn, and writes the results to a custom DynamoDB table. Configure a CloudWatch alarm on the DynamoDB metric.

* **C)** Enable **SageMaker Model Monitor data quality monitoring** to track drift in the input feature distribution. Set up a CloudWatch alarm that triggers when the Kullback-Leibler divergence exceeds a static threshold.

* **D)** Use **Amazon Bedrock evaluations** with a human-based evaluation job to have fraud analysts manually review sampled predictions weekly and record their judgments in a CSV file uploaded to S3.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** SageMaker Model Monitor's model quality monitoring job is purpose-built for this use case. It automatically merges captured inference data with ground truth labels (provided via S3), computes standard classification metrics (accuracy, precision, recall, F1, AUC), compares them against a statically computed baseline (from a baseline job run on a known-good dataset), and emits CloudWatch metrics that can trigger alarms when violations occur. This meets the "minimal operational overhead" constraint because Model Monitor is a fully managed service.

    #### Distractor Analysis
    * **B is Incorrect:** While functionally possible, building a custom Lambda function with manual metric computation introduces significant operational overhead (code maintenance, error handling, scheduling, state management) compared to Model Monitor's native capabilities. The question explicitly requires minimal operational overhead.
    * **C is Incorrect:** Data quality monitoring detects drift in the *input feature distribution* (e.g., new categories, missing values, statistical shifts), not degradation in *prediction accuracy*. The requirement is specifically about tracking model quality against ground truth labels.
    * **D is Incorrect:** Amazon Bedrock evaluations is designed for evaluating generative AI models (LLMs), not traditional ML classification models like fraud detection. Additionally, human-based evaluation jobs introduce manual overhead and are not automated. The scenario is about a traditional supervised learning model, not generative AI.

    > **Key Takeaway:** For traditional ML models deployed on SageMaker endpoints, **Model Monitor's model quality monitoring** is the managed service to automatically detect prediction quality degradation using ground truth labels and baseline statistics.

    #### Correct Option Analysis

### Question 8 - Training Convergence Debugging

A machine learning engineer is training a deep learning model on **Amazon SageMaker** for image classification. During training, the engineer observes that the **validation loss is improving while the training loss is also improving**, but after 20 epochs, the **validation loss starts increasing while training loss continues to decrease**.

The engineer needs to identify the root cause and fix it. Which **TWO** actions should the engineer take? (Select TWO)

* **A)** Enable early stopping with a patience parameter, monitoring validation loss to terminate training when it stops improving.

* **B)** Increase the learning rate significantly to help the model escape the region where training and validation diverge.

* **C)** Add the SageMaker debugger to track gradient norms and identify vanishing gradients as the cause of the divergence between training and validation loss.

* **D)** Add **dropout regularization** or **L2 weight decay** to reduce overfitting, and consider **data augmentation** to increase training data diversity.

* **E)** Switch from stochastic gradient descent (SGD) to a full-batch gradient descent to ensure the model converges to the global minimum.

??? note "Click to reveal Answer & Explanation"
    **Correct Answers:** **A** and **D**

    #### Correct Options Analysis
    * **A is Correct:** The described pattern (validation loss increasing while training loss continues to decrease) is classic **overfitting**. Early stopping with a patience parameter monitoring validation loss is an effective technique to halt training before the model memorizes training data and generalizes poorly. This is a standard best practice.
    * **D is Correct:** Dropout regularization and L2 weight decay explicitly reduce overfitting by preventing the model from relying too heavily on specific neurons or large weights. Data augmentation increases the effective training data size and diversity, further improving generalization.

    #### Distractor Analysis
    * **B is Incorrect:** Increasing the learning rate would exacerbate the problem. An excessively high learning rate typically causes loss to oscillate or diverge, not fix overfitting. The symptom described here is not a learning rate issue.
    * **C is Incorrect:** SageMaker Debugger is useful for monitoring training, but vanishing gradients typically cause the loss to plateau (not the validation loss to increase while training loss decreases). The pattern described is overfitting, not vanishing gradients.
    * **E is Incorrect:** Full-batch gradient descent reduces stochastic noise but does not address overfitting. In fact, full-batch gradient descent can be more prone to overfitting in some cases because it makes deterministic updates that may converge to sharp minima with poor generalization. It's also impractical for large datasets.

    > **Key Takeaway:** When **training loss improves but validation loss worsens**, diagnose it as **overfitting** and apply regularization (dropout, weight decay, augmentation) or early stopping.
