### Question 1 - Foundation Model Deployment Strategy

A financial services company has fine-tuned a Llama 3 model on proprietary trading data in their on-premises data center. They want to serve this customized model through a managed API without provisioning or maintaining any GPU instances. The model must support concurrent invocations from multiple internal applications, and the team needs to track token-level usage metrics per application.

Which deployment approach should the ML engineer use to meet these requirements with the least operational overhead?

**A)** Deploy the fine-tuned model to an Amazon SageMaker real-time endpoint with GPU instances and configure a custom inference container.

**B)** Import the fine-tuned model into Amazon Bedrock using Custom Model Import and invoke it through the Bedrock API.

**C)** Package the model in a Docker container and deploy it to Amazon ECS with EC2 GPU instances behind an Application Load Balancer.

**D)** Upload the model to Amazon SageMaker JumpStart and use the one-click deployment option to create a managed endpoint.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Option Analysis
    * **B is Correct:** Amazon Bedrock Custom Model Import supports importing fine-tuned open-weight models (Llama, Mistral, etc.) from Amazon S3 into Bedrock's serverless infrastructure. The model is then served through the standard Bedrock InvokeModel/Converse API without managing endpoints or GPU instances. Bedrock automatically handles scaling, availability, and provides token-level usage metrics through CloudWatch and the Bedrock console.

    #### Distractor Analysis
    * **A is Incorrect:** SageMaker real-time endpoints require provisioning and managing GPU instances, configuring scaling policies, and maintaining the endpoint—violating the "no GPU instances" constraint and introducing operational overhead.
    * **C is Incorrect:** ECS with EC2 GPU instances requires full container orchestration, cluster management, and load balancer configuration—maximum operational overhead, directly contradicting the requirement.
    * **D is Incorrect:** SageMaker JumpStart provides pre-trained models for quick deployment, but it does not accept fine-tuned models from external environments like on-premises data centers. Copying a custom fine-tuned model into JumpStart is not a supported migration path.

    > **Key Takeaway:** Amazon Bedrock Custom Model Import is the native path for serving externally fine-tuned open-weight foundation models without managing any endpoint infrastructure.

### Question 2 - Provisioned Throughput vs On-Demand

A healthcare analytics team has fine-tuned an Amazon Bedrock foundation model for medical entity extraction. The model will be called by a clinical workflow application requiring guaranteed low-latency responses (under 500ms) during business hours. The application processes approximately 50,000 requests per day, with predictable peak volumes between 9 AM and 5 PM. The compliance team requires consistent performance without throttling during patient-facing operations.

Which capacity configuration should the team select for the fine-tuned model?

**A)** On-demand inference, as Bedrock automatically scales to handle any request volume.

**B)** Provisioned Throughput with a specified number of model units covering the expected peak input/output token volume.

**C)** On-demand inference during off-hours and Provisioned Throughput during business hours using an automated schedule.

**D)** On-demand inference with a custom throttling policy configured through AWS WAF to cap request rates.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Option Analysis
    * **B is Correct:** Fine-tuned (customized) models in Amazon Bedrock require Provisioned Throughput—they cannot be invoked on-demand. Provisioned Throughput guarantees dedicated capacity with predictable latency and no throttling for the committed token throughput. The team should provision enough model units to cover peak hourly input and output token demands during business hours.

    #### Distractor Analysis
    * **A is Incorrect:** Bedrock fine-tuned models do not support on-demand inference. Only base foundation models can be invoked on-demand. Attempting to use on-demand for a customized model would result in deployment failure.
    * **C is Incorrect:** While conceptually clever, Bedrock does not support programmatic switching between on-demand and Provisioned Throughput for customized models. Customized models are exclusively served through Provisioned Throughput. Bedrock does not offer built-in scheduling of capacity modes.
    * **D is Incorrect:** AWS WAF controls HTTP/S traffic entering AWS services but does not apply to the Bedrock API control plane. Moreover, throttling is not a compliance-friendly way to guarantee low-latency clinical workflows—rejected requests would fail the application requirement.

    > **Key Takeaway:** A customized Bedrock model (fine-tuned in Bedrock) must be served through Provisioned Throughput, while imported models (Custom Model Import) are invoked on-demand.

### Question 3 - Multi-Model Endpoint Design

A retail analytics team is deploying 50 lightweight product categorization models. All models are built using the same XGBoost framework and container. Traffic patterns show that only 8-10 models are queried heavily each day (depending on product updates), while others remain idle for days. The team wants to minimize infrastructure costs while serving all 50 models simultaneously, and they can tolerate a 2-3 second delay for rarely invoked models.

Which deployment architecture BEST satisfies these requirements? (Select ONE)

**A)** Deploy each model to its own SageMaker serverless endpoint, achieving zero cost for idle models.

**B)** Deploy all 50 models to a single SageMaker Multi-Model Endpoint using a shared serving container that loads models from S3 on demand.

**C)** Deploy all models into a SageMaker multi-container endpoint with one container per model.

**D)** Deploy each model as a separate AWS Lambda function with the model artifacts stored in EFS.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Option Analysis
    * **B is Correct:** SageMaker Multi-Model Endpoints (MMEs) support hosting hundreds of models on a single endpoint using one shared serving container. Models are dynamically loaded from Amazon S3 into memory when invoked, while frequently used models remain cached in memory. This minimizes idle infrastructure costs while supporting all 50 models behind one endpoint. The 2-3 second load penalty aligns perfectly with the stated tolerance for rarely invoked models.

    #### Distractor Analysis
    * **A is Incorrect:** While serverless endpoints scale to zero, creating 50 separate endpoints introduces significant operational overhead in endpoint management, monitoring, and API gateway routing. Serverless endpoints also may experience cold starts each time an idle model is invoked, but the multi-endpoint architecture is unnecessarily complex when MME provides a simpler solution.
    * **C is Incorrect:** Multi-container endpoints support up to 15 containers per endpoint and are designed for different framework requirements or sequential inference pipelines—not for packing many small models with the same framework. The team would still need at least 4 endpoints and would lose the dynamic loading benefit of MMEs.
    * **D is Incorrect:** Lambda functions with EFS introduce significant architectural complexity, concurrency limits (default 1000 concurrent invocations), and latency issues with model loading. This pattern is not designed for serving ML models at scale.

    > **Key Takeaway:** Multi-Model Endpoints are ideal when many models share the same framework/container and traffic is uneven—you trade occasional load latency for drastically reduced infrastructure costs.

### Question 4 - Multi-Container Endpoint for Inference Pipeline

A fraud detection team needs to deploy a two-stage inference workflow. First, a feature engineering container transforms raw transaction data. Second, a model inference container (using PyTorch) generates a fraud probability score. The transformation container must always run before the model container, and results must be returned within 50 milliseconds. The team wants both containers on a single endpoint to minimize network overhead.

Which SageMaker hosting option supports this requirement? (Select ONE)

**A)** A SageMaker real-time endpoint with an inference pipeline using a multi-container endpoint configuration

**B)** Two separate SageMaker endpoints connected through a Lambda function for orchestration

**C)** A SageMaker asynchronous endpoint with both containers in a multi-container configuration

**D)** A SageMaker serverless endpoint with multi-model configuration

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** SageMaker multi-container endpoints (Inference Pipelines) support running up to 15 containers sequentially on a single endpoint. Container A (feature engineering) processes the input and passes results to Container B (model inference), with all data staying within the endpoint environment—eliminating network latency between services and meeting the 50ms latency requirement.

    #### Distractor Analysis
    * **B is Incorrect:** Two separate endpoints introduce external network hops between the transformation and inference stages, significantly increasing latency and likely exceeding the 50ms budget. The Lambda orchestration also adds additional invocation overhead and operational complexity.
    * **C is Incorrect:** Asynchronous inference is designed for long-running requests (>60 seconds) and queued workloads. It cannot meet a 50 millisecond synchronous response requirement, and queuing introduces unpredictable delays.
    * **D is Incorrect:** Serverless endpoints do not support multi-container configurations or inference pipelines. They are restricted to single-model serving, and the cold-start risk would make a 50ms guarantee unreliable.

    > **Key Takeaway:** Multi-container endpoints (Inference Pipelines) keep sequential ML processing steps within a single endpoint environment, crucial when low-latency budgets prohibit inter-service network hops.

### Question 5 - Foundation Model Self-Hosting vs Bedrock

A startup is building a real-time coding assistant that must generate completions in under 200 milliseconds. Their model is a large open-weight model (70B parameters) that has been fine-tuned on proprietary code. The team evaluated Amazon Bedrock Custom Model Import but discovered the required model architecture isn't currently supported. They need full control over the serving stack (custom tokenizer, custom inference optimization), and their budget allows for dedicated infrastructure.

Which deployment approach is most appropriate?

**A)** Package the model into a custom SageMaker inference container with GPU-accelerated instances, deployed as a real-time endpoint with auto scaling.

**B)** Wait until Bedrock adds support for the model architecture and use Custom Model Import.

**C)** Deploy the model on AWS Lambda using a custom container image with the model cached in the Lambda layer.

**D)** Use Amazon SageMaker JumpStart to deploy the model directly, as it supports all custom model architectures.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** When a model cannot be imported into Bedrock (unsupported architecture) and requires custom serving stack control (custom tokenizer, custom inference optimizations), self-hosting on SageMaker is the correct path. A real-time endpoint with GPU instances supports the 200ms latency requirement and enables full control over container configuration, model optimization, and scaling.

    #### Distractor Analysis
    * **B is Incorrect:** Waiting for Bedrock support is not a viable engineering decision for an active product roadmap.     > **Key Takeaway:** When Bedrock Custom Model Import doesn't support your architecture, self-hosting on SageMaker with custom inference containers is the correct fallback for low-latency, high-control deployment requirements.

### Question 6 - Retrieval Configuration for RAG

An enterprise legal research platform uses Amazon Bedrock Knowledge Bases with OpenSearch Serverless as its vector store. Users report that searches frequently return outdated contracts from completed negotiations. The vector similarity search retrieves relevant legal concepts correctly, but the results include documents from closed matters that should not be referenced. The team wants to ensure the retrieved results exclude documents with status "Closed" or "Expired" before semantic search is performed.

Which retrieval configuration change should the ML engineer implement?

**A)** Add a metadata filter to exclude documents where status equals "Closed" or "Expired" before vector similarity search runs.

**B)** Increase the number of retrieved passages (top-K) to push closed documents further down the result list.

**C)** Implement hybrid search with keyword matching to better identify closed documents.

**D)** Add a reranking model to deprioritize closed documents during the scoring phase.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** Metadata filtering in Bedrock Knowledge Bases (and OpenSearch Serverless) filters out documents based on metadata attributes (e.g., `status != "Closed"`) before the vector similarity search executes. This ensures the candidate set completely excludes stale or out-of-scope documents, addressing the root cause of the complaint.

    #### Distractor Analysis
    * **B is Incorrect:** Increasing top-K widens the retrieval set, which would introduce more outdated documents into the prompt rather than eliminating them. The complaint is about relevance of the candidate set, not about too few results being returned.
    * **C is Incorrect:** Hybrid search combines vector similarity with keyword matching (e.g., BM25). This improves exact-term matching but does not solve the problem of closed documents appearing in results. Closed documents would still match if they contain the same legal terms.
    * **D is Incorrect:** Reranking reorders already-retrieved candidates based on semantic relevance scores. It cannot remove documents from the candidate set that the initial vector search already retrieved. More importantly, a closed document might still be semantically relevant and would not be deprioritized by a reranker.

    > **Key Takeaway:** Metadata filtering is the correct tool when specific document attributes (status, date, department) must exclude documents before semantic similarity is computed.

### Question 7 - SageMaker Inference Component and Scale-to-Zero

A development team runs a SageMaker real-time endpoint for a QA testing environment. The endpoint serves a text classification model that is only used during weekday testing. The team wants to minimize costs by allowing the endpoint to scale down to zero instances when no requests have arrived for 30 minutes, then automatically scale back up when a new request arrives. They accept that the first request after scaling will experience a cold start delay.

Which configuration achieves this scale-to-zero behavior for a real-time endpoint? (Select ONE)

**A)** Configure Application Auto Scaling with a custom CloudWatch alarm that triggers scale-in to zero, and scale-out when the SageMaker NoCapacityInvocation metric is emitted.

**B)** Deploy the model to a SageMaker serverless endpoint, which natively scales to zero without any additional configuration.

**C)** Set the initial instance count to zero in the endpoint configuration and enable auto scaling with the SageMaker Invocations metric.

**D)** Scale-to-zero is not possible for SageMaker real-time endpoints; use asynchronous inference instead.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Option Analysis
    * **B is Correct:** SageMaker Serverless Inference natively scales to zero and provisions capacity on-demand when the first request arrives. This is the simplest solution for intermittent traffic with idle periods, eliminating endpoint management entirely and providing built-in cost optimization without extra auto scaling configuration.

    #### Distractor Analysis
    * **A is Incorrect:** While real-time endpoints can technically scale to zero using inference components and a custom scaling policy triggered by the NoCapacityInvocation metric, this solution is overly complex compared to serverless inference. The question doesn't require real-time endpoint features (VPC, accelerators, multi-model), so serverless is the simpler and more operationally efficient choice.
    * **C is Incorrect:** SageMaker real-time endpoints do not allow InitialInstanceCount to be set to zero. The minimum is one instance, and standard auto scaling configuration cannot scale down to zero using the standard Invocations metric alone.

Scale-to-zero is supported for real-time endpoints with inference components (though complex), and it's native for serverless endpoints.

    > **Key Takeaway:** Serverless inference is the default scale-to-zero solution for intermittent, synchronous workloads—real-time scale-to-zero requires inference components and custom scaling policies that introduce operational complexity.

### Question 8 - Agent Deployment with MCP Gateway

These operations are exposed through the company's existing REST APIs (OrderService, ReturnService, PaymentService) running on Amazon EKS. The architecture team wants the agent to discover and call these APIs without recreating them as Lambda functions or Bedrock-specific tool definitions. Which Bedrock capability should the team use for this integration?

**A)** Amazon Bedrock AgentCore with the Model Context Protocol (MCP) gateway to expose existing APIs as tools through an open standard.

**B)** Amazon Bedrock Guardrails to filter unsafe API calls before they reach the company's EKS services.

    **Correct Answer:** **A**

    #### Correct Option Analysis

### Question 9 - Batch Transform for Foundation Model Fine-Tuning Inference

The processing generates predictions that are uploaded back to S3, and the researchers review them the following Monday. Which inference strategy should the ML engineer implement?

    **Correct Answer:** **B**

    #### Correct Option Analysis
    * **B is Correct:** SageMaker Batch Transform processes large, pre-assembled datasets in bulk with no live caller waiting. The job provisions GPU instances on-demand, processes all 100,000 sequences from S3, writes predictions back to S3, and immediately releases all compute resources. This perfectly matches the weekly schedule pattern and ensures zero idle costs between jobs.

### Question 10 - Resource Allocation for Foundation Model Workloads

A production team is configuring Amazon Bedrock Provisioned Throughput for a fine-tuned summarization model. They measured their average workload as 2,000 input tokens and 500 output tokens per request, with 100 requests per minute during business hours. They want to right-size their committed capacity to handle peak volumes without over-provisioning. However, they notice the Bedrock console requires them to specify capacity in "model units" rather than instances or vCPUs.

What does a model unit represent in Amazon Bedrock Provisioned Throughput?

**A)** One dedicated GPU instance serving the model, similar to a SageMaker ml.g5 instance.

**B)** A unit of throughput capacity measured in tokens per minute (input and output counts specified separately).

**C)** One concurrent invocation slot that processes a single request at a time.

**D)** One vCPU and 4GB of memory allocated to the model serving infrastructure.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Option Analysis
    * **B is Correct:** Amazon Bedrock uses model units to measure Provisioned Throughput capacity. Each model unit represents a specified amount of tokens per minute—both input tokens and output tokens are accounted for separately. For example, one model unit for a particular model might provide 20,000 input tokens per minute and 8,000 output tokens per minute. Buyers commit to a number of model units based on their expected peak token throughput.

    #### Distractor Analysis
    * **A is Incorrect:** Model units are not directly tied to specific instance types or GPU counts. Bedrock abstracts the underlying infrastructure, allowing you to think in terms of throughput rather than hardware provisioning. This is a key benefit of using a managed foundation model service.
    * **C is Incorrect:** While concurrency affects throughput, a model unit is not defined as a single request slot. Multiple concurrent requests can be served by a single model unit as long as the aggregate token throughput stays within the unit's capacity.
    * **D is Incorrect:** Bedrock does not expose CPU/memory ratios to customers. The abstraction level is tokens per minute, not raw compute resources. This distractor confuses Bedrock's model units with EC2/vCPU concepts that apply to self-hosted infrastructure.

    > **Key Takeaway:** Provisioned Throughput in Bedrock is sized by model units—capacity measures in tokens per minute (input and output separately)—not by instances, vCPUs, or concurrent request slots.

### Question 11 - Reranking Configuration for Retrieval Quality

An AI engineering team uses Amazon Bedrock Knowledge Bases with vector search for a customer support chatbot. Currently, retrieval returns 20 passages, and users report that while relevant answers appear in the retrieved set, the top-ranked passages frequently miss the specific details needed. The correct passage often appears around position 8-10. The team wants to improve the ordering of retrieved results without reducing recall or re-embedding the entire knowledge base.

Which configuration change should the team implement?

**A)** Enable a reranking model in the Bedrock Knowledge Base configuration to reorder the top-K candidates by semantic relevance.

**B)** Reduce the number of returned passages from 20 to 5 so the correct passage appears closer to the top.

**C)** Switch from vector search to hybrid search to improve keyword matching precision.

**D)** Increase the embedding dimensionality of the vector index to capture more semantic detail.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** Reranking applies a cross-encoder model to re-evaluate query-document pairs from the initial vector search results. The reranker computes a deeper semantic relevance score for each candidate and reorders the list, moving the most contextually relevant passages to the top. This directly addresses the ordering problem without altering recall (all 20 passages remain available) and without re-embedding the corpus.

    #### Distractor Analysis
    * **B is Incorrect:** If the correct passage currently ranks at position 8-10, reducing top-K to 5 would completely remove it from the retrieved set, eliminating any chance of the LLM using that information. This reduces recall and worsens answer quality.
    * **C is Incorrect:** Hybrid search adds keyword matching (BM25) alongside vector similarity. While this can improve exact-term retrieval, the problem is not about missing exact keywords—the correct passage is already retrieved but misordered. Switching search modes doesn't solve ranking order directly.
    * **D is Incorrect:** Higher-dimensional embeddings may slightly improve semantic expressiveness but require re-embedding all documents and re-indexing the vector store—a costly operation. Moreover, bi-encoder embeddings still suffer from ranking limitations compared to cross-encoder rerankers, so the ordering issue would persist.

    > **Key Takeaway:** Reranking is a second-pass relevance scoring mechanism that reorders already-retrieved candidates—it improves ranking quality without changing recall, re-embedding documents, or switching search strategies.

### Question 13 - Hybrid Search Configuration

### Question 14 - Multi-Container Endpoint vs Multi-Model Endpoint Decision

A healthcare ML team plans to deploy:
- Model A: Radiology image classifier (PyTorch, 2GB model)
- Model B: Medical text summarizer (Hugging Face Transformers, 500MB model)
- Model C: Patient risk scorer (XGBoost, 50MB model)

All three models have high and consistent traffic throughout the day, requiring standalone scaling policies. The team wants to minimize endpoint management complexity.

Which SageMaker endpoint strategy is MOST appropriate?

**A)** Deploy all three models on one multi-model endpoint, with a single serving container supporting all three frameworks.

**B)** Deploy each model to its own dedicated single-model real-time endpoint with independent auto scaling policies.

**C)** Deploy Models A and B in a multi-container inference pipeline (sequential processing), and Model C on a separate endpoint.

**D)** Deploy all three models on a multi-container endpoint invoked by direct container name.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Option Analysis
    * **B is Correct:** The three models use different frameworks (PyTorch, Hugging Face Transformers, XGBoost), have high and consistent traffic, and require independent scaling policies. Dedicated single-model endpoints are appropriate because each model can scale independently based on its own traffic patterns and latency requirements. This approach also avoids resource contention between high-traffic models sharing a fleet.

    #### Distractor Analysis
    * **A is Incorrect:** Multi-model endpoints require models to share the same serving container (same framework/stack). PyTorch, Hugging Face Transformers, and XGBoost require different containers, making this configuration technically infeasible. Additionally, high-traffic models would contend for resources on the shared fleet.
    * **C is Incorrect:** An inference pipeline implies sequential processing where output from one container feeds into another. The models in this scenario are independent (image classification and text summarization don't feed into each other), making a pipeline semantically incorrect.

### Question 17 - Query Decomposition in RAG

When the RAG system retrieves passages using this compound question, it often gets results about currency fluctuations but misses passages about revenue growth or competitor data.

Which retrieval configuration technique should the ML engineer apply to improve retrieval quality for this query type?

**A)** Enable query decomposition so the system breaks the compound question into sub-queries (revenue growth, competitor revenue, currency impact) that retrieve independently against the knowledge base.

**B)** Increase the number of retrieved passages (top-K) to a higher value like 50 to capture all relevant topics in one retrieval pass.

**C)** Apply a stricter metadata filter to exclude documents that don't contain both "revenue" and "currency" in their metadata.

**D)** Use a larger embedding model with higher dimensionality to better capture the compound query semantics.

??? note "Click to reveal Answer & Explanation"

    #### Correct Option Analysis
    * **A is Correct:** Query decomposition breaks a compound or multi-part question into multiple sub-queries, each targeting a specific topic (e.g., "Q3 revenue growth", "competitor Q3 revenue", "currency fluctuation impact"). Each sub-query retrieves independently, ensuring coverage of all topics in the final retrieval set. This technique directly addresses the issue of a compound query overwhelming vector similarity search and retrieving only the dominant topic.

    #### Distractor Analysis
    * **B is Incorrect:** Increasing top-K (e.g., to 50) might incidentally include more relevant passages, but it also introduces significant noise—unrelated passages dilute the context window and can confuse the LLM.     > **Key Takeaway:** Query decomposition is the correct technique for compound questions—it retrieves each sub-topic independently and merges results, ensuring coverage across all dimensions of the query.
