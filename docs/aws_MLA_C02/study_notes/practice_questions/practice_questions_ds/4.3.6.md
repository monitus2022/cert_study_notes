### Question 1 - SageMaker Training in Private Subnet

A healthcare analytics company is training a machine learning model on sensitive patient data using **Amazon SageMaker**. The company has a strict security policy that requires all training jobs to run without any internet access, including no access to the public internet for downloading dependencies or uploading logs.

The data science team needs to store training data in **Amazon S3**, pull container images from **Amazon ECR**, and allow SageMaker to publish training metrics to **Amazon CloudWatch**—all while maintaining the zero-internet-access requirement.

Which combination of steps should the solutions architect implement? (Select TWO)

* **A)** Launch the SageMaker training job in a private subnet with security group rules that deny all outbound traffic to 0.0.0.0/0.
* **B)** Create VPC interface endpoints for Amazon S3, Amazon ECR, and Amazon CloudWatch in the private subnet.
* **C)** Add a NAT Gateway to the private subnet and restrict outbound traffic via a Network ACL to only AWS service IP ranges.
* **D)** Configure the SageMaker training job to use a public subnet with a security group that only allows inbound traffic from the corporate data center's CIDR range.
* **E)** Enable VPC Flow Logs on the private subnet to capture all traffic and block any unauthorized internet access attempts.

??? note "Click to reveal Answer & Explanation"
    **Correct Answers:** **A** and **B**

    #### Correct Options Analysis
    * **A is Correct:** Launching the training job in a private subnet ensures that the instances/containers running the training job do not have a public IP address. A security group explicitly denying outbound traffic to 0.0.0.0/0 prevents any unintended internet egress.
    * **B is Correct:** VPC interface endpoints (AWS PrivateLink) for S3, ECR, and CloudWatch allow the training job to access these AWS services over the AWS private network backbone without requiring any internet route. Traffic never leaves the VPC.

    #### Distractor Analysis
    * **C is Incorrect:** A NAT Gateway provides outbound internet access from a private subnet, which directly violates the zero-internet-access requirement. NAT Gateways are designed to enable internet egress, not restrict it.
    * **D is Incorrect:** Placing the training job in a public subnet with a restricted inbound security group still gives the training instances a public IP address and an internet gateway route, violating the no-internet-access policy. The outbound path would still exist.
    * **E is Incorrect:** VPC Flow Logs are a monitoring and auditing tool—they capture and record IP traffic metadata but do not actively block or prevent traffic. Flow Logs cannot substitute for proper network isolation or security group rules.

    > **Key Takeaway:** Private subnet + interface endpoints (AWS PrivateLink) is the standard pattern for zero-internet ML workloads; NAT Gateways and public subnets introduce internet egress paths that violate strict isolation requirements.

### Question 2 - SageMaker Endpoint Security Group Configuration

An e-commerce company has deployed a fraud detection model using **Amazon SageMaker real-time inference endpoints** within a VPC. The endpoint must be accessible only from an internal microservices application running on **Amazon ECS (EC2 launch type)** within the same VPC.

The security team requires that the SageMaker endpoint's security group permit the absolute minimum inbound traffic necessary, and the endpoint must be able to publish prediction logs to a central Amazon CloudWatch Logs group.

Which inbound security group rule configuration meets the least privilege requirement for the SageMaker endpoint?

* **A)** Allow inbound HTTPS (443) from the ECS task security group ID; allow outbound TCP 443 to the VPC CIDR range.
* **B)** Allow inbound HTTPS (443) from the ECS task security group ID; allow outbound TCP 443 to the CloudWatch Logs VPC endpoint security group ID.
* **C)** Allow inbound HTTPS (443) from 0.0.0.0/0; allow outbound TCP 443 to the CloudWatch Logs VPC endpoint security group ID.
* **D)** Allow inbound HTTPS (443) from the VPC CIDR range; allow outbound All Traffic to 0.0.0.0/0.
* **E)** Allow inbound TCP 8080 from the ECS task security group ID; allow outbound TCP 443 to 0.0.0.0/0.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** Configuring the inbound rule to reference the ECS task security group ID (rather than an IP address) ensures only traffic from that specific set of tasks can reach the SageMaker endpoint—this is the principle of least privilege. Configuring outbound traffic to target the CloudWatch Logs VPC endpoint security group ID allows the endpoint to publish logs privately without opening broad outbound access.

    #### Distractor Analysis
    * **A is Incorrect:** While the inbound rule is correct (referencing a security group ID), the outbound rule to "VPC CIDR range" is overly broad. It would allow the endpoint to communicate with any resource in the VPC, violating least privilege. Also, if CloudWatch Logs is accessed via a VPC endpoint, the traffic destination should be scoped to that endpoint's security group.
    * **C is Incorrect:** Allowing inbound HTTPS from 0.0.0.0/0 exposes the SageMaker endpoint to the entire internet. This is a critical security violation, even if other controls exist upstream.
    * **D is Incorrect:** Inbound from the entire VPC CIDR range is overly permissive—any resource in the VPC (e.g., compromised instances, public web servers) could call the endpoint. Outbound "All Traffic to 0.0.0.0/0" is dangerously open and would allow the endpoint to reach the internet.
    * **E is Incorrect:** SageMaker real-time endpoints expose HTTPS on port 443, not port 8080. Additionally, allowing outbound 443 to 0.0.0.0/0 opens a direct internet egress path from a sensitive ML endpoint.

    > **Key Takeaway:** Reference security group IDs (not CIDRs or 0.0.0.0/0) for least-privilege inter-service communication, and always scope outbound rules to specific destinations like VPC endpoint security groups.

### Question 3 - SageMaker Studio Domain Network Isolation

A financial services firm is setting up **Amazon SageMaker Studio** for its data science team to develop and test credit risk models. The firm's compliance team mandates that the SageMaker Studio domain must be accessible only from the corporate network (CIDR 10.100.0.0/16) and must never have direct internet access. All model training and inference must occur within private subnets.

The firm wants to use SageMaker Studio's built-in JupyterLab notebooks, which require access to Amazon SageMaker API operations, Amazon S3, and the ability to install packages from a private **Amazon CodeArtifact** repository—all without internet access.

Which architecture satisfies these requirements with the least operational overhead?

* **A)** Deploy SageMaker Studio in VPC-only mode. Attach a security group to the domain allowing inbound HTTPS (443) only from 10.100.0.0/16. Create VPC interface endpoints for SageMaker, S3, and CodeArtifact in the private subnets.
* **B)** Deploy SageMaker Studio in public internet mode. Restrict access via an IAM policy that only allows users from the corporate network to launch Studio applications. Use NAT Gateways for outbound traffic and rely on security groups for isolation.
* **C)** Deploy SageMaker Studio in VPC-only mode. Attach a default security group allowing all inbound traffic from the VPC CIDR. Create a single interface endpoint for SageMaker, and route all other traffic through a NAT Gateway in a public subnet.
* **D)** Deploy SageMaker Studio in public internet mode. Configure AWS WAF in front of the Studio domain to filter traffic by source IP. Disable all network interfaces in the Studio applications and use local storage only for notebooks.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Options Analysis
    * **A is Correct:** SageMaker Studio VPC-only mode enforces that all Studio applications (notebooks, training jobs, inference endpoints) run entirely within the specified VPC's private subnets with no internet access. Configuring the security group to allow inbound only from 10.100.0.0/16 restricts access to the corporate network. Interface endpoints for SageMaker, S3, and CodeArtifact provide private connectivity to these required services without relying on the internet.

    #### Distractor Analysis
    * **B is Incorrect:** Public internet mode exposes the SageMaker Studio domain to the internet, violating the compliance mandate of no direct internet access. While IAM policies can restrict which users can authenticate, they do not provide network-level isolation. NAT Gateways are used for outbound internet egress from private subnets, which also violates the no-internet requirement.
    * **C is Incorrect:** Allowing all inbound traffic from the VPC CIDR is overly permissive—any resource in the VPC could access the Studio domain. Additionally, routing traffic through a NAT Gateway introduces internet egress. Creating only a single interface endpoint leaves gaps in private connectivity to other required services.
    * **D is Incorrect:** Public internet mode fundamentally exposes the domain to the internet. While AWS WAF can provide some IP-based filtering at the application layer, it is not a substitute for network isolation. Additionally, disabling network interfaces and limiting notebook storage contradicts SageMaker Studio core functionality and the requirement to access S3 and CodeArtifact.

    > **Key Takeaway:** SageMaker Studio VPC-only mode combined with interface endpoints is the standard pattern for strict network isolation of ML development environments; WAF and IAM do not replace network-level controls.

### Question 4 - Bedrock VPC Interface Endpoint for Private Access

A financial regulatory compliance company is building an AI-powered contract analysis application using **Amazon Bedrock** foundation models. The application runs on **Amazon EKS** pods in a private VPC subnet with no internet gateway.

The compliance team requires that all calls to Bedrock foundation models traverse only the AWS private network, and that the endpoint URL used by the application must be resolvable within the private subnets.

Which steps should the ML engineer take to enable private access to Bedrock? (Select ONE)

* **A)** Create an interface VPC endpoint for `bedrock` in the private subnet. Enable private DNS. Then create an interface VPC endpoint for `bedrock-runtime` and enable private DNS for it as well. Update the SG on the interface endpoints to accept traffic from the EKS pods' security group.
* **B)** Create a Gateway VPC endpoint for `bedrock` and update the route table of the private subnet to point to the gateway endpoint. Add an IAM policy to the EKS pod role granting `bedrock:InvokeModel`.
* **C)** Create an interface VPC endpoint for `bedrock-runtime` only. Configure a custom DNS entry in the VPC's DHCP Options Set pointing `bedrock-runtime.us-east-1.amazonaws.com` to the interface endpoint's private IP.
* **D)** Create two interface VPC endpoints—one for `bedrock` and one for `bedrock-runtime`. Keep private DNS disabled to avoid conflicts. Configure the EKS application to use the interface endpoint's private IP address directly in the `endpointUrl` parameter.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Options Analysis
    * **A is Correct:** Amazon Bedrock requires **two separate interface VPC endpoints**—one for the control plane (`bedrock`) and one for model invocation (`bedrock-runtime`). Both endpoints must have private DNS enabled so that the standard Bedrock service DNS names resolve to the private IP addresses of the endpoints within the VPC. The security groups on these endpoints must allow inbound traffic from the EKS pods' security group to enforce least privilege.

    #### Distractor Analysis
    * **B is Incorrect:** Gateway VPC endpoints are available for Amazon S3 and Amazon DynamoDB, but **not** for Amazon Bedrock. Bedrock requires interface endpoints via AWS PrivateLink. Additionally, an IAM policy alone cannot establish private network connectivity—this option ignores the network routing requirement completely.
    * **C is Incorrect:** Creating only a `bedrock-runtime` endpoint is insufficient because Bedrock also requires the control plane endpoint (`bedrock`) for operations like listing models and creating guardrails. Custom DHCP Options Sets cannot be created in modern AWS VPCs for internal DNS resolution—AWS recommends using private DNS on the interface endpoint itself.
    * **D is Incorrect:** Disabling private DNS forces the application to use the endpoint's private IP address directly, which means the TLS handshake / SNI would fail with standard SDKs

 that rely on the service DNS name. Additionally, private IP addresses of interface endpoints can change, making this architecture less maintainable.

    > **Key Takeaway:** Amazon Bedrock requires two interface VPC endpoints (control plane + runtime) with private DNS enabled; gateway endpoints are only for S3/DynamoDB.

### Question 5 - Multi-Account Model Deployment Network Architecture

An enterprise is building a multi-account architecture for its ML platform. The data science team operates in a **development account** where they train models using SageMaker. The trained model artifacts are then promoted to a **centralized production account** where they are deployed as SageMaker endpoints.

The security team mandates that the production SageMaker endpoint must:
1. Not have a public IP address.
2. Be reachable only from applications in the production account's VPC.
3. Have all API calls and data events recorded in a centralized **audit account**.

Which combination of configurations achieves these requirements? (Select THREE)

* **A)** Deploy the SageMaker endpoint in a private subnet in the production account's VPC.
* **B)** Create a VPC peering connection between the development and production accounts and allow traffic over the peering connection.
* **C)** Create a security group on the SageMaker endpoint that allows inbound HTTPS (443) only from the production application's security group ID.
* **D)** Create a CloudTrail organization trail with `InvokeEndpoint` enabled as a data event and deliver the logs to an S3 bucket in the audit account.
* **E)** Deploy a NAT Gateway in the production account's public subnet and route the SageMaker endpoint traffic through it.

??? note "Click to reveal Answer & Explanation"
    **Correct Answers:** **A**, **C**, and **D**

    #### Correct Options Analysis
    * **A is Correct:** Deploying the SageMaker endpoint in a private subnet ensures the endpoint container does not receive a public IP address. This satisfies requirement #1 (no public IP).
    * **C is Correct:** A security group rule referencing the production application's security group ID (instead of an IP CIDR) ensures only traffic from that specific application's resources can reach the endpoint. This satisfies requirement #2 (reachable only from production applications) with least privilege.
    * **D is Correct:** An AWS Organizations-level CloudTrail trail with data events enabled for SageMaker `InvokeEndpoint` ensures every model invocation call is recorded. Delivering these logs to an S3 bucket in the audit account centralizes the audit record, satisfying requirement #3.

    #### Distractor Analysis
    * **B is Incorrect:** VPC peering between development and production accounts is not required for this scenario, as the requirement is that only production applications can call the endpoint. Introducing a peering connection would create an unnecessary network path between environments, increasing the attack surface and violating least privilege.

    > **Key Takeaway:** Private subnets + security group referencing (not CIDR-based) + organization CloudTrail with data events = the three pillars of secure, auditable SageMaker endpoint deployment.

### Question 6 - Training VPC with Egress Restrictions

A machine learning engineering team is building a SageMaker training pipeline that processes proprietary customer interaction data. The training job needs to:
1. Read input data from an S3 bucket that uses AWS KMS encryption with a customer-managed key.
2. Pull training image from Amazon ECR.
3. Write output artifacts back to the same S3 bucket.

The security policy forbids the training job from having any internet egress and requires that all inter-service communication remain on the AWS private network.

Which TWO actions are required for the training job to function within these constraints? (Select TWO)

* **A)** Attach the training job's IAM role to a policy granting access to the KMS key, S3 bucket, and ECR repository.
* **B)** Create an S3 Gateway VPC endpoint in the training VPC and an ECR interface VPC endpoint.
* **C)** Create an S3 interface VPC endpoint and a NAT Gateway to allow the training job to reach S3.
* **D)** Enable server-side encryption (SSE-KMS) on the S3 bucket and disable `Block Public Access` on the bucket.
* **E)** Attach a security group to the training job allowing outbound traffic to 0.0.0.0/0 for S3 access.

??? note "Click to reveal Answer & Explanation"
    **Correct Answers:** **A** and **B**

    #### Correct Options Analysis
    * **A is Correct:** Even with proper network connectivity, the training job's IAM role must have explicit permissions to access the S3 bucket, decrypt objects using the KMS key, and pull images from ECR. IAM authorization remains necessary regardless of network isolation.
    * **B is Correct:** An S3 **Gateway** VPC endpoint (proper for S3, not an interface endpoint) and an ECR **Interface** VPC endpoint allow the training job to reach these services over the AWS private network without internet egress. S3 gateway endpoints use route table entries; ECR requires interface endpoints via PrivateLink.

    #### Distractor Analysis
    * **C is Incorrect:** S3 interface endpoints are an alternative, but they are less cost-effective than gateway endpoints for high-volume data transfers. More critically, adding a NAT Gateway violates the no-internet-egress requirement, as NAT Gateways specifically enable outbound internet connectivity.
    * **D is Incorrect:** Enabling SSE-KMS and disabling Block Public Access do not address the network connectivity requirement. In fact, disabling Block Public Access is a dangerous suggestion that could expose the sensitive customer data bucket. This is a distractor that confuses data protection with network isolation.
    * **E is Incorrect:** Allowing outbound traffic to 0.0.0.0/0 from the training job's security group is a severe violation of the no-internet-egress policy. It would allow the training container to reach any internet destination.

    > **Key Takeaway:** S3 uses Gateway VPC endpoints (route-table based); ECR uses Interface VPC endpoints (PrivateLink). IAM permissions are orthogonal to network connectivity—both are required for secure access.

### Question 7 - Bedrock Guardrails and VPC Endpoint Integration

A legal tech company is deploying a document summarization application using **Amazon Bedrock** with **Bedrock Guardrails** applied to all model outputs. The application is hosted in a private subnet with no internet access. All model traffic must traverse the AWS private network, and all sensitive data must be filtered by Guardrails before being returned to the application.

Which statement is correct regarding the integration of Bedrock Guardrails with VPC endpoints?

* **A)** Bedrock Guardrails are applied automatically when Bedrock is accessed through an interface VPC endpoint; no additional endpoint configuration is required.
* **B)** When calling Bedrock through an interface VPC endpoint, the `bedrock-runtime` endpoint handles both model invocation and Guardrails enforcement. The `bedrock` control plane endpoint is optional.
* **C)** Bedrock Guardrails require a separate interface VPC endpoint dedicated to `bedrock-guardrails` to function within a VPC.
* **D)** Guardrails cannot be applied when using interface VPC endpoints. To use Guardrails, the application must call Bedrock over the public internet through AWS Shield.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Options Analysis
    * **A is Correct:** Bedrock Guardrails is a feature of the Bedrock service itself. When you call Bedrock through an interface VPC endpoint (either `bedrock` or `bedrock-runtime`), Guardrails policies are applied as part of the Bedrock API processing—there is no separate endpoint for Guardrails. The application includes the guardrail identifier in the API request, and Bedrock enforces the guardrail policies regardless of whether traffic enters via public endpoint or private endpoint.

    #### Distractor Analysis
    * **B is Incorrect:** This is partially correct but misleading. While the `bedrock-runtime` endpoint handles model invocation and Guardrails enforcement when specified in the request, the `bedrock` control plane endpoint is **not** optional—it is required for operations like creating, updating, and listing guardrails. The statement incorrectly implies the control plane endpoint can be omitted.
    * **C is Incorrect:** There is no dedicated `bedrock-guardrails` VPC endpoint in AWS. Guardrails is not a separate service with its own endpoint namespace; it is integrated into the Bedrock service API. Creating a fictional endpoint would be an implementation error.
    * **D is Incorrect:** This statement is completely false. Guardrails work seamlessly with interface VPC endpoints, and there is no requirement to expose Bedrock to the public internet to use Guardrails. AWS Shield is a DDoS protection service for public endpoints and has no relevance to Bedrock Guardrails functionality within a VPC.

    > **Key Takeaway:** Bedrock Guardrails is an integrated feature of Bedrock APIs; no separate VPC endpoint is needed—the same `bedrock` and `bedrock-runtime` interface endpoints carry both invocation and guardrails-enforced traffic.

### Question 8 - Isolating SageMaker Processing Jobs from training

An ML team is running a two-stage pipeline using **Amazon SageMaker**:
1. A **processing job** that performs feature engineering on raw data.
2. A **training job** that consumes the processed features.

The raw data lives in an S3 bucket that also contains other sensitive enterprise datasets. The company wants to isolate the processing and training jobs into different security groups to enforce different network access policies within the same VPC.

The processing job needs access to the raw data S3 bucket. The training job needs access to the processed features S3 bucket and to load a model from ECR. Neither job may communicate with each other directly.

Which network architecture correctly isolates these workloads? (Select TWO)

* **A)** Create two security groups—SG-Processing and SG-Training. Attach SG-Processing to the processing job and SG-Training to the training job. Do not add rules allowing traffic between SG-Processing and SG-Training.
* **B)** Create two subnets—one for processing jobs and one for training jobs—and ensure they are in different Availability Zones to prevent direct communication.
* **C)** Add outbound rules to SG-Processing allowing traffic only to the S3 gateway endpoint prefix list ID; add outbound rules to SG-Training allowing traffic only to the S3 gateway endpoint prefix list ID and the ECR interface endpoint security group ID.
* **D)** Create a single security group and attach it to both jobs. Use a Network ACL on the subnet to deny traffic between the specific IP addresses of the processing and training instances.
* **E)** Enable VPC Flow Logs on the subnets to block any direct communication between the processing and training jobs.

??? note "Click to reveal Answer & Explanation"
    **Correct Answers:** **A** and **C**

    #### Correct Options Analysis
    * **A is Correct:** Using two separate security groups with no rules that reference each other ensures that neither job can initiate direct communication with the other. Security groups are stateful and default-deny, meaning any traffic not explicitly permitted is blocked.
    * **C is Correct:** Scoping outbound rules to specific destinations (S3 gateway endpoint prefix list ID, ECR interface endpoint SG ID) limits each job's network egress to only the services it needs. This enforces least privilege at the network level and complements the separation achieved by using distinct security groups.

    #### Distractor Analysis
    * **B is Incorrect:** Subnets are a Layer 3 isolation mechanism, and instances in different subnets (even in different AZs) can still communicate with each other if security groups allow it. Subnet placement alone does not prevent communication; security groups (Layer 4) control inter-resource traffic within the same VPC.
    * **D is Incorrect:** Using a single security group for both jobs with the same rules means both jobs have identical network permissions. Network ACLs are stateless and typically operate at the subnet level, not the individual instance level. Maintaining per-IP ACL rules is operationally complex and fragile compared to using separate security groups.
    * **E is Incorrect:** VPC Flow Logs are a monitoring feature—they record traffic metadata for auditing but **cannot** block or prevent traffic. This is a fundamental misconception repeated in many exam distractors.

    > **Key Takeaway:** Security groups (not subnets or Flow Logs) control inter-resource communication; separate security groups with no cross-references are the standard pattern for isolating SageMaker jobs within a VPC.

### Question 9 - Security Group Rule Understanding for SageMaker Inference

An ML engineer at a retail company has set up a SageMaker real-time endpoint in a VPC. The endpoint must call out to a **third-party REST API** hosted on the internet to retrieve real-time pricing data during inference. The endpoint is currently in a private subnet.

The security group attached to the SageMaker endpoint has the following rules:
- **Inbound:** Allow HTTPS (443) from the internal application load balancer's security group ID.
- **Outbound:** Allow HTTPS (443) to 0.0.0.0/0 (for the third-party API only).

The ML engineer receives a security finding that outbound traffic to 0.0.0.0/0 is too broad. The third-party API's public IP address is `198.51.100.25`.

Which TWO changes should the ML engineer make to remediate this finding while maintaining functionality? (Select TWO)

* **A)** Add a NAT Gateway to the VPC Public Subnet may require the SageMaker endpoint to be in a private subnet with a route to NAT Gateway, but the current outbound SG rules already allow this.
* **B)** Restrict the outbound rule from "HTTPS (443) to 0.0.0.0/0" to "HTTPS (443) to 198.51.100.25/32 (Specific IP for third-party REST API)".
* **C)** Move the SageMaker endpoint to a public subnet with a public IP address so it can directly reach the internet, eliminating the need for a NAT Gateway and allowing tighter SG scoping.
* **D)** Add the route to **0.0.0.0/0** in the private subnet's route table to use internet gateway, so that the SageMaker endpoint can reach the third-party API over the internet.
* **E)** Implement an interface VPC endpoint for the third-party REST API (if supported) as a replacement for direct internet access; otherwise must have NAT Gateway.

??? note "Click to reveal Answer & Explanation"
    **Correct Answers:** **B** and **E**

    #### Correct Options Analysis
    * **B is Correct:** Tightening the outbound SG rule to allow only the specific third-party API's IP address (`198.51.100.25/32`) is a direct remediation for the "too broad" security finding. It maintains the exact functionality (outbound HTTPS to that API) while restricting egress to a single destination.
    * **E is Correct:** If the third-party REST API is accessible via **AWS PrivateLink** as a third-party service, creating an interface VPC endpoint would eliminate internet egress entirely and provide private connectivity. If PrivateLink is not available, a NAT Gateway (with corresponding route table update) is the standard pattern for allowing private subnet resources to reach specific internet destinations.

    #### Distractor Analysis
    * **A is Incorrect:** This option is misleading. It states that the "current outbound SG rules already allow this" but fails to address the actual remediation—tighter SG scoping. Adding a NAT Gateway is a necessary network routing component for private subnets to reach the internet, but the security group rule still needs to be scoped to the specific IP.
    * **C is Incorrect:** Moving the endpoint to a public subnet gives it a public IP address and makes it directly reachable from the internet (if inbound rules allow it). This increases the attack surface and violates the best practice of keeping inference workloads in private subnets. It also does not address the overly broad outbound rule—the endpoint would still have an outbound rule to 0.0.0.0/0 in a public subnet, which is equally problematic.
    * **D is Incorrect:** Adding a route to 0.0.0.0/0 via an Internet Gateway in the private subnet's route table would make the subnet effectively a **public subnet**, defeating the purpose of the private isolation. This is a common misconfiguration that exposes private resources to direct internet access. The correct pattern is a NAT Gateway for outbound-only internet access from private subnets.

    > **Key Takeaway:** For private subnet resources needing selective internet egress: (1) scope SG outbound to specific IP addresses, (2) use NAT Gateway (not IGW) for outbound-only routing, (3) consider PrivateLink as an internet-free alternative.

### Question 10 - Troubleshooting SageMaker Training Network Failure

A financial analytics company is running a SageMaker training job in a newly created VPC. The training script reads data from an S3 bucket and pushes metrics to CloudWatch. The VPC has two subnets in different AZs, and both are **private**.

After starting the training job, the ML engineer discovers that the job:
1. Fails to read data from the S3 bucket.
2. Cannot push metrics to CloudWatch.
3. Cannot pull the training container from ECR.

The training job's IAM role has full access to S3, CloudWatch, and ECR. The private subnets have no route to the internet.

Which combination of resources should the engineer deploy to fix this issue? (Select TWO)

* **A)** Create an S3 **Gateway** VPC endpoint and update the private subnet route tables.
* **B)** Create an S3 **Interface** VPC endpoint and an ECR Interface VPC endpoint, and update the private subnet security groups.
* **C)** Create an ECR **Interface** VPC endpoint and a CloudWatch **Interface** VPC endpoint, and update the private subnet security groups.
* **D)** Add a NAT Gateway to one of the private subnets and configure the other subnet to route through it.
* **E)** Create a VPC peering connection to the account that owns the ECR repository.

??? note "Click to reveal Answer & Explanation"
    **Correct Answers:** **A** and **C**

    #### Correct Options Analysis
    * **A is Correct:** Amazon S3 is accessed via a **Gateway** VPC endpoint (not an interface endpoint). Gateway endpoints use route table entries (not security groups) and are the recommended approach for private subnets to access S3 without internet. Creating an S3 gateway endpoint and updating the private subnet route tables enables the training job to read data from S3 privately.
    * **C is Correct:** Amazon ECR and CloudWatch are accessed via **Interface** VPC endpoints (AWS PrivateLink). These endpoints require security group rules to allow traffic from the training job's security group. Creating ECR and CloudWatch interface endpoints provides the necessary private connectivity for pulling container images and pushing metrics.

    #### Distractor Analysis
    * **B is Incorrect:** This option incorrectly specifies an S3 **Interface** endpoint. While S3 interface endpoints do exist, they are optional and typically used for specific scenarios (e.g., cross-region, cross-VPC, or on-premises access via Direct Connect). For a standard same-region private subnet scenario, the **Gateway** endpoint is recommended as it is simpler and more cost-effective for high-volume data transfers. The question asks for the correct fix, and using an S3 gateway endpoint is the best practice.
    * **D is Incorrect:** A NAT Gateway would provide internet egress, which is unnecessary and potentially violates security requirements. All three services (S3, ECR, CloudWatch) can be accessed privately via VPC endpoints without internet. Using a NAT Gateway would be an over-engineered and more expensive solution that undermines the private-by-design architecture.
    * **E is Incorrect:** VPC peering is for connecting two different VPCs. In this scenario, ECR is an AWS service (not a resource in a separate VPC) that should be accessed via an interface VPC endpoint. VPC peering to another account that owns the ECR repository would be irrelevant for accessing a public AWS service like ECR.

    > **Key Takeaway:** S3 = Gateway VPC endpoint (route-table based); ECR & CloudWatch = Interface VPC endpoints (PrivateLink); NAT Gateways and peering are incorrect choices when private AWS service access is required.
