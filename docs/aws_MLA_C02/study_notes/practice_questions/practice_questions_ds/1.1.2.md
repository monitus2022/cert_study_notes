### Question 1 - Columnar Format Optimization for Analytics Workloads

A data engineering team at a financial services company is building a curated data lake on **Amazon S3** to support quarterly risk modeling. The analytics platform uses **Amazon Athena** to run SQL queries that consistently scan historical transaction records across 500 million rows. Each query targets only 4 of the 40 available columns (e.g., `transaction_amount`, `counterparty_risk_score`, `settlement_date`, and `currency_code`). The team wants to reduce query time and minimize data scanned per query.

Which storage format should the team use for this curated dataset? (Select ONE)

- **A)** JSON Lines (one JSON object per line)
- **B)** CSV with gzip compression
- **C)** Apache Parquet with Snappy compression
- **D)** Plain text with server-side encryption
- **E)** Uncompressed TSV

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **C**

    #### Correct Options Analysis
    * **C is Correct:** Apache Parquet is a columnar storage format that allows Athena (and other query engines like Spark, Glue) to perform **column pruning (projection pushdown)**. When a query reads only 4 of 40 columns, Parquet enables reading only those column-chunks from S3, dramatically reducing data scanned, query time, and Athena scan costs. Snappy compression provides a good balance of compression ratio and decompression speed.

    #### Distractor Analysis
    * **A is Incorrect:** JSON Lines stores data in row-oriented document format. Athena must scan and parse all 40 fields in each record even when only 4 are requested, causing excessive I/O and CPU overhead.
    * **B is Incorrect:** CSV is row-oriented, and while gzip reduces storage size, Athena will still scan every column in every row during query execution. Additionally, gzip is not splittable, limiting query parallelism.
    * **D is Incorrect:** Plain text has no schema or type metadata, and encryption does not change the row vs. column scan I/O behavior.
    * **E is Incorrect:** Uncompressed TSV is row-oriented. It scans all columns across many rows, leading to maximum Athena query time and cost.

    > **Key Takeaway:** For analytics workloads that repeatedly read few columns across many rows, use columnar formats like Parquet or ORC to enable column pruning and dramatically reduce per-query I/O and cost.


### Question 2 - Vector Store Selection with pgvector for Existing PostgreSQL

A healthcare startup has patient records and clinical metadata stored in **Amazon RDS for PostgreSQL**. The ML team is building a semantic search application that will retrieve similar patient cases based on medical embeddings. The team wants to minimize data movement and infrastructure changes: embeddings must reside alongside the existing relational records so joins between patient metadata and vector similarity results are trivial.

Which storage configuration should the ML team use? (Select ONE)

- **A)** Migrate all embeddings to **Amazon OpenSearch Service** and use SQL-to-Elasticsearch connectors for joins across systems.
- **B)** Export embeddings to **Amazon S3** and use **Amazon Athena** v2 vector functions to run similarity search via SQL.
- **C)** Enable the **pgvector** extension on the Amazon RDS for PostgreSQL instance and store embeddings in a vector column.
- **D)** Store embeddings as JSON documents in **Amazon DynamoDB** and query nearest neighbors using a DynamoDB Streams consumer.
- **E)** Import embeddings into **Amazon ElastiCache for Redis** and run k-NN queries with RediSearch.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **C**

    #### Correct Options Analysis
    * **C is Correct:** The **pgvector extension** adds native vector data type and similarity search operators (`<->` for L2 distance, `<#>` for inner product, `<=>` for cosine distance) to PostgreSQL. Since the data already lives in RDS PostgreSQL, enabling pgvector allows embeddings to sit beside relational records, supporting native SQL joins without data movement, sync complexity, or new infrastructure.

    #### Distractor Analysis
    * **A is Incorrect:** Migrating embeddings to OpenSearch Service introduces a second storage system, cross-system joins are non-trivial, and operational overhead increases significantly compared to enabling a native extension.
    * **B is Incorrect:** Athena does not natively support vector similarity search in the way a vector database or pgvector does. Additionally, storing embeddings in S3 with Athena would decouple them from relational records, making bio-directional joins cumbersome.
    * **D is Incorrect:** DynamoDB cannot natively compute k-NN vector similarity. Implementing it with DynamoDB Streams and custom consumers would be a costly, custom, high-overhead workaround.
    * **E is Incorrect:** ElastiCache for Redis with RediSearch is a legitimate vector store option, but it introduces a caching layer and data replication from PostgreSQL to Redis. This violates the constraint of minimizing data movement and infrastructure changes.

    > **Key Takeaway:** When vector search requirements pair with existing relational data in PostgreSQL, enabling `pgvector` is the lowest-friction, lowest-data-movement solution.


### Question 3 - Streaming Ingestion Capacity Troubleshooting

A fraud detection platform ingests real-time payment events from **Amazon Kinesis Data Streams** into **Amazon OpenSearch Service**. The operations team notices that the Kinesis consumer (an **AWS Lambda** function using event source mapping) has a growing iterator age behind the latest record, indicating a backlog. The Lambda function's CPU and memory utilization are consistently below 30%, and error metrics are within normal limits. The OpenSearch cluster's `WriteThrottles` metric is at 90%.

What is the MOST likely bottleneck in this ingestion path? (Select ONE)

- **A)** The Kinesis stream is under-provisioned in shards
- **B)** The Lambda function's concurrency is insufficient
- **C)** The OpenSearch cluster's write throughput is saturated
- **D)** The Kinesis Data Streams retention period is set too low
- **E)** The Lambda function's invocation payload size is set too large

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **C**

    #### Correct Options Analysis
    * **C is Correct:** The `WriteThrottles` metric at 90% on the OpenSearch cluster is the smoking gun： the cluster is rejecting or queueing write requests because its indexing throughput (CPU, I/O, or index shard capacity) is saturated. When downstream write targets are throttling, Kinesis consumers will be forced to retry writes, causing them to fall behind the stream and increasing iterator age. Because Lambda CPU and memory are well below limits, the bottleneck is clearly in the downstream OpenSearch cluster, not the consumer itself.

    #### Distractor Analysis
    * **A is Incorrect:** A Kinesis stream under-provisioned in shards would limit total ingestion or consumption throughput. However, the stream is able to receive records (producers are keeping up), and Lambda is not maxing out its capacity. The issue manifests after Lambda attempts to write to OpenSearch.
    * **B is Incorrect:** Lambda concurrency is not the bound because CPU, memory, and invocation counts are comfortably under Lambda's limits. If Lambda were the bottleneck, we'd observe high concurrency utilization or throttling on the Lambda side.
    * **D is Incorrect:** A low retention period affects data durability/timeline for replay, not the real-time ability of consumers to keep up. If the retention is 24 hours vs. 48 hours, it doesn't cause a growing live backlog within minutes.
    * **E is Incorrect:** The Lambda invocation payload size affects how many records can be processed per invocation and can influence efficiency, but it is not the root cause when the target write system is clearly throttling.

    > **Key Takeaway:** In streaming backlogs, check all links in the chain—especially downstream write targets—before adding consumer capacity, because adding consumer workers to a saturated sink only amplifies write throttling.


### Question 4 - Multi-Source Data Merge and Data Catalog Governance

A media company generates user engagement data in two environments: a web app reading from **Amazon DynamoDB** and a mobile app reading from **Amazon RDS for PostgreSQL**. The ML team wants to create a unified training dataset in **Amazon S3** by merging daily event records from both sources. Each system assigns its own user identifiers, and some events appear in both systems with conflicting field values (e.g., `last_seen` timestamps). The team wants to use **AWS Glue** to orchestrate this pipeline and ensure downstream ML jobs can discover the merged table.

What are the **TWO** actions the ML team should take to build a reliable, queryable merged dataset? (Select TWO)

- **A)** Use an **AWS Glue crawler** to catalog both source tables into the **AWS Glue Data Catalog** before the merge.
- **B)** Use **AWS Glue Studio** to visually configure an ETL job that resolves source conflicts using a deterministic rule (e.g., "latest timestamp wins" for overlapping fields).
- **C)** Write a custom SQL query in **Amazon QuickSight** to merge the two tables at runtime without storing the merged output.
- **D)** Configure an **AWS Direct Connect** link between the DynamoDB and PostgreSQL endpoints to allow direct database-to-database replication.
- **E)** Move all DynamoDB records into **Amazon S3 Glacier** to reduce data transfer costs during the merge.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A** and **B**

    #### Correct Options Analysis
    * **A is Correct:** Using a Glue crawler to populate the AWS Glue Data Catalog with table definitions gives the Glue ETL job and downstream consumers (e.g., Athena, SageMaker) a consistent metadata reference. The merge job can then reference both sources by catalog table names instead of ad-hoc connection strings.
    * **B is Correct:** Merging two heterogeneous data sources with overlapping and conflicting fields requires a deterministic conflict resolution strategy. AWS Glue ETL (written in Python/PySpark or built visGlue Studio) can implement this logic—e.g., a rule that the more recent timestamp wins for overlapping fields—and write the unified dataset to S3.

    #### Distractor Analysis
    * **C is Incorrect:** QuickSight is a BI visualization tool, not a reusable ETL or catalog layer. It doesn't build the durable, cataloged training dataset that downstream ML jobs require.
    * **D is Incorrect:** AWS Direct Connect is a network connectivity service that links on-premises data centers to AWS. It does not enable database-to-database replication between two managed AWS services and is irrelevant to the actual data merge logic.
    * **E is Incorrect:** S3 Glacier is an archival storage class optimized for infrequent access at low cost. It is not appropriate for online data merge workloads involving daily events with frequent access, and it does not assist with joining DynamoDB and PostgreSQL records.

    > **Key Takeaway:** Cataloging sources and defining explicit conflict-resolution rules are mandatory design decisions for trustworthy multi-source data merges—your merged dataset is only as good as your source-of-truth policy.


### Question 5 - Shared File Storage for Distributed Training

A natural language processing (NLP) team at a biotechnology firm is fine-tuning a large transformer model using **Amazon SageMaker** distributed training (data parallelism). The team runs 8 training instances, each requiring simultaneous and consistent read access to a 200 GB preprocessed dataset stored as TFRecord files. The dataset updates hourly during active retraining cycles, and the job requires low, consistent read latency. **Amazon EBS** provisioned IOPS volumes are considered but rejected because they cannot be attached to multiple instances simultaneously.

Which AWS storage service BEST meets the team's latency and shared access requirements? (Select ONE)

- **A)** Amazon S3 (Standard) with S3 Transfer Acceleration
- **B)** Amazon ElastiCache for Redis with RDB persistence
- **C)** Amazon EFS (Elastic File System) mounted to all training instances
- **D)** Amazon RDS for MySQL with General-Purpose SSD storage
- **E)** Amazon DynamoDB with on-demand capacity mode

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **C**

    #### Correct Options Analysis
    * **C is Correct:** Amazon EFS provides a shared, POSIX-compliant file system that can be mounted concurrently on multiple EC2 and SageMaker training instances. It delivers low-latency file access over a single, unified namespace and can scale throughput automatically as the dataset or number of readers grows. TFRecord files are files on disk/datastore, and EFS matches this file-system access pattern.

    #### Distractor Analysis
    * **A is Incorrect:** While S3 is a common ML dataset source, S3 is object storage with higher read latency than a mounted file system. Repeated high-frequency reads across hundreds of GB of data during training will incur S3 GET request overhead and may throttle or become cost-ineffective. S3 Transfer Acceleration only optimizes upload speed over long distances, not read access for distributed training.
    * **B is Incorrect:** ElastiCache for Redis is an in-memory key-value store, not a general-purpose file system or shared namespace for TFRecord files. Loading 200 GB into Redis memory is expensive and architecturally mismatched.
    * **D is Incorrect:** RDS MySQL is a relational database for structured tables, not a file storage layer. It cannot serve TFRecord file reads to distributed training instances efficiently.
    * **E is Incorrect:** DynamoDB is a NoSQL key-value/document database; it doesn't serve a shared file namespace or large binary files like TFRecords.

    > **Key Takeaway:** For distributed training jobs needing a single shared file namespace with concurrent low-latency reads across multiple instances, use Amazon EFS or Amazon FSx rather than object storage (S3) or block volumes (EBS).


### Question 6 - Compliance-Driven Data Retention and Cost Optimization

A regulated insurance company is building an **Amazon S3**-based data lake for unstructured claim documents and historical policy data. Compliance rules mandate that all raw claim documents be retained immutably for at least 7 years, after which they must be automatically transitioned to a cheaper archival tier. The data will be accessed rarely after the first 90 days; access during the subsequent 7 years is unpredictable (likely a few times per year). The company's security team also requires that no object can be deleted or modified for the full 7-year retention window.

Which **TWO** S3 lifecycle and compliance actions should the company configure? (Select TWO)

- **A)** Create an S3 Lifecycle rule to transition objects to **S3 Glacier Flexible Retrieval** after 90 days, then to **S3 Glacier Deep Archive** after 7 years.
- **B)** Use **Amazon S3 Intelligent-Tiering** to automatically move objects between access tiers based on access patterns.
- **C)** Enable **S3 Object Lock** in **Compliance mode** with a 7-year retention period on the bucket.
- **D)** Use **AWS Backint Agent for SAP HANA** to manage automated backups that expire after 7 years.
- **E)** Set a **S3 Lifecycle delete** rule to permanently remove objects exactly on day 2,555 (7 years).

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A** and **C**

    #### Correct Options Analysis
    * **A is Correct:** A lifecycle rule transitioning objects to S3 Glacier Flexible Retrieval after 90 days (low-activity period) and eventually to S3 Glacier Deep Archive (if needed) optimizes cost while maintaining compliance. In this scenario, Glacier Flexible Retrieval or Deep Archive meets the "rare access after 90 days" pattern.
    * **C is Correct:** S3 Object Lock in Compliance Mode guarantees that no user—including root or administrators—can delete or overwrite objects until the retention period (7 years) expires. This directly satisfies the immutability and non-deletion requirement.

    #### Distractor Analysis
    * **B is Incorrect:** S3 Intelligent-Tiering optimizes costs by moving data between frequent and infrequent access tiers, but it does **not** enforce immutability or prevent deletion. It cannot meet the compliance requirement for non-deletion/non-modification.
    * **D is Incorrect:** AWS Backint Agent is a backup integration for SAP HANA databases, not relevant to S3 object lifecycle or document compliance retention. This option uses an unrelated, non-applicable service.
    * **E is Incorrect:** A lifecycle delete rule will permanently remove objects on day 2,555, which directly **violates** the compliance mandate to retain records immutably for 7 years. The correct approach is retention lock or legal hold, not automatic deletion.

    > **Key Takeaway:** Always map compliance retention requirements to S3 Object Lock (data immutability) and use S3 Lifecycle rules for cost-optimization of storage class transitions—never the other way around.


### Question 7 - Real-Time Feature Lookup Latency and Consistency

A machine learning team at a ride-hailing company uses **Amazon SageMaker Feature Store** to serve features for both training and online inference. The inference system (a set of **Amazon SageMaker real-time endpoints**) requires p95 feature lookup latency under 20 ms for a single entity (a driver or rider). Training jobs run nightly and read the full historical feature set for millions of entities. The feature store is enabled with both **online** and **offline** stores.

Which TWO statements accurately describe how SageMaker Feature Store meets these requirements? (Select TWO)

- **B)** The offline store is served by a high-throughput analytics query engine (Athena/Glue) for batch training reads.
- **C)** The online store stores features in columnar format on S3 with no latency guarantees for inference.
- **D)** Training jobs must read only from the online store to ensure feature consistency.
- **E)** The offline store automatically expires features after 24 hours to reduce storage costs.

    **Correct Answer:** **A** and **B**

    #### Correct Options Analysis
    * **A is Correct:** The SageMaker Feature Store online store is a NoSQL (Cassandra-based) store engineered for single-digit millisecond lookups by `record_id` (primary key) at inference time. It meets p95 < 20 ms latency for entity lookups.
    * **B is Correct:** The offline store is stored in Amazon S3 as Parquet files and can be queried at scale using Amazon Athena, AWS Glue, or Spark. Training jobs read this historical store in batch, which is the expected design pattern.

### Question 8 - Choosing Apache Kafka vs. Kinesis for On-Premises Hybrid Streaming

A global retail enterprise is migrating its streaming analytics pipeline to AWS. The pipeline already ingests 500,000 events/second from on-premises Apache Kafka clusters. The company wants to maintain Kafka compatibility, use the same client libraries, and gradually migrate to AWS without re-architecting its producers or consumers in the next 12 months. The workload requires exactly-once processing semantics for critical financial transactions, and the team needs to scale to 1,000,000 events/sec during Black Friday peaks.

Which AWS service and architecture best satisfies these hybrid and compatibility requirements? (Select ONE)

- **A)** Use **Amazon Kinesis Data Streams** with the Kafka Client Library adapter (`kinesis-client-library`) to emulate Kafka compatibility.
- **B)** Run **Amazon MSK (Managed Streaming for Apache Kafka)** and use **MSK Connect** with Kafka exactly-once semantics.
- **C)** Use **Amazon Managed Service for Apache Flink** to read from Kinesis Data Streams and write to an on-premises Kafka via a custom connector.
- **D)** Replace Kafka with **Amazon SQS** FIFO queues to guarantee exactly-once processing for all events.
- **E)** Replicate Kafka data into **Amazon DynamoDB** Streams and consume via Kinesis Client Library (KCL).

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** Amazon MSK is a fully managed Apache Kafka service that preserves Kafka's native protocol, client libraries, and topic/partition model. The existing on-premises Kafka applications can connect to MSK with the same Kafka APIs, minimizing migration effort. MSK Connect enables integration with Kafka connectors, and the Kafka ecosystem supports exactly-once semantics (EOS) for critical transactions.

    #### Distractor Analysis
    * **A is Incorrect:** Kinesis Data Streams is a proprietary AWS streaming service with its own API. While a Kafka-compatible adapter exists, it is not a drop-in replacement for Kafka client libraries, topic semantics, or exactly-once guarantees. Re-architecting producers and consumers would be necessary.
    * **C is Incorrect:** Amazon Managed Service for Apache Flink (formerly Kinesis Data Analytics) is a stream processing engine (Apache Flink), not a Kafka replacement. It can read from both Kinesis and Kafka, but it doesn't solve the on-premises Kafka compatibility or migration requirement on its own.
    * **D is Incorrect:** Amazon SQS FIFO queues offer exactly-once processing for messages, but they do not implement Kafka's publish-subscribe, partitioning, or consumer group model. Migrating from Kafka to SQS would require a complete consumer/producer rewrite.
    * **E is Incorrect:** DynamoDB Streams is a change data capture (CDC) mechanism for tables, not a Kafka compatibility layer. Replicating Kafka events into DynamoDB and consuming via KCL is architecturally backwards and introduces unnecessary complexity.

    > **Key Takeaway:** For hybrid cloud streaming with Kafka client compatibility, exactly-once semantics, and minimal producer/consumer code changes, Amazon MSK is the default choice over Amazon Kinesis.

    **Correct Answer:** **A** and **C**

    #### Correct Options Analysis
    * **A is Correct:** S3 is the optimal landing zone for massive volumes of unstructured data like images and LiDAR files.     **Correct Answer:** **A** and **C**

    #### Correct Options Analysis
    * **A is Correct:** SageMaker Feature Store is purpose-built for ML feature management.     * **C is Correct:** Amazon OpenSearch Service supports k-NN vector search via the `knn_vector` data type and can efficiently return approximate nearest neighbors with low latency (sub-20 ms) at scale. This is the correct choice for product embedding similarity search.
