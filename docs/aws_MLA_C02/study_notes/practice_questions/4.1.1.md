### Question 4 - Concept Drift vs. Data Drift Identification

A ride-hailing company operates a surge-pricing model that predicts fare multipliers based on features such as time of day, weather, and number of drivers within a geographic cell. The ML team recently observed that **prediction error on the training distribution has remained stable**, but **the relationship between some features (e.g., number of available drivers) and the correct surge price has changed** due to new city regulations.

Which drift detection approach should the team implement to catch this phenomenon? (Select ONE)

* **A)** Configure an input feature drift monitor on the model endpoint to detect distributional shifts in incoming requests.
* **B)** Set up a monthly model evaluation job that compares predictions against actual outcomes using newly labeled data.
* **C)** Use Amazon CloudWatch Anomaly Detection on the endpoint's invocation count metric.
* **D)** Deploy an A/B test comparing the old model with a candidate and monitor revenue per 1000 requests.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** This scenario describes **concept drift**, where the relationship $P(Y|X)$ between inputs (number of drivers, time of day) and the target (surge price) changes, even though the input distribution $P(X)$ remains stable. Model evaluation jobs that compare predictions against newly labeled ground-truth data over time can identify concept drift by tracking predictive accuracy on new data. This directly addresses the described phenomenon.

    #### Distractor Analysis
    * **A is Incorrect:** Input feature drift monitoring (e.g., SageMaker Model Monitor data quality) only detects **data drift** (a shift in $P(X)$). The scenario explicitly states that the input distribution has not changed, so this monitor would not fire an alert and would miss the concept drift.
    * **C is Incorrect:** CloudWatch Anomaly Detection on invocation counts monitors traffic volume, not the relationship between features and labels. A change in surge-pricing regulations would not alter invocation frequency, so this metric would not capture the drift.
    * **D is Incorrect:** A/B testing is used to compare model variants on live traffic under a chosen metric—not specifically for detecting that the underlying ground truth has changed. While revenue metrics might indirectly reflect degradation, A/B testing does not directly identify concept drift as a formal monitoring practice.

    > **Key Takeaway:** Data drift monitors detect changes in input distributions ($P(X)$), while concept drift requires evaluating predictions against fresh ground-truth labels ($P(Y|X)$)—implement model evaluation jobs or tracking of business metrics to catch concept drift.



### Question 5 - Inference Pipeline Anomaly Detection

A logistics company runs a daily batch inference pipeline using **AWS Glue** for data extraction and transform, then invokes a SageMaker endpoint for route-optimization predictions. The team currently monitors only the Glue job success status and the endpoint error rate. One Monday, the Glue job reports **successful completion**, but the endpoint's **error rate spikes to 35%** within an hour. Upon investigation, the team discovers the Glue job silently wrote empty files because the upstream database was unavailable.

Which monitoring improvement would have prevented this failure from going unnoticed until the endpoint errors appeared? (Select ONE)

* **A)** Add CloudWatch alarms on the endpoint's high error rate and low invocation count metrics.
* **B)** Configure an AWS Glue job to retry database extraction up to 10 times before reporting success.
* **C)** Add post-job data quality checks that verify record counts, non-null columns, and schema integrity before allowing downstream inference.
* **D)** Use Amazon SageMaker Model Monitor to detect data drift in the endpoint's input features.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **C**

    #### Correct Options Analysis
    * **C is Correct:** The root cause is that the pipeline monitored job **completion** rather than job **output**. A data quality check after the Glue job—verifying that the output has the expected number of records, non-null critical fields, and valid schema—would have caught the empty partition and blocked downstream inference. This addresses the monitoring gap directly: a successful exit code is not a guarantee of usable output.

    #### Distractor Analysis
    * **A is Incorrect:** Adding alarms on the endpoint's error rate only detects the symptom (failed invocations) after the damage has already occurred. It does not prevent the bad data from reaching the endpoint or alert the team before the error spike.
    * **B is Incorrect:** Retry logic on the Glue job is event-driven, not a monitoring improvement. The upstream database may be unavailable for longer than the retry window, and the job could still successfully finish with empty output after exhausting retries.
    * **D is Incorrect:** SageMaker Model Monitor detects distributional shifts in endpoint input data, but in this case the endpoint is receiving empty/malformed payloads that cause invocation errors. Model Monitor's drift detection would not necessarily catch a discrete batch of empty records.

    > **Key Takeaway:** A successful job exit code does not guarantee usable output—always pair pipeline job monitoring with data quality checks (record counts, schema validation, non-null constraints) to catch upstream failures before they reach inference.



### Question 6 - Amazon Bedrock Model Evaluation Types

The ML team wants to evaluate the model's summarization quality across four dimensions: **accuracy, harmfulness, helpfulness, and coherence**. They need to identify the specific problems in a generated summary and understand why each score was assigned, so they can tune their prompting strategy.

Which evaluation method should the team use? (Select ONE)

* **A)** Automatic model evaluation using task-specific metrics.
* **B)** Human-based model evaluation with a curated team of annotators.
* **C)** Judge-model evaluation using an Amazon Bedrock model as the evaluator.
* **D)** A/B testing using two production variants with weighted traffic distribution.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **C**

    #### Correct Options Analysis
    * **C is Correct:** Judge-model evaluation uses a special "judge" model (an LLM) to score the target model's responses. The team also wants to ensure that **both variants receive the same amount of traffic simultaneously for a fair comparison during the evaluation window**.

Which configuration should the team use? (Select ONE)

* **A)** Set both variants' weights to 50% and configure Amazon CloudWatch alarms on both variants' metrics.
* **B)** Set Variant-A weight to 0 and Variant-B weight to 100, then switch back after a day.

### Question 9 - Drift Detection for Generative AI Embeddings

A global news organization uses **Amazon Bedrock** with a text-embedding model to power a semantic search and content recommendation system. The ML team wants to monitor whether **the distribution of user search queries is drifting** over time, which could affect the quality of retrieval results. The query texts are embedded into vectors before being used for search. The team needs a drift detection method that is **robust in high-dimensional space** and works with the embedded representations.

Which approach should the team implement? (Select ONE)

* **A)** Compare the distribution of current query embeddings against a baseline using the **maximum mean discrepancy (MMD)** statistic, with an alarm triggered when the distance crosses a threshold.
* **B)** Compare the distribution of raw query strings using Levenshtein edit distance between each query and a baseline query set.
* **C)** Use Amazon CloudWatch Anomaly Detection on the number of unique words per query.
* **D)** Run a chi-square test comparing word frequencies between current queries and baseline queries, treating each word as a categorical variable.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Options Analysis
    * **A is Correct:** For high-dimensional embeddings (e.g., 384-dim or 1024-dim vectors), traditional distribution tests like chi-square or Kolmogorov-Smirnov become unreliable due to the curse of dimensionality and the continuous nature of embeddings. Maximum Mean Discrepancy (MMD) is a kernel-based statistic specifically designed to compare distributions in high-dimensional or non-Euclidean spaces. This matches the requirement for a drift detection method robust in high dimensions operating on embedded representations.

    #### Distractor Analysis
    * **B is Incorrect:** Levenshtein edit distance measures string similarity between individual pairs, not distributional differences between groups of queries. It would not capture broader semantic drift in query topics or distribution shifts.
    * **C is Incorrect:** CloudWatch Anomaly Detection on unique word counts per query is a simple aggregate metric that cannot capture semantic shifts in the types of queries users are asking. It also does not operate on embeddings.
    * **D is Incorrect:** A chi-square test on word frequencies treats words as independent categorical variables and is unstable in high-dimensional text data. It also ignores semantic relationships (e.g., "car" and "automobile" are different words but semantically similar) and would not detect drift in query meaning or context.

    > **Key Takeaway:** For drift detection on generative AI embeddings, use distribution-comparison methods like MMD that are designed for high-dimensional spaces—traditional univariate tests fail as dimensionality increases.



### Question 10 - Shadow Variant for Low-Risk Model Evaluation

A critical fraud-detection model serves a financial institution through a **SageMaker endpoint**. The ML team wants to test a new candidate model against live production traffic, but they cannot risk exposing customers to erroneous fraud predictions. The new model must be evaluated on its **predictive accuracy and inference latency under real production load**, but its predictions should not influence any customer-facing decisions.

Which deployment strategy should the team use? (Select ONE)

* **A)** Deploy the candidate as a **shadow variant** on the SageMaker endpoint, where its predictions are logged for offline analysis.
* **B)** Deploy the candidate with 5% traffic weight, monitor the business impact, and increase if performance looks acceptable.
* **C)** Use Amazon Bedrock Model Evaluation with a static validation dataset to score the candidate model before deployment.
* **D)** Deploy the candidate on a separate endpoint and run load tests with synthetic traffic generation.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Options Analysis
    * **A is Correct:** A shadow variant (also called a ghost variant) receives a copy of live production traffic but its predictions are not returned to users. This allows the team to evaluate the candidate model's accuracy and latency under real production load without any customer-facing risk. The predictions are logged for offline analysis and comparison against the production model's actual outcomes.

    #### Distractor Analysis
    * **B is Incorrect:** A 5% traffic weight does expose a small number of real customers to the candidate model's predictions. For a critical fraud-detection system, even a small exposure could result in missed fraud or false alerts. The constraint explicitly prohibits exposing customers to erroneous predictions.
    * **C is Incorrect:** Amazon Bedrock Model Evaluation with a static dataset tests model quality but does not evaluate inference latency or performance under real production load. Static datasets also cannot capture live traffic patterns or seasonal variation.
    * **D is Incorrect:** Load testing on a separate endpoint with synthetic traffic does not evaluate the candidate model's accuracy on real, live production data. It can measure infrastructure latency, but not how well the model performs on actual transactions.

    > **Key Takeaway:** Shadow variants evaluate models on live traffic without user exposure—use them when even small percentages of real traffic pose unacceptable risk; use weighted A/B variants when gradual live exposure provides the best business signal.
