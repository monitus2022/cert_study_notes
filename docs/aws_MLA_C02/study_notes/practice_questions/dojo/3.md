### Question: Orchestrating CI/CD for ML Workloads

**Category:** MLA – Deployment and Orchestration of ML and AI Workflows

**Review Bucket:** 
- [x] Bucket A (Term Mapping)
- [ ] Bucket B (Missed Constraint)
- [ ] Bucket C (Knowledge Gap)

A manufacturing company wants to develop a machine learning (ML) model for predicting equipment failures and optimizing maintenance schedules. The company has a team of data scientists who have developed custom Python scripts for data preprocessing, feature engineering, and model training. The company wants to leverage AWS services to build, train, and deploy its ML models in a scalable and automated manner.

Which AWS service should the company use to orchestrate continuous integration and continuous deployment (CI/CD) pipeline?

* **A)** AWS CodePipeline
* **B)** Amazon CodeGuru Reviewer
* **C)** AWS CodeDeploy
* **D)** AWS CodeBuild

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** AWS CodePipeline is a fully managed continuous integration and continuous delivery (CI/CD) service. It is designed to automate the build, test, and deploy phases of your release process. This makes it the correct "orchestration" tool, as it can string together other services (like CodeBuild and CodeDeploy) into a single automated workflow for the ML models.

    #### Distractor Analysis
    * **B is Incorrect:** Amazon CodeGuru Reviewer is an automated code review service that uses machine learning to identify critical issues, security vulnerabilities, and hard-to-find bugs in your code. It is not used to *orchestrate* pipelines but rather to analyze code quality *within* a build stage.
    * **C is Incorrect:** AWS CodeDeploy is a deployment service that automates code deployments to any instance (EC2, Lambda, on-premises). While it is often triggered *by* a pipeline, it is just one component of the CI/CD process, not the overall orchestration engine that coordinates the different stages.
    * **D is Incorrect:** AWS CodeBuild is a fully managed build service that compiles source code, runs tests, and produces software packages. Like CodeDeploy, it is a critical part of a pipeline but serves as a specific build stage rather than the orchestrator that ties stages (build -> deploy) together.

    > **Key Takeaway:** Understand the distinct roles of AWS Developer/Tooling services. **CodePipeline** is the orchestrator that integrates services like **CodeBuild** (Build) and **CodeDeploy** (Deploy). If the question asks for a service to "orchestrate" or "automate steps," CodePipeline is usually the right choice.

??? warning "self-notes"
    Code pipeline = CI/CD
    Code Deploy = IaC for infra

### Question: SageMaker Pipelines Decorators – `@step` vs `@remote`

**Category:** MLA – Deployment and Orchestration of ML and AI Workflows  
**Review Bucket:** [ ] Bucket A (Term Mapping) | [ ] Bucket B (Missed Constraint) | [x] Bucket C (Knowledge Gap)

A Machine Learning Engineer is working on an Amazon SageMaker Pipelines pipeline to build and deploy a model. The pipeline was provisioned using SageMaker::CreatePipeline and is tracked through SageMaker Experiments for reproducibility. The pipeline includes data processing, model training, and model deployment steps. The ML Engineer needs to incorporate a custom data validation step to ensure the quality of the input data before proceeding with model training.

Which approach should the ML Engineer take to add the custom data validation step to the existing SageMaker Pipelines pipeline?

* **A)** Create a custom Python function for data validation and use the @step decorator to integrate it into the pipeline. Add the decorated function as a step in the pipeline definition.
* **B)** Create a custom data validation script and use the TransformStep definition to integrate it into the pipeline.
* **C)** Create a custom AWS Glue job that performs the data validation step, and use the GlueJobStep definition to add the Glue job as a step in the pipeline.
* **D)** Create a custom Python function for data validation and use the @remote decorator to run it remotely. Add the decorated function as a step in the pipeline definition.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** The **`@step` decorator** in the SageMaker Python SDK converts a standard Python function directly into a step within a SageMaker Pipeline DAG. This provides a lightweight, pythonic way to incorporate custom data validation or processing steps without explicitly managing container specifications or external orchestrators.

    #### Distractor Analysis
    * **B is Incorrect:** `TransformStep` is used to run batch transform jobs on datasets to generate offline predictions, not for running custom data validation code.
    * **C is Incorrect:** While AWS Glue can perform data validation, bringing in external Glue resources adds unnecessary operational complexity compared to native Python function decoration via `@step`.
    * **D is Incorrect:** The **`@remote` decorator** executes a Python function as a standalone remote SageMaker Training Job. It is used for running code remotely from local notebooks, not for defining steps inside a SageMaker Pipelines DAG.

    > **Key SDK Distinction:** Use **`@step`** to turn a Python function into a **SageMaker Pipeline Step**. Use **`@remote`** to execute a Python function as a standalone **Remote SageMaker Training Job**.

??? warning "self-notes"
    | Step Primitive / Class | How It Is Defined | Best Used For |
    | --- | --- | --- |
    | **`@step` Decorator** | Native Python function with `@step` annotation. | Quick, pythonic custom data validation, light transformation, or evaluation logic directly in a pipeline. |
    | **`ProcessingStep`** | Uses a `ScriptProcessor` or `SKLearnProcessor` with an S3 input/output config. | Heavy-duty, containerized ETL data preprocessing and feature engineering (e.g., Spark, Pandas, Scikit-Learn). |
    | **`LambdaStep`** | References an AWS Lambda ARN or inline function code. | Lightweight, serverless operational triggers (e.g., sending a Slack notification, updating a database record). |
    | **`ConditionStep`** | Evaluates a logical expression (e.g., `F1 > 0.85`). | Branching pipeline execution (e.g., if model metrics exceed a threshold, register the model; otherwise, fail). |
    | **`RegisterModel`** | References a `ModelPackageGroup`. | Automatically publishing a trained model artifact to the SageMaker Model Registry for approval. |

### Question: SageMaker Production Variants for Multi-Model A/B Testing

**Category:** MLA – Deployment and Orchestration of ML and AI Workflows  
**Review Bucket:** [ ] Bucket A (Term Mapping) | [x] Bucket B (Missed Constraint) | [ ] Bucket C (Knowledge Gap)

A logistics company uses Amazon SageMaker AI to predict delivery delays in real time, while Amazon DynamoDB maintains current shipment information. Recent performance evaluations revealed a decline in prediction accuracy, prompting the development of three updated models. The company wants to perform A/B testing to the updated models and comparing accuracy before selecting a replacement. The solution must minimize infrastructure management.

Which approach will satisfy these requirements while minimizing operational effort?

* **A)** Create three separate SageMaker AI endpoints for the updated models. Use Amazon API Gateway deployment stages and canary settings to control the percentage of incoming requests.
* **B)** Configure a single SageMaker AI endpoint with three production variants, one for each updated model. Specify the traffic distribution for each variant and adjust the weights based on the evaluation results.
* **C)** Configure SageMaker AI shadow tests to evaluate each updated model against the existing production model. Mirror selected inference requests and compare the recorded predictions to determine model accuracy.
* **D)** Update the existing SageMaker AI endpoint with each revised model using deployment guardrails. Configure canary traffic shifting to evaluate prediction accuracy during each deployment.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Option Analysis
    * **B is Correct:** SageMaker natively supports **A/B testing** by configuring multiple **Production Variants** on a single endpoint. You specify traffic weights (`InitialVariantWeight`) to split live incoming requests across all three updated models without deploying separate endpoints or managing external routing logic, minimizing operational management.

    #### Distractor Analysis
    * **A is Incorrect:** Managing three separate endpoints and configuring custom routing via API Gateway introduces heavy operational overhead and violates the constraint to minimize infrastructure management.
    * **C is Incorrect:** Shadow testing duplicates requests asynchronously so candidate responses are dropped rather than returned to callers. The prompt explicitly requests A/B testing across the updated models.
    * **D is Incorrect:** Deployment guardrails with canary traffic shifting is a gradual rollout strategy for replacing an old model version with a new one, not a multi-candidate A/B test.

    > **Key Takeaway:** For **A/B testing multiple candidate models with minimal infrastructure overhead**, use **multiple Production Variants on a single SageMaker Endpoint**.
