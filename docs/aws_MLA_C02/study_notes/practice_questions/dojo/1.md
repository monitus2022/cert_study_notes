### Question: Storage for Distributed Deep Learning Training

**Category:** MLA – Data Preparation for ML and AI  

**Review Bucket:** 
- [ ] Bucket A (Term Mapping)
- [ ] Bucket B (Missed Constraint)
- [X] Bucket C (Knowledge Gap)

A research institute is developing a deep-learning model to analyze satellite images for weather forecasting. The dataset consists of millions of high-resolution images stored in a format that requires file-level access. The model training process involves multiple GPU-powered Amazon EC2 instances that require high throughput and low latency access to the dataset for efficient distributed training.

Which AWS storage solution is the MOST suitable to support the deep-learning model training process?

* **A)** Amazon FSx for Lustre
* **B)** Amazon FSx for Windows File Server
* **C)** Amazon Elastic File System (Amazon EFS)
* **D)** Amazon Simple Storage Service (Amazon S3)

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** Amazon FSx for Lustre is a fully managed, high-performance file system designed for workloads such as machine learning, high-performance computing (HPC), and media processing. It provides POSIX-compliant file-level access, sub-millisecond latencies, and high throughput, making it ideal for distributed training across multiple GPU instances. It can also be linked to Amazon S3 to ingest data seamlessly.

    #### Distractor Analysis
    * **B is Incorrect:** Amazon FSx for Windows File Server is built on Windows Server and is intended for Windows-based workloads, not for Linux-based GPU training environments. It does not offer the same level of performance for HPC or ML workloads as FSx for Lustre.
    * **C is Incorrect:** Amazon EFS is a scalable, general-purpose file system, but it is not optimized for the extreme throughput and low-latency requirements of distributed deep learning training. It may become a bottleneck when many GPU instances access large datasets concurrently.
    * **D is Incorrect:** Amazon S3 is object storage, not a file system. While it can be used with tools like S3 mountpoints, it does not natively provide the file-level access, high throughput, and low latency needed for efficient distributed training without additional complexity and potential performance trade-offs.

    > **Key Takeaway:** For high-performance, file-level access with low latency and high throughput in distributed ML training, choose **Amazon FSx for Lustre**. It is purpose-built for HPC and ML workloads, unlike general-purpose file systems or object storage.

### Question: AWS Services for Real-Time Data Ingestion and Processing

**Category:** MLA – Data Preparation for ML and AI

**Review Bucket:** 
- [ ] Bucket A (Term Mapping)
- [ ] Bucket B (Missed Constraint)
- [X] Bucket C (Knowledge Gap)

A machine learning engineer is working on an AWS project involving real-time fraud detection for an online payment platform. The platform generates a continuous stream of transaction data that needs processing and analysis using a pre-trained model on Amazon SageMaker AI.

Which combination of AWS services should the machine learning engineer choose to ingest and process the real-time transaction data before delivering it to SageMaker AI for inference? (Select TWO.)

* **A)** Amazon Managed Service for Apache Flink
* **B)** Amazon Managed Streaming for Apache Kafka (Amazon MSK)
* **C)** AWS Glue
* **D)** Amazon Data Firehose
* **E)** Amazon Kinesis Data Streams

??? note "Click to reveal Answer & Explanation"
    **Correct Answers:** **A, E**

    #### Correct Option Analysis
    * **A is Correct:** Amazon Managed Service for Apache Flink (formerly Amazon Kinesis Data Analytics) is a fully managed service for processing streaming data in real time using Apache Flink. It can consume data from Kinesis Data Streams or MSK, perform transformations, aggregations, and feature engineering in real-time, and then invoke SageMaker endpoints for inference.
    * **E is Correct:** Amazon Kinesis Data Streams is a highly scalable and durable real-time data streaming service designed to continuously capture gigabytes of data per second from sources such as payment transactions. It serves as the ingestion layer before processing and inference.

    #### Distractor Analysis
    * **B is Incorrect:** Amazon MSK is a fully managed Apache Kafka service that can capture streaming data, but it is primarily an ingestion and buffering service, not a processing service. It does not natively integrate with SageMaker for inference without building custom Kafka consumers. Since Kinesis Data Streams is already a correct ingestion option, MSK as a processing option is redundant and less optimal for SageMaker integration.
    * **C is Incorrect:** AWS Glue is a serverless data integration service primarily designed for batch ETL (Extract, Transform, Load), data cataloging, and periodic data processing. It is not suitable for real-time streaming inference.
    * **D is Incorrect:** Amazon Data Firehose (formerly Kinesis Data Firehose) is designed to capture, transform, and load streaming data into data lakes, warehouses, and analytics services (e.g., S3, Redshift, OpenSearch). It does not natively support invoking SageMaker endpoints for real-time inference and is primarily for data delivery rather than processing before inference.

    > **Key Takeaway:** For real-time ML inference pipelines in AWS, choose **Kinesis Data Streams** for ingestion and **Amazon Managed Service for Apache Flink** for stream processing (feature engineering, transformations) before invoking SageMaker endpoints.

??? warning "self-notes"

    - Glue: Batch ETL only
    - MSK: Can handle streaming, but mainly used for real-time data transfer between apps and system. No integration with Sagemaker

    | If the Scenario Requires... | Select This Service | Why / Why Not Others |
    | --- | --- | --- |
    | **Sub-second real-time processing & complex transformations** | **Kinesis Data Streams + Apache Flink** | Standard AWS native pair for real-time feature engineering & instant SageMaker inference. |
    | **Near real-time continuous loading into S3, Redshift, or OpenSearch** | **Amazon Data Firehose** | Firehose is for *delivery/loading* with mandatory buffering (minimum 60s or 1MB). **Not** for sub-second pre-inference processing. |
    | **Micro-batch / Spark-based ETL on streaming data** | **AWS Glue Streaming** | Based on Spark Streaming (micro-batches in seconds/minutes). Higher latency than Flink; best for ETL data lake ingestion. |
    | **Existing open-source Kafka ecosystem / low-level control** | **Amazon MSK** | Choose MSK **only** if the scenario explicitly mentions "Kafka," "Zookeeper," or migrating an existing Apache Kafka pipeline. |

    > **Sub-Second Real-Time Analytics/Features:** `Kinesis Data Streams` $\rightarrow$ `Apache Flink` $\rightarrow$ `SageMaker Endpoint`
    > **Data Lake Dump / Near Real-Time S3 Storage:** `Kinesis Data Streams` $\rightarrow$ `Amazon Data Firehose` $\rightarrow$ `Amazon S3`

### Question: Data Preparation for ML and AI

**Category:** MLA – Data Preparation for ML and AI

**Review Bucket:** 
- [X] Bucket A (Term Mapping)
- [ ] Bucket B (Missed Constraint)
- [ ] Bucket C (Knowledge Gap)

A retail company is building an ML model to forecast weekly product demand across multiple stores. An ML engineer uses Amazon SageMaker Data Wrangler to prepare several years of sales records that are maintained chronologically. The source data is cataloged in AWS Glue before being imported for processing.

The ML engineer needs to divide the dataset for model development so that the validation results reflect how the model is expected to perform as additional sales periods become available.

Which SageMaker Data Wrangler split transform should the ML engineer use?

* **A)** A randomized split with a fixed random seed to distribute sales records across the training and validation datasets.
* **B)** A stratified split based on predefined price ranges to preserve the distribution of product prices across both datasets.
* **C)** A stratified split based on store location to preserve the proportion of records from each geographic area across both datasets.
* **D)** An ordered split that divides the records according to the existing arrangement of the dataset.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **D**

    #### Correct Option Analysis
    * **D is Correct:** The data represents a time series of weekly sales records. To simulate real-world conditions where future sales periods become available, the validation set should consist of the **most recent chronological periods**, while training uses older periods. SageMaker Data Wrangler’s **ordered split** divides records based on the existing chronological order of the dataset, preventing data leakage from future periods into the training set.

    #### Distractor Analysis
    * **A is Incorrect:** A randomized split shuffles records, causing future sales periods to leak into the training data. This does not reflect how the model will be used on unseen future data and artificially inflates validation metrics.
    * **B is Incorrect:** A stratified split based on price ranges (or any non-temporal feature) also breaks the chronological ordering of the data. Random distribution of future and past records across both datasets leaks future information into the training process.
    * **C is Incorrect:** Stratifying by store location preserves the proportion of geographic data between splits, but like options A and B, it shuffles time-based records. This violates the requirement to validate on future periods and leads to data leakage in time-series forecasting.

    > **Key Takeaway:** For time-series forecasting, always use a **temporal/ordered split** (train on past, validate on future) rather than random or stratified splits, which can cause **data leakage**.

### Question: SageMaker Data Wrangler & Time-Series Imputation

**Category:** MLA – Data Preparation for ML and AI  
**Review Bucket:** Modified question from Dojo for revision

A logistics company is building a route optimization model using historical time-series delivery data stored in Amazon Redshift. An inspection reveals missing values across several time-dependent features. The ML team wants to implement a managed data preparation pipeline using Amazon SageMaker AI that connects directly to Redshift, handles the missing time-series values without introducing data leakage, and requires minimal custom code and operational overhead.

Which solution should the ML engineer implement?

* **A)** Connect SageMaker Data Wrangler directly to Amazon Redshift, configure a time-series transform using Forward Fill (or Interpolation) on the missing values, and export the feature pipeline to a SageMaker Training Job.
* **B)** Connect SageMaker Data Wrangler directly to Amazon Redshift, configure the built-in Numeric Impute transform using the global dataset Mean, and export the feature pipeline to a SageMaker Training Job.
* **C)** Create a SageMaker Processing Job with a custom Python/Pandas container that queries Redshift via the Redshift Data API, applies `df.fillna(method='ffill')`, and saves the cleaned dataset to Amazon S3.
* **D)** Ingest the raw Redshift data into an Amazon SageMaker Feature Store online store and enable SageMaker Clarify to automatically detect and impute missing feature values during ingestion.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** **SageMaker Data Wrangler** natively connects to Amazon Redshift for data ingestion and provides built-in time-series transformations. Using **Forward Fill** or time-aware interpolation handles missing values appropriately without causing lookahead bias (data leakage), fulfilling the requirement for minimal custom code and low operational overhead.

    #### Distractor Analysis
    * **B is Incorrect:** Global mean/median imputation on time-series data causes **data leakage** because global statistics incorporate future data points into historical timestamps.
    * **C is Incorrect:** While SageMaker Processing can perform this task, writing custom Python code and managing container execution introduces unnecessary operational and maintenance overhead compared to Data Wrangler's managed native transformations.
    * **D is Incorrect:** SageMaker Clarify evaluates models and datasets for bias and explainability (SHAP values); it does not perform automated data imputation on Feature Store ingestion.

    > **Key Takeaway:** For **time-series data prep with minimal custom code**, use **SageMaker Data Wrangler with Forward Fill/Interpolation** to avoid data leakage. Avoid global mean/median imputation on temporal datasets.

### Question: Redacting PII from Identity Documents for ML

**Category:** MLA – Data Preparation for ML and AI

**Review Bucket:** 
- [X] Bucket A (Term Mapping)
- [X] Bucket B (Missed Constraint)
- [ ] Bucket C (Knowledge Gap)

A global travel services company processes identity documents submitted as part of customer verification workflows. The company uses Amazon Textract to extract text from scanned passport pages. The extracted data is stored in Amazon S3 before being incorporated into a dataset for an ML workload.

An ML engineer must redact passport numbers from the extracted text before the dataset is used for model training. The company wants to avoid custom processing logic and reduce ongoing maintenance.

Which implementation would satisfy the requirements with minimal operational management?

* **A)** Submit the extracted text to an asynchronous Amazon Comprehend PII analysis job. Configure the output settings to replace detected passport numbers with masking characters.
* **B)** Call the Amazon Comprehend DetectPiiEntities API to locate passport numbers in the extracted text. Invoke AWS Lambda to mask the character ranges returned by the API.
* **C)** Use Textract with the AnalyzeDocument API and the FORMS feature to identify passport number fields. Use the detected key-value pairs to locate and mask passport numbers.
* **D)** Configure an Amazon Macie sensitive data discovery job for the S3 objects. Use the resulting findings to identify files containing passport numbers and initiate redaction processing.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **A**

    #### Correct Option Analysis
    * **A is Correct:** Amazon Comprehend supports native PII detection and redaction. An asynchronous analysis job for PII can be configured to directly output a modified version of the text with detected entities (like passport numbers) replaced with masking characters. This requires no custom processing logic (no Lambda functions to write or maintain) and is fully managed by AWS. The asynchronous nature is also ideal for processing large batches of documents in S3.

    #### Distractor Analysis
    * **B is Incorrect:** While `DetectPiiEntities` correctly identifies the PII and its character offsets, it only returns the location of the PII. This option requires building and maintaining a custom AWS Lambda function to perform the actual masking, violating the "avoid custom processing logic" requirement.
    * **C is Incorrect:** Using Textract's `FORMS` feature to detect key-value pairs is a valid text extraction technique, but it doesn't natively redact data. You would still need custom logic to parse the response and overwrite the data. Moreover, Amazon Comprehend PII detection is specifically designed to find entities like passport numbers regardless of their location in the document, making it a better fit than relying on particular field names.
    * **D is Incorrect:** Amazon Macie is used for **discovery** and **alerting** on sensitive data in S3 buckets (e.g., security, compliance). It is not an appropriate service for modifying or processing data. This option would require a complex integration (triggering a Lambda from Macie findings to perform redaction), which adds operational overhead rather than minimizing it.

    > **Key Takeaway:** For native PII identification **and** masking without writing code, use **Amazon Comprehend's native redaction capabilities** (available via the console or API) rather than building a pipeline. Macie is for visibility/compliance, not data transformation.
