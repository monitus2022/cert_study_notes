| **### Question 1 - Data Format and Storage Cost Optimization**<br><br>A machine learning team is building a data lake on Amazon S3 to store 50 TB of historical customer transaction data. Data scientists will use Amazon Athena to run ad-hoc analytical queries that typically filter on 3-4 specific columns out of 50 available columns. The team must optimize the storage solution for the **lowest query cost** and **highest performance** for this specific access pattern.<br><br>Which storage configuration and file format should the team implement? (Select ONE)<br><br>- **A)** Store the data as uncompressed CSV files and use Amazon S3 Standard storage.<br>- **B)** Store the data as JSON files and partition them by transaction date.<br>- **C)** Store the data in Apache Parquet format with Snappy compression and enable S3 Object Metadata for column stats.<br>- **D)** Store the data in ORC format but keep it in Amazon EBS volumes attached to an EC2 instance running Athena.<br>- **E)** Compress the CSV files into GZIP archives and store them in S3 Standard-Infrequent Access (S3 Standard-IA). | **Correct Answer:** **C**<br><br>**Correct Option Analysis:**<br>- **C is Correct:** Apache Parquet is a columnar storage format. When Athena queries a subset of columns, Parquet enables column pruning, meaning Athena only reads the required columns from S3. This drastically reduces the amount of data scanned, lowering query costs (Athena charges by TB scanned) and improving performance. Snappy compression further reduces storage costs while maintaining fast read speeds.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Uncompressed CSV is a row-oriented format. Athena must scan all columns in every row to execute the query, resulting in maximum data scanned and highest cost.<br>- **B is Incorrect:** JSON is also row-oriented. While partitioning by date helps filter out unneeded files, scanning within the files will still read all columns, incurring unnecessary costs.<br>- **D is Incorrect:** Athena cannot query data directly from EBS volumes; it is designed to query data in S3.<br>- **E is Incorrect:** While GZIP reduces storage and scan size, it is still a row-oriented CSV format. The query engine cannot perform column pruning on GZIP-compressed CSVs, making it slower and more costly than columnar formats for analytical queries.<br><br>> **Key Takeaway:** For analytical queries that touch a subset of columns, always use columnar formats like Parquet or ORC to enable column pruning and minimize data scanned in Athena. |

It provides a single shared file namespace and requires minimal operational overhead, natively integrating with SageMaker's distributed training configurations.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** EBS volumes are block storage devices that can only be attached to a single instance at a time, making them unsuitable for multi-instance concurrent access.<br>- **C is Incorrect:** While S3 Mountpoint allows mounting S3 as a file system, it is optimized for high-throughput object storage, not a true POSIX-compliant shared file system, and may introduce complexities for random read patterns common in ML training.<br>- **D is Incorrect:** FSx for Lustre is an excellent choice for high-performance computing and ML training, but it introduces higher operational overhead (managing file system configurations and metadata) compared to the serverless nature of EFS.<br>- **E is Incorrect:** RDS is a relational database and cannot be mounted as a shared file system for ML datasets.<br><br>> **Key Takeaway:** Amazon EFS provides a simple, serverless, shared file system ideal for distributed SageMaker training jobs needing concurrent read access to a shared dataset. |

| **### Question 5 - Data Compliance and Zero Retention**<br><br>A healthcare startup is building an ML pipeline to process highly sensitive patient records. Compliance regulations mandate that the raw data must be encrypted at rest using customer-managed keys (CMKs) and must be automatically deleted exactly 30 days after ingestion. The processing pipeline must have **zero data retention** after the 30-day period.<br><br>Which combination of S3 features fulfills these requirements with the least operational overhead? (Select TWO)<br><br>- **A)** Enable SSE-S3 encryption on the S3 bucket.<br>- **B)** Enable SSE-KMS encryption on the S3 bucket and specify a customer-managed KMS key.<br>- **C)** Configure an S3 Lifecycle rule to expire objects after 30 days.<br>- **D)** Enable S3 Object Lock in Governance Mode for 30 days.<br>- **E)** Configure an AWS Lambda function triggered by EventBridge to delete objects daily. | **Correct Answers:** **B** and **C**<br><br>**Correct Options Analysis:**<br>- **B is Correct:** SSE-KMS with a customer-managed key (CMK) fulfills the requirement for at-rest encryption using keys controlled by the customer, which is standard for healthcare compliance.<br>- **C is Correct:** An S3 Lifecycle rule to expire (delete) objects after 30 days natively and automatically deletes the data without requiring custom code, fulfilling the zero data retention requirement with the least operational overhead.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** SSE-S3 uses AWS managed keys, not customer-managed keys (CMKs), violating the compliance mandate.<br>- **D is Incorrect:** S3 Object Lock is used for Write-Once-Read-Many (WORM) protection to prevent objects from being deleted or overwritten for a compliance period. | **### Question 10 - Cost-Effective Storage for Infrequently Accessed ML Data**<br><br>A retail company has accumulated 100 TB of historical sales data in Amazon S3 Standard. This data is used as a fallback dataset for re-training ML models, which only happens once a year.
