| **### Question 1 - SageMaker Notebook Access to S3 Training Data**<br><br>A machine learning engineering team is setting up an environment for a new project using **Amazon SageMaker Notebooks**. The notebooks must read raw training datasets stored in a specific Amazon S3 bucket and write processed data back to a different prefix in the same bucket. The security team mandates that the solution follows the principle of **least privilege** and prohibits the use of long-lived credentials.<br><br>Which approach satisfies these requirements with the **least operational overhead**?<br><br>- **A)** Attach the `AmazonS3FullAccess` managed policy to the IAM user account that the data scientists use to log in to the SageMaker domain.<br>- **B)** Create an IAM execution role for the SageMaker notebook instance with a custom policy allowing `s3:GetObject` on the input data prefix and `s3:PutObject` on the output data prefix.<br>- **C)** Generate a pair of long-term AWS access keys for an IAM user and store them in the notebook's `.bashrc` file to be used by the processing scripts.<br>- **D)** Configure a public-read and public-write bucket policy on the specific S3 bucket so the notebook can access the data without needing IAM credentials. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Attaching a custom IAM execution role to the SageMaker notebook allows the notebook to assume temporary, automatically rotated credentials. Scoping the `s3:GetObject` and `s3:PutObject` actions to only the specific input and output prefixes adheres strictly to the principle of least privilege.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** `AmazonS3FullAccess` grants permissions to all S3 buckets and objects in the account, which violates the least privilege requirement. Attaching policies to IAM users rather than roles is also an anti-pattern for AWS service access.<br>- **C is Incorrect:** Embedding long-term access keys in configuration files is a severe security risk and explicitly violates the constraint prohibiting long-lived credentials.<br>- **D is Incorrect:** Making an S3 bucket public is a massive security vulnerability and violates standard data security compliance for enterprise ML workloads.<br><br>> **Exam Tip / AWS Best Practice:** Always use IAM roles for AWS service interactions (like SageMaker Notebooks) and scope S3 permissions down to specific bucket ARNs and prefixes. |

Scoping these permissions specifically to the input and output bucket ARNs follows the principle of least privilege.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** While `AmazonS3ReadOnlyAccess` allows reading the data, it does not grant the `s3:PutObject` permission required for the training job to write the model artifacts to the output S3 bucket.<br>- **C is Incorrect:** Using root account credentials is a major security anti-pattern. The company's security policy requires that the application's IAM role is configured with **least privilege** and can only invoke this specific foundation model.<br><br>Which IAM policy statement will meet these requirements?<br><br>- **A)** Allow `bedrock:InvokeModel` on resource `"arn:aws:bedrock:*::foundation-model/*"`.<br>- **B)** Allow `bedrock:InvokeModel` on resource `"arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-3-sonnet"`.<br>- **C)** Allow `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` on resource `"*"`.<br>- **D)** Allow `bedrock:*` on resource `"arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-3-sonnet"`. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** This policy statement grants exactly the required permission (`bedrock:InvokeModel`) and restricts access solely to the specific model ARN (`anthropic.claude-3-sonnet` in `us-east-1`), adhering perfectly to the principle of least privilege.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Using a wildcard (`*`) for the foundation model ID allows the EC2 instance to invoke *any* available Bedrock foundation model, which violates the least privilege constraint.<br>- **C is Incorrect:** Allowing `InvokeModelWithResponseStream` is unnecessary if the application only requires standard synchronous invocation. | **### Question 4 - Encrypting and Securing Model Artifacts in S3**<br><br>A financial services company stores trained ML model artifacts in an Amazon S3 bucket. Compliance policies mandate that the artifacts must be encrypted using a customer-managed key in AWS KMS. Furthermore, data scientists must be able to download and evaluate the models but must **not** be permitted to delete any artifacts.<br><br>Which combination of configurations provides the required security and least privilege? (Select TWO)<br><br>- **A)** Enable SSE-KMS encryption on the S3 bucket using the default AWS managed key (`aws/s3`).<br>- **B)** Enable SSE-KMS encryption on the S3 bucket using a customer-managed key (CMK).<br>- **C)** Grant the data scientists' IAM group `s3:GetObject`, `s3:PutObject`, and `s3:DeleteObject` permissions.<br>- **D)** Grant the data scientists' IAM group `s3:GetObject` and `kms:Decrypt` permissions scoped to the S3 bucket and the CMK.<br>- **E)** Create an S3 bucket policy that grants `s3:GetObject` to the public for auditing purposes. | **Correct Answers:** **B** and **D**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Compliance explicitly requires the use of a customer-managed key (CMK) for SSE-KMS encryption, not the default AWS managed key.<br>- **D is Correct:** To read the encrypted model artifacts, the data scientists need `s3:GetObject` on the bucket and `kms:Decrypt` on the CMK. By omitting `s3:DeleteObject`, they are prevented from deleting artifacts, satisfying the least privilege and operational constraints.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** While SSE-KMS is used, relying on the AWS managed key does not fulfill the compliance mandate requiring a *customer-managed* key.<br>- **C is Incorrect:** Granting `s3:DeleteObject` directly violates the constraint that data scientists must not be able to delete artifacts.<br>- **E is Incorrect:** Public read access is a severe security vulnerability and violates standard enterprise security compliance for proprietary model artifacts.<br><br>> **Exam Tip / AWS Best Practice:** When using SSE-KMS with CMKs, users need both S3 read permissions and KMS decrypt permissions. To prevent deletion, simply omit the `s3:DeleteObject` action from the IAM policy. |
| **### Question 5 - Secure Database Access in SageMaker Pipelines**<br><br>An Amazon SageMaker Pipeline includes a processing step that needs to connect to an Amazon RDS PostgreSQL database to extract feature data. The database credentials are stored securely in **AWS Secrets Manager**. The pipeline must be configured with **least privilege access** to retrieve the credentials.<br><br>How should the ML engineer configure the pipeline to securely access the database credentials without over-provisioning permissions?<br><br>- **A)** Attach the `SecretsManagerReadWrite` AWS managed policy to the SageMaker pipeline execution role.<br>- **B)** Create an inline policy for the pipeline execution role allowing `secretsmanager:GetSecretValue` exclusively on the ARN of the specific database secret.<br>- **C)** Hardcode the database username and password directly into the SageMaker Processing script's Python code.<br>- **D)** Store the database credentials as environment variables in the SageMaker Pipeline definition JSON. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Using an inline policy with `secretsmanager:GetSecretValue` restricted to the specific secret ARN ensures the pipeline can only read the exact credential it needs, adhering strictly to least privilege. The pipeline runtime role will assume these permissions to fetch the secret dynamically.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** `SecretsManagerReadWrite` grants read and write access to *all* secrets in the account, which is a massive over-provisioning of privileges and violates least privilege.<br>- **C is Incorrect:** Hardcoding credentials in scripts is a severe security anti-pattern that exposes sensitive data in source control and image layers.<br>- **D is Incorrect:** Storing credentials as plaintext environment variables in the pipeline definition JSON is insecure and does not utilize AWS Secrets Manager as required.<br><br>> **Exam Tip / AWS Best Practice:** For workloads needing secrets, scope the IAM role's `secretsmanager:GetSecretValue` permission down to the exact Secret ARN. Never use broad Secrets Manager managed policies. |

Explicitly deny `s3:*`.<br>- **B)** Allow `sagemaker:InvokeEndpoint` on `"*"` and `s3:GetObject` on the training data bucket ARN.<br>- **C)** Attach the `AmazonSageMakerFullAccess` policy to grant endpoint access.<br>- **D)** Allow `sagemaker:CreateEndpoint` and `sagemaker:InvokeEndpoint` on the endpoint ARN. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** This policy explicitly grants the only required action (`sagemaker:InvokeEndpoint`) and restricts it to the exact endpoint ARN. Adding an explicit deny for S3 ensures the microservice cannot inadvertently read the training data, perfectly matching the security constraints.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Granting `sagemaker:InvokeEndpoint` on `"*"` violates least privilege by allowing invocation of any endpoint in the account.
