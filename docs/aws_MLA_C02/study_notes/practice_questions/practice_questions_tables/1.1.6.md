| **### Question 1 - AWS Glue Job Bookmarks for Incremental Merges**<br><br>A retail company is building an ML pipeline to merge daily transaction logs (JSON) stored in an Amazon S3 bucket with customer profile data (Parquet) stored in another S3 bucket. The merged dataset must be written to a target S3 bucket in Apache Parquet format. The data engineering team requires the solution to process only newly added or updated records on each pipeline run to minimize compute costs, with the least operational overhead.<br><br>Which solution meets these requirements?<br><br>- **A)** Use an AWS Glue ETL job with job bookmarks enabled.<br>- **B)** Use an AWS Lambda function triggered by Amazon EventBridge to read the S3 objects and write the merged output.<br>- **C)** Use an Amazon EMR cluster with a custom Spark application and a manual state tracking table in DynamoDB.<br>- **D)** Use an AWS Glue Crawler to merge the data and write it to the target S3 bucket. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** AWS Glue ETL jobs natively support job bookmarks. Bookmarks track the state of the job and automatically process only new or updated data since the last run, eliminating the need to manually track state or reprocess the entire dataset.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** AWS Lambda has execution time limits (15 minutes) and memory constraints that make it unsuitable for large data merges. It also lacks native state tracking for incremental processing without custom DynamoDB/DDB code.<br>- **C is Incorrect:** Using Amazon EMR with a custom state tracking table introduces significant operational overhead compared to AWS Glue's serverless model and native bookmarking.<br>- **D is Incorrect:** AWS Glue Crawlers only discover schema and populate the Glue Data Catalog; they do not perform data transformations or merge datasets.<br><br>> **Exam Tip / AWS Best Practice:** AWS Glue job bookmarks are the native, serverless way to handle incremental loads and merge only new data without reprocessing the entire dataset. |
| **### Question 2 - Schema Standardization and Merging**<br><br>An ML engineering team needs to merge two large datasets in Amazon S3 for model training. Dataset A is in JSON format and Dataset B is in CSV format. Both datasets contain overlapping customer records, but Dataset A uses a `customer_id` field while Dataset B uses a `custID` field. The team needs to standardize the schemas, join the records on the customer identifier, and output a single Parquet file with the least amount of custom code.<br><br>Which approach should the team use?<br><br>- **A)** Use AWS Glue Studio with an ApplyMapping transform to standardize column names, followed by a Join transform.<br>- **B)** Use Amazon S3 Select to query and merge the datasets directly in place.<br>- **C)** Use AWS Glue DataBrew to profile the data and automatically merge the schemas.<br>- **D)** Use Amazon Athena to run a federated query joining the two tables. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** AWS Glue Studio provides a visual interface to easily configure data transformations. The ApplyMapping transform allows the engineer to rename columns (e.g., `custID` to `customer_id`) and cast data types without writing code, and the Join transform can natively merge the sources.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Amazon S3 Select is used to retrieve subsets of data from a single object, not for complex join operations or merging multiple datasets across different formats.<br>- **C is Incorrect:** AWS Glue DataBrew is primarily for data cleaning and profiling. While it can transform data, for a straightforward schema standardization and join in an ML pipeline, Glue Studio ETL is the standard approach.<br>- **D is Incorrect:** While Athena can join the data using SQL, it requires the tables to already be cataloged with matching schemas, and it does not natively provide the visual transformation (like renaming) before the join without writing a custom SQL view.<br><br>> **Exam Tip / AWS Best Practice:** Use AWS Glue Studio's visual transforms (like ApplyMapping and Join) to resolve schema conflicts and merge disparate sources without writing custom PySpark code. |

| **### Question 4 - Cross-Region Data Centralization**<br><br>A global media company has user interaction logs stored in regional Amazon S3 buckets across three different AWS Regions. They need to centralize and merge these logs into a single Parquet dataset in a primary Region for ML training. The solution must be highly cost-effective, handle the cross-region network transfer natively, and avoid maintaining long-running infrastructure.<br><br>Which solution meets these requirements?<br><br>- **A)** Run an AWS Glue ETL job in the primary region reading directly from the regional S3 buckets.<br>- **B)** Use AWS DataSync to transfer all data to the primary region, then run an Athena query.<br>- **C)** Set up S3 Cross-Region Replication to copy data, then run a Glue Crawler in the primary region.<br>- **D)** Run an Amazon EMR Serverless job in each region, then copy the results to the primary region. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** AWS Glue can read data directly from S3 buckets in other regions. By running a single Glue ETL job in the primary region, you can natively merge the data, convert it to Parquet, and write it locally, saving cross-region transfer costs for the raw data and avoiding duplicate storage.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** AWS DataSync is for migrating data between storage systems, not for merging datasets into a new format. It would also incur high cross-region transfer costs for raw data.<br>- **C is Incorrect:** S3 Cross-Region Replication simply duplicates the raw data across regions, increasing storage costs and requiring a secondary step to merge the data, which violates the cost-effectiveness constraint.<br>- **D is Incorrect:** Running jobs in each region and then copying results adds unnecessary orchestration complexity and requires syncing the final outputs.<br><br>> **Exam Tip / AWS Best Practice:** AWS Glue can read from cross-region S3 buckets natively; performing the read and merge from the primary region minimizes storage duplication and network transfer costs. |

| **### Question 7 - Data Deduplication with Case Sensitivity**<br><br>Two legacy databases contain customer information that needs to be merged into a single Amazon S3 data lake. Both databases contain overlapping records based on an email address, but the `email` field in Database A is always lowercase, while the `email` field in Database B contains mixed case. The engineer needs to ensure accurate deduplication during the merge so that `User@Example.com` and `user@example.com` are treated as the same record.<br><br>How should the engineer perform this merge?<br><br>- **A)** Use an AWS Glue ETL job with a PySpark transform that applies the `lower()` function to both email columns before performing a dropDuplicates.<br>- **B)** Use AWS Glue FindMatches to identify matching records based on machine learning.<br>- **C)** Use an Amazon Macie job to identify and standardize PII data before merging.<br>- **D)** Use S3 Object Lambda to normalize the email addresses at read time. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** To deduplicate accurately when string casing differs, the most deterministic and reliable method is to normalize the keys (e.g., making both lowercase) using a PySpark transform before applying a deduplication function like `dropDuplicates` or `groupBy`.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** AWS Glue FindMatches is an ML-based transform for fuzzy matching when there is no exact key or records are fragmented (e.g., "John Doe" vs "Jon D."). For exact string matching with casing differences, a simple string normalization function is more accurate and less resource-intensive.<br>- **C is Incorrect:** Amazon Macie is a data security service for discovering and protecting sensitive data (PII); it does not perform data transformation or deduplication.<br>- **D is Incorrect:** S3 Object Lambda transforms data as it is read, but it is not suitable for performing cross-database joins and deduplication during an ETL merge process.<br><br>> **Exam Tip / AWS Best Practice:** When merging datasets with overlapping keys that have formatting inconsistencies (like case sensitivity), explicitly normalize the keys using standard string functions before performing a deterministic deduplication. |
| **### Question 8 - Cost-Effective Large Scale Merge**<br><br>A data science team needs to merge 100 TB of clickstream data stored in Amazon S3 (CSV) with 10 GB of user metadata in an Amazon DynamoDB table. They want to output the merged data in Parquet format, partitioned by date. They want the most cost-effective, serverless solution that does not require managing infrastructure.<br><br>Which service should they use to perform the merge?<br><br>- **A)** AWS Glue ETL job using DynamicFrames.<br>- **B)** Amazon EMR Serverless with a custom Spark application.<br>- **C)** Amazon Athena CTAS (Create Table As Select) query.<br>- **D)** Amazon SageMaker Processing job with Spark. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** AWS Glue is a fully managed serverless ETL service that natively integrates with DynamoDB and S3. Using Glue DynamicFrames or Spark DataFrames allows for efficient, large-scale joins (e.g., broadcast joins) and native partitioning of Parquet outputs.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While EMR Serverless is serverless, it requires more configuration and has a higher baseline overhead than a standard Glue ETL job for a straightforward join-and-partition task. Glue is the preferred native service for this ETL pattern.<br>- **C is Incorrect:** Athena has a 100 TB per query scan limit and 100 partition limit per CTAS, making it unsuitable and often significantly more expensive for processing and partitioning 100 TB of CSV data into Parquet compared to a Glue job.<br>- **D is Incorrect:** SageMaker Processing jobs are designed for ML preprocessing and evaluation; while they can run Spark, AWS Glue is the purpose-built service for large data integration and ETL to S3 data lakes.<br><br>> **Exam Tip / AWS Best Practice:** For massive (100 TB+) serverless data merges requiring custom partitioning and DynamoDB integration, AWS Glue ETL is the standard, cost-effective choice over Athena or EMR. |
| **### Question 9 - Optimizing Spark Joins in Glue**<br><br>During a daily merge job in AWS Glue, a machine learning engineer notices that the join operation between a massive clickstream dataset (2 TB) and a small IP-to-location mapping table (5 MB) is taking several hours to complete and encountering out-of-memory errors on the executors. The engineer needs to optimize the join without increasing the Data Processing Units (DPUs) significantly to keep costs low.<br><br>How should the engineer resolve this?<br><br>- **A)** Broadcast the smaller IP-to-location mapping table to all executors using the `broadcast()` function in PySpark.<br>- **B)** Increase the number of DPUs allocated to the Glue job to the maximum allowed.<br>- **C)** Write the small mapping table to Amazon S3 and use an S3 Select operation to filter it.<br>- **D)** Use an AWS Glue Crawler to index the small table to speed up the join. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** A broadcast join sends the small table to all worker nodes, allowing the large table to be joined locally without shuffling the 2 TB of data across the network. This drastically reduces execution time and prevents out-of-memory errors related to shuffle operations.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While adding DPUs provides more memory and compute, it increases costs and does not address the fundamental inefficiency of shuffling a massive dataset for a join with a tiny table.<br>- **C is Incorrect:** S3 Select is for filtering data within a single object, not for performing relational joins between datasets in a distributed Spark environment.<br>- **D is Incorrect:** A Glue Crawler only creates table schemas in the Data Catalog; it does not optimize query execution or join strategies.<br><br>> **Exam Tip / AWS Best Practice:** When joining a very large dataset with a very small dataset in Spark/Glue, always use a broadcast join to avoid expensive network shuffles and out-of-memory errors. |
