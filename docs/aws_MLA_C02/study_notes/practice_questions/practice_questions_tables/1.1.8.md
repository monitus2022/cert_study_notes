| **### Question 1 - Ingesting Medical Images and Metadata for ML**<br><br>A healthcare AI company is building a diagnostic model that requires ingesting 500 GB of high-resolution X-ray images (DICOM format) alongside structured patient metadata (CSV). The data science team needs to query the metadata to filter specific patient cohorts for training, while keeping storage costs as low as possible. The ingestion pipeline must have the least operational overhead.<br><br>Which storage architecture meets these requirements? (Select ONE)<br><br>- **A)** Store images in Amazon EFS and metadata in Amazon RDS for PostgreSQL.<br>- **B)** Store images in Amazon S3 Standard, convert the metadata CSV to Apache Parquet, and store it in Amazon S3.<br>- **C)** Store images in Amazon S3 Glacier Instant Retrieval and metadata in Amazon DynamoDB.<br>- **D)** Store both images and metadata in Amazon S3 using CSV format for metadata.<br> | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Storing images in Amazon S3 Standard is cost-effective and the standard for ML datasets. Converting the CSV metadata to Apache Parquet (a columnar format) allows efficient, low-cost querying via Amazon Athena without managing infrastructure. This provides the lowest operational overhead and optimized read performance for columnar queries.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Using Amazon EFS for 500 GB of static image data introduces higher costs and unnecessary operational overhead compared to S3. Managing an RDS instance for static metadata also adds overhead.<br>- **C is Incorrect:** Amazon S3 Glacier Instant Retrieval is for rarely accessed data; ML training data is typically accessed more frequently. DynamoDB is excellent for key-value lookups but not ideal for complex cohort filtering and analytical queries compared to a columnar format on S3.<br>- **D is Incorrect:** Keeping the metadata in CSV format on S3 prevents column pruning during analytical queries, resulting in higher Athena scan costs and slower performance compared to Parquet.<br><br>> **Exam Tip / AWS Best Practice:** For analytical queries over structured metadata in a data lake, convert row-oriented formats (CSV, JSON) to columnar formats (Parquet, ORC) to reduce scanned data and lower costs. |
| **### Question 2 - Real-Time Audio Ingestion for Sentiment Analysis**<br><br>A call center platform streams live customer audio to an ML application that performs real-time speech-to-text and sentiment analysis. The ingestion pipeline must capture the continuous audio streams with sub-second latency and allow multiple independent consumers (the transcription service and the sentiment model) to read the streams independently. The team wants to use an AWS-native service to minimize operational complexity.<br><br>Which service should the ML engineer use to ingest the audio data? (Select ONE)<br><br>- **A)** Amazon Kinesis Data Streams<br>- **B)** Amazon Managed Streaming for Apache Kafka (Amazon MSK)<br>- **C)** Amazon SQS<br>- **D)** Amazon S3 Event Notifications<br> | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** Amazon Kinesis Data Streams is an AWS-native service designed for continuous, low-latency data ingestion. It supports multiple independent consumers (e.g., using Kinesis Client Library or enhanced fan-out) allowing both the transcription and sentiment applications to read the same audio stream concurrently without impacting each other.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While Amazon MSK supports multiple consumers, it introduces significantly more operational overhead (managing brokers, partitions, ZooKeeper historically) compared to a fully managed AWS-native service like Kinesis, violating the "minimize operational complexity" constraint.<br>- **C is Incorrect:** Amazon SQS is a message queue, not a stream. It does not support multiple independent consumers reading the same message for stream processing; once a message is consumed and deleted, it's gone.<br>- **D is Incorrect:** S3 Event Notifications are event-driven and not designed for continuous, low-latency streaming of audio data.<br><br>> **Exam Tip / AWS Best Practice:** For real-time streaming ingestion with multiple independent consumers and low operational overhead, use Amazon Kinesis Data Streams with Enhanced Fan-Out. |
| **### Question 3 - High-Performance Shared Storage for Distributed Training**<br><br>A machine learning team is training a computer vision model across 20 SageMaker training instances. The training dataset consists of 5 TB of high-resolution images and text annotations. Every instance must read the entire dataset concurrently during each epoch. The team requires the highest possible throughput and lowest read latency to minimize training time.<br><br>Which AWS storage service should be used to provide this shared file namespace? (Select ONE)<br><br>- **A)** Amazon Elastic Block Store (Amazon EBS)<br>- **B)** Amazon S3 with S3 Transfer Acceleration<br>- **C)** Amazon FSx for Lustre<br>- **D)** Amazon Elastic File System (Amazon EFS)<br> | **Correct Answer:** **C**<br><br>**Correct Answer Analysis:**<br>- **C is Correct:** Amazon FSx for Lustre is a fully managed, high-performance file system optimized for fast processing of large datasets. It can be linked to an S3 bucket and provides sub-millisecond latencies and hundreds of GBps of throughput, making it ideal for distributed ML training requiring concurrent access to massive image and text datasets.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** EBS volumes can only be attached to a single instance at a time (with rare, specific multi-attach exceptions that don't fit 20 nodes). It cannot provide a shared file namespace for distributed training.<br>- **B is Incorrect:** While S3 stores the data, it is object storage and does not provide the POSIX file system interface and local-cache-like low latency required for high-throughput, concurrent file access during intensive training epochs.<br>- **D is Incorrect:** EFS provides a shared file system, but its throughput scales with storage capacity. For a 5 TB dataset requiring maximum performance, FSx for Lustre is explicitly designed for HPC and ML workloads, whereas EFS may bottleneck on extreme IOPS/throughput.<br><br>> **Exam Tip / AWS Best Practice:** Use Amazon FSx for Lustre when distributed ML training requires extremely high throughput and low-latency concurrent access to large datasets stored in S3. |
| **### Question 4 - Vector Storage for Image Similarity Search**<br><br>An e-commerce platform wants to implement a reverse image search feature. They process millions of product images daily, generate vector embeddings, and need to store them in a highly scalable database. The application must perform approximate nearest neighbor (ANN) searches to find visually similar products. The team requires a fully managed, serverless solution that scales automatically without infrastructure management.<br><br>Which AWS service is the MOST appropriate for storing and querying these image embeddings? (Select ONE)<br><br>- **A)** Amazon RDS for PostgreSQL with the pgvector extension<br>- **B)** Amazon OpenSearch Serverless<br>- **C)** Amazon DynamoDB<br>- **D)** Amazon S3 with vector indexes<br> | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Amazon OpenSearch Serverless is a fully managed, serverless option for search and analytics that natively supports vector storage and approximate nearest neighbor (ANN) search. It automatically scales compute and storage capacity based on workload demands, eliminating infrastructure management for millions of embeddings.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** While RDS with pgvector can handle vector similarity search, it requires instance management and capacity provisioning, violating the "serverless" and "automatically scales without infrastructure management" constraint.<br>- **C is Incorrect:** Amazon DynamoDB is a key-value and document database. It does not natively support vector similarity search or ANN algorithms without complex workarounds.<br>- **D is Incorrect:** While S3 can store vectors, it is object storage and requires a separate compute engine to perform similarity searches, making it unsuitable for low-latency, interactive reverse image search compared to a purpose-built vector store.<br><br>> **Exam Tip / AWS Best Practice:** For serverless, auto-scaling vector similarity search (like image or text embeddings), use Amazon OpenSearch Serverless with its vector search collection type. |
| **### Question 5 - Low-Latency Feature Ingestion for Online Inference**<br><br>A fraud detection ML model requires real-time features derived from user text inputs and transaction metadata. The inference endpoint needs to retrieve these features with single-digit millisecond latency. The features are continuously updated by an upstream stream processing job. The architecture must prevent training-serving skew.<br><br>How should the ML engineer store these features? (Select ONE)<br><br>- **A)** Store features in Amazon S3 and use Amazon Athena for low-latency lookups.<br>- **B)** Ingest features into Amazon SageMaker Feature Store, enabling the online store.<br>- **C)** Store features in Amazon EFS and mount it to the SageMaker endpoint.<br>- **D)** Ingest features into Amazon SageMaker Feature Store, enabling only the offline store.<br> | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Amazon SageMaker Feature Store provides an online store backed by DynamoDB, designed for low-latency, real-time feature retrieval during inference. By using a single feature definition in Feature Store, it ensures consistency between the features used in training (offline store) and inference (online store), preventing training-serving skew.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Athena is an interactive query service over S3 and has query latencies in the seconds, not single-digit milliseconds. It is not suitable for real-time inference lookups.<br>- **C is Incorrect:** Mounting EFS to a SageMaker endpoint introduces latency and operational complexity, and EFS is not designed for ultra-low-latency, high-throughput key-value feature lookups.<br>- **D is Incorrect:** The offline store is optimized for batch training jobs (historical records), not for low-latency online inference. Enabling only the offline store prevents real-time retrieval.<br><br>> **Exam Tip / AWS Best Practice:** Use the SageMaker Feature Store Online Store for single-digit millisecond inference lookups and to maintain a single source of truth that prevents training-serving skew. |
| **### Question 6 - Merging Audio Files and Text Transcripts with Serverless ETL**<br><br>A media company ingests thousands of podcast audio files (WAV) and their corresponding text transcripts (JSON) daily into an Amazon S3 bucket. The data engineering team needs to merge the metadata from the JSON files with the audio files' S3 URIs by PodcastID, outputting a unified manifest file for a downstream SageMaker Processing job. The solution must be serverless and require the least operational overhead.<br><br>Which approach satisfies these requirements? (Select ONE)<br><br>- **A)** Spin up an Amazon EMR cluster to run a Spark job that joins the JSON and audio file metadata.<br>- **B)** Use AWS Glue Studio to create a visual ETL job that reads the JSON metadata, joins it with the S3 audio file inventory, and writes the manifest to S3.<br>- **C)** Deploy a long-running AWS Lambda function to iterate over the S3 bucket, parse the JSON, and write the manifest file.<br>- **D)** Use Amazon SageMaker Pipelines to orchestrate a custom Python script running on SageMaker Processing instances.<br> | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** AWS Glue is a serverless data integration service. AWS Glue Studio provides a visual interface to easily create ETL jobs that can read from S3, perform joins, and write the output back to S3 without managing any underlying compute infrastructure, perfectly meeting the serverless and least operational overhead constraints.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Amazon EMR requires provisioning and managing clusters, which introduces significant operational overhead compared to serverless AWS Glue.<br>- **C is Incorrect:** Using a Lambda function to iterate over thousands of files and perform complex joins is an anti-pattern due to execution time limits (15 mins) and lack of built-in distributed processing.<br>- **D is Incorrect:** SageMaker Processing requires provisioning instance types and managing the execution environment, which is more operational overhead than a serverless Glue job.<br><br>> **Exam Tip / AWS Best Practice:** For serverless, low-operational-overhead ETL tasks like merging metadata and file inventories in S3, use AWS Glue (or AWS Glue Studio) instead of managing EMR clusters or custom compute. |
| **### Question 7 - Cost-Effective Storage for Historical Text Logs**<br><br>A natural language processing (NLP) team needs to store 10 TB of historical text logs for a batch ML training job that runs once a month. The data is rarely accessed outside of this monthly job. Compliance rules dictate that the data must be retained for 5 years. The primary constraint is to minimize storage costs while ensuring the data is available when needed for the monthly job.<br><br>Which Amazon S3 storage class is the MOST appropriate? (Select ONE)<br><br>- **A)** S3 Standard<br>- **B)** S3 Standard-Infrequent Access (S3 Standard-IA)<br>- **C)** S3 Glacier Flexible Retrieval<br>- **D)** S3 Intelligent-Tiering<br> | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** S3 Standard-IA is designed for data accessed less frequently (like a monthly batch job) but requires rapid access when needed. It offers a lower storage price than S3 Standard while still providing millisecond access, making it ideal for monthly ML training jobs without retrieval delays.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** S3 Standard is for frequently accessed data. Storing 10 TB of rarely accessed data here would incur higher costs than necessary.<br>- **C is Incorrect:** S3 Glacier Flexible Retrieval takes minutes to hours to retrieve data, which adds latency to the start of the monthly batch job. Standard-IA provides immediate access.<br>- **D is Incorrect:** S3 Intelligent-Tiering has a small monthly monitoring and automation fee per object. For a flat, predictable access pattern (strictly once a month), Standard-IA is more cost-effective than Intelligent-Tiering.<br><br>> **Exam Tip / AWS Best Practice:** Use S3 Standard-IA for data accessed monthly or quarterly where millisecond retrieval is required, avoiding Glacier retrieval delays and Standard pricing. |

| **### Question 9 - Secure Ingestion of Sensitive Audio Recordings**<br><br>A financial services firm is building an ML pipeline to analyze sensitive customer service audio recordings. Compliance policies mandate that the audio data must be encrypted at rest using a customer-managed key (CMK) and that the compute instances processing the audio must not retain any data locally after the job completes. The solution must guarantee zero data retention on the ephemeral compute resources.<br><br>Which combination of AWS services meets these compliance constraints? (Select TWO)<br><br>- **A)** Store the audio files in Amazon S3 with SSE-KMS encryption using a CMK.<br>- **B)** Process the audio files using Amazon SageMaker Processing jobs configured with encrypted Amazon EBS volumes.<br>- **C)** Store the audio files in Amazon S3 with SSE-S3 encryption.<br>- **D)** Process the audio using an always-on Amazon EC2 instance with instance store volumes.<br>- **E)** Use AWS Glue to process the audio files in memory only.<br> | **Correct Answers:** **A** and **B**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** Storing the audio in S3 with SSE-KMS fulfills the requirement for encryption at rest using a customer-managed key (CMK).<br>- **B is Correct:** SageMaker Processing jobs use ephemeral compute instances. By configuring the job with encrypted EBS volumes, the data processed locally is encrypted. Once the processing job terminates, the EBS volumes and instance storage are destroyed, ensuring zero data retention on compute resources.<br><br>**Distractor Analysis:**<br>- **C is Incorrect:** SSE-S3 uses AWS managed keys, not customer-managed keys (CMK), violating the compliance policy.<br>- **D is Incorrect:** An always-on EC2 instance does not guarantee zero data retention unless manually wiped, and instance store volumes persist data until the instance is terminated, introducing risk. It also violates ephemeral processing best practices.<br>- **E is Incorrect:** AWS Glue is not designed for processing binary audio files in memory and does not natively support ephemeral EBS encryption for ML workloads the way SageMaker Processing does.<br><br>> **Exam Tip / AWS Best Practice:** To meet strict compliance for ephemeral processing with encrypted local storage, use SageMaker Processing with KMS-encrypted EBS volumes. For data at rest in S3, use SSE-KMS with a CMK. |

The pipeline must handle massive spikes in data volume without dropping frames. The startup wants to use AWS-native streaming and storage services.<br><br>Which architecture best meets these requirements? (Select ONE)<br><br>- **A)** Use Amazon Kinesis Data Streams to ingest video, use a Kinesis Data Analytics application to extract frames, and store the images and metadata in Amazon S3.<br>- **B)** Use Amazon Kinesis Video Streams to ingest video, use an AWS Lambda consumer to extract frames and metadata, and store the output in Amazon DynamoDB.<br>- **C)** Use Amazon SQS to queue video chunks, process them with EC2 instances, and store the output in Amazon EFS.<br>- **D)** Use Amazon Kinesis Video Streams to ingest video, use a consumer application to extract frames and telemetry metadata, and store the output in Amazon S3.<br> | **Correct Answer:** **D**<br><br>**Correct Answer Analysis:**<br>- **D is Correct:** Amazon Kinesis Video Streams is specifically designed to ingest streaming video at scale. S3 is the appropriate store for images.<br>- **C is Incorrect:** Amazon SQS is not built for real-time video streaming, and using EFS for a massive data lake of images is less scalable and cost-effective than S3.<br><br>> **Exam Tip / AWS Best Practice:** For ingesting video streams at scale on AWS, use Amazon Kinesis Video Streams. Extracted image frames and telemetry should be stored in Amazon S3 as a scalable data lake. |
