| **### Question 1 - GenAI Response Quality Testing in CI/CD**<br><br>An AI engineering team is setting up a CI/CD pipeline to deploy updates to a generative AI application using Amazon Bedrock. The team needs to ensure that a new version of the fine-tuned model does not degrade the quality of responses compared to the currently deployed version. Due to the non-deterministic nature of generative AI, exact string matching is not feasible. The pipeline must block deployment if the response quality drops below a defined threshold, with the least operational overhead.<br><br>Which **ONE** testing approach fulfills these requirements? (Select ONE)<br><br>- **A)** Run a fixed golden prompt dataset through both versions, use an LLM-as-a-judge to evaluate responses, and block deployment if the average score drops below the baseline.<br>- **B)** Assert that each response from the new version matches the expected output string stored in the test suite.<br>- **C)** Deploy the new version to a staging endpoint and manually review the responses for a week before promoting to production.<br>- **D)** Monitor the CPU utilization and latency of the new endpoint during a canary deployment to determine response quality. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** Generative AI models are non-deterministic, meaning responses vary across runs. To test response quality in an automated CI/CD pipeline, you run a curated "golden prompt dataset" through both the candidate and baseline versions. Using an LLM-as-a-judge or task-specific metrics (e.g., faithfulness, answer relevance) allows the pipeline to objectively compare scores and block deployment if the candidate version's quality drops.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Because generative AI responses naturally vary between runs, exact string assertions will cause false negatives and flaky pipeline builds.<br>- **C is Incorrect:** Manual review introduces significant operational overhead and eliminates the automated CI/CD gating required by the scenario.<br>- **D is Incorrect:** Monitoring infrastructure metrics like CPU utilization and latency checks throughput and responsiveness, but does not detect drops in semantic response accuracy or generation quality.<br><br>> **Exam Tip / AWS Best Practice:** For non-deterministic GenAI models, use automated evaluation frameworks (like LLM-as-a-judge or ROUGE/BERTScore) on a golden dataset to gate deployments in CI/CD pipelines. |
| **### Question 2 - Amazon Bedrock Prompt Management Versioning**<br><br>A company is using Amazon Bedrock Prompt Management to iterate on prompts for a customer service chatbot. The prompt engineering team frequently updates prompts to improve response relevance. The solution must ensure that a new prompt variant is automatically tested against a battery of test cases before it is updated in the production application.<br><br>Which **ONE** approach satisfies these requirements? (Select ONE)<br><br>- **A)** Store prompt text in an Amazon S3 bucket and use AWS Lambda to fetch and test the prompt before updating the application configuration.<br>- **B)** Hardcode the prompt text in the application code and use AWS CodeBuild to run unit tests on the text formatting.<br>- **C)** Use Amazon Bedrock Prompt Management to create and test prompt variants, then use the Bedrock API to retrieve the approved prompt version dynamically in the application.<br>- **D)** Save the prompt in an AWS Systems Manager Parameter Store and update it manually when tests pass. | **Correct Answer:** **C**<br><br>**Correct Answer Analysis:**<br>- **C is Correct:** Amazon Bedrock Prompt Management stores prompts as versioned resources with variables and comparable variants. This allows prompt changes to be tested and released through a pipeline rather than edited directly in application code. The application retrieves the specific version dynamically, ensuring updates are tracked and tested without code deployments.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Storing prompts in S3 and using Lambda introduces custom, unnecessary operational overhead compared to the native Bedrock Prompt Management service.<br>- **B is Incorrect:** Hardcoding prompt text in application code violates the requirement to decouple prompts from application logic and makes version control and automated variant testing difficult.<br>- **D is Incorrect:** Manually updating Parameter Store violates the automated testing and release requirements of the CI/CD pipeline.<br><br>> **Exam Tip / AWS Best Practice:** Treat prompts as code. Use Amazon Bedrock Prompt Management to version, test, and dynamically fetch prompt variants, avoiding hardcoded text in application logic. |
