| **### Question 1 - Event-Driven Retraining Triggers**<br><br>A financial services company is building an automated retraining pipeline for a credit risk prediction model using Amazon SageMaker Pipelines. New labeled training data arrives irregularly from a third-party vendor and is deposited into an Amazon S3 bucket. The machine learning engineering team wants to trigger the retraining pipeline immediately when the data arrives with the **least operational overhead**.<br><br>Which solution meets these requirements? (Select ONE)<br><br>- **A)** Configure an S3 Event Notification to invoke an AWS Lambda function, which then makes an API call to `StartPipelineExecution`.<br>- **B)** Use Amazon EventBridge to monitor S3 `ObjectCreated` events and target the Amazon SageMaker Pipeline execution API directly.<br>- **C)** Configure an Amazon EventBridge scheduled rule to run a daily check on the S3 bucket's object count and trigger the pipeline if new objects exist.<br>- **D)** Use AWS Step Functions to poll the S3 bucket every 5 minutes using a Wait state and trigger the SageMaker Pipeline. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>Amazon EventBridge can natively capture Amazon S3 event notifications (such as `ObjectCreated`) and route them to various AWS services. By setting the SageMaker Pipeline as the target for the EventBridge rule, the pipeline triggers automatically and immediately upon data arrival. This approach requires no custom compute code and provides the lowest operational overhead.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** While S3 Event Notifications can invoke Lambda, writing and maintaining a custom Lambda function solely to call the SageMaker API introduces unnecessary operational overhead compared to a direct EventBridge integration.<br>- **C is Incorrect:** A daily scheduled rule introduces latency (up to 24 hours) before retraining occurs, violating the requirement for immediate triggering upon data arrival.<br>- **D is Incorrect:** Polling S3 with Step Functions every 5 minutes is an anti-pattern that introduces unnecessary complexity, higher costs, and delayed triggering compared to event-driven architecture.<br><br>> **Exam Tip:** For irregular events (like S3 data drops), use EventBridge to trigger SageMaker Pipelines directly. For predictable cadences, use EventBridge Scheduler. |

By setting the `ModelApprovalStatus` parameter to `PendingManualApproval`, the pipeline will halt the automated deployment process, ensuring the model waits in the registry until a human reviewer manually evaluates the metrics and changes the status to `Approved`.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While sending an SNS notification for manual review is plausible, deploying to a staging endpoint within the same pipeline step does not explicitly prevent an automated downstream CI/CD pipeline from accidentally moving it to production without the formal registry approval gate.<br>- **C is Incorrect:** Automatically deploying to production based on a metric threshold violates the strict compliance mandate requiring explicit human approval.<br>- **D is Incorrect:** Simply saving artifacts to S3 and logging to MLflow does not establish a formal, immutable approval gate that downstream CI/CD deployment pipelines can reference.<br><br>> **Exam Tip:** Always end a retraining pipeline at the Model Registry (`PendingManualApproval`) to separate training orchestration from deployment approval. |

| **### Question 8 - RAG Knowledge Base Re-indexing**<br><br>A legal tech company uses an Amazon Bedrock Knowledge Base backed by an Amazon OpenSearch Serverless vector store to search through millions of case files. The engineering team has decided to switch the embedding model from a smaller model to a higher-dimension, more accurate model to improve search relevance. They need to update the vector index with the **least operational overhead** while ensuring all queries return accurate results.<br><br>What must the team do to fulfill this requirement? (Select ONE)<br><br>- **A)** Perform an incremental resync on the Bedrock Knowledge Base, as it will only update documents that have changed in the S3 data source.<br>- **B)** Copy the existing OpenSearch Serverless index to a new collection, then point the Bedrock Knowledge Base to the new collection.<br>- **C)** Start a full ingestion job in the Bedrock Knowledge Base to re-process all documents from the S3 data source using the new embedding model.<br>- **D)** Update the Bedrock Knowledge Base configuration with the new embedding model; OpenSearch Serverless will automatically re-embed existing vectors in the background. | **Correct Answer:** **C**<br><br>**Correct Answer Analysis:**<br>Changing the embedding model alters the dimensions and semantics of the resulting vectors. All existing documents must be re-parsed, re-chunked, and re-embedded using the new model. Starting a full ingestion job via the Bedrock Knowledge Base `StartIngestionJob` API will completely regenerate the vectors in the OpenSearch Serverless index based on the new embedding configuration.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** An incremental resync checks for S3 document changes (additions/modifications/deletions). Since the S3 documents haven't changed, an incremental resync will skip them, leaving the old, incompatible vectors in the index.<br>- **B is Incorrect:** Copying the index merely duplicates the existing vectors (which were generated by the old embedding model). It does not regenerate them.<br>- **D is Incorrect:** OpenSearch Serverless is a vector database; it cannot retroactively re-embed text into vectors using a newly specified model. It only stores and queries existing vectors.<br><br>> **Exam Tip:** Changing chunking strategy, embedding model, or vector dimensions requires a full re-ingestion of the data source, not an incremental resync. |
