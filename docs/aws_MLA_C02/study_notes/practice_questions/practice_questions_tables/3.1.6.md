| **### Question 1 - Agent Deployment for Bursty Traffic**<br><br>A startup is deploying a conversational AI agent designed to assist users with coding tasks. The agent must maintain session state across multiple turns, invoke custom tools, and handle highly bursty traffic with extended periods of zero usage during nights and weekends. The engineering team has a strict mandate to minimize operational overhead and infrastructure costs.<br><br>Which deployment approach best fits these requirements?<br><br>- **A)** Deploy the agent's orchestration logic on an Amazon SageMaker Real-Time Endpoint with auto-scaling, and store session state in Amazon DynamoDB.<br>- **B)** Host the agent on an Amazon Elastic Container Service (ECS) cluster with Fargate, scaling to zero based on CloudWatch CPU metrics.<br>- **C)** Use Amazon Bedrock AgentCore's serverless runtime to host the agent, leveraging its built-in memory and automatic scaling to zero.<br>- **D)** Deploy the agent as an AWS Lambda function triggered by Amazon API Gateway, using an S3 bucket to store conversational history. | **Correct Answer:** **C**<br><br>**Correct Answer Analysis:**<br>**C is Correct:** Amazon Bedrock AgentCore provides a serverless runtime specifically designed for hosting agents in production. It handles automatic scaling (including scaling to zero during idle periods), provides built-in memory for session state, and requires minimal operational overhead compared to managing containers or endpoints.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** A SageMaker Real-Time Endpoint maintains persistent instances to avoid cold starts, which incurs costs during idle periods. It also requires the team to manually manage session state in DynamoDB, increasing operational overhead.<br>- **B is Incorrect:** While ECS with Fargate can scale to zero, managing the container orchestration, auto-scaling policies, and state storage introduces unnecessary operational overhead compared to a managed agent runtime like AgentCore.<br>- **D is Incorrect:** AWS Lambda has strict execution time limits and payload size constraints that make it unsuitable for complex, multi-step agent reasoning. Managing conversational history in S3 also introduces high latency.<br><br>> **Exam Tip:** Bedrock AgentCore is the native AWS solution for serverless, stateful agent hosting with minimal operational overhead. |

| **### Question 5 - Filtering Stale Documents in Agent RAG**<br><br>An enterprise agent uses an Amazon Bedrock Knowledge Base to answer questions about corporate policies. Employees complain that the agent frequently hallucinates by citing outdated policies that have been superseded. The knowledge base contains documents spanning the last 10 years. The team must ensure the agent only retrieves current, valid policies.<br><br>Which retrieval configuration directly addresses this issue?<br><br>- **A)** Increase the number of returned passages (top_k) to give the agent more context to choose from.<br>- **B)** Apply metadata filters to the Knowledge Base retrieval to restrict document searches to the current year.<br>- **C)** Add a reranking model to reorder the retrieved candidates so the most recent ones appear first.<br>- **D)** Switch from semantic vector search to hybrid search to improve exact term matching. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>**B is Correct:** Applying metadata filters restricts the candidate set *before* similarity search is performed. By filtering on a metadata attribute like "year" or "effective_date", the agent ensures that outdated documents are never retrieved in the first place, directly preventing the citation of stale policies.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Increasing top_k widens recall and will actually include *more* outdated documents, exacerbating the hallucination problem.<br>- **C is Incorrect:** Reranking only reorders the candidates already retrieved. If the vector search retrieves mostly old documents, reranking will still leave old documents in the context window. It does not filter out stale data.<br>- **D is Incorrect:** Hybrid search improves recall of exact terms but does not filter based on temporal relevance (document age).<br><br>> **Exam Tip:** Use metadata filters in Knowledge Bases to restrict the candidate pool (e.g., by date) before vector search runs. |

| **### Question 10 - Resolving Poor Retrieval Ordering for Agents**<br><br>An agent retrieves technical manuals from a Bedrock Knowledge Base. Users report that the agent often ignores the correct answer. Upon investigation, the engineer finds that the vector search retrieves the correct passage, but it ranks 5th out of 10 returned passages. The top 4 passages are semantically similar but irrelevant. The model is getting confused by the irrelevant context.<br><br>Which configuration change will most directly fix this ordering issue?<br><br>- **A)** Reduce the number of returned passages (top_k) to 4.<br>- **B)** Apply a reranking model to reorder the retrieved candidates based on cross-encoder relevance scoring.<br>- **C)** Change the underlying embedding model to one with more dimensions.<br>- **D)** Switch the vector store from OpenSearch to Pinecone. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>**B is Correct:** A reranking model performs a second-pass evaluation of the retrieved candidates using a cross-encoder, which calculates a deep semantic relevance score between the query and each passage. This directly reorders the list, moving the correct passage from rank 5 to rank 1, preventing the model from being confused by irrelevant top results.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Reducing top_k to 4 would completely drop the correct passage (currently ranked 5th) from the context window, causing the agent to fail entirely.<br>- **C is Incorrect:** While changing embedding models might affect overall search quality, it does not guarantee the specific ordering issue is fixed and requires a costly full re-indexing of the knowledge base.<br>- **D is Incorrect:** The vector store itself executes the math based on the embeddings; switching databases does not change the inherent semantic similarity ranking generated by the embedding model.<br><br>> **Exam Tip:** Use a reranking model (cross-encoder) as a second pass to fix semantic ordering issues in retrieved Knowledge Base passages. |
