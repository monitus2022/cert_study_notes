| **### Question 1 - CloudFormation Cross-Stack References for SageMaker Endpoints**<br><br>A networking team owns the AWS VPC resources, and an ML engineering team owns the Amazon SageMaker AI endpoint resources. Both teams use AWS CloudFormation to manage their infrastructure. The ML team's endpoint stack must deploy instances into the private subnets and use the security groups created by the networking team's stack, without hardcoding IDs.<br><br>Which approach satisfies these requirements with the **least operational overhead** and maintains a **single source of truth** for identifiers? (Select ONE)<br><br>- **A)** Manually copy the subnet and security group IDs from the AWS Management Console and enter them as Parameters in the ML team's CloudFormation template.<br>- **B)** Configure the networking stack to output the resource IDs and use the `Fn::ImportValue` function in the ML team's stack to reference them.<br>- **C)** Create a custom AWS Lambda function that uses Boto3 to fetch the network IDs and pass them to the SageMaker stack deployment.<br>- **D)** Deploy both stacks as nested stacks within a single parent template to share resources automatically. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Exporting the subnet and security group IDs from the networking stack's `Outputs` section and importing them in the ML stack using `Fn::ImportValue` creates a direct cross-stack reference. This ensures the ML stack dynamically retrieves the current values without hardcoding, maintaining separation of concerns and minimizing operational overhead.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Manually copying IDs introduces configuration drift and operational overhead, violating the constraint of a single source of truth.<br>- **C is Incorrect:** Using a custom Lambda function adds unnecessary complexity and maintenance overhead when CloudFormation natively supports cross-stack references.<br>- **D is Incorrect:** Nested stacks combine the lifecycle of both stacks into a single parent stack, which violates the requirement for separate team ownership and independent lifecycle management.<br><br>> **Exam Tip:** Use CloudFormation `Export` and `Fn::ImportValue` to decouple infrastructure layers while securely passing configurations (like Subnet IDs) between separately owned stacks. |
| **### Question 2 - Orchestrating Ephemeral ML Environments with Step Functions**<br><br>An MLOps engineer is automating the deployment of a complex ML environment. If the endpoint deployment fails, the VPC endpoint must be rolled back automatically. The solution must minimize operational overhead.<br><br>Which orchestration strategy **best meets these requirements**? (Select ONE)<br><br>- **A)** Use AWS Step Functions to orchestrate AWS CloudFormation stack deployments, utilizing `CreateStack` and `DeleteStack` actions with `Catch` and `Retry` states for failure handling.<br>- **B)** Use AWS CodePipeline with separate stages for VPC and SageMaker deployments, relying on pipeline-level manual approvals for failure recovery.<br>- **C)** Use an AWS Lambda function triggered by EventBridge to make Boto3 API calls for provisioning, with custom try-except blocks for rollback.<br>- **D)** Deploy a single AWS CloudFormation nested stack containing both the VPC and SageMaker resources, using CloudFormation Rollback triggers. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** AWS Step Functions provides native orchestration for CloudFormation stack deployments. By using Step Functions states, you can define sequential execution, wait for completion, and use `Catch` blocks to execute rollback logic (e.g., deleting the VPC stack) if the SageMaker stack fails, minimizing manual intervention and operational overhead.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Relying on manual approvals for failure recovery introduces human intervention, violating the automation and low-operational-overhead constraints.<br>- **C is Incorrect:** Writing custom Lambda functions with try-except blocks for infrastructure orchestration is an anti-pattern compared to using native Step Functions integrations, resulting in higher maintenance overhead.<br>- **D is Incorrect:** While CloudFormation handles rollback within a single stack automatically, combining them into a nested stack violates the separation of concerns and doesn't provide the custom, multi-step validation workflow requested.<br><br>> **Exam Tip:** AWS Step Functions is the preferred service for orchestrating complex, stateful workflows involving multiple AWS service integrations (like CloudFormation) with custom error handling and rollback logic. |
| **### Question 3 - Passing Objects Between AWS CDK Stacks**<br><br>An engineering team is using the AWS Cloud Development Kit (AWS CDK) to provision resources for an ML workload. The networking stack creates a VPC, and the ML stack creates a SageMaker AI endpoint. The ML stack must reference the VPC created by the networking stack to configure private subnets for the endpoint.<br><br>Which method provides **integrated communication between the CDK stacks** with strong typing and the **least operational overhead**? (Select ONE)<br><br>- **A)** Pass the `vpc.Vpc` object from the networking stack directly to the ML stack's construct, allowing CDK to handle the cross-stack reference automatically.<br>- **B)** Export the VPC ID as a string from the networking stack and use `Fn.importValue` in the ML stack to pass the string to the SageMaker construct.<br>- **C)** Store the VPC ID in AWS Systems Manager Parameter Store and have the ML stack read it during synthesis.<br>- **D)** Deploy both stacks in the same AWS CDK App and use hardcoded VPC IDs in the ML stack's environment variables. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** In AWS CDK, you can pass the actual AWS resource object (e.g., `ec2.Vpc`) directly to a construct in another stack. CDK automatically creates the underlying CloudFormation cross-stack references (exports/imports) for you, providing strong typing and minimizing boilerplate code.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While `Fn.importValue` works in CDK, it returns a string token, losing the strong typing benefits of passing the native CDK object.
