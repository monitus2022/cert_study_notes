| **### Question 1 - CloudWatch Flatline Alarms for Inference Pipelines**<br><br>An ML platform team is monitoring a real-time inference pipeline. We will mark **A** as correct for dynamic traffic).<br><br>**Correct Option Analysis:**<br>- **A is Correct:** CloudWatch Anomaly Detection dynamically learns the normal traffic patterns of the endpoint (accounting for time-of-day fluctuations) and will trigger an alarm if the invocation count drops to zero unexpectedly, satisfying the requirement with minimal configuration and no custom code.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While a static threshold of < 1 is a valid "flatline" alarm, it does not account for natural periods of low or zero traffic (e.g., overnight), which would cause false positives and increase operational overhead.<br>- **C is Incorrect:** SageMaker Model Monitor analyzes the payload data captured from requests for data drift or model quality, not the volume of incoming requests.<br>- **D is Incorrect:** Writing a custom Lambda polling function introduces unnecessary operational overhead compared to native CloudWatch Anomaly Detection features.<br><br>> **Key Takeaway:** An invocation count that drops to zero indicates a broken upstream pipeline, and alarms must be configured to detect flat lines as well as spikes, ideally using dynamic anomaly detection. |

| **### Question 9 - Differentiating Data Drift vs Pipeline Error**<br><br>A production ML model is receiving inference requests, and the operations team notices a sudden shift in the distribution of features in the incoming payloads. The model's accuracy has degraded significantly. The team needs to determine if this is a natural data drift (e.g., a new customer demographic) or an error in the upstream data processing pipeline (e.g., a broken feature engineering job).<br><br>Which approach should the team use to differentiate between these two scenarios with the least operational overhead?<br><br>- **A)** Compare the incoming payload distribution to the distribution of the raw source data; if the raw data has shifted but the payload matches it, it's data drift.<br>- **B)** Retrain the model immediately on the new payload data.<br>- **C)** Check the CloudWatch logs of the SageMaker endpoint for 4xx errors.<br>- **D)** Deploy a shadow variant of the model to test its accuracy. | **Correct Answer:** **A**<br><br>**Correct Option Analysis:**<br>- **A is Correct:** By comparing the raw upstream data to the processed payload, the team can identify if the shift is a natural change in the input (data drift) or an artifact introduced by a broken processing job (pipeline error). If the raw data is stable but the payload shifted, it's a pipeline error.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Retraining immediately does not diagnose the root cause; if it's a pipeline error, retraining on corrupted data will bake in the error.<br>- **C is Incorrect:** 4xx errors indicate formatting issues, not a gradual or sudden shift in data distribution.<br>- **D is Incorrect:** A shadow variant tests model performance on new traffic but doesn't diagnose whether the shift is due to pipeline errors or natural drift.<br><br>> **Key Takeaway:** To differentiate between data drift and pipeline errors, you must monitor the entire data pipeline, comparing distributions at different stages (raw vs. processed) to isolate the source of the shift. |
