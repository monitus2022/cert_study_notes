| **### Question 1 - Multi-Model vs Multi-Container Endpoint Selection**<br><br>An ML team needs to deploy 500 custom XGBoost models for different retail stores. The models share the same framework and are infrequently accessed, with only a few receiving constant traffic. The team wants to minimize infrastructure costs and operational overhead.<br><br>Which deployment strategy satisfies these requirements with the **least operational overhead** and is the **most cost-effective**? (Select ONE)<br><br>- **A)** Deploy 500 separate SageMaker real-time endpoints.<br>- **B)** Deploy a SageMaker Multi-Model Endpoint (MME) with a shared serving container.<br>- **C)** Deploy a SageMaker Multi-Container Endpoint (MCE) with 500 containers.<br>- **D)** Package all models into a single massive container and deploy to a real-time endpoint. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** A Multi-Model Endpoint (MME) hosts multiple models on a single SageMaker endpoint using a shared compute fleet and serving container. SageMaker dynamically manages caching models in memory from Amazon S3, which is ideal for many models sharing the same framework with uneven traffic patterns. This drastically reduces hosting costs and operational overhead.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Provisioning 500 separate real-time endpoints would result in extremely high infrastructure costs and massive management overhead.<br>- **C is Incorrect:** A Multi-Container Endpoint (MCE) supports a maximum of 15 containers per endpoint, so 500 containers cannot be deployed this way. MCE is meant for different frameworks, not variations of the same model.<br>- **D is Incorrect:** Packaging 500 models into a single container creates a massive, fragile deployment artifact. It makes updating individual models highly inefficient and violates container design best practices.<br><br>> **Exam Tip:** Use Multi-Model Endpoints (MME) for hosting many models that share the same framework, relying on SageMaker to dynamically load/unload them from S3 based on traffic. |

(Select ONE)<br><br>- **A)** Deploy a SageMaker Inference Pipeline (Multi-Container Endpoint) with containers for preprocessing, inference, and post-processing.<br>- **B)** Use AWS Step Functions to orchestrate three separate AWS Lambda functions for each step.<br>- **C)** Deploy an MME with the three models sharing a single container.<br>- **D)** Use an asynchronous endpoint with custom logic to pass data between S3 buckets for each step. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** A SageMaker Multi-Container Endpoint (MCE) configured as an Inference Pipeline allows you to chain up to 15 containers sequentially. The data flows through the containers in-memory on the same instance, ensuring the lowest possible latency between preprocessing, inference, and postprocessing steps.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Using Step Functions and Lambda introduces network latency and data serialization overhead between each step, which violates the "lowest latency between steps" constraint.<br>- **C is Incorrect:** An MME is designed for hosting variations of models behind one endpoint, not for chaining different execution steps in a pipeline sequence.<br>- **D is Incorrect:** Asynchronous endpoints are for long-running, queued requests, not for optimizing inter-step latency. Passing data via S3 between steps adds massive latency.<br><br>> **Exam Tip:** Use SageMaker Inference Pipelines (a type of Multi-Container Endpoint) to sequentially execute preprocessing, inference, and postprocessing containers in-memory for strict latency requirements. |

(Select ONE)<br><br>- **A)** Use a Multi-Model Endpoint (MME) for all three models.<br>- **B)** Use a Multi-Container Endpoint (MCE) with Direct invocation for the TensorFlow model and Pipeline invocation for the Scikit-Learn and PyTorch models.<br>- **C)** Deploy three separate SageMaker Serverless endpoints.<br>- **D)** Package all three models into a single Docker container. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** A Multi-Container Endpoint (MCE) supports two invocation patterns: "Direct" (invoking a specific container by name) and "Pipeline" (invoking containers sequentially). You can configure the MCE to allow direct invocation of the TensorFlow model, while routing Scikit-Learn and PyTorch as a sequential pipeline.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** A Multi-Model Endpoint (MME) requires all models to share the same serving container and framework, which is not possible across Scikit-Learn, PyTorch, and TensorFlow.<br>- **C is Incorrect:** Deploying three separate Serverless endpoints does not meet the requirement of invoking the Scikit-Learn and PyTorch models sequentially in one request.<br>- **D is Incorrect:** Packaging multiple frameworks into a single container is an anti-pattern, making it difficult to manage dependencies, scale, and update individual models.<br><br>> **Exam Tip:** Multi-Container Endpoints allow mixing different frameworks on one endpoint, supporting both Direct (by container name) and Pipeline (sequential) invocations simultaneously. |

They have another model that processes 1 request per minute. They are currently sharing a Multi-Model Endpoint, but the fraud detection model's latency is degrading when the other model is loaded into memory.<br><br>What is the **most effective** architecture to resolve this performance issue? (Select ONE)<br><br>- **A)** Keep both models on the Multi-Model Endpoint and increase the instance size.<br>- **B)** Deploy the fraud detection model to a dedicated SageMaker Real-Time Endpoint with high-performance instances and Auto Scaling.<br>- **C)** Deploy the fraud detection model to a SageMaker Serverless Endpoint.<br>- **D)** Deploy both models to a SageMaker Batch Transform job. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** A model with extremely high throughput (10,000 TPS) and strict latency requirements (sub-10ms) should be isolated on its own dedicated Real-Time Endpoint. | **### Question 10 - Custom Container Orchestration for SQS Workers**<br><br>A video streaming service needs to run a continuous background process that extracts metadata from uploaded videos using a custom ML model packaged in a Docker container. The process must pull messages directly from an Amazon SQS queue, process them one by one, and scale horizontally based on the queue depth.<br><br>Which deployment strategy is the **most appropriate** with the **least operational overhead** for containers? (Select ONE)<br><br>- **A)** Deploy the model as a long-running service on Amazon ECS with AWS Fargate, scaling based on SQS queue depth.<br>- **B)** Use a SageMaker Asynchronous Inference endpoint to process the SQS queue.<br>- **C)** Deploy the model to a SageMaker Real-Time endpoint and trigger it via EventBridge.<br>- **D)** Run a custom Python worker on an EC2 instance managed by an Auto Scaling group. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** Amazon ECS with AWS Fargate is ideal for running custom containers as long-running workers. You can configure the ECS service to scale based on the `ApproximateNumberOfMessagesVisible` CloudWatch metric from SQS, directly satisfying the requirement to scale based on queue depth without managing EC2 instances (least operational overhead).<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** SageMaker Asynchronous Inference uses an internal managed queue, not Amazon SQS directly. To use SQS, you would need an intermediary (like Lambda), adding overhead. Also, it is designed for API invocations, not as a continuous SQS polling worker.<br>- **C is Incorrect:** A SageMaker Real-Time endpoint cannot natively poll from an SQS queue. EventBridge does not trigger endpoints directly based on SQS message arrival in a way that supports 1-by-1 long-running processing.<br>- **D is Incorrect:** Managing custom Python workers and Auto Scaling groups on EC2 introduces OS patching and instance management, which is higher operational overhead compared to Fargate.<br><br>> **Exam Tip:** When you need a custom container to act as a worker polling from an external queue (like SQS) and scaling based on that queue's depth, Amazon ECS with Fargate is the best choice for low overhead. |
