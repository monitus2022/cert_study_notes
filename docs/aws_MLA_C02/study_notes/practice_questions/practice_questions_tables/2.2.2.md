| **### Question 1 - SageMaker AI Script Mode vs. Bring Your Own Container (BYOC)**<br><br>A data science team has written a custom PyTorch training script to train a computer vision model. The script uses standard PyTorch libraries and does not require any external dependencies outside of the base PyTorch environment. The team wants to run this script as a managed SageMaker AI training job with the **least operational overhead** and wishes to **avoid maintaining Docker images**.<br><br>Which approach should the team use to configure the training job?<br><br>- **A)** Build a custom Docker container with PyTorch installed, push it to Amazon ECR, and use a `sagemaker.estimator.Estimator` to point to the ECR image.<br>- **B)** Use the `sagemaker.pytorch.PyTorch` estimator, provide the Python script as the `entry_point`, and rely on the AWS-maintained PyTorch Deep Learning Container (DLC).<br>- **C)** Use the SageMaker AI built-in Image Classification algorithm and pass the custom PyTorch script as a hyperparameter.<br>- **D)** Use an AWS Lambda function to execute the PyTorch script on an AWS Fargate container to avoid managing EC2 instances.<br><br>*(Select ONE)* | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** Using the `PyTorch` estimator in SageMaker AI Script Mode allows you to supply your custom Python script via the `entry_point` parameter. SageMaker automatically pulls a pre-built, AWS-managed Deep Learning Container (DLC) that matches your specified framework version, injects your script, and executes it. This completely removes the need to write Dockerfiles or manage container registries.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Building a custom Docker container (BYOC) requires writing Dockerfiles, maintaining base images, and pushing to ECR. This violates the constraint of avoiding Docker image maintenance and introduces high operational overhead.<br>- **C is Incorrect:** SageMaker AI built-in algorithms (like Image Classification) come with pre-packaged training logic. You cannot inject a custom PyTorch training script into a built-in algorithm.<br>- **D is Incorrect:** AWS Lambda and Fargate are not designed for long-running, compute-intensive GPU training jobs. SageMaker AI is the native service for managed ML training.<br><br>> **Key Takeaway:** Script Mode combines custom training logic (your script) with managed infrastructure (AWS Deep Learning Containers), eliminating the need for BYOC when using supported frameworks like PyTorch and TensorFlow. |
| **### Question 2 - Adding Custom Dependencies in Script Mode**<br><br>An ML engineering team is running a TensorFlow training script in SageMaker AI Script Mode. The script requires a specific external Python library (`texttable`) that is not included in the standard AWS TensorFlow Deep Learning Container. The team must deploy this dependency with the **lowest operational overhead** and without building a custom container image.<br><br>Which configuration fulfills these requirements?<br><br>- **A)** Create a `requirements.txt` file listing `texttable`, place it in the same S3 directory as the entry point script, and specify this directory in the `source_dir` parameter of the TensorFlow estimator.<br>- **B)** Use the `subprocess` module inside the training script to run `pip install texttable` at the start of the training loop.<br>- **C)** Build a custom Docker image extending the TensorFlow DLC, install `texttable`, and push it to Amazon ECR.<br>- **D)** Package the `texttable` library source code into an AWS Lambda layer and attach it to the SageMaker training job.<br><br>*(Select ONE)* | **Correct Answer:** **A**<br><br>**Correct Option Analysis:**<br>- **A is Correct:** In SageMaker AI Script Mode, if you provide a `requirements.txt` file in the same directory as your `entry_point` script (specified via `source_dir`), SageMaker will automatically run `pip install -r requirements.txt` inside the managed container before executing your training script. This is the simplest, code-free way to add external dependencies without BYOC.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While running `subprocess.run(['pip', 'install', 'texttable'])` in the script works, it is an anti-pattern, introduces unnecessary code overhead, and slows down the start of every training job. `requirements.txt` is the native, supported method.<br>- **C is Incorrect:** Building a custom Docker image violates the constraint of avoiding custom container images and introduces unnecessary operational overhead.<br>- **D is Incorrect:** AWS Lambda layers are for serverless functions, not SageMaker AI training containers. SageMaker does not support attaching Lambda layers to training jobs.<br><br>> **Key Takeaway:** To add Python dependencies in Script Mode without building a custom container, include a `requirements.txt` file alongside your training script in the `source_dir`. |

The team needs to visualize this validation loss curve in the SageMaker console and CloudWatch with **minimal infrastructure changes**.<br><br>Which **TWO** actions must the team take to achieve this? (Select TWO)<br><br>- **A)** Configure the `metric_definitions` parameter in the `PyTorch` estimator with a regular expression that extracts the numerical value from `Validation Loss: 0.15`.<br>- **B)** Modify the training script to use the `boto3` client to push custom metrics to CloudWatch using `put_metric_data`.<br>- **C)** Ensure the training script prints the metric string (e.g., `Validation Loss: 0.15`) to `stdout` or `stderr`.<br>- **D)** Save the loss values to a CSV file in `/opt/ml/output/metrics.csv` and configure SageMaker to parse it.<br>- **E)** Enable SageMaker Debugger and configure a custom rule to extract the loss metric.<br><br>*(Select TWO)* | **Correct Answer:** **A** and **C**<br><br>**Correct Option Analysis:**<br>- **A is Correct:** By defining a regex pattern in the `metric_definitions` parameter of the estimator (e.g., `{'Name': 'validation:loss', 'Regex': 'Validation Loss: ([0-9\\.]+)'}`), SageMaker will automatically parse the console output and emit the metric to CloudWatch.<br>- **C is Correct:** SageMaker Script Mode natively streams all standard output (`stdout`) and standard error (`stderr`) to CloudWatch Logs. The metric definitions rely on this text stream to extract the values.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Using `boto3` to manually push metrics introduces unnecessary code complexity and requires IAM permissions. Regex metric definitions are the simplest native method.<br><br>> **Key Takeaway:** To track custom metrics in SageMaker Script Mode, simply print them to `stdout` and define a regex pattern in the `metric_definitions` parameter of the estimator. |
| **### Question 5 - Accessing Input Data Channels**<br><br>A training script running in SageMaker AI Script Mode requires access to the training dataset. The dataset is stored in Amazon S3 and passed to the estimator via the `inputs` parameter (e.g., `inputs={'train': 's3://bucket/train'}`). The script needs to locate this data on the local container filesystem dynamically, without hardcoding paths.<br><br>Which environment variable should the script reference to find the local path for the 'train' channel?<br><br>- **A)** `SM_INPUT_DIR`<br>- **B)** `SM_CHANNEL_TRAIN`<br>- **C)** `SM_MODULE_DIR`<br>- **D)** `S3_TRAIN_BUCKET`<br><br>*(Select ONE)* | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** SageMaker AI automatically downloads data from the specified S3 URI to the local container before the training script begins. For a channel named `train`, the local path is exposed via the `SM_CHANNEL_TRAIN` environment variable (typically pointing to `/opt/ml/input/data/train`).<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** `SM_INPUT_DIR` points to the parent directory `/opt/ml/input`, but it does not specify the specific subdirectory for the 'train' data channel.<br>- **C is Incorrect:** `SM_MODULE_DIR` points to the directory where the training script itself is stored, not the input data.<br>- **D is Incorrect:** `S3_TRAIN_BUCKET` is not a standard SageMaker environment variable. SageMaker abstracts the S3 bucket away and provides local file paths instead.<br><br>> **Key Takeaway:** SageMaker downloads input channels to local paths accessible via environment variables named `SM_CHANNEL_<CHANNEL_NAME>` (e.g., `SM_CHANNEL_TRAIN`). |
| **### Question 6 - Saving Model Artifacts for Deployment**<br><br>A data scientist has completed a custom training script using SageMaker AI Script Mode with the Hugging Face `Transformer` class. The script successfully trains the model and saves the weights. The team needs to deploy this model to a SageMaker AI real-time endpoint with the **least operational overhead**.<br><br>Where inside the training container must the script save the serialized model artifact (e.g., `model.tar.gz`) so that SageMaker AI automatically uploads it to S3 for hosting?<br><br>- **A)** `/opt/ml/model/`<br>- **B)** `/opt/ml/output/`<br>- **C)** `/opt/ml/input/data/`<br>- **D)** `/opt/ml/checkpoints/`<br><br>*(Select ONE)* | **Correct Answer:** **A**<br><br>**Correct Option Analysis:**<br>- **A is Correct:** SageMaker AI automatically captures the contents of the `/opt/ml/model/` directory at the end of the training job, compresses it into a `model.tar.gz` file, and uploads it to the S3 output path specified in the estimator. This artifact is then used directly to create a model package for deployment.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** `/opt/ml/output/` is used for writing artifacts like the failure reason or metric data, not the final model artifact for deployment.<br>- **C is Incorrect:** `/opt/ml/input/data/` is where SageMaker downloads the input training and validation data channels.<br>- **D is Incorrect:** `/opt/ml/checkpoints/` is used for saving intermediate training states for spot instance interruption recovery, not the final model artifact.<br><br>> **Key Takeaway:** To ensure SageMaker captures and uploads your trained model for deployment, always save the serialized model files to the `/opt/ml/model/` directory in your training script. |
| **### Question 7 - Enabling Distributed Training in Script Mode**<br><br>An AI team is training a large language model using a custom PyTorch script in SageMaker AI Script Mode. The model fits in the memory of a single GPU, but the dataset is massive, and training takes weeks on a single instance. The team needs to reduce training time with the **least amount of code rewrite** to their training loop.<br><br>Which configuration should the team implement?<br><br>- **A)** Build a custom Docker container with MPI and Horovod pre-configured, and manually update the training script to use MPI primitives.<br>- **B)** Configure the `distribution` parameter in the `PyTorch` estimator to use `smdistributed` with `dataparallel` enabled.<br>- **C)** Use SageMaker AI Automatic Model Tuning (AMT) to run multiple training jobs in parallel across different instances.<br>- **D)** Save intermediate weights to S3 after every epoch and use an AWS Step Functions state machine to trigger sequential jobs on new instances.<br><br>*(Select ONE)* | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** By setting `distribution={"smdistributed": {"dataparallel": {"enabled": True}}}` in the PyTorch estimator, SageMaker AI automatically handles the complex setup of distributed data parallelism across multiple instances. The AWS DLC comes pre-installed with the SageMaker Distributed Data Parallel (SMDDP) library, requiring minimal code changes (just initializing the SMDDP framework in the script) to split batches across workers.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Building a custom MPI/Horovod container introduces heavy operational overhead. The SMDDP library is already available in AWS DLCs and is optimized for AWS network infrastructure, making it the simpler choice.<br>- **C is Incorrect:** AMT (Hyperparameter tuning) runs multiple jobs to find the best hyperparameters; it does not parallelize a *single* training job to make it run faster.<br>- **D is Incorrect:** Using Step Functions to manually orchestrate sequential epoch-based jobs introduces massive overhead and breaks the standard ML training loop.<br><br>> **Key Takeaway:** To enable distributed data parallelism in Script Mode with minimal overhead, use the `smdistributed` configuration in the estimator, leveraging the pre-installed SMDDP library. |
