| **### Question 1 - Optimizing Repeating Prompts in Amazon Bedrock**<br><br>An enterprise HR company is using an Amazon Bedrock-powered assistant to analyze employee handbook queries. The system sends a 10,000-token static company policy document as part of the prompt for every user query, along with a short dynamic user question. The team needs to reduce the token processing costs and latency of these requests with the least operational overhead.<br><br>Which solution will meet these requirements?<br><br>- **A)** Configure an AWS Lambda function to summarize the 10,000-token document before sending the request to Bedrock.<br>- **B)** Use Amazon Bedrock Provisioned Throughput to reserve model units for the baseline traffic.<br>- **C)** Enable Prompt Caching in Amazon Bedrock to cache the static 10,000-token document prefix.<br>- **D)** Switch from an on-demand foundation model to a smaller, less capable foundation model.<br><br>*(Select ONE)* | **Correct Answer:** **C**<br><br>**Correct Answer Analysis:**<br>- **C is Correct:** Amazon Bedrock Prompt Caching allows the system to cache the Key-Value (KV) states of a static prompt prefix. Since the 10,000-token document is repeated across requests, caching it significantly reduces the input token processing cost and latency for subsequent requests, meeting the requirement with no custom code.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Summarizing the document dynamically with a Lambda function adds compute costs, latency, and significant operational overhead compared to native caching.<br>- **B is Incorrect:** Provisioned Throughput secures capacity for predictable workloads by paying a fixed hourly rate, but it does not specifically optimize the cost of repeating tokens in the prompt itself.<br>- **D is Incorrect:** Switching to a smaller model might compromise the quality of the analysis and does not solve the fundamental inefficiency of repeatedly sending a 10,000-token static context.<br><br>> **Key Takeaway:** Prompt Caching reduces cost and latency for workloads that repeatedly send the same static context (like system instructions or large reference documents) by avoiding recomputation of the prompt prefix. |
| **### Question 2 - Asynchronous Document Summarization Cost Optimization**<br><br>A legal firm processes thousands of lengthy court transcripts daily using a large language model on Amazon Bedrock. It offers a significant cost discount (typically 50%) compared to on-demand inference, making it the most cost-effective solution for non-real-time bulk processing of transcripts.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Provisioned Throughput is used to guarantee model capacity for steady, predictable workloads at a fixed hourly rate, but it does not offer the bulk discount benefits of Batch Inference for asynchronous work.<br>- **C is Incorrect:** Bedrock Guardrails are used for safety, content filtering, and PII redaction, not for reducing inference costs.<br>- **D is Incorrect:** Knowledge Bases are used for Retrieval-Augmented Generation (RAG) to query existing data, not for generating summaries of newly uploaded bulk data in a batch process.<br><br>> **Key Takeaway:** For asynchronous, bulk processing workloads on Amazon Bedrock, Batch Inference provides a substantial cost discount over on-demand token pricing. |

This allows the engineer to see exactly how many tokens are consumed by each step of the agent's process, revealing hidden loops or overly verbose tool responses.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** AWS Compute Optimizer analyzes compute resource utilization (like EC2 or Lambda) and recommends right-sizing, but it has no visibility into Bedrock token consumption or agent orchestration traces.<br>- **C is Incorrect:** AWS Trusted Advisor provides high-level account best-practice checks, including identifying idle resources, but does not trace Bedrock agent token execution paths.<br>- **D is Incorrect:** While Cost Explorer shows the total Bedrock spend, it cannot break down the spend into individual agent steps or tool calls to identify the specific cause of the spike.<br><br>> **Key Takeaway:** Agent invocations amplify costs through multiple internal LLM calls (planning, tool calling, synthesis); use Bedrock AgentCore Observability to trace and optimize token consumption per agent step. |
| **### Question 4 - Model Selection for Cost Optimization**<br><br>An e-commerce company is building a customer support chatbot on Amazon Bedrock to classify incoming messages into categories (e.g., "Shipping", "Returns", "Billing"). The workload has high volume, and the team wants to drastically reduce inference costs while maintaining acceptable classification accuracy.<br><br>What is the most appropriate action to optimize costs for this specific task?<br><br>- **A)** Implement Amazon Bedrock Provisioned Throughput for Claude 3 Opus.<br>- **B)** Downsize the model to a smaller, faster, and cheaper model (e.g., Claude 3 Haiku) better suited for classification.<br>- **C)** Enable Prompt Caching for the classification instructions.<br>- **D)** Use AWS Batch to process the chat messages at the end of the day.<br><br>*(Select ONE)* | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** For simple, high-volume tasks like text classification, using a smaller, lighter-weight model (like Claude 3 Haiku) drastically reduces the cost-per-token compared to a large frontier model, while still easily handling the classification logic.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Provisioned Throughput would guarantee capacity for the large model, but the cost per token remains high. It does not address the fundamental overkill of using a large model for a simple task.<br>- **C is Incorrect:** Prompt caching reduces the cost of the static prompt prefix, but the dynamic input and generation costs still use the expensive large model's per-token rate.<br>- **D is Incorrect:** A customer support chatbot requires real-time, interactive responses. Delaying classifications to the end of the day using AWS Batch ruins the user experience.<br><br>> **Key Takeaway:** "Right-sizing" in the Bedrock world means selecting the smallest model capable of meeting the quality requirement, which is the most effective way to reduce on-demand token costs for high-volume tasks. |

| **### Question 6 - RAG Embedding Cost Management**<br><br>A financial services firm uses Amazon Bedrock Knowledge Bases to index thousands of daily updated research reports into an Amazon OpenSearch Serverless vector database. The team has noticed that the daily ingestion job is generating unexpectedly high costs. They want to reduce the cost of computing embeddings for this workload.<br><br>Which action will directly optimize the embedding computation costs without impacting the query performance?<br><br>- **A)** Switch to a smaller embedding model (e.g., Amazon Titan Text Embeddings Lite) if the dimensionality and quality meet the search requirements.<br>- **B)** Enable Provisioned Throughput on the OpenSearch Serverless collection.<br>- **C)** Increase the chunk size to the maximum limit to reduce the number of OpenSearch documents.<br>- **D)** Disable the vector index at night when users are not querying the system.<br><br>*(Select ONE)* | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** Embedding models are billed per token. If a smaller embedding model (which processes tokens at a lower cost per token) still produces embeddings of sufficient quality for the retrieval task, switching to it directly reduces the daily ingestion costs.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Provisioned Throughput on OpenSearch Serverless relates to the capacity allocated for searching the index, not the cost of computing the embeddings themselves via Bedrock.<br>- **C is Incorrect:** Increasing chunk size to the maximum limit might reduce the number of vectors stored, but it severely degrades the quality of retrieval (making chunks too large to be semantically accurate), and does not necessarily lower the Bedrock embedding processing cost proportional to the tokens read.<br>- **D is Incorrect:** Disabling the vector index at night would prevent the daily ingestion job from running and complicate availability; it does not optimize the embedding computation cost itself.<br><br>> **Key Takeaway:** In a RAG pipeline, embedding computation costs scale with text volume. Selecting a smaller, cheaper embedding model that meets your semantic search quality needs is a direct cost optimization. |
| **### Question 7 - Caching Dynamic Prompts**<br><br>An AI engineer is implementing Prompt Caching in Amazon Bedrock for an application that generates marketing copy. The prompt consists of a 2,000-token static system prompt, followed by a dynamically generated timestamp and user session ID, and then the user's specific request.<br><br>After a week of testing, the engineer notices that cache hit rates are 0% and costs have actually increased. What is the most likely cause of this issue?<br><br>- **A)** The static system prompt is not long enough to meet the minimum token requirement for caching.<br>- **B)** The dynamic timestamp and session ID are placed before the static prompt prefix, invalidating the cache on every request.<br>- **C)** The model selected does not support prompt caching.<br>- **D)** The application is using on-demand inference instead of batch inference.<br><br>*(Select ONE)* | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Prompt caching requires an exact, sequential match of tokens from the beginning of the prompt. If dynamic variables (like a timestamp or session ID) are inserted before or within the static prefix, the sequence hash changes on every request, causing a cache miss. Additionally, writing tokens to the cache often incurs a higher cost than reading uncached input tokens, leading to increased overall costs.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** While there is a minimum prefix length for caching, 2,000 tokens generally exceeds the minimum (which is often around 1024 tokens depending on the model). The 0% hit rate points to a sequence mismatch, not length.<br>- **C is Incorrect:** The prompt states caching is implemented but hitting 0%, implying the model supports it but the implementation is flawed.<br>- **D is Incorrect:** The choice between on-demand and batch inference does not affect the mechanics of prompt caching hit rates within real-time invocations.<br><br>> **Key Takeaway:** To achieve prompt cache hits, static content must be placed at the very beginning of the prompt. Any dynamic content must be appended at the end of the prompt. |

| **### Question 10 - Managing Token Costs via Application Logic**<br><br>A software company has built a coding assistant using Amazon Bedrock. Users frequently paste large codebases into the prompt and ask the model to "explain everything." The team wants to control the rising inference costs by limiting the amount of output the model generates, while keeping the solution completely native to AWS with the least operational overhead.<br><br>Which approach will effectively manage the output token costs?<br><br>- **A)** Implement a custom AWS Lambda proxy to count words in the response and cut off the connection.<br>- **B)** Set the `max_gen_tokens` (or equivalent max tokens to generate) parameter in the Bedrock `InvokeModel` API request.<br>- **C)** Use an Amazon Bedrock Guardrail to block long responses.<br>- **D)** Switch the workflow to Amazon Bedrock Batch Inference.<br><br>*(Select ONE)* | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** The `InvokeModel` or `Converse` API in Amazon Bedrock accepts inference configuration parameters, including `maxTokens` (the maximum number of tokens the model can generate). Setting this parameter caps the output length directly at the API level, strictly controlling the output token cost without requiring custom code.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Using a Lambda proxy to count words and cut off a streaming connection is complex, prone to errors, and introduces unnecessary operational overhead and latency.<br>- **C is Incorrect:** Bedrock Guardrails are used for content moderation, PII redaction, and safety filters, not for enforcing strict response length limits for cost control.<br>- **D is Incorrect:** The coding assistant is an interactive, real-time use case. Batch inference is inappropriate as it does not provide real-time responses.<br><br>> **Key Takeaway:** The most efficient way to control output token costs at the application level is to use the native inference configuration parameters (like `maxTokens`) available in the Bedrock API request. |
