| **### Question 1 - Separating Code and Model Tests in MLOps**<br><br>A company is building an MLOps pipeline using AWS CodePipeline and Amazon SageMaker Pipelines. The team must separate the testing of their Python data preprocessing scripts from the evaluation of the trained model's performance. They want to achieve this with the least operational overhead. Which **TWO** approaches should they implement to properly separate these testing domains? (Select TWO)<br><br>- **A)** Use AWS CodeBuild to execute unit tests for the Python preprocessing scripts during the pipeline's Build stage.<br>- **B)** Use an Amazon SageMaker Processing job within SageMaker Pipelines to evaluate the model's accuracy on a held-out validation dataset.<br>- **C)** Use AWS CodeDeploy to run `pytest` on the trained model artifacts before deployment.<br>- **D)** Use Amazon EventBridge to schedule automated model evaluation jobs independently of the pipeline execution. | **Correct Answers:** **A** and **B**<br><br>**Correct Options Analysis:**<br>- **A is Correct:** AWS CodeBuild is the standard service for running unit tests on application and pipeline code (like Python data preprocessing scripts). It executes deterministically and fails fast before any expensive ML compute resources are provisioned.<br>- **B is Correct:** Amazon SageMaker Processing jobs are designed to run model evaluation scripts on managed compute infrastructure. When integrated into SageMaker Pipelines, this natively evaluates the model's performance metrics on a validation dataset, separating the model test from the code test.<br><br>**Distractor Analysis:**<br>- **C is Incorrect:** AWS CodeDeploy is used for deploying applications to compute services (like EC2, ECS, Lambda) and managing blue/green deployments, not for running unit tests like `pytest` on model artifacts.<br>- **D is Incorrect:** Amazon EventBridge is an event router service. While it can trigger pipelines, it cannot run the evaluation tests itself, nor does it provide a native mechanism to evaluate model performance metrics.<br><br>> **Key Takeaway:** In MLOps, code tests (unit tests for preprocessing logic) belong in CodeBuild, whereas model tests (accuracy, F1 score on holdout data) belong in SageMaker Processing jobs orchestrated by SageMaker Pipelines. |
| **### Question 2 - Generative AI Response Quality Testing**<br><br>A company is deploying an LLM application using Amazon Bedrock. They need an automated testing strategy in their CI/CD pipeline to ensure that a new prompt version does not degrade response quality. The testing approach must handle the non-deterministic nature of LLM outputs and minimize operational overhead. Which approach should the engineering team implement?<br><br>- **A)** Run a script in AWS CodeBuild to assert that the exact string output of the new prompt matches the expected baseline string.<br>- **B)** Use Amazon Bedrock Model Evaluation to run a curated prompt dataset and compare aggregate semantic scores against the previous prompt version.<br>- **C)** Deploy the new prompt to a canary endpoint and monitor CloudWatch latency metrics to determine if the prompt is performing well.<br>- **D)** Use Amazon SageMaker Ground Truth to manually label the LLM outputs before approving the pipeline stage. | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** Amazon Bedrock Model Evaluation supports automatic evaluation using LLM-as-a-judge or task-specific metrics (like faithfulness or toxicity). By running a curated prompt dataset through both the candidate and baseline prompt versions, the pipeline can compare aggregate semantic scores and block deployment if the candidate version's quality drops below a defined threshold. This is specifically designed for non-deterministic LLM outputs.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** LLM responses are non-deterministic; they vary between runs even for identical prompts. Exact string assertions will cause false negatives and flaky pipeline builds.<br>- **C is Incorrect:** CloudWatch latency metrics measure infrastructure and network responsiveness, not the semantic quality or correctness of the LLM's generated text.<br>- **D is Incorrect:** Using SageMaker Ground Truth introduces a manual human-in-the-loop labeling process, which violates the requirement for an automated CI/CD pipeline and increases operational overhead significantly.<br><br>> **Key Takeaway:** For generative AI, exact string matching fails due to non-determinism. Use automated evaluation frameworks (like Bedrock Model Evaluation) to score responses against semantic criteria rather than asserting exact outputs. |
| **### Question 3 - Gating Deployment on Model Metrics**<br><br>A data science team uses SageMaker Pipelines to orchestrate their ML workflow. The team needs to ensure that a newly trained model is automatically registered in the SageMaker Model Registry but blocked from being deployed to production unless its F1 score is strictly greater than 0.85. The solution must enforce this gate automatically with the least operational overhead. Which configuration achieves this?<br><br>- **A)** Configure an Amazon EventBridge rule to check the F1 score and trigger the deployment stage if it passes.<br>- **B)** Add a `ConditionStep` in SageMaker Pipelines that checks the evaluation metrics, followed by a `RegisterModel` step that only executes if the condition passes.<br>- **C)** Use an AWS Lambda function in AWS CodePipeline to manually query the SageMaker API for the F1 score and transition the pipeline state.<br>- **D)** Set up an Amazon CloudWatch Alarm on the F1 score to halt the pipeline execution. | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** SageMaker Pipelines natively supports a `ConditionStep`. This step can evaluate the metrics output by a prior evaluation step (e.g., checking if `F1Score > 0.85`). If the condition evaluates to true, it allows the downstream `RegisterModel` step to execute. If false, the pipeline skips registration. This is a fully native, serverless approach with zero custom code overhead.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Amazon EventBridge is an event router and cannot inherently parse ML evaluation metrics or manage SageMaker pipeline state transitions based on metric thresholds.<br>- **C is Incorrect:** Writing a custom AWS Lambda function introduces unnecessary operational overhead and custom code maintenance when SageMaker Pipelines offers a native `ConditionStep` for exactly this purpose.<br>- **D is Incorrect:** CloudWatch Alarms are used for runtime monitoring of deployed endpoints (like latency or 5XX errors), not for gating internal pipeline workflow steps based on batch evaluation metrics.<br><br>> **Key Takeaway:** Use SageMaker Pipelines `ConditionStep` to automatically gate model registration and deployment based on evaluation metrics, eliminating the need for custom Lambda functions. |

The testing must be fully automated within their AWS CodePipeline with the least operational overhead. It can automatically run a dataset of test queries against the updated knowledge base, retrieve the contexts, and score the retrieval and generation quality using metrics like answer relevance and faithfulness. This native integration requires minimal operational overhead.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Manually duplicating a collection and running search queries is a highly manual process that cannot be easily automated in a CI/CD pipeline and incurs high operational overhead.<br>- **B is Incorrect:** Measuring indexing latency via Lambda only tests the performance of the ingestion process, not the semantic accuracy or retrieval quality of the RAG system.<br>- **D is Incorrect:** Checking CloudWatch Logs for indexing errors verifies system health, not the accuracy of the chunking strategy or the quality of vector retrieval.<br><br>> **Key Takeaway:** When updating RAG components like chunking strategies, use Amazon Bedrock Model Evaluation to assess retrieval and generation quality natively against a baseline dataset. |

| **### Question 6 - Orchestrating Code and ML Workflows**<br><br>A machine learning team wants to automate their end-to-end ML workflow. The pipeline must handle both the unit testing of their Python code and the training of the model. They want to ensure that unit tests are executed before any expensive model training resources are provisioned, minimizing unnecessary compute costs. How should they design the CI/CD pipeline integration?<br><br>- **A)** Use SageMaker Pipelines for the entire workflow, adding a Processing job at the start to run unit tests.<br>- **B)** Trigger an AWS CodePipeline execution on code commit, use AWS CodeBuild for unit tests, and then trigger a SageMaker Pipeline for training and deployment.<br>- **C)** Use Amazon EventBridge to trigger a SageMaker Training Job, and use SageMaker Model Monitor to run unit tests.<br>- **D)** Deploy the code using AWS CodeDeploy to an EC2 instance, run the unit tests, and then trigger a SageMaker Pipeline. | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** AWS CodePipeline is the orchestration layer. By using AWS CodeBuild as the first stage, the team can execute fast, cheap unit tests on their code. If the tests fail, the pipeline halts immediately. Only if the tests pass does CodePipeline trigger the downstream SageMaker Pipeline, thus avoiding the cost of provisioning expensive ML training instances on broken code.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** While a SageMaker Processing job can run tests, it provisions ML-optimized compute instances which are more expensive and slower to start than AWS CodeBuild. Running unit tests here wastes resources.<br>- **C is Incorrect:** EventBridge triggers events but cannot run unit tests. SageMaker Model Monitor is for post-deployment monitoring of production endpoints, not pre-deployment unit testing.<br>- **D is Incorrect:** Using AWS CodeDeploy to deploy code to EC2 instances just to run unit tests introduces massive operational overhead and unnecessary infrastructure management.<br><br>> **Key Takeaway:** Separate cheap, fast code validation (AWS CodeBuild) from expensive ML compute (SageMaker Pipelines) by orchestrating them sequentially in AWS CodePipeline to minimize costs. |

The agent's configuration includes a new action group that calls an internal API. The CI/CD pipeline must test that the agent correctly invokes the new action group and returns the correct structured response before deployment. Which testing strategy meets this requirement with the least operational overhead while verifying the specific API invocation?<br><br>- **A)** Deploy the agent to a staging environment and manually invoke the action group via the AWS CLI.<br>- **B)** Configure an AWS Lambda function in AWS CodePipeline to invoke the Bedrock `InvokeAgent` API and parse the trace data to verify the correct action group invocation.<br>- **C)** Use Amazon Bedrock Model Evaluation to assess the agent's semantic text generation quality using a prompt dataset.<br>- **D)** Enable AWS CloudTrail to log the API calls made by the agent and manually inspect the logs post-deployment. | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** To specifically verify that an Agent correctly routes a request to a specific action group and invokes the right API, the pipeline must inspect the agent's trace data. Using a lightweight AWS Lambda function to call `InvokeAgent` with a test prompt and parse the `trace` object in the response is the standard, programmatic way to validate agent routing logic in a CI/CD pipeline.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Manual CLI invocation violates the requirement for an automated CI/CD pipeline testing strategy.<br>- **C is Incorrect:** Bedrock Model Evaluation is designed to evaluate LLM text generation, toxicity, and semantic quality, not to verify the specific routing of Bedrock Agent action groups or API invocations.<br>- **D is Incorrect:** Manually inspecting CloudTrail logs post-deployment is a reactive, manual process that does not gate the deployment in the CI/CD pipeline.<br><br>> **Key Takeaway:** To automate testing of Bedrock Agent action group routing, use a Lambda function to call `InvokeAgent` and programmatically assert against the returned trace data. |
| **### Question 8 - Regression Testing for Recommendation Models**<br><br>A retail company updates its product recommendation model weekly. Before deploying the new model version, the team needs to ensure it does not regress on critical user segments compared to the currently deployed model. The test must be automated within the AWS CodePipeline. Which AWS service is best suited to run this batch evaluation against historical data to gate the deployment?<br><br>- **A)** Amazon SageMaker Processing job running a custom evaluation script that compares predictions on a held-out test set.<br>- **B)** Amazon SageMaker Model Monitor using the `Bias` analysis type on the production endpoint.<br>- **C)** AWS CodeBuild running unit tests against the recommendation algorithm's Python code.<br>- **D)** Amazon QuickSight to visualize the differences between the model outputs. | **Correct Answer:** **A**<br><br>**Correct Option Analysis:**<br>- **A is Correct:** An Amazon SageMaker Processing job can take the new model and the current deployed model, run batch predictions against a held-out validation dataset, and execute a custom script to compare their metrics (e.g., precision@k). If the new model underperforms, the pipeline can be configured to halt. This is the standard approach for batch model regression testing.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** SageMaker Model Monitor analyzes live production traffic in real-time to detect data drift or model quality issues; it is not designed for pre-deployment batch regression testing against historical data.<br>- **C is Incorrect:** AWS CodeBuild runs unit tests for code logic, but model regression testing requires deploying both models to compute resources to generate predictions, which SageMaker Processing handles natively.<br>- **D is Incorrect:** Amazon QuickSight is a BI tool for visualizing data; it cannot execute model predictions, compute evaluation metrics, or gate a CI/CD pipeline.<br><br>> **Key Takeaway:** Pre-deployment regression testing against historical data is best handled by an Amazon SageMaker Processing job executing evaluation scripts, whereas Model Monitor is for post-deployment runtime analysis. |

Which configuration achieves this with the least operational overhead?<br><br>- **A)** Add a `RegisterModel` step directly after the training step, and use AWS CodePipeline to approve it.<br>- **B)** Create a `ConditionStep` that checks the evaluation metric, and if true, proceeds to a `RegisterModel` step configured with `ModelApprovalStatus="Approved"`.<br>- **C)** Use an AWS Lambda function to query the model registry and change the approval status post-registration.<br>- **D)** Set up an Amazon EventBridge rule to trigger an AWS Lambda function to approve the model after registration. | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** SageMaker Pipelines natively supports the `ConditionStep` which can evaluate the output metrics of an evaluation step. If the condition (`Accuracy > 0.90`) is met, it routes the workflow to the `RegisterModel` step. The `RegisterModel` step natively accepts a `ModelApprovalStatus` parameter, allowing the pipeline to register the model as `Approved` automatically without any custom code.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Registering the model directly without checking the metric first means unqualified models will be registered. The engineering team wants to ensure that the updated model configuration does not cause the LLM to hallucinate when asked out-of-domain questions. The testing approach must use a standardized set of prompts and automatically grade the responses based on a rubric before allowing deployment. Which approach is the most appropriate?<br><br>- **A)** Use Amazon Bedrock Guardrails to automatically block hallucinations, bypassing the need for pre-deployment testing.<br>- **B)** Configure an Amazon Bedrock Model Evaluation job using LLM-as-a-judge to grade the responses of the candidate model against the standardized prompts based on a rubric.<br>- **C)** Configure an AWS Lambda function to compare the cosine similarity of the candidate response with a single expected response.<br>- **D)** Enable SageMaker Model Monitor to detect hallucinations after the model is deployed to production. | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** Amazon Bedrock Model Evaluation allows teams to define a dataset of out-of-domain prompts. By utilizing the LLM-as-a-judge evaluation method, the pipeline can automatically grade the candidate model's responses against a specific rubric (e.g., "Does the model admit it lacks knowledge?"). If the scores fall below a threshold, the pipeline gates the deployment.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** While Bedrock Guardrails can filter content and block topics, they do not eliminate the need for pre-deployment testing of model behavior and prompt configurations. Guardrails are a runtime mitigation, not a CI/CD test.<br>- **C is Incorrect:** Cosine similarity is a rigid vector comparison that is ill-suited for grading nuanced LLM behaviors like admitting a lack of knowledge, where responses may vary significantly in text but share the same semantic meaning.<br>- **D is Incorrect:** SageMaker Model Monitor is used for post-deployment monitoring of production traffic, not for pre-deployment CI/CD gating against a standardized test set.<br><br>> **Key Takeaway:** To test for specific generative behaviors like hallucination in CI/CD, use Bedrock Model Evaluation with LLM-as-a-judge to grade responses against a rubric rather than relying on similarity scores or post-deployment monitoring. |
