| **### Question 1 - Explaining Traditional ML Predictions**<br><br>A financial services company is using an XGBoost model deployed on Amazon SageMaker AI to predict loan defaults. Regulatory compliance mandates that the bank must be able to explain to an auditor exactly why a specific customer's loan application was rejected, based on the input features provided. The solution must provide per-instance feature attribution with the least operational overhead.<br><br>Which approach should the ML engineer use to fulfill this requirement? (Select ONE)<br><br>- **A)** Compute the global feature importance of the XGBoost model using the built-in tree summary and provide it to the auditor.<br>- **B)** Use Amazon SageMaker Clarify to generate SHAP values for the specific customer's inference request to show how each feature contributed to the rejection.<br>- **C)** Run an A/B test deploying a shadow variant against the production model to compare feature distributions.<br>- **D)** Deploy a SageMaker Debugger hook to capture the gradients during the inference request and log them to Amazon S3. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** SageMaker Clarify uses SHAP (SHapley Additive exPlanations) to provide per-instance feature attribution. This allows the engineer to explain exactly how much each input feature (e.g., credit score, income) contributed to the specific prediction for an individual customer, satisfying the auditor's requirement with managed AWS tooling.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Global feature importance only tells which features are important across the entire dataset on average, not why a *specific* local prediction was made for a single customer.<br>- **C is Incorrect:** A/B testing or shadow testing is used to evaluate and compare the performance of two model variants against live traffic, not to explain the output of a specific prediction.<br>- **D is Incorrect:** SageMaker Debugger is used to debug training issues (like convergence or gradients) during model training, not to explain inference outputs on deployed models.<br><br>**Exam Tip / AWS Best Practice:** Use SageMaker Clarify and SHAP values for local, per-instance explainability to answer "why did this specific prediction happen?" for stakeholders and regulators. |
| **### Question 2 - RAG vs Fine-Tuned Model Explainability**<br><br>A healthcare technology company is building an AI assistant to answer doctors' queries about patient symptoms. The solution must use native AWS services and minimize custom code.<br><br>Which approach should the team choose to meet the explainability requirement? (Select ONE)<br><br>- **A)** Fine-tune an Amazon Titan model using Amazon SageMaker JumpStart, and generate a SageMaker Model Card to explain the training data.<br>- **B)** Use Amazon Bedrock Knowledge Bases to retrieve relevant medical text chunks and generate a response that natively includes source citations pointing to the retrieved passages.<br>- **C)** Deploy a custom Hugging Face model on SageMaker endpoints and use SageMaker Clarify to compute token-level SHAP values for the generated response.<br>- **D)** Use Amazon Comprehend Medical to extract medical entities, and ask a fine-tuned LLM to infer where it learned the information. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** A retrieval approach (RAG) using Amazon Bedrock Knowledge Bases can point directly to its source. It natively returns the retrieved passages alongside the generated response, providing built-in source attribution that satisfies the explainability and compliance requirement with minimal operational overhead.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** A customized (fine-tuned) model cannot point at the specific source document for a given output. A model card only documents the overall training dataset and model characteristics, not the source of individual generated facts.<br>- **C is Incorrect:** While token-level SHAP can explain which input tokens influenced an output, it does not provide factual source citations to external medical literature. It also requires custom code and high operational overhead.<br>- **D is Incorrect:** Amazon Comprehend Medical extracts entities from text but does not generate answers or provide attribution for a generative model's output.<br><br>**Exam Tip / AWS Best Practice:** A retrieval approach (RAG) can point at its source (citations), whereas a customized (fine-tuned) model cannot inherently explain where it learned a specific fact. |
| **### Question 3 - Evaluation vs. Explanation**<br><br>A data science team presents a report to business stakeholders about a newly deployed fraud detection model. The stakeholders ask: "Why did the model output a 90% fraud probability for this specific transaction?" The data science team currently has a dashboard displaying the overall F1 score, ROC-AUC, and a confusion matrix of the model. The stakeholders require a direct answer to their specific question.<br><br>Which action should the ML engineer take to provide the required information? (Select ONE)<br><br>- **A)** Provide the global ROC-AUC score to prove the model is highly accurate overall.<br>- **B)** Generate a SHAP explanation for the specific transaction's prediction to show how individual features shifted the probability to 90%.<br>- **C)** Show the confusion matrix to demonstrate that the model has a low false-positive rate.<br>- **D)** Set up a shadow test to see how a previous model would have scored the transaction. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** A score (like F1 or AUC) says how well the system did overall, but an explanation says *why* this particular answer came out the way it did. Generating a SHAP explanation for the specific instance provides the local feature attributions that answer the stakeholder's question directly.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** The ROC-AUC score is an evaluation metric representing model performance across all predictions, not an explanation for a single prediction.<br>- **C is Incorrect:** A confusion matrix aggregates evaluation results across a dataset; it does not explain the driving factors behind a single transaction's probability score.<br>- **D is Incorrect:** Shadow testing is used to compare a candidate model against a production model using live traffic. It does not explain the internal feature contributions of a specific prediction.<br><br>**Exam Tip / AWS Best Practice:** Do not confuse evaluation (measuring performance with metrics like accuracy or BLEU) with explanation (identifying the inputs that caused a specific output). |
| **### Question 4 - NLP Text Classification Explainability**<br><br>A marketing team is using a transformer-based model deployed on Amazon SageMaker AI to classify customer reviews as positive, neutral, or negative. After a misclassification incident where a negative review was labeled as positive, the engineering team needs to explain to the marketing lead which specific words in the review contributed most to the incorrect "positive" classification. The solution must use an appropriate explainability technique for NLP.<br><br>Which approach should the team use? (Select ONE)<br><br>- **A)** Compute the BLEU score of the review against a reference positive review.<br>- **B)** Use SageMaker Clarify to generate token-level explainability (such as SHAP or Integrated Gradients) to show the contribution of each word.<br>- **C)** Calculate the ROUGE-L score to measure the lexical overlap with known positive reviews.<br>- **D)** Deploy an A/B test to compare the current transformer model against a baseline logistic regression model. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** SageMaker Clarify supports explainability for computer vision and NLP tasks. For text classification, it can use techniques like SHAP or Integrated Gradients to provide token-level feature attributions, showing exactly which words in the input sequence drove the model's classification decision.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** BLEU is an evaluation metric for machine translation, measuring n-gram overlap with reference text. It does not explain model predictions.<br>- **C is Incorrect:** ROUGE is an evaluation metric for text summarization, measuring recall of n-grams. It does not provide token-level explainability for classification models.<br>- **D is Incorrect:** A/B testing compares the performance of two models against live traffic; it does not provide explainability for the internal token contributions of a specific misclassification.<br><br>**Exam Tip / AWS Best Practice:** For NLP and CV models, SageMaker Clarify provides local explainability at the token or pixel level to understand which parts of the input drove the prediction. |

The legal department requires that each prediction in the batch output file must include a breakdown of the top three contributing features for that specific customer's prediction. The team must generate these explanations without modifying the existing inference container code. The solution must use the least operational overhead.<br><br>Which AWS service should the team use to achieve this? (Select ONE)<br><br>- **A)** Amazon SageMaker Clarify<br>- **B)** Amazon SageMaker Debugger<br>- **C)** Amazon Bedrock Evaluations<br>- **D)** Amazon CloudWatch Logs Insights | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** SageMaker Clarify can be run as an asynchronous processing job to analyze datasets and generate SHAP values for model predictions. It can be configured to output the top contributing features for each instance without requiring modifications to the original model's inference container code.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** SageMaker Debugger is used to debug training jobs in real-time (e.g., monitoring gradients, tensors, and loss), not to generate post-hoc explanations for batch inference outputs.<br>- **C is Incorrect:** Amazon Bedrock Evaluations is used to evaluate the performance of foundation models and RAG systems (e.g., using LLM-as-a-judge or human raters), not for explaining traditional ML batch predictions.<br>- **D is Incorrect:** CloudWatch Logs Insights queries log data but does not compute mathematical feature attributions like SHAP values.<br><br>**Exam Tip / AWS Best Practice:** Use SageMaker Clarify Processing jobs to generate SHAP feature attributions asynchronously for batch datasets when you cannot modify the model's inference container. |
| **### Question 6 - Explaining LLM Outputs via Prompt Engineering**<br><br>A legal firm uses an Amazon Bedrock LLM (Anthropic Claude) to generate summaries of complex legal contracts. The legal team wants the model to explain its reasoning alongside the summary so that lawyers can trace how the model arrived at its conclusions. The solution must use the simplest method to make the model explain its output without altering the model weights or using complex post-hoc explainability libraries.<br><br>Which approach should the firm implement? (Select ONE)<br><br>- **A)** Fine-tune the Claude model with historical legal summaries and model cards.<br>- **B)** Use a chain-of-thought (CoT) prompt template in Amazon Bedrock, instructing the model to output its step-by-step reasoning before the final summary.<br>- **C)** Deploy the model on a SageMaker endpoint and use SageMaker Clarify to compute token-level SHAP values for the prompt and response.<br>- **D)** Implement a shadow test on the Bedrock endpoint to compare the generated summary with a human-generated summary. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** For generative AI and LLMs, a simple and effective way to explain the output is to instruct the model to show its work. Using chain-of-thought (CoT) prompting in Amazon Bedrock forces the model to generate its reasoning steps before arriving at the final answer, providing transparency without requiring post-hoc libraries.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Fine-tuning a model alters its weights but does not inherently make it explain its reasoning for specific prompts. Model cards document training data, not individual inferences.<br>- **C is Incorrect:** Computing token-level SHAP values for large language models is computationally expensive, highly complex, and not supported natively by SageMaker Clarify for models hosted on Bedrock.<br>- **D is Incorrect:** Shadow testing compares model variants against live traffic; it does not explain the reasoning behind a specific generated summary.<br><br>**Exam Tip / AWS Best Practice:** For LLMs, using prompt engineering techniques like chain-of-thought (CoT) to ask the model to "think out loud" is a practical way to provide reasoning and traceability for outputs. |
| **### Question 7 - Inherent Interpretability vs. Post-Hoc Explanation**<br><br>An insurance company needs to deploy a model to automatically approve or deny claims. The compliance department mandates that the model's decision-making process must be fully transparent and globally interpretable, rather than relying on a black-box model with post-hoc explanation libraries. The team must choose a modeling approach that natively explains its outputs and violates no compliance rules.<br><br>Which modeling approach satisfies this requirement? (Select ONE)<br><br>- **A)** Train a deep neural network and use SageMaker Clarify SHAP values to approximate feature importance.<br>- **B)** Train a gradient-boosted tree (XGBoost) model and use LIME for local approximations.<br>- **C)** Train a linear regression or decision tree model and extract the exact feature coefficients or decision paths.<br>- **D)** Fine-tune a large language model and ask it to explain its decision in natural language. | **Correct Answer:** **C**<br><br>**Correct Answer Analysis:**<br>- **C is Correct:** Linear regression and decision trees are inherently interpretable (white-box) models. Their decision processes can be exactly mapped by extracting feature coefficients or following the tree's decision paths, fulfilling the compliance requirement for full transparency without needing post-hoc approximations.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Deep neural networks are black-box models. SHAP provides post-hoc approximations of feature importance, not full transparency of the internal decision process, which may violate strict compliance rules.<br>- **B is Incorrect:** XGBoost is often considered a black-box model. LIME (Local Interpretable Model-agnostic Explanations) provides local approximations, not inherent global transparency.<br>- **D is Incorrect:** LLMs are massive black-box models. Asking it to explain its decision in natural language does not guarantee factual accuracy of its internal state and does not constitute mathematically transparent decision-making.<br><br>**Exam Tip / AWS Best Practice:** When compliance demands full transparency, use inherently interpretable models (like linear models or decision trees). Use post-hoc tools (Clarify, SHAP) only when forced to use black-box models. |

The solution must use an appropriate AWS tool for computer vision explainability.<br><br>Which technique should the team use? (Select ONE)<br><br>- **A)** Compute the BERTScore between the input image and the training dataset.<br>- **B)** Use SageMaker Clarify to generate computer vision explainability outputs (such as Grad-CAM or Integrated Gradients) highlighting pixel importance.<br>- **C)** Run a SageMaker Debugger hook to capture the loss function during inference.<br>- **D)** Generate a confusion matrix of all object classes evaluated by the model. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** SageMaker Clarify supports explainability for computer vision models.
