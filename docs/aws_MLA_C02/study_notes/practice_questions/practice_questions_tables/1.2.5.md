The team plans to use Amazon Bedrock to generate vector representations of the product images.<br><br>**Constraint:** The solution must use the least operational overhead and natively support image-to-image similarity searches without requiring a custom model training pipeline.<br><br>Which AWS service or feature should the ML engineer use?<br><br>**Select ONE that applies:**<br><br>- **A)** Use Amazon Titan Text Embeddings (v2) and convert images to text descriptions using a separate LLM before embedding.<br>- **B)** Use Amazon Titan Multimodal Embeddings (G1) to generate embeddings directly from the image data.<br>- **C)** Train a custom ResNet model using Amazon SageMaker to output feature vectors for the images.<br>- **D)** Use Amazon Comprehend to extract key phrases from the image metadata and embed the text. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Amazon Titan Multimodal Embeddings (G1) is a foundation model available in Amazon Bedrock specifically designed to convert both text and images into numerical vector representations. | **### Question 2 - RAG Chunking Strategies for Embeddings**<br><br>A legal firm is building a Retrieval-Augmented Generation (RAG) application using Amazon Bedrock Knowledge Bases. The source data consists of large, complex PDF contracts where clauses and definitions are heavily interdependent. <br><br>**Constraint:** The retrieval step must return coherent, contextually complete passages rather than arbitrary fragments of sentences. The team wants to use an automated chunking method that breaks documents based on natural structural boundaries.<br><br>Which chunking strategy should the ML engineer configure in the Bedrock Knowledge Base to meet this requirement?<br><br>**Select ONE that applies:**<br><br>- **A)** Fixed-size chunking with a small chunk size and high overlap percentage.<br>- **B)** Semantic chunking.<br>- **C)** No chunking (treat each PDF as a single chunk).<br>- **D)** Document-based hierarchical chunking. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Semantic chunking groups content into chunks based on natural divisions in the text, such as paragraphs, topics, or sentences, rather than an arbitrary character count. This ensures that related sentences and context remain together, producing more coherent embeddings and better retrieval results for complex legal documents.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Fixed-size chunking breaks text at arbitrary character limits, which often splits sentences or clauses mid-way, destroying the contextual integrity required for legal definitions.<br>- **C is Incorrect:** No chunking would mean embedding the entire contract as one massive vector. This dilutes the semantic meaning of specific clauses and exceeds typical token limits for embedding models.<br>- **D is Incorrect:** While hierarchical chunking maintains parent-child relationships, semantic chunking is specifically designed to break on natural structural boundaries (meaning) to ensure coherent, standalone passages. <br><br>> **Key Takeaway:** Use semantic chunking in Amazon Bedrock Knowledge Bases when documents require context to be preserved across naturally related text blocks rather than arbitrary character counts. |
| **### Question 3 - Embeddings vs. Categorical Encoding**<br><br>A data science team is preparing a dataset for a hybrid machine learning system. The dataset is a structured table containing two key fields: `customer_region` (e.g., "North", "South", "East") and `support_ticket_text` (a free-text field containing a paragraph describing the customer's issue). <br><br>**Constraint:** The transformation step must correctly represent both categorical labels and semantic meaning for downstream ML models.<br><br>Which combination of transformations should the engineer apply?<br><br>**Select ONE that applies:**<br><br>- **A)** Apply One-Hot Encoding to `customer_region` and One-Hot Encoding to `support_ticket_text`.<br>- **B)** Apply Amazon Titan Text Embeddings to `customer_region` and One-Hot Encoding to `support_ticket_text`.<br>- **C)** Apply One-Hot Encoding to `customer_region` and Amazon Titan Text Embeddings to `support_ticket_text`.<br>- **D)** Apply Amazon Titan Text Embeddings to both `customer_region` and `support_ticket_text`. | **Correct Answer:** **C**<br><br>**Correct Answer Analysis:**<br>- **C is Correct:** Categorical variables (`customer_region`) should be encoded using methods like One-Hot Encoding because they act as label substitutes without inherent semantic relationships. Free-text fields (`support_ticket_text`) contain semantic meaning and context, which should be captured using an embedding model like Amazon Titan Text Embeddings.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Applying One-Hot Encoding to free text would result in an incredibly sparse and meaningless matrix where every unique word or sentence becomes a category, destroying semantic similarity.<br>- **B is Incorrect:** Embedding a simple categorical label like "North" or "South" is unnecessary overhead; categorical encoding handles this efficiently without needing an embedding model.<br>- **D is Incorrect:** Using an embedding model for `customer_region` is computationally wasteful and does not improve the representation of discrete, unrelated labels.<br><br>> **Key Takeaway:** Categories get encoded (e.g., One-Hot Encoding), and meaning gets embedded (e.g., Amazon Titan Embeddings). |
| **### Question 4 - Frequent Knowledge Updates: RAG vs. Fine-Tuning**<br><br>An AI engineering team is developing an internal HR assistant using a foundation model. The assistant answers employee questions based on the company's employee handbook, which undergoes revisions and updates on a monthly basis.<br><br>**Constraint:** The solution must require the least rework and lowest compute overhead when the source documents change.<br><br>Which data preparation approach should the team use?<br><br>**Select ONE that applies:**<br><br>- **A)** Split the handbook into chunks, generate embeddings, and store them in a vector store for RAG.<br>- **B)** Build prompt and response pairs from the handbook and fine-tune the foundation model.<br>- **C)** Assemble the handbook as unlabeled text for continued pre-training.<br>- **D)** Assemble a prompt set covering the handbook and distill a smaller model from a larger one. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** RAG preparation makes knowledge retrievable. By storing chunked document embeddings in a vector store, the model can access the latest information. When the handbook changes monthly, the team only needs to re-index the updated chunks, requiring minimal compute overhead and no model weight updates.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Fine-tuning bakes knowledge directly into the model weights. Every monthly handbook revision would require recreating prompt-response pairs and running expensive GPU training pipelines.<br>- **C is Incorrect:** Continued pre-training is highly compute-intensive and designed to teach a model a domain's vocabulary/patterns, not to update factual policies dynamically.<br>- **D is Incorrect:** Distillation transfers capabilities from a teacher to a student model. Re-running this process monthly for document updates is cost-prohibitive and operationally heavy.<br><br>> **Key Takeaway:** Frequently changing knowledge belongs in a vector store (RAG); static behavior and tone belong in fine-tuning data. |

| **### Question 8 - Metadata Filtering in Vector Stores**<br><br>A financial services company is using a RAG pipeline with Amazon Bedrock Knowledge Bases and OpenSearch Serverless. They have ingested quarterly earnings reports from the last 10 years. When users ask about "2023 revenue," the vector store retrieves chunks from 2018 and 2023 because the word "revenue" appears in both, leading to conflicting answers.<br><br>**Constraint:** The solution must strictly limit the semantic similarity search to the correct document subset *before* performing the k-NN search, without requiring a smaller embedding model.<br><br>Which technique should the ML engineer implement?<br><br>**Select ONE that applies:**<br><br>- **A)** Decrease the chunk size to reduce the chance of retrieving irrelevant years.<br>- **B)** Extract the `year` as metadata from the documents and attach it to the embeddings, then use pre-filtering in OpenSearch.<br>- **C)** Increase the overlap size during chunking to capture more context about the year.<br>- **D)** Use an LLM to post-process the retrieved chunks and filter out older years. | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Extracting the `year` as metadata and attaching it to the vector chunks allows OpenSearch to perform pre-filtering. Pre-filtering restricts the search space to only chunks where `year=2023` *before* calculating vector distances, ensuring accurate retrieval and saving compute resources.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Decreasing chunk size does not solve the fundamental issue that the vector store contains multiple years of data with similar vocabulary.<br>- **C is Incorrect:** Increasing overlap helps maintain context within a single document but does not prevent the retrieval of chunks from entirely different documents (years).<br>- **D is Incorrect:** Using an LLM to post-process retrieved chunks adds latency and compute cost, and the LLM might not even see the correct chunk if it wasn't retrieved in the first place due to vector limits.<br><br>> **Key Takeaway:** Extracting metadata during ingestion and using pre-filtering in the vector store narrows retrieval to the right subset before similarity is even considered. |
