| **### Question 9 - Fixing Prompt Caching Inefficiencies**<br><br>An enterprise has enabled prompt caching for its Amazon Bedrock-powered legal assistant. The system prompt contains static instructions, but the team placed a dynamic timestamp at the very beginning of the prompt to track request timing. CloudWatch shows that the cache is constantly missing, and token costs are not decreasing. The team must optimize the caching mechanism to achieve **cost savings**.<br><br>What must the team change to make prompt caching effective?<br><br>- **A)** Increase the maximum response length to ensure the cache is utilized.<br>- **B)** Move the dynamic timestamp to the end of the prompt, after the static system instructions.<br>- **C)** Convert the request to Bedrock Batch Inference to force caching.<br>- **D)** Increase the instance count provisioned for the Bedrock endpoint.<br> | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** Prompt caching relies on an exact token sequence match from the beginning of the prompt. By placing a dynamic timestamp at the very beginning, the sequence changes on every request, invalidating the cache. Moving the dynamic content to the end allows the static prefix to be cached and reused successfully.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Response length does not affect the caching of the input prompt prefix.<br>- **C is Incorrect:** Batch Inference is a separate execution mode for asynchronous processing and does not "force" real-time prompt caching to work.<br>- **D is Incorrect:** Bedrock is a serverless service; users cannot adjust the instance count for an endpoint to fix caching logic issues.<br><br>> **Key Takeaway:** Prompt caching requires a stable, static prefix at the beginning of the prompt. Any dynamic content placed before or within the static prefix will invalidate the cache on every request. |
