| **### Question 1 - Safe Validation of a New XGBoost Model**<br><br>An enterprise retail company is updating its recommendation engine from an older XGBoost model to a newly trained version. The engineering team must validate the new model's performance against real-time production traffic to ensure it can handle current payload sizes and request concurrency.<br><br>Compliance policies strictly mandate that no customer can receive a response from the new model until it is fully approved, and the solution must introduce the least operational overhead.<br><br>Which approach satisfies these requirements?<br><br>- **A)** Deploy the new model as a shadow variant on the existing SageMaker endpoint, routing a copy of live traffic to it while production continues to serve responses.<br>- **B)** Configure an A/B test by splitting traffic 50/50 between the production model and the new model on the SageMaker endpoint.<br>- **C)** Use Amazon Bedrock Evaluations to run a programmatic evaluation job comparing both models against a stored historical dataset.<br>- **D)** Deploy the new model to a separate SageMaker endpoint and manually route a portion of API Gateway traffic to it using a weighted distribution. | **Correct Answer:** **A**<br><br>**Correct Answer Analysis:**<br>- **A is Correct:** SageMaker AI shadow testing natively deploys a candidate model alongside a production variant on the same endpoint. It asynchronously routes a copy of live requests to the shadow variant without returning the shadow variant's responses to the caller, satisfying the compliance constraint with zero impact to users.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** A/B testing routes live traffic to the candidate model and returns the candidate's responses to a percentage of users, violating the compliance mandate.<br>- **C is Incorrect:** Bedrock Evaluations (or any offline programmatic evaluation) relies on stored datasets rather than real-time live traffic, failing to test against current payload sizes and concurrency.<br>- **D is Incorrect:** Deploying a separate endpoint and manually configuring API Gateway routing introduces unnecessary operational overhead and requires custom traffic mirroring logic.<br><br>> **Key Takeaway:** Shadow testing validates a candidate model on live traffic with zero impact to the end-user experience by returning only production responses. |

It routes a copy of live traffic to the shadow variant without returning the shadow responses to the caller, allowing the team to validate the new container and instance under real load.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** SageMaker Model Monitor monitors the quality of incoming data and model predictions post-deployment, but it does not route live traffic to an undeployed candidate variant for testing.<br>- **C is Incorrect:** Bedrock Prompt Management is used for versioning and comparing prompt text templates for LLMs, not for validating Docker containers or endpoint instance types.<br>- **D is Incorrect:** MLflow tracks training runs, parameters, and artifacts, but does not handle live endpoint traffic mirroring.<br><br>> **Key Takeaway:** Use SageMaker Shadow Testing when you need to evaluate endpoint configuration changes (like instance type or container updates) against real live traffic without affecting production. |

SageMaker automatically emits operational metrics like `ModelLatency`, `OverheadLatency`, and `Invocation4XXErrors` to CloudWatch, broken down by variant name (Production vs. Shadow).<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** CloudTrail records API-level audit events (like `CreateEndpoint` or `InvokeEndpoint` calls) but does not contain the granular operational metrics (latency, memory, errors) of the model variants.<br>- **B is Incorrect:** OpenSearch can be used to ingest and search logs, but it is not the native source of SageMaker endpoint operational metrics.<br>- **D is Incorrect:** S3 Access Logs track bucket-level access requests, completely irrelevant to real-time ML endpoint invocation metrics.<br><br>> **Key Takeaway:** Operational metrics for SageMaker production and shadow variants are natively captured in Amazon CloudWatch, allowing for direct performance comparison. |

| **### Question 6 - Asynchronous Traffic Routing Mechanics**<br><br>A financial services firm is deploying a candidate model as a shadow variant on a SageMaker Real-Time endpoint. The production endpoint currently serves requests with a strict 100ms p99 latency Service Level Agreement (SLA).<br><br>The team must evaluate the candidate model under live load, but the architecture must guarantee that the performance of the shadow variant does not impact the production SLA. How does SageMaker Shadow Testing natively handle this constraint?<br><br>- **A)** The endpoint synchronously waits for both variants to return a response before sending the production response to the caller.<br>- **B)** A copy of the live request is asynchronously sent to the shadow variant, while only the production variant's response is returned to the caller immediately.<br>- **C)** The shadow variant processes requests in a batch job overnight based on the traffic logged during the day.<br>- **D)** Traffic is split 80/20, where 80% of callers receive the production response and 20% receive the shadow response.<br><br>*(Select ONE)* | **Correct Answer:** **B**<br><br>**Correct Answer Analysis:**<br>- **B is Correct:** SageMaker AI shadow testing asynchronously forks a copy of the real-time production request to the shadow variant. The production endpoint responds to the caller immediately without waiting for the shadow variant to finish processing, ensuring production latency is unaffected.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** The endpoint does not wait synchronously for the shadow variant, as this would introduce severe latency to the production response.<br>- **C is Incorrect:** Shadow testing evaluates live requests in real-time, not in an overnight batch process.<br>- **D is Incorrect:** This describes an 80/20 A/B test traffic split, which would expose 20% of users to the candidate model's responses, violating the shadow testing paradigm.<br><br>> **Key Takeaway:** Shadow traffic is routed asynchronously; the caller's response time depends solely on the production variant, completely isolating production SLAs from shadow variant performance. |

They have rigorously tested the model on a static validation dataset, achieving high accuracy. However, they are concerned that the model may fail when exposed to the specific image resolutions and payload sizes currently hitting their SageMaker production endpoint.<br><br>They must ensure the new model handles these live patterns before fully replacing the production model. Which approach will definitively prove the model's readiness under these constraints?<br><br>- **A)** Run another programmatic evaluation job in Amazon Bedrock using the same static validation dataset.<br>- **B)** Increase the size of the validation dataset and re-run the training pipeline with SageMaker Experiments.<br>- **C)** Deploy the new model as a shadow variant on the SageMaker Real-Time endpoint to evaluate it against live request patterns.<br>- **D)** Deploy the new model to the production endpoint and rely on SageMaker Model Monitor to catch drift.<br><br>*(Select ONE)* | **Correct Answer:** **C**<br><br>**Correct Answer Analysis:**<br>- **C is Correct:** Offline evaluation and live traffic often disagree because stored datasets rarely contain the exact request shapes, payload sizes, and concurrency of live production traffic. Deploying the model as a shadow variant evaluates it against real request patterns without risking production availability.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Re-running the programmatic evaluation on a static dataset does not test the model against live request shapes or payload sizes.<br>- **B is Incorrect:** Re-running the training pipeline addresses training accuracy but does not validate inference performance against live payloads.<br>- **D is Incorrect:** Replacing the production model immediately and relying on Model Monitor exposes users to potential failures before readiness is validated.<br><br>> **Key Takeaway:** A model that scores well on a stored dataset can still fail on live request shapes and payload sizes; shadow testing bridges this gap by testing against real traffic. |
