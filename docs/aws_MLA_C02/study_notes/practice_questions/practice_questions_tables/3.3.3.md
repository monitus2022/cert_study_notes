| **### Question 1 - SageMaker Pipeline Training Job Configuration**<br>

<br>

<br>A machine learning team is building an automated CI/CD pipeline using AWS CodePipeline and Amazon SageMaker Pipelines to train a custom XGBoost model. The training script is stored in an Amazon S3 bucket, and the training data is also located in S3. The pipeline must configure the training job with the least operational overhead and ensure that compute resources are released immediately after the job completes.<br>

<br>

<br>Which **ONE** approach should the engineer use to configure the training job within the pipeline?<br>

<br>

<br>- **A)** Provision an Amazon EC2 instance using a custom CloudFormation script to run the training script and terminate upon completion.<br>

<br>- **B)** Configure an AWS Lambda function to invoke the `CreateTrainingJob` API with a custom ECR image and instance configuration.<br>

<br>- **C)** Use a SageMaker Estimator step in SageMaker Pipelines, specifying the S3 data inputs, instance type, and a built-in or custom training container URI.<br>

<br>- **D)** Deploy an Amazon ECS Fargate task to run the training script and save the model artifacts back to S3. | **Correct Answer:** **C**<br>

<br>

<br>**Correct Answer Analysis:**<br>

<br>- **C is Correct:** Using a SageMaker Estimator within a SageMaker Pipeline is the native, AWS-recommended approach for configuring training jobs. It automatically provisions the compute instances, mounts the S3 data channels, executes the container, and releases the resources immediately after the job finishes, minimizing operational overhead.<br>

<br>

<br>**Distractor Analysis:**<br>

<br>- **A is Incorrect:** Provisioning and managing raw EC2 instances introduces significant operational overhead compared to SageMaker's managed training infrastructure.<br>

<br>- **B is Incorrect:** While invoking `CreateTrainingJob` via Lambda is possible, it requires writing and maintaining custom orchestration code, which violates the "least operational overhead" constraint when SageMaker Pipelines exists natively.<br>

<br>- **D is Incorrect:** Using ECS Fargate requires building a custom container orchestration setup for training, data downloading, and artifact uploading, rather than relying on SageMaker's built-in capabilities.<br>

<br>

<br>> **Key Takeaway:** SageMaker Pipelines and Estimators provide a managed, serverless way to configure and run training jobs without managing underlying compute instances. |
| **### Question 2 - Asynchronous Inference for Large Payloads**<br>

<br>

<br>An AI engineering team is automating the deployment of an inference endpoint for a computer vision model. The model generates predictions from large image payloads (up to 100 MB), and processing can take up to 5 minutes. The CI/CD pipeline must configure the inference job to handle these payloads without blocking the client application or dropping requests due to timeout limits.<br>

<br>

<br>Which **ONE** configuration satisfies these requirements?<br>

<br>

<br>- **A)** Configure a SageMaker Real-Time Inference endpoint with multiple instances and Application Auto Scaling.<br>

<br>- **B)** Configure a SageMaker Asynchronous Inference endpoint with an Amazon S3 bucket for input and output payloads.<br>

<br>- **C)** Configure a SageMaker Batch Transform job to run on an hourly schedule to process queued images.<br>

<br>- **D)** Deploy the model as an AWS Lambda function with extended timeout limits and provisioned concurrency.<br>

<br>

<br> | **Correct Answer:** **B**<br>

<br>

<br>**Correct Answer Analysis:**<br>

<br>- **B is Correct:** SageMaker Asynchronous Inference endpoints are designed specifically for large payload sizes (up to 1GB) and long processing times (up to 15 minutes). Clients place requests in an S3 queue, and the endpoint processes them asynchronously, returning results to an output S3 bucket without blocking or timing out.<br>

<br>

<br>**Distractor Analysis:**<br>

<br>- **A is Incorrect:** Real-Time Inference endpoints have a strict 60-second timeout limit per request and a 6MB payload limit for synchronous invocations, which would fail under the 5-minute processing time and 100MB payload constraints.<br>

<br>- **C is Incorrect:** Batch Transform is for offline, bulk processing of datasets, not for handling individual, on-demand client requests in near real-time.<br>

<br>- **D is Incorrect:** AWS Lambda has a maximum payload size of 10MB for synchronous invocations and a maximum execution timeout of 15 minutes, but it is not suitable for hosting heavy ML inference workloads natively without SageMaker.<br>

<br>

<br>> **Key Takeaway:** Use SageMaker Asynchronous Inference for payloads up to 1GB or inference requests that take up to 15 minutes to process. |
| **### Question 3 - IAM Role for Encrypted Training Jobs**<br>

<br>

<br>An MLOps engineer is defining a training job in a SageMaker Pipeline. The job reads data from a private Amazon S3 bucket and writes model artifacts to another S3 bucket. Both buckets are encrypted using customer-managed keys (CMKs) in AWS KMS. The training job must assume an IAM role with exactly the required permissions to access the data and the KMS keys, adhering to the principle of least privilege.<br>

<br>

<br>Which **TWO** configurations are required to allow the training job to read the encrypted S3 data and write the encrypted artifacts?<br>

<br>

<br>- **A)** Grant `s3:GetObject` and `s3:PutObject` permissions to the IAM role assumed by the SageMaker training job.<br>

<br>- **B)** Grant `kms:Decrypt` and `kms:GenerateDataKey` permissions to the IAM role assumed by the SageMaker training job.<br>

<br>- **C)** Attach a policy to the IAM role allowing the `sagemaker:CreateModel` permission for the specific KMS key.<br>

<br>- **D)** Configure the S3 bucket policy to allow public read access so the SageMaker compute instances can download the data without IAM constraints.<br>

<br>

<br> | **Correct Answers:** **A** and **B**<br>

<br>

<br>**Correct Answer Analysis:**<br>

<br>- **A is Correct:** The execution role assumed by SageMaker must have explicit S3 permissions (`s3:GetObject`, `s3:PutObject`) on the specific buckets to read the training data and write the output artifacts.<br>

<br>- **B is Correct:** Because the S3 buckets are encrypted with a KMS CMK, the SageMaker execution role must have `kms:Decrypt` (to read the input data) and `kms:GenerateDataKey` (to encrypt the output artifacts) permissions on the specific KMS key ARN.<br>

<br>

<br>**Distractor Analysis:**<br>

<br>- **C is Incorrect:** `sagemaker:CreateModel` is an IAM permission for creating a model package, not for KMS interactions or data access during training.<br>

<br>- **D is Incorrect:** Making an S3 bucket public violates security best practices and least privilege principles. IAM roles should be used to grant private, scoped access.<br>

<br>

<br>> **Key Takeaway:** When reading from or writing to KMS-encrypted S3 buckets, the SageMaker execution role requires both S3 bucket permissions and explicit KMS key permissions. |
| **### Question 4 - Event-Driven Retraining Triggers**<br>

<br>

<br>An AI startup is setting up a CI/CD pipeline for a predictive maintenance model. They want to trigger a retraining pipeline automatically whenever the F1 score of the deployed model drops below a certain threshold, as detected by Amazon SageMaker Model Monitor. The trigger must require the least amount of custom code and operational overhead.<br>

<br>

<br>Which **ONE** AWS service combination provides the event-driven trigger to start the SageMaker Pipeline?<br>

<br>

<br>- **A)** Use AWS Lambda to poll SageMaker Model Monitor metrics and trigger the pipeline using the Boto3 SDK.<br>

<br>- **B)** Use Amazon EventBridge to listen for SageMaker Model Monitor alerts and trigger the SageMaker Pipeline execution.<br>

<br>- **C)** Use AWS CloudTrail to log model monitor alerts and an S3 Event Notification to trigger the pipeline.<br>

<br>- **D)** Use Amazon CloudWatch Alarms to detect metric drops and send an SNS message to a custom microservice that starts the pipeline.<br>

<br>

<br> | **Correct Answer:** **B**<br>

<br>

<br>**Correct Answer Analysis:**<br>

<br>- **B is Correct:** Amazon SageMaker Model Monitor emits baseline drift or model quality violation events directly to Amazon EventBridge. EventBridge can be configured with a rule to match these violation events and automatically invoke the SageMaker `StartPipelineExecution` API, creating a native, event-driven retraining trigger with zero custom polling code.<br>

<br>

<br>**Distractor Analysis:**<br>

<br>- **A is Incorrect:** Polling metrics with a Lambda function introduces unnecessary operational overhead and custom code compared to native EventBridge integration.<br>

<br>- **C is Incorrect:** CloudTrail logs API calls but does not provide real-time metric evaluation or native pipeline triggering capabilities for Model Monitor baseline violations.<br>

<br>- **D is Incorrect:** Routing through CloudWatch Alarms and a custom microservice adds architectural complexity and points of failure; EventBridge can trigger the pipeline directly.<br>

<br>

<br>> **Key Takeaway:** SageMaker Model Monitor integrates natively with Amazon EventBridge, which can trigger automated retraining pipelines when model quality degrades. |
| **### Question 5 - Manual Approval in MLOps Pipelines**<br>

<br>

<br>A company is deploying an automated MLOps pipeline using SageMaker Pipelines. The pipeline successfully trains a new model version and evaluates its accuracy. The team mandates that a human must review the model's metrics before it is deployed to the production endpoint, and the pipeline must not execute the deployment step automatically.<br>

<br>

<br>Which **ONE** configuration fulfills this requirement?<br>

<br>

<br>- **A)** Add a Manual Approval step in AWS CodePipeline after the model registration step in SageMaker Model Registry.<br>

<br>- **B)** Configure the SageMaker Pipeline to pause indefinitely after the training step and wait for an API call to resume.<br>

<br>- **C)** Use an AWS Lambda function to send an email via Amazon SES and halt the pipeline execution until a link is clicked.<br>

<br>- **D)** Register the model in the SageMaker Model Registry with a "PendingManualApproval" status and separate the deployment into a CodePipeline stage gated by an approval action.<br>

<br>

<br> | **Correct Answer:** **D**<br>

<br>

<br>**Correct Answer Analysis:**<br>

<br>- **D is Correct:** The best practice for human-in-the-loop MLOps is to have the SageMaker Pipeline register the newly trained model in the SageMaker Model Registry with a `PendingManualApproval` status. A separate CI/CD tool (like AWS CodePipeline) can then be configured to trigger a deployment stage only when a human manually updates the model status to `Approved` in the registry.<br>

<br>

<br>**Distractor Analysis:**<br>

<br>- **A is Incorrect:** While AWS CodePipeline has a manual approval action, placing it after a SageMaker registry step without checking the registry's approval status doesn't enforce the registry's governance model natively. Option D correctly describes linking the approval status to the deployment gate.<br>

<br>- **B is Incorrect:** Pausing a SageMaker Pipeline indefinitely is not a supported, robust native feature for human-in-the-loop approvals; pipelines are meant to execute to completion (e.g., up to registration).<br>

<br>- **C is Incorrect:** Building a custom email and link-clicking mechanism via SES and Lambda introduces unnecessary operational overhead and security complexities compared to using Model Registry's built-in approval statuses.<br>

<br>

<br>> **Key Takeaway:** SageMaker Model Registry's `PendingManualApproval` status combined with AWS CodePipeline provides a native, auditable human-in-the-loop gating mechanism. |
| **### Question 6 - Warm Pools for Frequent Training Jobs**<br>

<br>

<br>A data science team needs to configure a SageMaker training job for a large NLP model. The team wants to reduce the cold start time of the training jobs, as they run frequently in their CI/CD pipeline. The instances must retain the conda environments, downloaded packages, and pre-built Docker images between runs without requiring the instances to run continuously.<br>

<br>

<br>Which **ONE** configuration achieves this with the least operational overhead?<br>

<br>

<br>- **A)** Configure a SageMaker Processing job with `KeepAlive` set to True.<br>

<br>- **B)** Configure the SageMaker Estimator in the pipeline with `KeepAliveConfig` enabled.<br>

<br>- **C)** Deploy a persistent Amazon EMR cluster and submit training jobs via Spark.<br>

<br>- **D)** Use a custom Amazon ECR image with all dependencies pre-installed and skip dependency installation in the script.<br>

<br>

<br> | **Correct Answer:** **B**<br>

<br>

<br>**Correct Answer Analysis:**<br>

<br>- **B is Correct:** SageMaker Managed Warm Pools (`KeepAliveConfig`) allow a provisioned training cluster to be retained in a warm state after a training job completes. This drastically reduces cold start times for subsequent training jobs because the cluster retains the EBS volume contents, conda environments, and downloaded data, without incurring continuous compute costs while idle.<br>

<br>

<br>**Distractor Analysis:**<br>

<br>- **A is Incorrect:** `KeepAlive` is not a parameter for SageMaker Processing jobs; it is specifically a configuration for Training jobs via `KeepAliveConfig`.<br>

<br>- **C is Incorrect:** Deploying an EMR cluster introduces significant operational overhead and continuous cost, violating the "least operational overhead" and "not running continuously" constraints.<br>

<br>- **D is Incorrect:** While a custom ECR image reduces dependency installation time, it does not solve the cold start issue of provisioning the compute instances and downloading the massive training datasets each time.<br>

<br>

<br>> **Key Takeaway:** SageMaker Managed Warm Pools (`KeepAliveConfig`) persist EBS volumes and environments between training jobs to minimize pipeline cold start times. |

| **### Question 8 - Batch Transform Input Configuration**<br>

<br>

<br>A machine learning team is configuring a SageMaker Batch Transform job to generate offline predictions for a daily reporting pipeline. The input data consists of a large JSON file where each line is a separate JSON object. The team needs to ensure the Batch Transform job correctly parses each JSON object as an individual invocation and outputs the predictions to an S3 bucket without requiring custom pre-processing code.<br>

<br>

<br>Which **ONE** configuration is required to handle the JSON input effectively?<br>

<br>

<br>- **A)** Set the `MaxPayloadInMB` parameter to the maximum allowed value to prevent timeouts.<br>

<br>- **B)** Configure the `AssembleWith` parameter to "Line" to concatenate the results properly.<br>

<br>- **C)** Specify the `ContentType` parameter as "application/json" and the `SplitType` parameter as "Line".<br>

<br>- **D)** Set the `ContentType` parameter to "application/x-jsonlines" and the `SplitType` parameter to "None".<br>

<br>

<br> | **Correct Answer:** **C**<br>

<br>

<br>**Correct Answer Analysis:**<br>

<br>- **C is Correct:** By setting `SplitType` to "Line", SageMaker Batch Transform will automatically split the input JSON file by newline characters. Each line (JSON object) is sent as an individual invocation to the model container. Setting `ContentType` to "application/json" tells the container how to parse the individual payload.<br>

<br>

<br>**Distractor Analysis:**<br>

<br>- **A is Incorrect:** `MaxPayloadInMB` governs the maximum size of a single payload sent to the container, but does not dictate how the input file is split into individual records.<br>

<br>- **B is Incorrect:** `AssembleWith` controls how the output files are assembled after inference, not how the input file is parsed or split.<br>

<br>- **D is Incorrect:** Setting `SplitType` to "None" would send the entire massive JSON file as a single payload to the container, likely causing memory issues or failing to process records individually.<br>

<br>

<br>> **Key Takeaway:** In SageMaker Batch Transform, `SplitType="Line"` is used to break up newline-delimited JSON files into individual invocations without custom preprocessing. |
| **### Question 9 - Custom Inference Container Requirements**<br>

<br>

<br>An enterprise is deploying a custom inference container for a PyTorch model. The container must run on a SageMaker Real-Time Inference endpoint. The CI/CD pipeline builds the container image and pushes it to Amazon ECR. The team needs to ensure the container adheres to the SageMaker inference container requirements to receive traffic correctly.<br>

<br>

<br>Which **ONE** interface must the container implement to handle invocation requests correctly?<br>

<br>

<br>- **A)** The container must expose port 8080 and implement the `/ping` and `/invocations` endpoints.<br>

<br>- **B)** The container must expose port 443 and implement the `/health` and `/predict` endpoints.<br>

<br>- **C)** The container must implement a Flask application listening on port 80.<br>

<br>- **D)** The container must run an nginx web server that proxies requests to the model using gRPC.<br>

<br>

<br> | **Correct Answer:** **A**<br>

<br>

<br>**Correct Answer Analysis:**<br>

<br>- **A is Correct:** SageMaker Real-Time Inference containers must expose port 8080. They are required to respond to HTTP GET requests on `/ping` (for health checks) and HTTP POST requests on `/invocations` (to receive inference payloads).<br>

<br>

<br>**Distractor Analysis:**<br>

<br>- **B is Incorrect:** SageMaker does not use port 443 or the `/health` and `/predict` endpoints for standard container inference interfaces.<br>

<br>- **C is Incorrect:** While Flask is commonly used to build the web server inside the container, SageMaker strictly requires port 8080, not port 80, and it must implement the specific endpoints `/ping` and `/invocations`.<br>

<br>- **D is Incorrect:** Nginx is not a requirement for SageMaker containers, and gRPC is not the default required interface for basic real-time endpoints.<br>

<br>

<br>> **Key Takeaway:** SageMaker requires custom inference containers to serve HTTP traffic on port 8080 and implement the `/ping` and `/invocations` endpoints. |
| **### Question 10 - Automating Instance Selection for Inference**<br>

<br>

<br>A company is preparing to deploy a highly optimized custom ML model to a SageMaker Real-Time Inference endpoint. They want to minimize inference costs while meeting strict latency and throughput requirements. They need to automate the process of finding the optimal instance type and configuration without manual load testing in their CI/CD pipeline.<br>

<br>

<br>Which **ONE** SageMaker feature should they use to find the best instance configuration?<br>

<br>

<br>- **A)** SageMaker Hyperparameter Tuning<br>

<br>- **B)** SageMaker Inference Recommender<br>

<br>- **C)** SageMaker Autopilot<br>

<br>- **D)** SageMaker Debugger<br>

<br>

<br> | **Correct Answer:** **B**<br>

<br>

<br>**Correct Answer Analysis:**<br>

<br>- **B is Correct:** SageMaker Inference Recommender is a feature that automatically tests and evaluates different instance types and configurations for a given model container. It runs load tests, measures latency, throughput, and cost, and provides a recommendation for the optimal endpoint configuration, fulfilling the CI/CD automation requirement.<br>

<br>

<br>**Distractor Analysis:**<br>

<br>- **A is Incorrect:** SageMaker Hyperparameter Tuning is used to optimize model weights and algorithm hyperparameters during the *training* phase, not for finding the optimal inference compute infrastructure.<br>

<br>- **C is Incorrect:** SageMaker Autopilot is an automated machine learning (AutoML) tool for training models from a dataset, not for load-testing or recommending endpoint instances.<br>

<br>- **D is Incorrect:** SageMaker Debugger is used to monitor training metrics, detect anomalies, and debug training scripts, not for deployment infrastructure optimization.<br>

<br>

<br>> **Key Takeaway:** Use SageMaker Inference Recommender to automate instance type selection and endpoint configuration load testing to minimize costs and meet latency targets. |
