| **### Question 1 - Auditing SageMaker Endpoint Invocations**<br><br>An AI engineering team has deployed a machine learning inference endpoint using Amazon SageMaker. The compliance team requires a complete audit trail of every prediction request made to the endpoint, including the identity of the caller and the timestamp. The team has an existing AWS CloudTrail trail configured for the account, but it only captures management events.<br><br>**Constraint:** Must enable the specific logging feature required without increasing operational overhead.<br><br>Which action should the engineer take to fulfill the compliance requirement? (Select ONE)<br><br>**A)** Modify the existing CloudTrail trail to enable data event logging for SageMaker.<br>**B)** Enable AWS Config to record data-plane API calls for the SageMaker endpoint.<br>**C)** Attach an AWS Lambda function to the SageMaker endpoint to log invocations to Amazon S3.<br>**D)** Use Amazon CloudWatch Container Insights to capture endpoint invocation metadata. | || **Correct Answer: A** ||<br><br>**Correct Answer Analysis:** SageMaker's `InvokeEndpoint` is classified as a data-plane operation (data event) in AWS CloudTrail. By default, CloudTrail only logs management events (control-plane operations like `CreateEndpoint`). Enabling data events for SageMaker on the existing trail fulfills the audit requirement with the least operational overhead.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** AWS Config records resource configuration states and changes over time, not individual data-plane API request metadata.<br>- **C is Incorrect:** Writing custom Lambda code to intercept and log invocations introduces unnecessary operational overhead and complexity compared to native CloudTrail logging.<br>- **D is Incorrect:** CloudWatch Container Insights captures performance metrics (CPU, memory) and application logs, not the IAM principal identity or API audit trail required for compliance.<br><br>> **Exam Tip:** In AWS CloudTrail, high-volume "Invoke" API actions (like `InvokeEndpoint` or `InvokeModel`) are classified as data events and must be explicitly enabled on the trail configuration. |
| **### Question 2 - Monitoring SageMaker Notebook Internet Access**<br><br>A financial services company operates an ML pipeline on Amazon SageMaker. Security policies mandate that all SageMaker notebook instances must have network traffic restricted to a specific VPC and must not have direct internet access. The engineering team needs to continuously monitor these configurations and receive alerts if a notebook instance is launched or modified with internet access enabled.<br><br>**Constraint:** Automated continuous monitoring using AWS native services with the least operational overhead.<br><br>Which solution meets these requirements? (Select ONE)<br><br>**A)** Create an AWS Config rule to evaluate SageMaker notebook instances for `DirectInternetAccess` settings and trigger an Amazon SNS notification.<br>**B)** Use AWS CloudTrail to monitor the `CreateNotebookInstance` API call and trigger an AWS Lambda function to evaluate the parameters.<br>**C)** Use Amazon Inspector to scan the notebook instances for unintended network exposure.<br>**D)** Enable VPC Flow Logs for the VPC and use Amazon Athena to query for internet-bound traffic originating from notebook instances. | || **Correct Answer: A** ||<br><br>**Correct Answer Analysis:** AWS Config is designed to continuously evaluate the configuration state of AWS resources against desired rules. Creating a Config rule for SageMaker notebook instances to check the `DirectInternetAccess` attribute allows for automated, continuous compliance checking and alerting via SNS without custom polling logic.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While CloudTrail records the API event, using EventBridge and Lambda to evaluate parameters is a point-in-time check rather than continuous configuration monitoring, adding unnecessary operational overhead.<br>- **C is Incorrect:** Amazon Inspector scans for software vulnerabilities and network exposure on EC2 instances, ECR images, and Lambda functions, not SageMaker notebook configurations.<br>- **D is Incorrect:** Querying VPC Flow Logs with Athena requires manual or scheduled query execution and provides high operational overhead compared to AWS Config rules.<br><br>> **Exam Tip:** For continuous configuration compliance monitoring (e.g., ensuring a resource setting is "Off" or "Private"), AWS Config is the preferred service over CloudTrail. |
| **### Question 3 - Auditing Amazon Bedrock Model Invocations**<br><br>An enterprise is developing a generative AI application using Amazon Bedrock. The security team needs to maintain an audit log of all API calls made to the Bedrock service to track which foundation models are being invoked by different applications. They currently have a multi-region AWS CloudTrail trail enabled with default settings, but no Bedrock invocations are appearing in the logs.<br><br>**Constraint:** Must capture Bedrock model invocation activity without modifying the application code.<br><br>What should the team do to ensure these calls are logged? (Select ONE)<br><br>**A)** Enable data event logging for Amazon Bedrock in the CloudTrail trail configuration.<br>**B)** Enable management event logging for Amazon Bedrock in the CloudTrail trail configuration.<br>**C)** Configure AWS Config to record Bedrock model invocations.<br>**D)** Attach an IAM policy to the application roles that requires logging to Amazon CloudWatch Logs. | || **Correct Answer: A** ||<br><br>**Correct Answer Analysis:** Amazon Bedrock's `InvokeModel` and `Converse` API operations are classified as data-plane events (data events) because they involve high-volume operational data access. A default CloudTrail trail only captures management events, so data events for Bedrock must be explicitly enabled in the trail configuration to audit model invocations.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Management events are enabled by default, but they do not capture model invocation calls (data events).<br>- **C is Incorrect:** AWS Config tracks resource configurations (like creating a Bedrock Guardrail) and state changes, not individual data-plane API invocations.<br>- **D is Incorrect:** While IAM policies can enforce CloudWatch logging, this does not fulfill the specific requirement to capture the audit trail in CloudTrail and requires application-level changes.<br><br>> **Exam Tip:** Just like SageMaker `InvokeEndpoint`, Bedrock `InvokeModel` is a data event. To audit "who called which model", enable CloudTrail data events. |
| **### Question 4 - Auditing S3 Object Access for ML Datasets**<br><br>A retail company stores its proprietary ML training datasets in an Amazon S3 bucket. Data scientists access this bucket using various IAM roles from their SageMaker Studio environments. The compliance officer requires an audit trail showing exactly which IAM role accessed which specific object in the S3 bucket, and at what time, for a forensic investigation.<br><br>**Constraint:** Must capture object-level read/write operations with the caller's IAM identity.<br><br>Which configuration is required to meet this compliance need? (Select ONE)<br><br>**A)** Enable S3 Object-Level logging (data events) in AWS CloudTrail for the specific S3 bucket.<br>**B)** Enable S3 Server Access Logging on the S3 bucket.<br>**C)** Create an AWS Config rule to monitor S3 object access patterns.<br>**D)** Enable AWS CloudTrail management events for S3. | || **Correct Answer: A** ||<br><br>**Correct Answer Analysis:** To capture the identity of the IAM principal making the request along with specific object-level API calls (like `GetObject` or `PutObject`), you must enable S3 data event logging in AWS CloudTrail. CloudTrail records the IAM identity, source IP, and requested resource.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While S3 Server Access Logging captures object-level access, it does not natively capture the full IAM principal identity context as comprehensively as CloudTrail, making it less ideal for IAM-based security audits.<br>- **C is Incorrect:** AWS Config evaluates bucket configurations (like public access blocks or encryption settings), not individual object read/write API requests.<br>- **D is Incorrect:** CloudTrail management events for S3 only log bucket-level operations (like `CreateBucket` or `DeleteBucket`), not object-level operations.<br><br>> **Exam Tip:** When an audit requires the "IAM Identity" of who accessed a specific S3 object, enable S3 Data Events in CloudTrail. |
| **### Question 5 - Centralized Logging for ML Workloads**<br><br>A global enterprise manages its machine learning workloads across multiple AWS accounts using AWS Organizations. The security team needs to establish a centralized, immutable audit trail of all management and data events related to SageMaker and S3 across all member accounts.<br><br>**Constraint:** Must minimize operational overhead and ensure centralized logging.<br><br>Which architecture meets these requirements? (Select ONE)<br><br>**A)** Create an organization trail in the management account that logs events for all member accounts into a centralized S3 bucket.<br>**B)** Deploy an individual CloudTrail trail in each member account, pointing to a central S3 bucket.<br>**C)** Use AWS Config aggregators to collect SageMaker API activity from all accounts.<br>**D)** Configure Amazon CloudWatch cross-account observability to stream CloudTrail events to a central account. | || **Correct Answer: A** ||<br><br>**Correct Answer Analysis:** An organization trail is a CloudTrail feature that automatically applies a trail configuration to all member accounts within an AWS Organization. By creating this in the management account, all API events from member accounts are automatically logged to a single, centralized S3 bucket, providing the lowest operational overhead.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Deploying and managing individual trails in each account introduces significant operational overhead and potential configuration drift.<br>- **C is Incorrect:** AWS Config aggregators collect resource configuration states, not CloudTrail API activity logs.<br>- **D is Incorrect:** Streaming CloudTrail logs through CloudWatch cross-account observability is more expensive and complex than simply delivering CloudTrail logs directly to a centralized S3 bucket.<br><br>> **Exam Tip:** For multi-account AWS Organizations environments, an Organization Trail in the management account is the AWS best practice for centralized CloudTrail logging. |
| **### Question 6 - Auditing Bedrock Guardrail Modifications**<br><br>A company is deploying an AI assistant using Amazon Bedrock with Guardrails configured to block sensitive information. The security team requires an audit log showing which IAM user or role created or modified the Bedrock Guardrails configurations. The team currently relies on AWS CloudTrail management events for their audit logs.<br><br>**Constraint:** Must capture the specific configuration events without additional complex configuration.<br><br>Will the current CloudTrail configuration capture these events, and why? (Select ONE)<br><br>**A)** Yes, because creating or modifying Bedrock Guardrails are control-plane (management) events, which are logged by default.<br>**B)** No, because Bedrock Guardrail configurations are data-plane events and require enabling data event logging in CloudTrail.<br>**C)** Yes, because AWS CloudTrail automatically logs all AWS service configurations via AWS Config, not CloudTrail.<br>**D)** No, because Bedrock Guardrails do not support AWS CloudTrail logging for configuration changes. | || **Correct Answer: A** ||<br><br>**Correct Answer Analysis:** Creating (`CreateGuardrail`), updating (`UpdateGuardrail`), or deleting (`DeleteGuardrail`) Bedrock Guardrails are administrative control-plane actions. AWS CloudTrail records these management events by default, so no additional configuration is needed to audit who made these changes.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Guardrail configuration changes are management events, not high-volume data-plane invocations like `InvokeModel`.<br>- **C is Incorrect:** While AWS Config may record the state of the Guardrail, CloudTrail independently records the management API calls by default.<br>- **D is Incorrect:** Bedrock Guardrails fully support CloudTrail logging for all configuration changes.<br><br>> **Exam Tip:** "Create", "Update", and "Delete" API actions for AI services (like Bedrock Guardrails, SageMaker Endpoints) are Management Events in CloudTrail and are enabled by default. |
| **### Question 7 - Automated Remediation for Public S3 Buckets**<br><br>An ML engineering team stores highly sensitive model artifacts in an Amazon S3 bucket. The security policy mandates that this S3 bucket must never be made public. The team needs an automated mechanism to detect if the bucket policy is changed to allow public access and to automatically revert the change without human intervention.<br><br>**Constraint:** Must provide automated remediation with the least operational overhead.<br><br>Which AWS service configuration fulfills this requirement? (Select ONE)<br><br>**A)** Enable an AWS Config rule for public S3 buckets and configure automatic remediation using AWS Systems Manager (SSM) Automation.<br>**B)** Configure an Amazon EventBridge rule to listen for `PutBucketPolicy` events in AWS CloudTrail and trigger an AWS Lambda function to revert the policy.<br>**C)** Use AWS Trusted Advisor to detect the public S3 bucket and send an email alert to the security team for manual remediation.<br>**D)** Enable Amazon Macie to scan the S3 bucket for public access and automatically block the bucket. | || **Correct Answer: A** ||<br><br>**Correct Answer Analysis:** AWS Config can continuously evaluate S3 bucket configurations against a "no public access" rule. If a bucket policy drifts, Config can natively trigger an SSM Automation runbook (e.g., `AWS-DisableS3BucketPublicAccess`) to automatically remediate the configuration, satisfying the zero-touch remediation requirement with minimal overhead.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While possible, writing and maintaining custom Lambda code for remediation introduces higher operational overhead than using native AWS Config + SSM Automation.<br>- **C is Incorrect:** Trusted Advisor provides alerts but does not perform automated remediation.<br>- **D is Incorrect:** Amazon Macie is for discovering and protecting sensitive data (PII), not for remediating S3 bucket public access configurations.<br><br>> **Exam Tip:** AWS Config combined with SSM Automation is the AWS native, least-overhead way to achieve automated configuration drift remediation. |
| **### Question 8 - Tracking IAM Role Configuration Changes in ML Pipelines**<br><br>An ML platform team uses AWS Step Functions to orchestrate a complex training pipeline that includes AWS Glue jobs and Amazon SageMaker processing jobs. The team must ensure that any changes to the IAM execution roles attached to these Step Functions state machines are audited, and any over-permissive inline policies are flagged immediately.<br><br>**Constraint:** Continuous configuration evaluation with automated alerting.<br><br>Which AWS service should be used to monitor and evaluate the IAM roles for this pipeline? (Select ONE)<br><br>**A)** AWS Config<br>**B)** AWS CloudTrail<br>**C)** Amazon Inspector<br>**D)** AWS CloudWatch Logs | || **Correct Answer: A** ||<br><br>**Correct Answer Analysis:** AWS Config is designed to continuously monitor and record resource configurations, including IAM roles and their inline/managed policies. By creating a Config rule (e.g., checking for overly permissive IAM policies), the team can automatically flag configuration drift and trigger alerts.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** CloudTrail records the API event (e.g., `PutRolePolicy`), but it is a point-in-time log, not a continuous configuration evaluator.<br>- **C is Incorrect:** Amazon Inspector scans for software vulnerabilities in EC2, ECR, and Lambda, not IAM policy configurations.<br>- **D is Incorrect:** CloudWatch Logs stores application and system logs, it does not evaluate IAM configurations.<br><br>> **Exam Tip:** When the requirement is to "continuously monitor configurations" or "flag configuration drift", AWS Config is the correct service. |
| **### Question 9 - Ensuring Immutability of CloudTrail Logs**<br><br>An ML engineering team must secure their AWS CloudTrail logs to meet strict regulatory compliance. The logs are stored in an Amazon S3 bucket. The compliance mandate requires that no one, including the root user, can delete or modify the log files once they are written, for a retention period of 7 years.<br><br>**Constraint:** Must ensure immutability of the audit logs with minimal operational overhead.<br><br>Which feature should the team implement on the S3 bucket to meet this requirement? (Select ONE)<br><br>**A)** Enable S3 Object Lock in Compliance Mode on the CloudTrail S3 bucket.<br>**B)** Enable S3 Versioning and MFA Delete on the CloudTrail S3 bucket.<br>**C)** Configure a bucket policy that denies `s3:DeleteObject` to all principals.<br>**D)** Use AWS CloudTrail log file integrity validation and store the logs in AWS Config. | || **Correct Answer: A** ||<br><br>**Correct Answer Analysis:** S3 Object Lock in Compliance Mode enforces a Write-Once-Read-Many (WORM) model. In Compliance Mode, not even the root user can delete or overwrite the object until the retention period expires. This meets the strict regulatory mandate for immutable logs.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While MFA Delete prevents accidental deletion, a privileged user (like root) can still bypass it or disable it. It does not guarantee immutability against all internal actors.<br>- **C is Incorrect:** Bucket policies can be overwritten by the root user or an administrator with `s3:PutBucketPolicy` permissions, making them less strict than Object Lock.<br>- **D is Incorrect:** Log file integrity validation proves logs haven't been altered, but it does not physically prevent deletion like S3 Object Lock does.<br><br>> **Exam Tip:** To make logs truly immutable (even against root), use S3 Object Lock in Compliance Mode. Governance Mode allows privileged users to bypass. |

By creating a Config rule that inspects the `VpcConfig` of SageMaker training jobs, AWS automatically detects if a job lacks VPC settings and triggers an SNS alert.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** EventBridge evaluating a CloudTrail event only catches the moment of creation. AWS Config is the correct tool for continuously evaluating the configuration state of resources.<br>- **C is Incorrect:** Amazon GuardDuty is for threat detection (unusual API usage, compromised instances), not for evaluating resource configuration compliance.<br>- **D is Incorrect:** VPC Flow Logs capture network traffic metadata, they do not evaluate whether a training job was configured to run in a VPC.<br><br>> **Exam Tip:** AWS Config is purpose-built for continuously evaluating whether resources conform to desired configurations (like running in a VPC or being encrypted). |
