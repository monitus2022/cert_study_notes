| **### Question 1 - Implementing Hybrid Search for E-Commerce Catalogs**<br><br>A retail company is building a RAG application using **Amazon Bedrock Knowledge Bases**. The application must retrieve semantically similar product descriptions while also ensuring exact matches for specific alphanumeric product SKUs (e.g., "AB-1234") in the same query. The vector store must support this dual requirement natively, and the team wants to use a fully managed AWS service to minimize operational overhead.<br><br>Which **TWO** steps should the ML engineer take to fulfill these requirements? (Select TWO)<br><br>- **A)** Select **Amazon OpenSearch Serverless** as the vector store for the Bedrock Knowledge Base.<br>- **B)** Select **Amazon Neptune** as the vector store to leverage graph-based entity retrieval.<br>- **C)** Enable hybrid search in the OpenSearch collection configuration to combine k-NN vector search with lexical text matching.<br>- **D)** Configure a custom Lambda function to perform separate vector and keyword searches before merging them in the prompt.<br>- **E)** Use **Amazon S3** as the vector store, as it automatically indexes metadata for keyword filtering. | **Correct Answers:** **A** and **C**<br><br>**Correct Options Analysis:**<br>- **A is Correct:** Amazon OpenSearch Serverless is a fully managed AWS service that natively integrates with Bedrock Knowledge Bases and supports advanced search capabilities, satisfying the least operational overhead requirement.<br>- **C is Correct:** Hybrid search combines dense vector search (for semantic similarity) with sparse lexical search (like BM25, for exact keyword/SKU matches) in a single query. OpenSearch Serverless supports this over a filterable text field.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Amazon Neptune is a graph database used for relationship-based retrieval, not for native hybrid (semantic + lexical) search over document text and vectors.<br>- **D is Incorrect:** Writing a custom Lambda function to merge separate searches introduces unnecessary operational overhead and reinvents a feature natively supported by OpenSearch's hybrid search.<br>- **E is Incorrect:** Amazon S3 can be used as a vector store for cost-effective, low-frequency queries, but it does not support native hybrid search or lexical text matching out of the box.<br><br>> **Key Takeaway:** OpenSearch Serverless is the ideal fully managed vector store for Bedrock Knowledge Bases when hybrid search (combining semantic similarity and exact keyword matching) is required. |
| **### Question 2 - Optimizing Retrieval Relevance with Reranking**<br><br>A legal tech startup has deployed an enterprise Q&A bot using **Amazon Bedrock Knowledge Bases** with an OpenSearch vector store. Initial testing reveals that while the vector search retrieves topically relevant documents, the specific paragraphs containing the legally binding precedents are often buried at the bottom of the top 10 retrieved chunks. The team must improve the relevance order of the retrieved chunks without rewriting the ingestion pipeline or changing the embedding model.<br><br>Which configuration change meets these requirements with the **LEAST** operational overhead?<br><br>- **A)** Increase the `top_k` value in the Bedrock Knowledge Base retrieval configuration from 10 to 50.<br>- **B)** Enable a reranking model (e.g., Amazon Rerank) in the Bedrock Knowledge Base retrieval configuration to re-score the retrieved chunks.<br>- **C)** Change the embedding model from Amazon Titan Text Embeddings v2 to a larger dimensional model.<br>- **D)** Implement a custom chunking strategy with smaller overlapping chunks and re-run the ingestion job. | **Correct Answer:** **B**<br><br>**Correct Options Analysis:**<br>- **B is Correct:** Bedrock Knowledge Bases supports the configuration of a reranking model. After the vector store retrieves the top *K* candidate chunks based on semantic similarity, the reranker (a cross-encoder or specialized reranking model) re-scores them based on semantic relevance to the user's query, elevating the most precise answers to the top of the list without changing the ingestion pipeline.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Increasing the `top_k` value retrieves more chunks, but it does not improve the ranking order of the most relevant chunks. It also increases token consumption and latency for the LLM generation step.<br>- **C is Incorrect:** Changing the embedding model requires re-indexing the entire vector store (re-running ingestion) and does not guarantee better ordering of specific precedents within the top results compared to a dedicated reranker.<br>- **D is Incorrect:** Re-chunking requires modifying the ingestion pipeline and re-running the entire ingestion job, violating the least operational overhead constraint.<br><br>> **Key Takeaway:** Reranking models in Bedrock Knowledge Bases are applied at query time to improve the relevance order of retrieved chunks without altering the underlying vector index or ingestion pipeline. |
| **### Question 3 - Metadata Filtering for Secure Retrieval**<br><br>A financial services firm is building an HR document Q&A system using **Amazon Bedrock Knowledge Bases**. The HR documents are stored in Amazon S3 and contain sensitive salary bands restricted to management, as well as general policies available to all employees. The retrieval pipeline must ensure that an employee querying "salary bands" never retrieves management-only documents. The firm wants to enforce this at the retrieval stage before the LLM generates a response.<br><br>Which feature of Bedrock Knowledge Bases should the engineer implement to satisfy this requirement?<br><br>- **A)** Implement an Amazon Bedrock Guardrail to filter out PII in the generated response.<br>- **B)** Use metadata filtering in the retrieval configuration to restrict the search to documents tagged with the user's access level.<br>- **C)** Configure OpenSearch Serverless fine-grained access control to restrict read access to the index.<br>- **D)** Apply S3 bucket policies to restrict access to the management-only PDF files. | **Correct Answer:** **B**<br><br>**Correct Options Analysis:**<br>- **B is Correct:** Metadata filtering allows the retrieval pipeline to narrow the candidate set of vectors *before* similarity is measured. By ingesting documents with metadata (e.g., `access_level: "management"` or `access_level: "all"`) and passing this metadata as a filter during the retrieval API call, the vector store will only return chunks that match the user's specific permissions.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Bedrock Guardrails operate on the model's input and output to mask PII or block harmful content, but they do not restrict the document retrieval phase based on user roles.<br>- **C is Incorrect:** While OpenSearch supports fine-grained access control, Bedrock Knowledge Bases abstracts this. The standard pattern for access control within a KB is metadata filtering at query time, not changing the index's read permissions per user dynamically.<br>- **D is Incorrect:** S3 bucket policies protect the raw files in S3, but once the documents are parsed and embedded into the vector store, S3 policies have no effect on the retrieval pipeline.<br><br>> **Key Takeaway:** Metadata filtering turns retrieval into a secure pipeline by narrowing the candidate pool based on user attributes before vector similarity is even calculated. |
| **### Question 4 - Resolving Index Dimension Mismatches**<br><br>A data science team is configuring an **Amazon Bedrock Knowledge Base** using **Amazon Aurora PostgreSQL** as the vector store. The team selected the Amazon Titan Text Embeddings v1 model for ingestion. During the creation of the vector store configuration, they manually set the vector index dimensions to `1024`. When they start the ingestion job, it fails immediately with a configuration error. The team must resolve this with the least administrative effort.<br><br>What is the root cause of this failure and how should it be fixed?<br><br>- **A)** The index dimensions must match the output dimensions of the selected embedding model (e.g., 1536 for Titan v1); the team must update the vector store configuration.<br>- **B)** Aurora PostgreSQL does not support custom dimensions; the team must switch to OpenSearch Serverless.<br>- **C)** The ingestion job requires a VPC endpoint to Aurora; the team must add a private path to the database.<br>- **D)** The team must use a binary vector quantization format to reduce the 1024 dimensions to match the model's output. | **Correct Answer:** **A**<br><br>**Correct Options Analysis:**<br>- **A is Correct:** The vector index dimensions declared in the knowledge base configuration *must exactly match* the output dimensions of the specified embedding model. Amazon Titan Text Embeddings v1 outputs 1536 dimensions. A mismatch between the vector store schema and the embedding output will cause the ingestion job to fail when it attempts to insert the vectors.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Aurora PostgreSQL (with the `pgvector` extension) does support vector dimensions up to 16,000. The issue is the mismatch with the specific model, not a limitation of Aurora.<br>- **C is Incorrect:** While VPC configuration is necessary for private networking, a VPC connectivity issue would manifest as a timeout or network unreachable error, not an immediate configuration validation error regarding dimensions.<br>- **D is Incorrect:** Binary vector quantization is a storage optimization technique and is not the cause of an initial schema dimension mismatch during job setup.<br><br>> **Key Takeaway:** The index dimensions in the vector store configuration must be declared correctly before ingestion and must perfectly match the chosen embedding model's output dimensions. |

The solution must be highly available.<br><br>Which vector store configuration best meets these requirements?<br><br>- **A)** Use **Amazon OpenSearch Serverless** and store relational data as metadata fields.<br>- **B)** Use **Amazon Aurora PostgreSQL** with the `pgvector` extension as the vector store for Bedrock Knowledge Bases.<br>- **C)** Use **Amazon Neptune** to map relationships between tracking IDs and delivery notes.<br>- **D)** Use **Amazon S3** and retrieve the structured data using an AWS Lambda function after vector search. | **Correct Answer:** **B**<br><br>**Correct Options Analysis:**<br>- **B is Correct:** Aurora PostgreSQL with the `pgvector` extension is an integrated solution that allows vector embeddings to be stored right beside the relational records they describe. This fulfills the requirement of querying semantically similar text while natively joining with structured relational data (like tracking IDs) without managing a separate vector database, minimizing operational overhead.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** While OpenSearch can store metadata, it is not a relational database. The team wants to use a managed AWS service optimized for this specific retrieval pattern.<br><br>Which vector store and search strategy should the ML engineer implement?<br><br>- **A)** Amazon OpenSearch Serverless with hybrid search.<br>- **B)** Amazon S3 with metadata filtering.<br>- **C)** Amazon Neptune with SPARQL/Gremlin queries.<br>- **D)** Amazon RDS for MySQL with standard SQL LIKE queries. | **Correct Answer:** **C**<br><br>**Correct Options Analysis:**<br>- **C is Correct:** Amazon Neptune is a purpose-built graph database. For retrieval that explicitly requires following relationships and paths between interconnected entities (like drugs, genes, and proteins), a graph store supports traversals natively using query languages like Gremlin or SPARQL, which is exactly what this scenario requires.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** OpenSearch is a search service optimized for document text and vector similarity, not for traversing complex, multi-hop relationship graphs.<br>- **B is Incorrect:** S3 is an object store and cannot perform relationship traversals or complex graph queries.<br>- **D is Incorrect:** While SQL can perform JOINs, querying multi-hop relationships in a relational database is highly inefficient and complex compared to a native graph database.<br><br>> **Key Takeaway:** When the core business requirement is to retrieve information by traversing interconnected entities and relationships, Amazon Neptune (a graph database) is the correct architectural choice. |

| **### Question 10 - Balancing Retrieval Count and LLM Context Window**<br><br>An AI engineer is tuning the retrieval configuration of an **Amazon Bedrock Knowledge Base** for a technical support bot. The chosen LLM has a context window limit of 8,000 tokens. The current configuration retrieves the top 20 chunks (`k=20`), which frequently exceeds the context window and causes API errors. The team wants to ensure the generation step receives the most relevant context without exceeding token limits, using native Bedrock features.<br><br>Which configuration should the engineer modify to meet this requirement?<br><br>- **A)** Decrease the chunk size during the ingestion job and reduce the `k` value in the retrieval configuration.<br>- **B)** Increase the `k` value and switch to a larger embedding model.<br>- **C)** Implement a custom orchestrator using AWS Step Functions to truncate the text before passing it to the LLM.<br>- **D)** Use Amazon Bedrock Guardrails to automatically summarize the retrieved chunks. | **Correct Answer:** **A**<br><br>**Correct Options Analysis:**<br>- **A is Correct:** Retrieving 20 chunks can easily exceed the 8,000 token limit. Reducing the `k` value (e.g., top 3 or 5) limits the number of retrieved passages. If the chunks themselves are too large, adjusting the chunking strategy during ingestion to smaller chunks ensures that the total retrieved context fits within the LLM's context window.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Increasing the `k` value would worsen the context window overflow. The embedding model size does not dictate the output token count of the retrieved chunks.<br>- **C is Incorrect:** While a custom orchestrator could truncate text, it introduces high operational overhead. Bedrock Knowledge Bases natively handles prompt assembly, and standard practice is to adjust `k` and chunk size to fit context limits.<br>- **D is Incorrect:** Bedrock Guardrails are used for safety, content filtering, and PII redaction, not for summarizing context to fit token limits.<br><br>> **Key Takeaway:** To prevent exceeding the LLM context window in a RAG pipeline, tune the retrieval `top_k` value and the document chunk size during ingestion to control the total volume of text passed to the generation model. |
