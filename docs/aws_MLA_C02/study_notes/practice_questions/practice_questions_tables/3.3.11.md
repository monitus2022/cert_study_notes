| **### Question 1 - Event-Driven Sync for Bedrock Knowledge Bases**<br><br>An enterprise uses an Amazon Bedrock Knowledge Base connected to an S3 bucket containing internal HR policies. HR uploads new or updated PDF documents irregularly throughout the week.<br><br>The engineering team needs to automate the ingestion process to keep the vector index up-to-date with the **least operational overhead** and the **lowest latency** from the time a document is uploaded to its availability in the RAG application.<br><br>Which approach meets these requirements? (Select ONE)<br><br>- **A)** Configure an S3 Event Notification to trigger an AWS Lambda function that invokes the Bedrock `StartIngestionJob` API.<br>- **B)** Configure an Amazon EventBridge cron rule to run the `StartIngestionJob` API every 15 minutes.<br>- **C)** Create an AWS Glue crawler that detects changes and triggers an AWS Step Functions state machine to update OpenSearch Serverless.<br>- **D)** Enable S3 Versioning and configure the Bedrock Knowledge Base to automatically listen to S3 event notifications natively without custom code. | **Correct Answer:** **A**<br><br>**Correct Option Analysis:**<br>- **A is Correct:** Configuring an S3 Event Notification to trigger a Lambda function that calls the `StartIngestionJob` API provides an event-driven architecture. This ensures the ingestion job runs immediately when documents are uploaded, satisfying the lowest latency requirement with minimal operational overhead.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** While a scheduled EventBridge rule automates the process, a 15-minute cron interval introduces unnecessary latency compared to an event-driven trigger.<br>- **C is Incorrect:** Using an AWS Glue crawler and Step Functions introduces unnecessary operational complexity and overhead. Bedrock Knowledge Bases natively handle parsing and chunking, so custom orchestration is redundant.<br>- **D is Incorrect:** Amazon Bedrock Knowledge Bases do not currently support natively listening to S3 Event Notifications out-of-the-box to trigger ingestion jobs automatically without an intermediary compute service like Lambda.<br><br>> **Key Takeaway:** For irregular, latency-sensitive document uploads to a Bedrock Knowledge Base, use an S3 Event Notification to Lambda to trigger the `StartIngestionJob` API. |
| **### Question 2 - Updating Embedding Models in RAG Pipelines**<br><br>A financial services company is using a RAG pipeline with Amazon OpenSearch Serverless as its vector store, populated via an Amazon Bedrock Knowledge Base. The data science team decides to upgrade the embedding model from Amazon Titan Embeddings G1 to Titan Embeddings G2 to improve retrieval accuracy.<br><br>The team needs to update the pipeline while ensuring the application experiences **no stale vectors** and **no downtime** during the transition.<br><br>Which strategy should the team implement? (Select ONE)<br><br>- **A)** Update the embedding model configuration in the Bedrock Knowledge Base and trigger an incremental ingestion job to re-embed only the documents accessed most recently.<br>- **B)** Update the embedding model in the Knowledge Base configuration and perform a full re-sync of the data source to regenerate all vectors.<br>- **C)** Create a new OpenSearch Serverless collection and a new Knowledge Base with the G2 model, run a full ingestion job, then repoint the application to the new Knowledge Base.<br>- **D)** Export the vectors from OpenSearch, apply the new model via a SageMaker Processing job, and import them back into the existing collection. | **Correct Answer:** **C**<br><br>**Correct Option Analysis:**<br>- **C is Correct:** Creating a new collection and Knowledge Base alongside the existing one allows the new G2 model to ingest the full corpus independently. Once the new index is fully populated and verified, repointing the application to the new endpoint ensures zero downtime and guarantees no stale G1 vectors are served.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** An incremental sync will NOT re-embed unchanged documents. Because the embedding model changed, ALL existing vectors are stale, and an incremental sync will leave the majority of the corpus with G1 vectors.<br>- **B is Incorrect:** Updating the existing Knowledge Base and performing a full re-sync will cause downtime or a period where the index is a mix of G1 and G2 vectors, leading to inconsistent retrieval performance.<br>- **D is Incorrect:** Manually exporting, processing, and importing vectors bypasses the Bedrock Knowledge Base managed ingestion, introducing significant operational overhead and potential for error.<br><br>> **Key Takeaway:** When upgrading the embedding model in a RAG pipeline, use a blue/green deployment pattern by creating a new vector index and Knowledge Base to avoid serving mixed or stale vectors and to ensure zero downtime. |

(Select ONE)<br><br>- **A)** Configure a native S3 data source in Kendra and use an Amazon EventBridge schedule to trigger the `StartDataSourceSyncJob` API daily.<br>- **B)** Configure an AWS Glue ETL job to push documents to Kendra using the `BatchPutDocument` API daily.<br>- **C)** Use an S3 Event Notification to trigger an AWS Lambda function that calls the `BatchPutDocument` API for each file.<br>- **D)** Re-create the Kendra index daily using an AWS CloudFormation template to ensure a clean state. | **Correct Answer:** **A**<br><br>**Correct Option Analysis:**<br>- **A is Correct:** Configuring a native S3 data source connector in Kendra and triggering the `StartDataSourceSyncJob` API via EventBridge is the most operationally efficient method. Kendra's native sync performs incremental updates, only processing changed or deleted documents, avoiding a full re-index.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** Using a Glue ETL job to push documents via `BatchPutDocument` introduces unnecessary operational overhead and bypasses Kendra's built-in data source synchronization and change detection logic.<br>- **C is Incorrect:** Triggering a Lambda function for every S3 object upload to call `BatchPutDocument` is inefficient for batch updates and can lead to throttling limits, adding unnecessary operational complexity.<br>- **D is Incorrect:** Re-creating the Kendra index daily is highly inefficient, destroys access control configurations, and causes significant downtime, violating the least operational overhead requirement.<br><br>> **Key Takeaway:** For Amazon Kendra updates from S3, use the native S3 data source connector and trigger the `StartDataSourceSyncJob` API via EventBridge to perform incremental syncs efficiently. |
| **### Question 4 - CI/CD for Chunking Strategy Updates**<br><br>A healthcare company has a Bedrock Knowledge Base with a large corpus of medical journals. They want to implement a CI/CD pipeline using AWS CodePipeline that automatically updates the Knowledge Base when a new chunking strategy is committed to their repository.<br><br>The update must ensure that the entire corpus is re-processed to reflect the new chunking boundaries **without manual intervention**.<br><br>Which approach should the pipeline take? (Select ONE)<br><br>- **A)** Configure CodePipeline to trigger a full ingestion job on the Bedrock Knowledge Base using the `StartIngestionJob` API.<br>- **B)** Configure CodePipeline to trigger an incremental ingestion job, as the chunking strategy change will automatically flag all documents as changed.<br>- **C)** Configure CodePipeline to invoke a SageMaker Processing job that manually chunks the documents and writes the output directly to the existing OpenSearch index.<br>- **D)** Configure CodePipeline to deploy an AWS Lambda function that copies the existing OpenSearch index to a new collection, preserving the old vectors. | **Correct Answer:** **A**<br><br>**Correct Option Analysis:**<br>- **A is Correct:** Changing the chunking strategy means all existing chunks and their corresponding vectors are invalid. A full ingestion job is required to re-chunk and re-embed the entire corpus according to the new configuration.<br><br>**Distractor Analysis:**<br>- **B is Incorrect:** An incremental ingestion job only detects document-level changes (added, modified, or deleted files based on metadata). It does NOT detect changes to the Knowledge Base's global chunking configuration and will skip re-processing unchanged files.<br>- **C is Incorrect:** Invoking a SageMaker Processing job bypasses the managed capabilities of Bedrock Knowledge Bases, introducing unnecessary custom code and operational overhead.<br>- **D is Incorrect:** Copying the existing OpenSearch index preserves the old chunking strategy and vectors, defeating the purpose of the update.<br><br>> **Key Takeaway:** Changes to a Bedrock Knowledge Base's global settings (like embedding model or chunking strategy) require a full ingestion job (re-sync), as incremental syncs only track source data changes, not configuration changes. |

(Select ONE)<br><br>- **A)** Update the prompt text directly in the application code repository and deploy the application via AWS CodeDeploy.<br>- **B)** Use the `GetPrompt` API in the application to fetch the latest version of the prompt dynamically by specifying an alias.<br>- **C)** Hardcode the prompt ARN in the application configuration and update the configuration file via AWS Systems Manager Parameter Store on each new release.<br>- **D)** Use an S3 bucket to store the prompt text and have the application read the file at runtime. | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** Bedrock Prompt Management allows you to create version aliases (e.g., "PRODUCTION"). (Select ONE)<br><br>- **A)** Configure an S3 Event Notification for object deletion to trigger an AWS Lambda function that calls the `StartIngestionJob` API for every deletion event.<br>- **B)** Configure an S3 Event Notification for object deletion to trigger an AWS Lambda function that manually queries and deletes vectors from OpenSearch Serverless.<br>- **C)** Set up a daily scheduled EventBridge rule to run the Bedrock Knowledge Base ingestion job, which detects and removes deleted documents from the vector store.<br>- **D)** Enable S3 Object Lock on the bucket to prevent files from being deleted, thereby avoiding stale vectors. | **Correct Answer:** **C**<br><br>**Correct Option Analysis:**<br>- **C is Correct:** A daily scheduled sync via EventBridge is the most cost-effective approach for frequent deletions. The Bedrock ingestion job natively detects deleted files in the S3 data source and removes their corresponding vectors from the OpenSearch index, satisfying the 24-hour compliance window without incurring costs for running a job on every single deletion.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** Triggering an ingestion job for every single deletion event via Lambda is not cost-effective, as ingestion jobs have associated compute and embedding API costs, and running them hundreds of times a day is wasteful.<br>- **B is Incorrect:** Writing custom Lambda code to query and delete vectors directly from OpenSearch Serverless introduces significant operational overhead and bypasses the managed sync capabilities of Bedrock.<br>- **D is Incorrect:** Enabling S3 Object Lock prevents deletion, which violates the business process of deleting case files and fails to meet the technical requirement of removing stale vectors.<br><br>> **Key Takeaway:** When dealing with frequent deletions that have a flexible compliance window (e.g., 24 hours), schedule a single daily Bedrock Knowledge Base sync to detect and remove stale vectors cost-effectively rather than triggering a sync per deletion. |

(Select ONE)<br><br>- **A)** Configure an S3 Event Notification on the `pending_updates/` prefix to invoke an AWS Lambda function that calls the `StartPipelineExecution` API.<br>- **B)** Use an Amazon EventBridge schedule to trigger the SageMaker Pipeline every 15 minutes, and add a condition step to check if the prefix is populated.<br>- **C)** Configure an S3 Event Notification to directly trigger the SageMaker Pipeline execution without an intermediary service.<br>- **D)** Use AWS Glue to monitor the S3 bucket and trigger the SageMaker Pipeline via an EventBridge rule. | **Correct Answer:** **A**<br><br>**Correct Option Analysis:**<br>- **A is Correct:** S3 Event Notifications can be configured for specific prefixes. | **### Question 9 - Robust Retry Mechanisms for RAG Ingestion Jobs**<br><br>A global retailer is using Amazon Bedrock Knowledge Bases with an Amazon OpenSearch Serverless vector store. The ingestion job runs hourly via an EventBridge schedule. Recently, the ingestion jobs have been failing intermittently due to transient OpenSearch Serverless capacity limits during peak hours.<br><br>The team needs to implement a robust orchestration pattern to monitor the job status and automatically retry the execution if it fails, adhering to **MLOps best practices** and **minimizing manual intervention**.<br><br>Which solution meets these requirements? (Select ONE)<br><br>- **A)** Configure the EventBridge schedule to retry the `StartIngestionJob` API call automatically by setting the maximum retry attempts in the EventBridge target settings.<br>- **B)** Create an AWS Step Functions state machine to orchestrate the ingestion job, using the Bedrock `StartIngestionJob` API, and configure a Retry policy with an exponential backoff interval on the polling step.<br>- **C)** Increase the OpenSearch Serverless capacity units manually before the scheduled run.<br>- **D)** Enable auto-tuning for the OpenSearch Serverless collection to prevent capacity issues. | **Correct Answer:** **B**<br><br>**Correct Option Analysis:**<br>- **B is Correct:** Using AWS Step Functions to orchestrate the asynchronous `StartIngestionJob` API is the MLOps best practice. Step Functions can start the job, poll its status, and if the status returns `FAILED`, a Retry policy with exponential backoff can automatically re-trigger the job, handling transient capacity issues gracefully.<br><br>**Distractor Analysis:**<br>- **A is Incorrect:** EventBridge retries only apply if the *API invocation itself* fails (e.g., throttling of the `StartIngestionJob` call). If the API call succeeds but the *job execution* fails later, EventBridge will not retry the job.<br>- **C is Incorrect:** Manually adjusting capacity units does not automate the process and violates the requirement to minimize manual intervention.<br>- **D is Incorrect:** While increasing capacity via auto-scaling might prevent the issue, OpenSearch Serverless auto-scaling takes time to react and does not provide a retry mechanism for jobs that have already failed, making it an incomplete solution for robust orchestration.<br><br>> **Key Takeaway:** For asynchronous ML jobs (like Bedrock ingestion) that may fail during execution, use AWS Step Functions to orchestrate the API call and poll for job status, utilizing Retry policies for robust error handling. |
