### Question 1 - Bedrock Knowledge Base Vector Store Configuration

A global FinTech enterprise is building a generative AI application for internal financial analysts using **Amazon Bedrock Knowledge Bases**. The application must answer questions by performing semantic search over unstructured financial reports while simultaneously filtering results based on company year-end reporting periods (metadata filters). These retrieval operations must occur with **minimal operational overhead** and the infrastructure must support **hybrid search** in the future without requiring re-architecting the system.

Which configuration should the ML engineer choose for the Bedrock Knowledge Base vector store? (Select ONE)

* **A)** Configure the Knowledge Base to store vector embeddings directly in Amazon S3 as `.npy` files, enabling serverless access and minimal operational overhead.
* **B)** Configure the Knowledge Base with an Amazon OpenSearch Serverless vector collection, defining the vector field, text field, and metadata fields in the mapping before ingestion.
* **C)** Configure the Knowledge Base with an Amazon Aurora PostgreSQL cluster, storing embeddings in a vector column to keep embeddings alongside existing financial records.
* **D)** Configure the Knowledge Base with Amazon Neptune to leverage graph-based relationships between financial entities during retrieval.
* **E)** Configure the Knowledge Base to store embeddings in Amazon DynamoDB using a composite key for fast, low-latency lookups.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** Amazon OpenSearch Serverless is a native vector store option for Amazon Bedrock Knowledge Bases that provides managed vector search with minimal operational overhead and supports hybrid search, along with metadata filtering via filterable fields in the index mapping.

    #### Distractor Analysis
    * **A is Incorrect:** Amazon Bedrock Knowledge Bases does not support Amazon S3 as a vector store. S3 is an object storage option for source documents only; it cannot perform vector similarity searches.
    * **C is Incorrect:** While Amazon Aurora PostgreSQL supports the pgvector extension, using a relational database cluster for vector storage introduces more operational complexity (provisioning, scaling, maintenance) compared to OpenSearch Serverless, and it does not natively support hybrid search in a single query without additional configuration.
    * **D is Incorrect:** Neptune is a graph database that excels at relationship traversal, not as a primary vector index for semantic search within Bedrock Knowledge Bases. Graph stores are not a supported Knowledge Base vector store option.
    * **E is Incorrect:** DynamoDB is not a vector store. It does not natively support vector similarity search (k-NN), and hybrid search with lexical matching is not a native DynamoDB capability.

    > **Key Takeaway:** When Bedrock Knowledge Bases requires metadata filtering and future hybrid search, choose Amazon OpenSearch Serverless or Managed Cluster as the vector store. The field mapping must be defined before ingestion because it cannot be changed later without full reindexing.

### Question 2 - Bedrock Knowledge Base Ingestion and Resync Strategy

    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** Amazon Bedrock Knowledge Bases ingestion jobs support incremental sync when invoked against an existing data source.     #### Distractor Analysis

### Question 3 - Retrieval Optimization with Hybrid Search and Reranking

A healthcare provider is building a patient support chatbot using **Amazon Bedrock Knowledge Bases** with **Amazon OpenSearch Serverless**. The chatbot frequently receives queries containing medical codes (e.g., "ICD-10 code E11.9") and must return both exact code documentation and semantically relevant patient education material. The procurement team wants the solution to deliver **highest retrieval accuracy** while maintaining **minimal operational overhead**.

Which retrieval configuration accomplishes this? (Select ONE)

* **A)** Use pure semantic search (k-NN) with a high result count (top_k of 25) and rely on Bedrock's default ranking.
* **B)** Use hybrid search enabled in Bedrock Knowledge Bases with both vector (k-NN) and lexical (BM25) components, and configure a reranking model in the retrieval pipeline.
* **C)** Use a custom Lambda function that applies TF-IDF to all documents after retrieval from OpenSearch to reorder results.
* **D)** Use node-level metadata filters (e.g., only "patient education" category) to avoid pulling medical code documentation from the index.
* **E)** Store medical codes in a separate DynamoDB table and query that table first, merging results with OpenSearch retrieval.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** Hybrid search combines dense vector similarity (semantic meaning) with sparse lexical search (BM25 for exact keyword matching like medical codes) and reranking improves result ordering. Amazon Bedrock Knowledge Bases supports hybrid search and integration with rerank models. This maximizes retrieval accuracy for mixed query types while minimizing custom code.

    #### Distractor Analysis
    * **A is Incorrect:** Pure semantic search with high top_k only increases the number of retrieved candidates. It does not ensure exact keyword/documentation matches for medical codes because dense embeddings can fail on precise alphanumeric identifiers.
    * **C is Incorrect:** Custom Lambda with TF-IDF requires building and maintaining a custom lexical search layer and reranking logic, which directly violates minimal operational overhead.

    * **E is Incorrect:** Adding a separate DynamoDB table and merging results introduces a second retrieval system and custom merging logic — significantly more operational complexity than using built-in hybrid search.

    > **Key Takeaway:** When exact keyword matching and semantic similarity are both needed, enable hybrid search on OpenSearch (or OpenSearch Serverless) within Bedrock Knowledge Bases. Add a rerank model in the retrieval pipeline to boost top-1 accuracy without additional custom infrastructure.

### Question 4 - Embedding Dimension Mismatch Resolution

An ML engineering team is building a chatbot on **Amazon Bedrock Knowledge Bases** for internal company documentation. The team initially used **Amazon Titan Text Embeddings v1** (dimension 1536) and created an OpenSearch Serverless vector collection with those dimensions. The team recently decided to switch to **Amazon Titan Text Embeddings v2** (dimension 1024) for better performance. The new embedding model outputs 1024-dimensional vectors at ingestion time. They immediately start an ingestion job. The job fails with a dimension mismatch error.

What must the team do to resolve this? (Select ONE)

* **A)** Update the existing OpenSearch Serverless collection mapping to accept the new vector dimension field using the `UpdateVectorIndex` API.
* **B)** Delete the existing OpenSearch collection and create a new collection with dimensions matching the new embedding model (1024), then update the Bedrock Knowledge Base embedding model and re-ingest documents.
* **C)** Configure a SageMaker Processing job to pad vectors to 1536 dimensions with zeros before writing to OpenSearch.
* **D)** Keep the original OpenSearch collection and reduce the new embedding model's dimension by applying PCA in a Lambda before writing to OpenSearch.
* **E)** Disable vector validation in the Bedrock Knowledge Base ingest configuration to bypass dimension checking.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** Vector dimension is immutable once an OpenSearch Serverless collection (or any vector index with k-NN plugin) is created. Changing the embedding model requires creating a new vector collection with the correct dimension (1024), updating the Bedrock Knowledge Base to point to the new collection and embedding model, and re-ingesting documents from scratch.

    #### Distractor Analysis
    * **A is Incorrect:** You cannot demote/alter the dimension of an existing k-NN vector field in OpenSearch. Vector properties such as dimension and engine/algorithm are fixed at index creation time and cannot be changed via an update or remapping API.
    * **C is Incorrect:** Padding or extending vectors with zeros to match the old dimension would corrupt the semantic meaning captured in the embedding space, and OpenSearch's k-NN plugin expects vectors that align with the original embedding model.
    * **D is Incorrect:** Running PCA or any post-hoc dimensionality reduction on embeddings through Lambda is not a valid Bedrock Knowledge Bases pattern. It adds significant operational complexity and alters vector semantics.
    * **E is Incorrect:** There is no feature to bypass embedding dimension validation. The vector collection's index will reject vector writes with mismatched dimensions.

    > **Key Takeaway:** Vector index dimensions are immutable. Whenever you change the embedding model in Bedrock Knowledge Bases, you must create a new vector collection with matching dimension size and re-ingest all documents. Plan embedding model versions carefully to avoid expensive reindexing.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **C** and **E**

    #### Correct Options Analysis
    * **C is Correct:** OpenSearch Serverless encryption policies must be defined before creating the collection. Referencing a customer KMS CMK ARN ensures the vector index at rest is encrypted with a KMS key controlled by the security team.

    > **Key Takeaway:** For Bedrock Knowledge Bases with OpenSearch Serverless, encryption policies (KMS CMK) and IAM/data access policies must be properly defined and scoped to specific resources before collection creation, and the execution role must follow least privilege (specific ARN scoping).
