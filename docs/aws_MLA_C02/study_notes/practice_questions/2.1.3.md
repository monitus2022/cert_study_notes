### Question 1 - Foundation Model Selection vs. Custom Training

A financial services company needs to build an automated system that classifies customer emails into 12 internal categories (e.g., "loan inquiry," "fraud report," "account closure"). The company has approximately 50,000 labeled historical emails in Amazon S3. The ML team must decide between fine-tuning a foundation model from Amazon Bedrock or training a custom model using Amazon SageMaker AI. The system must achieve **high classification accuracy**, support **explainable predictions** for compliance audits, and minimize **ongoing inference costs**.

Which approach BEST satisfies all three requirements? (Select ONE)

- **A)** Fine-tune an Amazon Bedrock foundation model on the 50,000 labeled emails using supervised fine-tuning.
- **B)** Train a custom XGBoost classifier in Amazon SageMaker AI using TF-IDF text features, configured with SageMaker Clarify for feature attribution.
- **C)** Use Amazon Bedrock with zero-shot prompting and few-shot examples in the prompt (no fine-tuning).
- **D)** Use Amazon Comprehend's custom classification API to train a model on the labeled emails.
- **E)** Train a multi-layer transformer from scratch using SageMaker distributed training on a large GPU cluster.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **D**

    #### Correct Options Analysis
    * **D is Correct:** Amazon Comprehend custom classification is a managed AI service specifically designed for text categorization. It trains a custom classifier on labeled data, provides confidence scores, and requires no infrastructure management—offering the best balance of accuracy (trained on proprietary labels), explainability (confidence scores and word-level contributions), and low operational/inference cost (pay-per-use with no GPU hosting).

    #### Distractor Analysis
    * **A is Incorrect:** Fine-tuning a foundation model on 50,000 labeled emails would achieve high accuracy but incurs significantly higher inference costs than Amazon Comprehend custom classification. Bedrock fine-tuned model inference is priced per token and requires provisioned throughput for consistent latency—making it far more expensive for high-volume text classification.
    * **B is Incorrect:** Training a custom XGBoost model is viable but introduces unnecessary operational overhead compared to Amazon Comprehend. The team would need to manage data preprocessing, feature engineering, hyperparameter tuning, model hosting, and endpoint scaling—work that Comprehend fully manages. SageMaker Clarify adds value for explainability, but Comprehend's built-in explanations suffice for this use case.
    * **C is Incorrect:** Zero-shot or few-shot prompting without fine-tuning generally underperforms a model trained on 50,000 labeled examples for a 12-class specialized classification task. Additionally, per-token foundation model inference costs would be substantially higher than Amazon Comprehend's classification API.
    * **E is Incorrect:** Training a transformer from scratch requires enormous amounts of data (millions of examples), GPU clusters, and months of research/engineering time. This is completely disproportionate to the task and violates the cost constraint.

    > **Key Takeaway:** When an AWS managed AI service already solves the task (text classification, entity extraction, OCR), it typically beats both custom ML models and foundation models on combined accuracy, explainability, and cost.

### Question 2 - Prompt Engineering vs. Fine-Tuning

A healthcare startup is building an application that generates patient-facing summaries of clinical notes using **Amazon Bedrock** with a Llama 3 model. The summaries must use plain language and avoid medical jargon. Initial testing shows that the model produces overly clinical summaries despite a clear instruction in the prompt. The team has a dataset of 2,000 expert-written plain-language summaries paired with clinical notes.

What is the MOST cost-effective first step to close this quality gap? (Select ONE)

- **A)** Immediately initiate supervised fine-tuning on the 2,000 paired examples using Amazon Bedrock.
- **B)** Add 3–5 few-shot examples of clinical notes paired with plain-language summaries directly into the prompt and re-evaluate.
- **C)** Switch to a larger, more expensive foundation model available in Amazon Bedrock.
- **D)** Train a custom seq2seq model from scratch on the 2,000 examples.
- **E)** Use Amazon Comprehend Medical to rewrite the summaries before presenting them to patients.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** The standard adaptation hierarchy is **prompt engineering first, fine-tuning second**. Adding few-shot examples (in-context learning) directly into the prompt immediately changes model behavior with zero training overhead, zero infrastructure cost, and no model versioning. With 2,000 high-quality examples available, selecting 3–5 representative ones for in-context learning is the most cost-effective first step.

    #### Distractor Analysis
    * **A is Incorrect:** Supervised fine-tuning incurs significant overhead: data formatting (JSONL), training compute costs, model versioning, and evaluation. Per the AWS best practice hierarchy, fine-tuning should only be attempted after prompt engineering (including few-shot examples) has demonstrably failed to close the quality gap.
    * **C is Incorrect:** Switching to a larger model increases per-inference costs and may not address the stylistic gap. Larger models don't automatically produce plainer language; explicit examples and instructions in the prompt are more effective and cheaper.
    * **D is Incorrect:** Training a sequence-to-sequence model from scratch on only 2,000 examples is unrealistic—custom generative models typically require millions of examples and massive GPU resources. This option also creates unnecessary operational overhead.
    * **E is Incorrect:** Amazon Comprehend Medical extracts medical entities (conditions, medications, dosages) from text; it does not rewrite or simplify text for patient-facing audiences. This is a misapplication of the service.

    > **Key Takeaway:** Follow the "Prompt First, Fine-Tune Second" order: task-specific instructions + few-shot examples usually close stylistic/formatting gaps instantly at zero training cost.

### Question 3 - RAG vs. Fine-Tuning for Knowledge Freshness

A legal technology company is building an assistant that answers questions about a client's corporate policies. The policy documents change **multiple times per week**, and the assistant must **always cite the specific document and section** behind each answer. The legal team cannot accept answers that cite outdated policies. The application uses Amazon Bedrock Knowledge Bases.

Which architecture BEST satisfies the citation and freshness requirements? (Select ONE)

- **A)** Fine-tune a foundation model on the latest policy documents so the model internalizes the most recent knowledge.
- **B)** Use Amazon Bedrock Knowledge Bases to retrieve relevant policy passages at request time and include source metadata in the prompt for citation.
- **C)** Use Amazon Transcribe to convert all policy documents to audio and store them in S3 for fast retrieval.
- **D)** Encode all policy documents into a single large prompt and submit it with every question using the model's full context window.
- **E)** Train a custom document classification model to route questions to the appropriate policy document before querying a database.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** Retrieval-Augmented Generation (RAG) via Amazon Bedrock Knowledge Bases fetches fresh, relevant passages from a vector index at query time. Because documents are synced to the vector store as they change, answers reflect the newest policy versions. Each retrieved chunk carries source metadata (document title, section, page number), enabling the model to cite evidence in every response.

    #### Distractor Analysis
    * **A is Incorrect:** Fine-tuning embeds knowledge into model weights. When policies change multiple times per week, the team would need continuous retraining—hours or days each time—to keep the model current. Fine-tuned models also cannot reliably cite the exact source document behind a specific answer, violating the citation requirement.
    * **C is Incorrect:** Amazon Transcribe converts speech to text (or creates text from audio); it is completely unrelated to document retrieval or citation generation. Converting documents to audio and storing them in S3 provides no retrieval or Q&A capability.
    * **D is Incorrect:** Stuffing all policy documents into the prompt on every request is expensive (token costs escalate linearly with document size), may exceed the model's context window as documents grow, and does not inherently provide clean citation prompts. It is a non-scaling workaround, not an appropriate architecture.
    * **E is Incorrect:** Training a custom routing classifier adds unnecessary complexity. Amazon Bedrock Knowledge Bases already manages semantic retrieval across documents without a custom routing model, which would require separate training, hosting, and maintenance.

    > **Key Takeaway:** RAG is the correct pattern when content changes frequently and citations are required; fine-tuning is better when behavior (style/terminology) is the gap, not knowledge.

- **A)** Train an XGBoost model in Amazon SageMaker AI and use SageMaker Clarify to generate SHAP values for each prediction.
- **B)** Use Amazon Bedrock with a large language model and include the applicant's details in the prompt.
- **C)** Train a deep neural network with 10 hidden layers in SageMaker AI for maximum predictive accuracy.
- **D)** Deploy a trained XGBoost model to a SageMaker real-time endpoint with auto-scaling configured.
- **E)** Use Amazon Rekognition to analyze applicant ID photos for fraud detection signals.

??? note "Click to reveal Answer & Explanation"
    **Correct Answers:** **A** and **D**

    #### Correct Options Analysis
    * **A is Correct:** XGBoost is a tree-based gradient boosting algorithm that provides excellent predictive performance on tabular data while remaining interpretable through feature importance scores and SHAP values. SageMaker Clarify provides ready-to-use SHAP explanations, satisfying the regulatory compliance requirement.
    * **D is Correct:** Deploying the trained XGBoost model to a SageMaker real-time endpoint with auto-scaling ensures sub-50 ms inference latency for individual predictions while minimizing operational overhead through managed infrastructure.

    #### Distractor Analysis
    * **B is Incorrect:** Foundation models are not designed for binary classification on tabular loan data with 200 numerical features. ### Question 7 - Fine-Tuning Strategy Selection

An e-commerce company wants to adapt a foundation model in Amazon Bedrock to generate product descriptions in a **specific brand voice** (playful, informal, emoji-friendly). The team has **500 high-quality example descriptions** showing the exact writing style. The current model with prompt instructions produces descriptions that are "too formal and corporate."

Which fine-tuning strategy is MOST appropriate for this scenario? (Select ONE)

- **A)** Reinforcement fine-tuning (RFT) with a reward function that scores brand-voice adherence.
- **B)** Supervised fine-tuning (SFT) on the 500 labeled input-output pairs that demonstrate the target voice.
- **C)** Model distillation from a larger model to a smaller one using the 500 examples as prompts.
- **D)** Domain-adaptation fine-tuning (continued pre-training) on the company's entire product catalog.
- **E)** No fine-tuning—simply increase the model's temperature setting to make outputs more creative.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** Supervised fine-tuning (SFT) is the correct strategy when the gap is stylistic/formatting and you have a labeled dataset of prompt-response pairs that demonstrate the target behavior. The 500 high-quality example descriptions serve as the ground truth for updating model weights to produce consistently playful, informal, emoji-friendly text. SFT is available in Amazon Bedrock for supported foundation models.

    #### Distractor Analysis
    * **A is Incorrect:** Reinforcement fine-tuning (RFT) is best when the desired behavior can be scored but not easily demonstrated with labeled examples (e.g., "summaries should balance brevity with informativeness"). With 500 high-quality examples showing exactly what the output should look like, SFT is simpler, more direct, and more cost-effective than designing reward functions and running RLHF pipelines.
    * **C is Incorrect:** Model distillation compresses a larger teacher model into a smaller student to reduce latency/cost while preserving capability. It does not inherently teach a specific brand voice; distillation uses prompts to transfer general behavior, not to fine-tune a specific style on 500 labeled examples.
    * **D is Incorrect:** Domain-adaptation fine-tuning (continued pre-training) is used to inject broad domain knowledge (e.g., legal terminology, medical vocabulary) into a model before task-specific fine-tuning. It is not the right tool for adjusting writing style, and it requires substantially more data than 500 examples.
    * **E is Incorrect:** Increasing temperature makes outputs more random/diverse, not more aligned with a specific brand voice. High temperature often produces inconsistent or off-topic outputs rather than consistently playful descriptions. Temperature tuning is a prompt-level adjustment that has already been tried without success.

    > **Key Takeaway:** Supervised fine-tuning (SFT) is the correct path when you have high-quality labeled examples of the target behavior; reinforcement fine-tuning (RFT) is for cases where you can score outputs but not easily label them.

- **C)** Use Amazon Bedrock to fit a foundation model on the tabular delivery data in the prompt.
- **D)** Build a K-means clustering model to segment shipments into delay/no-delay groups.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** SageMaker built-in XGBoost is purpose-built for tabular classification problems with millions of rows and hundreds of features. It trains quickly (hours, not days), achieves state-of-the-art accuracy on tabular data, and requires minimal ML expertise to use. The SageMaker HyperparameterTuner automates hyperparameter search, further reducing the expertise barrier. This fits the 2-week deployment timeline and budget constraints perfectly.

Training custom LSTM models requires significant ML expertise, hyperparameter tuning, and typically delivers no accuracy improvement over gradient boosted trees on tabular problems.

    > **Key Takeaway:** For tabular data with structured features, gradient-boosted trees (XGBoost) almost always outperform deep learning while training faster and at a fraction of the cost.

### Question 9 - RAG Architecture Selection

A pharmaceutical company wants to build a **research assistant** that answers scientists' questions using a corpus of **50,000 internal research papers**. The answers must be **grounded in citations**, support **complex multi-hop reasoning** (e.g., "Which compounds studied in Paper A were also tested in Paper B?"), and handle documents up to **200 pages long**. The system must use Amazon Bedrock Knowledge Bases.

Which RAG architecture pattern BEST aligns with these requirements? (Select ONE)

- **A)** Basic semantic search RAG with standard chunking (fixed 500-token chunks).
- **B)** Parent-document retrieval with metadata filtering enabled in the Knowledge Base.
- **C)** Hierarchical chunking (document-level summary + section-level chunks) in the Knowledge Base, with a reranking step.
- **D)** A custom solution that retrieves all 50,000 paper embeddings simultaneously on every query.
- **E)** A purely generative approach—no retrieval—where the model answers from its training data.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **C**

    #### Correct Options Analysis
    * **C is Correct:** Hierarchical chunking stores both document-level summaries and section-level chunks in the vector index, enabling initial retrieval at the document level followed by targeted section retrieval. Adding a reranking step (available in Bedrock Knowledge Bases) improves precision for multi-hop reasoning by re-scoring retrieved passages using a more powerful cross-encoder model. This supports 200-page documents—which would overflow simple chunking pipelines—by first navigating to the right document, then to the right section.

    #### Distractor Analysis
    * **A is Incorrect:** Fixed 500-token chunking fragments 200-page documents into hundreds of context-isolated pieces. This approach cannot support multi-hop reasoning across documents (connecting compounds in Paper A to tests in Paper B) and often retrieves irrelevant chunks when documents are large. Reranking and document-level context are missing.
    * **B is Incorrect:** Parent-document retrieval helps by retrieving parent context around matching chunks, but for 200-page documents, the "parent" scope is still unclear. Metadata filtering supports retrieval by paper title, author, or year—not by relationships between compounds across papers. This doesn't fully address multi-hop reasoning.
    * **D is Incorrect:** Retrieving all 50,000 embeddings simultaneously on every query is computationally infeasible and would exceed context window limits. RAG relies on top-k nearest neighbor search; this option essentially abandons the retrieval mechanism.
    * **E is Incorrect:** A purely generative approach without retrieval cannot cite specific internal research papers. The model's training data doesn't include proprietary internal research, and it hallucinates heavily when asked about specific company documents. This option also violates the citation requirement.

    > **Key Takeaway:** Multi-hop reasoning across large corpora requires hierarchical retrieval (document-level navigation before section-level retrieval) and ideally a reranking step for precision.

### Question 10 - GenAI Model Performance/Cost Tradeoff

A startup is building a **customer support chatbot** using Amazon Bedrock. The chatbot handles two distinct tasks:

- **Task 1:** Classifying incoming messages into 8 intent categories (e.g., "billing," "technical support," "return request").
- **Task 2:** Generating empathetic, context-aware responses to customer messages.

The startup has **limited engineering resources** and must **minimize total monthly costs** while maintaining acceptable quality for both tasks.

Which architecture BEST optimizes cost and quality? (Select ONE)

- **A)** Use a single large foundation model for both tasks (the same Bedrock model classifies intent and generates responses).
- **B)** Use Amazon Comprehend's custom classification API for Task 1 and a foundation model in Amazon Bedrock for Task 2.
- **C)** Use a foundation model in Amazon Bedrock for Task 1 and Amazon Comprehend for Task 2.
- **D)** Train a custom intent classification model in SageMaker for Task 1 and a custom response generation model in SageMaker for Task 2.
- **E)** Use Amazon Rekognition to analyze message images and classify intent, then Bedrock for response generation.

??? note "Click to reveal Answer & Explanation"
    **Correct Answer:** **B**

    #### Correct Options Analysis
    * **B is Correct:** This architecture splits the workload appropriately: (1) Amazon Comprehend custom classification handles the intent routing task at a fraction of foundation model costs (pay-per-request pricing for text classification vs. per-token pricing for generative inference). (2) Amazon Bedrock handles response generation, which inherently requires generative capability that Comprehend cannot provide. This optimizes cost by using a specialized, cheaper service for the classification task and a foundation model only for the generative task.

    #### Distractor Analysis
    * **A is Incorrect:** Using a single large foundation model for both tasks means every intent classification call consumes expensive generative tokens. Classification is a simple structured-output task that Amazon Comprehend handles at a much lower cost. This approach violates the cost minimization requirement.
    * **C is Incorrect:** Amazon Comprehend cannot generate empathetic, context-aware responses—it performs NLP analysis like entity detection, sentiment analysis, and custom classification. Reversing the task assignment is a misapplication of services.
    * **D is Incorrect:** Training custom models for both tasks maximizes engineering effort and ongoing maintenance. A custom response generation model from scratch is realistically infeasible for a startup with limited resources (requires millions of examples, GPU training infrastructure, and months of development time).
    * **E is Incorrect:** Amazon Rekognition analyzes images and videos, not text messages. It cannot classify customer message intents. This is a misapplication of the service.

    > **Key Takeaway:** Split mixed traffic between managed AI services (cheap, task-specific) and foundation models (expensive, generative) to minimize total cost—use each service for what it is designed to do.
