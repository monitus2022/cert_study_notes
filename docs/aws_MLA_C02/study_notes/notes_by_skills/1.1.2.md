# Task 1.1: Data Preparation for ML and AI - Collect and store data

## Skill 1.1.2: Make storage decisions and configure storage services based on cost, performance, data structure, and data compliance

### Purpose

Selecting and configuring the correct AWS storage service for a machine learning or AI workload is a design decision, not an operational default. The right choice depends on four forces that often pull against each other:

- **Cost**
- **Performance**
- **Data structure**
- **Data compliance**

A storage service that is ideal for one ML workload may be expensive, slow, or non-compliant for another.

---

### Storage Decision Framework

Use the following sequence when choosing a storage service for ML data.

1. **Classify the data structure**
   - Unstructured objects: images, video, audio, PDFs, raw text files, model artifacts
   - Semi-structured data: JSON, CSV, Parquet, ORC, log files
   - Structured relational data: tables with SQL joins, transactions
   - Key-value or document data: fast lookups by ID
   - Embeddings: vector data for similarity search

2. **Define the access pattern**
   - Batch training data read repeatedly
   - High-throughput streaming data
   - Low-latency single-item lookups for inference
   - Shared file access across many distributed training instances
   - Similarity search for retrieval-augmented generation / semantic search

3. **Determine performance requirements**
   - Latency target: milliseconds vs seconds
   - Throughput: IOPS, MB/s, requests per second
   - Concurrency: how many readers/writers at once
   - Read vs write ratio

4. **Estimate cost and scalability**
   - Storage volume
   - Data access frequency
   - Request rates
   - Data retention period

5. **Apply compliance and security constraints**
   - Regulatory requirements: HIPAA, GDPR, PCI, MLPS, FINRA
   - Data residency and sovereignty
   - Encryption at rest and in transit
   - Long-term retention and immutability
   - Access auditing

### AWS Storage Services at a Glance

| AWS Service | Data Structure | Access Pattern | Typical ML Use Case | Cost/Performance Notes |
| --- | --- | --- | --- | --- |
| **Amazon S3** | Objects, files, images, audio, video, Parquet, CSV, JSON | Batch, high-latency compared with databases, highly scalable reads | Default data lake, training datasets, model artifacts, raw data ingestion | Very low cost per GB, 11 nines durability; storage classes reduce cost at expense of retrieval latency |
| **Amazon EBS** | Block storage volumes | Low-latency local disk for a single instance | Scratch space, local dataset cache, OS volume | High performance per volume; not shared; data is lost on instance termination by default |
| **Amazon EFS** | POSIX shared file system | Multi-instance concurrent reads/writes | Shared training dataset mounted on many SageMaker/EC2 instances | Pay for usage; higher cost than S3; lower latency than S3 |
| **Amazon FSx for Lustre** | High-performance shared file system | Sub-millisecond shared access | High-performance distributed training, HPC-style data access, large files | Higher cost; built for extreme throughput; integrates with S3 |
| **Amazon RDS** | Relational tables | SQL queries, joins, transactions | Structured metadata, labels, experiment tracking | Managed relational; predictable cost; limited vertical/horizontal scaling vs NoSQL |
| **Amazon DynamoDB** | Key-value and document | Single-digit millisecond lookups by key | Low-latency feature lookups, metadata store, real-time inference serving | Provisioned or on-demand; scales horizontally; expensive for large analytic scans |
| **Amazon OpenSearch Service** | Documents and vectors | Search, k-nearest neighbor, similarity search | Semantic search, RAG retrieval, embedding search | Good for search and vector workloads; cluster sizing matters for cost and performance |
| **Amazon SageMaker Feature Store** | Feature datasets | Online low-latency lookup + offline historical batch reads | Centralized feature storage for training and inference consistency | Online store for real-time; offline store in S3 for training |
| **Amazon Kinesis Data Streams / Amazon MSK** | Streaming records | Continuous ingestion | Real-time data buffering, streaming training, event ingestion | Pay per shard/broker-hour; designed for streaming, not long-term storage |

### Choosing Storage by Data Structure

#### Unstructured data: Images, audio, video, text, documents

**Recommended default:** Amazon S3

- S3 is the standard landing zone for ML datasets.
- SageMaker training jobs natively read from S3.
- S3 supports large objects, versioning, lifecycle policies, and cross-region replication.
- Use S3 for image datasets, audio files, videos, PDFs, and raw logs.

Example configuration:

- Store all training images under `s3://my-dataset/images/train/`
- Enable versioning to protect against accidental deletion
- Add a lifecycle rule to move older raw data to S3 Glacier for cost savings
- Encrypt using SSE-KMS

#### Semi-structured data: JSON, CSV, Parquet, ORC, logs

**Recommended default:** Amazon S3, usually in a data lake layout

- Row formats such as CSV and JSON are good for ingestion, interchange, and record-at-a-time writes.
- Columnar formats such as Apache Parquet and ORC are optimized for analytics queries that select a few columns across many rows.
- Use AWS Glue Data Catalog to catalog schemas and make the data queryable by Athena, Glue, EMR, or SageMaker.

#### Structured relational data

**Recommended default:** Amazon RDS

- Use RDS when data requires SQL joins, transactions, foreign keys, or strong consistency.
- Choose Amazon Aurora when you need higher performance and automatic storage scaling.
- Choose Amazon RDS for PostgreSQL with `pgvector` when you need relational data and vector similarity search in one place.

#### Key-value or low-latency lookup data

**Recommended default:** Amazon DynamoDB

- Use DynamoDB for features that are looked up by a known ID at inference time.
- Supports single-digit millisecond latency at any scale.
- Use on-demand mode for unpredictable workloads; use provisioned capacity with auto scaling for predictable workloads and cost optimization.

#### Vector embeddings for similarity search

**Options:**

- **Amazon OpenSearch Service:** Best for large-scale vector search, k-NN, and RAG applications.
- **Amazon RDS for PostgreSQL with `pgvector`:** Best when embeddings are already stored next to relational data and you do not want to move them.
- **Amazon S3:** Cheap storage for large volumes of embeddings, but not a native vector search engine. Use S3 to store embeddings in bulk and load them into OpenSearch or another index for serving.

#### Shared file access for distributed training

**Recommended options:**

- **Amazon EFS:** Shared POSIX file system for many instances across availability zones.
- **Amazon FSx for Lustre:** Higher performance shared file system optimized for ML training and HPC workloads requiring extreme throughput and sub-millisecond latency.

Use EFS when many training instances need to read or write to the same file namespace with moderate performance.

Use FSx for Lustre when distributed training requires high sustained throughput on very large datasets and low-latency reads. FSx can sync directly from S3.

### S3 Storage Classes and Cost Optimization

S3 is the most common ML data store, but not all S3 data should be stored in S3 Standard.

| S3 Storage Class | Use Case | Retrieval | Cost Profile |
| --- | --- | --- | --- |
| **S3 Standard** | Frequently accessed training data | Immediate | Highest storage cost, no retrieval fee |
| **S3 Intelligent-Tiering** | Unknown or changing access patterns | Immediate | Small monitoring fee; moves objects between tiers automatically |
| **S3 Standard-IA** | Infrequently accessed data | Immediate | Lower storage cost, retrieval fee |
| **S3 One Zone-IA** | Recreatable or non-critical data | Immediate | Lower cost, single-AZ durability |
| **S3 Glacier Instant Retrieval** | Rarely accessed, low-latency retrieval | Milliseconds | Very low storage cost |
| **S3 Glacier Flexible Retrieval** | Archive data | Minutes to hours | Lower cost, slower retrieval |
| **S3 Glacier Deep Archive** | Long-term compliance archive | Hours | Lowest storage cost |

Use S3 Lifecycle policies to move older raw data to colder storage automatically.

Example:
- Initial 30 days: S3 Standard
- After 30 days: S3 Standard-IA
- After 90 days: S3 Glacier Instant Retrieval
- Delete incomplete multipart uploads after 7 days

Compliance may require:
- Immutability: S3 Object Lock with WORM mode
- Long retention: S3 Glacier or Deep Archive with retention policies
- Data residency: Buckets created in a specific Region

### File Formats and Access Patterns

The file format for ML data should match how the data will be read.

| Format | Orientation | Best For | Characteristics |
| --- | --- | --- | --- |
| **CSV** | Row | Simple ingestion, exchange, small datasets | Human-readable, no schema enforcement, slow for analytical scans |
| **JSON** | Row/document | APIs, event data, nested structures | Flexible schema, larger file size, slow to scan all fields |
| **Apache Parquet** | Columnar | Analytical queries, training reads of few columns across many rows | Compressed, schema embedded, supports predicate pushdown and column pruning |
| **ORC** | Columnar | Hive/Spark analytics | Similar to Parquet, optimized for Hive |
| **Apache Avro** | Row | Streaming writes, schema evolution | Binary, compact, good for event serialization |

**Rule of thumb:**

- Raw ingest: CSV or JSON is acceptable.
- Curated dataset used repeatedly for training or analytics: Use Parquet or ORC.
- Streaming events: Avro or JSON are common.
- For ML training, Parquet often reduces the amount of data scanned and improves job performance.

Example:
A dataset is queried repeatedly by Athena, and each query reads only 5 of 200 columns across millions of rows. Store the curated output as Parquet, not CSV. This allows column pruning and reduces cost.

### Databases for ML Workloads

#### Amazon RDS

Use when:
- You need SQL joins, transactions, or strong relational integrity.
- The dataset is structured and relatively moderate in size.
- You want a managed relational database with backups and patching.

For PostgreSQL, enable the `pgvector` extension to store embeddings and run similarity search.

Example:
A metadata table of documents uses `doc_id`, `title`, `date`, `embedding`. With `pgvector`, you can query by cosine similarity without moving data to a separate vector database.

#### Amazon DynamoDB

Use when:
- You need single-digit millisecond reads by primary key.
- Workloads are highly dynamic or need web-scale throughput.
- The data model is key-value or document.

DynamoDB is ideal for real-time inference feature lookups. For example:
- Customer ID -> last 5 transaction amounts
- Product ID -> current price and category
- Model ID -> model version and status

DynamoDB is not ideal for large analytical scans across many items because of cost and read capacity.

#### Amazon OpenSearch Service

Use when:
- You need full-text search, analytics, log analysis, or vector similarity search.
- You want k-NN search over embeddings.
- Your AI application needs to find documents closest in meaning to a query.

OpenSearch Service can be used as a scalable vector database for RAG and semantic search.

### Vector Store vs Feature Store

These two purpose-built stores are often confused.

| Store | Question It Answers | Example |
| --- | --- | --- |
| **Vector store** | Given an embedding, what is most similar? | Find the nearest documents to a user question in a support knowledge base |
| **Feature store** | Given an entity, what are its current and historical feature values? | Return customer features used for inference, consistent with training |

#### Amazon SageMaker Feature Store

- **Online store:** Low-latency retrieval of latest feature values for real-time inference.
- **Offline store:** Historical feature data for model training and batch scoring.
- **Feature groups:** Logical definitions of features shared by training and inference.

Use SageMaker Feature Store to prevent training-serving skew.  
If training and inference use separate feature pipelines, a model may perform well in testing but fail in production due to inconsistent feature definitions.

### Performance and Scalability Considerations

| Service | Scaling Signal | Possible Fix |
| --- | --- | --- |
| **S3** | High request rate on same key prefix | Distribute keys, use suffixes/prefixes, use S3 access points |
| **EBS** | Volume throughput/IOPS latency | Use gp3/io2, increase provisioned IOPS, choose Nitro instances |
| **EFS** | Throughput declines after burst credits consumed | Use provisioned throughput or Elastic Throughput |
| **FSx for Lustre** | Slow reading of large dataset from S3 | Confirm sync job or choose higher storage throughput |
| **RDS** | High CPU or I/O, read contention | Add read replicas, increase instance class, use Aurora |
| **DynamoDB** | Throttling with provisioned capacity | Use on-demand or increase capacity units, use DynamoDB Accelerator |
| **OpenSearch** | Query latency increases, high CPU/JVM pressure | Scale data nodes, choose appropriate instance types, tune shard count |

For ML training:
- Store large training datasets in S3 and use SageMaker data loading for most jobs.
- Use EFS or FSx for Lustre when many instances need shared low-latency access.
- Avoid EBS for shared data because an EBS volume is generally attached to one instance at a time.

### Compliance and Security Configuration

Compliance often constrains storage configuration more than model code.

Key AWS compliance features:

| Requirement | AWS Feature |
| --- | --- |
| Encryption at rest | S3 SSE-S3, S3 SSE-KMS, EBS encryption, EFS encryption, RDS encryption, DynamoDB encryption |
| Encryption in transit | TLS, VPC endpoints, S3 bucket policies requiring HTTPS |
| Data residency | Choose the correct Region; do not replicate to non-approved Regions |
| Data immutability | S3 Object Lock in compliance mode or governance mode |
| Retention | Lifecycle policies, S3 Glacier Vault Lock |
| Auditing | AWS CloudTrail, S3 server access logs, RDS/DynamoDB audit streams |
| Access control | IAM roles, S3 bucket policies, VPC endpoints, resource-based policies |

Example:
For a regulated customer dataset, configure:
- S3 bucket in the required Region
- Server-side encryption with AWS KMS customer managed key
- Object Lock with retention or legal hold
- Bucket policy blocking public access and requiring HTTPS
- CloudTrail logging for all management events
- VPC endpoint for private access from SageMaker

### Scenario-Based Selection Examples

#### Scenario 1: Raw image dataset for model training

- **Data:** 10 TB of images and labels
- **Access:** Batch training jobs run weekly
- **Cost concern:** High storage volume, moderate retrieval frequency
- **Compliance:** Require encryption at rest

**Choice:** Amazon S3 Standard initially, lifecycle to S3 Standard-IA after 30 days. Use SSE-KMS and a VPC endpoint. Load batches directly into SageMaker training jobs from S3.

#### Scenario 2: Shared dataset for distributed training

- **Data:** 500 GB of sharded training data
- **Access:** Hundreds of SageMaker distributed training instances read simultaneously
- **Performance:** Need high throughput and low-latency reads

**Choice:** Amazon FSx for Lustre with automatic sync from S3. If less demanding, Amazon EFS mounted on all instances.

#### Scenario 3: Low-latency feature lookups for real-time inference

- **Data:** Millions of customer IDs mapped to current feature values
- **Access:** Single-item lookups at inference, under 10 ms latency
- **Structure:** Key-value

**Choice:** Amazon DynamoDB on-demand or provisioned with auto scaling. Alternatively, use SageMaker Feature Store online store if features must be shared across training and inference.

#### Scenario 4: Semantic search over documents

- **Data:** 5 million document embeddings
- **Access:** k-nearest neighbor search for user queries
- **Requirement:** Return most similar documents

**Choice:** Amazon OpenSearch Service as a vector store. If embeddings already live in PostgreSQL with relational metadata, use Amazon RDS for PostgreSQL with `pgvector`.

#### Scenario 5: Curated analytics dataset

- **Data:** 2 TB of clean tabular data
- **Access:** Repeated queries from Athena or SageMaker
- **Query pattern:** Reads few columns across many rows

**Choice:** Store in Amazon S3 as Apache Parquet. Use AWS Glue Data Catalog. Partition by date or other high-cardinality keys. Apply lifecycle policies for older partitions.

#### Scenario 6: Streaming log events for real-time training

- **Data:** Continuous clickstream events
- **Access:** Real-time consumer processes events as they arrive

**Choice:** Amazon Kinesis Data Streams for ingestion, with a consumer writing to S3 or DynamoDB as needed. Do not use Kinesis as a long-term store; use S3 as the durable layer.

### Exam Tips

- **S3 is the default answer for most ML training datasets, raw data, and model artifacts**, unless the question mentions shared file access, low-latency lookups, relational structure, or vector search.
- **Amazon EBS is attached to one instance.** Do not choose EBS when multiple training instances need shared storage.
- **Amazon EFS is the shared file system answer.** Use it when a distributed training job needs a common file namespace.
- **Amazon FSx for Lustre is the high-performance shared file option.** Choose it when S3 alone is not fast enough and EFS may not meet throughput requirements for large-scale distributed training.
- **Amazon DynamoDB is for fast key-value lookups.** Choose it over S3 for real-time inference features.
- **Columnar formats like Parquet and ORC suit analytical reads.** Row formats like CSV and JSON suit ingestion, interchange, and record-at-a-time writes.
- **Cost, performance, data structure, and compliance must be considered together.** The exam often tests whether you can identify which force should dominate in the scenario.
- **Compliance can override performance and cost.** If a question requires data residency or immutability, choose the option that satisfies compliance even if it costs more.
- **Vector store vs feature store:** A vector store answers “what is similar?”; a feature store answers “what are the current/historical feature values for this entity?”
- **SageMaker Feature Store prevents training-serving skew** by providing one feature definition for both training and inference.
- **S3 Lifecycle policies reduce storage cost** by moving old or infrequently accessed data to lower-cost storage classes.
- **SSE-KMS is often the compliance answer** when encryption with controlled access is required.

### Common Exam Traps

- **Choosing Amazon EBS for shared storage.** EBS is primarily for a single instance. For multi-instance shared data, use EFS or FSx.
- **Choosing Amazon S3 for low-latency item lookups.** S3 is object storage with higher request latency than DynamoDB. Use DynamoDB for millisecond key-value lookups.
- **Choosing CSV or JSON for repeated analytics.** Queries that read few columns across many rows should use columnar formats like Parquet or ORC.
- **Ignoring compliance constraints.** A solution may be cheap and fast but fail because it stores data in the wrong Region or lacks encryption.
- **Adding consumer capacity when the downstream target is throttled.** In streaming pipelines, scaling consumers does not help if the write destination is the bottleneck.
- **Confusing vector search with feature storage.** OpenSearch is for similarity search; SageMaker Feature Store is for training/inference feature consistency.
- **Choosing RDS for huge unstructured objects.** Relational databases are not a good fit for large images, videos, or audio; use S3.
- **Assuming S3 Standard is always required.** Many ML raw datasets become infrequently accessed. Use S3 lifecycle policies to reduce cost.
- **Overlooking S3 object security.** Bucket policies, block public access, encryption, and IAM permissions are part of storage configuration.
- **Selecting a service based on one force alone.** The correct exam answer balances cost, performance, data structure, and compliance.

### Skill Summary

For the AWS Certified Machine Learning – Associate exam, you must be able to:

- Select Amazon S3, EBS, EFS, FSx, RDS, DynamoDB, OpenSearch, or SageMaker Feature Store based on data structure, access pattern, performance, cost, and compliance.
- Configure S3 lifecycle policies, encryption, versioning, and Object Lock.
- Choose the correct file format for analytics vs ingestion.
- Identify when to use shared file storage for distributed training.
- Recognize the role of vector stores for similarity search and feature stores for training/inference consistency.
- Apply compliance constraints such as encryption, residency, retention, and immutability to storage decisions.
