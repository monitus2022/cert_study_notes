# Task 1.1: Data Preparation for ML and AI - Collect and store data
## Skill 1.1.1: Extract data from data sources (for example, Amazon S3, Amazon EBS, Amazon EFS, Amazon RDS, Amazon DynamoDB, Amazon OpenSearch Service)

## Overview

Extracting data from data sources is the first step in an ML data pipeline. Before you can clean, validate, transform, or train, you must be able to read data from the system where it currently resides and bring it into a location or processing framework that an ML workload can use efficiently.

For the AWS Certified Machine Learning - Associate exam, this skill focuses on understanding:

- What each AWS data source is designed to do
- How data is accessed from each source
- Which service or method to use in a given scenario
- The performance, cost, and operational trade-offs of different extraction methods

The main data sources covered are:

- Amazon S3
- Amazon EBS
- Amazon EFS
- Amazon RDS
- Amazon DynamoDB
- Amazon OpenSearch Service

These services are not interchangeable. Each has a different data model, access pattern, throughput profile, and cost structure.

---

## Source-by-Source Extraction Patterns

### Amazon S3

Amazon S3 is an object storage service. It stores files as objects inside buckets. It is the most common landing zone and source for ML datasets because it is durable, scalable, and cost-effective.

Data in Amazon S3 can include:

- CSV, JSON, Apache Parquet, ORC
- Images
- Audio files
- Video files
- Compressed archives
- Preprocessed training/test/validation splits

Common extraction methods:

| Method | Use case |
| --- | --- |
| AWS SDK for Python (boto3) `get_object` | Programmatic reads inside SageMaker processing or training jobs |
| AWS CLI `aws s3 cp` or `aws s3 sync` | Copying files to local instance storage |
| Amazon S3 Select | Running SQL-like queries on a single object to retrieve only needed records |
| Amazon Athena | Serverless SQL queries across many S3 objects using schema-on-read |
| AWS Glue | Crawling and cataloging S3 data, then reading it with Spark ETL jobs |
| SageMaker Data Wrangler | Interactive data preparation from S3 datasets |
| EventBridge + Lambda | Automatically extract or react to new objects in S3 |

Example boto3 extraction:

```python
import boto3

s3 = boto3.client("s3")
response = s3.get_object(Bucket="my-ml-data", Key="train/features.csv")
data = response["Body"].read().decode("utf-8")
```

Key points:

- S3 is object storage, not a file system or database.
- It does not support SQL natively, but Athena and S3 Select provide query access.
- For large analytical datasets, use columnar formats like Apache Parquet to reduce scanned data.
- Same-region access between S3 and AWS analytics services is generally preferred for performance and cost.

### Amazon Elastic Block Store (Amazon EBS)

Amazon EBS provides raw block storage volumes attached to an EC2 instance. It behaves like a local disk drive.

Extraction characteristics:

- Accessed through the operating system file system of the attached instance.
- Typically attached to a single EC2 instance at a time.
- EBS is useful when training jobs need low-latency local disk access.
- Snapshots can be taken and restored to create new volumes.
- EBS is not a shared storage layer.

When to use:

- A single EC2 or SageMaker training instance needs fast local storage for staging data.
- You are working with data already present on an EC2 application server.
- You need disk-level control over extraction.

How data is extracted:

- Mount the EBS volume as a file system.
- Read files using standard Python, Spark, or shell utilities.
- Optionally create an EBS snapshot and create a new volume from it.

Example:

```bash
df -h /mnt/dataset
head -n 100 /mnt/dataset/records.csv
```

Exam note:

- EBS is not designed for concurrent multi-instance access.
- For distributed training where many instances need the same files, EFS or FSx for Lustre is usually preferred.

### Amazon Elastic File System (Amazon EFS)

Amazon EFS is a fully managed, shared, POSIX-compliant file system. Multiple EC2 instances, SageMaker instances, or containers can mount the same EFS file system at the same time.

Extraction characteristics:

- Uses the NFS protocol.
- Provides a shared file namespace across instances.
- Supports automatic scaling of storage capacity.
- Read or write data using standard file APIs.

Common extraction methods:

- Mount the EFS file system on the instance using a mount target.
- Read files with Python, Spark, or any standard file-reading tool.
- Use it as a shared dataset location for distributed training jobs.

Example mount and read:

```bash
sudo mount -t nfs4 -o nfsvers=4.1 fs-12345678.efs.us-east-1.amazonaws.com:/ /mnt/efs
python train.py --data-dir /mnt/efs/dataset
```

When to use:

- Multiple training instances must access the same dataset concurrently.
- A shared file system is required without managing storage servers.
- You need POSIX semantics, such as file locking, directory structure, and file permissions.

Exam note:

- EFS is a shared file system, unlike EBS.
- EFS may be used by SageMaker training, processing, and inference jobs.
- For very high-performance distributed training on large datasets, Amazon FSx for Lustre can provide faster parallel file access to S3-backed data.

### Amazon Relational Database Service (Amazon RDS)

Amazon RDS is a managed relational database service. Data is stored in structured tables with rows and columns. RDS supports engines such as PostgreSQL, MySQL, MariaDB, Oracle, and SQL Server.

Extraction characteristics:

- Use SQL `SELECT` queries to extract data.
- Use JDBC or ODBC connections from application code.
- Data is relational and schema-based.
- Large extraction jobs should avoid impacting production database performance.

Common extraction methods:

| Method | Use case |
| --- | --- |
| SQL query from application code | Targeted extraction of records using SQL |
| AWS Glue JDBC connection | Serverless Spark ETL directly from RDS |
| RDS snapshot export to Amazon S3 | One-time or periodic full data export |
| AWS Database Migration Service (DMS) | Continuous extraction and change data capture |
| Read replica | Offloading analytical queries from production |
| SageMaker Data Wrangler | Interactive SQL-based extraction and preparation |

Example with Python and PostgreSQL:

```python
import pandas as pd
from sqlalchemy import create_engine

engine = create_engine("postgresql://user:pass@mydb.xxxx.us-east-1.rds.amazonaws.com:5432/analytics")
df = pd.read_sql("SELECT customer_id, age, churn FROM customers", engine)
```

When to use:

- Source data is transactional or relational.
- You need filtered extraction using SQL joins and conditions.
- The data has strongly enforced schema and relationships.

Exam note:

- RDS is for structured, queryable records.
- Use a read replica to avoid impacting production traffic.
- For large one-time exports, use RDS snapshot export to S3 rather than repeated SQL scans.
- RDS with PostgreSQL and the `pgvector` extension can store embeddings and support vector similarity search.

### Amazon DynamoDB

Amazon DynamoDB is a fully managed NoSQL key-value and document database. It provides single-digit millisecond lookups by primary key.

Extraction characteristics:

- Access by primary key using `GetItem`.
- Access a group of items with the same partition key using `Query`.
- Full table extraction using `Scan`, but this is inefficient for large tables and should be avoided for frequent analytics extraction.
- Supports DynamoDB Streams for capturing changes.
- Supports export to Amazon S3 for analytical workloads.

Common extraction methods:

| Method | Use case |
| --- | --- |
| `GetItem` | Retrieve one item by primary key |
| `Query` | Retrieve multiple items sharing a partition key |
| `Scan` | Full table read; limited use cases |
| DynamoDB export to S3 | Large-scale one-time or periodic dataset creation |
| DynamoDB Streams | Capturing inserts, updates, and deletes |
| AWS Glue ETL | Serverless extraction from DynamoDB into data lake |

Example with boto3:

```python
import boto3

dynamodb = boto3.resource("dynamodb")
table = dynamodb.Table("customers")

response = table.query(
    KeyConditionExpression="customer_id = :cid",
    ExpressionAttributeValues={":cid": "C12345"}
)
items = response["Items"]
```

When to use:

- Source data is key-value or document-oriented.
- Access pattern is known and key-based.
- You need low-latency retrieval of records.

Exam note:

- `Query` is preferred over `Scan` when possible because it uses partition keys efficiently.
- `Scan` consumes many read capacity units and may throttle production workloads.
- For large ML training datasets, export DynamoDB data to S3 first, then read from S3.
- DynamoDB is not a relational database and does not support SQL joins.

### Amazon OpenSearch Service

Amazon OpenSearch Service is a managed search and analytics service. It is often used for full-text search, log analytics, security analytics, observability, and vector search over embeddings.

Extraction characteristics:

- Data is stored in JSON documents inside indexes.
- Access uses REST APIs.
- Queries can perform full-text search, filtering, aggregations, and vector similarity search.
- Large extractions require pagination using scroll or point-in-time (PIT) APIs.

Common extraction methods:

| Method | Use case |
| --- | --- |
| OpenSearch `_search` API | Query documents by matching criteria |
| Scroll API | Paginate through large result sets |
| Point-in-time (PIT) search | Stable large dataset extraction |
| OpenSearch Ingestion | Pipeline-based data movement |
| AWS Glue and OpenSearch connectors | ETL extraction into a data lake |

Example search request:

```json
POST /customer-interactions/_search
{
  "query": {
    "match": {
      "topic": "billing"
    }
  },
  "size": 100
}
```

When to use:

- Data is searchable text, logs, events, or vector embeddings.
- You need to extract documents matching certain search criteria.
- You are building retrieval-augmented generation (RAG) pipelines and need to retrieve relevant documents.

Exam note:

- OpenSearch Service is not a primary transactional database.
- For large extraction, use `search_after` or point-in-time instead of deep pagination.
- OpenSearch can store embeddings and perform k-nearest neighbor (k-NN) vector search.
- Requests should be signed with SigV4 when using IAM authentication.

## Choosing the Right Extraction Method

| Source | Data model | Primary access | Common extraction path |
| --- | --- | --- | --- |
| Amazon S3 | Object storage | File/object read | boto3, CLI, Athena, Glue |
| Amazon EBS | Block storage | Local file system | EC2 file read |
| Amazon EFS | Shared file system | NFS file read | Mount on EC2/SageMaker |
| Amazon RDS | Relational tables | SQL | SQL, Glue JDBC, snapshot export |
| Amazon DynamoDB | Key-value/document | GetItem/Query/Scan | boto3, Glue, export to S3 |
| Amazon OpenSearch | Search index | REST search queries | `_search`, scroll, PIT |

## Worked Scenarios

### Scenario 1: Training Data from S3

A data scientist needs to train a model on historical CSV files stored in an S3 bucket.

Solution:

- Use Amazon Athena to explore the data using SQL without loading it into a database.
- Use AWS Glue crawlers to catalog the schema.
- Use boto3 or SageMaker training input channels to read the data directly from S3.

### Scenario 2: Shared Dataset for Distributed Training

A distributed training job runs across five SageMaker instances. All instances need to read from the same file namespace.

Solution:

- Store the dataset in Amazon EFS.
- Mount the same EFS file system on all five instances.
- Each instance reads the files through standard file APIs.

### Scenario 3: Relational Database Extraction Without Impacting Production

A production PostgreSQL database contains customer records needed for an ML experiment.

Solution:

- Create an RDS read replica.
- Run analytical SQL queries against the read replica.
- Alternatively, export an RDS snapshot to Amazon S3 and use Athena or Glue for processing.

### Scenario 4: Full Table Export from DynamoDB

A DynamoDB table contains millions of records that will be used to train a recommendation model.

Solution:

- Avoid using `Scan` repeatedly.
- Use DynamoDB export to S3.
- Read the exported data from S3 using Athena, Glue, or SageMaker.

### Scenario 5: Document Extraction for RAG

A RAG application needs to retrieve documents based on semantic similarity.

Solution:

- Store document embeddings in Amazon OpenSearch Service.
- Extract relevant documents using OpenSearch k-NN queries.
- Use the returned documents as context for the generative model.

## Exam Tips and Traps

### Exam Tips

1. **Know the data model of each service.**  
   S3 is object storage, EBS is block storage, EFS is a shared file system, RDS is relational, DynamoDB is key-value/document, and OpenSearch is search.

2. **For distributed shared access, choose EFS or FSx, not EBS.**  
   EBS is generally limited to a single instance. EFS is designed for concurrent multi-instance access.

3. **For large analytical reads from S3, prefer columnar formats and Athena.**  
   Columnar formats like Apache Parquet reduce the amount of data scanned.

4. **For DynamoDB extraction, avoid full table `Scan` when possible.**  
   Use key-based `Query` for targeted access or export to S3 for large dataset creation.

5. **Use RDS read replicas or snapshot exports to avoid production impact.**  
   Direct SQL extraction against the primary production database can degrade performance.

6. **For large OpenSearch extraction, use point-in-time or scroll.**  
   Deep pagination can become unstable and inefficient for large result sets.

7. **Use AWS Glue when you need serverless, scalable extraction and cataloging.**  
   Glue can crawl sources, store table definitions in the Data Catalog, and run Spark ETL jobs.

8. **Consider the difference between extraction and ingestion.**  
   Extraction reads from an existing source. Ingestion is the broader process of bringing data into a pipeline or store.

### Common Traps

1. **Thinking S3 is a file system or database.**  
   S3 does not provide POSIX file operations like arbitrary in-place updates or directory locks. Use EFS or EBS when file system semantics are required.

2. **Choosing EBS for shared access.**  
   EBS is not designed for multiple instances to mount the same volume simultaneously. Shared access requires EFS or FSx.

3. **Running `Scan` on a large DynamoDB table for training data.**  
   This is slow, expensive, and can throttle the production table. Export to S3 is usually the better choice.

4. **Using Amazon RDS for unstructured data or images.**  
   RDS is optimized for structured relational data. Unstructured files should usually go to S3 with metadata in a database or search index.

5. **Using OpenSearch as the system of record for transactional data.**  
   OpenSearch is a search engine, not a primary transactional database. Do not use it as the authoritative source for critical records unless the architecture explicitly justifies it.

6. **Ignoring pagination when extracting large result sets from OpenSearch or DynamoDB.**  
   APIs often have size limits. Use pagination, scroll, or point-in-time to retrieve all records reliably.

7. **Not considering source system load.**  
   Extraction from production databases and tables can cause throttling or performance degradation. Use read replicas, snapshots, or scheduled off-peak extraction.

8. **Reading row-oriented formats for analytical workloads without considering columnar alternatives.**  
   Row formats like CSV and JSON force readers to scan all columns. Columnar formats like Parquet and ORC are often more efficient for ML feature engineering and analytics.

## Summary

Extracting data from AWS data sources requires choosing the right access method for the source system. S3 is the default ML data lake, while EBS and EFS provide disk and file system access. RDS is for structured SQL extraction, DynamoDB is for key-based NoSQL access, and OpenSearch is for search and vector retrieval. The correct choice depends on the data model, access pattern, performance needs, and whether the extraction impacts a production system.
