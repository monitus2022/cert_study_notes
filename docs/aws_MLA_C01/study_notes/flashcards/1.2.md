# Task 1.2 flashcards

<details>
  <summary><b>Scenario 1: Interactive Visual Feature Engineering for a Data Science Team</b></summary>
  <p>A data science team needs to explore a 50 GB tabular dataset in S3, visualize distributions, detect target leakage, apply imputations, one-hot encoding, and scaling, then export a reusable transformation pipeline that can also write features directly into SageMaker Feature Store. They prefer a visual interface with minimal coding and want quick iteration before productionizing.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: Amazon SageMaker Data Wrangler</p>
    <p><strong>Decision process</strong>: The requirements emphasize interactive EDA, visualization, built-in analyses (Quick Model, Target Leakage), and seamless export to processing jobs or Feature Store. Data Wrangler is purpose-built for this inside SageMaker Studio.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs Glue DataBrew: Data Wrangler has deeper ML-specific analyses (target leakage, quick model) and native Feature Store/Pipeline export.</li>
      <li>vs AWS Glue: Glue is code-first/serverless ETL; slower for interactive exploration.</li>
      <li>vs EMR: Overkill and requires cluster management.</li>
    </ul>
    <p><strong>Cons</strong>: Not ideal for pure multi-TB production ETL without sampling; custom transforms should use PySpark (not pandas) at scale.</p>
    <p><strong>Final verdict</strong>: Data Wrangler is the clear winner for DS teams doing visual feature engineering that must flow into SageMaker Feature Store or Pipelines. Export the .flow and run as a Processing job for full scale.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 2: No-Code Cleaning Recipes for Business Analysts</b></summary>
  <p>Business analysts who cannot write code must clean a large CSV dataset: impute missing values, remove duplicates, standardize column names, apply binning, and create reusable recipes that data engineers can later schedule. The team wants profiling and visual quality checks.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: AWS Glue DataBrew</p>
    <p><strong>Decision process</strong>: Explicit no-code requirement + reusable recipes + data profiling points directly to DataBrew.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs Data Wrangler: DataBrew is more analyst-friendly, has stronger recipe versioning for pure cleaning, and does not require SageMaker Studio.</li>
      <li>vs Glue ETL: No coding needed.</li>
      <li>vs EMR: Far too complex.</li>
    </ul>
    <p><strong>Cons</strong>: Limited complex custom logic compared with PySpark; less ML-specific visualization than Data Wrangler.</p>
    <p><strong>Final verdict</strong>: Glue DataBrew is optimal for no-code, repeatable cleaning by non-engineers. Recipes can be called from Glue jobs or Step Functions later.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 3: Large-Scale Scheduled Serverless ETL with Data Catalog</b></summary>
  <p>An ML platform team must run daily transformations on 10+ TB of Parquet data: join multiple sources, deduplicate, engineer lag features, apply encoding, and update the AWS Glue Data Catalog. They want serverless operation, job bookmarks for incremental processing, and minimal infrastructure management.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: AWS Glue (Spark ETL jobs)</p>
    <p><strong>Decision process</strong>: Scale + serverless + Data Catalog integration + incremental bookmarks = Glue.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs EMR: No cluster management, auto-scaling, pay-per-use.</li>
      <li>vs Data Wrangler/DataBrew: Better for heavy scripted multi-TB joins and production scheduling.</li>
      <li>vs Lambda: Lambda cannot handle 10 TB efficiently.</li>
    </ul>
    <p><strong>Cons</strong>: Less interactive than Data Wrangler; cold starts possible; custom Spark configs limited vs EMR.</p>
    <p><strong>Final verdict</strong>: AWS Glue is the default production choice for large-scale, scheduled, serverless feature transformation with catalog integration. Use DynamicFrames + job bookmarks.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 4: Need Full Spark Cluster Control and Custom Libraries</b></summary>
  <p>A team must run a complex feature engineering job using a specific Spark 3.x version, custom native libraries, Ganglia monitoring, and fine-tuned executor memory settings on a 200-node cluster. The job runs for 6+ hours and reuses a long-lived cluster.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: Amazon EMR (Spark)</p>
    <p><strong>Decision process</strong>: Explicit need for cluster control, custom libs, and long-running tuned Spark points to EMR.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs Glue: Full control over hardware, Spark config, bootstrap actions, and persistent clusters.</li>
      <li>vs Data Wrangler: Can handle true multi-hundred-TB with custom code.</li>
    </ul>
    <p><strong>Cons</strong>: Higher operational overhead (cluster mgmt, patching, cost if idle); not serverless.</p>
    <p><strong>Final verdict</strong>: Choose EMR only when Glue’s abstractions are insufficient. Otherwise prefer Glue for simplicity. Use EMR on EKS or Serverless if partial control is enough.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 5: Preventing Train-Serve Skew with Consistent Features</b></summary>
  <p>A real-time fraud model requires the exact same feature values (including point-in-time correct aggregates) at training and low-latency inference (&lt;10 ms). Features are generated from both batch historical data and streaming events. The team must store features for both offline training and online serving.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: Amazon SageMaker Feature Store (Online + Offline stores)</p>
    <p><strong>Decision process</strong>: Dual online/offline requirement + point-in-time correctness + low latency = Feature Store.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs plain S3 + DynamoDB: Feature Store handles consistency, time-travel, ingestion APIs, and Athena/Spark integration automatically.</li>
      <li>vs Data Wrangler alone: Data Wrangler can feed Feature Store but does not serve online features.</li>
    </ul>
    <p><strong>Cons</strong>: Additional cost; requires record identifier + event time; offline store is S3 (or Iceberg).</p>
    <p><strong>Final verdict</strong>: Always write to both Online and Offline stores. Use Feature Store as the single source of truth to eliminate train-serve skew. Data Wrangler or Glue can ingest into it.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 6: Encoding Low-Cardinality Nominal Categories</b></summary>
  <p>A dataset contains a “city” column with 12 unique values and a “product_type” column with 8 values. The model is a linear learner / neural net. The engineer must choose an encoding that avoids implying ordinal relationships.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen technique</strong>: One-hot encoding (via Data Wrangler, DataBrew, or Spark)</p>
    <p><strong>Decision process</strong>: Low cardinality + nominal (no order) + linear/NN model → one-hot.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs Label encoding: Label encoding invents false order (bad for linear models).</li>
      <li>vs Binary/Hashing: Unnecessary for &lt;15-20 cardinality; one-hot is interpretable.</li>
    </ul>
    <p><strong>Cons</strong>: Dimensionality explosion if cardinality grows; sparse matrices.</p>
    <p><strong>Final verdict</strong>: One-hot for low-cardinality nominal. Use Data Wrangler’s encode categorical transform or Spark StringIndexer + OneHotEncoder. Drop one category to avoid multicollinearity if needed.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 7: High-Cardinality Categorical Features</b></summary>
  <p>An e-commerce dataset has a “user_id” (millions of values) and “product_sku” (100k+ values). Tree-based and embedding-based models will be used. Memory and sparsity are concerns.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen technique</strong>: Hashing / binary encoding or learned embeddings (not one-hot)</p>
    <p><strong>Decision process</strong>: Extreme cardinality makes one-hot impossible.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs One-hot: Hashing keeps fixed dimensions; embeddings capture similarity.</li>
      <li>vs Label encoding: Still creates artificial order and huge integer range.</li>
    </ul>
    <p><strong>Cons</strong>: Hash collisions; embeddings need training.</p>
    <p><strong>Final verdict</strong>: Use feature hashing (Spark FeatureHasher or Data Wrangler) for classic ML; prefer entity embeddings for deep learning. Never one-hot high-cardinality columns.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 8: Ordinal Feature Encoding</b></summary>
  <p>A dataset contains an “education_level” column with values “High School” &lt; “Bachelor” &lt; “Master” &lt; “PhD”. The model is XGBoost.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen technique</strong>: Ordinal / Label encoding with explicit order</p>
    <p><strong>Decision process</strong>: True rank exists → preserve order.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs One-hot: Preserves ordinal information that trees can split on efficiently.</li>
      <li>vs Binary: Less compact and loses order.</li>
    </ul>
    <p><strong>Cons</strong>: If the order is wrong, model performance suffers.</p>
    <p><strong>Final verdict</strong>: Use ordinal encoding only when a real order exists. In Data Wrangler or Spark, map values explicitly to integers 0,1,2,3…</p>
  </details>
</details>

<details>
  <summary><b>Scenario 9: Handling Missing Values Correctly</b></summary>
  <p>A training dataset has 15% missing values in numeric columns. The team will use a scikit-learn pipeline and later deploy with SageMaker. They must avoid data leakage.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen approach</strong>: Fit imputer (median/mean or iterative) on training data only, then transform both train and serve data. Prefer SageMaker Data Wrangler or Scikit-learn Processor + Feature Store.</p>
    <p><strong>Decision process</strong>: Leakage prevention is critical; statistics must come from train set.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs dropping rows: Loses too much data.</li>
      <li>vs mean of full dataset: Causes leakage.</li>
    </ul>
    <p><strong>Cons</strong>: Simple mean/median ignores relationships; consider model-based imputation for higher quality.</p>
    <p><strong>Final verdict</strong>: Always learn imputation parameters on train fold only. Store the fitted imputer or use Feature Store so inference uses identical logic. DataBrew/Data Wrangler make this visual and repeatable.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 10: Detecting and Treating Outliers</b></summary>
  <p>A sensor dataset contains extreme outliers that skew mean and variance. The model is a neural network sensitive to scale. The team wants a robust, repeatable method.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen techniques</strong>: IQR-based capping (winsorizing) or robust scaling + optional log transform. Implement in Data Wrangler or Spark.</p>
    <p><strong>Decision process</strong>: Neural nets need bounded inputs; IQR is robust to extremes.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs z-score removal: IQR less affected by the outliers themselves.</li>
      <li>vs keeping raw: Destroys gradient stability.</li>
    </ul>
    <p><strong>Cons</strong>: Capping loses some information; domain knowledge may prefer separate “outlier” flag feature.</p>
    <p><strong>Final verdict</strong>: Detect with IQR or modified z-score, treat by capping or transformation, then standardize. Document the exact percentiles used so inference matches.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 11: Log Transformation for Skewed Target or Features</b></summary>
  <p>A regression problem predicts house prices that are heavily right-skewed. Features such as “square_footage” are also skewed. The model is linear regression.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen technique</strong>: Log1p transformation on target and skewed features</p>
    <p><strong>Decision process</strong>: Linear models assume normality/homoscedasticity; log helps.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs raw: Better residual distribution and lower RMSE on original scale (after expm1).</li>
      <li>vs Box-Cox: Log is simpler and sufficient for many positive skew cases.</li>
    </ul>
    <p><strong>Cons</strong>: Only for positive values; must remember inverse transform for predictions.</p>
    <p><strong>Final verdict</strong>: Apply log1p in Data Wrangler or Spark. For trees, log is optional but often still helps. Always inverse-transform predictions.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 12: Binning Continuous Variables</b></summary>
  <p>An age column is continuous. The business wants interpretable risk bands (0-17, 18-25, 26-40, …) and the model is a generalized linear model. Monotonicity should be preserved if possible.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen technique</strong>: Supervised or equal-frequency/width binning + ordinal encoding of bins</p>
    <p><strong>Decision process</strong>: Interpretability + GLM → binning.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs keeping continuous: Bins give business-friendly coefficients.</li>
      <li>vs one-hot bins: Ordinal keeps order for monotonic relationships.</li>
    </ul>
    <p><strong>Cons</strong>: Information loss; arbitrary cut points if unsupervised.</p>
    <p><strong>Final verdict</strong>: Use Data Wrangler’s binning transform or Spark QuantileDiscretizer / Bucketizer. Prefer supervised binning (e.g., decision-tree based) when target is available.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 13: Lightweight Per-Record Streaming Transforms</b></summary>
  <p>Clickstream events arrive via Kinesis Data Streams. Each record needs simple enrichment (lookup a static dimension, parse JSON, add timestamp features) before being written to S3 and Feature Store. Latency must stay under 100 ms and volume is moderate.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: AWS Lambda (with possible Kinesis Data Firehose or direct Feature Store put)</p>
    <p><strong>Decision process</strong>: Simple per-record map operations + low latency + serverless = Lambda.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs Spark Streaming/EMR: Much lower ops overhead and cost for simple transforms.</li>
      <li>vs Glue Streaming: Overkill for map-only logic.</li>
    </ul>
    <p><strong>Cons</strong>: 15-min timeout, limited memory, no heavy state or large joins.</p>
    <p><strong>Final verdict</strong>: Lambda for lightweight streaming feature transforms. For windowed aggregates or complex state, move to Spark Structured Streaming on EMR or Glue Streaming.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 14: Complex Windowed Streaming Feature Engineering</b></summary>
  <p>The team needs 5-minute and 1-hour tumbling/ sliding window aggregates (count, sum, unique users) on high-volume clickstream data, then join with dimension data before landing in Feature Store.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: Spark Structured Streaming on Amazon EMR (or Glue Streaming)</p>
    <p><strong>Decision process</strong>: Stateful windowed aggregations require Spark’s streaming engine.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs Lambda: Native windowing, exactly-once, large state handling.</li>
      <li>vs pure Kinesis Analytics: More flexible joins and ML feature logic with Spark.</li>
    </ul>
    <p><strong>Cons</strong>: Higher cost and management than Lambda.</p>
    <p><strong>Final verdict</strong>: Use Spark Streaming when windows, state, or complex joins are required. Prefer Glue Streaming if serverless is desired and cluster control is unnecessary.</p>
  </details>
</details>

  <summary><b>Scenario 15: High-Quality Labeling with Sensitive Data</b></summary>
  <p>A healthcare company needs to label 50,000 medical images for a segmentation model. Data cannot leave the VPC, labelers must be trained employees, and label quality (inter-annotator agreement) must be measured.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: Amazon SageMaker Ground Truth with Private Workforce</p>
    <p><strong>Decision process</strong>: Data sensitivity + internal labelers + quality metrics = Ground Truth Private Workforce.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs Public Mechanical Turk: Data never leaves controlled environment; higher quality control.</li>
      <li>vs Vendor workforce: Cheaper if internal staff available; full control.</li>
      <li>vs plain Mechanical Turk direct: Ground Truth adds UI, consolidation, automated labeling, and audit trails.</li>
    </ul>
    <p><strong>Cons</strong>: Requires managing the private workforce Cognito setup.</p>
    <p><strong>Final verdict</strong>: Ground Truth Private Workforce is mandatory for PII/PHI. Enable automated data labeling to reduce human effort after a seed set.</p>
  </details>
</details>

  <summary><b>Scenario 16: Cost-Effective Labeling at Scale with Active Learning</b></summary>
  <p>A startup must label 1 million images for object detection but has a limited budget. They can label a few thousand themselves and want the system to automatically label the rest with human verification only on uncertain samples.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: SageMaker Ground Truth Automated Data Labeling (active learning) + Public or Vendor workforce</p>
    <p><strong>Decision process</strong>: Budget + large volume → active learning to minimize human labels.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs fully manual: 10x+ cost reduction after initial model is good.</li>
      <li>vs custom active learning loop: Ground Truth manages the loop, model training, and confidence thresholds.</li>
    </ul>
    <p><strong>Cons</strong>: Requires an initial labeled seed set; works best when model can learn quickly.</p>
    <p><strong>Final verdict</strong>: Enable Automated Data Labeling in Ground Truth. Start with Private or Vendor for quality seed, then switch to public for scale if data is non-sensitive.</p>
  </details>
</details>

  <summary><b>Scenario 18: Fuzzy Deduplication of Customer Records</b></summary>
  <p>A company has multiple source systems with customer records that contain typos, different formats, and partial matches (e.g., “Jon Smith” vs “John Smtih”). Exact match deduplication fails. They need an ML-based approach that scales.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen component</strong>: AWS Glue FindMatches ML Transform</p>
    <p><strong>Decision process</strong>: Fuzzy/non-exact matching at scale is exactly what FindMatches was built for.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs custom Spark ML: FindMatches is managed, provides labeling UI, and iteratively improves.</li>
      <li>vs DataBrew exact dedupe: Cannot handle fuzzy matches.</li>
    </ul>
    <p><strong>Cons</strong>: Requires some labeled matching pairs to train; iterative process.</p>
    <p><strong>Final verdict</strong>: Use Glue FindMatches for real-world entity resolution. Combine with DataBrew or Glue for exact-match cleanup first, then FindMatches.</p>
  </details>

<details>
  <summary><b>Scenario 19: Standardization vs Normalization Decision</b></summary>
  <p>Features have different units (income in dollars, age in years, temperature). The model will be a logistic regression / neural net. A second model will be Random Forest. The engineer must choose scaling strategy.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen technique</strong>: StandardScaler (zero mean, unit variance) for linear/NN; no scaling needed for Random Forest.</p>
    <p><strong>Decision process</strong>: Distance/gradient-based models need scaling; trees do not.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>Standardization vs MinMax (Normalization): Standardization is robust when outliers remain; MinMax useful when bounded [0,1] input is required (e.g., some NN activations).</li>
      <li>vs no scaling: Linear models fail or converge slowly.</li>
    </ul>
    <p><strong>Cons</strong>: Must persist the exact mean/std for inference.</p>
    <p><strong>Final verdict</strong>: Use StandardScaler by default for non-tree models. Apply via Data Wrangler, Scikit-learn in Processing, or Spark MLlib. Skip for pure tree ensembles. Store scaler parameters in Feature Store or model artifact.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 20: End-to-End Feature Pipeline with Export to Feature Store</b></summary>
  <p>A team uses Data Wrangler for exploration and feature creation (imputation, encoding, custom PySpark transforms). Once satisfied, they need the exact same logic to run daily on full data, write to both Online and Offline Feature Store, and be callable from a SageMaker Pipeline for training.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Chosen workflow</strong>: SageMaker Data Wrangler → Export to Studio Pipeline / Processing job → Ingest to SageMaker Feature Store (both stores)</p>
    <p><strong>Decision process</strong>: Visual development + production repeatability + Feature Store integration is Data Wrangler’s sweet spot.</p>
    <p><strong>Pros vs counterparts</strong>:</p>
    <ul>
      <li>vs pure Glue: Faster iteration and built-in ML analyses; still can export to Glue if desired.</li>
      <li>vs manual Feature Store ingestion: Data Wrangler generates the ingestion code.</li>
    </ul>
    <p><strong>Cons</strong>: For ultra-large or complex multi-source jobs, may still hand off the exported Spark code to Glue/EMR.</p>
    <p><strong>Final verdict</strong>: Develop in Data Wrangler, export the flow as a Processing step or Spark job, and configure it to write to Feature Store. This is the recommended AWS reference pattern for reproducible feature engineering that eliminates train-serve skew.</p>
  </details>

**Quick Exam Recall Checklist**
- Data Wrangler = visual DS feature eng + Feature Store export
- DataBrew = no-code analyst cleaning recipes
- Glue = serverless production Spark ETL
- EMR = when you need cluster knobs
- Feature Store = online + offline = no skew
- Ground Truth = labeling (Private / Public-MTurk / Vendor + Auto)
- Lambda = simple streaming map
- Spark Streaming = windowed/complex streaming
- One-hot low card, Hash/Embed high card, Ordinal only if ordered
- Always fit transforms on train only
- FindMatches = fuzzy dedupe
