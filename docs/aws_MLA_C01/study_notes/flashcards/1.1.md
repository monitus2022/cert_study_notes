  <summary><b>Scenario 1: Minimizing Training Startup Overhead for Multi-Terabyte Datasets with Many Small Files</b></summary>
  <p><b>Question:</b> An ML engineer is training a computer vision model in Amazon SageMaker using a 2 TB dataset stored as millions of small JPEG files in an S3 bucket. The current training job uses SageMaker <code>File</code> mode, but it spends over 30 minutes downloading data to the local EBS volume before training begins. Which change will reduce startup latency and storage costs with minimal code refactoring?</p>
  <ul>
    <li><b>A)</b> Convert all JPEG images to CSV format and store them in Amazon EFS.</li>
    <li><b>B)</b> Change the SageMaker S3 data input mode from <code>File</code> mode to <code>FastFile</code> mode.</li>
    <li><b>C)</b> Increase the provisioned IOPS (gp3/io2) of the local EBS storage volume attached to the training instance.</li>
    <li><b>D)</b> Export the dataset into Amazon DynamoDB and read directly from DynamoDB during model training.</li>
  </ul>
  <hr>  
  <details>
    <summary><b>Answer</b></summary>
    <p><b>Correct Answer: B</b></p>
    <p><b>Explanation:</b> FastFile mode presents S3 objects as a POSIX filesystem on the training instance and streams data on-demand as the training script reads it. Unlike File mode, it does not fully download the dataset to local EBS before the training script starts, eliminating the multi-minute (or multi-hour) startup latency for large datasets. It requires only a one-line change (<code>input_mode='FastFile'</code>) and works well when files are reasonably sized or when the model is compute-bound.</p>
    <p><b>Key Concepts:</b></p>
    <ul>
      <li><b>File mode</b>: Full download to EBS/NVMe before training starts → high startup latency + full local storage cost.</li>
      <li><b>FastFile mode</b>: On-demand streaming with POSIX interface → near-zero startup latency, no need to fit entire dataset on local disk.</li>
      <li><b>Pipe mode</b>: Older streaming mode (Unix named pipes); largely superseded by FastFile for most use cases.</li>
    </ul>
    <p><b>Exam Tips / Traps:</b></p>
    <ul>
      <li>Trap: Choosing FSx for Lustre or EFS when the question emphasizes “minimal code refactoring” – those require VPC, filesystem creation, and mount configuration.</li>
      <li>Trap: Thinking higher EBS IOPS helps – IOPS only matter after the download finishes.</li>
      <li>For many tiny files (&lt;50 MB), best long-term fix is to pack them into larger containers (TFRecord, WebDataset, RecordIO) even if you keep FastFile.</li>
      <li>FastFile currently supports S3 prefixes only (not manifest files).</li>
    </ul>
  </details>
</details>

  <summary><b>Scenario 2: Choosing the Optimal Columnar Format for Analytical Feature Extraction</b></summary>
  <p><b>Question:</b> A data scientist needs to extract a small subset of columns from a 5 TB historical clickstream table stored in Amazon S3 for feature engineering in SageMaker Data Wrangler and Athena. The team repeatedly runs SELECT queries that touch only 8–12 columns out of 200. Which data format should they convert the raw data into to minimize scanned bytes, query cost, and processing time?</p>
  <ul>
    <li><b>A)</b> CSV (gzip compressed)</li>
    <li><b>B)</b> JSON Lines</li>
    <li><b>C)</b> Apache Parquet</li>
    <li><b>D)</b> Apache Avro</li>
  </ul>
  <hr>  
  <details>
    <summary><b>Answer</b></summary>
    <p><b>Correct Answer: C</b></p>
    <p><b>Explanation:</b> Apache Parquet is a columnar storage format. When Athena or Data Wrangler queries only a few columns, the engine performs column pruning and predicate pushdown, reading only the required column chunks. This dramatically reduces bytes scanned (Athena bills per TB scanned) and improves compression because each column contains homogeneous data types.</p>
    <p><b>Key Concepts:</b></p>
    <ul>
      <li><b>Columnar (Parquet, ORC)</b>: Best for analytical scans, feature selection, wide tables, repeated queries.</li>
      <li><b>Row-oriented (CSV, JSON, Avro)</b>: Best for full-record reads, streaming writes, schema evolution (Avro especially).</li>
      <li>Parquet is the de-facto standard for SageMaker Feature Store offline store and Glue/Athena workloads.</li>
    </ul>
    <p><b>Exam Tips / Traps:</b></p>
    <ul>
      <li>Trap: Choosing Avro because “it has schema” – Avro is excellent for schema evolution in streaming but is row-based and does not give column pruning benefits.</li>
      <li>Trap: Thinking gzip CSV is “good enough” – it still forces full row scans.</li>
      <li>ORC is also columnar and acceptable, but Parquet appears far more frequently in AWS ML exam scenarios.</li>
      <li>Always convert landing-zone JSON/CSV into Parquet as part of the ETL step before heavy feature engineering.</li>
    </ul>
  </details>
</details>

  <p><b>Question:</b> A fraud-detection system must keep feature values fresh within seconds of a transaction event. Events arrive on Amazon Kinesis Data Streams. Which combination provides the lowest-latency path to the online store of Amazon SageMaker Feature Store? (Select TWO.)</p>
  <ul>
    <li><b>A)</b> Use Amazon Managed Service for Apache Flink to enrich events and call the Feature Store <code>PutRecord</code> API.</li>
    <li><b>B)</b> Deliver events via Kinesis Data Firehose to S3, then run a scheduled Glue job every 5 minutes to ingest into Feature Store.</li>
    <li><b>C)</b> Use a Lambda function triggered by Kinesis to transform records and invoke <code>PutRecord</code>.</li>
    <li><b>D)</b> Write events directly into the Feature Store offline store (Parquet on S3) and rely on the automatic online-store sync.</li>
    <li><b>E)</b> Land raw events in Amazon EFS and mount the filesystem from a SageMaker training job.</li>
  </ul>
  <hr>  
  <details>
    <summary><b>Answer</b></summary>
    <p><b>Correct Answers: A and C</b> (Select TWO)</p>
    <p><b>Explanation:</b> The online store is updated only by the synchronous <code>PutRecord</code> API (or the Spark connector that ultimately calls it). Both a Flink application and a Lambda function can consume the Kinesis stream in near real time and call <code>PutRecord</code>, keeping feature freshness in the low-second range. Batch paths through S3 + Glue introduce minutes of delay and primarily target the offline store.</p>
    <p><b>Key Concepts:</b></p>
    <ul>
      <li><b>Online store</b>: Low-latency key-value lookups for real-time inference; updated via <code>PutRecord</code>.</li>
      <li><b>Offline store</b>: Append-only Parquet history on S3 for training and batch inference; eventually consistent with online.</li>
      <li>Streaming sources (Kinesis, MSK) → Flink / Lambda / custom consumers → <code>PutRecord</code>.</li>
    </ul>
    <p><b>Exam Tips / Traps:</b></p>
    <ul>
      <li>Trap: Believing Firehose + Glue is “streaming” – Firehose buffers (minimum 60 s or 1 MB) and Glue is batch.</li>
      <li>Trap: Thinking writing to offline store automatically updates online store in real time – it does not.</li>
      <li>Data Wrangler is excellent for batch feature engineering and one-time ingestion, not for continuous low-latency streaming.</li>
    </ul>
  </details>

  <summary><b>Scenario 4: Storage Choice for Shared, Random-Access Training Data Across Multiple Jobs</b></summary>
  <p><b>Question:</b> A team runs dozens of SageMaker training jobs per day that all need random access to the same 8 TB dataset of many small files. Jobs are short-lived (15–40 minutes) and run in a VPC. Which storage solution provides the best combination of high IOPS, low latency, and no per-job download overhead?</p>
  <ul>
    <li><b>A)</b> Amazon S3 with FastFile mode</li>
    <li><b>B)</b> Amazon EFS (General Purpose performance mode)</li>
    <li><b>C)</b> Amazon FSx for Lustre linked to the S3 dataset</li>
    <li><b>D)</b> Amazon EBS io2 Block Express volumes attached to each training instance</li>
  </ul>
  <hr>  
  <details>
    <summary><b>Answer</b></summary>
    <p><b>Correct Answer: C</b></p>
    <p><b>Explanation:</b> FSx for Lustre is a high-performance parallel filesystem that can be linked to an S3 bucket. Once the filesystem is warm, SageMaker simply mounts it; there is no per-job download. It delivers hundreds of GB/s and millions of IOPS, making it ideal for many small files and random access patterns. EFS is easier but has higher latency and lower throughput ceilings. FastFile still streams from S3 on every read and is less optimal for heavy random I/O across many jobs.</p>
    <p><b>Key Concepts:</b></p>
    <ul>
      <li><b>FSx for Lustre</b>: Highest performance shared filesystem for ML training; integrates natively with S3; requires VPC.</li>
      <li><b>EFS</b>: Fully managed NFS, good when data already lives there or for moderate concurrency; lower peak throughput than Lustre.</li>
      <li><b>FSx for NetApp ONTAP</b>: Appears in the exam guide; useful for enterprise NAS workloads that need multiprotocol (NFS/SMB/iSCSI) access, not the first choice for pure high-throughput ML training.</li>
    </ul>
    <p><b>Exam Tips / Traps:</b></p>
    <ul>
      <li>Trap: Choosing EBS – EBS is instance-local and cannot be shared across jobs without snapshots or copying.</li>
      <li>Remember cold-start: first access to a new FSx for Lustre filesystem linked to S3 can be slow until data is lazy-loaded; subsequent jobs benefit.</li>
      <li>If the question stresses “data already resides in EFS”, then EFS becomes the correct answer.</li>
    </ul>
  </details>

  <ul>
    <li><b>A)</b> Switch from many small files to larger Parquet or ORC files (hundreds of MB each) and use S3 multipart uploads.</li>

    <ul>
      <li>Always look for “many small files” or “503 SlowDown” → answer involves larger files + better key design.</li>
      <li>S3 is infinitely scalable in theory; the practical limit is how you design keys and object sizes.</li>
    </ul>
  </details>

    <p><b>Key Concepts:</b></p>

      <li>Skill: “Extracting data \ldots by using \ldots Amazon EBS Provisioned IOPS.”</li>
      <li>File mode + high random I/O = classic use case for provisioned-IOPS EBS.</li>
    </ul>
    <p><b>Exam Tips / Traps:</b></p>
    <ul>
      <li>If the bottleneck is download time (not post-download I/O), switch to FastFile or FSx instead.</li>
      <li>Know the difference: gp3 (cost-effective, up to 16 k IOPS baseline + burst) vs io2 (highest performance, multi-attach capable).</li>
    </ul>

  <p><b>Question:</b> Clickstream events are continuously ingested via Kinesis Data Firehose into an S3 landing zone. The event schema changes frequently (new nested fields are added by mobile clients). Downstream Glue crawlers and Spark jobs must continue to read both old and new data without failure. Which format should Firehose be configured to write?</p>
  <ul>
    <li><b>A)</b> Apache Parquet with a rigid Glue schema</li>
    <li><b>B)</b> CSV</li>
    <li><b>C)</b> Apache Avro (or JSON) with schema registry support</li>
    <li><b>D)</b> RecordIO-protobuf</li>
  </ul>
  <hr>  
  <details>
    <summary><b>Answer</b></summary>
    <p><b>Correct Answer: C</b></p>
    <p><b>Explanation:</b> Apache Avro stores the schema with the data (or references a schema registry) and was designed for schema evolution—fields can be added, removed, or reordered with backward/forward compatibility. JSON is also schema-flexible (though less efficient). Parquet can handle some evolution but is less forgiving and is better used after a stabilizing transformation step.</p>
    <p><b>Key Concepts:</b></p>
    <ul>
      <li>Avro = row-based, binary, excellent schema evolution → ideal for streaming landing zones.</li>
      <li>Typical pattern: land as Avro/JSON → transform/stabilize → write Parquet for analytics & training.</li>
    </ul>
    <p><b>Exam Tips / Traps:</b></p>
    <ul>
      <li>Trap: Immediately choosing Parquet for every S3 use case – Parquet shines for read-heavy analytical workloads, not for rapidly evolving raw streams.</li>
    </ul>
  </details>

  <summary><b>Scenario 15: Cost-Performance Trade-off for Infrequently Accessed Training Archives</b></summary>
  <p><b>Question:</b> After a model is deployed, the 12 TB raw training dataset is only needed for occasional retraining or audit (once every 3–6 months). Which S3 storage class offers the best cost vs retrieval-time trade-off while still allowing a SageMaker training job to read the data within minutes when required?</p>
  <ul>
    <li><b>A)</b> S3 Standard</li>
    <li><b>B)</b> S3 Intelligent-Tiering or S3 Standard-Infrequent Access</li>
    <li><b>C)</b> S3 Glacier Deep Archive</li>
    <li><b>D)</b> S3 One Zone-Infrequent Access</li>
  </ul>
  <hr>  
  <details>
    <summary><b>Answer</b></summary>
    <p><b>Correct Answer: B</b></p>
    <p><b>Explanation:</b> S3 Standard-IA (or Intelligent-Tiering) provides significantly lower storage cost than Standard while still offering millisecond access. Glacier Deep Archive has the lowest storage cost but retrieval can take 12–48 hours, which is unacceptable if a training job needs to start “within minutes.” One Zone-IA is cheaper still but risks data loss if the AZ fails—usually avoided for irreplaceable training data.</p>
    <p><b>Key Concepts:</b></p>
    <ul>
      <li>Storage-class decision framework: access frequency + retrieval-time SLA + durability requirements.</li>
      <li>Intelligent-Tiering is often the “set-and-forget” exam answer when access patterns are unknown or change over time.</li>
    </ul>
    <p><b>Exam Tips / Traps:</b></p>
    <ul>
      <li>Watch the retrieval-time language in the question (“minutes” vs “hours” vs “days”).</li>
      <li>Glacier Instant Retrieval is a newer option that can also appear; it gives millisecond access at near-IA cost.</li>
    </ul>
  </details>

  <summary><b>Scenario 16: Debugging Capacity Issues with Amazon Kinesis Data Streams</b></summary>
  <p><b>Question:</b> A real-time feature pipeline using Kinesis Data Streams + Lambda suddenly experiences increased iterator-age and failed records. CloudWatch shows the stream is hitting its shard-level throughput limits. What is the most appropriate immediate remediation?</p>
  <ul>
    <li><b>A)</b> Switch the stream to on-demand capacity mode (or add shards in provisioned mode).</li>
    <li><b>B)</b> Change the Lambda runtime from Python to Java.</li>
    <li><b>C)</b> Move the data to Amazon EFS and read with a SageMaker Processing job.</li>
    <li><b>D)</b> Enable S3 Transfer Acceleration on the Kinesis stream.</li>
  </ul>
  <hr>  
  <details>
    <summary><b>Answer</b></summary>
    <p><b>Correct Answer: A</b></p>
    <p><b>Explanation:</b> Each Kinesis shard has fixed ingest (1 MB/s or 1000 records/s) and read limits. When those limits are exceeded, iterator age grows and records can be throttled. The direct fix is to increase capacity—either by switching to on-demand mode (auto-scales) or by splitting shards in provisioned mode. This directly addresses the “capacity and scalability” troubleshooting skill listed in the exam guide.</p>
    <p><b>Key Concepts:</b></p>
    <ul>
      <li>Kinesis capacity modes: provisioned (manual shard management) vs on-demand (automatic).</li>
      <li>Key metrics: IncomingBytes, IncomingRecords, GetRecords.IteratorAgeMilliseconds, WriteProvisionedThroughputExceeded.</li>
    </ul>
    <p><b>Exam Tips / Traps:</b></p>
    <ul>
      <li>Always check shard-level limits when you see iterator-age or throughput-exceeded errors.</li>
      <li>Enhanced fan-out can help consumer-side scaling but does not increase ingest capacity.</li>
    </ul>
  </details>
</details>

    </ul>

    <li><b>B)</b> Simple POSIX shared storage when the dataset already lives in EFS and concurrency is moderate</li>
    <li><b>C)</b> Lowest-complexity streaming access from S3 for large sequential or moderately random reads without managing a filesystem</li>
    <li><b>D)</b> Enterprise multiprotocol (NFS/SMB) access with NetApp features for hybrid research data</li>
    <li><b>E)</b> Maximum local random-I/O performance after a File-mode download on a single training instance</li>

    <p><b>Correct Matching:</b></p>
    <ul>
      <li>1 → C</li>
      <li>2 → A</li>
      <li>3 → B</li>
      <li>4 → D</li>
      <li>5 → E</li>
    </ul>
    <p><b>Explanation & Key Concepts Recap:</b></p>
    <ul>
      <li><b>S3 + FastFile</b> – simplest high-performance path from S3; no VPC filesystem needed.</li>
      <li><b>FSx for Lustre</b> – king of throughput/IOPS for ML training with small files or heavy random I/O across jobs.</li>
      <li><b>EFS</b> – easy elastic NFS; choose when data is already there or requirements are modest.</li>
      <li><b>FSx for NetApp ONTAP</b> – NetApp feature parity + multiprotocol for enterprise hybrid scenarios.</li>

    <p><b>Exam Tips / Traps:</b></p>
    <ul>
      <li>Memorize the decision tree: “Already in EFS?” → EFS; “Many small files + highest perf + shared?” → Lustre; “NetApp mentioned?” → ONTAP; “Simplest S3 streaming?” → FastFile; “Local disk bottleneck after download?” → EBS IOPS.</li>
      <li>This matching style forces you to know trade-offs cold—exactly what Task 1.1 tests.</li>
