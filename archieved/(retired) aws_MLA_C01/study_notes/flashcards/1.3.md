<details>
  <summary><b>Scenario 1: Detecting Class Imbalance Before Training a Fraud Model</b></summary>
  <p>An ML engineer is preparing a tabular fraud-detection dataset (10 M rows) stored in S3. The positive (fraud) class is only 0.8 %. Leadership requires proof that the training set is not severely imbalanced before any model is trained. The team already uses SageMaker and wants a managed, model-agnostic metric.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    Need a pre-training, model-agnostic metric that quantifies facet imbalance. SageMaker Clarify provides Class Imbalance (CI) = (n<sub>a</sub> − n<sub>d</sub>) / (n<sub>a</sub> + n<sub>d</sub>), range [−1, +1].</p>
    <p><b>Options considered</b></p>
    <ul>
      <li><b>Manual pandas value_counts</b> – free but not auditable, no integration with SageMaker Model Monitor later.</li>
      <li><b>SageMaker Data Wrangler bias report</b> – good for interactive exploration, less suitable for automated pipeline gates.</li>
      <li><b>SageMaker Clarify pre-training bias job</b> – produces CI (and DPL, KL, etc.) as a first-class Processing job, emits JSON metrics, integrates with pipelines.</li>
    </ul>
    <p><b>Pros / Cons</b></p>
    <ul>
      <li>Clarify: + standardized metrics, pipeline-native, audit trail; − small extra Processing cost.</li>
      <li>Manual: + zero cost; − no governance, easy to skip.</li>
    </ul>
    <p><b>Final verdict</b><br>
    Use <code>SageMaker Clarify</code> pre-training bias analysis with the CI metric. Gate the training step on |CI| &lt; 0.5 (or business threshold). This is the exam-expected, production-grade approach.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 2: Measuring Label Bias with Difference in Proportions of Labels (DPL)</b></summary>
  <p>A lending model uses a protected attribute “age_group”. Business wants to know whether the historical approval rate (positive label) differs significantly between age groups before training. Dataset is Parquet in S3; team must stay inside SageMaker.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    CI only looks at sample counts. DPL compares positive-label proportions: DPL = q<sub>a</sub> − q<sub>d</sub>. Needed for label bias / demographic parity check.</p>
    <p><b>Options</b></p>
    <ul>
      <li>SQL in Athena – possible but no standard metric name or Clarify integration.</li>
      <li>Clarify DPL metric – purpose-built, returns value in [−1, +1], documented interpretation.</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    Clarify DPL: + exam-aligned, reusable in Model Monitor bias drift; − requires facet and label configuration.<br>
    Custom SQL: + flexible; − not standardized for AWS audits.</p>
    <p><b>Final verdict</b><br>
    Run Clarify with <code>DPL</code> (and optionally CDD). If |DPL| &gt; threshold, apply re-weighting or resampling before training. Clarify is the required tool for MLA-C01 bias questions.</p>
  </details>
</details>

  <summary><b>Scenario 3: Choosing a Strategy to Fix Severe Class Imbalance in Tabular Data</b></summary>
  <p>After Clarify reports CI = 0.92 on a 5 GB numeric dataset, the engineer must balance classes. Constraints: keep all real minority samples, run on a budget, no external GPU for GANs, pipeline must be SageMaker-native.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    Strategies: random oversampling, undersampling, SMOTE-style synthetic, class weights.</p>
    <p><b>Options &amp; trade-offs</b></p>
    <ul>
      <li><b>Random undersampling majority</b> – loses information, fast, cheap.</li>
      <li><b>Random oversampling minority</b> – duplicates, risk of overfitting, simple.</li>
      <li><b>SMOTE / synthetic (imblearn in Processing job or Data Wrangler)</b> – generates new minority points, preserves all real data, moderate compute.</li>
      <li><b>Class weights in estimator</b> – no data change, but does not fix bias metrics upstream.</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    Synthetic (SMOTE): + keeps all real samples, improves CI/DPL; − slight distribution shift risk, extra Processing time.<br>
    Undersampling: + fastest; − discards majority signal (usually rejected when minority is tiny).</p>
    <p><b>Final verdict</b><br>
    Use SageMaker Processing (or Data Wrangler) with SMOTE-style synthetic generation for the minority class, then re-run Clarify to confirm CI near 0. Prefer synthetic over pure undersampling when data volume permits and all real minority examples must be retained.</p>
  </details>
</details>

  <summary><b>Scenario 4: Addressing Class Imbalance in an Image Dataset</b></summary>
  <p>A computer-vision model for rare defect detection has 2 000 defective vs 80 000 normal images. CI is extreme. Team cannot collect more real defects; GPU time is limited; must stay on AWS.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    Image-specific strategies: geometric/color augmentation, generative synthetic images, oversampling with augmentation.</p>
    <p><b>Options</b></p>
    <ul>
      <li>Heavy online augmentation only (Albumentations / torchvision in training script) – cheap, but Clarify still sees original CI.</li>
      <li>Offline augmentation + oversampling to disk (SageMaker Processing) – materializes balanced set, Clarify can re-measure.</li>
      <li>GAN-based synthetic (e.g., StyleGAN on SageMaker) – highest fidelity, expensive, complex.</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    Offline augmentation + oversample: + simple, deterministic, Clarify-friendly, low extra cost; − storage growth.<br>
    GAN: + realistic; − high cost, mode-collapse risk, overkill for associate level.</p>
    <p><b>Final verdict</b><br>
    Use SageMaker Processing to apply domain-appropriate augmentation (flip, rotate, brightness, elastic) and write a balanced training set (or use weighted sampling). Re-validate with Clarify. GAN only if realism is a hard requirement and budget exists. Exam prefers augmentation + resampling for images.</p>
  </details>
</details>

  <p>A multi-class NLP intent dataset has one intent with only 120 examples while others have 5 000+. Model is BERT-based on SageMaker. Need to improve CI without changing the label taxonomy.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    Text strategies: back-translation, synonym replacement, Easy Data Augmentation (EDA), oversampling, synthetic with LLMs.</p>
    <p><b>Options</b></p>
    <ul>
      <li>Simple random oversampling of minority texts – easy, risk of overfitting.</li>
      <li>EDA / synonym / back-translation in Processing job – creates lexical diversity.</li>
      <li>LLM-based paraphrasing (Bedrock or SageMaker JumpStart) – high quality, higher cost/latency.</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    EDA in Processing: + cheap, controllable, offline; − limited semantic diversity.<br>
    LLM paraphrase: + better variety; − cost, possible label drift, more moving parts.</p>
    <p><b>Final verdict</b><br>
    Start with SageMaker Processing implementing EDA or back-translation to oversample the minority class until CI is acceptable; re-run Clarify. Escalate to Bedrock paraphrasing only if quality metrics still fail. Associate exam expects augmentation/resampling, not full generative pipelines.</p>

    Use <b>AWS Glue DataBrew</b> for profiling, missing-value analysis, and lightweight quality rules when the primary users are analysts or when visual exploration is required. Use Glue Data Quality when the check must be an enforceable step inside a Glue ETL job. For this scenario DataBrew is the correct first choice.</p>

      <li>Glue Data Quality ruleset attached to the ETL job or Data Catalog – native, can stop the job, identifies failing rows.</li>

    <p><b>Final verdict</b><br>
    Author a DQDL ruleset (Completeness, Uniqueness, ColumnValues, etc.) and evaluate it inside the Glue ETL job. Configure the job to fail when the quality score is below threshold. This is the production pattern expected on the exam.</p>

  <summary><b>Scenario 8: Choosing Encryption for ML Training Data Containing PII</b></summary>
  <p>A healthcare analytics team stores patient features in S3. Compliance requires customer-managed keys, key rotation, and CloudTrail logging of key usage. Data is used by SageMaker training jobs in the same Region.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    SSE-S3 (AWS managed) vs SSE-KMS (customer managed CMK) vs client-side.</p>
    <p><b>Options &amp; trade-offs</b></p>
    <ul>
      <li><b>SSE-S3</b> – default, no extra cost, no key control or detailed usage audit.</li>
      <li><b>SSE-KMS with customer-managed CMK</b> – full control, automatic rotation, CloudTrail key events, IAM condition keys, works natively with SageMaker.</li>
      <li><b>Client-side encryption</b> – maximum control, but breaks S3 Select, Inventory, many AWS integrations, higher app complexity.</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    SSE-KMS CMK: + meets HIPAA/PII key-management requirements, seamless SageMaker; − small KMS API cost + request rate limits (mitigated by bucket keys).<br>
    SSE-S3: + simplest; − fails compliance that demands customer-managed keys.</p>
    <p><b>Final verdict</b><br>
    Use <b>SSE-KMS with a customer-managed CMK</b> (enable S3 Bucket Keys to reduce KMS costs). Grant the SageMaker execution role <code>kms:Decrypt</code>. This satisfies encryption, audit, and rotation needs while remaining fully managed.</p>
  </details>
</details>

  <summary><b>Scenario 12: Identifying and Mitigating Selection Bias</b></summary>
  <p>Clarify shows that a credit dataset under-represents young adults (selection bias). The model will be used for all age groups. Business wants mitigation before training.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    Selection bias = non-representative sampling. Mitigations: re-collect, re-weight, oversample under-represented facet, stratified sampling.</p>
    <p><b>Options</b></p>
    <ul>
      <li>Re-weight samples (Clarify or Processing) – keeps all data, adjusts loss.</li>
      <li>Oversample under-represented group (with synthetic if needed).</li>
      <li>Collect more data – ideal but slow/expensive.</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    Re-weighting / oversampling: + immediate, pipeline-friendly; − may not capture true distribution if missing population differs systematically.<br>
    New collection: + gold standard; − time and cost.</p>
    <p><b>Final verdict</b><br>
    Use Clarify to quantify CI/DPL, then apply SageMaker Processing to oversample or re-weight the under-represented facet. Document the mitigation. Re-measure bias metrics. This is the practical associate-level response when new data collection is not feasible.</p>
  </details>
</details>

  <p>An imbalanced medical dataset must be split into train/validation/test. Random split risks putting almost no positive cases into validation, causing unreliable metrics and hidden bias.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    Need splits that preserve class and protected-attribute distributions → stratified split.</p>
    <p><b>Options</b></p>
    <ul>
      <li>sklearn train_test_split(stratify=…) inside Processing or Data Wrangler.</li>
      <li>SageMaker built-in algorithms’ automatic split (limited control).</li>
      <li>Random split – rejected because of variance and bias risk.</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    Stratified: + stable metrics, fairer evaluation; − slightly more code.<br>
    Random: + simplest; − high risk of empty minority folds.</p>
    <p><b>Final verdict</b><br>
    Perform stratified splitting on both the target label and key demographic facets inside a SageMaker Processing job (or Data Wrangler). Shuffle within strata. This directly reduces prediction bias evaluation errors and is the expected technique.</p>

  <summary><b>Scenario 15: Using Shuffling and Augmentation to Reduce Prediction Bias</b></summary>
  <p>A vision model trained on images sorted by hospital ID learns spurious correlations (hospital-specific artifacts). Validation performance collapses on new hospitals.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    Order bias + domain shift → shuffle + strong augmentation + possibly domain-robust splits.</p>
    <p><b>Actions</b></p>
    <ul>
      <li>Fully shuffle the dataset before splitting (Processing job).</li>
      <li>Apply aggressive but realistic augmentation (color jitter, noise, affine) during training or offline.</li>
      <li>Optional: group-aware split so no hospital appears in both train and test (if leakage is the issue).</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    Shuffle + augmentation: + cheap, effective against order and superficial bias; − does not fix fundamental selection bias across hospitals.<br>
    Hospital-grouped split: + true generalization test; − smaller effective train set.</p>
    <p><b>Final verdict</b><br>
    Always shuffle, apply domain-appropriate augmentation, and prefer group-aware splits when a confounding variable (hospital) exists. These steps are explicitly listed in the exam guide for reducing prediction bias.</p>
  </details>

<details>
  <summary><b>Scenario 16: Minimizing Training Startup Overhead for Multi-Terabyte Datasets</b></summary>
  <p>An ML engineer is training a computer vision model in Amazon SageMaker using a 2 TB dataset stored as millions of small JPEG files in an S3 bucket. The current training job uses SageMaker File mode, but it spends over 30 minutes downloading data to the local EBS volume before training begins. Startup time must be reduced; random access is required.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    File mode copies everything first → slow for TB-scale or many small files. Alternatives: FastFile, Pipe, FSx for Lustre, EFS.</p>
    <p><b>Options &amp; trade-offs</b></p>
    <ul>
      <li><b>File mode</b> – simple, full local copy; − long startup, needs huge EBS.</li>
      <li><b>FastFile mode</b> – POSIX view of S3, streams on demand, no full download; excellent for large files, good for many files.</li>
      <li><b>Pipe mode</b> – legacy streaming, single-process, largely replaced by FastFile.</li>
      <li><b>FSx for Lustre (linked to S3)</b> – high IOPS, low latency after cache warm-up, ideal for millions of small files; − setup overhead, cost.</li>
      <li><b>EFS</b> – only if data already lives on EFS; lower throughput than Lustre for training.</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    FastFile: + zero code change for most frameworks, no startup copy, no extra file-system cost; − first-epoch cold reads from S3.<br>
    FSx for Lustre: + best sustained random I/O for small files; − provisioning time, hourly cost, VPC required.</p>
    <p><b>Final verdict</b><br>
    Switch to <b>FastFile mode</b> first (simplest win). If profiling still shows I/O bottleneck on millions of tiny JPEGs, deploy an S3-linked <b>FSx for Lustre</b> file system and mount it. Avoid classic File mode for multi-TB or many-small-file workloads.</p>
  </details>
</details>

  <summary><b>Scenario 17: Choosing FSx for Lustre vs EFS for High-Throughput Training</b></summary>
  <p>A distributed training job on 16 p4d instances needs &gt; 100 GB/s aggregate throughput to millions of small TFRecord shards. Data currently sits in S3. The cluster runs for several days with repeated epochs.</p>
  <hr>
  <details>
    <summary><b>Solution</b></summary>
    <p><b>Decision process</b><br>
    Throughput + small-file random I/O + multi-instance → FSx for Lustre is purpose-built. EFS is general-purpose NFS.</p>
    <p><b>Comparison</b></p>
    <ul>
      <li><b>FSx for Lustre</b> – hundreds of GB/s, millions IOPS, lazy-load from S3, POSIX, native SageMaker mount.</li>
      <li><b>Amazon EFS</b> – elastic, good for shared home dirs or moderate I/O; General Purpose or Max I/O modes still far below Lustre for this scale.</li>
      <li><b>FastFile</b> – may saturate S3 request rates with extreme multi-node small-file access.</li>
    </ul>
    <p><b>Pros / Cons</b><br>
    FSx Lustre: + performance king for this pattern; − cost while provisioned, cold-start lazy load on first epoch.<br>
    EFS: + simpler pricing, no capacity planning; − insufficient throughput/IOPS.</p>
    <p><b>Final verdict</b><br>
    Create an S3-linked FSx for Lustre file system sized for the working set, mount it read-only on the training jobs. Warm the cache with a first epoch or hsm restore if needed. EFS is inappropriate for this performance tier.</p>
  </details>

    </ol>

    Each service is the purpose-built, exam-aligned tool for its concern. FastFile/FSx addresses the loading skill; Clarify + resampling address bias; DataBrew/Glue DQ + Macie + KMS address integrity, privacy, and compliance.</p>
    <p><b>Final verdict</b><br>
    The pipeline above satisfies every bullet in Task 1.3 knowledge and skills while remaining serverless/managed and auditable. Prefer FastFile unless profiling demands FSx.</p>

      <li>Encryption &amp; residency: SSE-KMS CMK, single Region.</li>
    </ul>
    <p><b>Final verdict</b><br>
    Redact → quality/bias gate with DataBrew/Clarify → write balanced redacted dataset to S3 (KMS) → link FSx for Lustre → mount on training jobs. This simultaneously satisfies compliance, fairness, data integrity, and performance constraints—the full scope of Task 1.3.</p>

### Quick Exam Cheat-Sheet

| Need | First Choice | When to Prefer Alternative |
|------|--------------|---------------------------|
| Pre-training bias metrics | SageMaker Clarify (CI, DPL…) | — |
| Fix CI (tabular) | Processing + SMOTE / oversample | Class weights if data immutable |
| Fix CI (image/text) | Augmentation + oversample | GAN / LLM only if quality demands |
| Visual data quality | Glue DataBrew | — |
| Enforceable ETL quality gates | Glue Data Quality (DQDL) | — |
| PII discovery | Amazon Macie | Comprehend / Glue for custom |
| Masking / anonymization | DataBrew or Processing | — |
| Encryption + key control | SSE-KMS customer CMK | SSE-S3 only if no key-control req |
| Data residency | Single-Region CMK + SCPs | — |
| TB-scale, fast startup | FastFile mode | FSx for Lustre (many small files / extreme IOPS) |
| Data already on shared FS | EFS mount | — |
| Highest training I/O | FSx for Lustre | — |
| Reduce prediction bias | Stratified split + shuffle + augmentation | — |

**Remember**: Always measure bias with Clarify **before** training, enforce quality gates, encrypt with the right KMS key, strip or mask sensitive data, and choose the data-loading mechanism that eliminates unnecessary startup copy while meeting I/O needs. That combination is Task 1.3 in a nutshell.
