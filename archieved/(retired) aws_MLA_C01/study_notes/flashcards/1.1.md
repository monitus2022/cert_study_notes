# Task 1.1 flashcards

<details>
  <summary><b>Scenario 1: Minimizing Training Startup Overhead for Multi-Terabyte Datasets</b></summary>
  <p>An ML engineer is training a computer vision model in Amazon SageMaker using a 2 TB dataset stored as millions of small JPEG files in an S3 bucket. The current training job uses SageMaker <code>File</code> mode, but it spends over 30 minutes downloading data to the local EBS volume before training begins. The team wants faster job startup while still supporting random access patterns required by the custom PyTorch DataLoader.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong> SageMaker offers three primary input modes: File, Pipe, and FastFile.</p>
    <ul>
      <li><strong>File mode</strong>: Downloads entire dataset to EBS before training. Pros – simple, full random access, works with all algorithms. Cons – high startup latency and EBS storage cost for multi-TB data.</li>
      <li><strong>Pipe mode</strong>: Streams data via FIFO. Pros – near-zero startup, lower storage cost. Cons – sequential only, limited algorithm support, no random access (breaks many DataLoaders).</li>
      <li><strong>FastFile mode</strong>: FUSE-based POSIX mount that streams objects on-demand from S3. Pros – supports random access, minimal startup overhead, works with most frameworks. Cons – slightly higher per-read latency than local disk after full download.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Switch to <strong>FastFile mode</strong>. It eliminates the 30-minute download while preserving random access needed by the DataLoader. For even higher throughput on repeated runs, pair with FSx for Lustre later, but FastFile is the immediate Associate-level fix.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 2: Choosing Columnar Format for Analytical Feature Queries</b></summary>
  <p>A data scientist frequently runs Athena and SageMaker Data Wrangler queries that select only 5–10 columns out of a 200-column customer dataset (several hundred GB). The data currently sits in CSV. Queries are slow and expensive. The team needs a format that supports predicate and projection pushdown.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li><strong>CSV / JSON</strong>: Row-oriented, human-readable. Pros – easy to inspect. Cons – full scans, no compression efficiency, high I/O and cost.</li>
      <li><strong>Apache Avro</strong>: Row-oriented, schema evolution friendly. Good for streaming write-heavy workloads, poor for selective column reads.</li>
      <li><strong>Apache ORC / Parquet</strong>: Columnar, highly compressed, support predicate/projection pushdown. Parquet has broader AWS ecosystem support (Athena, Glue, SageMaker, Spark).</li>
      <li><strong>RecordIO-Protobuf</strong>: Optimized for SageMaker built-in algorithms, not general analytics.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Convert to <strong>Apache Parquet</strong> (Snappy or ZSTD compression). It delivers the best balance of query performance, cost, and compatibility with Athena, Data Wrangler, and Glue for this analytical access pattern.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 3: High-Throughput Shared Storage for Distributed GPU Training</b></summary>
  <p>An ML team runs distributed training jobs across 32 p4d instances that all need to read the same 8 TB image dataset repeatedly. Current S3 + FastFile setup saturates and becomes the bottleneck. They need POSIX semantics and very high aggregate throughput.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li><strong>Amazon S3 + FastFile</strong>: Cheap, scalable. Cons – object-storage latency and request-rate limits under extreme parallel reads.</li>
      <li><strong>Amazon EFS</strong>: Fully managed NFS, elastic. Pros – simple sharing for notebooks. Cons – throughput scales with size or provisioned mode but still far below Lustre for HPC/ML (single-digit to low hundreds MB/s).</li>
      <li><strong>Amazon FSx for Lustre</strong>: Parallel file system designed for HPC/ML. Pros – hundreds of GB/s aggregate, sub-ms latency, native S3 repository integration (lazy-load or hydrate). Cons – higher cost, must manage capacity.</li>
      <li><strong>FSx for NetApp ONTAP</strong>: Enterprise NAS features (multi-protocol, snapshots). Better for mixed Linux/Windows or lift-and-shift, not peak ML training throughput.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Deploy <strong>Amazon FSx for Lustre</strong> linked to the S3 data repository. It is the clear choice for multi-node GPU training that repeatedly reads the same large dataset.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 4: Real-Time Feature Ingestion vs Batch Archive</b></summary>
  <p>A fraud-detection system must compute sliding-window aggregates (last 5 minutes of transactions) and write them to SageMaker Feature Store Online Store with &lt;1 s latency. At the same time the raw events must be durably archived in S3 for retraining. The team is evaluating Kinesis services.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li><strong>Amazon Data Firehose</strong>: Fully managed delivery to S3/Redshift. Pros – zero consumer code, automatic format conversion (JSON→Parquet). Cons – minimum buffering ~60 s, no sub-second fan-out or custom logic.</li>
      <li><strong>Amazon Kinesis Data Streams (KDS)</strong>: Real-time stream with multiple consumers, enhanced fan-out, replay. Pros – sub-second latency. Cons – you manage scaling and consumers.</li>
      <li><strong>Amazon Managed Service for Apache Flink</strong>: Stateful stream processing (windows, joins). Ideal for the 5-minute aggregates.</li>
      <li><strong>Amazon MSK</strong>: When existing Kafka ecosystem or exactly-once Kafka semantics are required.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Use <strong>Kinesis Data Streams → Managed Flink</strong> for real-time feature computation into Feature Store, and a parallel <strong>Firehose</strong> delivery stream (or Flink sink) for cost-effective S3 archival. This satisfies both latency and durability requirements.</p>
  </details>
</details>

  <p>An ML engineer needs to prepare a training set that combines CSV files in S3, relational data in Amazon RDS (PostgreSQL), and NoSQL clickstream data in DynamoDB. They want a visual, low-code experience inside SageMaker Studio.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li>Direct SDK / boto3 extraction – full control but high code overhead.</li>
      <li>AWS Glue crawlers + ETL jobs – powerful for large-scale merges, but heavier operationally.</li>
      <li>SageMaker Data Wrangler – native connectors for S3, Athena, Redshift, Feature Store, and (via Athena or direct) RDS/DynamoDB through appropriate drivers or federated queries. Provides visual transforms, join, and export to Feature Store or S3.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Use <strong>SageMaker Data Wrangler</strong> with its built-in S3 connector, Athena (for RDS via Glue Data Catalog or federated query), and DynamoDB connector (or export-to-S3 first). This is the Associate-level recommended path for interactive data preparation and joining multiple sources.</p>

<details>
  <summary><b>Scenario 6: Cost-Effective Storage for Infrequently Accessed Training Archives</b></summary>
  <p>A company keeps 50 TB of historical training data that is used only once every 3–6 months for model re-training or audit. Current S3 Standard storage bill is high. Retrieval time of a few hours is acceptable.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li><strong>S3 Standard</strong>: Immediate access, highest cost.</li>
      <li><strong>S3 Standard-IA / One Zone-IA</strong>: Lower cost, ms retrieval, minimum 30-day charge.</li>
      <li><strong>S3 Glacier Instant Retrieval</strong>: ms access, cheaper than IA for rarely accessed data.</li>
      <li><strong>S3 Glacier Flexible Retrieval / Deep Archive</strong>: Minutes-to-hours retrieval, lowest cost. Ideal when hours of delay are tolerable.</li>
      <li><strong>EBS Snapshots or EFS</strong>: Far more expensive for cold archives.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Transition the dataset to <strong>S3 Glacier Flexible Retrieval</strong> (or Deep Archive if 12-hour retrieval is fine). Use S3 Lifecycle policies. This optimizes cost while meeting the infrequent-access pattern.</p>
  </details>
</details>

<details>
  <summary><b>Scenario 7: Handling Small-File Problem Before Training</b></summary>
  <p>A computer-vision dataset consists of 40 million individual 50 KB PNG files in S3. Listing and opening each object during training causes massive request overhead and slow epochs even with FastFile mode. The team needs a better packaging strategy.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li>Keep millions of small objects – simple but suffers from S3 LIST/GET rate limits and high latency.</li>
      <li>WebDataset / tar shards or TFRecord / RecordIO – pack thousands of images per file. Pros – sequential reads, far fewer requests. Cons – less flexible random access unless indexed.</li>
      <li>Apache Parquet with binary columns – good for mixed tabular+image, but heavier for pure image pipelines.</li>
      <li>FSx for Lustre with data repository – helps throughput but does not solve the small-file metadata problem as elegantly as sharding.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Repackage into <strong>sharded tar files (WebDataset style) or RecordIO/TFRecord</strong> and store in S3. Combine with FastFile or FSx for Lustre. This is the standard high-performance pattern for large image/video datasets on SageMaker.</p>
  </details>
</details>

  <summary><b>Scenario 8: Low-Latency Online Feature Serving Storage</b></summary>
  <p>A real-time recommendation model needs to look up user and item features with single-digit millisecond latency at 10 000 QPS. Features are updated both in batch (daily) and via streaming. The team is choosing the backing store for SageMaker Feature Store Online Store.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li>SageMaker Feature Store Online Store is backed by <strong>DynamoDB</strong> (low-latency key-value). Offline Store uses S3 + Glue Catalog.</li>
      <li>Alternatives: self-managed Redis/ElastiCache (more ops), Aurora (higher latency for pure KV), S3 (too slow for online).</li>
    </ul>
    <p><strong>Pros of Feature Store + DynamoDB</strong>: fully managed consistency between online/offline, point-in-time recovery, IAM integration, automatic scaling.<br>
    <strong>Cons</strong>: cost at very high QPS if not using on-demand carefully; eventual consistency options must be understood.</p>
    <p><strong>Final Verdict:</strong> Use <strong>SageMaker Feature Store</strong> (Online Store). It abstracts DynamoDB and is the exam-preferred solution for low-latency feature serving with unified online/offline governance.</p>
  </details>
</details>

  <summary><b>Scenario 9: Merging Multi-Source Data at Scale with Glue and Spark</b></summary>
  <p>An ML pipeline must join 2 TB of clickstream Parquet data in S3 with 500 GB of customer dimension data in Redshift and 100 GB of product attributes in DynamoDB every night. The joined result feeds SageMaker training. Runtime must finish in under 2 hours.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li>Python pandas / single SageMaker Processing job – will not scale to multi-TB joins.</li>
      <li>Amazon Athena – good for ad-hoc, less ideal for complex multi-source ETL with tight SLAs.</li>
      <li>AWS Glue (Spark) ETL jobs – serverless Spark, native connectors to S3, Redshift, DynamoDB (via connector), automatic scaling, job bookmarks.</li>
      <li>Amazon EMR – more control, higher ops overhead.</li>
      <li>SageMaker Data Wrangler – interactive, not designed for 2 TB nightly production joins.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Build an <strong>AWS Glue Spark ETL job</strong> (or Glue Studio visual job). Use Glue Data Catalog, dynamic frames or Spark DataFrames for the joins, write Parquet output to S3, then register for SageMaker. This is the standard scalable merge pattern.</p>
  </details>
</details>

  <summary><b>Scenario 10: Accelerating Cross-Region Dataset Transfer</b></summary>
  <p>A global team stores a 15 TB training dataset in S3 us-east-1. Training clusters are frequently launched in eu-west-1. Copy times using the AWS CLI are unacceptably long and the team wants a managed acceleration option.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li>Standard S3 cross-region COPY / aws s3 sync – uses public internet, subject to variable bandwidth.</li>
      <li><strong>S3 Transfer Acceleration</strong> – uses CloudFront edge locations to speed uploads/downloads. Pros – simple bucket-level enablement. Cons – still object-by-object, extra cost, best for long-distance clients.</li>
      <li>S3 Cross-Region Replication (CRR) – automatic, continuous; good for keeping a warm copy.</li>
      <li>AWS DataSync – scheduled or on-demand high-throughput transfer between S3 buckets or to FSx/EFS, with bandwidth control and verification.</li>
      <li>Snowball / Snowmobile – only for initial petabyte migration.</li>
    </ul>
    <p><strong>Final Verdict:</strong> For repeated on-demand transfers enable <strong>S3 Transfer Acceleration</strong> or, better for large recurring datasets, configure <strong>S3 CRR</strong> plus <strong>DataSync</strong> for controlled syncs. Transfer Acceleration is the quickest Associate-level answer when the stem mentions “accelerate transfers to S3 over long distances.”</p>
  </details>

  <summary><b>Scenario 11: Provisioning IOPS for High-Performance Local Training Disk</b></summary>
  <p>A SageMaker training job on a single large instance performs heavy random reads and writes of intermediate checkpoints and a memory-mapped dataset on the local volume. The default gp3 EBS volume is throttling. The job needs consistent high IOPS.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li>Default SageMaker EBS (gp3) – baseline 3000 IOPS, burstable.</li>
      <li><strong>Provisioned IOPS SSD (io1/io2)</strong> – set exact IOPS (up to 64 000+), consistent performance, higher cost.</li>
      <li>Instance store (NVMe) – extremely fast but ephemeral; data lost on stop/terminate. Available on certain instance families (e.g., g5, p4d local disks).</li>
      <li>EFS / FSx – shared, not local-attached latency.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Attach an <strong>Amazon EBS io2 Block Express</strong> (or io1) volume with provisioned IOPS when the workload needs durable, consistent high IOPS on a single instance. Prefer instance-store NVMe when the instance type offers it and durability of the scratch space is not required.</p>
  </details>
</details>

  <summary><b>Scenario 12: Choosing Between EFS and FSx for NetApp ONTAP for Shared Notebook Storage</b></summary>
  <p>A team of 20 data scientists uses SageMaker Studio and needs a shared home directory for notebooks, scripts, and small-to-medium datasets (&lt;1 TB total). They also want Windows-based legacy tools to access the same files via SMB and the ability to create snapshots.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li><strong>Amazon EFS</strong>: Serverless NFS, elastic, great for Linux SageMaker Studio home directories. Pros – simple, pay-for-use. Cons – no native SMB, limited enterprise snapshot/clone features.</li>
      <li><strong>Amazon FSx for NetApp ONTAP</strong>: Full ONTAP experience – NFS + SMB, multi-protocol, FlexClone, snapshots, compression, deduplication. Pros – enterprise features, multi-OS. Cons – more expensive, capacity planning required.</li>
      <li><strong>FSx for Lustre</strong>: Overkill and wrong protocol set for interactive notebook home dirs.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Choose <strong>Amazon FSx for NetApp ONTAP</strong> because the requirements explicitly include SMB access and snapshot capabilities. Pure Linux Studio-only workloads would prefer EFS for simplicity and cost.</p>
  </details>
</details>

    <p><strong>Final Verdict:</strong> Use <strong>Amazon Data Firehose</strong> with enabled data format conversion to Parquet and dynamic partitioning. This is the classic low-code pattern for turning streaming JSON into analytics-ready columnar data for ML.</p>

  <summary><b>Scenario 14: Troubleshooting S3 Request-Rate Throttling During Distributed Training</b></summary>
  <p>A distributed training job across 50 instances suddenly receives elevated 503 Slow Down errors when reading a dataset of 5 million small objects from a single S3 prefix. Training throughput collapses.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process / Root Causes:</strong></p>
    <ul>
      <li>S3 prefix request-rate limits (historically ~3 500–5 500 GET/s per prefix).</li>
      <li>Too many tiny files.</li>
      <li>Lack of randomization in key names or sequential listing.</li>
    </ul>
    <p><strong>Remediation options:</strong></p>
    <ul>
      <li>Re-shard / pack into larger files (RecordIO, tar, Parquet).</li>
      <li>Distribute keys across many prefixes (hash-based).</li>
      <li>Use S3 Express One Zone for ultra-high request rates (if latency-critical and same AZ).</li>
      <li>Switch to FSx for Lustre with S3 repository so metadata and data are cached on the parallel file system.</li>
      <li>Enable S3 Transfer Acceleration only helps long-distance, not request-rate.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Immediate mitigation – reduce object count by packaging and spread keys across prefixes. Long-term best practice for this scale – <strong>FSx for Lustre</strong> or heavily sharded files + FastFile. This tests troubleshooting capacity and scalability knowledge.</p>
  </details>
</details>

  <summary><b>Scenario 15: Validated vs Non-Validated Data Formats in SageMaker</b></summary>
  <p>A team is deciding how to feed data to a SageMaker built-in XGBoost algorithm. They can use CSV or the proprietary RecordIO-Protobuf format. They also wonder when to use a “validated” channel.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li><strong>CSV</strong>: Human-readable, easy debugging. Cons – slower parsing, larger size, no sparse support.</li>
      <li><strong>RecordIO-Protobuf</strong>: Dense or sparse binary format optimized for SageMaker built-in algorithms. Faster I/O, lower size, required for some pipe-mode optimizations.</li>
      <li>Validated vs non-validated channels: SageMaker can run a validation channel in parallel for early stopping / hyperparameter tuning metrics. The format must be understood by the algorithm.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Prefer <strong>RecordIO-Protobuf</strong> for production XGBoost/Linear Learner jobs (especially with Pipe mode). Keep a CSV version for Data Wrangler exploration. Always supply a separate validated channel when using Automatic Model Tuning or early stopping.</p>
  </details>
</details>

  <summary><b>Scenario 16: Ingesting Data into SageMaker Feature Store from Multiple Sources</b></summary>
  <p>Daily batch features are computed by a Glue job and must land in both Feature Store Offline (S3) and Online (low-latency) stores. In addition, real-time events must upsert a subset of features within seconds.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li>Feature Store Ingestion APIs / PutRecord – for low-volume or streaming.</li>
      <li>Feature Store batch ingestion (via DatasetBuilder, Data Wrangler export, or Spark connector) – efficient for large daily loads; writes to Offline store and can sync to online.</li>
      <li>Streaming path: Kinesis → Flink or Lambda → Feature Store PutRecord for online-only low-latency updates.</li>
      <li>Direct S3 write bypasses Feature Store governance and is not recommended.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Use <strong>batch data ingestion</strong> (Glue/Spark → Feature Store) for the daily load into both stores, and a <strong>Kinesis + Lambda/Flink streaming path</strong> for real-time online upserts. This is the canonical dual online/offline pattern.</p>
  </details>

  <summary><b>Scenario 17: Storage Decision Based on Data Structure and Access Pattern</b></summary>
  <p>An ML feature set is highly nested JSON (user profiles with arrays of maps). It is written once per day and read by Spark jobs that need to explode nested fields. The team must choose storage format and location.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li>Raw JSON in S3 – flexible but slow and expensive to query repeatedly.</li>
      <li>Flatten to relational tables in RDS/Redshift – loses flexibility of nested schema, higher cost.</li>
      <li>Apache Avro – excellent schema evolution and nested support, row-oriented (good for full-record writes).</li>
      <li>Parquet with nested types (or exploded columns) – best analytical read performance.</li>
      <li>DynamoDB – great for key-value nested items but expensive for full scans by Spark.</li>
    </ul>
    <p><strong>Final Verdict:</strong> Land as <strong>Parquet</strong> (preserving nested structure or selectively exploding) in <strong>S3</strong>. Use Glue Catalog for schema. This gives the best cost/performance for Spark/Athena access patterns on nested data.</p>
  </details>

  <summary><b>Scenario 18: Extracting Data from RDS and DynamoDB for ML</b></summary>
  <p>A fraud model needs a one-time extract of 1 TB from Amazon RDS MySQL (complex joins) and 200 GB of recent items from DynamoDB. The extract must land in S3 as Parquet with minimal impact on production databases.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Decision Process:</strong></p>
    <ul>
      <li>RDS: Use AWS DMS (CDC or full load), Glue JDBC connection with Spark, or RDS export to S3 (for supported engines). Avoid long-running SELECT * from application instances.</li>
      <li>DynamoDB: Use DynamoDB Export to S3 (point-in-time, no capacity consumption), or Glue DynamoDB connector / EMR, or parallel Scan with controlled RCU.</li>
      <li>Direct Lambda/boto3 – not scalable for TB-scale.</li>
    </ul>
    <p><strong>Final Verdict:</strong> <strong>RDS → AWS DMS or Glue JDBC Spark job</strong>; <strong>DynamoDB → native Export to S3</strong>. Both land in S3; a subsequent Glue job converts/merges to Parquet. This minimizes production impact and follows AWS best practices.</p>
  </details>

This preserves code investment while meeting AWS streaming requirements.</p>

  <summary><b>Scenario 20: Holistic Storage Selection for Hybrid Batch + Streaming ML Pipeline</b></summary>
  <p>Design the storage and ingestion layer for an ML platform that must support: (a) nightly 10 TB batch training on GPU clusters, (b) continuous streaming feature updates at 50 000 events/s, (c) interactive Data Wrangler exploration by data scientists, and (d) strict cost control for data older than 90 days. Provide the end-to-end component choices and rationale.</p>
  <hr>  
  <details>
    <summary><b>Solution</b></summary>
    <p><strong>Recommended Architecture & Decision Rationale:</strong></p>
    <ul>
      <li><strong>Hot streaming path</strong>: Kinesis Data Streams (or MSK) → Managed Flink → SageMaker Feature Store Online + Firehose → S3 (Parquet, partitioned).</li>
      <li><strong>Batch path</strong>: Raw / cleaned data in S3 (Parquet). Nightly Glue Spark jobs merge sources and write training-ready datasets.</li>
      <li><strong>Training access</strong>: FSx for Lustre (S3 repository) for the multi-TB GPU jobs; FastFile mode for smaller experiments.</li>
      <li><strong>Interactive</strong>: SageMaker Data Wrangler connected to S3 / Feature Store / Athena.</li>
      <li><strong>Shared notebooks</strong>: EFS or FSx for NetApp ONTAP.</li>
      <li><strong>Cold data</strong>: S3 Lifecycle → Glacier Flexible Retrieval after 90 days.</li>
      <li><strong>Local scratch</strong>: Instance store or provisioned IOPS EBS when needed.</li>
    </ul>
    <p><strong>Trade-off Summary:</strong> S3 is the durable system of record (cost-effective, scalable). FSx for Lustre provides the performance tier for training. Kinesis/Flink/Feature Store handle real-time. Glue unifies batch merges. Lifecycle policies enforce cost control. This combination satisfies all performance, cost, and access-pattern constraints at Associate level.</p>
    <p><strong>Final Verdict:</strong> The pipeline above is the canonical, exam-aligned design that demonstrates mastery of Task 1.1 decision making across formats, storage services, streaming, and SageMaker ingestion.</p>
  </details>

- Always map the access pattern first (sequential vs random, batch vs real-time, single-node vs distributed, frequency of access).
- Remember the “performance ladder”: S3 (FastFile) → FSx for Lustre for extreme training throughput; EFS for shared notebooks; FSx for NetApp ONTAP when multi-protocol/enterprise features are required.
- Formats: Parquet for analytics, RecordIO/TFRecord/WebDataset for dense training I/O, Avro for schema-evolution streaming writes.
- Streaming cheat-sheet: Firehose = managed delivery + conversion; KDS = real-time multi-consumer; Flink = stateful windows; MSK = Kafka compatibility.
- Every storage choice on the exam can be justified by **cost, performance, data structure, or operational simplicity**—practice articulating the trade-offs exactly as shown in the solutions above.
