## 1. Foundation Model (FM) Selection Criteria

Choosing the right FM requires balancing technical capabilities against cost and latency constraints.

### Key Selection Criteria
*   **Modality**: Match the input and output types required by the application (Text-to-Text, Text-to-Image, Vision-to-Text, Multi-modal).
*   **Model Size & Complexity**:
    *   *Large Models*: Deliver deep reasoning, complex logic, and high multi-step execution quality, but incur higher token costs and higher latency.
    *   *Small / Compact Models*: Provide sub-second latency and minimal token cost, ideal for simple classification, routing, and entity extraction.
*   **Context Window (Input/Output Length)**: The maximum token limit a model can process in a single request (prompt + completion). Large context windows accommodate big documents but increase cost and Time to First Token (TTFT).
*   **Latency**:
    *   *Time to First Token (TTFT)*: Critical for real-time user-facing applications.
    *   *Token Generation Rate*: Tokens generated per second during response streaming.
*   **Multi-Lingual Support**: Native pre-training capability across non-English languages for global enterprise deployment.
*   **Prompt Caching**: Capability to cache static prompt sections (e.g., system instructions or large reference documents) to reduce input token cost and TTFT by up to 90%.
*   **Cost Model**: Token-based On-Demand pricing vs. fixed Provisioned Throughput capacity.

## 2. Controlling Outputs via Inference Parameters

Inference parameters adjust the mathematical sampling process during token generation without altering the model's underlying weights.

| Inference Parameter | Operational Effect | Recommended Value Settings |
| :--- | :--- | :--- |
| **Temperature** | Controls the degree of randomness/creativity in token selection. Lower values make output more deterministic; higher values make output more random and creative. | • **0.0 - 0.2**: Coding, JSON extraction, factual Q&A, classification.<br>• **0.7 - 1.0**: Creative writing, marketing copy, brainstorming. |
| **Top-P (Nucleus Sampling)** | Considers only the smallest set of top tokens whose cumulative probability reaches value $P$ (e.g., $P = 0.9$ means top 90% probability mass). | • **0.1 - 0.3**: Focused, deterministic responses.<br>• **0.9 - 1.0**: Broader vocabulary and diverse phrasing. |
| **Top-K** | Truncates the token selection pool to strictly the top $K$ most probable next tokens. | • **K = 1 - 10**: Highly predictable output.<br>• **K = 50+**: Higher variability. |
| **Max Length / Max Tokens** | Sets a strict upper bound on the number of tokens the model can generate in the response completion. | Set to prevent run-away generations and cap token generation costs. |
| **Stop Sequences** | Specifies explicit text strings (e.g., `\n`, `User:`, `END`) that instantly halt token generation when produced by the model. | Used in multi-turn chat and structured formatting to prevent model rambling. |

*Note for Exam*: Lowering `Temperature`, `Top-P`, or `Top-K` decreases randomness and increases output determinism. High `Temperature` combined with high `Top-P` increases creativity but raises hallucination risk.

## 3. Retrieval-Augmented Generation (RAG) & Vector Stores

RAG is an architectural pattern that connects an FM to external, private enterprise knowledge sources at query time. It injects retrieved document snippets directly into the prompt context.

### Business Value of RAG
*   Eliminates model hallucinations by grounding answers in verified private data.
*   Provides source citations and transparent lineage for generated facts.
*   Bypasses static model knowledge cutoffs without costly retraining.
*   Enforces data security by filtering retrieved contexts using user IAM permissions.

### Managed RAG on AWS: Amazon Bedrock Knowledge Bases
**Amazon Bedrock Knowledge Bases** provides a fully managed RAG pipeline that automatically handles:
1.  Connecting to data sources (Amazon S3, Confluence, Salesforce, SharePoint).
2.  Parsing and chunking unstructured documents.
3.  Generating vector embeddings using Amazon Titan Embeddings.
4.  Storing and indexing embeddings in a vector database.
5.  Executing vector similarity search and passing context to the FM.

### AWS Services for Storing Embeddings (Vector Databases)

| AWS Vector Store Service | Service Type | Exam Anchor / Best For |
| :--- | :--- | :--- |
| **Amazon OpenSearch Serverless** | Managed Vector Search Engine | Default vector database choice for **Amazon Bedrock Knowledge Bases**. Serverless, high-scale vector indexing. |
| **Amazon Aurora (pgvector)** | Relational Vector Storage | Existing PostgreSQL workloads adding vector search alongside transactional SQL data via `pgvector`. |
| **Amazon RDS for PostgreSQL** | Relational Vector Storage | Managed relational database using `pgvector` extension for combined relational and vector queries. |
| **Amazon Neptune** | Graph Vector Database | Combining Graph Database connections (Knowledge Graphs) with vector similarity search. |
| **Amazon DocumentDB** | NoSQL Vector Database | JSON document store supporting vector search capabilities. |

## 4. FM Customization Spectrum & Cost Trade-Offs

When off-the-shelf prompting is insufficient, organizations customize FMs using techniques along a spectrum of increasing cost, effort, and data requirements.

| Customization Technique | Description | Cost & Effort Level | Primary Use Case |
| :--- | :--- | :--- | :--- |
| **1. In-Context Learning (Prompt Engineering)** | Providing instructions, constraints, and few-shot examples inside the prompt text. | **Lowest Cost & Effort** (Zero training; token usage only) | Adjusting output format, setting persona, guiding simple task logic. |
| **2. Retrieval-Augmented Generation (RAG)** | Dynamically fetching relevant facts from a vector store and passing them into the prompt. | **Low-to-Moderate Cost** (Vector storage + embedding generation) | Grounding answers in dynamic enterprise data; preventing hallucinations. |
| **3. Model Distillation** | Training a smaller, compact "student" model to replicate the outputs of a massive, expensive "teacher" model. | **Moderate Cost** (Inference generation from teacher + fine-tuning student) | Reducing latency and operational token cost for high-volume production apps. |
| **4. Fine-Tuning (Instruction Tuning)** | Updating a pre-trained model's internal weights using a smaller, task-specific labeled dataset. | **High Cost & Effort** (Requires labeled dataset + Bedrock Provisioned Throughput) | Adapting model tone, style, complex domain vocabulary, or specialized formatting. |
| **5. Pre-Training from Scratch** | Training a foundation model from ground zero using massive raw unlabelled datasets. | **Highest Cost & Effort** (Millions of dollars; months of GPU compute) | Building proprietary, highly specialized base models (very rare). |

### RAG vs. Fine-Tuning Key Distinction
*   **Use RAG** when you need to teach the model **NEW FACTS, dynamic information, or private knowledge** with exact citations.
*   **Use Fine-Tuning** when you need to teach the model a **NEW STYLE, tone, specialized output format, or industry terminology** (Fine-tuning does *not* reliably teach models new facts).

## 5. Role of AI Agents & Business Applications

An **AI Agent** uses a Foundation Model as a reasoning engine to break down goals into sub-tasks, execute multi-step workflows, maintain state memory, and call external tools (APIs, databases).

### Key Operational Capabilities
*   **Reasoning & Planning**: Decomposing a user request into logical execution steps (e.g., using the ReAct framework: *Reason $\rightarrow$ Act $\rightarrow$ Observe*).
*   **Tool Invocation (Function Calling)**: Invoking external microservices, database queries, or AWS Lambda functions using OpenAPI schemas.
*   **Memory Management**: Maintaining short-term state across complex multi-turn interactions.

### AWS Agent Solutions
*   **Agents for Amazon Bedrock**: Managed serverless agent orchestrator that links FMs to enterprise data sources (via Knowledge Bases) and executes business logic via **AWS Lambda**.
*   **Amazon Bedrock AgentCore**: Production runtime for deploying, securing, and managing multi-agent enterprise applications.

## 6. Exam Decision Rules & Common Pitfalls

### High-Yield Decision Rules
1.  **Select Temperature = 0.0** whenever an application requires **strictly factual, reproducible, or deterministic JSON/code outputs**.
2.  **Select RAG (Amazon Bedrock Knowledge Bases)** when the requirement is **grounding model answers in private enterprise documents without retraining the model**.
3.  **Select Amazon OpenSearch Serverless** as the default, fully managed vector database for **Amazon Bedrock Knowledge Bases**.
4.  **Select Aurora / RDS PostgreSQL with `pgvector`** when an enterprise wants to **add vector search capabilities to their existing relational SQL database**.
5.  **Select Model Distillation** when an enterprise wants to **lower operational costs and latency by transferring knowledge from a large model to a smaller model**.
6.  **Select Fine-Tuning over RAG** when the business goal is **teaching the model a specific writing style, tone, or complex response schema**.
7.  **Select Agents for Amazon Bedrock** when an application must **autonomously execute multi-step tasks that involve calling AWS Lambda functions or external APIs**.

### Common Exam Traps
*   **Trap 1: Choosing Fine-Tuning to Add Knowledge**
    *   Fine-tuning is ineffective for introducing rapidly changing facts and causes hallucinations. Always choose **RAG** for injecting up-to-date facts.
*   **Trap 2: Confusing Temperature with Top-P**
    *   Both control randomness, but `Temperature` scales output token logits (overall entropy), whereas `Top-P` cuts off the long tail of low-probability tokens.
*   **Trap 3: Forgetting Provisioned Throughput for Fine-Tuned Models**
    *   In Amazon Bedrock, custom fine-tuned models cannot be served via standard On-Demand pricing. They require **Provisioned Throughput**.
